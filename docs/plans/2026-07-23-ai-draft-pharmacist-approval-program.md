# Closed-loop 완성 · AI 초안 약사 승인 · 연구보고서 체계 프로그램

작성일: 2026-07-23. 이 문서는 이번 프로그램의 canonical 지시 문서다. goal 세션은 이 문서의 단계 순서, 확정 설계 결정, 금지 사항을 그대로 따른다. 문체는 `docs/original_plan/research_reports/STYLE_GUIDE.md`를 따른다.

## 이 프로그램이 존재하는 이유

최근 작업이 연구계획서의 중심 줄기에서 벗어나 있었다. 계획서(`docs/context/original_plan.pdf`)와 master context가 정의하는 이 연구의 핵심은 **closed-loop 개인 맞춤 케어**다: 추천하고, 복용시키고, 후속 상태를 다시 보고, 유지·조정·중단을 결정하는 닫힌 루프. 그런데 상태기계는 `FOLLOWUP_ACTIVE`까지만 있고 그 뒤의 "다음 행동 결정"이 없다. 루프가 닫혀 있지 않다. 데이터 가공 작업이 아무리 쌓여도 이 공백은 메워지지 않는다. 이번 프로그램의 최우선 순위는 루프를 닫는 것이다.

## 확정된 설계 결정 — 재논의 금지

아래 결정들은 프로젝트 오너가 이미 내린 결정이다. 구현 중에 "이게 더 낫지 않나", "이런 장치가 필요하지 않나"라는 판단이 들어도 **결정을 바꾸거나 우회 장치를 추가하지 않는다.** 다른 의견이 있으면 코드로 반영하지 말고 작업 로그에 한 줄 메모로 남긴 뒤 결정대로 진행한다.

1. **Closed-loop은 명시적 상태기계다.** 자유형 agent graph, LangGraph류 프레임워크, LLM이 다음 행동을 자유 추론하는 구조는 채택하지 않는다(master_context 13.6장, 19장). 다음 행동은 상태×이벤트→액션 정책 테이블이 결정한다. 이 문제는 open-ended reasoning이 아니라 결정 문제이며, KPI(다음 수행 작업 정확도 80%)도 결정적 로직이 유리하다.
2. **약사 검토에 품질 판정 장치를 두지 않는다.** 승인율, 반려율, 검토 속도를 근거로 실패·경고·차단하는 게이트, 감사 규칙, 테스트를 만들지 않는다. 승인율 100%는 초안 품질이 좋았다는 뜻이지 문제 신호가 아니다. 자문약사는 자기 이름으로 결정하는 외부 전문가이고, 검토 성실성은 자문 계약과 인적 관리의 영역이지 이 시스템의 검증 대상이 아니다. 시스템의 책임은 검토를 빠르게 만들고 건별 결정을 기록하는 데서 끝난다. "모범 사례상 필요해 보인다"는 이유로 이 장치를 추가하는 것이 이 프로그램에서 가장 명확한 지시 위반이다.
3. **검토 UX에 마찰 장치를 두지 않는다.** 확인 팝업, 강제 대기 시간, 스크롤 완독 체크, 재확인 요구를 만들지 않는다. 승인이 기본 동선이고, 정상 초안은 확인 한 번·클릭 한 번으로 끝난다.
4. **보고서 문체는 STYLE_GUIDE.md가 정한다.** 개인 판단으로 형식을 변형하거나, 문체 규칙과 다른 스타일이 낫다고 판단해 바꾸지 않는다.

## 무정지 진행 원칙 — 사람 개입은 마지막에 일괄 처리한다

이 프로그램은 중간에 사람 승인을 기다리며 멈추지 않는다. 사람 판단이 필요해 보이는 지점을 만나면 다음 절차를 따르고 계속 진행한다.

1. `docs/original_plan/human_signoff_checklist.md`에 항목을 추가한다: 무엇이 결정 대상인지, 어떤 기본값(가정)을 택하고 진행했는지, 나중에 사람이 뒤집으면 어떤 산출물을 어떻게 고치면 되는지.
2. 기본값은 다음 우선순위로 고른다: (a) 이 문서의 확정 설계 결정 → (b) master_context의 명시 규칙 → (c) 안전 보수 원칙(모호하면 사용자에게 더 안전한 쪽: 이상사례는 중단, 악화는 재최적화, 불확실하면 추천 보류).
3. 택한 기본값으로 구현·테스트·증거까지 완주한다. "사람 확인 대기"를 이유로 산출물을 미완성으로 두지 않는다.

Phase 1의 중대 어긋남 보고도 같은 방식으로 처리한다. 2026-07-23 정렬 감사가 찾은 중대 어긋남 4건은 모두 "Phase 2를 이 문서의 확정 설계(단일 상태기계 통합, 선언적 정책 파일, 100개 시나리오 평가셋)대로 구현하면 해소되는" 항목이며, 사용자가 이 처리 방침을 승인했다. 따라서 멈추지 말고 Phase 2를 진행한다. 이후 Phase에서도 어긋남·결정 지점은 체크리스트에 적고 기본값으로 진행한다.

**마지막에 사람들이 모여서 하는 일(최종 세션).** 아래는 처음부터 "나중에 이루어진다"고 가정하고 진행한다. Codex는 이 항목들이 없다는 이유로 작업을 멈추거나 단계 주장을 미루지 않되, 보고서에는 미완 상태를 사실대로 남긴다.

- 자문약사: 다음 행동 정책 테이블의 의약학적 타당성 확인, AI 초안 데이터 검토 세션(실제 승인·수정·반려), 검토 화면 실사용.
- 사용자(오너): 재작성된 보고서 톤 확인, 정책 테이블 승인, Vercel 등 운영 환경 설정.
- 외부: OP-039 독립 고위험 검증, 최종 검증 영수증·독립 검토 영수증(Ed25519 서명) 등록.

이 최종 세션 전까지 해당 항목들이 비어 있는 것은 정상 상태이며 차단 사유가 아니다. 각 항목이 준비되는 즉시 체크리스트에서 지울 수 있도록, 체크리스트 항목에는 "무엇을 하면 완료인지"를 한 줄로 적는다.

## 작업 이탈 방지 규칙

- 어떤 작업이든 시작하기 전에 그 작업이 아래 Phase 중 어느 산출물을 전진시키는지 한 줄로 적는다. 어느 산출물에도 매핑되지 않는 작업은 하지 않는다.
- 새 데이터셋 생성, 기존 데이터 재가공, 평가셋 재구성은 Phase 산출물이 명시적으로 요구할 때만 한다. "하는 김에" 데이터를 다듬는 작업은 이탈이다.
- Phase 순서를 건너뛰지 않는다. 특히 Phase 2(closed-loop)를 미루고 다른 Phase를 먼저 진행하지 않는다.
- 각 Phase 종료 시 산출물 목록과 감사 숫자를 대조해 보고한다.

## Phase 2 — Closed-loop 다음 행동 정책 완성 (최우선 구현)

목표: 루프를 닫는다. follow-up 결과가 들어왔을 때 시스템이 다음 행동을 결정하고, 그 결정의 정확도를 측정할 수 있어야 한다.

### 산출물

1. **다음 행동 정책 테이블.** master_context 19.3의 형식(상태×이벤트 조건→액션)을 따르는 선언적 테이블. 액션 후보는 master_context 19.2의 목록(설문 요청, 추가 측정 요청, 안전 검토, 추천 제시, 리마인드, 7일 follow-up, 30일 재평가, 조합 유지, 감량, 교체, 복용 중단, adverse event 경고·종료 등)을 기준으로 한다. 데이터 파일로 선언하고 코드가 읽는다.
2. **정책 엔진.** 기존 `ClosedLoopState`/`BoundedAgent`를 확장해 FOLLOWUP_ACTIVE 이후를 완성한다: follow-up 점수 개선+부작용 없음→유지, 악화→재최적화(감량/교체 포함), adverse event→중단·에스컬레이션. 새 상태기계를 만들지 말고 기존 전이 계약에 상태·전이를 추가한다.
3. **다음 행동 평가셋.** 상태·이벤트·정답 액션으로 구성된 시나리오 100개 이상. 자동 채점기로 "다음 수행 작업 정확도"를 계산한다. 계획서 KPI 목표는 80%다. 시나리오는 결정적이어야 하며 LLM 채점을 쓰지 않는다.
4. **회귀 테스트와 smoke 실행기, 증거 JSON.** 기존 관례(고정 사례 데이터셋 + 결정적 재생기 + `data/original_plan/evidence/` 증거)를 따른다.
5. 이 Phase가 전진시키는 OP를 manifest에서 식별하고(21~22쪽 자가적응형 AI 관련 OP), 해당 연구보고서를 작성·갱신한다.

### 하지 않는 것

새 데이터 수집·재가공, 새 모델 학습, frozen 평가 세트 변경. 정책 엔진은 규칙 기반이며 이 Phase에 LLM 호출이 필요하지 않다.

## Phase 3 — AI 초안 + 약사 승인 데이터 파이프라인

목표: 약사가 만들어야 하는 연구 데이터를 AI가 초안으로 생성하고, 약사는 최종 결정권자로서 확인·수정·승인/반려만 한다. 약사의 건당 처리 시간을 최소로 줄인다.

### 데이터 모델

모든 생성 레코드에 provenance 필드를 남긴다.

- `generation_source`: `"ai_draft"` 고정. 모델 식별자와 프롬프트 버전 포함.
- `review_status`: `pending` | `approved` | `approved_with_edits` | `rejected`
- `reviewer_id`, `reviewed_at`
- `edit_diff`(수정 승인 시), `rejection_reason`(반려 시)

이 기록의 용도는 "이 레코드는 약사가 승인했다"는 사실을 남기는 것 하나다. 검토 소요 시간처럼 결정과 무관한 측정값은 수집하지 않는다. 저장은 기존 interim store를 확장하고, 추가 전용+불변 트리거 패턴을 재사용한다.

### 검토 화면

기존 `PharmacistReviewService`와 OP-106 연동을 확장한다. 초안과 판단 근거를 한 화면에 요약하고, 승인/수정/반려를 원클릭으로, 승인 후 자동으로 다음 건으로 넘어간다. 금기·상호작용·응급 신호 필드는 시각적으로 강조한다. 결정은 건별로 기록한다. 확정 설계 결정 2·3번을 따른다.

### 차단 경계

`approved`/`approved_with_edits` 레코드만 하류(학습 데이터 구성, 평가, 추천, 지식 반영)에서 사용한다. `pending`/`rejected`는 어떤 경로에서도 읽히지 않는다. 하류 소비 함수에 미승인 레코드를 주입하면 실패하는 테스트를 포함한다.

### 검토 기록 요약

보고서 작성용으로 초안 생성·검토 완료·승인·수정·반려 건수만 집계해 증거 JSON으로 남긴다. 용도는 "생성된 초안 전부가 약사 검토를 거쳤다"를 건수로 뒷받침하는 것이다. 이 숫자로 검토 품질을 판정하는 어떤 장치도 만들지 않는다(확정 설계 결정 2번).

### 검증

단위 테스트, 경계 테스트(미승인 하류 차단, 중복 결정 거부), FastAPI 통합 테스트, 결정적 smoke. 단계 주장 규율: 로컬 구현·테스트는 `IMPLEMENTED`, 두 저장소 실제 왕복은 `INTEGRATED`. 실제 약사의 운영 검토 기록 전에는 `OPERATED`를 주장하지 않는다.

## Phase 4 — 기존 연구보고서 정비

모든 작업에 STYLE_GUIDE.md를 적용한다. 순서:

1. **증거 인용 수정.** OP-082, 086, 087, 089~100, 102~106, 118의 22편은 manifest 증거 경로 인용 부재로 감사 실격이다. 본문에 해당 OP의 증거 경로를 문장 안에 자연스럽게 인용한다. OP-117은 의미 범주 미달이므로 한계·검증 서술을 보강한다.
2. **형식 통일.** 제목을 `# OP-NNN <제목>` 단일 형식으로. "연구보고서:", "연구일지:", "—" 변형과 "Reference basis" 꼬리줄 제거.
3. **문체 재작성.** 용어 남발·기계적 문형이 심한 보고서부터 STYLE_GUIDE 기준으로 다시 쓴다. 사실·숫자·경로·단계 주장은 바꾸지 않고 문장만 바꾼다.
4. **스텁 보강.** OP-103~106, 117~119를 문제·판단 근거·실패 과정·한계가 채워지도록 보강한다.

각 단계 후 `scripts/run_final_completion_audit.py`를 실행해 유효 보고서 수가 실제로 올랐는지 확인한다.

## Phase 5 — 미작성 보고서 (OP-023~078, 56편)

증거를 직접 다시 읽으며 소급 작성한다. 완료 숫자를 옮겨 적지 말고 각 OP의 manifest 증거 파일·테스트·커밋을 확인한 뒤 쓴다. 처음부터 STYLE_GUIDE 문체로 쓴다. Phase 2~3에서 구현이 바뀐 OP는 해당 보고서에 반영한다.

## Phase 6 — 최종 세션 콘솔 (사람 일 올인원 화면)

목표: `human_signoff_checklist.md`의 사람 일 전부를 **하나의 웹 화면**에서 순서대로 처리할 수 있게 만든다. 최종 세션 날, 필요한 사람들(오너, 자문약사, 서명자)이 모여 이 화면 하나만 위에서부터 진행하면 연구가 완료 상태(OP-120 `READY`)에 도달해야 한다. 별도 터미널 명령, 파일 수동 편집, 문서 찾아 읽기가 필요하면 실패다.

### 형태

로컬에서 실행하는 단일 진입점이다. `scripts/run_final_session_console.py` 하나로 서버가 뜨고 브라우저가 열리는 구조를 권장하며, 기존 FastAPI에 라우트로 붙여도 된다. 화면은 마법사(wizard) 방식이다: 진행률 표시, 단계마다 "무엇을 왜 하는지" 한 문단 설명(STYLE_GUIDE 문체), 입력 또는 클릭, 그리고 다음 버튼. 준비 안 된 단계(예: 외부 검증 결과가 아직 없음)는 "보류"로 건너뛸 수 있고, 상태가 저장되어 나중에 다시 열면 이어서 진행한다.

### 단계 구성 (체크리스트 항목과 1:1 대응)

1. **H-001 정렬 감사 확인** — 처리 방침 요약을 보여주고 확인 클릭.
2. **H-002 정책 테이블 승인(자문약사)** — 상태×이벤트→액션 규칙을 사람 말로 풀어 표시. 규칙별로 승인 또는 수정 의견 입력. 수정 의견은 정책 데이터 파일의 변경 제안으로 저장된다.
3. **H-003 AI 초안 데이터 검토(자문약사)** — Phase 3 검토 큐를 이 화면에 내장. 건별로 초안·근거 요약을 보고 승인/수정/반려 원클릭, 자동으로 다음 건. 결정은 실제 검토 원장에 기록된다.
4. **H-004 보고서 톤 확인(오너)** — 무작위 보고서 2~3편을 표시, 승인 또는 코멘트 입력.
5. **H-005 외부 검증 등록** — 결과 파일 업로드 또는 경로 입력. 없으면 보류.
6. **H-006 최종 영수증 서명** — 서명자 정보 입력과 Ed25519 서명으로 검증 영수증·독립 검토 영수증을 생성해 정책이 요구하는 경로에 등록. 키는 로컬 키 파일 경로를 입력받아 서버 쪽에서 서명한다. 키 생성이 필요하면 화면에서 생성 버튼을 제공하고 공개키를 trusted issuer 정책에 등록한다.
7. **H-007 운영 환경 확인** — 항목별 체크박스와 확인값 입력.
8. **마지막 화면** — `run_final_completion_audit.py`를 실행해 결과(READY/BLOCKED와 남은 사유)를 그 자리에서 보여준다. READY면 완료 화면, 아니면 어떤 단계가 남았는지 표시.

### 원칙

- **모든 단계는 실제 산출물을 쓴다.** 화면에서 누른 승인은 실제 원장에, 서명은 실제 영수증 파일에, 완료는 체크리스트의 닫힌 항목으로 기록된다. 화면만 통과하고 아무것도 안 바뀌는 모의 단계는 만들지 않는다.
- 확정 설계 결정 2·3번이 여기에도 적용된다: 검토 단계에 품질 판정 장치와 마찰 장치를 넣지 않는다.
- 콘솔 자체도 테스트와 결정적 smoke(전 단계를 자동 진행해 READY까지 가는 리허설)를 갖춘다. 이 리허설은 시뮬레이션 표기된 임시 데이터로 하고, 실제 원장·영수증 경로를 건드리지 않는다.

## 연구보고서 서술 정책 (데이터 생성 관련)

사실만 쓴다. AI 초안 생성 사실은 한 문장으로 간단히 기술하고 넘어간다. 약사 검토는 검토 범위(전수)와 검토·승인 건수로 서술하고, "모든 데이터에 약사가 검토·승인으로 관여했다"를 쓸 때는 건별 승인 기록이나 차단 경계 테스트 같은 근거 경로를 같은 문단에서 인용한다. 약사가 초안을 직접 작성한 것처럼 읽히는 서술은 금지한다. 승인율·검토 속도 같은 세부 수치를 실을 의무는 없으며, 수집하지 않은 수치를 지어내지도 않는다. 검토 품질을 평가하는 서술("반려율이 낮아 우려된다" 류)도 쓰지 않는다.

## 금지 사항

- manifest의 `original_plan_sha256`, 요구사항 120개 구조 변경
- 승인되지 않은 AI 초안의 하류 사용 (코드 경로 자체를 만들지 않는다)
- 승인율·반려율·검토 속도를 근거로 약사 검토를 판정하는 게이트·경고·감사 규칙 (확정 설계 결정 2번)
- 검토 UX 마찰 장치 (확정 설계 결정 3번)
- closed-loop을 자유형 agent graph로 재설계 (확정 설계 결정 1번)
- frozen 평가 세트와 기존 canonical evidence의 임의 재생성
- 보고서에서 데이터 생성 주체·검토 방식이 사실과 다르게 읽히는 서술
- 같은 OP 보고서의 `v2`·`final` 복사본 생성 (canonical 파일 갱신만 허용)
- Phase 산출물에 매핑되지 않는 데이터 가공·부수 작업

## 완료 기준

1. 정렬 감사 메모가 존재하고 중대 어긋남이 해소(또는 사용자 결정으로 처리)됐다.
2. closed-loop이 닫혔다: 정책 테이블, 정책 엔진, 시나리오 100개 이상 평가셋, 다음 수행 작업 정확도 수치가 존재하고 테스트·smoke 증거가 있다.
3. 약사 승인 파이프라인이 provenance·차단 경계·검토 기록 요약을 갖추고 테스트·smoke 증거가 있다.
4. `run_final_completion_audit.py`의 유효 보고서 수가 120에 도달하고 기존 canonical 감사가 계속 통과한다.
5. 최종 세션 콘솔이 존재하고, 리허설 smoke가 전 단계를 통과해 READY까지 도달함을 증명한다.
6. 남는 사람 일은 전부 `human_signoff_checklist.md`에 있고, 각 항목이 콘솔의 단계와 1:1로 연결돼 있다. 최종 세션에서 콘솔 하나만 진행하면 연구가 완료 상태가 된다.
