# OP-025 사용자 행동 로그와 연구평가 로그를 분리해 저장한다

## 화면을 본 기록과 안전 판단 기록은 같은 이벤트가 아니다

원본 계획 16쪽에는 두 종류의 로그가 함께 나온다. 상품 노출 횟수·시간, 구매 내역, 재구매율, 세션과 페이지 체류 시간 같은 사용자 행동 패턴 데이터가 하나다. 사용자와 모델의 대화, 엔진 호출과 결과처럼 연구 판단을 재구성하는 상호작용 로그가 다른 하나다. 두 로그를 같은 event table에 넣고 이름만 달리하면 조회 실수나 분석 조건 하나로 의미가 섞일 수 있다.

OP-025는 사용자 행동을 `behavior_events`, 연구평가 이벤트를 `execution_events`에 따로 저장한다. 두 table은 허용하는 event vocabulary도 다르다. 사용자 행동은 page view나 product click처럼 화면·상품 행동을 나타내고, 연구평가는 recommendation·safety·optimization처럼 판단 단계를 나타낸다. 한 endpoint에 다른 종류의 이름을 보내면 저장하지 않고 오류를 반환한다.

## 두 table이 서로 다른 식별자와 결속 단위를 가진다

`src/wellnessbox_rnd/interim/store.py`의 `execution_events`는 `execution_id`와 event index를 중심으로 구성된다. 한 추천 실행 안에서 recommendation, safety, optimization, conversation, followup evaluation이 어떤 순서로 생겼는지를 기록한다. unique key도 `(execution_id, event_type, idempotency_key)`다.

`behavior_events`는 profile ID, event name과 idempotency key를 중심으로 구성된다. page view, product exposure, product click, cart add, order view, notification open, session start, session end 여덟 이름만 CHECK 제약이 허용한다. 실행 ID를 외래키로 요구하지 않는다. 사용자가 화면을 본 행동이 특정 추천 실행과 항상 일대일이라고 가정하지 않기 때문이다.

두 table은 consent snapshot, 생성 시각, canonical payload와 SHA-256, effective payload hash, payload 상태를 공통으로 가진다. 행동이 실제로 일어난 시각 `occurred_at`과 `data_class`는 `behavior_events`에만 있으며, `execution_events`에는 `created_at`만 있다. 물리적으로 나눈다고 각 로그에 필요한 감사 필드를 버리지는 않는다. 다만 `execution_events`에는 별도 `log_class` column이 없고, 연구평가 class는 table과 bounded event type으로 식별한다. `behavior_events.log_class`는 `user_behavior` 하나만 허용한다.

## behavior recorder가 event 이름을 저장 전에 검사한다

`src/wellnessbox_rnd/interim/behavior_log.py`는 연구 event type 다섯 개와 행동 event name 여덟 개를 별도 집합으로 정의한다. `BehaviorLogRecorder.append_event`에 `safety` 같은 연구 type을 보내면 `research_event_type_not_allowed_in_behavior_log`로 실패한다. 두 목록에 없는 이름도 `behavior_event_name_not_supported`로 거부한다.

행동 event에는 timezone-aware `occurred_at`이 필요하다. recorder는 입력 시각을 UTC ISO 형식으로 정규화한다. timezone 정보가 없는 시각을 서버 local time으로 추정하지 않는다. payload는 key 순서를 고정한 canonical JSON으로 만들고 SHA-256을 계산한다.

같은 profile, event name, idempotency key와 같은 payload·발생 시각이 다시 오면 기존 behavior event ID를 반환하고 `deduplicated=true`로 표시한다. 같은 key인데 payload나 발생 시각이 달라지면 409 conflict다. 재시도를 새 행동으로 중복 집계하거나 바뀐 payload로 기존 행동을 덮어쓰지 않는다.

## 저장 동의는 행동 로그에도 별도로 적용된다

행동 recorder는 해당 profile의 `active_profile_consents`를 먼저 읽는다. survey 출처의 `allow_persistent_storage`가 false이면 `persistent_storage_consent_denied:survey`로 저장을 거부한다. 과거 추천 실행이 저장 허용 상태였다는 사실만으로 현재 행동 로그 권한을 추정하지 않는다.

profile이나 활성 동의가 없으면 새 profile을 자동으로 만들지 않는다. `active_consent_not_found`로 실패한다. 저장된 behavior row에는 실제 사용한 consent snapshot ID가 들어간다. 이후 동의 상태가 바뀌어도 어느 동의 아래에서 그 행동을 저장했는지 확인할 수 있다.

이 구현이 analytics 수집 전체를 자동으로 허용한다는 뜻은 아니다. 현재 행동 event는 survey 저장 동의 하나를 사용한다. source별 행동 분류나 retention 정책이 추가되면 consent contract도 그 범위에 맞게 확장해야 한다.

## API 경계도 행동과 연구 event를 갈라 놓는다

`apps/inference_api/routes/interim.py`는 행동 기록을 `/v1/interim/behavior-events`로 받는다. 연구 지연 이벤트는 `/v1/interim/executions/{execution_id}/events`를 사용한다. 두 endpoint는 내부 token 보호를 받고 서로 다른 Pydantic request model과 recorder를 호출한다.

행동 endpoint에 `safety`를 보내면 422다. 연구 endpoint의 event type은 `conversation`과 `followup_evaluation`으로 더 좁게 제한되므로 `page_view`를 보내도 422다. request body를 table에 그대로 넣은 뒤 나중에 분류하는 방식이 아니다. API validation과 저장기 validation이 같은 분리를 지킨다.

실행 trace 조회는 execution events와 execution identity, knowledge lineage를 반환하지만 behavior events를 포함하지 않는다. 행동 로그를 보려면 별도 저장 경로를 사용해야 한다. `GET /v1/interim/log-classes`는 두 table의 count, table 이름, class 값과 cross-contamination count를 요약한다.

## 오염 검사는 이름과 class를 양쪽에서 센다

`BehaviorLogRecorder.log_class_summary`는 execution table에 행동 이름이 들어갔는지, behavior table에 연구 type이 들어갔는지, behavior row의 log class가 `user_behavior`가 아닌지 각각 센다. 세 값을 더한 `cross_contamination_count`가 0이어야 분리가 유지된다.

schema CHECK만 믿지 않고 조회 시점에도 오염을 집계하는 이유가 있다. migration이나 수동 import처럼 application validation을 지나지 않는 변경이 생길 수 있기 때문이다. summary는 연구 event count와 행동 event count도 각각 반환해 smoke가 실제 저장 행 수와 API 응답을 대조할 수 있게 한다.

현재 이 summary는 운영 monitoring dashboard나 alert가 아니다. 인증된 내부 endpoint에서 현재 SQLite 상태를 읽는 구현이다. 장기 운영에서 오염 0을 보장하려면 배포 환경의 주기적 관측과 receipt가 더 필요하다.

## 테스트는 양방향 오입력을 실제 route에서 막는다

`tests/test_log_separation_execution_identity.py`는 추천 실행을 만든 뒤 page view 행동을 별도 endpoint에 추가한다. behavior table은 1행, execution events는 추천의 core event만 유지되는지 확인한다. 같은 행동 재전송은 deduplicate되고 payload 변경 재전송은 conflict가 된다.

행동 endpoint의 `safety`, 연구 endpoint의 `page_view`는 각각 거부돼야 한다. 저장 동의 거부, timezone 없는 시각, 알려지지 않은 profile도 별도 사례로 실패를 확인한다. 실행 trace에 behavior event가 없고 log-class summary의 두 table 이름, count, cross-contamination 0이 맞는지도 검사한다.

`tests/test_interim_store.py`는 table CHECK와 migration 제약을 보완한다. application test만 통과하고 SQLite가 임의 이름을 받는 상태를 허용하지 않는다. 이 검증 범위는 행동 분석 KPI의 정확도나 실제 서비스 UI instrumentation 완성도를 뜻하지 않는다.

## canonical smoke는 두 실행과 한 행동을 분리한다

`scripts/run_log_separation_identity_smoke.py`는 현재 schema 14 임시 SQLite와 실제 FastAPI 앱을 사용한다. 추천 두 번에서 연구 event 6개를 만들고, page view 하나를 기록한 뒤 같은 요청 재시도와 충돌 요청을 보낸다. 연구 type을 behavior endpoint에, 행동 이름을 research endpoint에 넣는 음성 사례도 포함한다.

`data/original_plan/evidence/op025_op026_log_separation_identity_smoke_v1.json`은 case count 2, execution identity 2개, research event 6개, behavior event 1개를 기록한다. behavior replay는 1행만 남고 cross-contamination은 0이며 execution trace에 행동 event가 없다는 모든 check가 true다.

기존 smoke는 schema version 8을 기록한 뒤 migration 변경 때 재생되지 않았다. 이번 loop에서 schema 14로 재생하고, evidence의 schema와 dataset identity 목록이 현재 코드 상수와 같은지 확인하는 회귀 테스트를 추가했다. smoke JSON은 두 번 같은 SHA-256을 만들어 비결정적 event ID를 결과에 넣지 않는다.

## IMPLEMENTED 완료는 제품 analytics 운영을 뜻하지 않는다

manifest의 required·claimed stage는 `IMPLEMENTED`다. 분리된 table·vocabulary·endpoint, consent와 idempotency 경계, 오염 summary, 실제 route 테스트와 canonical smoke가 있으므로 OP-025는 `COMPLETE`다. 하지만 production clickstream, 상품 노출 instrumentation, retention·삭제 실행, analytics warehouse와 KPI dashboard를 운영했다는 증거는 없다.

이번 loop는 smoke 현재성 방어와 보고서만 바꾼다. 서비스 보호 파일, production, 사용자 원천 데이터, frozen 256건, 학습 데이터, 모델과 simulation은 변경하지 않는다. 공식 frozen 일곱 지표, replay와 weakest slice delta는 0이다. `OPERATED` 승격에는 실제 서비스에서 두 log class를 수집하고 오염 0·동의 거부·보존 정책을 장기 관측한 receipt가 필요하다.
