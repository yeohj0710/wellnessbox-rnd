# OP-066 안전 차단 성분이 최적화 결과에 다시 들어오지 못하게 한다.

manifest에 등록된 증거 `wellnessbox-rnd/data/original_plan/evidence/op065_op066_product_combination_filter_smoke_v1.json`은 안전 판정이 만든 제외 조건을 서비스의 상품 조합 단계에서 다시 적용한 결과를 담고 있다.

## 차단 성분을 두 번 다루는 이유

성분 추천이 안전 단계에서 막혔는데 실제 상품을 고르는 단계에서 그 성분을 포함한 복합 제품이 다시 선택되면 앞선 안전 판정은 무의미해진다. 예를 들어 아연만 따로 고르지 않았더라도 칼슘·마그네슘·비타민D·아연 복합 제품을 고르면 아연이 최종 조합에 들어올 수 있다. OP-066은 추천 성분 이름만 지우는 요구가 아니라, 상품에 선언된 모든 성분을 다시 펼쳐 안전 제외 목록과 대조하는 요구다.

R&D 추천 API는 `apps/inference_api/routes/interim.py`에서 프로필에 저장된 위험 정보와 현재 요청의 안전 정보를 각각 평가한다. 둘 중 하나라도 중대한 위험이면 추천 모델을 실행하지 않고 상태를 `BLOCKED`로 둔다. 이때 요청 성분과 모델 후보를 정리한 `excluded_ingredient_keys`, 발동한 규칙 식별자인 `safety_rule_ids`를 상품 최적화 조건에 함께 넣는다. 제외 성분이 있는데 규칙 식별자가 없으면 `ProductCombinationFilterPolicyV1`이 입력 자체를 거부한다. 이 결합은 나중에 어떤 안전 규칙 때문에 어떤 성분을 뺐는지 잃지 않기 위한 장치다.

## 상품 조합에서 다시 막는 방식

실제 조합 판정은 `src/wellnessbox_rnd/optimizer/product_combinations.py`의 `evaluate_product_combination_filters_v1()`이 맡는다. 각 조합의 `ingredient_totals`에는 선택한 모든 상품의 성분 식별자와 합산량이 들어 있다. 함수는 비용 초과, 상품 수 초과, 안전 제외 성분 포함을 서로 다른 집합으로 계산하고, 세 집합 어디에도 속하지 않은 조합만 통과시킨다. 따라서 안전 제외 성분이 부성분으로 들어 있는 복합 상품도 통과할 수 없다.

이 구조를 선택한 이유는 안전 판정과 상품 탐색의 책임을 분리하면서도 안전 조건을 상품 탐색의 고정 입력으로 유지하기 위해서다. 추천 API가 특정 상품 목록까지 미리 알아야 하는 구조로 합치면 카탈로그가 바뀔 때 안전 모듈도 함께 고쳐야 한다. 반대로 서비스가 제외 성분을 임의로 해석하게 두면 R&D가 내린 차단을 약화할 수 있다. 현재 계약은 R&D가 제외 성분과 규칙을 내리고, 서비스가 실제 상품 성분 식별자로 바꾼 뒤, R&D 쪽 판정 모델과 같은 규칙으로 결과를 다시 계산하는 형태다.

## 실패 조건을 어떻게 확인했는가

집중 테스트 `wellnessbox-rnd/tests/test_product_combinations.py`는 `ING:ZINC`가 들어 있는 조합 하나와 `SAFE-OP066-TEST` 규칙을 넣는다. 결과는 통과 조합 0건, 안전 제외 조합 1건이어야 한다. 같은 테스트는 제외 성분만 넣고 규칙 식별자를 빼거나, 계산된 통과 목록을 사후에 바꾼 자료도 거부되는지 확인한다. 즉, 호출자가 “통과했다”는 배열만 위조해도 모델이 원래 상품과 정책에서 결과를 다시 계산한다.

기준 증거에서는 실제 R&D 응답으로 `magnesium_glycinate` 제외와 `SAFE-EMERGENCY-001` 규칙이 서비스 경계까지 전달됐다. 별도 안전 재진입 사례에서는 `ING:ZINC`가 포함된 조합 한 건이 전부 탈락했다. 서비스가 제외된 추천을 억지로 다시 넣은 경우에는 HTTP 502와 `WB_RND_PRODUCT_MATCH_excluded_recommendation_reentered`가 기록됐다. 이 실패는 빈 결과를 안전한 상품처럼 바꾸지 않고 연결을 중단하는 동작을 보여 준다.

구현 중 어떤 오류가 먼저 발생했고 어떤 커밋에서 고쳤는지는 등록된 소스·테스트·증거 파일만으로 확인되지 않았다. 이번 조사에서는 manifest 항목, 위 기준 증거, `apps/inference_api/routes/interim.py`, `src/wellnessbox_rnd/optimizer/product_combinations.py`, `tests/test_interim_api.py`, `tests/test_product_combinations.py`, 생성 스크립트까지 읽었다. 외부 서비스 저장소 파일은 저장소 경계 규칙 때문에 직접 열지 않았다.

## 현재 단계와 남은 한계

증거 파일은 `op066_proven_stage`를 `INTEGRATED`로 기록한다. 실제 R&D 안전 조건을 서비스 함수가 소비했고, 서비스에서 만든 상품 조합 자료를 R&D 모델로 독립 재계산했으므로 이 단계 주장은 타당하다. 다만 `actual_ready_filter_path_proven=false`, `actual_prisma_query_executed=false`, `production_catalog_operation_proven=false`도 같은 파일에 남아 있다. 실제 운영 카탈로그의 최신성과 공개 배포 동작까지 확인한 결과는 아니다.

따라서 OP-066의 현재 단계는 `INTEGRATED`다. 믿을 수 있는 범위는 서비스 함수 연결에서 안전 제외 성분이 상품 조합에 다시 나타나지 않고, 모순된 결과가 오류로 끝나는 데까지다. 실제 운영 데이터베이스 조회, 운영 카탈로그 갱신 직후의 차단 유지, 공개 환경의 주문 경로는 확인되지 않았다.
