# OP-001 원본 해시를 고정해 모든 후속 검증의 출발점을 통일했다

## 먼저 해결해야 했던 문제

원본 사업계획서를 해석해 요구사항을 만들려면 모든 작업자가 같은 파일을 보고 있다는 사실부터 증명해야 한다. 파일명이 같아도 내용이 다를 수 있고, PDF를 다시 저장하거나 일부 페이지만 교체해도 이후의 페이지 인용과 요구사항 해석은 달라진다. OP-001은 전달된 원본과 저장소 원본이 같은지 감으로 확인하는 작업이 아니다. 원본 바이트 전체에서 계산한 SHA-256 값을 고정하고, 요구사항 목록과 회귀 테스트가 그 값을 계속 확인하게 만드는 요구사항이다.

## 무엇을 비교하고 어떤 값을 기준으로 삼았나

검증 대상은 `docs/context/original_plan.pdf`의 59쪽 PDF다. 저장소 원본에서 계산한 SHA-256은 `31291e6f93977fa2d5d083d0161743c49debef25caf12dccf6edc7fa1c2197d4`이며, `data/original_plan/requirements_manifest_v1.json`의 `original_plan_sha256`에 같은 값을 기록했다. 해시는 파일의 이름이나 수정 시각이 아니라 실제 바이트에 따라 달라진다. 따라서 한 글자나 메타데이터가 바뀐 사본도 같은 원본으로 오인하지 않는다.

이 값은 단순 참고 문구가 아니다. `tests/test_original_plan_manifest.py`의 `test_original_plan_manifest_covers_all_120_requirements_without_gaps`는 manifest에 기록된 값이 고정 기대값과 같은지 검사한다. 같은 테스트는 OP-001부터 OP-120까지 번호가 빠짐없이 이어지는지도 함께 확인한다. 이 단위 테스트는 PDF 바이트를 직접 읽지 않으므로 PDF만 교체한 변경까지 단독으로 잡지는 못한다. 실제 PDF에서 SHA-256을 다시 계산해 manifest 값과 비교하는 검사는 `src/wellnessbox_rnd/governance/original_plan_audit.py`의 canonical manifest 감사가 담당하며, CI는 `scripts/audit_original_plan_requirements.py`로 그 감사를 실행한다.

## 구현 증거는 어디에 남아 있나

manifest가 지정한 구현 증거는 `wellnessbox-rnd/docs/plans/2026-07-15-original-plan-completion-program.md`다. 이 문서는 원본 SHA-256 확인을 OP-001의 완료 조건으로 기록하고, 원본 요구사항을 구현·통합·운영·외부 검증 단계로 나누는 공통 규칙을 정의한다. 저장소 안에서 경로를 사용할 때는 `docs/plans/2026-07-15-original-plan-completion-program.md`로 읽는다. 테스트 증거는 manifest에 기록된 `wellnessbox-rnd/tests/test_original_plan_manifest.py`이며 저장소 내부 경로는 `tests/test_original_plan_manifest.py`다.

Git 이력도 근거의 생성 시점을 보여 준다. 원본 PDF와 기본 컨텍스트는 2026-03-08의 `e5ef1ecf8575d1a09cf4fb3a8d0063e9a8b24d4d` 커밋에서 함께 추적되기 시작했다. SHA-256과 120개 요구사항을 manifest 및 테스트 계약으로 고정한 핵심 이력은 2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad` 커밋이다. 이후 감사와 보고서 자동화가 추가됐어도 원본 해시 값은 바뀌지 않았다.

## 검증이 막아 주는 실패 사례

누군가 PDF를 새 사본으로 교체하면 파일 경로는 그대로여도 canonical manifest 감사가 다시 계산한 해시가 manifest 값과 달라져 실패한다. PDF는 그대로 두고 manifest 값만 임의로 바꾸면 단위 테스트의 고정 기대값과 어긋난다. PDF, manifest, 테스트 기대값을 모두 함께 바꾸는 변경은 자동 검사만으로 원본 교체의 정당성까지 판단할 수 없지만 Git 차이에 세 변경이 모두 드러나므로 검토자가 승인 여부를 판단할 수 있다. 반대로 문서 설명만 고치고 PDF 바이트를 건드리지 않으면 해시는 유지된다. 이 구분은 문구 수정과 원본 교체를 서로 다른 검토 대상으로 만든다.

SHA-256은 파일 동일성을 확인하지만 문서가 진실인지, 최신인지, 법적 원본인지까지 보증하지 않는다. 전달 주체의 전자서명이나 외부 보관소의 공증도 대신하지 않는다. OP-001의 문제는 저장소가 분석한 파일과 기준 파일의 바이트 동일성을 고정하는 데 한정된다. 외부 진본성 검증을 하지 않았다는 한계를 숨기지 않아야 이후 감사에서 과도한 완료 주장이 생기지 않는다.

## 완료 단계와 이번 보고서의 범위

OP-001의 기본 요구 단계와 현재 주장 단계는 모두 `IMPLEMENTED`다. 원본 식별값이 데이터 계약과 테스트에 구현됐으므로 이 단계는 충족한다. 서비스 저장소와의 런타임 통합, 실제 운영에서의 반복 관측, 제3자 외부 검증은 OP-001의 현재 주장에 포함하지 않는다. 데이터셋 학습, 모델 훈련, 시뮬레이션 결과도 바꾸지 않았다. 이번 보강은 기존 구현과 검증 증거를 한 문서에서 재현 가능하게 설명하는 연구 보고서 작업이다.

## 결론

OP-001은 59쪽 원본 PDF를 SHA-256 `31291e6f93977fa2d5d083d0161743c49debef25caf12dccf6edc7fa1c2197d4`로 식별하고, manifest와 회귀 테스트가 같은 값을 요구하도록 구현했다. 구현 문서, 테스트 파일, Git 도입 이력이 서로 같은 원본을 가리킨다. 따라서 연구개발 요구사항 분석의 출발점은 재현 가능하다. 다만 이 결론은 저장소 원본의 바이트 동일성에 대한 `IMPLEMENTED` 판정이며 외부 공증이나 운영 완료 판정은 아니다.
