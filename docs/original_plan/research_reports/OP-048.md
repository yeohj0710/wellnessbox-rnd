# OP-048 학습 산출물이 없거나 의심스러우면 결정 규칙 기준선으로 복귀한다

## 결론과 안전 경계

OP-048은 학습 모델 산출물(learned artifact)을 선택적으로 사용하되, 파일이 없거나 형식·계수가 의심스럽거나 실행 중 오류가 나면 결정 규칙 기준선(deterministic baseline)과 정확히 같은 결과로 돌아가도록 요구한다. 현재 구현은 학습 재정렬을 기본으로 끄고, 저위험 일반 건강 요청에만 적용한다. 실패하면 일부 후보에 계산된 학습 점수까지 모두 버리고 원래 후보 순서와 선택을 그대로 반환한다.

이 규칙이 필요한 이유는 “모델 오류가 있어도 가능한 후보까지만 재정렬”하는 방식이 조용한 부분 적용을 만들기 때문이다. 앞 후보는 학습 점수, 뒤 후보는 기준 점수로 정렬되면 결과를 재현하기 어렵고 안전 검토도 불가능해진다. 현재 코드는 학습 산출물 전체가 유효하고 모든 후보 예측이 완료될 때만 적용 상태를 기록한다.

매니페스트의 구현 경로 `wellnessbox-rnd/src/wellnessbox_rnd/models/efficacy_model_v0.py`를 포함한 등록 파일을 모두 열었다. 모델 형식, 합성자료 학습 코드, 최적화 적용점, 오케스트레이션, 런타임 경계 감사 코드가 서로 다른 책임을 맡고 있다. 등록 테스트와 스모크 증거도 이 구분과 일치한다.

## 적용 조건과 산출물 검증

`wellnessbox-rnd/src/wellnessbox_rnd/optimizer/service.py`의 `_apply_learned_efficacy_reranking`은 안전 상태가 `OK`이고 안전 통과 후보가 있으며, 임신·질환·약물 위험 입력이 없고 목표가 오직 `general_wellness`인 경우에만 학습 재정렬을 시도한다. 고위험 와파린 사례나 다른 목표에는 모델 파일이 있어도 적용하지 않는다. 설정 경로가 없으면 `fallback_missing_path`, 파일이 없으면 `fallback_missing_file`, 구조가 잘못되면 `fallback_invalid_artifact`, 허용 범위를 벗어나면 `fallback_suspicious_artifact`, 예측 중 오류가 나면 `fallback_artifact_runtime_error`로 이유를 구분한다.

`EfficacyModelArtifact`와 `validate_efficacy_model_artifact_for_runtime`은 모델·목표 이름, 코호트 버전, 특성 이름, 계수, 절편을 검사한다. 특성은 허용된 정적·동적 목록에 있어야 하고 후보별 특성이 포함되어야 한다. 중복·공백·지원하지 않는 특성, 닫힌 범주 밖 값, 카탈로그에 없는 성분, 4,096개 초과 특성, 절댓값 10을 넘는 계수, 유한하지 않은 숫자는 거부한다. `load_efficacy_model_artifact`가 파일 파싱과 Pydantic 검증을 수행하고, `build_runtime_efficacy_feature_dict`와 `predict_effect_proxy_from_feature_dict`가 실행 입력과 예측값을 만든다.

학습 점수는 결정 규칙 점수 차이가 1.0 이내인 가까운 후보에만 보너스로 반영된다. 적용 중 어느 후보에서든 예외가 발생하면 함수는 처음 받은 후보 목록을 반환한다. 성공한 경우에만 `OPT-LEARNED-001` 규칙 표시와 `learned_effect_bonus`가 이유 분해에 들어간다. `LearnedRerankingDecision.validate_learned_decision`과 `RecommendationResponse.validate_decision_diagnostics`는 `applied` 상태, 선택 후보, 응답 모드와 표시가 서로 맞는지 재검증한다.

`wellnessbox-rnd/src/wellnessbox_rnd/training/efficacy_model_v0.py`는 합성 레코드를 사용자 단위로 결정론적으로 나누고 릿지 회귀 산출물을 만드는 연구 도구다. 이 파일이 런타임 자동 승격을 수행하지는 않는다. `wellnessbox-rnd/src/wellnessbox_rnd/evals/learned_runtime_boundary_audit.py`는 공개 추천 경로가 `recommend(payload)`만 호출하는지, 학습 기능 기본값이 꺼져 있는지, 안전 모듈이 학습 모델을 가져오지 않는지, 파일 누락 때 선택이 같은지를 감사한다.

## 실패 사례와 회귀 검증

`wellnessbox-rnd/tests/test_decision_uncertainty_learned_fallback.py`는 누락 경로와 누락 파일이 기준선과 정확히 같은 결과를 내는지 확인한다. 잘못된 JSON, 필수 식별자 누락, 공백 코호트 버전, 지원하지 않는 특성, 과도한 계수는 각각 유효하지 않거나 의심스러운 산출물로 분류된다. `test_prediction_error_discards_partial_rerank_and_falls_back`은 중간 예측 실패 뒤 일부 재정렬이 남지 않는지 검증한다. `test_non_applied_response_requires_exact_deterministic_mode`는 미적용 상태에서 응답 모드가 학습 모드로 표시되는 변조를 거부한다.

`wellnessbox-rnd/tests/test_learned_optimizer_integration.py`의 `test_learned_rerank_can_swap_near_tied_general_wellness_single_product`는 유효 산출물이 가까운 후보 순서를 실제로 바꿀 수 있음을 확인한다. `test_learned_rerank_does_not_apply_to_high_risk_anticoagulant_case`는 와파린 사례에서 학습 경로가 안전 결정을 넘지 못하게 한다. `test_learned_rerank_missing_artifact_falls_back_to_deterministic_selection`은 파일 부재 시 성분·순위·점수가 기준선과 같음을 확인한다.

`wellnessbox-rnd/tests/test_learned_runtime_boundary_audit.py`의 두 테스트는 감사 결과와 JSON·Markdown 출력 생성을 검증한다. 등록된 `wellnessbox-rnd/data/original_plan/evidence/op047_op048_decision_uncertainty_learned_fallback_smoke_v1.json`에는 12개 실패·미적용 상태, 두 번의 런타임 호출, 각 상태의 동일한 기준선 후보, 유효 산출물의 순서 교체가 기록되어 있다. 관련 집중 테스트를 포함한 74개가 이번 확인에서 통과했다.

## 현재 단계와 남은 위험

OP-048은 `IMPLEMENTED` 단계다. 등록된 소스와 증거 파일은 연구 코드 커밋 `94b0374a3599973ba5201a3cc751912f07bb146a`를 가리키며, 이후 해당 경로에 차이가 없다. 코드가 산출물 실패를 분류하고 기준선 복귀를 검증한다는 주장은 가능하지만, 학습 산출물이 운영 추천에 배포되었다는 주장은 불가능하다.

증거 파일은 `production_operation_proven=false`다. 감사 코드는 소스 구조와 기본값을 확인하는 정적·결정론적 검사이지 운영 장애 주입이나 실제 배포 감시는 아니다. 합성자료로 만든 산출물의 임상 유효성, 모델 레지스트리 승인 절차, 파일 무결성 서명, 운영 중 메모리·동시성 오류, 장기간의 기준선 동등성은 검증되지 않았다. 따라서 이 결과는 안전한 선택적 실행 경계의 구현 증거이며 운영 성과 증거가 아니다.
## 추천 후보를 점수로 바꿀 때
추천 후보를 잘 고르는 일과 특정 후보를 복용했을 때의 효과를 추정하는 일은 다르다. 이 그룹은 입력 신호가 어떤 점수로 바뀌는지, 안전 차단 전후의 후보가 어떻게 보존되는지, 불확실성을 어디에 표시하는지를 분리해 설명한다.

`OP-048`는 “learned artifact가 없거나 의심스러우면 deterministic baseline으로 복귀한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/models/efficacy_model_v0.py`, `wellnessbox-rnd/src/wellnessbox_rnd/training/efficacy_model_v0.py`, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/service.py`, `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/recommendation_service.py` 외 1개
- 테스트·실행: `wellnessbox-rnd/tests/test_decision_uncertainty_learned_fallback.py`, `wellnessbox-rnd/tests/test_learned_optimizer_integration.py`, `wellnessbox-rnd/tests/test_learned_runtime_boundary_audit.py`, `wellnessbox-rnd/scripts/run_decision_uncertainty_learned_fallback_smoke.py` 외 1개

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
