# OP-033 임신과 수유 제한 규칙을 독립적으로 적용한다.

`wellnessbox-rnd/data/rules/safety_rules.json`에는 임신 규칙 `SAFETY-PREG-001`과 수유 규칙 `SAFETY-LACT-001`이 서로 다른 항목으로 등록되어 있다. 입력 스키마부터 실행용 지식 파일, 안전 서비스, 사전 점검, 자동화 테스트와 대표 시나리오 실행 결과까지 대조했으며, 한 상태가 다른 상태를 대신하지 않고 두 상태가 동시에 적용되는 동작을 확인했다. 판정 단계는 `IMPLEMENTED`다.

## 요구사항과 합쳐져 있던 과거 규칙

OP-033은 임신과 수유를 하나의 특수 인구 조건으로 축약하지 말고 각각의 입력과 제한 규칙으로 보존하라고 요구한다. 두 상태는 동시에 참일 수도 있고 정책 근거와 제한 대상이 달라질 수도 있으므로, `pregnant or lactating` 같은 조건 하나로 처리하면 어떤 규칙이 적용됐는지 추적하기 어렵다.

커밋 `9e1a171` 이전 diff에는 단일 `pregnancy_rule`이 있었고 사전 점검도 임신 또는 수유 중 하나가 참이면 같은 `SAFE-PREG-001`을 내보냈다. 커밋은 도메인 모델을 복수 `special_population_rules`로 바꾸고 별도 수유 규칙과 테스트를 추가했다. 커밋 `c39f0f6`은 뒤이어 대표 시나리오 증거의 단순 URL 목록을 규칙 ID와 성분이 연결된 `policy_bases`로 강화했다. 따라서 이전 결손과 수정 방향은 이력으로 확인되지만, 당시 실패 테스트의 터미널 출력은 남아 있지 않다.

## 독립 상태를 보존하는 구현

`wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`의 사용자 프로필은 `pregnant`와 `lactating`을 별도 불리언으로 정의한다. 두 값은 각각 기본값이 거짓이며 동시에 참일 수 있다. `wellnessbox-rnd/pyproject.toml`에서 Pydantic 의존성이 2.12 계열로 갱신된 변경은 거짓인 수유 필드를 과거 요청의 정규화 기록에서 제외하는 `exclude_if` 동작과 함께 들어왔다. 이 호환 처리는 과거 요청의 정규화 해시를 불필요하게 바꾸지 않으면서 참인 수유 상태는 명시적으로 보존한다.

`wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`는 특수 인구 규칙을 목록으로 보관한다. 안전 서비스인 `wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py`는 임신이 참이면 `pregnancy`, 수유가 참이면 `lactation`을 독립적으로 상태 집합에 추가하고 각 상태와 일치하는 모든 규칙을 적용한다. JSON의 두 규칙은 현재 모두 아슈와간다와 베르베린을 제외하고 `needs_review`를 만든다. 결과가 같더라도 규칙 ID는 분리되어 있으므로 감사 로그에서 어느 상태가 근거였는지 구분할 수 있다.

`wellnessbox-rnd/src/wellnessbox_rnd/knowledge/runtime_db.py`는 프로필 필드 이름을 런타임 조건 키 `pregnancy`와 `lactation`으로 명시적으로 매핑한다. 생성된 `wellnessbox-rnd/data/knowledge/runtime_knowledge_db_v1.json`에는 `SAFETY-PREG-001`이 임신에만, `SAFETY-LACT-001`이 수유에만 적용된다고 기록되어 있다. `wellnessbox-rnd/src/wellnessbox_rnd/interim/safety.py`도 두 상태를 각각 `SAFE-PREG-001`, `SAFE-LACT-001`로 재생한다. 다만 사전 점검 규칙 ID와 추천 경로 규칙 ID는 이름 공간이 다르다.

## 테스트와 생성 증거가 확인하는 계약

`wellnessbox-rnd/tests/test_special_population_condition_safety.py`의 `test_user_profile_keeps_pregnancy_and_lactation_independent`는 두 불리언이 독립적으로 직렬화되는지 검사한다. `test_pregnancy_and_lactation_apply_distinct_rules`는 임신만 있을 때 `SAFETY-PREG-001`, 수유만 있을 때 `SAFETY-LACT-001`만 적용되고 두 결과가 모두 아슈와간다를 제외하며 `needs_review`인지 단언한다. `test_combined_pregnancy_and_lactation_applies_each_rule_once`에서는 두 상태가 함께 참일 때 두 규칙이 각각 한 번만 나타나야 한다.

`test_runtime_knowledge_keeps_special_population_and_condition_effects`에서는 런타임 DB의 조건 키가 `pregnancy`와 `lactation`이어야 하고 잘못된 `pregnant`, `lactating` 키는 없어야 한다. 각 규칙의 `applies_when_pregnant`와 `applies_when_lactating`도 반대 상태에서 거짓이어야 한다. `wellnessbox-rnd/tests/test_consent_and_input_hash_contracts.py`의 `test_explicit_false_lactation_preserves_legacy_snapshot_and_hash`는 명시적 `lactating=false`가 기존 시점 기록(스냅샷)과 SHA-256 해시를 바꾸지 않는 호환 계약을 고정한다. `wellnessbox-rnd/tests/test_interim_safety.py`의 `test_pregnancy_and_lactation_have_separate_replay_rule_ids`는 사전 점검에서도 규칙이 합쳐지지 않는지 검증한다.

`wellnessbox-rnd/scripts/run_special_population_condition_safety_smoke.py`는 대표 시나리오를 빠르게 확인하는 스모크 스크립트다. 저장 대상인 `wellnessbox-rnd/data/original_plan/evidence/op033_op034_special_population_condition_safety_smoke_v1.json`에는 임신, 수유, 동시 상태를 포함한 여덟 사례가 기록되어 있다. 동시 사례는 두 추천 경로 규칙과 두 사전 점검 규칙을 각각 보존한다. 이 JSON은 식별 정보를 포함하지 않는 고정 입력의 로컬 실행 결과이며 운영 기록은 아니다.

## 정책 근거와 판정 한계

대표 시나리오 증거는 NCCIH 아슈와간다 자료와 NCBI MotherToBaby 베르베린 자료를 두 규칙의 외부 정책 근거로 연결한다. 이번 재검토에서 아슈와간다 자료의 임신·수유 회피 안내와 베르베린 자료의 제한된 임신 정보 및 수유 중 주의 내용을 확인했다. 다만 `wellnessbox-rnd/data/knowledge/runtime_knowledge_db_v1.json`의 두 규칙에는 reference ID와 claim ID가 없으므로, 실행 시점 응답이 문헌의 정확한 문장 범위를 인용한다는 증거는 아니다. 베르베린 자료도 모든 상황의 절대 금기를 단정하지 않으므로 현재 제외는 보수적인 제품 정책으로 읽어야 한다.

등록된 구현 경로 여덟 개와 테스트·증거 경로 다섯 개는 모두 존재하고 내용도 임신·수유 분리 요구와 일치한다. 저장소 수준 구현과 회귀 검사가 있으므로 `IMPLEMENTED`로 유지한다. 실제 의료진 검토, 배포 환경 통합, 운영 결과, 외부 독립 평가는 확인하지 않아 더 높은 단계는 주장하지 않는다.
## 안전 판단에서 놓치면 안 되는 경계
안전 그룹의 기준은 추천을 많이 만드는 것이 아니라 위험한 결과를 통과시키지 않는 것이다. 입력 단계와 후보 생성 뒤에 안전 판단을 두고, 중대한 위험이나 불명확한 용량이 나오면 fail-closed로 멈추는 경계를 확인한다.

`OP-033`는 “임신·수유 상태별 제한 규칙을 분리한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=17`
- 구현·설계: `wellnessbox-rnd/pyproject.toml`, `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`, `wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py` 외 4개
- 테스트·실행: `wellnessbox-rnd/tests/test_special_population_condition_safety.py`, `wellnessbox-rnd/tests/test_consent_and_input_hash_contracts.py`, `wellnessbox-rnd/tests/test_interim_safety.py`, `wellnessbox-rnd/scripts/run_special_population_condition_safety_smoke.py` 외 1개

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
