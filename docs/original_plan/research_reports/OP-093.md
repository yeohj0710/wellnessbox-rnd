# OP-093 유전자 변이, 판정 기준, 검사기관, 검사일을 정규화한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/domain/sensor_parser.py`에서 구현과 검증 대상을 확인할 수 있다.

## 태그 하나로는 검사 결과를 설명할 수 없다

OP-093은 유전자 변이, 판정 기준, 검사기관, 검사일을 정규화하라고 요구한다. 기존 R&D 경로에도 유전자 입력은 있었다. `phenotypes`, `risk_flags`, `markers`, `gene_markers` 같은 필드에서 문자열을 모은 뒤 소문자 스네이크 표기 태그로 바꾸고, 허용된 태그만 추천 점수에 제한적으로 반영했다. 이 경로는 `lpl_triglyceride_risk`처럼 이미 해석이 끝난 연구용 신호를 전달하기에는 충분했다. 그러나 태그가 어떤 유전자와 변이를 가리키는지, 누가 언제 검사했는지, 어떤 판정 기준을 썼는지는 남지 않았다.

이 누락은 단순한 표시 문제에 그치지 않는다. 같은 변이라도 검사 패널과 판정 기준이 다를 수 있다. 판정이 바뀌었을 때 과거 결과를 다시 검토하려면 검사기관과 검사일을 알아야 한다. `high risk`라는 문자열만 저장하면 원본 검사 결과인지, 서비스가 나중에 붙인 분류인지 구분하기 어렵다. 따라서 이번 구현의 핵심은 새로운 유전자 점수 규칙을 만드는 일이 아니라, 판정의 출처와 시점을 잃지 않는 구조화 기록을 만드는 일이었다.

## 기존 경로에서 유지해야 할 부분

조사 대상은 `sensor_parser.py`, 추천 요청 스키마, intake 동의 게이트, 후보 점수 계산, Data Lake 프로필 스냅샷이었다. 기존 구조는 웨어러블·연속혈당측정기·유전자 정보를 하나의 `NormalizedSensorGeneticSnapshot`으로 전달한다. 추천 점수는 별도 규칙 파일에 등록된 유전자 태그만 읽는다. 알 수 없는 태그는 0점이며 다른 후보로 신호가 번지지 않는다. 이 제한은 안전 경계이므로 그대로 유지했다.

새 저장소나 유전자 전용 추천 엔진은 만들지 않았다. `NormalizedSensorGeneticSnapshot`에 구조화 변이 목록을 추가하고, 기존 parser와 동의 경로가 그 목록을 함께 다루도록 확장했다. 이 선택으로 기존 추천 API, 입력 해시, 후보 점수 계산, Data Lake 계보를 재사용할 수 있었다. 기존 자유형 태그도 호환성을 위해 남겼다. 구조화 변이 자체가 곧바로 점수로 변환되지는 않는다. 점수에는 기존 규칙 레지스트리에 등록된 태그만 들어간다.

## 정규화 기록에 포함한 항목

새 `NormalizedGeneticVariant` 모델은 유전자 기호, 변이 식별자, 유전자형, 판정, 판정 기준, 검사기관, 검사일을 요구한다. 유전자 기호는 대문자로 바꾸고 허용 문자 범위를 제한한다. `RS762551` 같은 rs 식별자는 `rs762551`로 통일한다. 유전자형의 `C|A`와 `C/A`는 이번 입력 계약에서 위상 정보를 쓰지 않으므로 `A/C`처럼 정렬된 슬래시 표기로 바꾼다. 검사일은 ISO 8601 날짜인 `YYYY-MM-DD`만 허용한다.

판정은 `increased_risk`, `typical`, `reduced_risk`, `carrier`, `indeterminate` 다섯 값으로 제한했다. 입력에서 `high risk`, `normal`, `low risk`, `uncertain`, `VUS`처럼 자주 쓰이는 표현은 이 값으로 매핑한다. 목록에 없는 `certain cure` 같은 표현은 의미를 추측하지 않고 거부한다. 이 제한은 유전자 결과를 진단이나 치료 확정 문구로 바꾸는 것을 막는다. 판정 기준과 검사기관은 공백을 정리하되 원래의 사람이 읽을 수 있는 이름을 유지한다.

## 여러 공급자 필드를 한 계약으로 읽는 방법

공급자별 차이를 흡수하기 위해 필드 별칭을 제한적으로 허용했다. 유전자 기호는 `gene_symbol` 또는 `gene`, 변이는 `variant_id`, `variant`, `rsid`, 유전자형은 `genotype`, `call`, `result`를 읽는다. 판정은 `interpretation`, `classification`, `risk_assessment`를 허용한다. 판정 기준은 `interpretation_criterion`, `criterion`, `basis`, 검사기관은 `testing_laboratory`, `laboratory`, `lab`, `testing_lab`, 검사일은 `tested_on`, `test_date`, `collection_date`를 허용한다.

별칭이 둘 이상 들어오면 먼저 나온 값을 고르지 않는다. 대소문자와 불필요한 공백을 제외하고 값이 다르면 `conflicting_genetic_variant_*_aliases` 오류로 중단한다. 예를 들어 `gene=CYP1A2`와 `gene_symbol=APOE`가 함께 오면 어느 값을 믿을지 정할 근거가 없으므로 실패한다. `variants`, `variant_results`, `genotypes`가 동시에 서로 다른 목록을 제공하는 경우도 `conflicting_genetic_variant_sources`로 막는다.

## 누락과 중복을 조용히 넘기지 않는 이유

구조화 변이에는 일곱 필드가 모두 필요하다. 판정 기준이나 검사기관이 없으면 빈 문자열로 채우지 않는다. 검사일이 `06/30/2026`처럼 지역에 따라 해석이 달라지는 형식이면 날짜를 추측하지 않는다. 변이 목록이 배열이 아니거나 배열 안의 항목이 객체가 아니어도 명시적 오류를 반환한다. 동일한 유전자 기호, 변이 식별자, 검사일 조합이 두 번 나오면 중복으로 거부한다.

초기 구현 과정에서는 유전자 파일 스키마 검증기가 기존 태그와 새 변이 목록을 모두 필수로 요구하는 회귀가 생겼다. 기존 `gene_profile_v1.json`은 태그만 포함하므로 정상 fixture가 실패했다. 요구사항은 두 형식을 동시에 강제하는 것이 아니라 적어도 하나의 지원된 유전자 정보가 있어야 한다는 뜻이다. 검증기를 `태그 또는 변이 목록 중 하나` 규칙으로 고쳐 기존 파일을 보존했다. 이 실패는 새 필드를 더할 때 기존 alias-group 공통 검증기를 그대로 재사용하면 의미가 달라질 수 있음을 보여줬다.

## 재현 가능한 여덟 사례

동결 데이터셋 `data/original_plan/op093_op094_genetic_normalization_consent_cases_v1.json`에는 여덟 사례가 있다. OP-093과 직접 관련된 사례는 별칭 정규화, 여러 변이의 결정적 정렬, 기존 태그 호환, 판정 기준 누락 거부, 비표준 검사일 거부, 충돌하는 유전자 별칭 거부다. 별칭 정상 사례는 `cyp1a2`, `RS762551`, `C|A`, `high risk`, 검사 패널 이름, 검사기관, 검사일을 완전한 구조화 기록으로 바꾼다.

canonical smoke는 저장된 Git blob에서 데이터와 코드의 SHA-256을 계산한다. 작업 디렉터리의 임시 내용으로 source identity를 꾸미지 않는다. 모든 정상 사례는 전체 정규화 결과를 동결 기대값과 비교하고, 실패 사례는 정확한 오류 문자열을 비교한다. 두 번 실행한 결과가 같은 바이트인지 별도로 확인할 수 있도록 출력에는 현재 시각이나 임시 데이터베이스 경로를 넣지 않았다.

## 검증 범위와 단계 판단

집중 테스트는 parser, gene-profile 파일 스키마, 동의와 입력 해시, Data Lake 저장 분리, 후보 점수 경로를 함께 실행한다. 새 모델의 JSON 스키마도 기존 추천 요청 스키마에 포함된다. Ruff 검사는 새 parser 보조 함수와 smoke runner를 포함한다. 전체 original-plan 감사에서는 manifest에 등록한 구현 파일과 테스트 파일이 실제로 존재하는지, canonical evidence가 PASS인지 다시 검사한다.

OP-093의 required stage는 `IMPLEMENTED`다. 로컬 버전 계약, 구조화 모델, fail-closed parser, 동결 사례, 자동 테스트와 canonical evidence가 있으므로 구현 검증 단계는 충족한다. 다만 실제 유전자 검사기관 API, 파일 업로드 운영, 검사 결과 원본 검증, 외부 임상 판정 검토는 관찰하지 않았다. 따라서 `INTEGRATED`, `OPERATED`, `EXTERNALLY_VALIDATED`를 주장하지 않는다.

## 남은 한계

현재 변이 식별자는 rs 번호와 일반 문자열을 수용하지만 HGVS 문법 전체를 검증하지 않는다. reference genome build, transcript, zygosity, specimen identifier, 검사 방법, 보고서 개정판도 아직 별도 필드가 아니다. 유전자형의 위상 정보는 이번 점수 경로에서 사용하지 않으므로 `|`를 `/`로 정규화한다. 위상이 필요한 요구가 생기면 현재 스키마 버전을 조용히 바꾸지 말고 새 버전에서 phased genotype을 분리해야 한다.

또한 구조화 판정은 의료적 진단이 아니다. 시스템은 검사기관의 판정과 근거 문구를 기록할 뿐 독자적으로 질병 위험을 재판정하지 않는다. 추천 점수는 승인된 태그 규칙만 사용한다. 다음 단계에서는 OP-095의 부분 성공 응답과 OP-096의 원본 파일 해시 계보가 이 구조화 기록을 어느 입력 파일에서 만들었는지 연결해야 한다.
## 센서와 유전자 자료를 넣는 기준
센서와 유전자 자료는 많이 넣는 것보다 동의한 자료를 올바른 단위와 시점으로 연결하는 것이 중요하다. 이 그룹은 파일 원본, 출처별 정규화, data_class, 동의, 중복 수신, 실제 점수 반영을 분리해 확인한다.

`OP-093`는 “유전자 변이, 판정 기준, 검사기관, 검사일을 정규화한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=23`, `docs/context/original_plan.pdf#page=24`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/domain/sensor_parser.py`, `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_sensor_parser.py`, `wellnessbox-rnd/scripts/run_genetic_normalization_consent_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op093_op094_genetic_normalization_consent_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
