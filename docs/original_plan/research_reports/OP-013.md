# OP-013 복용 약물의 이름, 분류, 용량, 단위를 구조화한다.

## 약 이름 한 줄로는 안전 판단에 필요한 뜻이 부족하다

원본 PDF의 개인 특성 파라미터에는 복용 약물이 포함된다. 같은 이름도 분류 체계가 다를 수 있고, `500`만 적으면 mg인지 mcg인지 알 수 없다. OP-013의 결과는 약물명, 분류 code와 system, 표시명, 용량 숫자와 단위를 명시적인 요청 계약으로 만드는 것이다. 진단이나 처방을 만드는 기능이 아니라 기존 추천·안전·모델 경로가 약물 입력을 잃지 않게 하는 기반이다.

## 기존 RecommendationRequest를 확장했다

`src/wellnessbox_rnd/schemas/recommendation.py`의 `MedicationInput`은 name, 선택적인 `MedicationClassification`, 선택적인 dose를 가진다. 분류는 code, 기본 `local`인 system, 선택 display name으로 구성된다. 구조화 dose는 0 초과 1,000,000 이하 amount와 `g`, `mg`, `mcg`, `ng`, `mL`, `IU`, tablet, capsule 중 하나인 unit을 요구한다. 과거 요청과의 호환을 위해 1~128자의 legacy dose 문자열도 받지만, 구조화 값처럼 단위를 추정하지 않는다. strict 모델은 알 수 없는 필드를 거부한다.

`src/wellnessbox_rnd/domain/intake.py`는 약물명을 소문자 canonical text로 바꾸고, 분류 code와 system도 정규화한다. 분류 key는 `system::code`이므로 ATC `123`과 RxNorm `123`이 충돌하지 않는다. legacy dose의 가장자리 공백만 제거하고 내용은 보존한다. 새 약물 저장소나 별도 feature pipeline을 만들지 않고 기존 efficacy·policy feature builder가 `medication::metformin`, `medication_classification::atc::a10ba02` 같은 안정된 key를 사용한다.

## API 예제와 실패 경계가 단위를 드러낸다

`apps/inference_api/routes/recommend.py`와 `data/samples/api_recommend_structured_safety_block_request_v1.json`은 Metformin, ATC A10BA02, Biguanides, 500mg을 실제 JSON 구조로 제공한다. amount 0은 validation error다. boolean, 알 수 없는 unit, 빈 name·code, schema 밖 필드도 받아들이지 않는다. 반면 legacy `5mg`은 문자열로 유지되므로 숫자 5mg과 동일한 정밀도를 자동 주장하지 않는다.

`tests/test_medication_supplement_input_contracts.py`는 이름·분류·용량이 정규화 뒤 손실 없이 남는지, 서로 다른 분류 system이 충돌하지 않는지, 구조화 name과 classification이 기존 두 모델 feature 경로에 도달하는지 확인한다. `tests/test_inference_api.py`는 같은 요청 계약이 실제 FastAPI endpoint에서 parsing되는 경계를 검사한다. 핵심 도입 커밋은 `405484dd5245828363be58ae97c9da445708af97`이며 후속 안전·dose 작업도 이 객체를 재사용했다.

## canonical evidence와 완료 단계

manifest 감사는 schema, intake, 모델, API 예제, sample과 두 테스트 파일이 Git에 추적되고 R&D 소유인지 검사한다. completion generator는 required와 claimed stage가 모두 `IMPLEMENTED`이고 issue가 없으므로 COMPLETE로 판정한다. OP-120은 이 보고서의 의미 범주와 evidence 인용을 다시 검사한다.

OP-013은 `IMPLEMENTED / COMPLETE`다. production 약물 데이터의 정확성, 처방 확인, 서비스 운영, 외부 임상 검증은 증명하지 않으므로 `INTEGRATED`, `OPERATED`, 외부검증을 주장하지 않는다. 이번 backfill은 코드·서비스·원천/frozen/학습 데이터·모델·simulation을 바꾸지 않아 평가·replay·slice delta는 0이다. 남은 조건은 실제 통합·운영이 필요한 후속 OP에서 승인된 환경 증거를 확보하는 것이다.
## 입력값을 먼저 고정한 이유
이 그룹에서 입력을 세분화한 이유는 값 하나를 편의상 문자열로 받으면 안전 판단과 효과 해석이 서로 다른 의미를 사용할 수 있기 때문이다. 단위, 누락, 지원하지 않는 입력, 동의 범위를 먼저 고정해야 뒤의 계산과 차단 결과를 설명할 수 있다.

`OP-013`는 “복용 약물의 이름, 분류, 용량, 단위를 구조화한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/models/efficacy_model_v0.py`, `wellnessbox-rnd/src/wellnessbox_rnd/models/policy_model_v0.py` 외 2개
- 테스트·실행: `wellnessbox-rnd/tests/test_medication_supplement_input_contracts.py`, `wellnessbox-rnd/tests/test_inference_api.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
