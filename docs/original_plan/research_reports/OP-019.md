# OP-019 wellnessbox 프로필을 R&D 요청으로 손실 없이 변환한다.

## 두 서비스의 필드 이름이 다르면 중간에서 의미가 사라질 수 있다

원본 계획 16쪽은 UI로 받은 성별, 연령, 키, 체중, 병력, 증상, 복용 약물, 생활 습관을 개인 특성 파라미터로 모아 엔진이 읽게 한다. 실제 WellnessBox 프로필은 `heightCm`, `dietaryRestrictions`, `pregnantOrBreastfeeding` 같은 이름을 쓰고, R&D 추천 요청은 `height_cm`, `dietary_patterns`, `pregnant`처럼 다른 계약을 쓴다. OP-019의 결과는 서비스가 가진 profile을 R&D `RecommendationRequest`로 바꾸되, 지원하는 운영 필드를 빠뜨리거나 모르는 필드를 조용히 버리지 않는 adapter다.

이 요구를 R&D 안에 별도 사용자 profile 저장소로 해결하지 않았다. profile의 소유자는 WellnessBox 서비스이고, R&D는 추천에 필요한 최소 정보와 원본 계약 trace만 받는다. 변환 책임은 `wellnessbox/lib/server/wb-rnd-profile-adapter.ts`에 두고, 전송과 응답 검증은 기존 `wb-rnd-client.ts`를 재사용한다. 서비스 route는 클라이언트가 임의로 보낸 R&D payload를 우선하지 않고 저장 profile을 adapter에 넣는다.

## adapter는 먼저 원본 profile을 엄격하게 검사한다

서비스 adapter의 Zod schema는 name, age, sex, heightCm, weightKg, conditions, medications, allergies, goals, dietaryRestrictions, pregnantOrBreastfeeding, caffeineSensitivity만 허용한다. 문자열의 최대 Unicode code point 수, 빈 문자열, 배열 개수, 나이와 신체 수치 범위를 검사한다. `silentLossCandidate` 같은 알 수 없는 필드는 `.strict()` 검증에서 `invalid_source_profile`로 실패한다. 잘못된 필드를 제거한 뒤 계속하는 방식이 아니다.

추천에 필요한 age, sex, goals가 없으면 `missing_required_profile_fields`를 반환한다. survey 추천 사용 동의가 false이면 `survey_recommendation_consent_required`다. 목표는 공백·대소문자·구분자를 정리한 뒤 승인된 alias table로 `sleep_support`, `stress_support`, `gut_health` 같은 R&D enum에 매핑한다. `quantum wellness`처럼 지원하지 않는 목표는 `unsupported_profile_goal`과 `goals.0` 경로를 돌려준다.

## 최소 원본 trace와 운영 입력을 함께 만든다

adapter 결과의 `source_profile`은 schema version `wellnessbox.chat.UserProfile.v1`, pseudonymous subject ID, 최소화한 원본 profile을 가진다. 이름과 caffeineSensitivity는 현재 R&D 판단에 전달하지 않는다. 반면 age, sex, 키, 체중, 질환, 약물, 알레르기, 목표, 식이 제한, 임신·수유 표시는 원본 표기 trace에 남는다. 이 최소화 규칙은 어떤 값이 변환 전 profile에서 왔는지 감사할 수 있게 하면서 불필요한 직접 식별 정보를 줄인다.

같은 값은 R&D 운영 필드에도 매핑된다. age와 sex는 `user_profile`, 임신·수유 표시는 현재 보수적인 `pregnant`, 목표 alias는 `goals`, 약물 문자열은 name을 가진 구조화 medication, 질환과 알레르기는 각각 목록, 식이 제한은 `dietary_patterns`가 된다. survey만 available이며 명시된 survey 동의를 사용한다. NHIS, wearable, CGM, genetic은 available과 두 동의를 모두 false로 둔다. 지원하지 않는 source data가 있다고 추정하지 않는다.

## 공유 fixture가 두 저장소 사이의 계약이다

`wellnessbox/contracts/wb-rnd/profile-adapter-v1.json`과 `wellnessbox-rnd/data/contracts/wellnessbox_profile_adapter_v1.json`은 byte-identical한 versioned contract snapshot이다. fixture는 원본 profile, adapter option, validation case 10개, 기대 R&D 요청을 함께 고정한다. 약물명 128/129자, Unicode code point 수, 문자열 나이, 정수형 float 나이, 소수 나이, boolean 키, 빈 약물명, 조건 101개 같은 경계를 두 언어에서 같은 기대값으로 검사한다.

`wellnessbox/scripts/qa/check-rnd-profile-adapter.cts`는 TypeScript adapter 결과가 fixture의 `expected_request`와 정확히 같은지 확인한다. 실제 `callWbRndRecommendPreview`가 그 payload를 body로 전달하는지, localhost route가 저장 profile을 다시 adapter에 넣는지 확인한다. client가 `payload: {bypass: ...}`를 보내도 profile 기반 결과를 우회하지 못한다. malformed JSON은 400, null·array body와 adapter 오류는 422다.

R&D의 `tests/test_wellnessbox_profile_adapter_contract.py`는 서비스 fixture와 R&D fixture의 바이트 동일성을 먼저 검사한다. 기대 요청을 실제 `RecommendationRequest`로 읽고 최소화 profile과 운영 mapping을 필드별로 비교한다. 같은 요청을 FastAPI `/v1/recommend`에 보내 200 응답을 확인하고, OpenAPI가 versioned source profile schema를 노출하는지도 검사한다. unknown source property와 공유 validation case는 R&D Pydantic 경계에서도 같은 위치로 실패해야 한다.

## 통합 증거와 운영 증거를 구분한다

서비스 adapter는 `485da91`에서 도입됐고 subject lineage, R&D 안전 권한, 최소화 계약을 거치며 `1205904`까지 강화됐다. manifest는 서비스 adapter·client·payload builder와 R&D schema를 구현 증거로, 양쪽 QA를 테스트 증거로, 실제 preview route와 두 계약 snapshot을 통합 증거로 등록한다. 두 저장소의 코드가 같은 fixture를 읽고 실제 localhost 요청 body를 검증하므로 OP-019의 required·claimed stage `INTEGRATED`를 충족한다.

이 단계는 production 사용자가 실제 route를 호출했다는 운영 receipt가 아니다. production 배포, 실제 데이터 저장, 동의 UI, 외부 개인정보 검증도 주장하지 않는다. 이번 backfill은 서비스의 보호된 사용자 변경, R&D 구현, production, 원천·frozen·학습 데이터, 모델, simulation을 바꾸지 않았다. 공식 frozen 256건의 일곱 지표와 replay·weakest slice delta는 0이다. `OPERATED`를 주장하려면 승인된 환경에서 profile 조회부터 R&D 응답까지 이어진 실제 실행 기록이 더 필요하다.
## 입력값을 먼저 고정한 이유
이 그룹에서 입력을 세분화한 이유는 값 하나를 편의상 문자열로 받으면 안전 판단과 효과 해석이 서로 다른 의미를 사용할 수 있기 때문이다. 단위, 누락, 지원하지 않는 입력, 동의 범위를 먼저 고정해야 뒤의 계산과 차단 결과를 설명할 수 있다.

`OP-019`는 “wellnessbox 프로필을 R&D 요청으로 손실 없이 변환한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox/lib/server/wb-rnd-profile-adapter.ts`, `wellnessbox/lib/server/wb-rnd-client.ts`, `wellnessbox/lib/server/wb-rnd-recommend-preview-payload.ts`, `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`
- 테스트·실행: `wellnessbox/scripts/qa/check-rnd-profile-adapter.cts`, `wellnessbox-rnd/tests/test_wellnessbox_profile_adapter_contract.py`
- 통합 증거: `wellnessbox/lib/server/wb-rnd-recommend-preview-route.ts`, `wellnessbox/contracts/wb-rnd/profile-adapter-v1.json`, `wellnessbox-rnd/data/contracts/wellnessbox_profile_adapter_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
