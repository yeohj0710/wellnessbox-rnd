# OP-017 데이터 출처마다 사용 동의와 저장 동의를 따로 판단한다

## 데이터가 있다는 사실과 쓸 수 있다는 권한은 다르다

원본 계획 16쪽은 설문과 국민건강보험, 웨어러블·연속혈당측정기 같은 마이데이터를 개인 특성 파라미터로 모으는 데이터 레이크를 그린다. 여러 출처를 한곳에 모으더라도 “값이 도착했다”는 사실만으로 추천에 사용하거나 영구 저장할 수는 없다. OP-017의 결과는 설문, 국민건강보험(NHIS), 웨어러블, 연속혈당측정기(CGM), 유전자 다섯 출처마다 추천 사용 동의와 영구 저장 동의를 독립된 boolean으로 표현하는 것이다.

한 사용자는 웨어러블 운동량을 추천에는 쓰게 하되 저장은 허용하지 않을 수 있다. 반대로 CGM 자료를 나중에 보관하도록 허용했더라도 현재 추천에 사용하는 데 동의하지 않을 수 있다. 동의를 하나의 `consented=true`로 합치면 이 차이를 잃는다. 구현은 새 권한 서비스나 병렬 데이터 저장소를 만들지 않고 기존 `RecommendationRequest`와 intake 정규화 경계에 출처별 권한을 넣었다.

## 요청 계약은 다섯 출처와 두 권한을 고정한다

`src/wellnessbox_rnd/schemas/recommendation.py`의 `DataSourceConsent`는 `use_for_recommendation`과 `allow_persistent_storage`를 가진다. `DataSourceConsents`는 survey, nhis, wearable, cgm, genetic 다섯 필드만 받는다. 값은 strict boolean이므로 0이나 1을 동의값으로 해석하지 않고, `unknown` 같은 새 출처도 조용히 버리지 않는다. 지원하지 않는 필드와 잘못된 타입은 Pydantic validation error가 된다.

설문은 추천 요청의 기본 정보를 담으므로 `use_for_recommendation=false`이면 요청 자체를 거부한다. 선택 출처는 다르게 처리한다. 사용자가 CGM을 available이라고 표시했어도 CGM 추천 사용 동의가 false이면 요청을 거부하는 대신 effective availability에서 제외한다. 이 경계는 선택 자료를 거부한 사용자가 기본 설문 추천까지 받지 못하는 일을 막고, 동의하지 않은 자료가 추천 결과에 영향을 주는 일도 막는다.

명시적 동의 block을 일부만 보내면 생략한 출처는 추천 사용과 저장을 모두 false로 채운다. 새 동의 계약을 전혀 보내지 않은 legacy 요청은 호환성을 위해 다섯 출처의 추천 사용을 true, 저장은 false로 materialize한다. legacy 기본값은 기존 호출을 읽기 위한 제한된 호환 규칙이다. 영구 저장을 묵시적으로 허용하지 않으며, 구조화된 sensor·genetic snapshot은 명시적 동의가 없으면 거부된다.

## intake가 선언 상태와 실제 사용 상태를 분리한다

`src/wellnessbox_rnd/domain/intake.py`의 `normalize_request`는 요청의 `input_availability`를 declared availability로 보존한다. 그다음 available이면서 추천 사용 동의가 true인 출처만 effective availability로 만든다. 이 집합은 `recommendation_authorized_input_source_set`에 들어간다. 영구 저장 동의 집합은 별도의 `storage_authorized_input_source_set`에 들어가므로 추천 권한이 저장 권한으로 번지지 않는다.

검사 관측값에는 survey 또는 nhis 출처가 붙는다. 해당 출처가 unavailable이거나 추천 사용에 동의하지 않았다면 관측은 정규화 목록에 들어가지 않는다. sensor·genetic snapshot도 wearable, CGM, genetic별 effective availability를 적용한다. 특히 유전자 사용 동의를 거부하면 variant와 tag를 비워 추천 점수와 정규화 hash에서 제외한다. 동의가 없는 값을 먼저 충돌 검사해 정상 요청을 막지 않도록, 같은 시각의 검사 충돌도 consent gate를 통과한 관측만 대상으로 판단한다.

## 같은 입력을 빼도 같은 결과인지 확인한다

`tests/test_consent_and_input_hash_contracts.py`는 CGM이 available이지만 추천 동의가 false인 요청과 CGM 자체가 absent인 요청을 비교한다. 두 요청의 다음 행동, 결측 정보, 추천 목록이 같아야 한다. 국민건강보험 검사값도 사용 동의가 없으면 값을 열 배 바꿔도 정규화 관측, snapshot, SHA-256, 추천 결과가 바뀌지 않는다. 유전자 variant를 넣었지만 사용 동의를 거부한 요청도 유전자 자료가 없는 요청과 같은 hash와 추천을 만든다.

테스트는 다섯 출처의 실제 동의 객체, 추천 허용 집합, 저장 허용 집합, effective availability를 모두 비교한다. survey 사용 거부는 모델과 `/v1/recommend` API에서 함께 실패한다. unknown source와 숫자형 boolean도 거부한다. `data/samples/api_recommend_consent_hash_request_v1.json`은 survey와 wearable만 추천·저장을 허용한 대표 입력이며, `apps/inference_api/routes/recommend.py`는 같은 계약을 OpenAPI 예제로 노출한다. fixture는 모델 정규화와 실제 API 200 응답을 함께 검증한다.

## 구현 증거가 말하는 범위를 지킨다

핵심 구현 커밋 `5d7ccf4`는 동의 schema, effective availability, canonical snapshot과 hash, API 예제, 대표 fixture, 계약 테스트를 함께 도입했다. 뒤이은 sensor·genetic 작업은 같은 출처별 동의 경계를 구조화 variant와 관측에 적용했다. manifest는 schema, intake, API route, fixture와 `tests/test_consent_and_input_hash_contracts.py`를 OP-017 증거로 등록한다. original-plan 감사는 이 경로가 저장소 안에 있고 Git으로 추적되는지 확인한다.

OP-017의 required stage와 claimed stage는 `IMPLEMENTED`다. completion generator는 등록 증거에 감사 issue가 없어 COMPLETE로 판정한다. 이 결과는 로컬 요청과 추천 경로의 동의 enforcement를 증명한다. production 동의 화면, 법적 동의 문구, 철회 처리, 실제 저장 삭제, 운영 audit log, 외부 개인정보 검증까지 증명하지 않는다. 이번 backfill은 서비스 저장소, production 환경, 원천·frozen·학습 데이터, 모델 artifact, simulation을 바꾸지 않았다. 공식 frozen 256건의 일곱 지표와 replay·weakest slice delta는 0이다.
