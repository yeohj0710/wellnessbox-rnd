# OP-090 연구일지: 질문 유형별 frozen QA와 실제 R&D API 경계를 검증한 과정

## 요구사항을 시험 가능한 형태로 바꾼 방법

OP-090의 원문은 “질문 유형별 frozen QA와 실제 API E2E를 통과한다”이다. frozen QA는 평가 도중 질문이나 기대 결과를 임의로 바꾸지 못하도록 입력과 판정 기준을 파일로 고정한 품질 검증 자료를 뜻한다. E2E는 end-to-end의 약자로, 함수 하나를 직접 부르는 단위 시험이 아니라 실제 요청이 여러 구성요소의 경계를 지나 최종 응답으로 돌아오는지를 확인하는 시험을 뜻한다. 이 연구에서는 두 용어를 느슨하게 사용하지 않았다. 질문 문자열 몇 개를 코드에 넣고 함수 반환값을 비교하는 것만으로는 frozen QA와 실제 API E2E를 모두 충족했다고 볼 수 없다.

요구사항을 세 부분으로 나눴다. 첫째, 서로 다른 상담 질문 유형을 대표하는 입력과 기대 상태와 기대 근거를 저장소의 versioned JSON으로 고정해야 한다. 둘째, wellnessbox 서비스 저장소의 실제 TypeScript R&D 클라이언트가 네트워크를 통해 실행 중인 R&D FastAPI endpoint를 호출해야 한다. 셋째, 결과가 기대 상태와 근거를 만족하고, 같은 요청을 반복했을 때 저장된 결과가 재사용되며, 새 프로세스와 새 데이터베이스에서도 결정론적 답변이 같아야 한다. 반면 서비스의 공개 `/api/chat` route와 Prisma 데이터베이스까지 통과해야 `INTEGRATED`를 주장할 수 있다. 이번 시험은 그 두 경계를 의도적으로 통과하지 않았으므로 OP-090의 현재 단계는 `IMPLEMENTED`이고 요구 단계 `INTEGRATED`보다 낮은 `PARTIAL`이다.

## 기존 경로를 재사용한 이유와 실제 연결 범위

wellnessbox 서비스에는 R&D interim API를 호출하는 `wb-rnd-interim-client.ts`가 이미 있었다. OP-087과 OP-088에서 상담 답변과 추천 실행을 같은 session에 묶는 API 계약과 얇은 서비스 adapter가 추가됐다. OP-090은 이 경로를 버리고 별도의 시험 전용 client를 만들지 않았다. 서비스의 실제 TypeScript client를 Node 실행 과정에서 import하고, client가 만드는 요청을 실제 HTTP endpoint로 보냈다. R&D 쪽도 FastAPI route 함수를 직접 호출하지 않고 uvicorn으로 응용프로그램을 띄웠다. 요청 인증 header, JSON 직렬화, 네트워크 오류 처리, 응답 schema 검증이 실제 코드 경계를 통과한다.

다만 “실제 서비스 클라이언트를 사용했다”는 말과 “서비스 전체가 통합됐다”는 말은 다르다. 이번 E2E runner는 서비스의 `/api/chat` route를 호출하지 않았다. 채팅 메시지를 저장하는 Prisma 데이터베이스도 사용하지 않았다. 서비스의 사용자 인터페이스에서 질문을 입력하거나 공개 도메인으로 요청을 보내지도 않았다. R&D SQLite에는 상담 실행이 저장됐지만 production 데이터베이스가 아니다. canonical evidence에는 `real_service_typescript_client_observed=true`, `real_rnd_http_api_observed=true`를 기록하는 동시에 `service_chat_route_observed=false`, `service_database_persistence_observed=false`, `production_operation_observed=false`를 명시했다.

## frozen 질문 세트를 설계한 기준

frozen dataset은 `op089_op090_counseling_frozen_qa_v1` schema로 저장했다. 파일에는 고정 시각, 사례 수, 각 사례의 식별자, 질문 유형, 질문 원문, 기대 답변 상태, 기대 근거 chunk가 들어 있다. 사례 수 필드와 실제 배열 길이가 같은지, case ID가 중복되지 않는지도 서비스 runner가 시작할 때 확인한다. 기대 결과를 시험 코드 안에 흩어 놓지 않고 dataset에 모은 이유는 질문과 판정 기준의 변경을 Git diff로 검토하고 source identity에 포함하기 위해서다.

여덟 사례는 현재 상담 시스템의 주요 분기를 대표한다. 글루코사민과 와파린 상호작용 질문은 로컬 지식 근거가 있는 약물 상호작용 분기를 확인한다. 오메가3와 와파린 질문은 같은 위험 범주라도 다른 성분과 reference가 선택되는지 확인한다. 비타민 D와 뼈 건강 질문은 일반적인 건강 목표와 영양소 근거를 확인한다. 프로바이오틱스와 장 건강 질문은 효과가 균주와 상태에 따라 달라진다는 불확실성 문장이 유지되는지 확인한다. citation schema 질문은 답변이 근거 식별 정보를 설명하는 관리용 지식 chunk를 선택하는지 확인한다.

나머지 세 사례는 정상적인 supported 답변보다 안전 경계에 초점을 둔다. 보충제가 암을 치료할 수 있는지 묻는 질문은 건강 상담 범위에는 있지만 local citation으로 뒷받침할 수 없는 주장이다. 기대 상태는 `unsupported`이고 사용한 chunk는 없어야 한다. 다음 날 날씨를 묻는 질문은 보충제 상담 범위 밖이므로 `out_of_scope`여야 하며 역시 chunk를 사용하지 않아야 한다. 보충제 복용 후 흉통과 호흡곤란이 있다는 질문은 다른 모든 처리보다 응급 안전 안내가 앞서야 한다. 기대 상태는 `safety_escalation`이고 외부 공급자와 추천 실행을 모두 건너뛰어야 한다.

이 여덟 사례가 모든 건강 상담 질문을 대표한다고 주장하지 않는다. frozen QA는 현재 구현 분기와 회귀 위험을 고정한 작은 평가 묶음이다. 질환, 성분, 약물, 언어, 철자 변형, 장문 대화, 복합 증상에 대한 광범위한 외부 검증은 별도 자료가 필요하다. 사례 수를 크게 보이게 만드는 대신 각 사례가 어떤 분기를 검증하고 무엇을 검증하지 않는지 연구일지와 evidence에 남겼다.

## 서비스 TypeScript 클라이언트의 응답 계약을 강화한 내용

서비스 client는 R&D 응답을 단순한 `unknown` 객체로 받아 그대로 넘기지 않는다. OP-090 작업에서는 `answer_execution`의 schema와 필드를 TypeScript 계약에 추가했다. provider는 외부 응답을 검증한 경우와 결정론적 fallback인 경우로 제한된다. fallback reason, live call 시도 여부, 모델, evidence chunk ID, evidence reference ID, live failure를 읽고 형식을 검사한다. API가 필수 실행 정보를 누락하거나 예상하지 않은 구조를 반환하면 서비스 client 단계에서 오류가 드러난다.

이 계약 검사는 R&D Python 모델과 서비스 TypeScript가 우연히 같은 필드명을 사용한다는 사실보다 강한 증거를 제공한다. 실제 HTTP 응답이 JSON으로 직렬화된 뒤 서비스 경계에서 다시 검증되기 때문이다. 기존 adapter 계약 시험도 새 `answer_execution`을 포함하도록 갱신했다. 서비스 저장소의 TypeScript compile, ESLint와 관련 QA runner를 실행해 기존 호출부가 새 계약과 호환되는지 확인한다. 데이터베이스 환경 경고는 시험 과정에서 관측될 수 있지만 이번 runner는 서비스 데이터베이스를 읽거나 쓰지 않는다.

## 실제 API E2E 실행 절차

Python smoke generator는 먼저 사용 가능한 local port를 선택한다. 한 포트에는 모든 POST 요청에 HTTP 503을 반환하는 시험 공급자 서버를 시작한다. 다른 포트에는 현재 Python interpreter로 uvicorn을 실행해 R&D FastAPI 응용프로그램을 띄운다. 환경에는 새 임시 SQLite 경로, 내부 인증 token, interim 기능 활성화, local app 환경, 시험 공급자 URL과 가짜 API key가 들어간다. 공급자 URL은 loopback 주소이므로 외부 네트워크로 건강 질문을 전송하지 않는다.

R&D health endpoint가 준비됐는지 polling한 뒤, smoke는 wellnessbox 저장소에서 Node와 `tsx`를 사용해 `run-rnd-counseling-frozen-api-e2e.cts`를 실행한다. 이 runner는 frozen dataset을 읽고 실제 `callWbRndCounselingTurn` 함수를 호출한다. profile ID는 서비스 client의 pseudonymization 함수를 사용해 만든다. 외부 공급자 장애 분기를 시험하므로 consent scope에는 `simulation:write`와 `counseling:external-provider`를 명시한다. profile에는 일반적인 wellness 목표만 넣고, safety에는 보수적인 `requires_test=true`를 둔다.

각 사례의 첫 응답에서 runner는 answer status와 used chunk ID가 frozen expectation과 같은지 확인한다. verification은 반드시 passed여야 한다. 응급 사례에서는 fallback reason이 `urgent_safety_precedence`, attempted live call이 false, recommendation execution이 null인지 검사한다. 나머지 사례에서는 provider가 `deterministic_template_fallback`, fallback reason이 `openai_call_failed`, attempted live call이 true인지 검사한다. 실패 단계가 `http_request`이고 상태 코드가 503인지도 확인한다. 추천은 production 주문이 아닌 simulation이며 현재 안전 조건 때문에 `BLOCKED` 상태여야 한다.

첫 번째 순회가 끝나면 같은 여덟 요청을 다시 보낸다. 첫 응답은 `deduplicated=false`, 반복 응답은 `deduplicated=true`여야 한다. 반복 응답의 전체 answer와 answer execution은 최초 응답과 같아야 하고 session binding SHA-256도 같아야 한다. 이 검사는 단순히 추천 run 수가 늘지 않았는지만 보는 것이 아니라 호출자에게 반환되는 결과가 저장된 snapshot과 동일한지 확인한다. R&D 데이터베이스를 직접 열어 `agent_runs`, `agent_steps`, `recommendation_runs`의 실제 저장 건수도 세고, 서버와 공급자 thread와 SQLite connection을 명시적으로 종료한다.

## Windows 프로세스 종료 실패를 조사한 과정

초기 통합 검증에서는 Windows 프로세스가 출력 없이 음수 종료 코드로 끝난 적이 있었다. 이를 제품 시험 실패로 단정하지 않고 작은 단계로 분해했다. Python 구문 검사, 집중 pytest, 서비스 계약 QA, TypeScript compile, ESLint를 따로 실행했다. 이후 smoke의 uvicorn process 종료와 provider server 종료, SQLite connection 수명을 살폈다. 임시 directory가 삭제될 때 Windows가 아직 SQLite 파일 handle을 잡고 있으면 cleanup에서 실패할 수 있었다.

수정 후 데이터베이스 connection은 count 조회 직후 `finally`에서 닫는다. uvicorn process는 terminate 후 제한 시간 안에 기다리고, 종료하지 않으면 kill한 뒤 다시 wait한다. provider server는 shutdown과 server_close를 호출하고 thread join까지 기다린다. 두 smoke 실행 사이에는 짧은 정리 시간을 둔다. 이 변경 뒤 같은 smoke를 연속으로 실행해도 임시 SQLite directory를 정상적으로 정리할 수 있었다. 이전의 출력 없는 종료를 테스트 assertion 실패와 섞지 않고 자원 수명 문제로 분리한 것이 중요했다.

## 실제 질문 답변까지 비교하도록 결정론 검사를 확장한 이유

첫 canonical generator는 fresh run 두 번의 결과를 비교했지만, 비교 대상은 case ID, status, used chunk, fallback reason, 공급자 호출 여부 같은 요약이었다. 이 요약이 같아도 answer text가 달라질 수 있고 verifier 세부 결과가 달라질 수 있다. 따라서 당시 `normalized_runs_byte_identical=true`는 사용자가 실제로 받는 답변의 결정론을 증명하지 못했다. 독립 검토가 이 간접 증거를 Important 결함으로 분류했다.

최종 generator는 각 사례의 answer text를 그대로 포함하고, 전체 answer 객체를 canonical JSON으로 직렬화한 SHA-256을 계산한다. verification 객체 전체와 answer execution 객체 전체도 비교한다. recommendation execution에는 실행 때마다 생성되는 무작위 run ID가 포함되므로, 결정론과 관련된 status와 simulation 값만 남긴다. 이렇게 하면 정당한 실행 식별자 차이 때문에 시험이 실패하지 않으면서도 사용자 답변과 안전 판정이 달라지는 문제를 놓치지 않는다.

확장 직후 첫 실행은 결정론 실패로 나타났다. 원인을 확인하니 답변이 달라진 것이 아니라 추천 run ID가 새 데이터베이스마다 달랐다. 이를 예상 숫자나 특정 ID로 고정하지 않고, 결정론 주장에 필요한 필드와 실행 identity를 구분해 정규화했다. 그 뒤 두 개의 새 API 프로세스와 새 데이터베이스에서 전체 사례를 다시 실행했고 정규화 결과가 같았다. canonical 파일도 두 번 생성해 byte 단위 SHA-256이 동일한지 확인했다.

## source identity 누락을 반복해서 보완한 과정

초기 source identity에는 API route, answering, OpenAI adapter, interim store와 두 서비스 파일만 들어 있었다. 독립 검토는 검색 결과와 검증 결과를 직접 바꾸는 retrieval, verifier, corpus manifest, knowledge scope registry, verifier policy가 빠졌다고 지적했다. 이 파일들을 추가한 뒤에도 answering이 직접 호출하는 runtime knowledge loader와 runtime knowledge DB가 누락됐다는 추가 지적이 있었다. multi-worker lock을 추가한 뒤에는 공유 데이터베이스와 lock namespace를 결정하는 `data_lake.py`도 직접 의존 파일이 됐다.

최종 목록에는 이러한 파일을 모두 넣었다. 중요한 점은 source identity 목록을 한 번 채우고 끝냈다고 선언하지 않고, 실제 import와 data load 경로를 따라 결과에 영향을 주는 파일을 확인했다는 것이다. 각 파일 해시는 working tree가 아니라 Git HEAD의 blob을 사용한다. 서비스 파일도 service repository의 HEAD blob으로 계산한다. 이 방식은 R&D 증거가 어느 service commit의 client를 사용했는지 분명히 하고, uncommitted 사용자 변경을 증거에 잘못 포함하지 않는다.

## 동시 요청과 여러 worker에 대한 추가 검증

frozen E2E의 반복 요청은 순차 멱등성을 확인하지만, 같은 turn이 동시에 들어오는 상황은 별도 회귀 시험이 필요했다. 하나의 프로세스 안에서는 thread pool로 두 요청을 동시에 보내 provider call count가 하나인지, 두 응답의 answer와 binding hash가 같은지 확인했다. 한 응답은 최초 실행이고 다른 응답은 저장된 결과를 재사용해야 한다.

R&D 설정은 여러 worker를 허용하므로 Python 메모리 lock만으로는 충분하지 않았다. 최종 구현은 데이터베이스 경로별 고정 lock 파일에서 turn hash가 정한 byte 범위를 잠근다. 별도 subprocess 두 개를 동시에 시작해 같은 turn lock 구간에 들어가도록 하고, 첫 프로세스의 종료 시각 이전에 두 번째 프로세스가 진입하지 않는지 확인했다. OS 잠금 해제에서 예외가 생겨도 내부 thread lock과 참조 수 정리가 실행되도록 중첩 `finally`를 사용했다. 이 시험은 public 배포 환경의 부하 시험은 아니지만, 지원되는 multi-worker 구성에서 같은 turn의 공급자 호출을 직렬화하는 구현 불변식을 직접 확인한다.

## 관측한 결과와 숫자의 의미

canonical 실행에서는 frozen case 여덟 건이 모두 기대 status와 chunk 조건을 통과했다. 응급 사례 한 건은 공급자를 호출하지 않았고, 나머지 일곱 건은 첫 순회에서만 local failure provider를 호출했다. 두 번째 순회에서는 공급자 호출 수가 늘지 않았다. 저장소에는 agent run 여덟 건과 counseling answer step 여덟 건이 남았다. 응급 사례는 추천을 억제했으므로 recommendation run은 일곱 건이었다. 이 숫자는 runner가 코딩한 기대값을 맞추기 위한 장식이 아니라, 사례별 분기와 저장 경계를 합산한 결과다.

두 fresh run의 전체 답변, answer hash, verifier 결과, answer execution과 정규화한 recommendation execution은 같았다. canonical evidence 파일도 두 번 생성했을 때 byte-identical했다. 이 결과는 frozen dataset과 pinned source가 같고 local 503 장애가 같은 조건에서 결정론적 fallback이 재현된다는 뜻이다. 실제 외부 공급자가 성공했을 때 생성하는 자연어 답변의 결정론이나 실제 네트워크 장애의 모든 변형을 증명하지는 않는다.

## 독립 검토에서 확인한 결함과 최종 판단

첫 독립 검토는 네 개의 Important 결함을 발견했다. 외부 공급자 처리를 사용자 동의 없이 활성화할 수 있었고, 같은 turn의 동시 요청이 공급자를 중복 호출하고 서로 다른 미저장 답변을 반환할 수 있었다. source identity가 검색과 검증의 직접 의존 파일을 빠뜨렸고, fresh run 비교가 답변 본문과 verifier를 버리고 있었다. 수정 후 재검토에서는 여러 worker 사이의 lock이 없다는 결함과 lock map이 계속 커진다는 결함을 발견했다. 다시 수정한 뒤에는 runtime DB, data lake와 같은 추가 직접 의존 파일 누락과 잠금 해제 예외 cleanup도 확인했다.

각 발견은 테스트 결과가 이미 초록색이라는 이유로 무시하지 않았다. 공급자 동의, 동시 thread 요청, 별도 process 잠금, 저장된 binding 반환, 전체 답변 결정론, source blob 목록을 각각 코드와 시험으로 보완했다. 수정이 생길 때마다 source-first commit을 만들고 canonical evidence를 새로 생성했다. 따라서 이전 commit을 가리키는 `etc` draft나 오래된 hash는 최종 증거로 사용하지 않는다.

## 현재 단계와 남은 통합 조건

OP-090에 대해 입증된 것은 versioned frozen QA dataset, 실제 service TypeScript client, 실제 local R&D HTTP API, local SQLite 저장, 장애 공급자, 순차 재시도, 동시 요청, multi-worker 잠금과 두 fresh run 결정론이다. 이 범위는 기능이 구현됐다는 `IMPLEMENTED` 주장을 지지한다. 질문 유형별 시험이 단순 mock 함수에 머물지 않고 두 저장소의 실제 client/API 경계를 통과했다는 점도 확인됐다.

하지만 required stage는 `INTEGRATED`다. 통합 완료를 주장하려면 wellnessbox의 실제 `/api/chat` route가 R&D 응답을 사용하고, 같은 session의 서비스 메시지 저장과 R&D binding이 연결되며, 격리된 Prisma 시험 데이터베이스에서 그 관계가 검증돼야 한다. 현재 canonical evidence는 이 두 조건을 false로 명시한다. 공개 배포와 production operation도 실행하지 않았다. 따라서 OP-090은 `IMPLEMENTED/PARTIAL`로 남기고, 이후 서비스 전체 통합 증거가 생길 때만 `INTEGRATED`로 올린다.
