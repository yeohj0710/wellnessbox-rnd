# OP-018 같은 입력이 같은 정규화 결과와 해시를 만드는지 회귀 테스트한다.

## 요청 JSON이 달라도 건강 상태가 같을 수 있다

추천 요청에는 순서와 표기 때문에 생기는 차이가 많다. `Fish`와 ` fish `는 같은 알레르기이고, 목표 목록의 순서를 뒤집어도 사용자의 목표는 달라지지 않는다. 검사 관측 목록과 보충제 성분의 순서도 의미보다 전송 방식에 가깝다. 이런 차이를 그대로 hash하면 같은 건강 상태가 매번 다른 입력으로 기록된다. OP-018의 결과는 먼저 의미를 정규화한 snapshot을 만들고, 그 canonical JSON에 SHA-256을 적용해 같은 의미에는 같은 64자리 소문자 hex를 돌려주는 것이다.

이 hash는 원본 요청 파일의 checksum이 아니다. request ID처럼 실행마다 달라지는 값과 추천 결과처럼 입력이 아닌 값은 제외한다. 반대로 실제 판단 범위를 바꾸는 출처 동의와 effective availability는 포함한다. 그래야 표현만 바뀐 재요청은 같은 입력으로 인식하면서도, 유전자 저장 동의가 달라진 요청을 같은 상태로 잘못 합치지 않는다.

## intake snapshot이 hash의 재료를 한곳에서 정한다

`src/wellnessbox_rnd/domain/intake.py`의 `build_normalized_input_snapshot_v1`은 `normalize_request` 결과를 hash용 객체로 만든다. 사용자 profile, 목표, 증상, 질환, 알레르기, 위험 신호, 약물, 보충제, 식이 패턴, 검사 관측, 생활 습관, 출처 availability와 동의, 선호, sensor·genetic snapshot이 이 객체에 들어간다. 문자열은 canonical text를 사용하고 집합 의미의 목록은 안정된 순서로 정렬한다.

약물과 보충제는 Pydantic model dump를 만든 뒤 canonical JSON을 기준으로 정렬한다. 보충제 안의 ingredient도 같은 방식으로 정렬한다. 검사 관측과 식이 객체도 정렬된 model payload를 사용한다. float의 `-0.0`은 `0.0`과 같은 값으로 정리한다. 이 단계가 없으면 JSON 직렬화는 배열 순서와 부호 없는 0 표현에 따라 다른 바이트를 만들 수 있다.

`calculate_normalized_input_sha256_v1`은 snapshot을 key 정렬과 compact separator를 사용한 JSON으로 직렬화하고 UTF-8 바이트의 SHA-256을 계산한다. 출력은 64자리 소문자 hexadecimal 문자열이다. hash 함수가 자체적으로 입력을 다시 해석하지 않으므로 정규화 규칙과 hash 재료가 `build_normalized_input_snapshot_v1`에 모인다. 새 입력 필드가 판단에 참여하면 snapshot 계약과 회귀 테스트도 함께 갱신해야 한다.

## 동의로 제외된 값은 hash에도 영향을 주지 않는다

hash는 원본 payload 전체를 복사하지 않는다. OP-017의 consent gate를 통과한 정규화 결과를 사용한다. 국민건강보험 검사 사용 동의가 false이면 그 검사값을 5.8에서 58로 바꿔도 snapshot과 hash는 같다. 유전자 사용 동의가 false이면 variant와 tag가 비워지므로 유전자 자료가 absent인 입력과 같은 hash가 된다. 추천이 읽지 못하도록 막은 민감 정보가 hash를 통해 존재 차이를 남기는 일도 줄인다.

동의 자체는 별도 상태다. 예를 들어 genetic의 `allow_persistent_storage`를 false에서 true로 바꾸면 현재 추천 내용이 같더라도 snapshot과 hash가 달라진다. 저장 허용 범위가 바뀌었기 때문이다. declared availability와 effective availability를 함께 넣어 “자료가 없었음”과 “자료는 있다고 선언했지만 사용 동의가 없어 제외됨”도 감사 시 구분할 수 있다.

## 회귀 테스트가 동일성과 차이를 양쪽에서 고정한다

`tests/test_consent_and_input_hash_contracts.py`의 대표 동일성 테스트는 두 payload의 request ID, 목표·검사·성분 순서, 증상·알레르기·식이 표기를 바꾼다. 두 요청을 각각 정규화한 뒤 snapshot 객체가 같고 SHA-256이 같은지 확인한다. 직렬화된 snapshot에 `request_id`가 없는지와 hash가 `[0-9a-f]{64}` 형식인지도 검사한다. 이 테스트는 단순히 hash 함수를 두 번 부르는 것이 아니라 서로 다른 원본 표현이 하나의 정규화 결과로 모이는지를 검증한다.

양의 0.0과 음의 0.0 운동 시간은 같은 snapshot과 hash를 만든다. 새 lactating 필드가 명시되지 않은 legacy 요청과 `lactating=false` 요청도 같은 의미이므로 snapshot에 불필요한 false 값을 넣지 않고 같은 hash를 유지한다. 반대로 genetic 저장 동의를 바꾸는 테스트는 hash가 달라져야 한다. 같은 값만 확인하지 않고 의미가 달라질 때 분리되는지도 함께 검사한다.

대표 fixture `data/samples/api_recommend_consent_hash_request_v1.json`은 실제 schema와 API가 읽는 고정 입력이다. 테스트는 fixture에서 hash를 계산하고, survey·wearable 추천 허용 집합과 저장 허용 집합을 확인한 뒤 `/v1/recommend`에서 200 응답을 받는다. OpenAPI의 `consent_scoped_deterministic_input` 예제도 fixture와 같은 동의 객체를 갖는다. 이렇게 schema, 설명 예제, 실제 API, hash 회귀가 한 입력 계약에 연결된다.

## 재현 가능한 hash와 전체 운영 완료는 다르다

OP-018의 핵심 구현은 `5d7ccf4` 커밋의 snapshot builder, SHA-256 계산기, fixture와 계약 테스트다. manifest는 `src/wellnessbox_rnd/domain/intake.py`, 대표 fixture, `tests/test_consent_and_input_hash_contracts.py`를 증거로 등록한다. canonical manifest 감사가 경로와 Git 추적 여부를 확인하고, completion generator는 required `IMPLEMENTED`와 claimed `IMPLEMENTED`가 일치하므로 COMPLETE로 판정한다.

현재 hash는 정규화 입력의 동일성을 표시한다. 원본 데이터의 진위, 사용자의 실제 신원, production 저장 레코드, 암호학적 서명, 외부 timestamp authority를 증명하지 않는다. hash 충돌에 대한 별도 업무 보증이나 법적 동의 receipt도 아니다. 이번 보고서 backfill은 구현 코드, 서비스, production, 원천·frozen·학습 데이터, 모델, simulation을 변경하지 않았다. 공식 frozen evaluation 256건의 일곱 지표와 replay·slice delta는 0이다. 운영 단계에는 실제 요청·저장 레코드가 같은 canonical hash를 기록하고 재조회할 수 있다는 별도 receipt가 필요하다.
## 입력값을 먼저 고정한 이유
이 그룹에서 입력을 세분화한 이유는 값 하나를 편의상 문자열로 받으면 안전 판단과 효과 해석이 서로 다른 의미를 사용할 수 있기 때문이다. 단위, 누락, 지원하지 않는 입력, 동의 범위를 먼저 고정해야 뒤의 계산과 차단 결과를 설명할 수 있다.

`OP-018`는 “같은 입력이 같은 정규화 결과와 해시를 만드는지 회귀 테스트한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`, `wellnessbox-rnd/data/samples/api_recommend_consent_hash_request_v1.json`
- 테스트·실행: `wellnessbox-rnd/tests/test_consent_and_input_hash_contracts.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
