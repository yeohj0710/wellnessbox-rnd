# OP-015 알레르기, 식이 패턴, 생활 습관 입력을 정규화한다.

## 입력 이름이 조금 달라도 같은 건강 신호로 읽어야 한다

원본 계획 16쪽은 성별, 연령, 병력, 증상, 복용 약물, 생활 습관처럼 출처와 표현 방식이 다른 사용자 정보를 개인 특성 파라미터로 모으라고 요구한다. OP-015는 이 가운데 알레르기, 식이 패턴, 생활 습관을 추천 엔진이 반복해서 읽을 수 있는 형태로 정리한다. 목표는 사용자가 `Fish`, ` fish `처럼 입력한 값을 서로 다른 알레르기로 세거나, `Mediterranean   Diet`와 `mediterranean diet`를 별개 식이 패턴으로 처리하지 않는 것이다. 정규화 결과는 안전 규칙과 효과·정책 모델이 같은 의미를 같은 key로 사용하게 해야 한다.

이 요구가 필요한 이유는 입력 문자열의 대소문자나 공백이 추천 결과를 바꾸면 안 되기 때문이다. 반대로 서로 다른 개념을 과도하게 합쳐서도 안 된다. 구현은 자유 입력을 무제한 추론하는 별도 자연어 시스템을 만들지 않았다. 기존 `RecommendationRequest`와 intake 경로에서 공백과 대소문자를 정리하고, 구조화된 식이 패턴에는 code와 표시 이름을 따로 보존한다. 이 선택은 기존 추천 API, 안전 엔진, 효과 모델과 정책 모델을 재사용하면서 정규화 책임을 한곳에 둔다.

## 요청 schema와 intake가 정규화 경계를 나눈다

`src/wellnessbox_rnd/schemas/recommendation.py`의 `RecommendationRequest`는 알레르기 목록, `DietaryPatternInput` 목록, `LifestyleInput`을 받는다. 식이 패턴은 문자열 또는 code와 display name을 가진 객체로 입력할 수 있다. 생활 습관은 수면 시간, 스트레스 수준, 활동 수준, 운동 시간, 흡연, 주간 음주량, 하루 카페인 섭취량처럼 의미가 정해진 필드만 허용한다. 알 수 없는 필드는 strict schema가 거부한다. 숫자 필드에는 범위가 있으며 Python의 boolean을 숫자 0이나 1로 받아들이지 않는다.

`src/wellnessbox_rnd/domain/intake.py`의 `normalize_request`는 schema를 통과한 값을 실제 엔진 입력으로 바꾼다. 알레르기는 앞뒤 공백과 연속 공백, 대소문자를 정리한 뒤 중복을 제거해 정렬한다. 식이 패턴도 canonical code를 만들고, 같은 code가 반복되면 하나로 합치되 사람이 읽을 display name은 보존한다. 생활 습관은 `NormalizedLifestyle`에 옮기고 입력된 운동 시간과 카페인 양이 있다는 signal flag를 추가한다. 따라서 뒤쪽 모델은 원래 JSON의 표기 차이를 다시 해석하지 않는다.

입력 예시는 `data/samples/api_recommend_diet_lifestyle_lab_request_v1.json`에 고정돼 있다. 이 fixture에는 중복된 `Fish`, `fish`, `Peanut`, 객체와 문자열이 섞인 식이 패턴, 주 95분 운동, 하루 240mg 카페인이 들어 있다. 정규화 결과는 알레르기 `fish`, `peanut`, 식이 code `low sodium`, `mediterranean diet`가 된다. 이 fixture는 설명용 문서에 머물지 않고 API와 모델 경로 테스트가 함께 읽는 실행 입력이다.

## 기존 효과·정책 모델이 같은 feature를 사용한다

`src/wellnessbox_rnd/models/efficacy_model_v0.py`와 `src/wellnessbox_rnd/models/policy_model_v0.py`는 별도의 식이·생활 모델을 만들지 않는다. 두 runtime feature builder가 intake의 공통 feature 사전을 사용한다. 알레르기는 `allergy::fish`, 식이 패턴은 `dietary_pattern::mediterranean diet`처럼 안정된 key가 되고, 운동 시간과 카페인 양은 정해진 상한으로 scale된다. 빈 값은 임의의 평균값으로 채우지 않는다. 입력이 없으면 수치 feature는 0.0이고 별도의 `*_missing` feature는 1.0이 되므로 뒤쪽 로직이 실제 0과 결측을 구분할 수 있다.

`apps/inference_api/routes/recommend.py`는 같은 fixture 계약을 OpenAPI 예제로 노출한다. `/v1/recommend`는 구조화 요청을 Pydantic schema로 먼저 검사하고 기존 추천 실행 경로로 전달한다. 올바른 예시는 200 응답을 내며, 운동 시간에 `true`를 넣거나 지원하지 않는 생활 필드를 추가하면 422로 실패한다. 이 실패 방식은 잘못된 값을 조용히 보정해 건강 신호로 사용하는 것보다 안전하다.

## 테스트가 성공과 실패를 함께 고정한다

`tests/test_diet_lifestyle_lab_input_contracts.py`는 중복과 표기 차이가 손실 없이 정규화되는지 확인한다. 알레르기 목록과 set, 식이 code 순서와 display name, 운동·카페인 수치, 세 가지 context flag를 직접 비교한다. 같은 테스트는 efficacy와 policy feature 양쪽에 알레르기와 식이 key가 들어가고 수치 feature가 예상 비율로 scale되는지도 검사한다. OpenAPI schema와 실제 API 응답까지 확인하므로 모델 객체만 통과하고 서비스 경계가 빠지는 상태를 허용하지 않는다.

경계값 테스트는 음수 운동 시간을 거부하고, 새 숫자 필드의 boolean을 모델과 API 경계에서 거부한다. legacy 요청은 새 필드를 생략해도 빈 식이 목록과 `None` 생활 수치로 계속 읽힌다. 이 호환성은 과거 요청을 억지로 새 정보가 있는 것처럼 만들지 않으면서 새 입력만 엄격하게 검사한다. 지원하지 않는 필드는 `tests/test_unsupported_input_contracts.py`가 별도로 fail closed 동작을 확인한다.

## 증거가 말하는 단계와 말하지 않는 단계

핵심 구현은 `93714c62` 커밋에서 schema, intake, 모델 feature, API 예제, fixture와 계약 테스트로 함께 들어왔다. 현재 manifest는 이 여섯 구현 파일과 `tests/test_diet_lifestyle_lab_input_contracts.py`를 OP-015 증거로 등록한다. original-plan 감사기는 등록 경로가 R&D 저장소 안에 있고 Git으로 추적되는지 검사한다. completion generator는 required stage와 claimed stage가 모두 `IMPLEMENTED`이고 감사 issue가 없으므로 OP-015를 COMPLETE로 판정한다.

이 결과는 구조화 입력 구현을 증명한다. wellnessbox production 화면이 이 필드를 실제 사용자에게 받고 있다는 증거, 실제 사용자 데이터 운영, 의료 전문가의 외부 검증은 아니다. 이번 backfill은 서비스 저장소, production 설정, 원천 데이터, frozen evaluation, 학습 데이터, 모델 artifact, simulation 정책을 바꾸지 않았다. 따라서 공식 frozen 256건의 일곱 지표, replay, weakest slice delta는 모두 0이다. 다음 단계가 필요하다면 실제 서비스 payload가 이 계약을 호출한 통합 receipt와 동의가 확인된 운영 기록을 별도 증거로 남겨야 한다.
