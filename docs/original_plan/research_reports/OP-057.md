# OP-057 실제 사용자 입력으로 PRO 점수를 수정하고 즉시 재계산한다.

## 사용자가 답을 고쳤을 때 필요한 동작

설문 저장 뒤 오입력을 발견했는데 화면의 숫자만 바꾸고 효과 해석을 그대로 두면 서로 모순된 결과가 남는다. OP-057은 같은 시점의 사용자 입력이 다시 들어왔을 때 원래 사건의 식별 관계를 유지하면서 점수, 효과 해석과 다음 행동을 즉시 다시 계산하도록 요구한다. “실제 사용자 입력”은 사람이 서비스 화면에서 입력할 수 있는 경로가 연결됐다는 뜻이다. 현재 기준 실행이 실제 사람의 건강 결과를 사용했다는 뜻은 아니다.

핵심 구현 경로 `wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_correction.py`는 수정 대상이 해당 실행의 엄격한 PRO 후속 사건인지 먼저 확인한다. 복용 전 사건은 수정 대상으로 받지 않고, 같은 계획의 복용 전 사건이 정확히 하나 있어야 한다. 추천 사건과 최적화 사건도 각각 하나씩 있어야 하며 선택 성분 목록이 남아 있어야 한다. 이 조건을 모두 만족한 뒤에만 수정 원장에 보정 내용을 기록한다.

## 즉시 재계산과 이력 보존 방식

`correct_and_recalculate_pro_followup_v1`은 새 입력으로 점수 해석과 계획 연결 정보를 먼저 계산한다. 계산이 성공한 뒤 `DataMutationLedger`가 원래 사건의 자료 상태를 `CORRECTED`로 바꾸고 수정 이력을 추가한다. 평가 ID, 계획 ID, 시점, 예정일, 실제 경과일과 관찰 시각은 수정할 수 없다. 설문명·채점 버전·시작 분포 지문도 유지해야 한다. 사용자는 문항 답과 순응도 같은 관찰 내용을 바로잡을 수 있지만, 보정이라는 이름으로 다른 사람·다른 계획·다른 시점의 사건을 만들 수는 없다.

`src/wellnessbox_rnd/orchestration/pro_plan_service.py`는 같은 시점 기록이 이미 있으면 새 사건을 추가하지 않고 보정 경로를 고른다. 새 문항 답을 공식 설문 계약으로 다시 채점하고, 기존 복용 전 분포로 건강 Z 점수와 백분위를 다시 만든다. 그 결과로 효과 해석과 다음 행동을 계산해 `recalculated_immediately=true`와 함께 반환한다. 보정 멱등 키에는 수정 대상 사건과 새 내용의 지문이 들어가므로 같은 보정 요청을 반복하면 수정 이력 한 건을 재사용한다.

## 서비스 화면까지 연결한 범위

R&D API는 인증 토큰이 필요한 `/v1/interim/pro/followups`와 `/v1/interim/pro/followups/correct-and-recalculate`를 제공한다. 서비스 쪽 등록 경로 `wellnessbox/app/api/tips/pro/effects/route.ts`는 로그인 세션을 확인한 뒤 사용자의 원래 ID 대신 가명 ID를 만들고, 브라우저가 보낸 `profile_id`는 버린다. `wellnessbox/lib/tips/pro-study-rnd-client.ts`는 같은 계획과 시점의 답을 서비스 API로 보내며 반환된 `operation`, 해석, 계획 연결 정보와 다음 행동의 형식을 다시 확인한다.

`wellnessbox/components/tips/ProStudySimulation.tsx`에서는 사용자가 복용 전 입력을 저장하고 2주 또는 4주 답을 다시 제출할 수 있다. 같은 주차를 다시 저장하면 R&D가 `corrected`를 반환하고 화면 상태도 새 원점수·해석·다음 행동으로 교체된다. 후속 입력 전에는 사전 입력값이 실제 상태와 맞는지 사용자가 확인해야 한다. 이 연결은 실제 UI 구성요소가 호출 함수를 사용한다는 코드 근거이며, 브라우저에서 사람이 끝까지 눌러 본 운영 증거와는 구분된다.

## 실패를 먼저 계산하고 저장은 나중에 한 이유

보정 과정에서 추천·최적화 사건이 사라졌거나 계획 연결이 깨졌다면 수정 자체를 남기지 않는다. `tests/test_pro_followup_effects.py`는 최적화 사건을 지운 뒤 보정을 시도해 `recommendation_lineage_events_required` 오류가 나는지, 원래 점수 8과 `ACTIVE` 상태 및 수정 이력 0건이 그대로인지 확인한다. 효과 재계산과 연결 정보 구성을 저장보다 앞에 둔 이유가 이 원자성 보장이다. 중간 실패가 “입력은 바뀌었지만 해석은 옛값”인 상태를 만들지 않는다.

보고서 검증 중 서비스 시험을 `tsx`로 직접 실행했을 때 `server-only` 모듈 조건이 없어 한 번 실패했다. `package.json`에 등록된 방식대로 Node에 `--conditions=react-server`를 추가하자 `check-tips-pro-correction-route.cts`와 `check-tips-pro-study-rnd-client.cts`가 모두 종료 코드 0으로 통과했다. 이는 코드 결함 수정이 아니라 서버 전용 모듈을 불러오는 공식 시험 실행 조건을 따른 조정이다. R&D의 `tests/test_pro_followup_effects.py`와 `tests/test_pro_plan_service.py`도 현재 실행에서 통과했다.

## 통합 기준 실행 결과와 남은 경계

기준 증거 `wellnessbox-rnd/data/original_plan/evidence/op057_op058_pro_correction_plan_lineage_smoke_v1.json`은 실제 서비스 TypeScript 경로가 로컬 HTTP로 실행 중인 R&D API를 호출한 결과다. 복용 전 원점수는 10, 최초 후속 점수는 8, 사용자 보정 뒤 점수는 7이었다. 저장 자료 상태는 `CORRECTED`, 엄격한 PRO 사건 수는 복용 전과 2주 후 두 건으로 유지됐고 `recalculated_immediately`는 참이었다. 인증된 계획 등록·후속 생성·후속 보정이 각각 한 번씩 관측됐다.

현재 단계는 요구 단계와 같은 `INTEGRATED`다. 서비스의 인증·가명화 경로, 실제 TypeScript 호출 코드, 로컬 R&D HTTP API와 SQLite 보정까지 연결됐다는 뜻이다. 기준 증거는 동시에 `browser_render_proven=false`, `production_deployment_proven=false`, `production_operation_proven=false`, `real_world_outcome_used=false`를 명시한다. 실제 사용자 운영, 공개 배포, 브라우저 수동 확인과 임상적으로 올바른 재해석은 `확인되지 않음`으로 남긴다. 조사 범위는 매니페스트의 R&D 구현·시험·통합 증거와 등록된 서비스 경로·QA·화면 구성요소까지였으며, `OPERATED` 이상을 주장하지 않는다.
