# OP-057 실제 사용자 입력으로 PRO 점수를 수정하고 즉시 재계산한다.

## 같은 추적 시점의 재제출은 새 관찰이 아니라 수정과 재계산으로 처리한다

OP-057은 사용자가 이미 제출한 추적 PRO 응답을 고쳤을 때 같은 시점 이벤트를 하나 더 만들지 않고 수정과 재계산으로 처리하도록 요구한다. 계획 서비스는 같은 `plan_id`, 평가 도구, 추적 시점의 제출이 처음이면 새 이벤트를 만들고, 이미 있으면 데이터 수정 원장에 변경을 기록한 뒤 관찰 효과를 즉시 다시 계산한다. 현재 수정 기록은 프로필 ID, 수정 연산, 이전·결과 저장 내용의 해시와 수정 계보를 남기고 대상 이벤트에는 새 점수를 저장한다. 이전 점수 원문과 별도 수정 사유 필드는 보존하지 않으므로 그 두 항목까지 남는다고 확대해서는 안 된다.

매니페스트의 연구 측 핵심 구현은 `wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_correction.py`와 `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`다. API 경계는 `wellnessbox-rnd/apps/inference_api/routes/interim.py`, 제품 서버 경계는 `wellnessbox/lib/server/wb-rnd-interim-route.ts`, 사용자 경로는 `wellnessbox/app/api/tips/pro/effects/route.ts`, `wellnessbox/app/api/tips/pro/plans/route.ts`, `wellnessbox/lib/tips/pro-study-rnd-client.ts`, `wellnessbox/components/tips/ProStudySimulation.tsx`에 있다. 요구사항은 연구 라이브러리 안의 함수 호출에 그치지 않고 제품 서버를 거쳐 같은 수정 결과를 돌려받는 통합까지 포함한다.

기능 도입 전에는 저장된 PRO 이벤트를 일반 수정 원장으로 바꿀 수는 있어도, 수정이 성공한 즉시 효과를 다시 계산하고 추천·최적화 이벤트와 같은 계획 계보를 검증하는 단일 트랜잭션 경계가 없었다. 같은 추적 시점의 재시도를 신규 관찰과 구분하는 계획 서비스 규칙과 사용자 화면의 대체 표시도 없었다.

## 재계산 모델은 수정 이벤트와 추천 계보를 한 결과로 묶는다

`PRORecommendationEffectLineageV1`은 실행 ID, 계획 ID, 추천 이벤트 ID, 최적화 이벤트 ID, 선택 성분 키, 시작·추적 평가 ID를 보관하고 인과 해석 허용값을 `false`로 고정한다. `PROCorrectionRecalculationResultV1`은 `EventMutationResult`, 새 `PROFollowUpEffectInterpretationV1`, 추천 효과 계보, `recalculated_immediately=true`를 한 결과로 묶고 수정 대상과 계획 식별자를 다시 대조한다.

`correct_and_recalculate_pro_followup_v1`은 수정 대상과 소유자, 엄격한 복용 후 PRO 이벤트 여부를 검사한다. 같은 실행에서 일치하는 시작 이벤트가 정확히 하나이고 추천 이벤트와 최적화 이벤트가 각각 하나이며 선택 성분 목록이 있는지 확인한다. 함수는 수정될 페이로드로 효과 해석과 추천 계보를 먼저 계산해 유효성을 확인한 뒤 `DataMutationLedger.apply`를 호출한다. 따라서 추천 계보가 불완전해 재계산할 수 없는 요청은 원본 이벤트를 바꾸지 않는다.

`wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`의 `enroll_pro_plan_v1`은 설문 저장 동의와 점수 계약을 확인한 뒤 실행·계획·시작 점수를 묶는다. `record_or_correct_pro_followup_v1`은 저장된 시작 분포로 추적 점수를 만들고, 같은 시점이 이미 있으면 위 수정 함수를 호출한다. idempotency 해시는 점수 일부가 아니라 전체 대체 페이로드를 반영하므로 순응도만 바꾼 수정도 구별한다. 반복 등록은 같은 요청과 시작 평가일 때 기존 실행을 재사용하지만, 같은 재시도 키로 시작 평가 식별자를 바꾸면 충돌로 거부한다.

## 제품 서버는 사용자 세션을 연구 프로필로 바꾸고 내부 API만 호출한다

제품의 plans 경로는 사용자 세션과 설문 저장 동의를 요구하고 `requestId`와 데이터 등급을 검증한다. effects 경로도 사용자 세션을 요구하지만 별도의 동의·`requestId`·데이터 등급 필드를 다시 받지는 않는다. 두 경로의 서버 helper는 앱 사용자 식별자를 HMAC 규칙으로 가명화하며, 클라이언트가 보낸 `profile_id`를 연구 API 식별자로 신뢰하지 않는다. 등록된 연구 프로필이 있으면 서버가 확인한 연결을 사용하고, 추적 요청에서도 같은 가명 식별자를 보존한다. 신규 추적 저장은 연구 원장에서 설문 지속 저장 동의를 다시 확인하지만, 같은 시점 수정 경로의 동의 철회 동작은 등록 테스트가 직접 다루지 않는다.

`callWbRndInterim`은 등록된 연산만 내부 토큰으로 호출하고 제한시간과 회로 차단 정책을 적용한다. 상태를 바꾸는 POST 요청은 자동 재시도하지 않아 중복 수정 위험을 줄인다. `pro-study-rnd-client.ts`는 plans/effects 응답을 검증해 화면 컴포넌트에 전달하고, `ProStudySimulation.tsx`는 같은 시점 수정 응답이 오면 기존 행을 새 결과로 대체한다. 이 파일 검사는 호출과 상태 갱신 구조를 증명하지만 실제 브라우저 렌더링이나 사용성까지 증명하지는 않는다.

## 실패한 재계산이 원본을 바꾸던 순서 문제가 공통 함수에서 수정됐다

커밋 `ea073ad`은 수정·재계산 모델과 연구 API를 처음 추가했다. 초기 순서에서는 수정 원장에 변경을 반영한 뒤 추천 계보를 검증할 수 있어, 필수 최적화 이벤트가 없으면 재계산은 실패하면서 원본 이벤트는 이미 바뀌는 문제가 있었다. 커밋 `c8c0767`은 예상 수정 페이로드로 해석과 계보를 먼저 검증하고 마지막에만 수정을 커밋하도록 순서를 바꿨다. `test_failed_recalculation_does_not_commit_correction`은 최적화 이벤트가 없는 경우 `recommendation_lineage_events_required` 오류가 나고, 원점수 8의 기존 이벤트가 `ACTIVE` 상태로 남으며 수정 기록 수가 0임을 확인한다.

커밋 `c1bb470`은 등록과 같은 시점 수정의 재시도 정체성을 보강했고, `86823c3`은 같은 등록 재시도에서 시작 평가 식별자를 바꾸는 충돌을 거부했다. 제품 저장소에서는 `b0a7af9`이 최초 수정 서버 경로를 추가했고, `252041d`가 계획 등록과 추적 생성·수정 경로 및 화면 연동으로 확장했다. `d4c197e`는 안정적인 요청 식별자를, `9dfc1d0`은 복구 가능한 오류 처리를 보강했다. 후속 `f545b83`은 추적 호출에서도 서버가 결정한 연구 프로필 가명을 보존하도록 고쳤다.

## 단위 테스트는 수정 성공, 실패 원자성, 재시도 충돌을 나눠 검증한다

`wellnessbox-rnd/tests/test_pro_followup_effects.py`의 `test_user_correction_recalculates_effect_and_links_recommendation_plan`에서는 사용자 수정 뒤 다시 계산한 효과가 같은 추천 계획에 연결되어야 한다. `test_pro_correction_api_returns_immediate_recalculation`은 연구 API 응답에 수정 기록과 재계산 결과가 즉시 돌아와야 한다고 정한다. `test_failed_recalculation_does_not_commit_correction`은 앞서 설명한 실패 원자성 경계를 고정한다.

`wellnessbox-rnd/tests/test_pro_plan_service.py`의 `test_followup_create_then_same_timepoint_correction_recalculates`는 첫 제출은 생성, 같은 시점의 다음 제출은 수정이 되는지 확인한다. `test_correction_can_change_adherence_without_changing_score`는 원점수가 같아도 순응도 변화가 새 해석과 idempotency 내용에 반영되는지 확인한다. `test_followup_rejects_cross_plan_and_cross_instrument`는 다른 계획이나 평가 도구의 시작 분포를 섞지 못하게 한다. `test_enrollment_retry_reuses_execution_and_baseline`과 `test_enrollment_retry_rejects_changed_baseline_identity`는 동일 재시도와 충돌 재시도를 구분한다. `test_pro_plan_and_followup_api_require_token_and_persist`는 내부 토큰과 영속 경계를 함께 확인한다.

현재 `test_pro_followup_effects.py` 23개와 `test_pro_plan_service.py` 20개를 포함한 핵심 네 파일의 79개 테스트가 모두 통과했다. 제품 저장소에서 `npm run qa:tips:pro-correction`과 `npm run qa:tips:pro-study-rnd`도 모두 종료 코드 0으로 통과했다. correction QA는 package script에 지정된 `node --conditions=react-server --import tsx`로 실행되고, client QA는 `node --import tsx`로 실행된다. 두 QA 모두 React Server 조건이 필요하다는 기존 설명은 사실과 달라 바로잡았다. correction QA 중 데이터베이스 URL 설정 충돌 경고가 출력됐지만 검사 실패로 이어지지는 않았다.

## 통합 스모크는 실제 HTTP 경계를 거쳤지만 등록 해시는 현재 소스와 다르다

`wellnessbox-rnd/data/original_plan/evidence/op057_op058_pro_correction_plan_lineage_smoke_v1.json`은 로컬 uvicorn 연구 API와 제품의 TypeScript 서버 helper를 실제 HTTP로 연결한다. 같은 실행에서 시작 원점수 10을 등록하고 추적 원점수 8을 만든 뒤 7로 수정했으며, 엄격한 PRO 이벤트 수는 시작과 추적 두 개로 유지됐다. 수정 결과는 같은 실행·계획을 보존하고 추천·최적화 이벤트의 `magnesium_glycinate`, `l_theanine` 선택 성분 계보와 연결됐다. 이 실행은 인메모리 함수만 직접 부른 것이 아니라 두 저장소의 서버 경계를 왕복했다는 통합 근거다.

다만 증거의 합산 소스 해시 `04d6548…`는 현재 등록 경로에서 다시 계산한 `611873ea…`와 다르다. 당시 연구 저장소 커밋은 `a5a6908`, 제품 저장소 커밋은 `a24b6c`였고, 조사한 관련 경로에는 각각 `651984d`와 `f545b83`까지 후속 변경이 있다. 매니페스트의 테스트 경로인 `wellnessbox/scripts/qa/check-tips-pro-correction-route.cts`는 현재 QA로 별도 검증했지만, 정식 스모크의 합산 소스 경로에는 포함되지 않는다. 그러므로 과거 통합 JSON과 현재 QA 통과를 별도 증거로 구분해야 한다.

## 현재 단계는 INTEGRATED이며 브라우저와 운영 사용은 남아 있다

매니페스트의 OP-057 요구 단계와 현재 단계는 `INTEGRATED`다. 연구 모듈, 연구 API, 제품 서버 route/helper, 제품 client/component가 연결되고 로컬 HTTP 왕복 스모크와 현재 서버·클라이언트 QA가 통과했으므로 통합 단계 근거는 있다. 반면 OP-057에 등록된 운영 영수증은 없으며 `OPERATED`로 올릴 근거도 없다.

실제 브라우저에서 입력·수정·대체 표시를 수행한 E2E 기록, 프로덕션 배포, 실제 사용자 장기 세션, 프로세스 재시작 뒤 영속 복구, 동시 수정 충돌, 네트워크 중단 직후 재제출, 접근성·오류 문구 검증은 확인되지 않았다. 수정 전 점수 원문과 수정 사유를 수정 원장에 별도 보존하는 기능, 동의 철회 뒤 같은 시점 수정을 차단하는 동작도 현재 등록 증거에 없다. 합성 점수와 로컬 서버를 쓴 통합 결과는 임상 효과나 실제 사용성을 입증하지 않는다. OP-057의 완료 경계는 인증된 제품 서버 경로로 수정 요청을 보내고 연구 서비스가 원자적으로 수정·재계산해 같은 계획 계보를 반환하는 통합까지다.
## 효과를 측정할 때 분리한 것
효과를 말하려면 예측값과 실제 복용 전후 관측값을 섞지 않아야 한다. 이 그룹은 PRO 원점수, 표준화, 개인별 변화, 집단 평균, 신뢰구간, 순응도와 이상사례를 각각 기록해 숫자가 무엇을 의미하는지 확인한다.

`OP-057`는 “실제 사용자 입력으로 PRO 점수를 수정하고 즉시 재계산한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_correction.py`, `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`, `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox/lib/server/wb-rnd-interim-route.ts` 외 4개
- 테스트·실행: `wellnessbox-rnd/tests/test_pro_followup_effects.py`, `wellnessbox-rnd/tests/test_pro_plan_service.py`, `wellnessbox/scripts/qa/check-tips-pro-correction-route.cts`, `wellnessbox/scripts/qa/check-tips-pro-study-rnd-client.cts` 외 2개
- 통합 증거: `wellnessbox/lib/server/wb-rnd-interim-client.ts`, `wellnessbox/lib/tips/pro-study-rnd-client.ts`, `wellnessbox/components/tips/ProStudySimulation.tsx`, `wellnessbox/scripts/qa/run-tips-pro-correction-client.cts` 외 1개

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
