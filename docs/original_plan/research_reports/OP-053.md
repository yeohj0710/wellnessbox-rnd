# OP-053 복용 전, 2주, 4주, 중단 시점 PRO 이벤트를 저장한다.

## 요구사항은 네 시점의 순서와 연구 식별자를 영속 기록에서 보존하는 것이다

OP-053은 환자보고결과(PRO) 추적을 일회성 점수 계산으로 끝내지 않고 `pre_intake`, `week_2`, `week_4`, `discontinuation` 이벤트로 저장하도록 요구한다. 정식 해석 계약은 `wellnessbox-rnd/data/contracts/pro_followup_interpretation_v1.json`이며, `pre_intake`는 계획 시작 0일, `week_2`는 14일, `week_4`는 28일로 고정한다. 중단 시점에는 고정 예정일이 없지만 중단 사유가 있어야 한다. 정상 순서는 복용 전에서 2주 또는 중단, 2주에서 4주 또는 중단으로 진행하며, 4주 뒤에는 중단만 허용하고 중단 이후 이벤트는 받지 않는다.

모든 추적 이벤트는 같은 `plan_id`, 데이터 등급, 평가 도구, 점수 계약 버전, 시작 분포 해시를 유지해야 한다. `assessment_id`는 중복될 수 없고 `actual_day`와 `observed_at`은 앞선 이벤트보다 증가해야 한다. 복용 전 이벤트에는 순응도와 이상사례가 없어야 하고, 복용 후 이벤트에는 순응도 창이 있어야 한다. 영속화 단계에서는 설문 동의가 유효해야 하며 같은 idempotency key의 재시도는 내용이 완전히 같을 때만 기존 이벤트를 재사용한다.

도입 전 부모 커밋에는 시점 계약과 전용 추적 모델이 없었고, 실행 원장도 일반 이벤트와 엄격한 PRO 이벤트를 구별해 순서·점수 계보를 검증하지 않았다. 따라서 이전 상태의 핵심 부족은 네 시점의 이름만 없었던 것이 아니라, 잘못된 순서나 다른 계획의 점수가 영속 원장에 들어가기 전에 막을 불변조건이 없었다는 점이다.

## 추적 모델과 실행 원장은 저장 직전에 같은 규칙을 다시 검사한다

`wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_followup.py`의 `PROAdherenceWindowV1`은 예정 복용 수, 실제 복용 수, 누락 수가 서로 맞는지 확인하고 순응률을 다시 계산한다. `PROAdverseEventContextV1`은 이상사례의 존재와 중증도 문맥을 담는다. `PROFollowUpEventV1`은 시간대가 있는 관측 시각, 계획일, 시점, 평가·계획·분포 식별자를 한 이벤트로 묶는다. `normalize_pro_followup_event_v1`과 `validate_pro_followup_sequence_v1`은 모델을 재검증하고 전체 순서를 확인한다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/data_lake.py`의 `ExecutionLedger.append_event`는 엄격한 PRO 저장에 `followup_evaluation` 이벤트 유형과 `survey` 출처를 동시에 요구한다. 설문 출처의 지속 저장 동의를 확인하고, 추천 응답의 계획 ID와 이벤트 계획 ID도 대조한다. 이미 저장된 엄격한 이벤트까지 다시 읽어 새 이벤트와 함께 순서를 검사한 뒤에만 추가하므로, API 앞단 검사를 건너뛰어도 원장이 마지막 방어선이 된다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/data_mutation.py`의 `DataMutationLedger.apply`는 일반 이벤트를 엄격한 PRO 이벤트로 바꾸거나 그 반대로 바꾸는 수정을 거부한다. 엄격한 PRO를 수정할 때는 `assessment_id`, `plan_id`, 데이터 등급, 시점, 예정일, 실제일, 관측 시각, 점수 계약 버전, 시작 분포 해시를 보존하고 새 점수도 다시 검증한다. 수정 기록은 이전·새 페이로드 해시와 수정 계보를 남긴다.

## 실패 사례가 확인된 뒤 우회 경로 세 가지가 닫혔다

커밋 `334bd70`은 시점 계약, 추적 모델, 실행 원장·수정 원장 연동, 단위 테스트와 스모크를 처음 추가했다. 이후 커밋 `83997c1`은 엄격한 PRO 페이로드를 `conversation` 이벤트처럼 위장해 저장하는 경로, 중복 `assessment_id`, 뒤로 가는 `observed_at`을 실패시키도록 보강했다. 이 커밋은 대응 단위 테스트와 스모크 실패 항목도 함께 추가했으므로, 우회 가능성 발견과 수정 내용이 같은 변경 이력으로 확인된다. 커밋 `706fb4a`는 보강된 실행 결과를 정식 증거로 등록했다.

이 이력은 “모든 저장 경로가 처음부터 안전했다”는 설명을 허용하지 않는다. 초기 구현 뒤에 일반 이벤트 분류를 이용한 우회와 시간·평가 식별자 검증 누락이 발견됐고, 공통 영속 경계에서 차단하는 방식으로 수정됐다. 반대로 저장소에는 실제 운영 데이터가 이 결함으로 오염됐다는 기록도 없으므로, 코드 결함과 운영 사고를 같은 사실처럼 서술하지 않는다.

## 테스트는 정상 네 시점, 잘못된 순서, 수정 시 식별자 보존을 나눠 검증한다

`wellnessbox-rnd/tests/test_pro_followup_effects.py`의 `test_existing_execution_ledger_persists_all_four_timepoints_in_order`는 복용 전·2주·4주·중단 이벤트가 순서대로 영속화됨을 확인한다. `test_followup_sequence_and_schema_fail_closed_inside_ledger`는 원장 내부에서 잘못된 시점 전이와 스키마가 거부됨을 확인하고, `test_strict_pro_payload_cannot_be_persisted_as_conversation`은 이벤트 유형 위장을 차단한다. 같은 파일의 `test_execution_event_correction_cannot_convert_generic_event_to_strict_pro`는 일반·엄격 이벤트 사이 변환을 막고, `test_execution_event_correction_preserves_identity_and_revalidates_scores`는 수정 후에도 식별자와 점수 계약이 보존됨을 증명한다.

매니페스트에 함께 등록된 `wellnessbox-rnd/tests/test_data_lake_lineage.py`는 `test_delayed_event_replay_is_idempotent_and_conflicts_fail_closed` 등으로 원장의 일반 재시도·충돌 규칙을 다룬다. `wellnessbox-rnd/tests/test_event_idempotency_data_mutation.py`의 `test_event_endpoints_deduplicate_replays_and_reject_changed_payloads`와 `test_correction_and_deletion_preserve_lineage_and_append_hash_audits`는 이벤트 중복 제거와 수정 계보의 해시 감사 경계를 고정한다. 엄격한 네 시점 PRO 규칙의 직접 검사는 앞선 `test_pro_followup_effects.py`에 있고, 두 공통 원장 파일은 그 아래 영속·수정 기반을 맡는다.

현재 점수·추적·집단효과·계획 서비스 핵심 파일 네 개에서 수집된 79개 테스트는 모두 통과했다. 반면 매니페스트에 등록된 여섯 테스트 파일을 한 번에 실행한 결과는 106개 중 104개 통과, 2개 실패였다. 실패한 `test_canonical_lineage_evidence_matches_current_database_schema`와 `test_canonical_evidence_uses_current_database_schema`는 정식 증거가 데이터베이스 스키마 14를 기록했지만 현재 코드가 15를 요구해서 실패했다. 네 시점 저장 계산의 회귀는 아니지만, 등록 증거 전체가 현재 저장소와 완전히 동기화됐다고 주장할 수 없게 하는 품질 신호다.

## 스모크는 네 이벤트와 실패 차단을 재현하지만 현재 소스 해시는 다르다

`wellnessbox-rnd/data/original_plan/evidence/op053_op054_pro_followup_interpretation_smoke_v1.json`에는 활성 상태의 네 이벤트와 각 이벤트 해시가 기록돼 있다. 계약 변조, 다른 시작 분포·계획, 중복 평가, 일반 이벤트 보존 위반, 잘못된 수정, 스키마 누락, 순서 오류, 출력 변조, 역행 관측 시각, 잘못된 엄격 이벤트 유형 등 12개 실패 차단 결과도 모두 `true`다. 이 증거는 합성 입력으로 네 시점 경로를 한 번에 실행했다는 구현 증거다.

그러나 증거에 저장된 소스 해시 `ba663ac…`는 현재 같은 소스 집합에서 다시 계산한 `e455b85…`와 일치하지 않는다. 기록된 소스 커밋은 `94b0374`이고, 조사한 관련 경로의 이후 커밋은 `3f67d0b`까지 진행됐다. 따라서 JSON은 생성 당시의 성공 기록으로는 유효하지만 현재 코드 바이트의 정식 다이제스트로 사용할 수 없다. 현재 핵심 테스트 통과 결과는 별도 최신 검증이며, 오래된 JSON의 출처 해시를 자동으로 갱신하지 않는다.

## 직접 확인한 단계는 IMPLEMENTED이며 운영 영수증은 네 시점을 식별하지 못한다

매니페스트는 OP-053의 요구 단계와 주장 단계를 모두 `OPERATED`로 기록한다. `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-053.json`은 `wellnessbox-local-research-pc` 환경의 `ACTUAL` 세션 `local-20260724T010245964049Z`에서 프로필 또는 설문, 추적, 약사 검토 경로가 실행됐고 `followups`가 1 증가했다고 기록한다. 이 파일의 존재는 매니페스트 스키마가 요구하는 운영 경로 형식을 충족하지만, 영수증 내용만으로 OP-053의 네 시점 저장을 구별할 수는 없다.

영수증에는 네 시점 각각의 이벤트 ID, 구체적인 `plan_id`, 평가 도구, 원점수, 시작 분포 해시가 없다. 증가량도 추적 1건이므로 한 운영 세션에서 네 시점을 모두 완료했다는 증거가 아니다. 현재 소스와 집중 테스트는 네 시점 계약과 로컬 영속화를 뒷받침하므로 직접 확인되는 단계는 `IMPLEMENTED`다. 앞선 스모크도 자체 단계 값을 `IMPLEMENTED`로 기록하고 `op053_operated_stage_proven=false`라고 제한한다.

프로덕션 배포, 실제 의료 의사결정, 외부 기관 검증, 장기간 재시작 후 복구도 확인하지 않았다. `OPERATED`로 올리려면 복용 전·2주·4주·중단 이벤트의 가명 식별자, 같은 계획 ID, 도구·점수 계약·시작 분포 해시, 저장 시각을 한 실제 세션에서 연결해야 한다.
## 효과를 측정할 때 분리한 것
효과를 말하려면 예측값과 실제 복용 전후 관측값을 섞지 않아야 한다. 이 그룹은 PRO 원점수, 표준화, 개인별 변화, 집단 평균, 신뢰구간, 순응도와 이상사례를 각각 기록해 숫자가 무엇을 의미하는지 확인한다.

`OP-053`는 “복용 전, 2주, 4주, 중단 시점 PRO 이벤트를 저장한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/data/contracts/pro_followup_interpretation_v1.json`, `wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_followup.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/data_lake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/data_mutation.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_pro_followup_effects.py`, `wellnessbox-rnd/tests/test_data_lake_lineage.py`, `wellnessbox-rnd/tests/test_event_idempotency_data_mutation.py`, `wellnessbox-rnd/scripts/run_pro_followup_adherence_interpretation_smoke.py` 외 1개
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-053.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-053.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
