# OP-103 wellnessbox Vercel에 WB_RND 환경변수를 안전하게 등록한다.

manifest에 등록된 증거 `wellnessbox/lib/server/wb-rnd-environment.ts`에서 구현과 검증 대상을 확인할 수 있다.

## 먼저 결론

WellnessBox에는 R&D 추천 서버를 켤 때만 적용되는 서버 전용 환경변수 계약을 추가했다. 운영 모드에서는 `WB_RND_SERVICE_BASE_URL`이 HTTPS여야 하고, URL에 사용자 이름·비밀번호·쿼리·해시가 들어가면 요청을 시작하지 않는다. `WB_RND_SERVICE_TOKEN`은 앞뒤 공백을 제거한 뒤 32자 이상이어야 한다. 제한 시간은 500~15,000밀리초 범위의 정수만 허용한다. 설정이 하나라도 맞지 않으면 호출 경로가 예외를 내고 닫힌 상태로 멈춘다.

하지만 Vercel 프로젝트에 실제 값을 등록하지는 않았다. 공개 배포와 비밀값 변경은 별도 승인이 필요한 운영 작업이다. 따라서 OP-103의 요구 단계 `OPERATED`에 비해 이번 증거가 주장하는 단계는 `IMPLEMENTED`다. 안전한 등록 규칙과 실제 호출 경로의 강제는 구현했지만, Vercel 설정과 운영 트래픽은 증명하지 않는다.

## 왜 기존 읽기 방식으로는 부족했나

기존 추천 미리보기 코드는 URL의 끝 슬래시를 지우고 토큰 문자열을 읽었다. 이 방식은 개발용 호출에는 간단하지만 운영 경계를 설명하지 못한다. HTTP 주소를 운영 모드에서 허용하는지, URL 안에 자격 증명이 섞여도 되는지, 너무 짧은 토큰을 거부하는지 알 수 없었다. 잘못된 제한 시간도 기본값이나 보정값으로 조용히 바뀔 수 있었다. 설정 오류가 숨겨지면 운영자는 연결됐다고 생각하지만 실제 요청은 다른 주소로 나가거나 인증 없이 실패할 수 있다.

새 계약은 `WB_RND_RECOMMEND_ENABLED`가 켜졌을 때 네 항목을 한 번에 검사한다. 플래그가 꺼져 있으면 상태는 `disabled`이고 비밀값을 요구하지 않는다. 플래그가 켜져 있으면 URL, 토큰, 제한 시간을 모두 통과해야 `configured`가 된다. 호출 함수도 같은 계약을 직접 사용한다. 독립 검토에서 처음에는 계약 함수만 있고 실제 호출 경로가 옛 파서를 계속 사용한다는 Important 문제가 발견됐다. 수정 뒤 `callWbRndRecommendPreview`가 strict 계약에서 URL·토큰·제한 시간을 받도록 바꿨다.

## 무엇을 검사했나

고정 데이터셋에는 8개 사례가 있다. 비활성 상태, 운영 HTTP 거부, URL 자격 증명·쿼리·해시 거부, 짧은 토큰 거부, 제한 시간 범위, 원격 실행 출처, 로컬 스냅샷 출처, 모호한 출처 거부를 각각 독립 사례로 둔다. 서비스 QA는 안전한 HTTPS 설정이 정규화되는지 확인한다. 실제 호출 함수에 운영 HTTP 주소를 넣었을 때 `https_required`로 거부되는지도 확인한다.

정상 계약은 토큰 자체를 공개 상태에 포함하지 않는다. 공개용 상태에는 활성 여부, 계약 상태, 서비스 설정 여부, 제한 시간만 남는다. `NEXT_PUBLIC_WB_RND` 이름의 환경변수도 만들지 않았다. 브라우저 번들로 서버 토큰이 이동하는 경로를 만들지 않기 위해서다.

## 증거가 말하는 범위

정형 증거는 WellnessBox 커밋의 다섯 파일을 Git blob으로 읽는다. 작업 디렉터리의 우연한 변경이 아니라 커밋된 환경 계약, 호출 경로, 출처 판별, 화면, QA를 검사한다. 데이터셋은 8건이며 모든 검사가 참이어야 증거 파일이 생성된다. 서비스의 기존 사용자 변경 파일은 스테이징하지 않았고 그대로 보존했다.

이 증거로 말할 수 있는 것은 안전 계약이 코드와 호출 경로에 들어갔다는 사실이다. Vercel 대시보드에 값이 존재한다거나, Preview·Production 환경이 분리됐다거나, 비밀값 교체가 끝났다고 말할 수는 없다. 다음 운영 단계에서는 승인된 값으로 Vercel 환경을 설정하고, 배포 식별자와 R&D health를 확인한 뒤 토큰이 로그와 클라이언트 번들에 나타나지 않는지 다시 검사해야 한다.
## 서비스에 연결할 때 확인한 경계
서비스 통합은 R&D 코드가 존재한다는 사실만으로 끝나지 않는다. 두 저장소의 계약, 인증, 실제 요청·응답, 상품·주문 경계와 상태 환류를 같은 실행에서 확인해야 하며, 승인 전 데이터 변경은 허용하지 않는다.

`OP-103`는 “wellnessbox Vercel에 WB_RND 환경변수를 안전하게 등록한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox/lib/server/wb-rnd-environment.ts`, `wellnessbox/scripts/qa/check-rnd-environment-result-origin.cts`
- 테스트·실행: `wellnessbox-rnd/scripts/run_environment_result_origin_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op103_op104_environment_result_origin_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-103.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-103.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
