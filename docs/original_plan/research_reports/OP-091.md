# OP-091 연구일지: Apple Health와 범용 CSV의 활동·심박·수면 자료를 일별 계약으로 정규화한 과정

## 요구사항을 구현 가능한 데이터 계약으로 해석한 기준

OP-091의 원문은 Apple Health와 범용 CSV의 활동, 심박, 수면 필드를 정규화하라는 것이다. 이 요구사항은 파일을 읽을 수 있다는 사실만 요구하지 않는다. 같은 날짜와 같은 측정값이 입력 형식에 따라 서로 다른 필드명과 단위를 사용하더라도, 이후 추천과 추적 시스템이 하나의 명확한 자료형으로 읽을 수 있어야 한다. 또한 원본 파일에 중복 행이나 겹치는 수면 구간이 있을 때 단순 합산으로 잘못된 값을 만들지 않아야 하고, 날짜와 시간대가 불명확하면 임의로 추측하지 않아야 한다.

이 연구에서는 실제 Apple Health 계정이나 HealthKit API에 연결하지 않았다. 공개 배포나 운영 권한도 사용하지 않았다. 대신 Apple Health export를 CSV로 변환했을 때 흔히 볼 수 있는 long-form record 구조와, 여러 웨어러블에서 공통으로 만들 수 있는 wide daily-summary CSV를 versioned 입력 계약으로 정의했다. 따라서 이번 증거는 로컬 parser 구현을 증명하며 실제 Apple Health API 연동이나 production 데이터 수집을 증명하지 않는다. OP-091의 required stage는 `IMPLEMENTED`이고 현재 주장도 그 단계로 제한한다.

## 기존 시스템을 조사한 결과

R&D 저장소에는 이미 `sensor_parser.py`가 있었다. 기존 함수는 Python dictionary에서 `sleepHours`, `sleep_minutes`, `steps`, `step_count`, `restingHR` 같은 alias를 읽어 `NormalizedSensorGeneticSnapshot`으로 변환했다. 분 단위 수면을 시간으로 바꾸고 문자열 숫자를 정수로 바꾸는 기능도 있었다. `validate_wearable_summary_csv_schema`는 한 행짜리 sample CSV가 필요한 필드를 포함하는지 검사했다. Data Lake와 intake canonicalization도 이 snapshot을 기존 추천 입력 경로에 사용했다.

그러나 기존 parser는 CSV 문자열 자체를 일별 record로 읽지 않았다. schema validator는 첫 행을 확인하는 데 초점이 있었고 여러 날짜를 가진 파일을 정규화하지 않았다. Apple Health long-form record의 `type`, `startDate`, `endDate`, `value`, `unit` 구조도 구분하지 않았다. 따라서 OP-091을 위해 별도 wearable 저장소를 만들지 않고 기존 parser 안에 CSV-to-daily-summary 계층을 추가했다. 정규화된 값은 기존 snapshot의 활동·심박·수면 의미와 같은 단위를 사용한다.

## 범용 wearable CSV 계약

범용 CSV는 날짜별로 한 행을 두는 wide 형식이다. 날짜는 `date`, `day`, `recorded_date` 중 하나를 사용할 수 있다. 활동량은 `steps`, `step_count`, `daily_steps`를 허용한다. 안정시 심박수는 `resting_heart_rate`, `restingHR`, `resting_hr`를 허용한다. 수면은 시간 단위 `sleep_hours`, `sleepHours` 또는 분 단위 `sleep_minutes`, `sleepMinutes`, `sleep_duration_minutes`를 허용한다. parser는 분 단위를 60으로 나눠 시간으로 바꾸고 소수점 둘째 자리까지 보존한다.

각 날짜는 `NormalizedWearableDailySummary` 한 건이 된다. 이 계약은 날짜, 걸음 수, 안정시 심박수 bpm, 수면 시간, source format, 원본 행 수, normalization note를 가진다. 숫자의 허용 범위는 기존 건강 입력 경계와 맞췄다. 걸음 수는 0에서 200,000, 심박수는 20에서 250 bpm, 수면은 0에서 24시간이다. 이 범위를 벗어나면 Pydantic validation이 실패하므로 극단값을 조용히 받아들이지 않는다.

같은 날짜가 두 행에 나타나면 자동으로 더하거나 마지막 행을 선택하지 않는다. 범용 daily-summary는 날짜별 한 행이라는 계약이므로 `duplicate_wearable_daily_summary_date`로 실패한다. 어떤 행에도 활동·심박·수면 값이 없으면 `wearable_daily_summary_has_no_metrics`로 실패한다. 날짜가 없거나 ISO 날짜가 아니면 각각 명시적인 오류를 낸다. 이 fail-closed 방식은 파일 제공자가 중복의 의미를 결정하기 전에 parser가 임의로 평균하거나 합산하는 문제를 막는다.

## Apple Health long-form CSV를 판별하는 방법

CSV header에 `type`, `startDate`, `value`가 함께 있으면 Apple Health long-form 형식으로 판별한다. 현재 지원하는 type은 `HKQuantityTypeIdentifierStepCount`, `HKQuantityTypeIdentifierRestingHeartRate`, `HKCategoryTypeIdentifierSleepAnalysis`의 suffix와 일치하는 record다. 다른 Apple Health record는 오류로 바꾸지 않고 현재 요구 범위 밖이므로 건너뛴다. 지원 record가 하나도 없으면 `apple_health_csv_has_no_supported_records`로 실패한다.

Apple Health 시각은 반드시 timezone offset을 포함해야 한다. `2026-07-21T08:00:00+09:00` 같은 ISO 8601 표현과 날짜·시간 사이가 공백인 표현을 읽는다. timezone이 없는 시각을 서버 local timezone으로 가정하면 같은 파일이 실행 환경에 따라 다른 날짜로 묶일 수 있다. 그래서 offset이 없거나 해석할 수 없는 값은 `apple_health_datetime_invalid_or_timezone_missing`으로 거부한다. 현재 일별 bucket은 record의 `startDate`가 속한 local date를 사용한다. 이 선택은 canonical evidence에 고정돼 있으며, 자정을 넘는 수면을 어느 날짜에 귀속할지 다른 정책이 필요하면 schema version을 올려야 한다.

## 활동과 심박을 일별 값으로 만드는 규칙

Apple Health step count는 하루에 여러 구간 record로 나뉠 수 있으므로, 서로 다른 record의 값을 일별로 합산한다. 숫자가 아니면 `invalid_numeric_value::apple_health_steps`로 실패한다. 완전히 같은 type, start, end, value, unit 조합이 반복되면 같은 export record의 중복으로 보고 한 번만 사용한다. 이 identity는 sourceName을 사용하지 않으므로 서로 다른 기기가 우연히 같은 시각과 값으로 기록한 사례도 중복으로 취급할 수 있다. 현재 목표는 export 중복으로 인한 이중 합산을 막는 것이며, 여러 기기의 기여도를 보존하는 운영 정책은 별도 요구가 필요하다.

숫자만 검사하면 `km`로 기록된 값을 걸음 수로 합산하거나 임의 단위를 안정시 심박으로 해석할 수 있었다. 독립 검토에서 이 의미 손실을 확인한 뒤 StepCount는 `count`만 허용하고, RestingHeartRate는 `count/min`, `bpm`, `beats/min`, `beats/minute`만 허용하도록 수정했다. 잘못된 단위는 각각 `unsupported_apple_health_step_unit`과 `unsupported_apple_health_resting_heart_rate_unit`으로 거부한다. 회귀 시험은 두 오류를 직접 재현한다.

안정시 심박 record가 여러 건이면 산술평균을 구하고 소수점 첫째 자리까지 보존한다. 이 값은 raw heart-rate sample의 시간가중 평균이 아니라 Apple Health가 제공한 resting-heart-rate summary record의 평균이다. parser가 measurement semantics를 바꿔 raw pulse series를 resting heart rate로 재해석하지 않는다. 범용 CSV의 resting heart rate가 정수로 정규화되는 기존 계약과 달리 Apple Health daily summary는 여러 summary의 평균일 수 있어 float를 허용한다.

## 겹치는 수면 구간을 합집합으로 계산한 이유

Apple Health sleep export에는 전체 asleep 구간과 Core, Deep, REM 같은 세부 stage 구간이 함께 들어갈 수 있다. 모든 `Asleep` 문자열을 단순히 더하면 전체 구간과 stage 구간이 겹쳐 실제 수면 시간이 두 배 가까이 계산될 수 있다. 초기 구현 초안도 각 구간 duration을 바로 합산했지만, 구현 검토 중 이 위험을 확인했다.

최종 parser는 같은 start-date bucket의 수면 interval을 시작 시각순으로 정렬한다. 다음 interval이 이전 interval과 겹치면 끝 시각의 최댓값으로 병합한다. 겹치지 않으면 새 interval을 시작한다. 병합된 interval들의 초를 합산해 시간으로 바꾸므로 전체 asleep 구간 안에 deep sleep 구간이 포함돼도 7.5시간은 7.5시간으로 남는다. 종료가 시작보다 빠르거나 한 interval이 24시간을 넘으면 `invalid_apple_health_sleep_interval`로 실패한다.

frozen 사례에는 00:00부터 07:30까지의 전체 asleep record와 01:00부터 03:00까지의 deep-sleep record를 함께 넣었다. 합집합 결과는 7.5시간이다. 같은 step record도 한 번 중복해 넣었고 최종 걸음 수는 3,000과 2,500의 합인 5,500으로 유지됐다. source row count는 중복을 제거한 지원 record 다섯 건을 나타낸다.

## 기존 건강 입력과 Data Lake 경로를 유지한 방법

CSV parser가 만드는 daily model은 파일 단위 정규화 결과다. 추천 요청이 사용하는 기존 `NormalizedSensorGeneticSnapshot`의 `sleep_hours`, `steps`, `resting_heart_rate` 필드 의미는 바꾸지 않았다. 기존 dictionary normalization과 intake canonicalization, Data Lake execution event 저장 경로도 그대로 유지했다. 후속 연결은 선택한 일별 record를 기존 snapshot으로 전달하면 되고 별도 wearable database가 필요하지 않다.

이번 loop에서 CGM 식후 수치 필드를 snapshot에 추가하면서 Data Lake와 intake canonical payload도 함께 확장했다. wearable 필드의 기존 직렬화는 변하지 않았다. 기존 consent와 source availability 검증도 유지된다. wearable_available이 false인데 wearable 값을 넣으면 여전히 schema validation이 실패한다. CSV를 읽었다는 사실만으로 사용 동의나 production 연결을 주장하지 않는다.

## frozen QA와 재현 가능한 증거

canonical dataset에는 OP-091과 OP-092를 합쳐 여덟 사례가 있다. OP-091 관련 사례는 범용 wearable 두 날짜 정상화, Apple Health 중복·겹침 정상화, 범용 CSV 중복 날짜 거부, Apple Health timezone 누락 거부다. 정상 사례는 전체 normalized record를 evidence에 남기고, 예상 필드의 값이 frozen expectation과 같은지 비교한다. 실패 사례는 예외 종류뿐 아니라 정확한 오류 문자열을 비교한다.

smoke generator는 working tree 파일을 직접 source identity로 사용하지 않는다. Git HEAD의 blob을 읽어 SHA-256을 계산한다. parser, recommendation schema, intake, Data Lake, 두 sample CSV, frozen dataset, generator 자체를 직접 의존 목록에 포함한다. 단위 없는 식후 동의어까지 환산·비교하는 소스 커밋 `603eeb1993ec4f02edcf21bd4cb1898603714486`에서 같은 generator를 두 번 실행한 canonical 파일은 byte-identical했고 SHA-256은 `82c016013d247be2a992e91872c93d986374705b3e2b325a3a4bec272685c860`이다. 이전 evidence hash는 수정 전 parser를 가리키므로 최종 증거로 사용하지 않는다.

## 시험 결과와 알려진 한계

새 parser와 기존 sensor, schema, Data Lake, consent, candidate-signal, inference API 시험을 함께 실행했다. Apple Health와 범용 CSV의 정상·오류 사례, 기존 dictionary alias와 mmol/L 변환, CGM TIR 경계, Data Lake lineage가 통과했다. 이 결과는 기존 추천 입력 경로와 호환되는 구현 근거다.

그러나 실제 Apple Health export.xml 전체를 읽는 기능은 구현하지 않았다. HealthKit authorization, iOS background delivery, 사용자 계정 연결, incremental sync, 삭제 record, device-source 우선순위도 이번 범위가 아니다. Apple Health CSV는 export 또는 변환 도구가 long-form header를 보존한다는 전제다. 자정을 넘는 수면을 start date에 귀속하는 정책과 서로 다른 기기의 동일 record deduplication도 운영 규칙으로 추가 검증해야 한다.

## 현재 단계

OP-091은 기존 parser에 Apple Health long-form CSV와 범용 daily-summary CSV를 연결하고 활동, 안정시 심박, 수면을 명시적인 일별 모델로 정규화했다. 중복 날짜, timezone 누락, 지원 record 부재, 비정상 수면 interval을 fail-closed하고, 겹치는 수면 stage는 interval 합집합으로 계산한다. frozen QA와 source identity가 이 동작을 재현한다.

현재 주장 단계는 `IMPLEMENTED`다. required stage도 `IMPLEMENTED`이므로 감사와 독립 검토가 최종 통과하면 COMPLETE 후보다. 실제 Apple Health API 연결, production ingestion, 사용자 consent operation과 서비스 UI는 관측하지 않았으므로 `INTEGRATED`나 `OPERATED`로 확대하지 않는다.
