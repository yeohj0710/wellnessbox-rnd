# OP-098 생산 기기 세션과 시뮬레이션 세션을 data_class로 구분한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/interim/contracts.py`에서 구현과 검증 대상을 확인할 수 있다.

## 결론

기기 추천·후속평가 행에 `PRODUCTION_DEVICE_SESSION`과 `SIMULATED_DEVICE_SESSION`을 구분해 저장한다. 데이터 분류만 문자열로 받지 않는다. `DEVICE_PROVIDER` 출처는 생산 기기 분류와만 짝을 이룰 수 있고, `SIMULATION_FIXTURE` 출처는 시뮬레이션 분류와만 짝을 이룰 수 있다. 조합이 다르면 요청 모델이 저장 전에 거부한다. 후속평가는 기준 평가와 데이터 분류 및 출처가 같아야 한다.

OP-098의 요구 단계는 `OPERATED`다. 분류 계약, API 검증, SQLite 저장과 재조회는 구현했다. 하지만 실제 생산 기기 공급자 트래픽이나 배포 환경의 운영 기록은 없다. 따라서 현재 주장 단계는 `IMPLEMENTED`, 완료 판정은 `PARTIAL`이다. 필드 이름에 `PRODUCTION`이 들어간다고 운영 증거가 생기는 것은 아니다.

## 왜 기존 분류로는 부족했나

기존 `DataClass`에는 합성 데이터, 시뮬레이션 프록시, 약사 골드, 외부 블라인드, 실제 결과 같은 여러 값이 있었다. 기존 `connector_sessions`도 `environment`와 `data_class` 열을 가졌다. 그러나 기기 세션 수집 함수는 모든 행의 데이터 분류를 `INTERIM_RUNTIME_EVENT`로 고정했다. 환경 문자열에는 기본값 `simulation`이 있었지만 생산 세션과 시뮬레이션 세션을 데이터 분류 수준에서 강제하지 않았다.

이 상태에서는 평가 결과를 모아 볼 때 실제 기기에서 온 값과 테스트 픽스처에서 온 값을 안정적으로 나누기 어렵다. 단순히 `environment="production"` 같은 자유 문자열을 믿으면 오표기를 막을 수 없다. 시뮬레이션 결과가 생산 지표에 섞이면 성공률이나 후속 변화량이 실제보다 좋아 보일 수 있다. OP-098은 이 혼합을 막는 명시적 경계를 요구한다.

## 두 값이 아니라 두 쌍으로 검증한다

새 계약은 데이터 분류와 세션 출처를 함께 본다. 허용 조합은 두 개뿐이다.

- `PRODUCTION_DEVICE_SESSION` + `DEVICE_PROVIDER`
- `SIMULATED_DEVICE_SESSION` + `SIMULATION_FIXTURE`

시뮬레이션 픽스처가 생산 기기 분류를 주장하거나, 기기 공급자 출처가 시뮬레이션 분류를 주장하면 `device_session_origin_data_class_mismatch`로 실패한다. 이 규칙은 API 처리 함수 안쪽의 조건문이 아니라 Pydantic 요청 모델에 있다. 같은 모델을 직접 호출하는 내부 코드도 동일한 검증을 받는다.

`DEVICE_PROVIDER`는 공급자 연결이 실제라는 증거가 아니다. 호출자가 선언하는 출처 종류이며, 현재는 계약 경계를 시험하기 위해 로컬 요청에서도 사용할 수 있다. 운영 단계에서는 인증된 공급자 커넥터가 이 값을 만들고, 배포 환경의 접근 기록과 함께 증명해야 한다. 이번 보고서에서는 생산 분류 행의 존재와 생산 운영을 구분한다.

## 후속평가에서 분류를 바꿀 수 없다

기준 평가가 시뮬레이션이면 그 기준 평가를 참조하는 후속평가도 시뮬레이션이어야 한다. 기준 행을 읽은 뒤 프로필 ID, 데이터 분류, 세션 출처를 비교한다. 하나라도 다르면 후속 변화량을 계산하거나 저장하지 않는다. 생산 기준 평가에 시뮬레이션 후속평가를 붙이는 반대 경우도 같은 규칙으로 막힌다.

이 검사는 집계 단계에서 뒤늦게 행을 걸러내는 방식보다 강하다. 잘못 연결된 종단 데이터가 처음부터 생기지 않기 때문이다. 기준과 후속의 수치 차이는 같은 분류 안에서만 의미가 있다. 시뮬레이션 시작값과 실제 기기 후속값을 빼서 만든 변화량은 계산할 수는 있어도 해석할 수 없다.

## 저장 구조와 불변성

스키마 버전 13의 `device_recommendation_assessments` 테이블은 `data_class`에 두 기기 세션 값만 허용한다. `session_origin`에도 두 출처 값만 허용한다. SQL `CHECK`가 허용 목록을 제한하고, 애플리케이션 모델이 두 값의 올바른 조합을 제한한다. 한 층은 알 수 없는 값을 막고 다른 층은 의미가 어긋난 조합을 막는다.

기준 행은 `baseline_assessment_id`가 없어야 한다. 후속 행은 기준 평가 ID가 있어야 한다. 이것도 SQL `CHECK`와 요청 모델에 반영했다. 저장한 행은 수정하거나 삭제할 수 없다. 분류가 잘못됐다고 기존 행을 생산에서 시뮬레이션으로 바꾸는 대신, 잘못된 입력을 거부하고 올바른 새 평가 ID로 다시 기록해야 한다.

정확 재생은 허용한다. 평가 ID와 저장할 모든 값이 같으면 기존 행을 반환한다. 같은 평가 ID에 다른 데이터 분류나 다른 요청을 넣으면 충돌한다. 데이터 분류 변경을 업데이트처럼 사용할 수 없다.

## 고정 사례가 확인한 경계

첫 사례는 시뮬레이션 기준 평가와 후속평가를 같은 분류와 출처로 연결한다. 수면 값과 추천 점수 변화가 정상 계산된다. 두 번째 사례는 `PRODUCTION_DEVICE_SESSION`과 `DEVICE_PROVIDER` 조합이 별도 행으로 저장되는지 확인한다. SQLite에서 고유 데이터 분류를 조회하면 생산과 시뮬레이션 두 값이 분리돼 나온다.

세 번째 사례는 `SIMULATION_FIXTURE`와 생산 분류처럼 두 선언이 어긋난 조합을 보낸다. API는 422를 반환하고 행을 만들지 않는다. 두 값을 모두 생산으로 허위 선언하는 행위까지 이 계약만으로 판별하지는 못한다. 네 번째 사례는 시뮬레이션 기준 평가에 생산 기기 후속평가를 붙인다. 요청 자체의 생산 조합은 유효하지만 기준 행과 분류가 다르므로 `device_follow_up_data_class_mismatch`로 실패한다.

다섯 번째 사례는 기준 평가를 그대로 재생하고 중복 제거를 확인한다. 여섯 번째 사례는 저장 행을 수정하고 삭제하려고 시도한다. 두 SQL 모두 `device_recommendation_assessments_append_only` 오류로 거부된다. 일곱 번째 사례는 후보 진입·이탈 상태를 보존한다. 최종 저장 행은 시뮬레이션 기준, 시뮬레이션 후속, 생산 경계 기준의 세 개다.

## 구현 단계에서 발견한 문제

canonical 실행기를 처음 돌렸을 때 임시 데이터베이스 환경 변수 이름을 잘못 사용했다. API는 저장소 기본 경로를 열었고, 실행기가 확인한 임시 파일에는 새 테이블이 없었다. 환경 변수를 실제 `WB_RND_INTERIM_DATABASE`로 고쳤다. 잘못된 실행이 기본 로컬 데이터베이스에 만든 평가 행 네 개는 평가 ID를 정확히 확인한 뒤 제거했고, 기존 행은 건드리지 않았다.

두 번째 실행에서는 기준 행 조회에 사용한 SQLite 연결이 닫히지 않아 Windows가 임시 파일을 정리하지 못했다. Python의 SQLite 연결 컨텍스트 관리자는 트랜잭션을 끝내지만 연결 자체를 닫지 않는다는 점이 원인이었다. 조회 코드를 `try/finally`로 바꿔 연결을 명시적으로 닫았다. 회귀 테스트와 canonical 실행이 이후 통과했다.

## 운영 단계에 필요한 추가 증거

`OPERATED`로 올리려면 실제 공급자 또는 실제 기기 앱이 인증된 경로로 생산 세션을 보내야 한다. 배포된 API와 운영 데이터베이스가 생산 분류를 보존하는지, 시뮬레이션 트래픽이 생산 지표에서 제외되는지 확인해야 한다. 공급자 세션 ID, 사용자 동의 시점, 기기 식별정보 최소화, 보존 기간, 삭제 요청, 접근 감사도 운영 정책과 함께 검증해야 한다.

운영 성공률을 계산할 때는 분모와 분자를 데이터 분류별로 나눠야 한다. 시뮬레이션 성공을 생산 성공에 더하지 않아야 한다. OP-100의 W/C/G 출처별 성공률과 macro 평균을 다시 계산할 때 이번 분류를 집계 조건으로 사용해야 한다. 그 전까지 생산 분류 행을 만들 수 있다는 사실만으로 운영 성과를 주장하지 않는다.

## 현재 판정

타입 계약, 오표기 거부, 교차 분류 후속평가 거부, 별도 저장, 재조회, 중복 제거, 불변성은 구현됐다. 실제 운영은 확인하지 않았다. 따라서 OP-098은 구현 증거는 충분하지만 요구 단계에는 부족하다. 이 차이를 manifest와 canonical 증거에 그대로 기록했다.
