# OP-111 내부 API 인증과 역할 권한 회귀 검증 연구보고서

## 결론

OP-111은 요구 단계인 `INTEGRATED`에 도달했다. WellnessBox 서비스의 사용자, 약국, 관리자 경로가 각자 다른 세션 guard를 통과해야만 R&D 프록시를 호출한다. WellnessBox와 R&D 사이의 내부 HTTP 요청은 별도 내부 토큰을 요구한다. canonical smoke는 인증이 없는 세 역할을 모두 거부하고, 인증된 역할의 서버 소유 범위가 브라우저 입력보다 우선하며, 올바른 내부 토큰은 실제 FastAPI 요청을 통과하고 잘못된 토큰은 HTTP 401로 거부되는지 실행한다.

이번 판정은 운영 단계가 아니다. 실제 운영 계정, 운영 신원 제공자, 운영 약국 세션, 운영 관리자 세션을 사용하지 않았다. 로컬의 실제 서비스 TypeScript 함수와 별도 FastAPI 프로세스를 연결한 통합 검증이다. 따라서 운영 트래픽이나 실제 권한 사고 대응이 증명됐다고 해석하면 안 된다.

## 요구사항을 검증 가능한 조건으로 바꾼 방법

“내부 API 인증과 사용자·약국·관리자 권한”은 하나의 토큰 검사만으로 충족되지 않는다. 외부 요청이 서비스에 들어오는 경계와 서비스가 R&D를 호출하는 경계를 나누어야 한다. 외부 경계에서는 사용자는 로그인한 AppUser, 약국은 로그인한 pharmacyId, 관리자는 관리자 세션을 가져야 한다. 내부 경계에서는 서비스만 아는 `x-wb-rnd-token`이 필요하다.

사용자 권한 검증은 브라우저가 보낸 `profile_id`를 신뢰하지 않는지 포함한다. 서비스는 세션의 `appUserId`를 HMAC 기반 가명 식별자로 바꾸고 요청 본문의 같은 필드를 덮어쓴다. 약국 권한 검증도 같은 원칙을 따른다. 검토 목록의 `pharmacy_id`와 검토 결정 본문의 `pharmacy_id`는 로그인한 약국 ID에서 정한다. 관리자는 관리자 세션이 없으면 R&D 상태, KPI, 데이터 출처, 규칙·모델·실행 집계를 조회하지 못한다.

내부 토큰 검증은 정적 코드 검색에 그치지 않는다. smoke runner가 임시 SQLite 데이터베이스와 별도 FastAPI 프로세스를 시작한다. 서비스의 실제 `callWbRndInterim` 함수가 올바른 토큰으로 `/v1/interim/status`를 호출한다. 이어 토큰을 잘못된 값으로 바꿔 같은 경로가 401을 반환하는지 확인한다. 이 방법은 헤더 이름, 환경변수 연결, HTTP 전달, FastAPI dependency가 함께 작동해야 통과한다.

## 구현 구조

서비스의 역할 guard는 기존 `lib/server/route-auth.ts`를 재사용한다. 사용자 경로는 `requireUserSession`, 약국 경로는 `requirePharmSession`, 관리자 경로는 `requireAdminSession`을 호출한다. 이번 작업은 별도 인증 체계를 만들지 않았다. `lib/server/wb-rnd-interim-route.ts`의 실제 경로 함수에 의존성을 주입해 승인과 거부 분기를 같은 구현에서 실행했다.

R&D 내부 인증은 `apps/inference_api/routes/interim.py`의 router dependency를 사용한다. `WB_RND_INTERIM_ENABLED`가 켜졌는데 내부 토큰이 설정되지 않으면 503으로 닫힌다. 토큰이 설정됐는데 헤더가 없거나 값이 다르면 401로 닫힌다. 비교에는 `hmac.compare_digest`가 사용된다. 이벤트 mutation 경로는 기능 활성화 여부와 무관하게 내부 토큰이 없으면 503으로 닫히는 더 엄격한 dependency를 유지한다.

서비스 내부 호출은 `lib/server/wb-rnd-interim-client.ts`에서 허용된 `/v1/interim/` 경로만 받는다. 상대 경로 탈출과 이중 슬래시를 거부하고, URL의 검색·해시를 제거하며, 서버 환경변수의 토큰만 헤더에 넣는다. 브라우저가 내부 토큰을 전달하거나 선택할 수 있는 입력 필드는 없다.

## 데이터셋과 사례

canonical 데이터셋은 `data/original_plan/op111_op112_security_boundary_cases_v1.json`이며 8건이다. OP-111에 직접 대응하는 사례는 내부 토큰, 사용자 역할, 약국 역할, 관리자 역할, 가명 식별자다. OP-112와 공유하는 최소수집, 로그 마스킹, 제한된 오류 사례도 같은 실행에서 검증한다. 역할별 거부 사례는 인증 실패 뒤 R&D 호출 함수가 실행되면 즉시 실패하도록 구성했다. 단순히 응답 코드만 우연히 401인 경우를 배제하기 위해서다.

사용자 spoof 사례는 공격자가 `usr_attacker`와 전화번호를 요청 본문에 넣는다. 실제 서비스 경로는 세션의 AppUser ID를 가명처리한 `usr_` 식별자로 덮어쓰고 전화번호를 R&D 본문 최상위에 전달하지 않는다. 약국 spoof 사례는 공격자가 `pharmacy_id=999`를 제출해도 인증된 약국 112로 바뀌는지 확인한다. 관리자 거부 사례는 인증 실패 시 상태·KPI·출처·런타임 호출이 하나도 실행되지 않는지 확인한다.

## canonical evidence

증거 파일은 `data/original_plan/evidence/op111_op112_security_boundary_smoke_v1.json`이다. 데이터셋 경로, Git blob 기반 SHA-256, 사례 수, 각 검사 결과, 관찰값, 서비스 커밋, 서비스 파일별 Git blob, R&D 라우트의 소스 커밋을 기록한다. 서비스 커밋은 실제 프로필 저장 경계와 운영 오류 로그 마스킹 보강까지 포함한 `af62c9a0e364f74b3aef4c7672126273c73f48ad`다.

증거는 실제 서비스 경로의 인증 허용·거부 분기를 실행하고 역할 guard 구현의 소스 계약을 검증했음을 기록한다. 실제 R&D HTTP 토큰 왕복도 실행한다. 반대로 `production_identity_provider_operation_proven=false`와 `production_log_sink_inspection_proven=false`를 명시한다. 로컬 QA가 운영 세션 백엔드를 실행했다는 주장은 하지 않는다.

## 실패 폐쇄 특성

사용자, 약국, 관리자 인증 실패는 모두 R&D 호출 전 단계에서 끝난다. 내부 토큰 누락과 불일치도 R&D route handler 실행 전에 끝난다. 요청 본문의 역할 범위가 세션 범위와 충돌하면 세션 값으로 덮어쓴다. 검토 ID는 `review_[a-f0-9]+` 형식만 허용한다. 내부 클라이언트는 허용 경로가 아니거나 토큰·기본 URL이 없으면 요청을 보내지 않는다.

오류 처리도 권한 경계의 일부다. 임의 예외 메시지는 클라이언트 응답에 그대로 포함하지 않는다. 제한된 어댑터 오류 코드와 `WB_RND_INTERIM_upstream_<status>`만 공개하며, 나머지는 `R&D request failed`로 바꾼다. 이 정책은 오류 문자열에 사용자 입력이나 토큰이 섞였을 때 외부 노출되는 문제를 줄인다.

## 재현 방법

서비스 저장소에서 `npm run typecheck`, `npm run qa:rnd:profile-adapter`, `npm run audit:encoding`을 실행한다. R&D 저장소에서 `python scripts/run_security_boundary_integration_smoke.py`를 실행한다. runner는 빈 임시 DB를 migration하고 사용 가능한 포트를 선택한 뒤 FastAPI를 시작한다. Node QA가 서비스 경로와 실제 R&D HTTP를 실행하고 JSON 결과를 반환한다. runner는 모든 조건을 다시 검증한 뒤 canonical evidence를 쓴다.

동일 커밋에서 runner를 다시 실행하면 증거 파일이 바뀌지 않아야 한다. GitHub Actions는 OP-111/112 서비스 커밋을 별도 checkout하고 같은 runner를 실행한 뒤 `git diff --exit-code`로 재현성을 검사한다. requirement audit와 completion report도 같은 최신 서비스 checkout을 사용한다.

## 한계와 다음 검증

이번 검증은 로컬 세션 guard의 허용·거부 분기와 실제 내부 HTTP 토큰을 다룬다. 운영 쿠키 발급, 세션 만료, 계정 정지, 다중 약국 소속, 관리자 권한 회수, 운영 비밀 회전은 실행하지 않았다. 실제 공격 트래픽, WAF, 중앙 감사 로그, 운영 경보도 범위 밖이다.

OP-111을 운영 단계로 높이려면 승인된 비운영 또는 운영 환경에서 실제 신원 제공자 세션을 사용해야 한다. 사용자·약국·관리자 계정의 허용·거부 행렬, 세션 만료, 역할 회수, 토큰 회전, 권한 변경 뒤 캐시 무효화, 감사 로그와 경보를 증거로 남겨야 한다. 공개 배포나 운영 인증정보 변경은 별도 승인이 필요하다.

## 최종 판정

OP-111은 실제 서비스 역할 guard와 실제 R&D HTTP 내부 토큰을 한 실행에서 검증했으므로 `INTEGRATED`다. 요구 단계와 현재 단계가 같아 COMPLETE로 판정할 수 있다. 다만 운영 신원 제공자와 운영 트래픽은 검증하지 않았으므로 `OPERATED` 또는 외부 검증으로 올리지 않는다.
