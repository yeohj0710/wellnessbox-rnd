# OP-082 연구보고서: 질문에서 건강 목표, 성분, 약물, 위험 신호를 추출한다

## 요구사항이 필요한 이유

OP-082의 원문은 “질문에서 건강 목표, 성분, 약물, 위험 신호를 추출한다”이다. 상담 질문은 추천 요청처럼 이미 정리된 JSON으로 들어오지 않는다. 사용자는 “수면이 안 좋은데 오메가3를 와파린과 같이 먹어도 되나요”처럼 목표, 성분, 복용 약, 위험 상황을 한 문장에 섞어 쓴다. 검색기가 이 문장을 일반 문자열로만 다루면 수면 자료만 찾고 warfarin 상호작용을 놓치거나, 성분 이름을 잘못 잘라 엉뚱한 근거를 가져올 수 있다. 답변 생성 전에 질문의 핵심 대상을 안정적인 canonical ID로 바꾸는 단계가 필요한 이유다.

위험 신호는 일반 검색 키워드보다 더 엄격하게 다뤄야 한다. 현재 출혈, 흉통, 호흡곤란, 아나필락시스 같은 표현이 포함된 질문은 단순한 성분 효능 질문과 같은 경로로 처리할 수 없다. OP-086에서 안전 안내 우선 정책을 구현하려면 OP-082가 먼저 위험 표현을 놓치지 않고 구조화해야 한다. 다만 이 단계가 질병을 진단하거나 응급도를 의학적으로 판정하는 것은 아니다. 문자열에서 정해진 신호를 발견하고 그 사실을 다음 안전 단계에 전달하는 것이 정확한 책임 범위다.

## 기존 canonical vocabulary를 사용한 이유

새 엔터티 사전이나 별도 NLP 저장소를 만들지 않았다. `runtime_knowledge_db_v1.json`에는 현재 R&D가 실제 추천과 안전 규칙에서 사용하는 ingredient key, ingredient alias, medication key, condition key가 이미 있다. 성분 추출이 이 목록과 다른 이름 체계를 사용하면 상담이 찾은 `omega3`와 추천 엔진이 사용하는 `omega3`, 서비스 mapping이 사용하는 `ING:OMEGA3` 사이의 연결을 다시 만들어야 한다. 중복 사전은 시간이 지나면서 서로 다른 성분을 같은 것으로 취급하거나 같은 성분을 서로 다른 것으로 취급할 위험이 있다.

건강 목표는 `RecommendationGoal`의 아홉 canonical 값과 맞췄다. stress support, sleep support, immunity support, energy support, gut health, bone and joint, heart health, blood glucose, general wellness가 그 값이다. 질문 표현은 영어와 한국어가 섞일 수 있으므로 각 canonical goal에 제한된 별칭을 연결했다. 성분은 runtime DB의 catalog·knowledge alias를 우선 사용하고, 현재 corpus가 영어 중심이라 부족한 주요 한국어 표현만 같은 canonical key에 보완했다. 약물은 runtime DB의 warfarin과 Coumadin을 사용하고 한국어 와파린·쿠마딘 표기를 연결했다. condition risk도 runtime DB에 실제로 등록된 kidney disease, kidney failure, liver failure, cirrhosis, pregnancy, lactation 범위 안에서 한국어 표현을 연결했다.

## 결정론적 추출 계약

`QuestionEntityExtraction`은 원 질문, 건강 목표 ID 목록, 성분 ID 목록, 약물 ID 목록, 위험 신호 ID 목록, 긴급 위험 발견 여부, 개별 match trace를 반환한다. 각 trace에는 종류, canonical key, 질문에서 실제로 일치한 문자열, 시작 위치와 끝 위치가 들어간다. 결과 목록은 입력 사전의 순서나 set 순서에 의존하지 않고 안정적으로 정렬한다. 같은 질문을 다시 처리하면 JSON byte가 달라지지 않아야 canonical evidence와 후속 상태기계가 같은 결정을 재현할 수 있다.

추출기는 LLM이나 외부 provider를 호출하지 않는다. 별칭을 길이 우선으로 정렬하고, 대소문자를 무시한 명시적 pattern으로 질문을 검사한다. 영어 별칭은 단어 경계를 요구한다. 예를 들어 `zincography` 안의 `zinc`를 성분으로 오인하지 않는다. 한국어는 명사 뒤에 조사나 어미가 바로 붙기 때문에 영어와 같은 뒤쪽 단어 경계를 적용하지 않는다. “수면과”, “혈당이”, “오메가3를”, “와파린과”에서도 해당 명사를 찾는다. 이 차이는 언어별 문법을 고려한 deterministic matching이지, 질문 의미를 추측하는 자유 형식 NLP가 아니다.

위험 신호는 두 종류로 구분한다. runtime DB의 condition key는 임신, 수유, 신장질환 같은 안전 문맥을 나타내지만 모두 즉시 응급인 것은 아니다. 별도의 고정 urgent vocabulary는 active bleeding, chest pain, difficulty breathing, anaphylaxis만 포함한다. urgent vocabulary와 일치한 경우에만 `urgent_risk_detected=true`가 된다. 신장질환이 검출됐다는 이유만으로 응급이라고 표시하지 않고, 반대로 “지금 출혈이 있다”는 표현은 일반 condition과 분리해 긴급 신호로 남긴다.

## 첫 실패에서 드러난 한국어 조사 문제

초기 구현은 모든 별칭 앞뒤에 영어식 word boundary를 사용했다. focused test에서 영어 질문은 통과했지만 “수면과 혈당이 걱정됩니다. 오메가3를 와파린과 먹는데 지금 출혈이 있어요”라는 한국어 질문에서는 어떤 엔터티도 나오지 않았다. Python 정규식에서 한국어 글자와 조사는 모두 word character로 취급되므로 `수면` 뒤의 `과`가 경계 조건을 깨뜨린 것이 원인이었다.

이 실패를 해결하기 위해 한국어 전체를 느슨한 부분 문자열 검색으로 바꾸지는 않았다. ASCII 문자, 숫자, 공백, 하이픈으로만 구성된 영어 별칭에는 기존 양쪽 word boundary를 유지했다. 그 외 문자 체계를 포함한 별칭은 명시된 별칭 문자열을 찾도록 분리했다. 그 결과 한국어 조사가 붙은 표현은 검출하면서 `zincography` 같은 영어 내부 문자열 오탐은 계속 차단했다. 회귀 테스트에는 이 두 사례를 함께 넣어 한쪽을 고치면서 다른 쪽을 망가뜨리지 않게 했다.

## 아홉 질문 사례가 보여준 결과

canonical smoke는 한국어와 영어 질문 아홉 개를 사용한다. 첫 질문에서는 `sleep_support`, `blood_glucose`, `omega3`, `warfarin`, `active_bleeding`을 함께 추출하고 urgent flag를 true로 만들었다. 두 번째 질문은 glucosamine, Coumadin, joint health를 각각 `glucosamine`, `coumadin`, `bone_joint`로 바꿨다. 세 번째 한국어 질문은 신장 질환, 비타민 D3, 마그네슘 글리시네이트를 `kidney disease`, `vitamin_d3`, `magnesium_glycinate`로 바꾸되 urgent flag는 false로 유지했다. 일반적인 “비타민 D”나 “마그네슘”만 나온 질문은 특정 D3 또는 glycinate 제형으로 단정하지 않는 별도 회귀 테스트를 통과해야 한다.

네 번째 질문은 chest pain과 difficulty breathing을 동시에 긴급 신호로 추출하고 zinc 성분도 남겼다. 다섯 번째 질문은 프로바이오틱스, 장 건강, 전반적 건강을 `probiotics`, `gut_health`, `general_wellness`로 구조화했다. 여섯 번째 질문의 “흉통은 없습니다”는 risk mention을 trace에 남기되 negated로 표시하고 urgent flag를 false로 유지한다. 일곱 번째 질문의 “No bleeding, but I have chest pain”은 앞 절의 부정이 뒤 절의 실제 흉통을 숨기지 않아 urgent flag가 true다. 여덟 번째 질문은 한국어 호흡곤란·부종 변형을 긴급 신호로 검출한다. 마지막 질문은 “zincography”라는 단어가 포함되지만 실제 zinc 성분 질문이 아니므로 모든 엔터티 목록과 match trace가 비어 있다.

같은 smoke를 두 번 실행한 결과 파일은 byte-identical했고 SHA-256은 두 번 모두 `03c0efdc6110208f4e2e185c17524099d5b8fcdc5f27366cf6bd47c5ecb332f4`였다. source identity는 extractor와 runtime knowledge loader, builder, 테스트, smoke를 묶어 기록하고, data identity는 runtime knowledge DB와 reference·claim artifact를 별도로 묶는다. 질문별 match trace, negation 상태, 집계 목록의 일치 여부가 canonical evidence에 그대로 남으므로 사례 수만 맞춘 결과가 아니다.

## 정확성의 경계와 다음 단계

이 extractor는 현재 canonical vocabulary에 없는 성분, 상품명, 약물 별칭을 임의로 추측하지 않는다. 오타 교정이나 완전한 형태소·의미 분석도 하지 않는다. 다만 명시적인 `no <signal>`, `<signal> is absent`, `<signal>은 없습니다`처럼 신호 바로 옆에 결합된 제한된 부정 표현은 match에 `negated=true`로 남기고 긴급 집계에서 제외한다. 부정은 고정 길이 창 전체에 전파하지 않는다. 독립 검토에서 “No bleeding, but I have chest pain”과 “No bleeding and I have chest pain”의 실제 흉통까지 부정되는 안전상 결함을 발견했고, 수정 후에는 각각 흉통 match가 non-negated 상태로 남아 urgent flag가 true다. trace와 건강 목표·성분·약물·위험 목록, urgent flag가 서로 모순되는 serialized payload도 Pydantic validator가 거부한다. 이 제한된 처리는 임상 응급 판정이나 자유로운 문장 의미 해석을 대신하지 않으며, 실제 답변 우선순위는 OP-085와 OP-086에서 다시 검증해야 한다.

OP-082의 required stage는 `IMPLEMENTED`다. 기존 runtime knowledge vocabulary 재사용, 한국어·영어 deterministic extraction, trace와 위치 보존, 긴급 신호 분리, 부분 문자열 오탐 회귀, 결정론적 canonical evidence가 모두 확인됐으므로 OP-082는 `IMPLEMENTED` 단계에서 COMPLETE로 기록할 수 있다.

서비스 통합과 운영은 여전히 증명되지 않았다. WellnessBox 채팅이 extractor를 호출하지 않았고, 배포된 API에서 실제 사용자 질문을 처리하지 않았으며, 외부 라벨러가 recall과 precision을 평가하지 않았다. evidence에는 LLM entity inference 미사용, production operation 미증명, service integration 미증명, external validation 미증명을 명시했다. 다음 OP-083/084 loop는 이 구조화 결과를 이용해 허용된 passage만 검색하고 답변에 근거 ID, 유효일, 불확실성을 넣어야 한다.
