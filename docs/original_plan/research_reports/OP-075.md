# OP-075 PRO와 기기 데이터 수신 후 다음 작업을 다시 결정한다.

manifest에 등록된 중심 구현은 `wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`이고, 입력별 결과 기록은 `wellnessbox-rnd/data/original_plan/evidence/op075_op076_followup_input_serious_ae_smoke_v1.json`이다.

## 새 측정값을 보관하는 데서 끝내면 폐쇄형 관리가 아니다

PRO는 사용자가 설문으로 보고한 상태를 뜻한다. 이 값이나 웨어러블 측정값이 도착했는데 저장만 하고 다음 판단을 열지 않으면 기존 복용 계획은 새 정보를 반영하지 못한다. OP-075는 입력 수신을 “재평가가 필요한 사건”으로 바꾸고, 같은 계획의 다음 작업을 공용 업무 큐에 즉시 넣도록 요구한다. 잘못된 파일이나 이미 중단된 계획까지 재평가하면 안전하지 않으므로 입력 성공 여부와 계획 상태를 먼저 확인해야 한다.

## 입력 영수증을 재평가 업무의 식별자로 사용했다

`enqueue_input_reevaluation()`은 `PRO`와 `DEVICE` 두 종류만 받는다. 실행 ID, 계획 ID, 입력 종류, 입력 ID를 일정한 순서로 정리해 지문 값을 만들고, 그 값으로 후속 ID와 `input-reevaluation:{identity}` 멱등 키를 계산한다. 실제 입력 내용의 지문도 업무 내용에 별도로 저장한다. 같은 입력 ID의 내용이 달라지면 기존 작업을 재사용하지 않고 `workflow_job_idempotency_payload_conflict`로 거부한다.

재평가를 새 예약 시스템으로 보내지 않은 이유는 만기 재평가와 같은 선점·취소·동의 검사를 사용하기 위해서다. 업무 종류는 `PLAN_REEVALUATION`, 예정 시각은 입력을 받은 시각이다. `agent.py`의 PRO 입력과 기기 입력 경로도 저장 성공 뒤 이 함수를 호출한다. FastAPI 기기 경로는 정규화가 실패한 세션에 `next_job_decision`을 붙이지 않는다. PRO 수정 경로는 현재 유효한 이벤트 지문을 입력 ID에 포함하므로 값이 정정되면 새 재평가 업무를 만든다.

## 다음 행동 선택과 업무 생성의 경계를 나눴다

업무 큐에 행이 생겼다는 사실과 상태기계가 유지·조정·중단 중 하나를 끝까지 선택했다는 사실은 다르다. `BoundedAgent.decide_followup_action()`은 실행 상태가 `FOLLOWUP_ACTIVE`일 때만 정책표를 읽고 다음 상태를 저장한다. PRO API는 설문 해석 결과의 `action_decision`을 반환하면서 재평가 업무도 만든다. 기기 API는 성공한 기기 자료에 재평가 업무를 연결하지만, 등록된 기준 실행은 업무 처리 프로그램이 그 업무를 가져가 최종 행동을 저장하는 단계까지 다루지 않는다.

이 분리를 문서에 남기는 이유는 큐 생성만 보고 모든 재평가가 완료됐다고 오해하지 않기 위해서다. `tests/test_pro_plan_service.py`에서는 정상 PRO 입력이 `maintain`과 `REEVALUATE_PLAN`을 함께 반환하고, 유효하지 않은 기기 단위는 성공이 false이며 업무가 생기지 않는다. `tests/test_interim_agent.py`는 에이전트 경로의 PRO와 기기 입력이 각각 별도 업무를 한 건씩 만드는지 확인한다.

## 변경된 입력과 중단 계획을 조용히 받아들이지 않는다

현재 증거에서 개발 당시의 최초 실패 로그는 확인되지 않음이다. 대신 회귀 시험이 두 가지 잘못된 처리를 재현한다. 같은 입력 식별자에 다른 지문을 넣으면 충돌로 중단하고, 중단 이벤트가 추가된 계획에 새 입력을 연결하면 `followup_active_execution_plan_required`로 거부한다. 기기 정규화가 실패한 경우에도 “자료가 왔다”는 이유만으로 재평가를 만들지 않는다. 조사한 범위는 jobs·agent·API 구현, 세 테스트 파일, 기준 실행 생성기와 등록 결과다.

## 고정 실행이 입증한 것은 즉시 업무 생성까지다

고정 실행은 PRO 입력 `pro_smoke_1`과 기기 입력 `device_smoke_1`을 같은 계획에 넣었다. 결과는 서로 다른 `PLAN_REEVALUATION` 두 건이며, 예정 시각은 각각 12:00과 12:01 UTC다. 두 작업에는 `PRO_INPUT_RECEIVED`와 `DEVICE_INPUT_RECEIVED`가 기록되고 입력 지문도 보존된다. 이어진 중대 이상사례 시험 때문에 최종 상태가 모두 `CANCELLED`가 됐지만, 취소 전 두 입력이 즉시 다음 업무를 만들었다는 결과는 JSON에 남아 있다.

## 운영 주장에 필요한 마지막 연결이 남았다

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-075.json`을 근거로 `OPERATED`를 표시한다. 하지만 로컬 세션 영수증의 증가량은 `pro_observations=0`, `adverse_events=0`, `workflow_jobs=1`이며 기기 입력 건수는 별도로 적지 않는다. 따라서 실제 PRO 또는 기기 수신이 그 한 건의 업무를 만들었다고 직접 대조할 수 없다.

현재 직접 입증 단계는 `IMPLEMENTED`로 제한한다. 운영 업무 처리 프로그램이 입력 업무를 선점하고 정책 판단을 실행한 기록, 결정된 행동이 후속 계획에 반영된 기록, 운영 기기 자료의 재평가 결과는 확인되지 않음이다. `OPERATED`를 뒷받침하려면 입력 영수증 ID, 생성된 업무 ID, 정책 규칙 ID, 상태 변경을 한 묶음으로 남긴 운영 기록이 필요하다.
