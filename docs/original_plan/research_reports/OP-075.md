# OP-075 PRO와 기기 데이터 수신 후 다음 작업을 다시 결정한다.

OP-075는 환자 보고 결과(PRO, Patient-Reported Outcome)나 기기 측정값을 저장하는 데서 끝내지 않고, 성공적으로 수신한 최신 자료를 다음 계획 판단 업무로 바꾸라는 요구다. manifest에 등록된 `wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`의 입력 재평가 큐와 상위 호출 경로는 이 연결을 구현한다. 다만 등록 실행은 업무 생성까지만 재현하고 작업자가 정책 결정을 완료하는 과정은 실행하지 않아 현재 증거 단계는 `IMPLEMENTED`다.

## 입력 수신과 다음 판단 사이의 계약

새 증상·순응도·기기 수치가 들어왔는데 기존 계획을 그대로 유지하면 후속 관리가 새 정보를 반영하지 못한다. 반대로 파싱에 실패한 기기 자료, 다른 실행에 속한 계획, 이미 중단된 계획에도 재평가를 만들면 잘못된 자료로 추천을 갱신할 수 있다. 따라서 이 요구는 “입력이 도착했다”가 아니라 “저장된 유효 입력을 활성 계획과 연결했다”는 시점에만 다음 업무를 연다.

`WorkflowJobQueue.enqueue_input_reevaluation()`은 입력 종류를 `PRO` 또는 `DEVICE`로 제한하고 64자리 소문자 SHA-256 지문을 요구한다. 실행·계획·입력 종류·입력 식별자를 정규화해 업무 정체성 값(identity)을 만들고, 후속 식별자 `fu_input_…`와 멱등 키 `input-reevaluation:{identity}`를 계산한다. 업무 종류는 만기 재평가와 같은 `PLAN_REEVALUATION`이며 실행 예정 시각은 `received_at`이다. 업무 내용에는 입력 지문과 수신 시각, `PRO_INPUT_RECEIVED` 또는 `DEVICE_INPUT_RECEIVED`, 동의 스냅샷과 실행 근거 지문이 포함된다.

## 저장된 입력 행을 기준으로 업무를 버전 관리한다

`wellnessbox-rnd/src/wellnessbox_rnd/interim/agent.py`의 `BoundedAgent.ingest_pro()`는 요청에 함께 온 plan context가 사용자·실행과 맞는지 확인하고 PRO를 저장한다. 이어서 데이터베이스에서 실제 저장된 행의 지문과 유효 내용을 다시 읽어 큐에 전달한다. `ingest_wearable()`도 기기 커넥터가 성공하고 계획·실행 식별자가 모두 있을 때만 저장된 세션 행을 사용해 재평가를 만든다. 호출자가 주장한 원본 내용이 아니라 저장소가 정규화하고 받은 행이 업무 버전의 기준이다.

`wellnessbox-rnd/apps/inference_api/routes/interim.py`의 PRO 경로는 수정 이벤트를 수용한 뒤 현재 유효한 이벤트의 지문과 관찰 시각으로 새 업무 식별자를 계산한다. 같은 PRO 식별자의 값이 수정되면 정정 지문이 달라져 별도 재평가 업무가 생긴다. 기기 경로에서는 정규화 결과가 성공이고 계획 문맥이 모두 전달된 경우에만 `next_job_decision`을 반환한다. 지원하지 않는 단위처럼 커넥터 결과가 실패하면 측정 수신 시도는 기록할 수 있어도 계획 재평가 행은 추가하지 않는다.

같은 입력 identity와 같은 내용의 재전송은 기존 업무로 합쳐진다. 동일 identity에 다른 입력 지문을 억지로 전달하면 `workflow_job_idempotency_payload_conflict`가 발생한다. 활성 계획이 아니면 `followup_active_execution_plan_required`로 중단한다. 이 두 오류는 변경된 자료를 과거 업무로 숨기는 경우와 중단 계획을 다시 여는 경우를 구분한다.

## 구현 과정에서 입력의 기준점이 바뀐 이유

커밋 `c35abf`가 PRO·기기 수신 뒤 즉시 재평가 업무를 만드는 최초 경로와 중대 이상사례 중단을 함께 추가했다. 초기 diff에서는 일부 업무 식별 정보가 요청 본문(payload)과 요청 시각에 의존해, 정규화되거나 정정된 데이터베이스 행과 실제 재평가 버전이 어긋날 가능성이 있었다. 커밋 `b8d470`은 PRO와 기기 모두 저장된 행의 SHA-256과 유효 본문을 다시 읽도록 변경했다. PRO 정정에서는 새 지문을 입력 ID에 포함해 정정 전후 업무를 서로 다른 버전으로 남겼다.

커밋 `617d7f`는 PRO API가 정정 이벤트의 요청 시각이 아니라 저장 후 계산된 `effective_observed_at`을 업무 수신 시각으로 사용하도록 보강했다. `test_pro_correction_job_uses_stored_effective_observed_at`은 이 수정이 회귀하지 않도록, 미래에 기록된 원 이벤트를 과거 시각의 정정이 대체할 때 업무가 유효 관찰 시각을 따르는지 확인한다.

커밋 `3e6b7d`는 큐 생성 뒤의 결정 고리를 추가했다. `BoundedAgent.decide_followup_action()`은 실행 상태가 `FOLLOWUP_ACTIVE`일 때 정책의 `decide_next_action()`을 호출하고 결과 상태를 저장하며, `stop_and_escalate`면 실행을 `STOPPED`로 전환한다. 이 함수가 존재한다는 사실과 OP-075 등록 스모크가 해당 함수를 실행했다는 사실은 다르다. 현행 manifest 증거는 입력 업무 생성은 보여 주지만 배포 작업자가 업무를 선점해 이 결정을 호출했다는 기록은 제공하지 않는다.

## 테스트 이름별로 확인되는 결과

`wellnessbox-rnd/tests/test_interim_jobs.py`의 `test_pro_and_device_inputs_decide_immediate_reevaluation_jobs`는 PRO와 DEVICE가 서로 다른 `PLAN_REEVALUATION` 업무를 만들고 수신 시각·이유·입력 지문을 보존하는지 단언한다. `test_input_reevaluation_rejects_changed_receipt_and_stopped_plan`은 같은 identity의 지문 변경을 충돌로 거부하고, 계획 중단 뒤 새 입력이 큐에 들어가지 않는지 본다.

`wellnessbox-rnd/tests/test_interim_agent.py`의 `test_followup_inputs_decide_next_jobs_on_agent_path`는 에이전트 공개 메서드를 통해 PRO와 기기 자료를 넣은 뒤 공용 큐에 업무가 각각 한 건씩 생기는지를 확인한다. 이 검증은 큐 함수의 단위 시험을 넘어 입력 저장과 업무 생성이 상위 계층에서 끊기지 않았음을 보여 준다.

`wellnessbox-rnd/tests/test_pro_plan_service.py`의 `test_pro_plan_and_followup_api_require_token_and_persist`는 인증되지 않은 요청을 막고, 정상 PRO에서 `REEVALUATE_PLAN`과 초기 재평가 업무가 생기며 정정 후 별도 업무가 추가되는지 검사한다. 정상 기기 입력은 세 번째 업무를 만들고 잘못된 단위는 업무를 만들지 않아 최종 수가 3건이어야 한다. `test_pro_correction_job_uses_stored_effective_observed_at`은 앞서 설명한 저장 행 기준 시각을 직접 단언한다.

## 고정 실행은 큐 생성과 이후 안전 취소를 보여 준다

`wellnessbox-rnd/scripts/run_followup_input_serious_ae_smoke.py`는 임시 데이터베이스에 활성 계획을 준비하고 PRO `pro_smoke_1`과 기기 입력 `device_smoke_1`을 순서대로 넣는다. 출력 파일 `wellnessbox-rnd/data/original_plan/evidence/op075_op076_followup_input_serious_ae_smoke_v1.json`에는 12:00과 12:01 UTC에 예정된 별도 재평가 업무, `PRO_INPUT_RECEIVED`와 `DEVICE_INPUT_RECEIVED`, 각 입력 지문이 기록돼 있다. 뒤이어 같은 스크립트가 중대 이상사례를 넣기 때문에 최종 업무 상태는 둘 다 `CANCELLED`지만, 취소 전 입력별 업무가 생성된 결과는 보존된다.

그 JSON은 `op075_proven_stage=IMPLEMENTED`라고 자체 경계를 두며 배포 작업자, 서비스 연동, 프로덕션 입력 처리를 증명하지 않았다고 적는다. `source_commit=24d82df`에서 저장한 소스 묶음 해시 `3e2e9b…`도 현재 파일들로 계산한 `6686066e…`와 일치하지 않는다. 특히 후속 결정 함수는 스모크 뒤 커밋에서 추가됐으므로, 과거 JSON을 현행 결정 고리의 실행 증거로 쓰지 않았다.

## 현재 단계와 운영에서 필요한 연결 자료

manifest 운영 경로 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-075.json`은 로컬 실제 세션과 `workflow_jobs +1`을 기록하지만 `pro_observations` 증가는 0이고 기기 세션 증가량 항목도 없다. 입력 ID, 업무 ID, 업무 이유, 정책 결정 결과가 없으므로 그 한 건이 PRO 또는 기기 자료에서 만들어졌다고 역추적할 수 없다.

결론은 `IMPLEMENTED`다. 유효 입력 저장, 저장된 입력 버전(revision) 지문, 즉시 업무 생성, 정정 버전, 실패한 기기 자료 제외, 중단 계획 거부는 코드와 시험으로 확인됐다. 아직 확인되지 않은 것은 운영 자료를 선점한 작업자가 `decide_followup_action()`까지 호출한 기록, `maintain`·`adjust`·`stop_and_escalate` 중 선택한 규칙 ID, 선택 결과가 다음 복용 계획에 반영된 운영 행, 실제 입력 지연과 중복률이다. `OPERATED` 증거에는 가명 입력 영수증, 생성 업무, 선점·완료, 정책 출력, 상태 변경을 같은 추적 ID로 묶어야 한다.
