# OP-085 연구보고서: 상담 답변 검증기가 무엇을 막아야 하는가

## 결론부터 말하면

OP-085는 상담 답변 뒤에 형식 검사를 하나 붙이는 요구사항이 아니다. 사용자가 읽는 최종 문장에 근거 없는 주장이 섞이지 않았는지, 근거가 경고한 위험이 답변에서 빠지지 않았는지, 시스템이 말해서는 안 되는 진단이나 확정 표현이 들어가지 않았는지를 서버가 다시 판단하고, 하나라도 어긋나면 그 답변을 내보내지 말라는 요구사항이다. 이번 구현에서는 이 책임을 언어 모델에 맡기지 않았다. 언어 모델을 쓰더라도 모델은 허용된 상태와 근거 조각 식별자만 제안할 수 있고, 최종 문장은 저장소가 관리하는 템플릿으로 서버가 다시 만든다. 그 뒤 검증기가 원 질문, 저장소가 승인한 정책, 실제 검색 근거를 이용해 답변을 처음부터 다시 대조한다.

이 방식으로 OP-085의 required stage인 `IMPLEMENTED`, 즉 구현과 로컬 검증 단계까지 증명했다. WellnessBox 서비스의 운영 채팅에 연결했다거나, 배포된 환경에서 실제 사용자 답변을 차단했다거나, 외부 전문가가 차단 품질을 검증했다는 뜻은 아니다. 이번 증거가 말하는 범위는 현재 R&D 저장소에서 동일한 입력이 동일한 검증 결과를 만들고, 준비한 정상 사례와 변조 사례를 구분하며, 실패할 때 답변을 통과시키지 않는다는 데까지다.

## 왜 기존의 근거 연결 검사만으로는 부족했는가

OP-083과 OP-084를 구현하면서 상담 경로에는 이미 중요한 안전장치가 생겼다. 검색은 저장소가 승인한 지식 범위 안에서만 이루어졌고, 답변에는 근거 조각 식별자, 참고문헌 식별자, 주장 식별자, 유효일과 불확실성이 붙었다. 검증기는 답변이 존재하지 않는 근거를 가리키는지, 유효기간이 지난 근거를 사용하는지, 사용한 조각과 인용 목록이 서로 맞는지 확인했다. 이 검사는 출처의 신원을 보호하지만, 답변 문장의 의미까지 보호하지는 못했다.

예를 들어 올바른 와파린 상호작용 근거를 인용한 뒤 “효과가 보장된다”는 문장을 덧붙일 수 있었다. 인용 식별자는 진짜여도 덧붙인 문장은 근거가 지지하지 않는다. 반대로 근거에는 출혈 위험이 적혀 있는데 답변에서는 “주의해야 한다”는 모호한 말만 남길 수도 있었다. 이 경우 출처는 맞지만 사용자에게 필요한 핵심 위험이 사라진다. “제가 진단하겠습니다”, “완전히 안전합니다”, “반드시 치료됩니다” 같은 표현도 근거 식별자 검사만으로는 막을 수 없다. 따라서 OP-085에는 출처 무결성보다 한 단계 더 안쪽인 답변 의미 경계가 필요했다.

## 기존 시스템에서 재사용한 부분

새로운 상담 엔진이나 별도 근거 저장소는 만들지 않았다. 질문 분석에는 OP-082에서 만든 `extract_question_entities`를 그대로 사용한다. 이 함수는 건강 목표, 원료, 의약품, 위험 신호를 원 질문의 실제 문자열 위치와 함께 반환하며, 명시적인 부정 표현과 문장 절 경계도 구분한다. 검색 근거는 OP-081의 passage manifest와 OP-083의 승인된 지식 범위를 사용한다. 근거의 참고문헌 식별자와 주장 식별자, 유효 시작일과 폐기일은 OP-084의 답변 계약을 그대로 유지한다.

최종 답변 모델도 기존 `ChatTemplateAnswer`를 확장했다. 검증 결과 모델인 `ChatAnswerVerification`에는 기존의 인용 연결, 예상 참고문헌, 예상 주장, 범위, 유효일, 불확실성 검사에 더해 답변 grounding, 필수 위험 포함, 금지 표현 부재, 응급 우선순위, 정책 신원 검사를 추가했다. 한 검증 결과 안에서 이전 요구사항과 이번 요구사항을 함께 판단하므로, 앞선 안전장치를 우회하는 별도 경로가 생기지 않는다.

## 검증 정책을 코드에 숨기지 않은 이유

검증 규칙은 `data/knowledge/counseling_answer_verifier_policy_v1.json`에 버전이 있는 데이터로 기록했다. 정책에는 응급 위험 키, 응급 안내 세 문장과 순서, 금지 표현, 응급 답변에서 허용하지 않는 추천 표현, 약물 상호작용 답변이 반드시 포함해야 하는 위험 용어가 들어 있다. 정책 파일은 사람이 검토할 수 있고, 변경 이력을 Git에서 확인할 수 있다.

정책 로더는 알 수 없는 필드를 허용하지 않는다. 목록에는 빈 값이나 중복이 있을 수 없고, 정렬된 고유 값만 허용한다. 호출자가 같은 정책 식별자를 붙인 임의의 내용을 넘겨도 통과하지 않는다. 검증기는 전달받은 객체와 저장소의 정책 파일 전체가 정확히 같은지 비교한다. 따라서 정책 이름만 맞춰서 금지 표현 목록을 비우거나 응급 안내를 약하게 바꾸는 우회를 차단한다.

이 정책은 의학 지식 전체를 표현하려는 데이터베이스가 아니다. 현재 상담 모듈이 출력할 수 있는 좁은 답변 범위에서 지켜야 할 문장 경계를 적은 것이다. 새로운 상담 유형을 추가할 때는 근거 유형, 승인 템플릿, 필수 위험 표현과 변조 검사를 함께 확장해야 한다. 정책 파일에 단어 몇 개를 추가하는 것만으로 새로운 임상 능력이 생겼다고 주장해서는 안 된다.

## 근거 없는 주장을 어떻게 차단했는가

가장 강한 변경은 최종 문장의 소유자를 바꾼 것이다. 이전 OpenAI adapter 계약에서는 공급자가 상태, 답변 문장, 사용한 근거 조각을 반환할 수 있었다. 서버는 근거 조각이 허용 목록에 있는지 확인했지만, 공급자가 쓴 자유 문장 전체가 근거와 같은 뜻인지 결정적으로 증명하기 어려웠다. 자연어 함의 판정기를 또 붙이면 그 판정기 역시 불확실한 모델이 된다.

이번 구현에서는 공급자 응답 스키마에서 `answer_text`를 제거했다. 공급자는 `supported`, `unsupported`, `out_of_scope` 가운데 하나의 상태와 허용된 근거 조각 식별자만 반환한다. 서버는 지원되는 답변이면 정확히 한 개의 승인된 근거 조각을 선택하고, 해당 주장 유형에 연결된 서버 템플릿으로 문장을 만든다. 지원되지 않는 주장과 범위 밖 질문도 저장소에 있는 고정 문장을 사용한다. 공급자가 존재하지 않는 조각을 고르거나, 같은 조각을 중복해서 보내거나, 지원되지 않는 상태인데 근거를 붙이면 응답 파싱 단계에서 거부한다.

검증기는 여기서 한 번 더 같은 계산을 한다. 지원되는 답변은 선택한 근거 조각과 `answer_template_key`로 다시 만든 문장과 글자 단위로 같아야 한다. 지원되지 않는 답변과 범위 밖 답변도 각각 승인 문장과 정확히 같아야 한다. 누군가 Pydantic의 `model_copy` 같은 내부 기능으로 생성 후 객체를 바꿔도 최종 검증에서 `unsupported_or_unapproved_answer_text`가 발생한다. 단순히 “근거가 하나 있으니 통과”하는 구조가 아니다.

## 위험 누락은 근거 없는 주장과 다른 문제다

위험 누락은 거짓 문장을 추가하지 않아도 발생한다. 약물 상호작용 근거가 출혈 위험을 명시하는데 답변이 상호작용과 출혈을 말하지 않으면, 문장 자체는 조심스럽게 보일 수 있어도 사용자에게 필요한 정보가 사라진다. 그래서 검증 결과에서 답변 grounding과 필수 위험 포함을 별도 항목으로 나눴다.

현재 승인된 약물 상호작용 템플릿은 `drug interaction`과 `bleeding risk`를 모두 포함해야 한다. 검증기는 선택된 근거 조각의 `normalized_claim_type`이 `drug_interaction`이면 정책에 등록된 두 위험 용어가 최종 문장에 모두 있는지 확인한다. “조심해서 드세요”처럼 위험의 종류를 없앤 변조 답변은 템플릿 불일치뿐 아니라 `required_risk_omitted`로도 실패한다. 두 오류를 나누어 기록하면 답변이 왜 거부됐는지 재현할 수 있고, 향후 다른 위험 유형을 추가할 때도 누락 규칙을 독립적으로 확장할 수 있다.

## 금지 표현 검사는 어디까지 책임지는가

정책은 현재 범위에서 분명히 금지할 수 있는 표현을 보수적으로 등록했다. 시스템이 사용자를 진단한다고 말하는 표현, 치료나 효과를 보장하는 표현, 완전한 안전을 보장하는 표현, 응급 증상을 무시하거나 진료를 미루게 하는 표현이 포함된다. 검증은 대소문자를 통일한 최종 문장에 금지 문자열이 들어 있는지 확인한다. 하나라도 발견하면 `forbidden_expression_detected`를 기록하고 전체 검증을 실패시킨다.

문자열 목록만으로 모든 교묘한 자연어 우회를 잡을 수 있다고 주장하지 않는다. 동의어, 철자 변형, 여러 문장에 나눈 암시, 다른 언어 표현은 별도 평가 자료가 필요하다. 이번 구현에서 더 중요한 1차 방어선은 자유 문장 자체를 서버 출력 경로에서 제거한 것이다. 금지 표현 검사는 내부 객체 변조나 미래 템플릿 실수를 잡는 두 번째 방어선이다. 외부 언어 모델이 마음대로 쓴 문장을 금지어 목록만으로 안전하게 만든다는 설계가 아니다.

## 변조 검사를 어떻게 구성했는가

canonical smoke는 정상 상호작용 답변을 먼저 생성하고 모든 검증 항목이 참인지 확인한다. 그다음 동일한 근거와 메타데이터를 유지한 채 답변 문장만 다르게 바꾼다. 첫 번째 변조는 보장 표현을 덧붙여 근거 없는 주장과 금지 표현이 함께 잡히는지 본다. 두 번째는 상호작용과 출혈 위험을 지워 필수 위험 누락이 잡히는지 본다. 세 번째는 진단 표현을 넣는다. 네 번째는 응급 진료를 미루라는 문장으로 응급 안내를 바꾼다. 다섯 번째는 올바른 응급 안내 뒤에 보충제 추천을 덧붙인다. 마지막으로 정책 식별자를 위조한 객체를 넘겨 저장소 정책 신원 검사가 실패하는지 확인한다.

각 변조는 단순히 `passed=false`만 기록하지 않는다. 어떤 독립 검사에서 어떤 issue code가 생겼는지를 canonical JSON에 남긴다. smoke를 두 번 실행한 파일은 byte-identical해야 하며, source commit, source SHA-256, data SHA-256을 함께 기록한다. 이 증거로 테스트 문자열 하나만 맞춘 것이 아니라 정상 생성, 내부 변조, 정책 위조, 응급 경계가 같은 실행 안에서 구분되는지 확인한다.

## 검증 결과와 남은 한계

집중 테스트에서는 기존 검색·답변·adapter 회귀와 새 변조 사례가 함께 통과했다. canonical smoke는 24개 passage와 19개 출처로 구성된 기존 상담 corpus를 그대로 사용한다. 모델 학습이나 frozen evaluation 자료 변경은 없었다. 서비스 저장소도 수정하지 않았다. 따라서 이번 결과는 기존 R&D 상담 경로를 강화한 구현 증거이지, 새 상담 제품이나 운영 성과의 증거가 아니다.

가장 큰 한계는 승인 템플릿 밖의 풍부한 자연어 상담을 아직 제공하지 않는다는 점이다. 이 제한은 의도적이다. 근거 없는 문장을 자유롭게 만들 수 있게 한 뒤 사후 분류기로 막는 것보다, 현재 증명할 수 있는 문장만 생성하는 편이 OP-085에 더 직접적으로 맞는다. 앞으로 답변 범위를 넓히려면 문장 단위 주장 구조, 각 주장과 근거의 정확한 연결, 위험 유형별 필수 정보, 다국어 금지 표현 평가를 함께 설계해야 한다.

또한 로컬 테스트는 실제 사용자의 표현 다양성과 운영 중 공격 입력을 대표하지 않는다. 외부 전문가 검토, 운영 로그, 차단 오탐과 미탐 측정은 별도 증거 단계다. 그러므로 OP-085는 required stage인 `IMPLEMENTED`까지만 완료로 기록하며, 서비스 통합이나 운영, 외부 검증을 수행했다고 적지 않는다.

## 최종 판단

OP-085의 핵심은 “검증기라는 이름의 함수가 있다”가 아니라, 검증에 실패한 문장이 최종 출력 경계를 넘지 못하는 구조다. 이번 구현은 공급자의 자유 문장을 최종 답변에서 제거하고, 저장소 정책과 실제 근거로 답변을 재구성하며, 근거 없는 주장·필수 위험 누락·금지 표현·정책 위조를 서로 다른 검사로 차단한다. 이 구조와 변조 증거를 기준으로 OP-085는 `IMPLEMENTED`를 충족한다. 더 높은 단계의 주장은 실제 서비스 연결과 운영 관측, 외부 평가가 생긴 뒤에만 가능하다.

Reference basis: Toss의 쉬운 개념 설명형 글과 기술 설명형 글의 문제 제시→구체적 예시→판단 경계 흐름.
