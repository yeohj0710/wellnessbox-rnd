# OP-041 서비스와 R&D 성분 식별자의 변환표를 버전 관리한다.

## 요구사항과 식별자 불일치 문제

WellnessBox 서비스는 ING:MAGNESIUM 같은 서비스 식별자를 쓰고 R&D 저장소는 magnesium_glycinate 같은 카탈로그 키를 쓴다. OP-041은 두 이름을 문자열 추측으로 바꾸지 않고, 관계와 허용 방향을 명시한 같은 버전의 계약을 두 저장소가 사용하게 하는 요구사항이다. 변환할 수 없는 식별자는 조용히 버리지 않고 오류 진단을 남겨야 한다.

manifest 파일은 data/original_plan/requirements_manifest_v1.json이다. OP-041의 required_stage와 claimed_stage는 INTEGRATED다. 현재 구현 파일은 최신 버전으로 일치하지만, 등록된 저장 스모크와 실행 스크립트가 이전 버전을 요구하므로 현재 근거를 INTEGRATED로 볼 수 없다.

## 현재 변환표의 계약

R&D 원본은 data/contracts/wellnessbox_ingredient_identifier_map_v1.json이고 서비스 복사본은 C:/dev/wellnessbox/contracts/wb-rnd/ingredient-identifier-map-v1.json이다. 두 파일의 mapping_version은 2026-07-24.1이며 바이트가 완전히 같다. 현재 SHA-256은 두 파일 모두 cf86d34c8ebaab03e9819de2e5b436b8c0badc93389a5c55fd9df6b8317fb749다.

계약에는 10개 변환이 있다. equivalent 관계는 coq10, l_theanine, omega3, probiotics, vitamin_c, zinc에 양방향 변환을 허용한다. calcium_citrate→ING:CALCIUM, magnesium_glycinate→ING:MAGNESIUM, vitamin_d3→ING:VITAMIN_D는 서비스 범주가 더 넓은 service_broader라서 rnd_to_service만 허용한다. soluble_fiber→ING:PSYLLIUM은 서비스 항목이 더 좁은 service_narrower이고 현재 서비스 응답에 필요한 rnd_to_service 방향만 등록됐다.

서비스에만 있는 ING:FOLATE, ING:IRON, ING:LUTEIN, ING:PROTEIN, ING:VITAMIN_B12 다섯 개와 R&D에만 있는 berberine, vitamin_b_complex 두 개는 unmapped 목록에 이유와 함께 남는다. 특히 vitamin_b_complex를 ING:VITAMIN_B12로 바꾸지 않는 이유는 복합 비타민 B와 단일 B12가 동등하지 않기 때문이다.

## 두 저장소에서 사용하는 코드

C:/dev/wellnessbox/lib/server/wb-rnd-ingredient-map.ts는 계약을 읽고 버전, 중복, 카탈로그 범위, 관계별 허용 방향을 검사한다. C:/dev/wellnessbox/lib/server/wb-rnd-interim-safety-authority.ts는 R&D의 준비된 추천 성분을 서비스 식별자로 바꿀 때 이 변환표를 사용한다. 변환이 없거나 허용되지 않은 방향이면 추천을 누락하는 대신 전체 상위 응답을 service_fail_closed로 바꾼다.

R&D와 서비스가 JSON 복사본을 따로 두는 대신 완전한 바이트 일치를 요구한 이유는, 같은 버전 문자열 아래 내용이 달라지는 문제를 막기 위해서다. 서비스 계약에서 허용한 service_narrower 관계도 코드와 QA가 명시적으로 이해해야 하며, 단순한 이름 동일성으로 처리하지 않는다.

## 2026-07-24.1에서 수정한 공통 결함

처음 저장된 2026-07-16.1 계약은 8개 변환만 포함했고 l_theanine과 soluble_fiber를 미변환 항목으로 남겼다. 커밋 558d703 계열은 l_theanine↔ING:L_THEANINE을 equivalent로 추가하고, soluble_fiber→ING:PSYLLIUM을 service_narrower 및 rnd_to_service로 추가했다. R&D 테스트도 서비스 식별자가 R&D 식별자와 항상 일대일로 같은 집합이라는 잘못된 가정을 없애고 방향 관계를 따로 검사하도록 바뀌었다.

서비스 저장소의 커밋 2be075 계열은 같은 2026-07-24.1 계약을 반영하고 service_narrower를 허용하며, 남은 미변환 식별자를 진단으로 노출하도록 고쳤다. 이 수정은 두 성분만 예외 처리한 것이 아니라 관계 종류와 변환 방향이라는 공통 규칙을 계약에 추가한 변경이다.

## 등록 테스트와 자동 검사

manifest의 구현 근거는 data/contracts/wellnessbox_ingredient_identifier_map_v1.json, C:/dev/wellnessbox/contracts/wb-rnd/ingredient-identifier-map-v1.json, C:/dev/wellnessbox/lib/server/wb-rnd-ingredient-map.ts, C:/dev/wellnessbox/lib/server/wb-rnd-interim-safety-authority.ts다. 모두 존재하고 현재 2026-07-24.1 계약을 사용한다.

테스트 근거는 tests/test_ingredient_identifier_mapping.py, scripts/run_ingredient_mapping_goal_prior_smoke.py, C:/dev/wellnessbox/scripts/qa/check-rnd-ingredient-map.cts, C:/dev/wellnessbox/scripts/qa/check-rnd-final-safety-authority.cts다. test_service_and_rnd_identifier_map_contracts_are_byte_identical는 복사본 동일성을 확인한다. test_identifier_map_covers_both_current_catalogs_without_ambiguity, test_identifier_map_keeps_lossy_relationships_directional, test_every_mapping_supports_the_live_rnd_to_service_response_direction은 범위·방향·실제 응답 방향을 나눠 검증한다.

통합 근거로 data/original_plan/evidence/op041_op042_ingredient_mapping_goal_prior_smoke_v1.json, .github/workflows/original-plan-evidence.yml, C:/dev/wellnessbox/.github/workflows/encoding-guard.yml이 등록되어 있다. 두 workflow는 관련 스모크와 QA를 실행하도록 구성되어 있고, 서비스의 check-rnd-final-safety-authority.cts는 현재 2026-07-24.1을 기대한다.

## 저장 스모크가 현재 통합을 증명하지 못하는 이유

data/original_plan/evidence/op041_op042_ingredient_mapping_goal_prior_smoke_v1.json은 mapping.version=2026-07-16.1과 SHA-256 791665daff71fa747783cc2ff732daf9411ebb52940dd77b94b633130124ce53을 기록한다. observed 값도 ING:MAGNESIUM 변환, 미변환 HTTP 502 등 이전 계약에서 관측한 결과다. production_operation_proven은 false다.

더 중요한 문제는 현재 scripts/run_ingredient_mapping_goal_prior_smoke.py의 95행이 observed_authority.mapping_version을 여전히 2026-07-16.1과 비교한다는 점이다. 현재 서비스 QA는 2026-07-24.1을 반환하도록 구현되어 있으므로 두 저장소의 최신 코드를 함께 실행하면 이 스크립트가 mapping_version_not_observed로 실패할 수밖에 없다. 저장 JSON을 새 버전으로 바꾸는 것만으로는 부족하고, 실행 스크립트의 기대값과 현재 해시·관계 사례를 함께 갱신해야 한다.

## 현재 단계와 남은 검증

현재 근거 단계는 IMPLEMENTED다. 최신 계약, 두 저장소의 바이트 동일성, 서비스 변환 코드와 단위·QA 검사는 존재한다. 그러나 등록된 교차 저장소 스모크는 이전 맵을 기록하고 현재 실행 스크립트도 이전 버전을 강제하므로 INTEGRATED 주장은 현재 상태와 맞지 않는다. 이번 검토에서는 스모크나 CI를 재실행하지 않았다.

INTEGRATED로 올리려면 scripts/run_ingredient_mapping_goal_prior_smoke.py를 2026-07-24.1 계약과 10개 관계에 맞게 수정하고, 두 현재 저장소를 실제 HTTP 또는 동등한 교차 저장소 경로로 실행해 새 JSON을 남겨야 한다. 새 결과는 L-테아닌·차전자피 변환, 남은 5개 서비스·2개 R&D 미변환 항목, 매핑 실패 HTTP 502, 두 계약의 현재 SHA-256을 확인해야 한다. 운영 및 외부 근거는 등록되어 있지 않다.
## 추천 후보를 점수로 바꿀 때
추천 후보를 잘 고르는 일과 특정 후보를 복용했을 때의 효과를 추정하는 일은 다르다. 이 그룹은 입력 신호가 어떤 점수로 바뀌는지, 안전 차단 전후의 후보가 어떻게 보존되는지, 불확실성을 어디에 표시하는지를 분리해 설명한다.

`OP-041`는 “서비스와 R&D 성분 식별자의 변환표를 버전 관리한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/data/contracts/wellnessbox_ingredient_identifier_map_v1.json`, `wellnessbox/contracts/wb-rnd/ingredient-identifier-map-v1.json`, `wellnessbox/lib/server/wb-rnd-ingredient-map.ts`, `wellnessbox/lib/server/wb-rnd-interim-safety-authority.ts`
- 테스트·실행: `wellnessbox-rnd/tests/test_ingredient_identifier_mapping.py`, `wellnessbox-rnd/scripts/run_ingredient_mapping_goal_prior_smoke.py`, `wellnessbox/scripts/qa/check-rnd-ingredient-map.cts`, `wellnessbox/scripts/qa/check-rnd-final-safety-authority.cts`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op041_op042_ingredient_mapping_goal_prior_smoke_v1.json`, `wellnessbox-rnd/.github/workflows/original-plan-evidence.yml`, `wellnessbox/.github/workflows/encoding-guard.yml`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
