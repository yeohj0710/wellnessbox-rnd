# OP-023 원문, 파싱 구간, 주장, 규칙, 추천 결과의 계보를 연결한다

## 결과만 남기면 같은 판단을 다시 설명할 수 없다

원본 계획 16쪽은 의약학 데이터베이스와 학술지, 식품의약품안전처·약학정보원 자료를 문단이나 표 단위로 나누고 태그와 ID를 붙인 뒤 엔진이 직접 근거를 조회하는 구상을 보여 준다. 추천 결과에 문헌 제목만 적는 것으로는 부족하다. 원문의 어느 구간을 어떻게 해석했고, 어떤 주장과 규칙을 만들었으며, 그 규칙이 실제 추천 결과에 쓰였는지를 한 줄로 따라갈 수 있어야 한다.

OP-023은 이 연결을 `source → passage → claim → rule → execution output`으로 고정한다. source는 로컬에 보존한 원문과 출처 메타데이터다. passage는 줄 번호와 발췌문이 있는 파싱 구간이다. claim은 그 구간에서 정규화한 주장이고 rule은 실행 가능한 안전·추천 규칙이다. 마지막 execution output은 실제 추천 실행에서 생성된 안전 판단, 추천 결정 또는 추천 항목이다.

## ingestion 단계에서 원문과 파싱 구간을 분리한다

`src/wellnessbox_rnd/ingestion/reference_ingestion.py`는 `data/raw_references/*.md`의 frontmatter와 JSON claim block을 읽는다. frontmatter에는 reference ID, 원문 제목, source type, 원본 URI, 파싱 원문 URI, license, 시행일과 만료일이 들어간다. claim block에는 claim ID, 정규화된 claim type, 성분·약물·도메인 key와 선택적 rule candidate가 들어간다.

parser는 claim의 JSON block이 있는 실제 시작·종료 줄과 excerpt를 `CitationSpan`으로 만든다. claim이 reference ID를 잃거나 줄 시작이 종료보다 늦거나 발췌문이 비어 있으면 artifact validation이 실패한다. rule도 claim ID와 reference ID, 같은 citation span을 가져야 한다. 따라서 문헌 제목과 규칙만 이어 붙인 추정 계보를 허용하지 않는다.

현재 `data/knowledge/reference_knowledge_base_v1.json`에는 출처 19개, 파싱 claim 24개, rule candidate 5개가 있다. `data/knowledge/runtime_knowledge_db_v1.json`은 같은 reference 19개와 reference span 24개를 실행용 계약으로 옮긴다. 원문 artifact와 runtime DB가 각자 새 ID를 만들지 않고 reference·claim 식별자를 공유한다.

## normalized store가 source부터 rule까지 외래키로 묶는다

`src/wellnessbox_rnd/interim/store.py`는 `source_registry`, `evidence_passages`, `knowledge_claims`, `knowledge_rules`, `claim_rule_links`를 정의한다. passage는 source를, claim은 passage를, link는 claim과 rule을 각각 외래키로 참조한다. `execution_knowledge_lineage`는 실행·이벤트·규칙·주장·passage·source를 한 행에 연결한다.

`src/wellnessbox_rnd/interim/knowledge_lineage.py`의 `KnowledgeLineageRegistry.sync_reference_artifact`는 reference artifact를 검증한 뒤 이 표들을 채운다. 원문 파일 bytes의 SHA-256을 source metadata에 넣고, claim excerpt와 줄 범위를 passage에 저장한다. claim과 rule의 canonical payload도 checksum으로 만든다. 같은 artifact를 다시 sync하면 같은 식별자를 갱신하므로 중복 source나 claim을 늘리지 않는다.

데이터 class도 분리한다. 정본에서 만든 source·claim·rule은 `PROXY_GOLD_SIMULATION`으로 등록하고, 실제 요청 처리에서 생긴 결과 연결은 `INTERIM_RUNTIME_EVENT`로 기록한다. 정적 지식 자산과 실행 로그가 같은 계보를 공유하더라도 두 데이터의 성격을 혼동하지 않는다.

## 추천 실행은 응답에 실제로 등장한 규칙만 연결한다

`apps/inference_api/routes/recommend.py`는 추천 전에 정본 지식 artifact를 registry에 sync한다. `src/wellnessbox_rnd/interim/data_lake.py`가 추천·안전·최적화 core event를 저장할 때 `persist_execution_knowledge_lineage`를 호출한다. 이 함수는 응답의 `safety_summary.rule_refs`와 각 rule의 claim ID를 읽고, normalized store에서 실제 claim–rule link가 존재하는지 확인한다.

안전 event에는 `safety_rule`, 추천 event에는 `recommendation_decision`을 연결한다. 선택된 추천 성분과 관련 claim이 있으면 optimization event에 `recommendation_item`도 연결할 수 있다. 존재하지 않는 rule·claim 조합은 추정해서 만들지 않는다. 한 rule이 여러 claim을 가질 때도 `(output, rule, claim)`별로 별도 lineage를 보존한다.

각 lineage 행의 ID는 execution ID, event ID, output type·key, rule ID와 claim ID의 canonical hash로 결정한다. 같은 연결을 다시 넣어도 `insert or ignore`와 unique key가 중복을 막는다. 서로 다른 claim을 가진 같은 rule은 같은 행으로 합쳐지지 않는다. 이 경계는 `ab0307b`에서 multi-rule·multi-claim 보존 규칙으로 강화됐다.

## 동의가 없으면 결과 계보도 저장하지 않는다

계보가 자세할수록 사용자 결과와 지식 근거를 쉽게 결합할 수 있다. 그래서 `ExecutionLedger.record_recommendation`은 실제 사용한 출처가 모두 영속 저장을 허용할 때만 execution knowledge lineage를 기록한다. 저장 동의를 거부한 요청도 안전 추천은 계산할 수 있지만 trace의 `knowledge_lineage`는 빈 배열이고 table에도 행이 남지 않는다.

이 규칙은 source와 claim 같은 공용 지식 정본을 지우는 규칙이 아니다. 사용자 실행과 지식 근거를 결속한 runtime row만 저장하지 않는다. 공용 지식의 존재와 특정 사용자가 그 지식을 적용받았다는 사실을 분리해 개인정보 저장 동의를 적용한다.

## 대표 실행은 warfarin 차단 계보를 끝까지 보여 준다

`tests/test_knowledge_lineage.py`는 warfarin 5 mg을 복용하고 glucosamine을 입력한 요청을 실제 `/v1/recommend`에 보낸다. 응답은 blocked이고, trace에는 `KB-SAFETY-ANTICOAG-001` 규칙, `CLM-KNOWLEDGE-ANTICOAG-001` 주장, `REF-KNOWLEDGE-ANTICOAG-001` source가 연결된다. output type은 `safety_rule`과 `recommendation_decision` 두 개다.

두 lineage는 모두 응답의 같은 execution ID를 사용한다. source URI는 파싱된 로컬 원문 `data/raw_references/supplement_warfarin_interaction.md`, upstream reference URI는 `data/knowledge/supplements/supplement_overdose_and_drug_interactions_expert.md`다. citation span은 13~33줄이며 source content checksum도 64자리 SHA-256으로 반환된다.

같은 테스트 묶음은 정본 sync를 두 번 실행해 count가 변하지 않는지, 한 규칙의 여러 claim이 모두 보존되는지, 저장 동의 거부 시 결과 계보가 비어 있는지 검사한다. `tests/test_reference_ingestion.py`와 `tests/test_runtime_knowledge_db.py`는 parser와 runtime artifact의 ID·span 전달을 따로 검증한다.

## canonical smoke는 현재 정본에서 기대 개수를 계산한다

`scripts/run_knowledge_lineage_smoke.py`는 임시 schema 14 SQLite와 실제 FastAPI route를 사용한다. 정본 artifact에서 기대 source·passage·claim·rule·link 수를 읽고, route가 sync한 database count와 비교한다. 현재 `data/original_plan/evidence/op023_op024_knowledge_lineage_smoke_v1.json`은 19 sources, 24 passages, 24 claims, 5 rules, 5 claim-rule links와 실행 lineage 2개를 기록한다.

기존 smoke는 초기 artifact의 `3/5/5/5/5`를 하드코딩해 정본 확장 뒤 재생에 실패했다. 이번 loop에서 하드코딩을 제거하고, evidence의 schema version과 다섯 count가 현재 코드·artifact와 같은지 검사하는 회귀 테스트를 추가했다. smoke를 두 번 재생한 SHA-256은 같아 실행 ID나 시각이 정본 JSON에 섞이지 않는다.

## IMPLEMENTED 완료와 근거 품질의 한계

manifest의 required·claimed stage는 `IMPLEMENTED`다. parser, normalized schema, 추천 결과 연결, 동의 경계, API trace, 회귀 테스트와 재현 가능한 smoke가 있으므로 OP-023은 `COMPLETE`다. 그러나 모든 외부 문헌을 수집했다거나 각 claim의 의학적 진실을 독립 검증했다는 뜻은 아니다. 현재 승인된 로컬 artifact 안에서 계보를 잃지 않는 구현 완료다.

이번 loop는 stale smoke 재생기와 현재성 테스트, 보고서만 변경했다. production, 서비스 보호 파일, 원천 지식 내용, frozen 256건, 학습 데이터, 모델과 simulation은 변경하지 않았다. 공식 frozen 일곱 지표, replay와 weakest slice delta는 0이다. `OPERATED`를 주장하려면 배포 환경에서 장기 실행 trace의 계보 완전성, 원문 교체·폐기 처리, 조회 장애와 복구 receipt를 관측해야 한다.
