# OP-099 같은 기기 이벤트의 중복 수신을 차단한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/interim/connectors.py`에서 구현과 검증 대상을 확인할 수 있다.

## 결론

같은 기기 이벤트가 새 세션 ID로 다시 들어와도 한 번만 저장하도록 수신 경계를 바꿨다. 중복 판정 기준은 클라이언트가 매번 새로 만들 수 있는 `session_id`가 아니다. 사용자 프로필, W/C/G 출처, 공급자가 부여한 `source_record_id`를 묶어 `event_identity`를 만든다. 같은 식별자와 같은 payload가 다시 오면 최초 영수증을 반환하고 `deduplicated=true`를 표시한다. 같은 식별자에 다른 payload가 붙으면 `duplicate_device_event_conflict`로 거절한다. 한 세션 ID를 다른 이벤트에 다시 쓰는 경우도 `device_session_identity_conflict`로 거절한다.

OP-099의 요구 단계는 `OPERATED`다. 이번 변경은 로컬 API, SQLite 트랜잭션, 고정 사례, 자동 테스트로 구현과 통합 동작을 증명했다. 실제 기기 공급자의 운영 트래픽, 배포 환경의 중복률, 장기 보관 정책은 증명하지 않았다. 따라서 주장 단계는 `IMPLEMENTED`, 완료 판정은 `PARTIAL`이다.

## 세션 ID만 비교하면 놓치는 중복

기존 수신 함수는 `connector_sessions.session_id`가 이미 있는지만 확인했다. 네트워크 재시도나 모바일 앱 재시작 뒤에 새 세션 ID가 붙으면 같은 공급자 이벤트도 새 행으로 저장됐다. 반대로 같은 세션 ID에 다른 payload가 오면 `on conflict do nothing`으로 저장만 생략하고, 호출자에게는 입력 payload로 계산한 성공 결과를 돌려줄 수 있었다. 저장 결과와 응답 결과가 어긋날 수 있는 경계였다.

기기 이벤트의 정체성은 전송 시도와 분리해야 한다. 이번 구현은 `profile_id:source:source_record_id`를 해시해 안정적인 `event_identity`를 만든다. 사용자와 출처를 포함하므로 서로 다른 사용자의 `watch-1`, W와 C가 각각 보낸 `record-1`은 충돌하지 않는다. `source_record_id`가 빠진 잘못된 payload는 세션 ID를 보조 식별자로 사용한다. 잘못된 이벤트끼리 무관하게 합쳐지지 않게 하면서 schema 실패 기록도 남길 수 있다.

## 첫 기록과 재수신을 한 트랜잭션에서 가른다

`InterimStore.transaction(immediate=True)`가 중복 조회, 세션 저장, 영수증 저장을 한 쓰기 트랜잭션으로 묶는다. 처리 순서는 다음과 같다.

1. 요청 출처와 동의 범위를 확인한다.
2. `environment`와 `data_class` 조합을 확인한다.
3. 정규화한 JSON의 SHA-256과 이벤트 식별자를 계산한다.
4. `device_event_receipts`에서 같은 이벤트 식별자를 찾는다.
5. 영수증이 있으면 프로필, 출처, 공급자 레코드 ID, 데이터 분류, payload 해시를 모두 비교한다.
6. 모든 값이 같으면 최초 세션 ID와 최초 후조건을 반환한다.
7. 하나라도 다르면 충돌로 거절한다.
8. 영수증이 없지만 세션 ID가 이미 있으면 세션 재사용 충돌로 거절한다.
9. 새 이벤트만 `connector_sessions`와 `device_event_receipts`에 함께 저장한다.

중복 요청에 새 세션 ID가 들어와도 응답은 최초 저장된 세션 ID를 돌려준다. 후속 작업 큐도 응답의 canonical 세션 ID를 사용한다. 존재하지 않는 재시도 세션을 조회하거나 작업 입력 ID로 등록하지 않는다.

## 영수증은 나중에 고칠 수 없다

스키마 버전 14에 `device_event_receipts`를 추가했다. 영수증에는 이벤트 식별자, 최초 세션 ID, 사용자 프로필, W/C/G 출처, 공급자 레코드 ID, 데이터 분류, 후조건별 성공 여부, payload SHA-256, 생성 시각을 저장한다. `event_identity`는 기본키다. SQLite의 update/delete trigger는 두 연산을 `device_event_receipts_append_only`로 거절한다.

이 테이블은 중복 차단 결과를 사후에 재구성하는 최소 감사 기록이다. `connector_sessions`는 KPI와 수집 결과를 담고, 영수증은 어떤 이벤트 정체성이 어떤 최초 세션과 payload에 묶였는지 담는다. 두 역할을 나누면 중복 요청을 별도 성공 표본으로 세지 않으면서도, 충돌 원인을 분명하게 설명할 수 있다.

## API는 충돌과 잘못된 입력을 구분한다

`/v1/interim/connectors/device`는 이벤트 정체성 충돌과 세션 정체성 충돌에 HTTP 409를 반환한다. 지원하지 않는 출처, 환경, 데이터 분류 불일치는 422다. 동의 범위가 없으면 403이다. 호출자는 같은 요청을 안전하게 재시도할 수 있고, payload가 달라진 충돌은 자동 재시도 대신 조사 대상으로 분류할 수 있다.

재수신이 성공 후속 작업을 요구하는 경우에도 최초 행의 payload와 해시를 읽는다. 따라서 첫 요청과 재시도 요청이 같은 실제 이벤트라는 조건 아래 작업 큐의 입력도 하나의 canonical 세션을 가리킨다.

## 고정 사례에서 확인한 결과

`op099_op100_device_dedup_linkage_cases_v1.json`은 일곱 사례를 고정한다. OP-099와 직접 연결되는 사례는 새 세션 ID를 사용한 동일 이벤트 재수신, 같은 공급자 레코드 ID에 값이 달라진 충돌, 같은 세션 ID에 다른 공급자 레코드를 붙인 충돌, 환경과 데이터 분류의 불일치, append-only 영수증 변조다.

canonical smoke는 실제 FastAPI `TestClient`와 임시 SQLite를 사용했다. `watch-1`을 `w1`로 먼저 보낸 뒤 `w-retry`로 다시 보내자 두 번째 응답은 `deduplicated=true`, canonical 세션 ID는 `w1`이었다. 값만 99로 바꾼 요청은 409와 `duplicate_device_event_conflict`를 반환했다. `w1` 세션에 `watch-2`를 붙인 요청도 409와 `device_session_identity_conflict`를 반환했다. 성공·실패를 포함한 고유 이벤트 다섯 개를 보낸 뒤 두 테이블의 행 수는 모두 다섯 개였다. 영수증 update는 append-only trigger가 거절했다.

집중 테스트는 서로 다른 세션 ID 중복, 변경 payload 충돌, 세션 재사용, production 데이터 분류, 환경·분류 불일치, 영수증 불변성을 각각 검사한다. 기존 proxy KPI와 importer 기록도 회귀하지 않도록 기존 테스트를 함께 실행했다.

## 구현 단계에서 남은 경계

이번 증거의 `environment="production"`은 production 데이터 분류 계산을 검사하기 위한 로컬 입력이다. 실제 공급자 인증, 서명 검증, 배포 인스턴스, 운영 데이터베이스, 운영 대시보드를 뜻하지 않는다. 이름에 production이 포함됐다는 이유로 운영 증거로 올리지 않았다.

`OPERATED`로 올리려면 실제 공급자 이벤트의 안정적인 `source_record_id` 계약을 확인해야 한다. 여러 인스턴스가 같은 운영 데이터베이스를 사용할 때 동시에 도착한 재시도가 한 행만 만드는지 부하 조건에서 검사해야 한다. 기간별 총 수신 수, 고유 수신 수, exact replay 수, payload conflict 수를 관측하고 충돌 대응 절차를 연결해야 한다. 보존 기간과 개인정보 삭제 요구가 append-only 감사 기록에 어떤 예외 절차를 요구하는지도 운영 정책으로 정해야 한다.

## 현재 판정

중복의 정체성을 세션에서 실제 공급자 이벤트로 옮겼고, exact replay와 conflicting replay를 분리했다. 영수증은 append-only이며 API와 후속 작업은 최초 세션을 일관되게 사용한다. 구현과 로컬 재현 증거는 충분하지만 실제 운영 수신 기록이 없으므로 OP-099는 `IMPLEMENTED / PARTIAL`로 남는다.
