# OP-105 사용자 프로필 저장과 추천 API가 R&D 서버까지 왕복하는지 검증한다

요구사항 장부(manifest)에 등록된 통합 증거는 `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`이다. 이 파일과 생성기, 서비스 호출 코드, R&D 저장·추천 경로를 함께 대조했다.

## 왜 저장과 추천을 한 번에 따라가야 하는가

이 요구사항의 핵심은 두 번의 요청이 같은 사람을 가리키는지 입증하는 것이다. 프로필을 저장한 요청과 추천 요청의 식별자가 다르면, 추천 엔진은 방금 받은 나이·임신 상태·복용 약물을 읽지 못한다. 반대로 브라우저가 보낸 식별자를 그대로 믿으면 다른 사용자의 프로필을 지정할 위험이 생긴다. 그러므로 로그인한 서비스 사용자에서 가명 식별자를 만들고, 그 식별자가 R&D 저장소에 기록된 뒤 추천 안전 판정에 다시 쓰이는 전 과정을 확인해야 했다.

WellnessBox의 `lib/server/wb-rnd-interim-route.ts`는 브라우저가 보낸 `profile_id`를 버리고 로그인 세션의 `appUserId`를 사용한다. `lib/server/wb-rnd-interim-client.ts`는 비밀값을 섞어 원래 값을 알아내기 어려운 식별자를 만드는 HMAC-SHA256 방식으로 `usr_` 접두사의 32자리 가명 ID를 만든다. 이 호출 코드는 서버 전용이며, 허용된 API 경로만 통과시키고 내부 토큰과 제한 시간을 적용한다. 프로필 본문도 `minimizeWbRndStoredProfile`을 거쳐 R&D 서버로 보낸다. 이 선택은 원래 사용자 ID와 불필요한 개인정보를 R&D 데이터베이스에 복제하지 않으면서 두 요청의 동일성을 유지한다.

## R&D 서버가 저장 내용을 다시 사용하는 방식

`apps/inference_api/routes/interim.py`의 `/v1/interim/profiles`는 프로필을 키 순서가 고정된 JSON으로 정리하고 SHA-256 지문과 함께 `user_profiles`에 저장한다. 같은 ID가 다시 들어오면 동의 범위, 저장 내용과 지문을 갱신한다. `/v1/interim/recommendations`는 먼저 해당 ID의 저장 행을 읽는다. 행이 없으면 `profile_not_found`로 끝나며, 저장된 프로필과 이번 요청의 안전 입력을 따로 평가한 뒤 합친 결과도 다시 평가한다.

저장된 위험 사실을 새 추천 요청의 빈 `safety` 값으로 지울 수 없게 한 점이 중요하다. 등록 핵심 경로 시험(smoke)에서 프로필은 임신 상태와 와파린 복용을 포함하고, 추천 요청은 심혈관 목표와 오메가3를 보낸다. 결과는 `BLOCKED`, 추천 목록은 빈 배열이며 추천 실행 ID는 남는다. 안전 차단 전에는 모델을 실행하지 않고, 차단되지 않은 경우에만 모델 결과를 다시 안전 규칙에 통과시킨다. 따라서 왕복 성공을 추천 상품 생성으로 꾸미지 않고, 저장된 고위험 정보가 실제 최종 권한으로 작동했는지를 관찰값으로 삼았다.

## 실제 두 프로세스 검증과 실패 경계

`scripts/run_profile_review_roundtrip_smoke.py`는 빈 임시 SQLite를 만든 뒤 FastAPI를 별도 프로세스로 띄운다. 이어서 WellnessBox의 `scripts/qa/check-rnd-profile-review-roundtrip.cts`를 Node.js에서 실행해 실제 서비스 라우트와 실제 HTTP 클라이언트를 거친다. 고정 사례는 8건이며, OP-105에 직접 해당하는 검사는 프로필 저장, 저장 프로필을 사용한 추천, 비어 있지 않은 추천 실행 ID, 로그인 거부, 브라우저 식별자 무시다. 결과 파일에는 `profile_roundtrip_completed=true`, `recommendation_roundtrip_completed=true`, `service_route_auth_denial_executed=true`, `service_profile_id_override_executed=true`가 기록돼 있다.

검증은 위험 정보 때문에 추천이 차단되는 경로를 골랐다. 모델 자료가 없어서 우연히 실패한 것과 저장 프로필을 읽어 안전 규칙이 차단한 것을 구분할 수 있기 때문이다. 서비스 라우트는 인증되지 않은 요청을 R&D 호출 전에 401로 막았고, 추천 응답의 실행 ID와 차단 상태를 확인했다. 다만 생성기는 서비스 소스의 Git 식별자로 `fb00e4ebd972a6630235dda8b09593d27e277ccd`를 기록할 뿐, 이 보고서 작업에서는 금지된 git 명령을 실행하지 않아 현재 파일과 그 커밋의 동일성은 다시 계산하지 않았다.

## 현재 단계와 운영 영수증의 한계

왕복 전체에 대해 직접 입증된 단계는 `INTEGRATED`다. 실제 WellnessBox 서버 코드, 별도 FastAPI 프로세스, 내부 인증, HTTP 직렬화와 임시 SQLite를 통과했기 때문이다. smoke 자체도 요구 단계 `OPERATED`, 주장 단계 `INTEGRATED`로 기록하고 공개 배포와 실제 운영을 `false`로 남겼다.

manifest에는 이후 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-105.json`이 추가돼 OP-105가 `OPERATED`로 표시돼 있다. 그러나 이 영수증의 세션에서는 `user_profiles`가 1건 늘었지만 `recommendation_runs`와 `recommendation_items`는 0건이다. 실행 경로도 `profile_or_survey`, `followup`, `pharmacist_review`뿐이며, OP-105는 일반 매핑표에서 `pharmacist_review`에 묶여 포함됐다. 그러므로 이 영수증만으로 “프로필 저장 뒤 추천 API까지 왕복했다”는 운영 관찰을 직접 확인할 수 없다.

공개 주소, 지속 운영 데이터베이스, 실제 사용자 세션과 운영 추천 실행은 확인되지 않았다. 결론적으로 구현과 로컬 서비스 통합은 재현됐지만, OP-105 전체 동작의 운영 관측은 증거가 더 필요하다. 다음 운영 영수증에는 같은 세션에서 `user_profiles` 증가와 `recommendation_runs` 증가가 함께 나타나고, 두 행의 가명 프로필 ID가 같다는 조회 결과가 포함돼야 `OPERATED` 주장을 요구사항 문장과 직접 연결할 수 있다.
