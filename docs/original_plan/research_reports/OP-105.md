# OP-105 — 사용자 프로필과 추천 API의 R&D 왕복

## 결론

WellnessBox의 서버 전용 R&D 클라이언트가 사용자 프로필을 저장한 뒤 같은 가명 프로필 ID로 추천을 요청하는 왕복을 실제 두 프로세스로 검증했다. 서비스 QA는 `POST /v1/interim/profiles`와 `POST /v1/interim/recommendations`를 차례로 호출한다. R&D FastAPI는 같은 임시 SQLite 파일에서 저장된 프로필을 다시 읽고, 저장된 임신 상태와 와파린 복용 정보를 최종 안전 규칙에 반영해 추천을 `BLOCKED`로 반환한다. 추천 목록은 비어 있고 실행 ID가 남는다.

요구 단계는 `OPERATED`이지만 이번 증거는 `INTEGRATED`다. 로컬에서 분리된 Node 서비스 호출자와 FastAPI 프로세스가 실제 HTTP·내부 토큰·SQLite를 거쳐 왕복했다. 공개 배포, Vercel 환경, 실제 사용자 트래픽은 검증하지 않았다.

## 무엇을 증명했나

프로필과 추천 호출이 단순한 모의 함수에 머물지 않는다. Python runner가 빈 임시 데이터베이스를 만들고 FastAPI를 별도 프로세스로 시작한다. Node QA는 WellnessBox의 실제 `callWbRndInterim`을 사용한다. 프로필 응답의 가명 ID가 요청 ID와 같은지 확인한 뒤 추천 요청을 보낸다. 추천 결과가 저장 프로필의 고위험 사실 때문에 차단되는지는 프로필 저장과 추천 읽기가 같은 데이터 경계를 사용한다는 관찰 가능한 증거다.

가명 ID는 이메일·전화번호를 전달하지 않는다. 서비스 라우트는 로그인 세션의 애플리케이션 사용자 ID를 HMAC으로 변환하고, 브라우저가 임의의 프로필 ID를 지정하지 못하게 덮어쓴다. 내부 API는 서버 토큰을 요구한다. 고정 데이터셋은 프로필 저장, 추천 응답, 실행 식별자, 약국 범위, 결정 완료, 불변 재시도, 인증 경계, 화면 경로를 포함한 8건이다.

## 남은 운영 경계

이번 결과로 실제 Vercel 서비스가 배포된 R&D 서버에 연결됐다고 말할 수 없다. 운영 완료에는 승인된 환경변수, 배포 식별자, 지속 DB, 실제 서비스 세션을 사용한 왕복, 로그의 비밀값·개인정보 비노출을 추가로 확인해야 한다. 현재 결과는 그 운영 검증 전 단계의 재현 가능한 통합 증거다.
