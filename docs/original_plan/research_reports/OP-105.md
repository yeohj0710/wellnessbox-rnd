# OP-105 사용자 프로필 저장과 추천 API가 R&D 서버까지 왕복하는지 검증한다

## 요구사항은 같은 사용자의 저장 정보가 추천 판단에 다시 쓰이는지 묻는다

OP-105의 판단 기준은 프로필 저장 요청과 추천 요청이 각각 HTTP 200을 받는지가 아니다. WellnessBox에 로그인한 한 사용자의 건강 정보가 R&D 저장소에 들어가고, 뒤이은 추천 요청이 바로 그 저장 행을 찾아 안전 판단에 사용하는지가 핵심이다. 브라우저가 임의의 `profile_id`를 끼워 넣어도 다른 사람의 기록을 읽을 수 없어야 하며, 추천 요청에서 위험 정보를 빈 값으로 보내 저장된 임신 상태나 복용 약물을 지울 수도 없어야 한다.

요구사항 장부 `data/original_plan/requirements_manifest_v1.json`은 `wellnessbox/lib/server/wb-rnd-interim-client.ts`, `wellnessbox/lib/server/wb-rnd-interim-route.ts`, `wellnessbox/scripts/qa/check-rnd-profile-review-roundtrip.cts`를 구현 근거로 등록한다. 통합 결과는 `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`, 운영 주장의 근거는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-105.json`이다. 등록된 파일은 모두 존재한다. 다만 두 결과 파일이 증명하는 단계와 요구사항 장부의 `OPERATED` 표시는 일치하지 않는다.

## 서비스는 로그인 식별자를 가명으로 바꾸고 브라우저 식별자를 버린다

`pseudonymizeInterimSubjectId`는 `WB_RND_INTERIM_PSEUDONYM_SALT`를 키로 HMAC-SHA256을 계산한다. HMAC은 비밀 키를 섞어 만든 지문 값이어서 원래 서비스 사용자 ID를 그대로 R&D에 넘기지 않는다. 반환값은 `usr_`와 32자리 16진수로 제한된다. `pseudonymizeInterimUserId`는 이 함수를 사용자 ID에 적용한다. 비밀값이 없으면 `WB_RND_INTERIM_PSEUDONYM_SALT_missing`으로 중단하므로 평문 ID로 조용히 대체하지 않는다.

`runUserInterimProfileRoute`는 `requireUserSession`이 돌려준 `appUserId`만 가명화한다. 요청 본문의 `profile_id`는 프로필 저장 자료에 복사하지 않는다. 저장 범위는 `minimizeWbRndStoredProfile`로 줄이고, 동의 범위가 배열이 아니면 빈 목록으로 바꾼다. `runUserInterimRecommendationRoute`도 같은 로그인 사용자 ID를 다시 가명화해 `/v1/interim/recommendations`에 넣는다. 따라서 두 요청이 같은 로그인 세션에서 출발하면 같은 가명 ID를 사용하고, 브라우저가 다른 ID를 제출해도 서버가 덮어쓴다.

내부 호출 함수 `callWbRndInterim`은 등록된 메서드와 경로만 허용한다. `/v1/interim/` 밖의 주소, `..`, 이중 슬래시를 거부하고 `x-wb-rnd-token`을 붙인다. 읽기 요청만 한 번 재시도하며, 쓰기 요청은 중복 저장을 피하려고 한 번만 보낸다. 이 제한은 프로필과 추천 연결 자체의 증거는 아니지만, 서비스가 임의 주소나 무제한 재시도로 왕복을 흉내 내지 못하게 하는 경계다.

## R&D 서버는 저장된 위험 사실을 최종 안전 판단에 포함한다

`apps/inference_api/routes/interim.py`의 `upsert_profile`은 프로필을 키 순서가 고정된 JSON으로 만들고 SHA-256(내용에서 계산한 64자리 지문 값)을 저장한다. `profile_id`가 이미 있으면 동의 범위, 프로필 JSON과 지문을 갱신한다. `/recommendations`가 호출하는 `_recommendation`은 먼저 `user_profiles`에서 같은 `profile_id`를 찾으며, 없으면 `profile_not_found`로 끝낸다.

추천 안전성은 세 번 계산된다. `_source_safety_input`으로 저장 프로필과 현재 요청을 따로 평가하고, `_merge_safety_input`으로 두 자료를 합친 뒤 다시 평가한다. `hard_failure`가 하나라도 있으면 `recommend_with_registered_model`을 호출하지 않는다. 결과는 `BLOCKED`, 빈 `recommendations`, 안전 규칙 목록으로 남고 `recommendation_runs`에는 실행 ID와 요청 지문이 기록된다. 모델을 거친 경우에도 모델이 낸 성분을 다시 안전 규칙에 통과시킨다.

집중 시험 `test_current_safety_input_cannot_remove_stored_high_risk_facts`는 이 경계를 직접 겨냥한다. 저장 프로필에는 `pregnant=true`와 와파린을 넣고, 추천 요청에는 `pregnant=false`, 빈 약물 목록과 오메가3를 넣는다. 모델 함수는 호출되면 즉시 시험을 실패시키도록 바꿔 둔다. 기대 결과는 `SAFE-PREG-001`과 `SAFE-DDI-001`이 모두 남고, 추천 목록이 비며, 제외 원료에 오메가3가 포함되는 것이다. `test_dynamic_rule_predicate_combines_risk_facts_across_sources`는 한 위험 조건은 저장 프로필에, 다른 조건은 현재 요청에 두어 두 출처를 합쳐야만 발동하는 규칙도 차단되는지 확인한다.

## 등록 핵심 경로 시험은 실제 두 프로세스와 인증 라우트를 통과했다

`wellnessbox-rnd/scripts/run_profile_review_roundtrip_smoke.py`는 임시 SQLite를 만들고 R&D FastAPI를 별도 프로세스로 시작한다. 서비스 저장소에서는 Node.js가 `wellnessbox/scripts/qa/check-rnd-profile-review-roundtrip.cts`를 실행한다. 시험은 `runUserInterimProfileRoute`와 `runUserInterimRecommendationRoute`를 실제 내부 HTTP 호출 함수에 연결한다. 단순히 TypeScript 함수를 흉내 내거나 Python 라우트를 직접 부르지 않는다.

고정 사례 `profile_saved_through_authenticated_service_route`는 로그인 사용자의 HMAC 가명 ID가 응답에 돌아오는지 본다. `recommendation_uses_saved_profile`과 `recommendation_run_identity_returned`는 저장된 임신·와파린 정보 때문에 오메가3 추천이 `BLOCKED`가 되고 실행 ID가 생기는지 확인한다. `service_routes_require_user_and_pharm_auth`는 인증 실패 요청이 R&D 호출에 도달하지 않는지, 브라우저가 넣은 ID와 약국 번호는 서버 세션 값으로 교체되는지도 함께 본다. 결과 JSON의 10개 `checks`는 모두 참이며 데이터 8건의 SHA-256은 실제 파일과 일치한다.

Git 이력에는 시험이 구체화된 과정이 남아 있다. `e39a11a`의 첫 버전은 고정 `profile_id`로 내부 클라이언트를 바로 불렀으므로 로그인 라우트와 가명 변환을 지나지 않았다. `4aa0e4f`는 안전한 추천이 우연히 성공하는 약한 사례를 임신·와파린·오메가3 차단 사례로 바꿨다. `3d69a5f`는 실제 인증 라우트와 브라우저 ID 무시 검사를 넣었고, `d878c97`은 약사 인증 거부를 추가했다. `07fff30`은 실행마다 달라지는 추천 ID와 검토 ID를 고정 문자열로 치환해 결과 파일을 다시 만들 때 불필요한 차이가 나지 않게 했다.

서비스 쪽 `b153dfd`는 인증 함수를 주입할 수 있게 라우트를 고쳐, 인증 실패가 R&D에 닿지 않는지 시험할 수 있게 했다. `fb00e4e`는 이미 끝난 약사 결정을 일반 502로 바꾸던 오류를 409 `review_already_completed`로 보존했다. 이 변경은 OP-106에도 걸치지만, OP-105 시험이 더 이상 내부 클라이언트 성공만으로 왕복을 주장하지 않게 했다는 점에서 중요하다.

## 통합 결과는 재현 범위를 명시하지만 현재 소스 전체를 고정하지 않는다

등록 결과 파일은 OP-105의 요구 단계를 `OPERATED`, 자체 주장 단계를 `INTEGRATED`로 기록한다. 실제 서비스 라우트, 별도 R&D 프로세스, 내부 토큰, HTTP 직렬화와 임시 데이터베이스를 통과했으므로 로컬 통합 증거로는 내용이 맞다. `public_deployment_proven=false`와 `production_pharmacist_operation_proven=false`도 분명히 남아 있다.

다만 결과 파일의 소스 식별자는 WellnessBox 커밋 `fb00e4ebd972a6630235dda8b09593d27e277ccd` 하나뿐이다. R&D 코드 커밋이나 각 파일 지문은 들어 있지 않다. 현재 서비스의 세 등록 파일 중 클라이언트와 라우트는 그 커밋 뒤에도 크게 바뀌었고, 결과 파일을 현재 소스로 다시 생성한 기록은 없다. 고정 사례 파일과 등록 결과의 SHA-256은 일치하지만, 이 사실만으로 현재 두 저장소 조합의 재실행까지 증명되지는 않는다.

## 운영 영수증은 프로필 저장은 보이지만 추천 왕복은 보이지 않는다

`OP-105.json`은 `wellnessbox-local-research-pc`에서 수행한 2026-07-24 세션을 담고 있다. `user_profiles`와 `profile_snapshots`가 각각 1건 늘었고 실행 경로에 `profile_or_survey`가 있으므로 프로필 저장 활동은 관찰됐다. 그러나 `recommendation_runs`, `recommendation_items`, `agent_runs`, `agent_steps`의 증가는 모두 0이다. OP-105가 포함된 이유는 `operational_action_coverage_v1.json`에서 `pharmacist_review` 한 번을 OP-105와 넓게 묶었기 때문이다.

따라서 영수증의 `covered_requirement_ids`에 OP-105가 있다는 사실은 “같은 사용자의 저장 프로필을 추천 API가 읽었다”는 직접 관찰이 아니다. 영수증에는 프로필 행과 추천 실행 행의 가명 ID를 대조한 값도 없다. 서명 문자열과 내용 지문 필드는 존재하지만, 이번 보고서 검토에서 별도 공개키로 서명을 다시 검산하지 않았다.

## 현재 단계와 확인하지 못한 범위

현재 증거가 직접 지지하는 단계는 `INTEGRATED`다. 로그인 세션에서 만든 가명 ID가 서비스 라우트, 실제 로컬 HTTP, R&D 저장소와 안전 차단 추천까지 이어졌다. 저장 위험을 현재 요청으로 지우지 못하는 집중 시험과 모델 호출 전 차단도 확인됐다. 반면 요구사항 장부가 표시한 `OPERATED`는 등록 운영 영수증으로는 뒷받침되지 않는다.

확인되지 않은 범위는 공개 주소의 배포, 실제 사용자 세션, 지속 운영 데이터베이스, 같은 운영 세션에서의 프로필·추천 행 결속, 현재 서비스 커밋으로 핵심 경로 시험을 다시 실행한 결과다. 운영 단계로 올리려면 한 세션에서 `user_profiles`와 `recommendation_runs`가 함께 늘고, 두 행의 가명 ID가 같으며, 추천이 저장 위험 사실 때문에 차단 또는 제한됐다는 조회 결과를 요구사항별 영수증에 남겨야 한다.
## 서비스에 연결할 때 확인한 경계
서비스 통합은 R&D 코드가 존재한다는 사실만으로 끝나지 않는다. 두 저장소의 계약, 인증, 실제 요청·응답, 상품·주문 경계와 상태 환류를 같은 실행에서 확인해야 하며, 승인 전 데이터 변경은 허용하지 않는다.

`OP-105`는 “사용자 프로필 저장과 추천 API가 R&D 서버까지 왕복하는지 검증한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox/lib/server/wb-rnd-interim-client.ts`, `wellnessbox/lib/server/wb-rnd-interim-route.ts`, `wellnessbox/scripts/qa/check-rnd-profile-review-roundtrip.cts`
- 테스트·실행: `wellnessbox-rnd/scripts/run_profile_review_roundtrip_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`, `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-105.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-105.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
