# OP-020 지원하지 않는 입력을 버리지 않고 오류 또는 missing_information으로 반환한다.

## 모르는 값과 아직 없는 값은 같은 문제가 아니다

원본 계획 16쪽은 여러 출처의 사용자 정보를 정규화해 엔진이 직접 근거를 조회하도록 요구한다. 이때 요청에 `unsupported_profile_field`가 들어왔는데 schema가 그 값을 버리면 사용자는 정보가 반영됐다고 생각하고 엔진은 값이 없는 상태로 판단한다. OP-020의 결과는 지원하지 않는 구조나 단위를 명시적 오류로 반환하고, 지원하는 정보가 아직 없을 때는 응답의 `missing_information`으로 다음 입력을 알려 주는 것이다.

둘을 구분해야 복구 방법도 분명해진다. 알 수 없는 필드는 요청 계약을 고쳐 다시 보내야 한다. 혈당 목표에 필요한 검사나 CGM context가 없는 경우에는 지원되는 필드를 추가하면 된다. 구현은 모든 결측을 422로 만들거나, 모든 오류를 missing 정보로 낮추지 않는다. parsing할 수 없는 값은 요청 경계에서 fail closed하고, 정상 요청 안의 정보 부족은 추천 결과에 구조화해 남긴다.

## strict schema가 silent drop을 막는다

`src/wellnessbox_rnd/schemas/recommendation.py`의 요청·하위 health input model은 extra field를 금지한다. `tests/test_unsupported_input_contracts.py`는 top level, `user_profile`, `lifestyle`, `input_availability`, `preferences` 각각에 모르는 필드를 넣는다. Pydantic은 `extra_forbidden`과 정확한 field location을 반환하고, FastAPI `/v1/recommend`도 같은 요청을 422 detail로 돌려준다. 서버가 값을 제거한 뒤 200을 반환하지 않는다.

지원하는 field 안에서도 의미를 모르면 오류다. 구조화 약물 dose에 enum에 없는 `milligrams`를 쓰면 단위 오류가 난다. 검사 단위 `bananas`는 `unsupported laboratory unit`으로 모델과 API 양쪽에서 실패한다. strict 단위 목록은 모든 임상 단위를 이미 지원한다는 뜻이 아니다. 현재 정규화와 안전 계산이 해석할 수 없는 단위를 명확하게 거부한다는 뜻이다.

## 중복 충돌도 입력 손실로 처리하지 않는다

같은 medication이 canonical name과 분류 key로 중복됐는데 dose가 다르면 하나를 선택하지 않고 `conflicting duplicate medications`로 거부한다. Unicode normalization만 다른 이름도 같은 identity로 비교한다. supplement와 내부 ingredient도 이름, dose, 성분 multiplicity를 포함한 signature가 다르면 충돌이다. `vitamin c`와 exact catalog alias `ascorbic acid`를 다른 성분처럼 받아 우회하지 못한다.

완전히 동일한 약물·보충제 중복은 legacy 호환을 위해 읽을 수 있다. 이 경우에도 원본 배열을 임의로 삭제하지 않으며, 요청 model에는 두 항목이 남는다. 반면 의미가 다른 중복은 순서에 따라 앞이나 뒤 값을 고르지 않는다. 이 경계는 “지원하지 않는 입력을 버리지 않는다”를 unknown field뿐 아니라 상충하는 입력에도 적용한다.

## 알려진 결측은 missing_information으로 설명한다

정상 schema를 통과한 요청이라도 목표와 상태에 필요한 정보가 없을 수 있다. intake는 설문 availability, pregnancy·lactation 여부, allergy·condition·medication context, 혈당 관련 CGM·검사 context, 유전자·웨어러블 context 같은 규칙을 평가한다. 빠진 정보는 code, message, required source와 함께 `MissingInformationItem`으로 만든다. 추천 응답의 `missing_information`과 provenance 구성 요소가 같은 code 집합을 가져야 한다.

예를 들어 혈당 목표가 있지만 관련 laboratory observation과 CGM 값이 없으면 `missing_glucose_context`를 반환한다. 검사값이 지원되는 구조로 들어오면 같은 결측 code가 사라진다. 반대로 검사 단위가 알 수 없으면 missing으로 바꾸지 않고 422다. 사용자가 “필드를 채우면 되는지” 또는 “요청 형식을 고쳐야 하는지”를 응답 종류로 구분할 수 있다.

`apps/inference_api/routes/recommend.py`는 `RecommendationRequest`를 FastAPI body model로 사용하고 실제 recommendation service 응답을 반환한다. Pydantic validation error는 FastAPI의 구조화 422 detail이 된다. 정상 요청은 추천이 부족한 context를 `missing_information`에 포함한다. OP-020은 별도 오류 번역 시스템을 만들지 않고 기존 schema·intake·response contract를 연결했다.

## 회귀 테스트가 API 경계까지 확인한다

`tests/test_unsupported_input_contracts.py`는 모르는 필드 다섯 위치, 모호한 dose unit, 지원하지 않는 검사 unit, 약물·보충제·성분 충돌, Unicode·catalog alias 우회, 동일 중복 호환, 대표 요청 무손실 수용을 검사한다. 각 rejection은 가능한 경우 Pydantic model과 실제 `/v1/recommend` API를 모두 호출한다. 대표 fixture는 model dump가 원본 payload와 같은지와 API가 request ID를 보존하는지도 확인한다.

missing 정보 경계는 diet·lab 계약과 recommendation baseline 테스트가 보완한다. 관련 laboratory observation이 있으면 `missing_glucose_context`가 없어지고, observation을 빼면 다시 생긴다. 응답 schema는 `missing_information` code와 provenance의 additional input condition이 정확히 일치하는지도 검사한다. 따라서 unknown field를 조용히 제거하는 실패와 정상 결측을 설명하지 않는 실패를 서로 다른 테스트가 잡는다.

## INTEGRATED 주장의 정확한 범위

OP-020의 strict 입력 강화는 `91dc57d` 커밋에서 실제 FastAPI 경계와 회귀 테스트로 도입됐고 이후 건강 입력 계약 강화가 같은 원칙을 확장했다. manifest는 R&D schema와 recommend route를 구현 증거로, `tests/test_unsupported_input_contracts.py`를 테스트·통합 증거로 등록한다. 외부 호출자가 사용하는 실제 HTTP route에서 오류 body와 422를 확인하므로 required·claimed stage `INTEGRATED`를 충족한다.

이 증거는 production 트래픽이나 장기 운영 telemetry를 뜻하지 않는다. 모든 가능한 건강정보 field를 지원한다는 주장도 아니다. 현재 계약 밖 입력은 명시적으로 실패하며, 새 field를 지원하려면 schema·정규화·응답·테스트를 함께 확장해야 한다. 이번 backfill은 코드, 서비스 보호 변경, production, 원천·frozen·학습 데이터, 모델, simulation을 변경하지 않았다. 공식 frozen 256건의 일곱 지표와 replay·slice delta는 0이며, 운영 단계에는 실제 client 오류 처리와 missing 정보 보완 흐름의 receipt가 추가로 필요하다.
## 입력값을 먼저 고정한 이유
이 그룹에서 입력을 세분화한 이유는 값 하나를 편의상 문자열로 받으면 안전 판단과 효과 해석이 서로 다른 의미를 사용할 수 있기 때문이다. 단위, 누락, 지원하지 않는 입력, 동의 범위를 먼저 고정해야 뒤의 계산과 차단 결과를 설명할 수 있다.

`OP-020`는 “지원하지 않는 입력을 버리지 않고 오류 또는 missing_information으로 반환한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/apps/inference_api/routes/recommend.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_unsupported_input_contracts.py`
- 통합 증거: `wellnessbox-rnd/apps/inference_api/routes/recommend.py`, `wellnessbox-rnd/tests/test_unsupported_input_contracts.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
