# OP-114 R&D와 서비스 OpenAPI·TypeScript 계약 차이를 CI에서 차단한다.

## 결론

OP-114는 요구 단계 `INTEGRATED`에 도달했다. R&D FastAPI 애플리케이션이 실제로 생성하는 OpenAPI에서 `/v1/interim/*` 경로와 그 경로가 참조하는 schema 폐쇄 집합을 결정적으로 추출한다. 같은 snapshot을 WellnessBox 저장소에 고정하고, 서비스의 TypeScript operation registry와 실제 사용 경로를 비교한다. R&D CI는 OpenAPI를 다시 생성해 snapshot의 최신 상태를 확인하고 두 저장소 파일의 바이트 동일성을 검사한다. 서비스 CI는 TypeScript registry의 모든 method/path가 snapshot에 존재하고 실제 서비스 소스에서 발견한 모든 R&D 경로가 registry에 등록됐는지 검사한다.

이번 결과는 저장소와 CI 수준의 계약 차단이다. production에 배포된 두 애플리케이션의 버전이 동일한 snapshot을 사용하는지, 점진 배포 중 구버전과 신버전이 호환되는지, 외부 gateway가 schema를 바꾸지 않는지는 검증하지 않았다. 따라서 운영 단계가 아니라 `INTEGRATED`로 판정한다.

## 계약 원본 선택

계약의 원본은 사람이 별도로 작성한 문서가 아니라 `apps.inference_api.main.app.openapi()` 결과다. FastAPI route, Pydantic request model, response model이 바뀌면 OpenAPI 결과가 바뀐다. 생성기는 전체 API 중 서비스 통합 경계인 `/v1/interim/` 경로만 선택한다. 선택된 operation에서 `$ref`로 참조하는 component schema를 찾고, 각 schema가 다시 참조하는 schema를 재귀적으로 포함한다. 참조 폐쇄 집합을 사용하므로 request나 response가 같은 schema 이름을 유지한 채 내부 필드를 바꾸는 경우도 snapshot 차이로 검출된다.

생성 결과는 key 정렬, UTF-8, LF, 마지막 newline을 고정한다. timestamp, 현재 디렉터리, 실행 ID 같은 비결정적 값은 포함하지 않는다. 현재 snapshot에는 OpenAPI 경로 31개와 component schema 63개가 들어 있다. generator의 `--check` 모드는 파일을 수정하지 않고 현재 FastAPI 결과와 byte-equivalent한지 판정한다.

## TypeScript operation registry

WellnessBox는 `lib/server/wb-rnd-interim-contract.ts`에 실제 사용하는 19개 method/path 쌍을 선언한다. status와 KPI 조회, 프로필 저장, 추천, 상담, agent run과 tool, device connector, 실행 조회와 replay, 주문 컨텍스트와 binding 검증, PRO 계획·후속·정정, 관리자 source·runtime·review·decision가 포함된다. 동적 실행 ID와 review ID는 FastAPI의 `{execution_id}`, `{review_id}` 표기로 정규화한다. query parameter는 path identity에서 분리한다.

서비스 QA는 호출부 형태를 regex로 추정하지 않는다. 실제 `callWbRndInterim` 함수의 인자 타입이 registry의 method/path union에서 파생된다. 고정 경로, query가 붙은 경로, 실행 ID와 review ID가 들어간 동적 경로만 해당 operation의 method와 함께 컴파일된다. 변수, wrapper, 작은따옴표를 사용하더라도 최종 client 호출은 같은 타입 경계를 통과해야 한다. 강제 cast로 TypeScript를 우회해도 런타임 registry matcher가 method와 정규화된 path를 다시 검사하고 등록되지 않은 요청은 fetch 전에 거부한다. 반대로 registry의 각 operation은 OpenAPI snapshot에 같은 method와 path가 있어야 한다. 음성 타입 회귀와 런타임 장애 주입은 미등록 경로와 잘못된 method가 모두 차단되는지 확인한다.

## 저장소 사이 차이 차단

R&D 저장소의 canonical 파일은 `data/contracts/wb_rnd_interim_openapi_surface_v1.json`이다. WellnessBox 저장소의 복제본은 `contracts/wb-rnd/interim-openapi-surface-v1.json`이다. OP-113/114 runner는 두 파일을 byte-for-byte 비교한다. schema 내용, required 배열, enum, numeric constraint, response status, request body, operation metadata 중 어느 하나라도 달라지면 `cross_repository_contract_exact`가 false가 되고 canonical smoke가 실패한다.

두 저장소가 각각 자체 snapshot만 검사하면 양쪽이 서로 다른 정상 상태를 가질 수 있다. 그래서 R&D `Original plan evidence` workflow는 고정된 WellnessBox 커밋을 checkout하고 generator check, 서비스 QA, cross-repository byte comparison, canonical evidence diff를 한 실행에서 수행해야 한다. WellnessBox `Encoding Guard`도 서비스 snapshot과 TypeScript 사용 경로를 독립적으로 검사한다. 한 저장소의 CI만 통과하는 것으로 양쪽 계약 일치를 주장하지 않는다.

## 변경 절차와 실패 해석

R&D API를 의도적으로 변경할 때는 FastAPI route와 model을 먼저 수정하고 generator로 R&D snapshot을 갱신한다. workflow는 `apps/inference_api/main.py`와 `apps/inference_api/routes/**` 변경에도 실행되므로 router 등록 변경이 검사를 우회하지 않는다. 이어서 TypeScript 호출과 registry, 런타임 validator를 호환되게 수정한 뒤 서비스 snapshot을 같은 생성 결과로 갱신한다. 두 저장소의 테스트와 고정 커밋을 함께 갱신해야 한다. snapshot만 복사해 CI를 통과시키고 TypeScript registry나 실제 parser를 바꾸지 않으면 서비스 QA가 실패해야 한다.

snapshot 차이는 자동으로 호환성 파괴라고 단정하지 않는다. optional response field 추가처럼 호환 가능한 변화도 의도적 검토를 요구한다. OP-114의 목적은 모든 변화 금지가 아니라 두 저장소가 모르는 상태로 서로 다른 계약을 사용하는 일을 차단하는 것이다. 변경 승인과 호환성 판단은 별도 리뷰에서 수행하고, CI는 검토되지 않은 차이를 멈춘다.

## 재현 가능한 증거

데이터셋 `data/original_plan/op113_op114_resilience_contract_cases_v1.json`의 `openapi_snapshot`과 `typescript_registry` 사례가 OP-114 기대값을 정의한다. canonical evidence는 generator current, cross-repository exact match, registry operation 19개, 실제 사용 path 19개, OpenAPI path 31개, component schema 63개를 기록한다. 서비스 커밋과 client, registry, 두 QA, snapshot의 Git blob도 함께 기록해 어떤 계약을 검증했는지 식별한다.

## 단계 경계와 다음 검증

현재 증거는 실제 FastAPI OpenAPI 생성과 실제 TypeScript 사용 경로를 양쪽 CI 계약으로 연결하므로 `INTEGRATED` 요구를 충족한다. production artifact의 OpenAPI hash, 배포된 서비스 bundle의 registry version, rolling deployment 호환성, gateway 변환은 범위 밖이다. `OPERATED` 승격에는 승인된 배포에서 두 artifact hash를 읽고, 호환 기간 동안 양방향 smoke를 수행하며, 불일치 시 배포가 실제로 중단됐다는 운영 증거가 필요하다.
## 운영 증거와 종료 판단을 나눈 이유
운영 증거는 구현 파일을 나열하는 데서 끝나지 않는다. 보안, 장애 복구, 계약 일치, 배포 health, 브라우저 경로, 운영 증거, 외부 의존성과 최종 감사가 각각 어떤 주장을 지지하는지 단계별로 나눈다.

`OP-114`는 “R&D와 서비스 OpenAPI·TypeScript 계약 차이를 CI에서 차단한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15-26`
- 구현·설계: `wellnessbox-rnd/scripts/build_interim_openapi_contract.py`, `wellnessbox-rnd/data/contracts/wb_rnd_interim_openapi_surface_v1.json`, `wellnessbox/lib/server/wb-rnd-interim-contract.ts`, `wellnessbox/contracts/wb-rnd/interim-openapi-surface-v1.json`
- 테스트·실행: `wellnessbox/scripts/qa/check-rnd-openapi-contract.cts`, `wellnessbox-rnd/scripts/run_resilience_openapi_contract_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op113_op114_resilience_contract_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op113_op114_resilience_contract_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
