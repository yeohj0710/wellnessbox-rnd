# OP-068 같은 입력과 카탈로그 버전에서 같은 최적 조합을 재현한다.

## 재현성의 비교 단위

같은 추천 요청과 같은 상품 카탈로그 내용이면 상위 조합, 순위, 비선택 사유가 다시 실행해도 같아야 한다. 사용자 입력만 같다고 같은 실험은 아니다. 상품 가격, 재고, 옵션, 성분 선언이 바뀌면 최적 조합이 달라지는 것이 정상이다. OP-068은 추천·제약의 입력 지문과 카탈로그 내용 버전을 함께 고정하고, 두 값이 같은 경우에 결과 지문도 같도록 요구한다.

첫 순위 구현은 입력 지문과 카탈로그 버전을 함수 인자로 받았다. 호출자가 실제 자료와 관계없는 64자리 값을 넣어도 형식만 맞으면 결과 증거가 만들어질 수 있었다. 서비스 쪽 초기 카탈로그 버전에는 옵션 종류와 용량이 완전하게 정규화되어 들어가지 않았고, 상품 조합 출력 상한에 도달하면 더 싼 후보를 뒤에서 찾지 못할 가능성도 있었다. 이 상태에서는 “같은 버전”과 “전체 후보에서 같은 최적 조합”이라는 주장을 강하게 할 수 없었다.

## 실패를 닫은 커밋 순서

서비스 커밋 `1e5fe20`은 재현 입력을 완전한 자료로 바꿨다. `canonicalCatalogIdentity()`가 상품 식별자·이름·분류·성분 선언·정규화 함량·제형·가격·재고·옵션 종류·용량을 정렬된 자료로 만들고, `catalogVersion()`이 그 전체에서 SHA-256 지문 값을 계산한다. 약국 상품 식별자가 카탈로그 전체에서 중복되면 즉시 실패한다. 같은 커밋은 모든 적격 조합을 비용·상품 수·식별자 순으로 정렬한 다음 출력 상한을 적용하도록 탐색 순서를 고쳤다.

R&D 커밋 `0476ac5`는 `evaluate_product_combination_ranking_v1()`의 인자를 임의의 지문 문자열에서 실제 `ProductCombinationOptimizationInputV1`과 `CatalogProductIdentityV1` 자료로 바꿨다. 이제 함수가 입력 지문과 카탈로그 버전을 직접 만든다. 서비스와 R&D의 커밋 `a27de7c`와 `dc8e145`는 정규화된 서비스 제외 성분 식별자를 입력 지문에 추가하고, 순위 정책과 지문 속 제약이 일치하는지도 강제했다. 이 보강 전에는 결과 지문이 같아도 실제 필터 정책이 지문 밖에서 달라질 여지가 있었다.

## 현재 구현이 계산하는 세 지문

`wellnessbox-rnd/src/wellnessbox_rnd/optimizer/product_combinations.py`의 `_canonical_sha256()`은 JSON 필드 순서를 자료형이 정한 순서로 직렬화해 SHA-256을 계산한다. 입력 지문에는 추천 성분 이름과 서비스 식별자, 순위, 점수, 근거 식별자, 최대 비용, 최대 상품 수, R&D 제외 키, 서비스 제외 식별자, 안전 규칙이 들어간다. 카탈로그 버전에는 `CatalogProductIdentityV1` 배열 전체가 포함된다.

결과 지문은 `_ranking_result_sha256()`이 만든다. 입력 지문, 카탈로그 버전, `top_k`, `non_selection`을 한 자료로 묶으므로 순위 숫자나 비선택 사유 하나만 바뀌어도 다른 값이 된다. 조합 식별자도 선택 상품의 `product_id`와 `pharmacy_product_id`를 정렬한 뒤 계산한 앞 16자리 지문이다. 실행할 때 임의 식별자를 발급하지 않기 때문에 같은 상품 묶음은 같은 조합 식별자를 갖는다.

서비스의 `wellnessbox/lib/server/wb-rnd-product-candidates.ts`는 카탈로그 행을 `id`로 정렬한다. 각 상품 안에서도 분류, 성분 선언, 성분 함량, 약국 상품을 정렬한 뒤 버전을 만든다. 추천은 순위와 서비스 성분 식별자로 정렬하고 근거 식별자도 정렬한다. `wellnessbox/contracts/wb-rnd/product-candidate-match-v1.json`의 `catalog_version_contract_version`은 이 규칙을 `product_catalog_content_sha256_v1`로 명명한다. 이 서비스 정규화가 있기 때문에 원본 카탈로그 행 순서를 뒤집어도 같은 버전이 나온다.

R&D의 `_canonical_sha256()` 자체가 임의 배열을 자동 정렬하는 것은 아니다. 서비스 정규화 경계를 거치지 않은 호출자가 카탈로그 배열 순서를 바꿔 직접 R&D 함수에 넣으면 같은 버전을 보장한다고 확대해서는 안 된다. 확인된 재현성 범위는 서비스가 기준 형식으로 정렬한 카탈로그와 R&D가 같은 기준 자료형으로 검증한 경우다.

## 반복 실행과 변조 시험

`wellnessbox-rnd/tests/test_product_combinations.py`의 `test_combination_ranking_recomputes_top_k_reasons_and_result_identity`는 같은 조합·정책·입력·카탈로그로 두 번 계산한 객체와 `result_sha256`이 같은지 본다. `test_combination_ranking_rejects_forged_outputs`는 추천 점수, 카탈로그 상품명, 순위, 비선택 사유, 결과 지문을 각각 바꾼 자료가 거부되는지 확인한다. `test_combination_ranking_rejects_policy_outside_hashed_input`은 지문 속 예산과 실제 정책 예산이 다른 경우를 별도로 차단한다.

서비스 시험 `wellnessbox/scripts/qa/check-rnd-product-candidates.cts`는 같은 요청을 두 번 실행하고 카탈로그 행 배열을 뒤집어 다시 실행한다. 세 실행의 상위 목록·비선택 사유·재생 정보가 같아야 한다. 반대로 첫 상품의 `optionType`과 `capacity`를 바꾸면 카탈로그 버전이 달라져야 하며, 중복 약국 상품 식별자는 HTTP 502로 끝나야 한다. 탐색이 4,096 상태에서 잘리면 불완전한 Top-k를 재현 결과처럼 내지 않고 빈 목록과 `SEARCH_TRUNCATED`를 반환한다.

`wellnessbox-rnd/scripts/run_product_combination_top_k_reproducibility_smoke.py`는 위 서비스 보고의 조합 네 건, 최적화 입력, 카탈로그 전체를 R&D 자료형으로 읽는다. R&D가 다시 계산한 상위 목록, 비선택 사유, 재생 정보가 서비스 값과 완전히 같아야 기준 파일을 쓴다. `wellnessbox-rnd/data/original_plan/evidence/op067_op068_product_combination_top_k_smoke_v1.json`의 고정 값은 입력 지문 `709f6bd9adb7b584624e3f672e4f6d3cc39de6953bdcc841299a2f0afd3bc768`, 카탈로그 버전 `catalog_1a7aefae72413f07ca27d119ebd04cccdcf2f5e800ef5fd0b210f486da6794a6`, 결과 지문 `2413b3afd3ab40f4cba41f03f1914895a3103bf0842693f244155b2bd81baf1d`이다.

## 증거 수준과 재현하지 않은 환경

현재 증거 단계는 `INTEGRATED`다. 서비스 함수가 행 순서가 다른 카탈로그를 같은 기준 자료로 정리했고, R&D 검증기가 실제 입력과 카탈로그에서 세 지문과 순위 결과를 독립적으로 다시 만들었다. 이는 매니페스트의 요구 단계와 일치한다.

운영 카탈로그의 실시간 재현성은 확인되지 않았다. 등록 증거는 `actual_prisma_query_executed=false`, `actual_ready_rnd_http_path_proven=false`, `production_catalog_freshness_proven=false`, `production_deployment_proven=false`를 남긴다. 재고나 가격이 실행 사이에 바뀌면 카탈로그 버전도 달라지므로 결과가 달라도 오류가 아니다. 공개 서비스의 같은 버전 자료가 여러 프로세스와 배포 인스턴스에서 같은 결과를 내는지는 별도 운영 증거가 필요하다.
