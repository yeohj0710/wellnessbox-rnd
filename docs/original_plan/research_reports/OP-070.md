# OP-070 추천 조합을 장바구니 후보로 변환하되 승인 전 주문을 생성하지 않는다.

manifest에 연결된 `wellnessbox-rnd/data/original_plan/evidence/op069_op070_product_combination_stock_cart_smoke_v1.json`은 대체 조합을 장바구니에 넣을 수 있는 세 항목으로 바꾸면서 저장과 주문은 하지 않은 결과를 기록한다.

## 후보와 주문 사이에 경계가 필요한 이유

추천 엔진의 결과는 사용자가 검토할 선택지이지 구매 의사가 아니다. 알고리즘이 1위 조합을 골랐다는 이유로 장바구니를 바꾸거나 주문·결제를 만들면 사용자의 승인 없이 금전적 행위가 일어난다. OP-070은 상품 조합을 기존 서비스의 장바구니 항목 형식으로 변환하되, 승인 전에는 화면에 제안할 자료만 반환하도록 경계를 고정한다.

`src/wellnessbox_rnd/optimizer/product_combinations.py`의 `ProductCombinationCartCandidateV1`은 각 항목을 `productId`, `productName`, `optionType`, 수량 1로 표현한다. 선택된 현재 1위 조합의 상품 순서를 그대로 사용하므로 다른 조합의 상품이 섞이면 상위 모델 검증에서 거부된다. 옵션 종류가 없거나 안전 조건·최적화 입력이 달라진 경우에는 준비 완료 후보를 만들 수 없고, 정해진 미사용 사유를 반환해야 한다.

자료형 자체도 승인 전 상태를 바꿀 수 없게 제한한다. `approval_required`는 항상 true, `approval_status`는 `NOT_APPROVED`, `cart_storage_written`과 `order_created`는 false, `order_id`는 null만 허용한다. 즉, 호출자가 같은 구조에 “승인 완료”나 주문 번호를 끼워 넣어 R&D 증거처럼 보이게 할 수 없다. 실제 승인과 주문은 이 계약 바깥의 별도 서비스 행위여야 한다.

## 변환 결과와 부작용 검증

기준 사례는 재고 변경 후 새 1위 조합에서 장바구니 후보 세 항목을 만들었다. 결과는 `status=READY`이지만 `approval_status=NOT_APPROVED`다. `cart_storage_written=false`, `order_created=false`, `order_id=null`도 함께 남았다. 준비 완료는 사용자에게 제안할 자료가 완성됐다는 뜻이며, 장바구니나 주문이 이미 만들어졌다는 뜻이 아니다.

`wellnessbox-rnd/tests/test_product_combinations.py`는 정상 후보의 다섯 보호 필드를 하나씩 뒤집는다. 승인 필요를 false로 만들거나, 승인 상태를 `APPROVED`로 바꾸거나, 장바구니 저장·주문 생성을 true로 두거나, 주문 번호를 넣으면 모두 자료형 검증이 실패한다. 이 시험은 주문 데이터베이스를 감시하는 시험이 아니라 R&D와 서비스 사이의 후보 계약이 승인 전 부작용을 표현하지 못하게 하는 시험이다.

생성 스크립트 `wellnessbox-rnd/scripts/run_product_combination_stock_cart_smoke.py`는 서비스 보고를 받은 뒤 현재 조합의 장바구니 항목을 R&D에서 다시 만든다. 서비스 보고는 경로와 어댑터 소스에서 Prisma 주문·주문항목·결제 변경, 주문 생성·승인·결제 함수, `writeClientCartItems`, 브라우저 저장소 변경 호출을 찾는 검사를 수행했다. 기준 증거에는 이 금지 기호 검사가 통과했고, 기존 장바구니 항목 계약도 유지됐다고 적혀 있다.

## 실패 자료를 다룬 범위

잘못된 승인 상태와 부작용 표시는 회귀 시험에서 의도적으로 넣어 모두 거부했다. 다만 구현 과정에서 실제로 주문이 잘못 생성됐다가 수정된 기록은 등록 자료에서 확인되지 않았다. 따라서 이 보고서는 과거 사고가 있었다고 쓰지 않고, 현재 계약과 소스 검사가 어떤 실패를 막는지만 설명한다. manifest의 서비스 구현 경로는 R&D 저장소 밖이므로 직접 읽지 않았으며, 기준 증거에 기록된 서비스 커밋과 검사 결과를 사용했다.

소스 기호가 없다는 사실은 승인 전 경로와 어댑터에 명백한 쓰기 코드가 없다는 근거다. 동적으로 불러온 코드나 이 범위 밖의 서비스 기능 전체에 부작용이 절대 없다는 증명은 아니다. 그래서 실제 주문 데이터베이스의 행 수를 확인한 것처럼 표현하지 않는다.

## 현재 단계와 사람 승인 이후의 한계

서비스 함수에서 현재 최적 조합을 기존 장바구니 항목 형식으로 바꾸고, R&D 모델이 조합 일치와 보호 필드를 다시 확인했으므로 OP-070은 `INTEGRATED`다. 이 단계는 두 코드 경계가 연결됐다는 의미이며 사용자 승인이나 운영 구매가 있었다는 의미가 아니다.

증거는 `actual_prisma_query_executed=false`, `user_approval_obtained=false`, `production_operation_proven=false`를 명시한다. 실제 사용자가 후보를 보고 승인한 뒤 장바구니가 한 번만 갱신되는지, 승인 취소가 주문을 막는지, 공개 환경에서 결제 경계가 유지되는지는 확인되지 않았다. 이 항목들은 사람 승인과 격리된 운영 시험이 있어야 추가로 주장할 수 있다.
