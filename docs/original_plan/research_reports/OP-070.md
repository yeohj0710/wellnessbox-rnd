# OP-070 추천 조합을 장바구니 후보로 변환하되 승인 전 주문을 생성하지 않는다.

## 추천 결과와 구매 행위를 분리해야 한다

최적화 1위는 사용자가 검토할 제안이지 구매 승인이나 주문 지시가 아니다. OP-070은 선택된 상품을 기존 장바구니 항목 형식으로 변환할 수 있게 하되, 사용자 승인 전에는 장바구니 저장·주문·결제 상태를 바꾸지 못하게 한다. 따라서 “후보가 준비됨”과 “주문이 생성됨”은 서로 다른 상태여야 한다.

기존 서비스에는 `wellnessbox/lib/client/cart-storage.ts`의 `writeClientCartItems()`와 `mergeClientCartItems()`가 이미 있었다. 이 함수들은 실제 브라우저 저장소를 바꿀 수 있으므로 R&D 추천 경로에서 호출하면 안 된다. 상품 조합 기능을 처음 붙인 시점에도 후보 항목을 이 기존 `ClientCartItem` 형식에 맞추는 것과 실제 저장 함수를 실행하는 것을 구분할 필요가 있었다.

커밋 `7d4da4b`는 R&D에 `ProductCombinationCartItemV1`, `ProductCombinationCartCandidateV1`, `ProductCombinationStockCartEvidenceV1`을 추가했다. 초기 자료형부터 승인 필요는 true, 승인 상태는 `NOT_APPROVED`, 저장과 주문 생성은 false, 주문 번호는 null로만 허용했다. 커밋 `a2ae7a2`는 증거 표현도 더 엄격하게 고쳤다. 실제 데이터베이스 행을 확인하지 않았는데 “주문이 생성되지 않았다”고 넓게 쓰는 대신, 경로·어댑터 소스에 주문·결제·브라우저 저장소 변경 기호가 없다는 검사 결과로 경계를 명시했다.

## 후보를 만드는 코드와 고정 필드

`wellnessbox/lib/server/wb-rnd-product-candidates.ts`의 `buildCartCandidate()`는 현재 Top-k의 1위 조합만 입력으로 받는다. 탐색이 잘렸거나, 재고 대체 중 안전 조건 또는 최적화 입력이 바뀌었거나, 선택 상품의 `option_type`이 비어 있으면 `UNAVAILABLE`을 반환한다. 사용할 수 있을 때는 각 상품을 `productId`, `productName`, `optionType`, `quantity: 1`로 바꾼다.

반환 자료에는 구매를 막는 다섯 필드가 항상 붙는다. `approval_required=true`, `approval_status=NOT_APPROVED`, `cart_storage_written=false`, `order_created=false`, `order_id=null`이다. 서비스 커밋 `62b4824`는 과거와 현재의 안전 조건이 다를 때 후보를 `UNAVAILABLE`로 만들었고, `4d904f4`는 추천 점수 등 다른 입력이 바뀐 경우를 `OPTIMIZATION_INPUT_CHANGED`로 따로 설명하게 했다.

R&D 쪽 `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/product_combinations.py`는 위 다섯 값을 `Literal`로 제한한다. `ProductCombinationStockCartEvidenceV1`은 후보 항목을 현재 1위 조합의 `selected_products`에서 다시 만든 뒤 전달된 항목과 비교한다. 다른 조합의 상품을 섞거나 상품명·옵션·수량을 바꾸면 증거 자료가 성립하지 않는다. 수량도 후보 단계에서는 1만 허용한다.

서비스 경로 `wellnessbox/lib/server/wb-rnd-interim-route.ts`는 R&D 응답을 검증하고 상품 후보를 붙여 반환할 뿐, `writeClientCartItems()`를 부르지 않는다. `wellnessbox/app/api/tips/route.ts` 역시 POST를 그 경로 함수로 넘기는 얇은 진입점이다. 실제 장바구니 저장 함수는 클라이언트 모듈에 존재하지만 추천 경로와 상품 어댑터에는 연결되지 않았다. 따라서 현재 구현은 장바구니와 호환되는 자료를 만드는 기능이지 장바구니를 쓰는 기능이 아니다.

## 시험이 다루는 변조와 부작용 범위

`wellnessbox-rnd/tests/test_product_combinations.py`의 `test_cart_candidate_rejects_preapproval_side_effects`는 보호 필드를 하나씩 바꾼다. `approval_required=false`, `approval_status=APPROVED`, `cart_storage_written=true`, `order_created=true`, `order_id=1`의 다섯 경우가 모두 자료형 검증에서 실패해야 한다. 이 시험은 호출자가 승인 완료나 주문 생성 흔적을 R&D 증거 안에 끼워 넣지 못하게 하는 계약 시험이다.

`wellnessbox/scripts/qa/check-rnd-product-candidates.cts`는 서비스가 만든 후보를 `parseClientCartItems()`로 읽어 기존 장바구니 항목 계약과 같은지 확인한다. 이어 추천 경로와 상품 어댑터의 소스 문자열을 직접 읽는다. Prisma `Order`, `OrderItem`, `Payment`, `PaymentAttempt`의 생성·수정·삭제 호출, `createOrder`·`authorizePayment`·`capturePayment`, `writeClientCartItems`, `localStorage.setItem/removeItem/clear`가 하나라도 있으면 시험이 실패한다. 이 검사는 승인 전 경로에 명시적인 부작용 코드가 들어오는 회귀를 막는다.

기준 실행은 재고 대체 뒤 세 상품을 후보로 만들었다. `productId`는 20000, 20014, 20024이고 각 `optionType`은 `30 days`, 수량은 1이다. `status=READY`이지만 승인 상태는 여전히 `NOT_APPROVED`다. `wellnessbox-rnd/scripts/run_product_combination_stock_cart_smoke.py`는 서비스가 보고한 현재 1위를 R&D에서 재계산하고 후보 세 항목이 그 조합과 정확히 같은지 확인한다.

매니페스트에 등록된 `wellnessbox-rnd/data/original_plan/evidence/op069_op070_product_combination_stock_cart_smoke_v1.json`은 `cart_item_count=3`, `approval_required=true`, `cart_storage_written=false`, `order_created=false`를 기록한다. 같은 파일은 `preapproval_side_effect_source_scan_passed=true`와 금지 기호 네 범주도 보존한다. 이 근거는 후보 계약과 검사 대상 소스 안의 부작용 부재를 보여 주지만, 서비스 전체 데이터베이스를 감시한 결과로 해석하면 안 된다.

## 통합 단계에서 말할 수 있는 범위

현재 증거 단계는 `INTEGRATED`다. 서비스 함수가 최적 조합을 기존 장바구니 항목 형식으로 변환했고, R&D 모델이 현재 1위와 보호 필드를 다시 확인했다. `wellnessbox/lib/client/cart-storage.ts`도 직접 열어 후보의 네 항목 필드가 `ClientCartItem`과 호환됨을 대조했다.

사람 승인은 없었고 운영 주문도 실행하지 않았다. 증거 파일은 `user_approval_obtained=false`, `actual_prisma_query_executed=false`, `production_deployment_proven=false`, `production_operation_proven=false`를 명시한다. 소스 기호 검사는 동적으로 불러온 코드나 검사 대상 밖의 모든 기능에 부작용이 없다는 증명이 아니다. 사용자가 후보를 승인한 뒤 장바구니가 정확히 한 번 갱신되는지, 승인을 취소하면 주문이 생기지 않는지, 운영 데이터베이스에 주문·결제 행이 추가되지 않았는지는 확인되지 않았다.
