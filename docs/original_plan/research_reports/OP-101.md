# OP-101 R&D FastAPI 배포 계약 확정 결과

## 결론

R&D FastAPI를 어디에 올리고, 어떤 데이터베이스를 쓰고, 내부 요청을 어떻게 인증할지 하나의 실행 계약으로 묶었다. staging 또는 production은 별도 플래그가 없어도 계약을 의무적으로 검사한다. 활성화된 interim API, 배포 대상과 배포 ID, 실행 커밋과 같은 image build SHA, 절대 SQLite 경로, provider 영속 볼륨, 내부 인증 방식, provider secret reference, 32바이트 이상의 비밀 토큰, 단일 worker가 모두 준비돼야 프로세스가 시작된다. 하나라도 빠지면 `deployment_contract_invalid`로 시작을 중단한다.

이번 루프에서는 provider에 서비스를 올리지 않았다. 공개 URL, provider 배포 ID, 운영 볼륨, 운영 트래픽이 없으므로 OP-101의 요구 단계 `OPERATED`에는 도달하지 않았다. 두 개의 독립 로컬 프로세스와 재시작 뒤 DB 보존까지 확인했으므로 주장 단계는 `INTEGRATED`, 완료 판정은 `PARTIAL`이다.

## 기존 문서만으로는 배포 조건을 강제할 수 없었다

기존 `Dockerfile`, `scripts/start_inference_api.py`, `docs/deployment/staging_api.md`에는 FastAPI 앱 경로와 시작 명령이 있었다. `WB_RND_HOST`, `WB_RND_PORT`, `PORT`, `WEB_CONCURRENCY` 같은 실행 변수도 정리돼 있었다. 로컬 컨테이너를 띄우고 `/health`와 `/v1/recommend`를 확인하는 smoke도 있었다.

하지만 세 가지가 서로 떨어져 있었다. SQLite 파일이 실제 영속 볼륨에 있는지 실행 코드가 확인하지 않았다. `WB_RND_INTERIM_INTERNAL_TOKEN`이 비어 있을 때 일부 환경에서 요청을 막는 로직은 있었지만, 토큰 길이와 인증 방식은 배포 계약으로 고정되지 않았다. 마지막으로 실행 중인 코드 커밋과 provider 배포 ID를 함께 기록하는 필수 조건이 없었다. 문서를 잘 읽으면 올바르게 배포할 수는 있어도, 잘못된 설정으로 시작하는 프로세스를 코드가 막지는 못했다.

OP-101에서 말하는 “확정”은 변수 이름을 나열하는 데서 끝나지 않는다. 배포 프로세스가 같은 규칙을 읽고, 조건이 틀리면 실제로 시작하지 않아야 한다. 그래서 `validate_deployment_contract`를 시작 경계에 연결했다.

## 배포 계약을 이루는 아홉 가지 조건

첫 번째는 실행 환경이다. `WB_RND_APP_ENV`는 `staging` 또는 `production`이어야 한다. `local`과 `test`는 배포 계약을 통과하지 못한다. 로컬 개발 프로세스를 provider 배포처럼 기록하는 일을 막는다.

두 번째는 interim API 활성화다. `WB_RND_INTERIM_ENABLED`가 참이어야 한다. health만 뜨고 상태기계·기기·상담 API가 인증 단계에서 비활성 상태인 배포를 완성된 R&D API로 보지 않는다.

세 번째와 네 번째는 배포 대상과 배포 ID다. `WB_RND_DEPLOYMENT_TARGET`은 provider 서비스 이름을, `WB_RND_DEPLOYMENT_ID`는 특정 배포를 식별하는 값을 받는다. 같은 서비스가 여러 번 배포돼도 어떤 실행을 조사해야 하는지 구분할 수 있다.

다섯 번째는 `WB_RND_CODE_COMMIT`이다. 짧은 SHA나 임의 문자열을 허용하지 않고 소문자 16진수 40자리만 받는다. canonical evidence의 소스 커밋과 실행 프로세스의 커밋을 같은 형식으로 비교할 수 있다.

여섯 번째와 일곱 번째는 DB 위치와 내구성이다. `WB_RND_INTERIM_DATABASE`는 절대 경로여야 한다. 상대 경로는 작업 디렉터리가 바뀌면 다른 DB를 만들 수 있기 때문이다. 경로만 절대라고 영속성이 생기지는 않는다. 그래서 `WB_RND_DATABASE_DURABILITY=provider_persistent_volume`도 함께 요구한다. 이 값은 provider 볼륨을 자동 생성하지 않는다. 배포 설정자가 실제 마운트 계약을 명시하게 하는 선언이며, 운영 검증에서는 provider 설정과 파일 보존을 다시 증명해야 한다.

여덟 번째는 내부 인증이다. 현재 지원 방식은 `shared_header_hmac_sha256_v1` 하나다. 요청자는 `x-wb-rnd-token` 헤더에 provider secret store에서 받은 토큰을 넣는다. 애플리케이션은 `hmac.compare_digest`로 비교한다. 토큰은 UTF-8 기준 32바이트 이상이고 문자 다양성 조건을 통과해야 하며 provider secret reference도 필수다. health 응답에는 원문, 해시, secret reference, DB 경로, 배포 ID, 대상 이름을 포함하지 않는다.

아홉 번째는 worker 수다. 현재 영속 저장소가 SQLite이므로 `WB_RND_WORKERS=1`을 요구한다. 여러 worker가 필요해지는 시점에는 단순히 숫자를 늘리지 않고, 동시 쓰기와 migration을 지원하는 관리형 DB 계약으로 바꿔야 한다.

## staging과 production은 계약 검증을 건너뛸 수 없다

FastAPI lifespan은 `staging`과 `production`에서 별도 플래그 없이 배포 계약을 검증한다. `local`과 `test`는 기존 개발 실행을 보존하고, 필요할 때만 `WB_RND_DEPLOYMENT_CONTRACT_ENFORCED=1`로 같은 검증을 켤 수 있다. staging 또는 production은 enforcement 값을 `0`으로 두거나 누락해도 계약을 건너뛰지 못한다.

검증이 켜진 프로세스는 오류 목록을 정렬해 한 번에 반환한다. 예를 들어 상대 DB 경로와 짧은 토큰을 함께 주면 두 조건을 모두 보고한다. 토큰 원문은 오류와 계약 결과 어디에도 포함하지 않는다. 배포 계약이 통과하면 `READY_FOR_PROVIDER_DEPLOYMENT` 상태와 비밀이 제거된 계약 요약을 `app.state`에 보관한다. `/health`가 그 요약을 반환한다.

여기서 `READY_FOR_PROVIDER_DEPLOYMENT`는 이름 그대로 준비 상태다. `DEPLOYED`나 `OPERATING`이라고 부르지 않았다. 코드가 provider API를 조회하거나 실제 트래픽을 관측하지 않았기 때문이다.

## 두 프로세스와 한 DB로 확인한 내용

canonical smoke는 사용 가능한 localhost 포트를 고르고 첫 FastAPI 프로세스를 별도로 시작한다. 배포 계약 검증을 켜고 임시 디렉터리 아래 절대 DB 경로를 provider 영속 볼륨 역할로 지정한다. health가 준비될 때까지 기다린 뒤 계약 상태와 API 목록을 읽는다.

첫 프로세스에서는 토큰 없는 `/v1/interim/status`가 401인지 확인한다. 올바른 토큰으로 사용자 프로필을 만들고 production 분류의 기기 이벤트를 한 건 저장한다. 공개 deterministic 추천 API도 호출해 기존 `deterministic_baseline_v1` 결과가 유지되는지 확인한다.

그다음 첫 프로세스를 정상 종료하고 같은 DB 경로로 두 번째 프로세스를 시작한다. 배포 ID만 process-b로 바꾼다. 같은 공급자 이벤트를 새 세션 ID로 다시 보내면 `deduplicated=true`와 최초 세션 `deployment-device-1`을 돌려준다. 상태 API에서 connector 행 수는 한 건이다. 메모리 상태를 우연히 재사용한 결과가 아니라 디스크 DB가 프로세스 재시작 사이에 보존됐다는 뜻이다.

## 운영 단계에 필요한 추가 증거

provider 배포에서는 실제 서비스 리소스와 비공개 네트워크 경계를 확인해야 한다. provider가 발급한 배포 ID와 실행 커밋, 영속 볼륨 마운트 경로, 재시작 전후 DB 파일 identity, backup·restore 결과를 남겨야 한다. secret store에서 토큰을 주입하고 로그와 health에 원문이 없는지 점검해야 한다. 인증 실패율, DB 쓰기 오류, migration 실패, 디스크 용량을 관측해야 한다.

공개 배포나 운영 설정 변경은 사용자 승인이 필요한 작업이다. 이번 루프는 그 승인을 우회하지 않았다. provider 계정이나 인증정보를 찾거나 수정하지 않았고, 로컬 프로세스만 사용했다.

## 현재 판정

배포 대상, 영속 DB 선언, 내부 인증, 실행 identity를 하나의 fail-closed 계약으로 확정했다. 독립 프로세스 재시작 뒤 저장과 인증도 재현했다. 그러나 provider에서 실제로 운영하지 않았으므로 OP-101은 `INTEGRATED / PARTIAL`이다.
