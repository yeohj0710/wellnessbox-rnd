# OP-060 data_class 교체만으로 실제 결과 데이터를 같은 API에서 처리한다.

이 요구의 직접 근거는 `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`와 `wellnessbox-rnd/apps/inference_api/routes/interim.py`다. 등록된 통합 결과 `wellnessbox-rnd/data/original_plan/evidence/op059_op060_pro_action_real_outcome_smoke_v1.json`도 함께 열었다. 결론은 `INTEGRATED`다. 같은 요청 창구와 계산 절차가 시험용 합성 결과와 실제 관찰 결과 표시를 모두 받지만, 기준 시험에는 실제 운영 데이터가 들어가지 않았다.

## 데이터 종류 때문에 처리 절차가 갈라지면 생기는 문제

복용 전후 효과 계산을 합성 자료 전용과 실제 자료 전용으로 따로 만들면 두 경로의 점수 계산, 안전 우선순위, 수정 처리 방식이 쉽게 달라진다. 그러면 연구 단계에서 통과한 규칙이 실제 자료를 넣는 순간 다른 결과를 낼 수 있다. OP-060은 입력 내용은 그대로 두고 `data_class`라는 데이터 종류 표지만 바꿔 동일한 처리 경로를 쓸 것을 요구한다.

허용 값은 `SYNTHETIC_OUTCOME_PROXY`와 `REAL_WORLD_OUTCOME` 두 개뿐이다. 앞 값은 시험용 대체 결과, 뒤 값은 실제 관찰 결과라는 뜻이다. 기본값은 시험용이다. 이 표지는 점수나 행동을 유리하게 바꾸는 조건이 아니라 자료의 출처 성격을 보존하는 구분자다. 후속 입력은 별도의 데이터 종류를 받지 않고 복용 전 기준 사건에 저장된 값을 물려받는다. 따라서 같은 계획 안에서 기준값과 후속값의 출처 구분이 어긋날 수 없다.

## 같은 요청 창구를 유지한 구현

`enroll_pro_plan_v1`은 두 데이터 종류 모두 같은 설문 점수 계산, 추천 실행, 실행 원장 기록, 기준 사건 저장을 거친다. `record_or_correct_pro_followup_v1`도 같은 표준화와 해석, 다음 행동 결정을 사용한다. R&D API의 `/v1/interim/pro/plans`는 두 값만 받도록 제한하며, 실제 관찰 결과일 때는 기존 추천 결과를 약사 검토용 초안 목록에 추가한다. 이 추가 기록은 계산 경로를 바꾸지 않는다.

서비스 쪽 `wellnessbox/lib/tips/pro-study-rnd-client.ts`는 `dataClass`를 같은 `/api/tips/pro/plans` 요청에 넣고 응답의 기준 사건에서 같은 값을 읽는다. `wellnessbox/components/tips/ProStudySimulation.tsx`에는 시험용 합성 결과와 실제 관찰 결과를 고르는 입력란이 있다. 새 실제자료 전용 URL이나 별도 점수 계산기를 만들지 않은 이유는 두 자료 종류의 차이를 출처 표시로 한정하고 나머지 동작을 비교 가능하게 유지하기 위해서다.

## 교체 시험과 잘못된 입력의 처리

기준 smoke는 내용이 같은 등록·후속 입력을 두 번 만들고 데이터 종류만 바꿨다. 운송용 식별자를 제외한 의미 입력의 SHA-256 지문 값은 두 실행에서 같았다. 두 경우 모두 해석 가능한 악화로 `re_optimize`를 선택했고, 복용 전과 후 사건에는 각각 지정한 데이터 종류가 그대로 남았다. 별도로 실제 관찰 결과 표시 네 사례를 보내 네 가지 행동 분기도 같은 서비스 경계를 통과시켰다.

현재 `tests/test_pro_plan_service.py`는 실제 관찰 결과가 같은 계획 API에서 처리되고, 기준·후속 사건 모두 해당 값을 보존하는지 다룬다. 한 번 등록한 요청을 다른 데이터 종류로 재시도하면 `baseline_conflict`로 거부한다. 허용 목록에 없는 `PHARMACIST_GOLD`를 보내면 HTTP 422가 나온다. 서비스 계약 시험 `check-tips-pro-study-rnd-client.cts`도 성공했다. 이 실패 사례는 잘못된 분류가 조용히 다른 계획으로 섞이지 않도록 만든 현재 방어 동작이다. 과거에 어떤 실패가 이 설계를 촉발했는지는 코드, 시험, 기준 JSON까지 조사했지만 `확인되지 않음`으로 기록한다.

## 통합 판정에서 제외한 범위

정본에는 `localhost_two_process_integration_proven=true`와 `real_world_outcome_contract_proven=true`가 기록돼 있다. 그러나 `production_data_used`, `production_operation_proven`, `causal_effect_proven`은 모두 false다. `REAL_WORLD_OUTCOME`이라는 문자열을 넣었다는 사실만으로 실제 사용자 측정값이나 약사 승인이 생기지는 않는다. 실제 자료의 수집 동의, 출처 확인, 운영 저장과 사람 검토는 이 요구가 입증한 범위 밖이다.

또한 기준 증거가 저장한 소스 결합 지문은 현재 파일들로 계산한 값과 달랐다. 현재 Python 집중 시험 96개와 서비스 계약 시험은 통과했으나, 현재 두 저장소 상태를 함께 띄운 네트워크 smoke는 git 명령 금지 조건 때문에 재실행하지 않았다. 따라서 `INTEGRATED`는 등록된 시점의 통합 증거에 근거하며, 최신 소스의 동일 실행 재현은 남은 확인 사항이다.
