# OP-060 data_class 교체만으로 실제 결과 데이터를 같은 API에서 처리한다.

이 요구사항은 `data_class`만 바꿔도 합성 결과와 실제 관찰 결과가 같은 API와 점수 계산 경로를 사용하도록 요구했다. `data_class`는 계산 방법을 고르는 스위치가 아니라 결과 자료의 출처 성격을 남기는 표지다. `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`를 기준으로 두 자료가 같은 등록 함수, 같은 후속 함수, 같은 점수 계산을 거치는지 추적했다. 등록 smoke는 이 경로를 WellnessBox 서비스까지 연결했으므로 증거 단계는 `INTEGRATED`다. 그러나 `REAL_WORLD_OUTCOME`이라는 문자열은 실제 사용자 자료, 동의, 약사 승인 또는 운영 배포를 대신하지 않는다.

## 원래 경로는 합성 결과로 고정돼 있었다

초기 `enroll_pro_plan_v1`은 기준 사건의 `data_class`를 `SYNTHETIC_OUTCOME_PROXY`로 직접 넣었다. 실제 관찰 자료를 같은 함수에 넣어도 출처를 다르게 보존할 방법이 없었던 셈이다. 커밋 `8448cec`는 `OutcomeDataClass`를 두 값의 리터럴 형식으로 선언하고, 등록 함수 인자와 `/v1/interim/pro/plans` 요청 모델에 `data_class`를 추가했다. 기준 사건이 선택한 값을 저장한 뒤 후속 사건은 새 값을 받지 않고 `baseline.data_class`를 물려받는다. 같은 계획 안에서 복용 전은 실제 자료인데 후속은 합성 자료로 뒤섞이는 통로를 없앤 설계다.

WellnessBox 쪽 최초 연결은 `ede6b38`에서 이뤄졌다. 이 변경은 `wellnessbox/lib/tips/pro-study-rnd-client.ts`의 기존 `/api/tips/pro/plans` 요청에 `dataClass`를 넣고, `wellnessbox/lib/server/wb-rnd-interim-route.ts`가 이를 R&D의 `data_class`로 옮기게 했다. 별도 실제자료 API는 만들지 않았다. 화면 `wellnessbox/components/tips/ProStudySimulation.tsx`도 같은 등록 함수에 두 선택지만 전달한다.

## “같은 처리”는 점수·행동 경로가 같다는 뜻이다

`enroll_pro_plan_v1`은 두 분류 모두 `score_and_standardize_runtime_pro_v1`, `recommend`, 실행 원장 기록, 기준 사건 저장을 차례로 사용한다. `record_or_correct_pro_followup_v1`도 데이터 종류로 분기하지 않는다. 설문 점수를 기준 분포로 표준화하고, 복용 이행과 이상사례를 포함한 해석을 만든 뒤 `decide_pro_plan_action_v1`으로 다음 행동을 계산한다. 후속 입력에서 별도 분류를 받지 않기 때문에 데이터 종류를 바꿔 점수나 행동을 유리하게 만드는 우회도 없다.

두 경로의 모든 부수 효과가 같다는 뜻은 아니다. 현재 `wellnessbox-rnd/apps/inference_api/routes/interim.py`의 `enroll_pro_plan`은 `REAL_WORLD_OUTCOME`일 때만 `AiDraftService.create`로 `actual_recommendation_review` 초안을 만든다. 실제 결과를 약사 검토 후보로 올리는 추가 기록이며 추천·점수 계산기를 바꾸지는 않는다. 따라서 OP-060이 보장하는 동일성은 요청 창구와 효과 계산 절차다. 검토 대기열 생성까지 완전히 같다고 쓰면 현재 코드와 맞지 않는다.

## 기본값과 재시도 충돌은 후속 커밋에서 고쳤다

최초 서비스 변경 `ede6b38`은 `dataClass`가 빠진 기존 요청도 오류로 만들었다. 바로 다음 커밋 `c77e698`은 `body.dataClass ?? "SYNTHETIC_OUTCOME_PROXY"`를 적용해 이전 호출의 합성 기본값을 보존했다. 이 차이는 git diff에서 직접 확인된다. 또 `86823c3`의 기준 사건 동일성 검사 뒤에는 같은 `request_id`로 데이터 종류만 바꿔 재시도해도 새 계획을 만들지 않고 `pro_enrollment_baseline_conflict`로 거부한다. 이미 저장한 사건의 출처 표시를 나중 요청이 덮어쓰지 못한다.

현재 집중 시험 96개 중 `test_same_plan_api_accepts_real_world_outcome_data_class`는 실제 관찰 표시로 등록한 뒤 기준·후속 사건 양쪽에 같은 값이 남고, 해석 가능한 악화가 `re_optimize`로 계산되는지 본다. `test_enrollment_retry_rejects_changed_data_class`는 같은 등록 요청의 분류 변경을 충돌로 처리한다. `test_pro_plan_api_accepts_only_outcome_data_classes`는 허용한 실제 관찰 값은 HTTP 200과 검토 초안 1건을 만들고, `PHARMACIST_GOLD`는 HTTP 422로 거부하는지 확인한다. 서비스 계약 시험 `check-tips-pro-study-rnd-client.cts`는 실제 관찰 값이 `/api/tips/pro/plans` 본문에 들어가고 응답에서 되돌아오는지 확인했으며 이번 검토에서 성공했다.

## 같은 의미 입력을 바꾼 smoke의 결과

`wellnessbox-rnd/data/original_plan/evidence/op059_op060_pro_action_real_outcome_smoke_v1.json`은 운송용 요청 ID와 `data_class`를 제외한 등록·후속 입력을 같게 만든 두 사례를 보관한다. 두 의미 입력의 SHA-256 지문 값은 모두 `b9d15422fbce9fa3457e35f217705bd5441c050142b8b4272c14d360a77cbe55`였다. 합성 결과와 실제 관찰 결과 모두 `interpretable_worsening_re_optimize`, `re_optimize`, `adjust_plan`을 냈고, 사건에는 각 분류가 그대로 남았다. 이 비교가 “분류 교체만으로 같은 계산”을 직접 뒷받침한다.

다만 이 smoke는 등록 당시 `production_data_used=false`였고, 실제 관찰 사례도 시험 입력이었다. 파일은 `real_world_outcome_contract_proven=true`와 `causal_effect_proven=false`를 함께 기록한다. 실제 데이터를 넣을 수 있는 계약과 실제 데이터로 효과를 입증했다는 주장을 구분한 것이다.

## 통합 단계와 아직 비어 있는 증거

등록 증거의 결합 지문은 `cf54b2e62cc8a2ca15195d0c6cfc4ba2d2a34ca551f7ed4a49a462d2db64f6d3`이고, 현재 같은 소스 목록의 값은 `70159f73f8625b511b55dda31ae979a31aec0fc661def844a793fe80e7d035a8`이다. 현재 Python 시험과 서비스 클라이언트 시험은 통과했지만, R&D 서버와 서비스 보조 함수를 함께 띄우는 smoke는 등록 JSON을 덮어쓰지 않기 위해 재실행하지 않았다. 최신 두 저장소 상태의 네트워크 재현은 확인되지 않았다.

실제 관찰 자료의 수집 동의가 운영에서 어떻게 보관되는지, 자료 출처가 사람에 의해 확인됐는지, 검토 초안이 약사 승인으로 이어졌는지도 이 증거에는 없다. 따라서 현재 판정은 등록 시점의 `INTEGRATED`로 유지하되, 운영 자료 처리와 외부 검토가 완료된 것으로 해석하지 않는다.
