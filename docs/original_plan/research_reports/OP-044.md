# OP-044 웨어러블, CGM, 유전자 관측값을 수치로 점수에 반영한다.

## 요구사항과 변경 전 점수의 한계

OP-044는 웨어러블·연속혈당측정기(CGM)·유전자 자료를 단순히 “있음”으로 표시하는 데서 멈추지 않고, 관측값에 따라 후보 정렬 점수를 바꾸라는 요구사항이다. 단, 이 점수는 질병 진단, 복용량 권고, 치료 목표, 개인별 효능 확률이 아니다. 등록된 성분 후보 안에서 먼저 보여 줄 순서를 조정하는 제한된 수치다.

정확한 manifest 위치는 data/original_plan/requirements_manifest_v1.json이다. OP-044의 claimed_stage는 IMPLEMENTED이며, 등록 구현·테스트 경로를 다시 대조해도 이 단계가 맞다. 운영과 외부 검증 근거는 등록되지 않았다.

커밋 26fe130 전의 score_candidate는 목표 prior, 증상, 생활 신호, 근거 준비도, 예산, 안전 조정을 합산했다. 입력 가용성에 wearable·cgm·genetic 표시는 있었지만, 현재의 정규화된 센서 기록에서 수면 5.5시간이나 목표 범위 내 시간 비율(TIR) 55%를 읽어 별도 점수 항목으로 남기지는 않았다. 유전자 신호도 구조화된 점수 규칙과 적용 기록 없이 맥락 플래그에 따른 근거 준비도 조정으로 들어갔다.

## 세 종류 관측값이 실제 점수로 바뀌는 방법

점수 규칙의 기준 파일은 wellnessbox-rnd/data/rules/candidate_signal_scoring_rules_v1.json이다. scoring_version은 2026-07-16.1이고, 웨어러블 2개, CGM 2개, 유전자 2개를 포함한 구조화 규칙 10개가 들어 있다. src/wellnessbox_rnd/knowledge/candidate_signals.py의 CandidateSignalScoringRegistry는 점수와 상한, 적용 성분·목표, 출처·주장 소유 관계, 제한 문구를 검사한다. 등록되지 않은 임계값이나 유전자 태그를 추가하면 candidate_signal_rule_contract_mismatch로 거부한다.

웨어러블 규칙은 sleep_hours가 7보다 작을 때만 적용된다. 마그네슘 후보는 부족한 1시간당 2점, 최대 6점을 받는다. L-테아닌은 1시간당 1.5점, 최대 4.5점이다. src/wellnessbox_rnd/efficacy/service.py의 _numeric_below_points는 `min(max_points, max(0, threshold - value) * points_per_unit)`를 계산한다. 따라서 5.5시간 수면은 마그네슘에 3점, L-테아닌에 2.25점을 더한다. 7시간 이상은 0점이고, 매우 짧은 수면을 넣어도 각 상한을 넘지 않는다.

CGM 규칙은 값 하나만 보지 않는다. 사용자의 목표에 blood_glucose가 있고, 현재 질환에 diabetes·type 1 diabetes·type 2 diabetes 중 하나가 있으며, 임신 중이 아니어야 한다. TIR은 70~180 mg/dL 범위에서 계산한 값이어야 하며, 70%보다 낮은 부분만 점수로 바꾼다. 수용성 식이섬유는 부족한 1%p당 0.2점·최대 6점, 베르베린은 0.1점·최대 3점이다. TIR 55%라면 각각 3점과 1.5점이다. 질환 맥락이 없거나, 임신 중이거나, TIR 범위가 80~140 mg/dL처럼 다르면 점수는 0이다.

유전자 규칙은 수치 검사값을 재해석하지 않고, 정확히 등록한 태그만 4점으로 바꾼다. cyp1a2_slow_metabolizer 또는 slow_caffeine_metabolism은 sleep_support·stress_support 목표의 L-테아닌에, adverse_lpl_variant 또는 lpl_triglyceride_risk는 heart_health 목표의 오메가3에 적용된다. unknown_research_tag처럼 알 수 없는 태그는 0점이다. _genetic_signals은 성분과 목표가 둘 다 맞을 때만 점수를 더하므로, CYP1A2 태그가 마그네슘 점수나 설명에 번지지 않는다.

## 단위, 범위, 동의를 점수 전에 정리한다

입력 값은 src/wellnessbox_rnd/domain/sensor_parser.py와 src/wellnessbox_rnd/schemas/recommendation.py의 경계를 지나야 점수에 들어간다. normalize_sensor_genetic_payloads는 sleepMinutes 390을 sleep_hours 6.5로 바꾸고, CGM 평균 혈당 6.8 mmol/L를 122.4 mg/dL로 바꾸며 변환 기록을 normalization_notes에 남긴다. 불리언, 숫자가 아닌 문자열, NaN·무한대, 허용 범위 밖의 값은 정상 수치로 받지 않는다. 다만 변환할 수 없는 일부 요약 숫자는 전체 입력을 거부하기보다 값을 비우고 `*_invalid_numeric_ignored` 기록을 남긴다. 이 차이를 “모든 오류를 거부한다”로 써서는 안 된다.

TIR 필드는 범위 의미를 보존한다. time_in_range_70_180_pct 별칭을 쓰면 하한 70과 상한 180을 붙인다. 범위가 적히지 않은 일반 time_in_range_pct는 70과 180을 명시해야 하며, 표준 별칭과 다른 범위를 같이 넣으면 bounds_mismatch로 멈춘다. 같은 의미의 별칭을 두 번 넣고 값을 다르게 적으면 conflicting_cgm_time_in_range_aliases를 반환한다. src/wellnessbox_rnd/schemas/cgm_events.py는 이 범위와 TIR을 평가·재생용 투영값에 복사하고 서로 다르면 오류를 낸다. 단, 이 CGM event bridge는 보조 투영 계층이며 score_candidate는 NormalizedSensorGeneticSnapshot을 직접 읽는다.

동의 차단은 src/wellnessbox_rnd/domain/intake.py에서 실제로 적용된다. input_availability가 true여도 data_source_consents의 use_for_recommendation이 false면 effective_input_availability는 false가 된다. _consent_gate_sensor_snapshot은 그 출처의 가용 표시와 관측값을 비운다. 그래서 동의를 거부한 웨어러블 값이 4시간에서 8시간으로 바뀌어도 정규화 입력의 SHA-256 지문과 점수는 바뀌지 않는다. tests/test_data_lake_lineage.py는 웨어러블만 저장을 허용했을 때 수면·걸음·안정 시 심박수만 남고, CGM 수치와 유전자 태그·검사실·판정 근거는 저장되지 않는지 확인한다.

## 유전자 변이 출처와 점수 태그는 아직 별개다

유전자 자료는 두 층으로 나뉘어 보아야 한다. 첫 번째는 점수에 쓰는 genetic_tags다. phenotypes·risk_flags·markers·gene_markers에서 읽은 문자열을 소문자 snake_case로 바꾸고, 정확히 등록한 태그와 맞을 때만 4점을 더한다. 두 번째는 genetic_variants다. 이 구조는 gene_symbol, variant_id, genotype, interpretation, interpretation_criterion, testing_laboratory, tested_on을 필수로 받아 출처와 해석 근거를 보존한다.

하지만 현재 코드는 genetic_variants를 읽어 cyp1a2_slow_metabolizer나 lpl_triglyceride_risk 태그를 자동으로 만들지 않는다. _genetic_signals이 사용하는 값은 snapshot.genetic_tags뿐이다. 따라서 “검사실 출처가 있는 변이만 점수에 쓴다”고 말하면 실제 구현보다 높은 주장이 된다. 변이 출처 보존은 구현됐지만, 점수 태그의 출처 검증·변이 파생 규칙·외부 검사기관 진위 확인은 아직 확인되지 않았다.

## 실패한 경계를 어떻게 고쳤는가

커밋 이력은 센서 숫자를 받는 것만으로 끝나지 않았음을 보여 준다. 26fe130은 여섯 구조화 규칙과 _wearable_signals·_cgm_signals·_genetic_signals를 추가해 관측값을 CandidateScoreSignal로 남겼다. 이후 395acc4는 일별 웨어러블 CSV와 CGM 요약 CSV를 정규화하는 경로를 추가했다.

첫 번째 보완은 단위와 별칭 충돌이었다. b686690은 mean_glucose_mg_dl 필드에 붙은 일반 mmol/L 단위를 다시 곱하지 않도록 고쳤고, 일반 TIR 필드에 70~180 범위가 없으면 거부하게 했다. 87063de는 동일 의미의 CGM 별칭 둘에 다른 값을 넣었을 때 첫 값을 묵시하고 지나가던 경계를 막았다. 603eeb1은 식후 최고값과 상승량의 mg/dL·mmol/L 별칭을 같은 단위로 바꿔 비교하게 했다.

두 번째 보완은 유전자 출처였다. 1d79e2b는 변이 식별자·유전형·해석·해석 기준·검사실·검사일을 구조화하고 출처를 저장 경계까지 넘겼다. 이 변경에서 숫자와 객체를 str로 자동 변환하면 허위 출처가 만들어질 수 있었다. 7ebac67은 genotype이 객체이거나 testing_laboratory가 숫자인 입력을 `*_must_be_string`으로 거부하도록 바꿔 이 틈을 막았다.

## 테스트가 증명하는 것

tests/test_candidate_signal_scoring.py는 점수 계산과 범위 제한을 직접 확인한다. test_wearable_sleep_value_produces_bounded_numeric_points는 5.5시간 수면에서 마그네슘 3점과 L-테아닌 2.25점을 비교한다. test_cgm_value_requires_consent_diabetes_context_and_goal은 수용성 식이섬유 3점과 베르베린 1.5점을 확인하고, 당뇨 맥락 부재·비표준 범위·임신·동의 거부에서 0점이 되는지 나눠서 본다. test_genetic_tag_is_converted_to_numeric_points_and_unknown_tag_is_zero와 test_genetic_tag_does_not_spill_into_unscoped_candidate_or_rationale는 등록 태그만 해당 성분에 영향을 주는지 검사한다.

tests/test_sensor_parser.py는 390분→6.5시간, 6.8 mmol/L→122.4 mg/dL 변환과 표준 TIR 범위를 본다. 중복 날짜, 단위 의미가 다른 Apple Health 레코드, 충돌하는 CGM 별칭, 비표준 TIR, 필수 출처가 빠진 유전자 변이는 실패하는지도 포함한다. tests/test_cgm_events.py의 test_build_cgm_normalized_event_v1_projects_parser_output_to_eval_and_replay는 파서의 평균 혈당·TIR 범위·식후 신호가 평가와 재생 투영값에 같게 들어가는지 확인한다. tests/test_data_lake_lineage.py의 test_sensor_snapshot_is_partitioned_by_each_source_storage_consent는 출처별 저장 동의 경계를 본다.

scripts/run_candidate_signal_scoring_smoke.py는 규칙 10개의 근거 연결, 실행용 지식 DB의 결정성, 저장본 일치, 점수 예시, 동의 거부 값의 지문 제외를 한 번에 묶어 검사한다. 저장된 wellnessbox-rnd/data/original_plan/evidence/op043_op044_candidate_signal_scoring_smoke_v1.json은 수면 5.5시간→마그네슘 3점, TIR 55%→수용성 식이섬유 3점, 임신·다른 TIR 범위→0점, lpl_triglyceride_risk→오메가3 4점을 남겼다. 스모크의 source_sha256은 ab17bdd5807bd26121ea2e733861214e2cb5577405efa4b723e68ba932cce5e4이며, 현재 SOURCE_PATHS로 다시 계산한 값과 같다. 저장 결과는 현재 등록 소스와 일치한다.

## 등록 경로, 현재 단계, 아직 알 수 없는 것

manifest가 등록한 구현 근거는 data/rules/candidate_signal_scoring_rules_v1.json, src/wellnessbox_rnd/knowledge/candidate_signals.py, src/wellnessbox_rnd/efficacy/service.py, src/wellnessbox_rnd/domain/sensor_parser.py, src/wellnessbox_rnd/schemas/cgm_events.py, src/wellnessbox_rnd/schemas/recommendation.py, data/knowledge/runtime_knowledge_db_v1.json이다. 테스트 근거는 tests/test_candidate_signal_scoring.py, tests/test_sensor_parser.py, tests/test_cgm_events.py, tests/test_data_lake_lineage.py, scripts/run_candidate_signal_scoring_smoke.py, data/original_plan/evidence/op043_op044_candidate_signal_scoring_smoke_v1.json이다. 모든 경로가 존재하고, 각 파일에 위에서 설명한 규칙·파서·점수·동의·저장 경계가 실제로 있다.

현재 근거 단계는 IMPLEMENTED다. 수치 관측값이 score_candidate의 wearable_adjustment·cgm_adjustment·genetic_adjustment에 들어가고, 각 CandidateScoreSignal은 관측값·단위·점수·규칙 ID·점수 버전·출처·주장·제한을 남긴다. CandidateScoreBreakdown.total은 이 세 항목을 각각 한 번씩 합산하고, 총점과 표시 항목의 합이 다르면 추천 계약 테스트가 실패한다.

하지만 현재 근거는 실제 기기 API에서 일별 요약을 받아 RecommendationRequest까지 자동으로 전달한 전 경로를 입증하지 않는다. 일별 CSV 파서가 존재하지만, 그 결과가 항상 추천 입력 기록으로 들어간다는 운영 근거는 없다. 유전자 점수 태그는 변이 출처와 자동으로 결속되지 않았고, 외부 검사기관 진위 검증도 없다. 점수 가중치와 임계값이 실제 사용자의 임상 결과를 예측한다는 외부 평가도 없다. 따라서 INTEGRATED, OPERATED, EXTERNAL 단계는 확인되지 않았다.
## 추천 후보를 점수로 바꿀 때
추천 후보를 잘 고르는 일과 특정 후보를 복용했을 때의 효과를 추정하는 일은 다르다. 이 그룹은 입력 신호가 어떤 점수로 바뀌는지, 안전 차단 전후의 후보가 어떻게 보존되는지, 불확실성을 어디에 표시하는지를 분리해 설명한다.

`OP-044`는 “웨어러블, CGM, 유전자 관측값을 수치로 점수에 반영한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/data/rules/candidate_signal_scoring_rules_v1.json`, `wellnessbox-rnd/src/wellnessbox_rnd/knowledge/candidate_signals.py`, `wellnessbox-rnd/src/wellnessbox_rnd/efficacy/service.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/sensor_parser.py` 외 3개
- 테스트·실행: `wellnessbox-rnd/tests/test_candidate_signal_scoring.py`, `wellnessbox-rnd/tests/test_sensor_parser.py`, `wellnessbox-rnd/tests/test_cgm_events.py`, `wellnessbox-rnd/tests/test_data_lake_lineage.py` 외 2개

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
