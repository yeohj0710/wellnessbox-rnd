# OP-104 — 평가 결과의 출처를 화면에서 구분하기

## 먼저 결론

추천 미리보기 응답은 이제 `resultOrigin`을 반드시 가진다. R&D 서버가 계약에 맞는 응답을 돌려주면 화면은 `R&D 실행 결과`와 실행 ID를 표시한다. 연결 실패, 시간 초과, 잘못된 응답처럼 서비스가 안전 차단 결과를 만들면 화면은 `로컬 스냅샷 결과`와 스냅샷 ID, 차단 사유를 표시한다. 원본 JSON 위에 출처 카드를 따로 두어 사용자가 결과 내용을 읽기 전에 생성 주체를 확인할 수 있다.

요구 단계는 `OPERATED`지만 이번 주장은 `INTEGRATED`다. 서비스 호출 결과와 화면 표시는 연결했고 단위·회귀 테스트를 통과했다. 실제 공개 평가 화면의 운영 트래픽과 브라우저 재현은 아직 증명하지 않았다.

## `rnd`와 `fallback`만으로는 왜 모자랐나

기존 응답에도 `source` 값은 있었다. 하지만 값은 원본 JSON 안의 `rnd` 또는 `fallback`이었다. 사용자는 이 값이 서버 실행인지, 로컬에 저장된 결과인지, 안전 차단 응답인지 해석해야 했다. 화면 제목도 `raw response`여서 결과의 출처보다 데이터 구조를 먼저 보여줬다.

새 출처 계약은 두 종류만 허용하는 판별 가능한 구조다. `rnd_execution`은 R&D 응답의 `execution_id`와 `metadata.generated_at`이 모두 있어야 만들어진다. 둘 중 하나가 없으면 원격 실행으로 표시하지 않고 예외를 낸다. `local_snapshot`은 fallback 사유가 반드시 있어야 한다. 사유가 없으면 모호한 결과로 간주해 닫힌 상태로 실패한다. 한 결과가 두 출처로 동시에 표시될 수 없도록 종류를 하나의 `kind` 값으로 고정했다.

## 스냅샷 ID도 실행마다 나뉜다

초기 구현은 요청 시각의 숫자만으로 스냅샷 ID를 만들었다. 독립 검토는 같은 밀리초에 두 결과가 생기면 ID가 겹칠 수 있다고 지적했다. 수정 뒤 로컬 안전 차단 응답이 이미 가진 무작위 실행 ID를 스냅샷 ID의 재료로 사용한다. 실행 ID가 없는 비표준 입력에만 요청 시각을 보조값으로 쓴다. 이 변경으로 정상 호출 경로의 두 fallback 결과는 같은 시각이어도 서로 다른 ID를 가진다.

## 화면에서는 무엇이 달라졌나

응답 영역 맨 위에 `aria-live="polite"`인 출처 카드를 추가했다. 아직 응답이 없으면 “결과 출처를 확인하는 중입니다”라고 표시한다. 원격 결과이면 `R&D 실행 결과`와 실행 ID를 보여준다. 로컬 안전 차단 결과이면 `로컬 스냅샷 결과`와 스냅샷 ID, 사유를 보여준다. 아래에는 `원본 응답`을 그대로 남겨 개발자가 세부 계약을 확인할 수 있게 했다.

출처 라벨은 응답 본문의 모델 버전이나 임의 문자열을 믿지 않는다. 서비스가 HTTP 성공 여부와 응답 계약을 검사한 뒤 결정한 `source`, 실행 ID, 생성 시각, fallback 사유만 사용한다. 잘못된 JSON, 4xx·5xx, 계약 불일치, 시간 초과, 네트워크 오류는 모두 로컬 스냅샷으로 귀결된다. 정상 R&D 계약만 원격 실행으로 표시된다.

## 검증과 남은 경계

서비스 QA는 두 라벨, 필수 식별자, 모호한 fallback 거부를 검사한다. 기존 추천 미리보기 회귀 검사는 정상 R&D 응답, 네트워크 오류, 잘못된 계약, 상태 불일치, JSON 해석 실패, HTTP 오류, 시간 초과, 설정 누락을 다시 통과했다. TypeScript 검사와 인코딩 검사도 통과했다. R&D 정형 증거는 커밋된 화면이 `resultOrigin.label`을 렌더링하고 호출 함수의 모든 반환 경로가 출처 판별기를 사용하는지 확인한다.

남은 단계는 실제 브라우저와 배포 환경이다. 운영 완료를 주장하려면 공개되지 않은 승인된 평가 경로에서 원격 성공과 로컬 fallback을 각각 재현하고, 화면 캡처나 접근성 트리로 라벨을 확인해야 한다. Vercel 설정, 공개 URL, 실제 사용자 트래픽은 이번 루프에서 변경하거나 증명하지 않았다.
