# OP-011 나이·성별·임신 상태·키·체중을 구조화 입력으로 정의한다

## 개인 특성을 문자열 메모로 남기지 않는다

원본 PDF 13쪽은 건강데이터 연동·분석에서 시작해 소분·배송과 추적·관리로 이어지는 사용자 흐름을 제시한다. PDF의 물리 16쪽에 보이는 데이터 레이크 그림은 UI 입력의 성별, 연령, 키, 체중, 병력과 생활습관을 개인 특성 파라미터로 모아 엔진과 모델이 같은 저장 구조에서 읽게 한다. OP-011의 실제 결과는 나이·생물학적 성별·임신 상태·키·체중을 자유 텍스트가 아니라 검증 가능한 필드로 정의하는 것이다. 추천 정확도를 직접 증명하는 요구가 아니라, 후속 안전·추천 코드가 입력 뜻을 잃지 않게 하는 계약이다.

## 기존 RecommendationRequest 안에 한 번만 정의했다

구현 중심은 `src/wellnessbox_rnd/schemas/recommendation.py`의 `UserProfile`이다. 별도 프로필 데이터베이스나 두 번째 요청 객체를 만들지 않고 기존 `RecommendationRequest.user_profile`을 사용한다. `age`는 18~120의 정수, `biological_sex`는 `female`, `male`, `other`, `undisclosed` enum, `pregnant`는 기본값 false인 boolean이다. `height_cm`과 `weight_kg`은 선택값이며 각각 0 초과 300 이하, 0 초과 500 이하로 제한한다. 후속 안전 요구에서 추가된 `lactating`도 같은 프로필에 들어가지만 false일 때 기존 직렬화와 hash를 바꾸지 않도록 제외된다.

서비스 원천 프로필을 받는 `WellnessBoxChatUserProfileV1`과 R&D의 canonical `UserProfile`은 역할이 다르다. 전자는 서비스 camelCase 계약을 손실 없이 추적하고, 후자는 추천 실행이 사용하는 정규형이다. 두 계약을 같은 이름의 임의 dict로 섞지 않는다. OP-011의 manifest는 canonical schema, 실제 FastAPI 예제 경로 `apps/inference_api/routes/recommend.py`, 샘플 `data/samples/api_recommend_structured_health_input_request_v1.json`을 구현 증거로 등록한다.

## API 예제는 필드 모양과 단위를 함께 보여 준다

샘플은 52세 남성, 임신 false, 키 176.5cm, 체중 82.4kg을 JSON 숫자로 보낸다. FastAPI `/v1/recommend` OpenAPI 예제도 같은 구조를 노출한다. 키와 체중 이름에 단위가 포함돼 있어 176.5를 inch나 82.4를 pound로 추정하지 않는다. 누락 가능한 키·체중은 `null`과 실제 값이 구분된다. 나이와 성별은 추천 요청에 필수이므로 없으면 Pydantic validation error가 발생한다.

`_StrictRequestInput`은 `extra="forbid"`를 사용한다. `gender_text`, `height`, `bodyWeight`처럼 계약에 없는 필드를 조용히 버리지 않는다. 키 0이나 음수, 300 초과, 체중 0이나 500 초과, 18 미만 또는 120 초과 나이는 거부한다. enum에 없는 성별 표현도 임의로 남성이나 여성으로 보정하지 않는다. 다만 이 범위는 데이터 형식의 방어선이지 의학적으로 가능한 모든 사람을 판정하는 기준은 아니다. 입력값의 진실성, 측정 장비 교정, 보호자 동의는 이 schema만으로 검증하지 못한다.

## 테스트는 schema와 공개 계약을 직접 확인한다

`tests/test_health_input_contracts.py`는 `UserProfile`에 키 176.5와 체중 82.4를 넣어 값이 보존되는지 확인하고 키 0이 validation error인지 확인한다. 같은 파일은 FastAPI OpenAPI의 `UserProfile` properties에 `height_cm`, `weight_kg`이 실제로 노출되는지 검사한다. 샘플 요청은 schema로 역직렬화되어 OP-012의 구조화 증상·질환·위험 신호 테스트에도 공통 입력으로 쓰인다. 따라서 문서에 필드명만 적힌 상태가 아니라 실제 요청 parsing 경로가 실행된다.

도입 커밋 `d57c8804be59c19932db01262df82ee1ee265bad`는 schema, API 예제, 샘플, intake와 계약 테스트를 함께 추가했다. 이후 `10ba2a760902b595d8741f3535a1de19cba820a8`이 서비스 프로필 adapter를 같은 canonical 요청에 연결했고, 임신·수유 안전 규칙과 센서 입력도 이 객체를 확장했다. 이 계보는 새 프로필 저장소를 만든 것이 아니라 기존 요청 계약을 재사용했음을 보여 준다.

## canonical evidence가 증명하는 범위

manifest 감사는 OP-011의 implementation과 test 경로가 R&D 저장소 소유이며 Git에 추적되는지 확인한다. completion generator는 required stage와 claimed stage가 모두 `IMPLEMENTED`이고 감사 issue가 없으므로 COMPLETE로 판정한다. GitHub Actions는 계약 테스트와 Ruff, manifest 감사, generated report stale 검사를 clean runner에서 실행한다. 연구보고서는 이 구현·테스트·원문 관계와 주장 한계를 설명하고 OP-120이 파일명, 분량, 의미 범주와 manifest evidence 인용을 다시 검사한다.

이번 backfill은 schema나 API를 바꾸지 않는다. 서비스 저장소, 원천 데이터, frozen 256건, 학습 데이터, 모델과 simulation도 바꾸지 않는다. 따라서 이전 일곱 평가 지표와 weakest slice, replay 결과의 delta는 0이다. 보고서 추가 뒤 OP-120 report inventory와 canonical evidence만 다시 생성한다.

## 완료 단계와 남은 한계

OP-011의 required stage와 claimed stage는 `IMPLEMENTED`다. strict `UserProfile`, 단위가 드러나는 필드, 범위 검증, 실제 OpenAPI 예제와 회귀 테스트가 있으므로 구현 단계는 충족한다. 그러나 production 사용자가 실제 값을 입력했는지, 서비스 프로필이 production traffic에서 왕복했는지, 측정값이 정확한지는 증명하지 않는다. `INTEGRATED`, `OPERATED`, 외부검증을 주장하지 않는다.

남은 조건은 후속 OP가 이 입력을 안전·추천·운영 경로에서 요구 단계까지 사용하고, production 통합과 운영 증거가 필요한 항목은 승인된 환경에서 별도로 확인하는 것이다. OP-011은 개인 특성의 뜻과 단위를 잃지 않는 입력 계약이지 건강 판정이나 임상 검증 결과가 아니다.
