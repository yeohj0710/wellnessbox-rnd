# OP-094 연구보고서: 동의하지 않은 유전자 데이터를 점수와 저장소에서 함께 제외하기

## 사용 동의와 저장 동의는 같은 질문이 아니다

OP-094는 동의하지 않은 데이터 출처를 저장하거나 점수에 사용하지 말라고 요구한다. 여기에는 서로 다른 두 결정이 들어 있다. 사용자가 추천 계산에는 허용하지만 영구 저장은 원하지 않을 수 있다. 반대로 저장은 허용했지만 현재 추천에는 사용하지 않도록 선택할 수도 있다. 하나의 `consent=true` 값으로 두 결정을 합치면 어느 한쪽의 의사를 어기기 쉽다.

기존 요청 계약은 설문, 국민건강보험, 웨어러블, 연속혈당측정기(CGM), 유전자 출처마다 `use_for_recommendation`과 `allow_persistent_storage`를 분리한다. 이번 작업은 새 구조화 유전자 변이가 이 계약의 빈틈으로 빠져나가지 않는지 확인하고, 추천 입력과 Data Lake 저장 경로 양쪽에 같은 출처 경계를 적용했다.

## 추천 계산 전에 데이터를 제거한다

추천 사용 동의는 `normalize_request`에서 적용된다. 먼저 사용자가 데이터가 있다고 선언한 출처와 출처별 추천 사용 동의를 결합해 effective availability를 만든다. 유전자 사용 동의가 없으면 `genetic_available`을 false로 바꾸고, 기존 `genetic_tags`와 새 `genetic_variants`를 모두 빈 목록으로 만든다. 점수 계산기가 나중에 동의 값을 다시 해석하도록 맡기지 않는다. 점수 계산기가 받는 정규화 입력 자체에서 비동의 데이터를 제거한다.

이 위치를 선택한 이유는 영향 범위를 한곳에서 차단하기 위해서다. 유전자 태그는 후보별 bounded adjustment에 쓰이고 설명 문구에도 반영될 수 있다. 각 소비자에서 별도로 동의를 검사하면 새 소비자가 추가될 때 누락될 수 있다. intake 경계에서 제거하면 후보 점수, 추천 순위, 설명, 입력 해시가 모두 같은 비동의 상태를 보게 된다.

## 비동의 데이터가 해시에도 영향을 주지 않아야 한다

데이터를 점수에서만 무시하고 canonical input hash에 남기면 비동의 변이 내용에 따라 실행 identity가 달라질 수 있다. 이는 추천 결과가 같더라도 시스템이 비동의 내용을 처리한 흔적이 된다. 회귀 테스트는 유전자 데이터가 선언되어 있지만 추천 사용 동의가 false인 요청과 유전자 내용이 비어 있는 요청을 비교한다. 정규화 뒤 두 요청의 `genetic_tags`와 `genetic_variants`는 모두 비어 있고, canonical input SHA-256과 추천 목록이 같다.

허용 사례에서는 기존 규칙 레지스트리에 등록된 `lpl_triglyceride_risk` 태그가 오메가3 후보에 4점의 제한된 조정을 더한다. 거부 사례에서는 같은 원본 태그와 구조화 변이를 넣어도 조정값이 0점이다. 구조화 변이의 `increased_risk` 판정을 보고 자동으로 점수를 만들지는 않는다. 판정 기록과 점수 규칙을 분리해야 검사기관 문구가 곧바로 추천 정책이 되는 일을 막을 수 있다.

## 영구 저장은 출처별로 다시 나눈다

Data Lake의 프로필 스냅샷은 전체 추천 요청을 그대로 저장하지 않는다. 설문, 국민건강보험, 웨어러블, CGM, 유전자별로 저장 가능한 payload를 만들고 `allow_persistent_storage=true`인 출처만 넣는다. 유전자 저장이 허용되면 `genetic_tags`와 `genetic_variants`를 유전자 출처 아래 저장한다. 허용되지 않으면 두 필드 모두 프로필 스냅샷에 나타나지 않는다.

기존 회귀 테스트는 웨어러블 저장만 허용한 요청에 CGM 혈당값과 비공개 유전자 태그를 함께 넣는다. 저장 결과에는 수면, 걸음 수, 안정 시 심박수만 있고 CGM과 유전자 출처는 없다. 이번에는 `private-panel-v1` 판정 기준과 `Private Genetics Lab` 검사기관을 가진 구조화 변이도 추가했다. 저장된 JSON 전체에서 태그, 판정 기준, 검사기관 문자열이 모두 발견되지 않는지 확인한다.

## 재실행 자료와 파생 결과의 저장 경계

실행 원장은 추천에 사용된 모든 출처가 저장에 동의했을 때만 파생 결과와 원래 request identifier를 보존한다. 요청에 표현된 모든 출처가 저장에 동의했을 때만 전체 재실행 스냅샷을 저장한다. 일부 출처가 거부되면 request identifier는 가명화하고 raw request JSON 재실행 스냅샷을 만들지 않는다. 프로필 스냅샷은 앞서 설명한 출처별 허용 payload만 담는다.

이 구분은 “프로필 화면에 안 보인다”만으로 저장 금지를 증명하지 않기 위해 필요하다. 같은 비동의 데이터가 replay table이나 execution event에 남아 있으면 요구사항을 충족하지 못한다. canonical smoke의 비동의 사례는 실제 임시 SQLite 데이터베이스에서 추천 실행을 기록한 뒤 유전자 프로필 스냅샷이 없는지 확인한다. 허용 사례는 같은 경로에서 유전자 출처가 실제로 저장되는지 확인해 테스트가 무조건 미저장만 반환하는 거짓 양성이 아님을 증명한다.

## 여덟 사례 중 동의 경계를 검증하는 두 사례

동결 데이터셋의 마지막 두 사례는 동일한 유전자 태그와 구조화 변이를 사용한다. 첫 사례는 추천 사용과 영구 저장을 모두 거부한다. 예상 결과는 유전자 점수 조정 0점, 유전자 저장 false다. 둘째 사례는 두 동의를 모두 허용한다. 예상 결과는 승인된 태그에 따른 4점, 유전자 저장 true다.

smoke runner는 정상화된 intake로 실제 `score_candidate`를 호출하고, 별도로 전체 `recommend`를 실행한 뒤 `ExecutionLedger`를 통해 임시 SQLite에 기록한다. 저장 여부는 테스트용 보조 함수의 반환값이 아니라 실제 `profile_snapshots.payload_json`을 다시 읽어 판정한다. 출력에는 임시 경로나 무작위 실행 ID를 담지 않으므로 같은 Git HEAD에서 바이트가 같아야 한다.

## 구현 중 확인한 실패와 수정

첫 집중 테스트에서는 비동의 요청과 데이터 부재 요청을 비교하려고 `input_availability.genetic=false`로 바꾸면서 원래 구조화 변이를 그대로 남겼다. 요청 스키마가 “유전자 값은 genetic availability가 true여야 한다”는 기존 불변식을 먼저 적용해 ValidationError가 발생했다. 이 오류는 제품 결함이 아니라 잘못 만든 비교 fixture였다. 데이터 부재 기준 요청의 스냅샷을 `genetic_available=false`와 빈 값으로 바꿔, 스키마를 우회하지 않고 실제 의미가 같은 두 정규화 결과를 비교하도록 고쳤다.

canonical smoke의 첫 실행에서는 catalog loader를 잘못된 모듈에서 import해 ImportError가 났다. 기존 후보 점수 테스트가 사용하는 `domain.catalog.get_catalog_index`로 import를 고쳤고, source identity가 수정된 runner를 가리키도록 구현 커밋을 다시 고정했다. 이 실패도 보고서에 남기는 이유는 canonical evidence가 테스트 코드와 독립적으로 실제 실행 가능한지 확인하는 과정이기 때문이다.

## 검증 결과를 해석하는 기준

집중 검증은 동의 계약, canonical input hash, 후보 점수, Data Lake 계보, sensor/genetic parser와 파일 스키마를 함께 다룬다. 거부 요청은 태그와 구조화 변이를 모두 제거하고, 허용 요청은 제한된 태그 점수와 출처별 저장을 보존한다. manifest 감사는 OP-094가 intake, Data Lake, 점수 서비스, 스키마, 테스트, canonical evidence에 연결되었는지 확인한다.

OP-094의 required stage는 `IMPLEMENTED`다. 요청 스키마, 추천 전 제거, 점수 회귀, 저장 분리, 실제 SQLite 재조회, 동결 사례와 canonical evidence가 있으므로 구현 검증 단계는 충족한다. 그러나 실제 유전자 공급자, 운영 데이터베이스, 동의 철회 운영, 배포 환경의 로그와 백업 삭제는 관찰하지 않았다. 따라서 production 운영이나 외부 개인정보 검증을 주장하지 않는다.

## 남아 있는 운영 과제

현재 저장 금지는 R&D의 구조화 Data Lake 경로에서 검증했다. 외부 업로드 버킷, 메시지 큐, 애플리케이션 로그, 오류 추적 도구, 데이터베이스 백업까지 포함한 운영 검증은 OP-101 이후 배포·보안 요구에서 별도 증거가 필요하다. 동의 철회 뒤 이미 저장된 유전자 프로필을 삭제하는 전체 보존정책도 이번 요구의 로컬 입력 차단과는 다른 운영 과제다.

다음 OP-095는 파일의 일부 행만 정상일 때 성공·실패 건수를 명시해야 한다. OP-096은 원본 파일 해시와 각 정규화 결과의 계보를 운영 단계에서 증명해야 한다. 두 요구를 구현할 때도 비동의 원본 파일의 내용이나 해시가 허용되지 않은 저장소에 남지 않도록 이번 출처 경계를 가장 앞단에서 재사용해야 한다.
