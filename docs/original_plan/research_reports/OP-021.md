# OP-021 사용자 프로필 버전과 동의 스냅샷을 영속 저장한다

## 요구사항은 현재 값뿐 아니라 판단 당시의 값을 보존하는 것이다

원본 계획 16쪽은 성별, 연령, 키, 체중, 병력, 증상, 복용 약물과 생활 습관을 개인 특성 파라미터로 모아 추천 엔진이 사용하도록 제시한다. 추천이 끝난 뒤 프로필이 바뀌면 현재 프로필만 조회해서는 과거 판단의 입력을 설명할 수 없다. OP-021은 추천 실행마다 사용한 프로필 버전과 동의 상태를 별도 스냅샷으로 남기고, 실행 레코드가 두 스냅샷을 참조하게 만드는 요구사항이다.

여기서 영속 저장은 모든 원본 정보를 무조건 보관한다는 뜻이 아니다. 출처별 `allow_persistent_storage`가 허용한 정보만 저장해야 한다. 저장을 거부한 출처의 원문 값은 프로필 스냅샷에 들어가면 안 되지만, 어떤 출처가 추천 사용과 저장을 허용했는지를 나타내는 동의 스냅샷은 감사에 필요하다. 따라서 프로필 payload와 동의 payload는 서로 다른 수명과 식별자를 가진다.

## SQLite schema가 프로필과 동의 이력을 분리한다

`src/wellnessbox_rnd/interim/store.py`는 `profile_snapshots`, `consent_snapshots`, `active_profile_consents`, `executions`를 정의한다. 프로필과 동의 스냅샷은 각각 `profile_id`, 증가하는 `version`, canonical payload의 SHA-256을 저장한다. 같은 프로필에서 버전 번호와 payload hash가 중복되지 않도록 unique 제약을 둔다. 실행은 `profile_snapshot_id`와 필수 `consent_snapshot_id`를 참조하므로 추천 당시 상태를 현재 활성 동의와 구분할 수 있다.

프로필 저장이 거부되면 `profile_snapshot_id`는 null일 수 있다. 반면 동의 스냅샷은 필수다. 이 비대칭은 누락이 아니라 개인정보 최소화 규칙이다. `active_profile_consents`는 프로필별 최신 활성 동의 스냅샷을 가리키며, 지연 도착한 대화나 후속평가 이벤트가 과거 동의만 믿고 저장되는 일을 막는다. 외래키와 transaction은 실행, 스냅샷, 이벤트가 절반만 기록되는 상태를 줄인다.

## 저장 함수가 출처별 동의를 먼저 적용한다

`src/wellnessbox_rnd/interim/data_lake.py`의 `_persisted_profile_payload`는 survey 저장 동의가 있을 때만 `user_profile`, lifestyle, medication 등 설문 기반 입력을 구성한다. NHIS, wearable, CGM, genetic도 각 출처의 `allow_persistent_storage`를 따로 확인한 뒤 허용된 값만 source payload에 넣는다. 사용 가능 여부나 추천 사용 동의만으로 영속 저장 권한을 추정하지 않는다.

`ExecutionLedger.record_recommendation`은 요청과 응답을 한 transaction에서 처리한다. canonical payload hash로 기존 snapshot을 재사용하거나 새 version을 만들고, 활성 동의를 갱신한 뒤 실행에 두 식별자를 결속한다. 사용된 모든 출처의 저장 동의가 있어야 파생 결과와 지식 lineage를 저장하고, 요청의 모든 출처가 허용돼야 replay용 원문 요청 snapshot을 저장한다. 저장 범위가 다르면 request ID도 redaction되어 원문 식별자가 우회 저장되지 않는다.

## 서비스 프로필 계약이 원본과 실행용 프로필의 경계를 고정한다

WellnessBox의 `lib/server/wb-rnd-profile-adapter.ts`는 서비스 프로필을 R&D `RecommendationRequest`로 변환한다. 두 저장소가 공유하는 `wellnessbox/contracts/wb-rnd/profile-adapter-v1.json`과 `data/contracts/wellnessbox_profile_adapter_v1.json`은 최소화한 `source_profile`, 가명 subject ID, 추천 입력 mapping을 같은 fixture로 고정한다. `tests/test_wellnessbox_profile_adapter_contract.py`는 두 snapshot의 byte 동일성과 R&D schema 수용을 검사한다.

이 계약은 OP-021이 별도 사용자 원장을 새로 만들지 않게 한다. 사용자 프로필의 소유 시스템은 WellnessBox이고, R&D는 추천 당시 받은 최소 입력과 허용된 snapshot만 보관한다. 서비스의 `scripts/qa/check-rnd-profile-adapter.cts`는 실제 TypeScript adapter와 preview 호출 body가 계약을 따르는지 검사한다. 다만 이 통합 증거는 OP-019의 범위이며, OP-021의 완료 주장은 R&D 영속 저장 구현과 테스트에 한정한다.

## 버전 규칙은 동일 입력 재사용과 변경 입력 증가를 구분한다

스냅샷 resolver는 payload를 canonical JSON으로 만든 뒤 SHA-256을 계산한다. 같은 profile ID와 같은 payload가 다시 오면 기존 snapshot ID와 version을 재사용한다. payload가 달라지면 현재 최대 version 다음 번호를 부여한다. 이 규칙은 재시도마다 의미 없는 버전을 늘리지 않으면서 실제 변경은 순서대로 남긴다.

동의도 같은 규칙을 사용한다. 저장 동의를 허용했다가 철회한 뒤 같은 거부 payload를 다시 제출하면 예전 거부 snapshot을 재사용하지만, `active_profile_consents`는 그 거부 snapshot을 다시 최신 상태로 가리킨다. 그러므로 snapshot version이 새로 생기지 않았다는 이유로 철회를 무시하지 않는다. 지연 이벤트는 실행 당시 동의와 현재 활성 동의를 함께 확인할 수 있다.

## 검증은 허용·변경·거부 세 경계를 모두 다룬다

`tests/test_data_lake_lineage.py`는 허용된 프로필이 version 1로 저장되고 변경된 payload가 version 2가 되는지 확인한다. 같은 payload 재실행의 snapshot 재사용, consent version 증가와 재사용, 활성 동의 교체도 검사한다. 저장 동의를 거부한 요청에서는 원본 프로필 값이 snapshot에 남지 않아야 하며, 이후 conversation과 follow-up event 저장도 최신 동의가 거부 상태이면 실패해야 한다.

`tests/test_inference_api.py`는 실제 `/v1/recommend` 요청에서 `execution_id`, profile version, consent version과 core event를 다시 읽는다. `tests/test_interim_store.py`는 schema 초기화와 제약을, `tests/test_wellnessbox_profile_adapter_contract.py`는 서비스 입력 계약을 확인한다. 즉 단위 함수만 검증하지 않고 FastAPI 경계에서 생성된 요청이 같은 ledger로 기록되는 경로를 포함한다.

## canonical smoke는 세 실행과 두 허용 버전을 재생한다

`scripts/run_data_lake_lineage_smoke.py`는 임시 SQLite 데이터베이스와 실제 FastAPI 앱을 사용한다. 저장 허용 프로필 v1, 변경된 v2, 저장 거부 요청의 세 사례를 실행한다. 생성된 `data/original_plan/evidence/op021_op022_data_lake_lineage_smoke_v1.json`은 case count 3, database schema version 8, 허용 profile version `[1, 2]`, consent snapshot 2개, execution 3개를 기록한다.

같은 증거는 저장 거부 프로필의 snapshot 수가 0이고 금지된 원문 값이 데이터베이스에 없다는 검사를 `true`로 남긴다. 이 결과는 테스트 fixture만 읽은 선언이 아니라 새 임시 데이터베이스에 route를 호출하고 SQL 집계를 수행한 결과다. smoke의 Git 이력은 실행 lineage를 도입한 `934f428`, 서비스 프로필 연결을 도입한 `10ba2a7`과 이후 강화 변경을 추적할 수 있다.

## IMPLEMENTED 완료와 운영 증거의 한계를 구분한다

manifest가 요구하고 주장하는 단계는 모두 `IMPLEMENTED`다. schema, transaction 저장기, 동의별 redaction, API 경로, 단위·통합 테스트와 canonical smoke가 있으므로 OP-021은 `COMPLETE`다. 로컬 SQLite 파일을 닫았다 다시 열어도 레코드가 유지되는 영속성은 구현했지만 production 데이터베이스 운영, backup·복구 훈련, retention 삭제, 실제 사용자 동의 UI, 배포 환경의 장기 관측 receipt는 증명하지 않는다.

이번 보고서 backfill은 코드, 서비스 보호 변경, production, 원천 데이터, frozen 256건, 학습 데이터, 모델과 simulation을 변경하지 않는다. 공식 frozen 일곱 지표, replay와 weakest slice delta는 모두 0이다. `OPERATED`로 승격하려면 승인된 production 환경에서 동의 변경, 프로필 버전 조회, 보존·삭제 정책, 복구 절차를 실행한 서명 가능한 운영 증거가 추가로 필요하다.
