# OP-079 연구보고서: 계획을 유지하고 바꾸고 멈추는 전 과정을 어떻게 검증했는가

## 이 요구사항이 해결하려는 문제

OP-079의 원문은 “유지, 조정, 교체, 중단, 모니터링 상태 전이를 E2E로 검증한다”이다. 이 문장은 짧지만 실제로 요구하는 범위는 넓다. 추천 결과를 한 번 계산하는 것으로는 closed-loop 시스템이 되지 않는다. 사용자가 계획을 시작한 뒤 효과와 순응도, 이상사례, 기기 데이터를 다시 받았을 때 기존 계획을 그대로 유지할지, 일부를 조정할지, 다른 계획으로 교체할지, 즉시 중단할지, 관찰을 이어갈지 결정하고 그 결과를 다음 실행에서도 일관되게 읽을 수 있어야 한다. API 응답에 `maintain` 같은 문자열을 넣는 것만으로는 충분하지 않다. 전이가 실제 저장소에 기록되어야 하고, 잘못된 순서와 중복 요청을 거부해야 하며, 중단된 계획의 예약 작업이 계속 실행되지 않아야 한다.

이 요구사항을 구현하기 전에도 R&D 저장소에는 closed-loop의 앞부분이 있었다. `workflow_contract.py`는 사용자 입력에서 안전 검사, 후보 생성, 근거 조회, 최적화, 계획 시작까지의 순서를 강제했다. `jobs.py`는 후속 일정과 재평가 작업을 저장했고, `execution_events`는 추천과 후속 평가의 이력을 append-only 방식으로 보존했다. OP-075와 OP-076은 PRO 또는 기기 데이터가 들어오면 다음 작업을 만들고 중대한 이상사례가 발생하면 계획을 멈추게 했다. 그러나 정상적인 후속 판단에서 “유지”, “조정”, “교체”, “모니터링”을 실제 계획 상태로 기록하는 공통 계약은 없었다. 기존 코드는 시작과 강제 중단에는 강했지만, 시작과 종료 사이의 일상적인 계획 변화는 하나의 검증 가능한 lifecycle로 연결하지 못했다.

## 새 상태 저장소를 만들지 않은 이유

가장 먼저 결정한 것은 별도의 `plan_states` 테이블이나 두 번째 이벤트 저장소를 만들지 않는 것이었다. 이미 `execution_events`에는 실행 ID, 동의 snapshot ID, 이벤트 순번, idempotency key, 원본 payload hash와 유효 payload hash가 저장된다. 이 저장소는 앞선 OP에서 추천, 안전 검사, 최적화, PRO 후속 관측과 correction까지 연결하는 기준 장부로 사용됐다. 계획 상태만 다른 테이블에 저장하면 어느 상태가 최신인지 판단할 때 두 저장소를 다시 맞춰야 하고, correction이나 동의 철회가 일어났을 때 서로 다른 진실이 생길 수 있다.

이번 구현은 `src/wellnessbox_rnd/interim/plan_lifecycle.py`를 추가하되 저장 대상은 기존 `execution_events`로 제한했다. 계획 전이는 `followup_evaluation` 이벤트로 들어가며 payload의 schema version은 `plan_lifecycle_transition_v1`이다. payload에는 대상 실행, 사용자, 계획, 행동, 전이 전 상태, 전이 후 상태, 이유 코드, 교체 계획 ID, 발생 시각과 요청 hash가 들어간다. 이 구조 덕분에 새로운 계획 상태를 조회할 때 별도 현재값 컬럼을 믿지 않고, 추천 이벤트에서 시작해 활성 lifecycle 이벤트를 순서대로 재생하여 현재 상태를 다시 계산할 수 있다.

## 다섯 행동을 상태로 표현한 방법

초기 추천 이벤트에 연결된 계획은 `ACTIVE`에서 시작한다. `maintain`은 `MAINTAINED`, `adjust`는 `ADJUSTED`, `monitor`는 `MONITORING`, `replace`는 `REPLACED`, `stop`은 `STOPPED`로 이동한다. `REPLACED`와 `STOPPED`는 기존 계획의 terminal state다. 교체 요청은 임의의 새 식별자를 활성화하지 않는다. 먼저 같은 실행의 추천 또는 최적화 이벤트에 `replacement_candidate` 역할, 교체 대상 계획 ID, 새 계획 ID가 기록되어 있어야 한다. 이 후보는 교체 전에는 `CANDIDATE`라서 실행 가능한 계획으로 취급하지 않는다. 교체 이벤트는 후보 이벤트 ID와 유효 payload hash를 함께 고정한 뒤 기존 계획을 `REPLACED`로 닫고 후보를 `ACTIVE`로 바꾼다. 후보가 없거나 다른 계획을 교체하도록 만들어졌거나 여러 후보가 겹치면 요청을 거부한다.

상태를 단순히 덮어쓰지 않고 전이 전 상태를 요청에 포함시킨 이유도 있다. 두 작업자가 같은 `ACTIVE` 계획을 보고 한쪽은 조정, 다른 쪽은 중단을 거의 동시에 요청할 수 있다. 서버가 현재 상태를 다시 확인하지 않으면 늦게 도착한 요청이 먼저 완료된 판단을 덮을 수 있다. `PlanLifecycleTransitionRequestV1`은 `expected_state`를 받고, 서비스는 `BEGIN IMMEDIATE` 트랜잭션 안에서 현재 이벤트를 재생한 결과와 이 값을 비교한다. 값이 다르면 `plan_lifecycle_stale_state`로 거부한다. 동시 실행 테스트에서는 같은 요청 두 개가 들어와도 이벤트는 하나만 생성되고, 한 응답만 새 기록이며 다른 응답은 같은 이벤트를 가리키는 deduplicated 결과가 된다.

## 중복 요청과 변경된 재시도를 구분한 방법

네트워크 재시도는 정상적인 운영 상황이므로 같은 요청을 두 번 보냈다는 이유로 두 상태 전이를 만들면 안 된다. 실행 ID, 이벤트 종류, idempotency key 조합으로 기존 이벤트를 찾고, 저장된 payload SHA-256과 새 요청에서 계산한 payload SHA-256을 비교한다. 두 값이 같으면 기존 이벤트 ID를 그대로 돌려준다. 같은 key로 행동이나 계획, 예상 상태, 이유, 시각이 바뀌면 `plan_lifecycle_idempotency_conflict`를 발생시킨다. 이 검사는 테스트 문자열만 맞추기 위한 조건이 아니다. canonical smoke는 다섯 행동을 실제 FastAPI 경로로 각각 한 번 실행하고 같은 payload로 다시 호출하여, 모든 행동에서 이벤트 ID가 같고 두 번째 결과가 deduplicated인지 확인한다.

처음 smoke를 실행했을 때 lifecycle 로직이 아니라 스크립트 import 경로 때문에 `ModuleNotFoundError: No module named 'apps'`가 발생했다. 저장소가 editable package로 설치되어 `wellnessbox_rnd`는 찾을 수 있었지만, `python scripts/...py` 방식에서는 저장소 루트가 `sys.path`에 없어 FastAPI 앱 패키지를 찾지 못한 것이다. 실패를 API나 상태기계 문제로 오해하지 않고, 스크립트가 자신의 저장소 루트를 명시적으로 import 경로에 추가하도록 수정했다. 같은 smoke를 다시 실행하자 다섯 전이와 API 검증이 완료됐다. 이 실패는 최종 기능 결함은 아니지만, 재현 명령이 깨져 있으면 canonical evidence를 다시 만들 수 없다는 점에서 연구 기록에 포함할 가치가 있다.

## 전이가 후속 작업에 미치는 영향

유지, 조정, 모니터링은 계획을 종료하지 않는다. 따라서 기존 follow-up과 READY 작업은 그대로 보존한다. 조정 상태라고 해서 아직 확정되지 않은 새 주문이나 계획을 자동으로 만들지 않는다. 반대로 교체와 중단은 기존 계획을 더 실행하면 안 되는 terminal 전이다. 이 두 행동이 저장되면 같은 트랜잭션에서 기존 계획의 `OPEN` 또는 `REEVALUATION_QUEUED` follow-up을 `CLOSED`로 바꾸고, `READY` 또는 `CLAIMED` workflow job을 `CANCELLED`로 바꾼다. job의 `last_error`에는 `PLAN_LIFECYCLE_REPLACED` 또는 `PLAN_LIFECYCLE_STOPPED`가 기록된다.

`WorkflowJobQueue._execution_plan_is_active`도 같은 lifecycle 재생 함수를 사용하도록 바꿨다. 예전 구현은 추천 이벤트가 있고 discontinuation 이벤트가 없는지만 확인했다. 이제 `REPLACED` 또는 `STOPPED`인 기존 계획은 비활성으로 판단한다. 교체 후보는 실제 추천·최적화 이벤트가 있어도 교체 승인 전에는 비활성이고, 후보를 가리키는 교체 이벤트가 저장된 뒤에만 활성 계획이 된다. 단위 테스트는 교체 직후 기존 계획이 비활성이고 근거 이벤트가 있는 새 계획만 활성인지 같은 SQLite 트랜잭션에서 확인한다. 중단 테스트는 follow-up과 job이 모두 닫혔고, 저장소에 lifecycle 전용 테이블이 새로 생기지 않았다는 사실도 확인한다.

독립 검토는 lifecycle 이벤트 자체를 일반 데이터 정정 또는 삭제 절차로 무효화할 수 있다는 결함도 찾았다. 중단 이벤트를 지우면 상태 재생 결과는 `ACTIVE`로 돌아가지만 이미 닫힌 follow-up과 취소된 job은 그대로 남아 모순이 생겼다. 수정 후 `DataMutationLedger`는 lifecycle schema를 발견하면 정정과 삭제를 모두 거부한다. 교체 전이가 소비한 후보 이벤트도 같은 불변 의존성으로 보호한다. SQLite trigger는 전이 이벤트와 소비된 후보의 UPDATE와 DELETE를 막아 애플리케이션 계층을 우회한 직접 변경까지 차단한다. 상태 재생은 교체 이벤트에 고정된 후보 이벤트 ID와 실제 payload SHA-256이 현재 후보와 일치하는지도 검사한다. 또한 발생 시각이 기존 실행 lineage보다 과거이면 전이를 거부한다. 이 방어들은 상태, 후속 작업, 후보 근거, 감사 시각이 서로 다른 사실을 말하지 않도록 보존한다.

## 실제 API를 통과한 E2E 검증

canonical smoke는 메서드를 직접 호출하는 데서 끝나지 않는다. 임시 SQLite 데이터베이스에 한 사용자와 활성 동의 snapshot을 만들고, 유지·조정·교체·중단·모니터링에 각각 독립된 실행과 계획, follow-up, workflow job을 준비한다. 그다음 `POST /v1/interim/plan-lifecycle/transitions`를 TestClient로 호출한다. 이 경로는 기존 내부 mutation token 검사를 그대로 사용하므로, 로컬 테스트라고 해도 실제 라우터의 인증 의존성과 Pydantic 요청 검증을 지난다.

다섯 사례에서 전이 이벤트가 정확히 다섯 개 저장됐고, 유지·조정·모니터링 사례의 follow-up과 job은 각각 `OPEN`, `READY`로 남았다. 교체·중단 사례는 각각 `CLOSED`, `CANCELLED`가 됐다. 교체된 기존 계획은 비활성이고, 기존 최적화 이벤트에 후보로 저장된 `plan_op079_replacement_active`만 활성으로 재구성됐다. 모든 정확 재시도는 같은 이벤트를 반환했다. 생성 파일 `data/original_plan/evidence/op079_op080_plan_lifecycle_order_boundary_smoke_v1.json`은 두 번 실행했을 때 byte-identical했고, 두 실행의 SHA-256은 모두 `d01d915be2daa94864ffcd724a243915543849952c676bbb0f6d041f7a86c7b8`이었다.

## 무엇을 증명했고 무엇은 아직 증명하지 못했는가

이번 결과는 로컬 R&D 프로세스에서 다섯 lifecycle 행동의 계약, 저장, idempotency, stale-state 차단, terminal cleanup, replacement activation과 FastAPI 왕복을 증명한다. 이는 `IMPLEMENTED` 단계의 직접 증거다. 그러나 OP-079가 속한 manifest 그룹 H의 required stage는 `OPERATED`다. 현재 증거에는 배포된 R&D 프로세스, 지속 실행되는 production worker, 실제 사용자 follow-up, 운영 중 발생한 동시 전이, 운영 데이터베이스 장애 복구가 없다. WellnessBox 서비스가 이 새 API를 호출한다는 증거도 이번 loop에는 없다.

따라서 OP-079는 COMPLETE가 아니라 PARTIAL로 남는다. 운영 단계로 올리려면 배포 승인을 받은 뒤 인증된 서비스가 실제 후속 입력을 보내고, production R&D가 전이를 저장하며, worker가 새 상태를 읽어 올바른 작업을 실행하거나 취소하는 전체 과정을 관측해야 한다. 특히 교체 도중 네트워크 장애가 발생했을 때 기존 계획과 새 계획 중 하나만 활성으로 남는지, 여러 worker가 같은 전이를 시도해도 한 이벤트만 유지되는지 운영 telemetry로 확인해야 한다. 로컬 SQLite 테스트가 이 가능성과 계약을 보여주지만 실제 운영을 대신하지는 않는다.
