# OP-076 중대한 이상사례 발생 시 계획과 추가 추천을 즉시 중단한다.

OP-076의 안전 조건은 중대한 이상사례를 한 행으로 기록하는 것보다 넓다. 연결된 복용 계획의 중단 사건, 진행 중 실행과 추천의 정지, 후속 업무 취소, 새 추천 진입 차단, 긴급 검토 생성까지 중간 성공 없이 함께 끝나야 한다. manifest의 구현 경로와 실패 회귀 자료는 이 원자적 중단을 `IMPLEMENTED` 수준으로 뒷받침하지만, 등록 운영 세션에는 이상사례가 한 건도 없어 실제 운영 중단을 입증하지 못한다.

## 중단 대상과 처리 순서를 먼저 고정한다

중대한 이상사례가 들어온 뒤에도 기존 재평가 업무나 추천 실행이 남으면 사용자는 “중단” 상태와 새 복용 제안을 동시에 받을 수 있다. 설문 저장을 먼저 완료하고 안전 중단이 충돌로 실패하는 순서도 위험하다. OP-076은 사례의 심각도를 확인한 순간 일반 후속 처리를 앞세우지 않고, 활성 계획을 기준으로 모든 파생 작업을 닫도록 요구한다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/agent.py`의 `BoundedAgent.record_adverse_event()`는 `BEGIN IMMEDIATE` 트랜잭션을 시작한 뒤 `execution_id`, `profile_id`, `plan_id`가 같은 활성 계획인지 확인한다. 관계가 틀리거나 이미 중단된 계획이면 `serious_adverse_event_active_plan_required`로 거부한다. 유효한 사례는 `adverse_events`에 `ESCALATED` 상태로 넣고 실행 원장에 `serious_adverse_event_plan_stop_v1` 이벤트를 추가한다. 중단 이벤트의 멱등 정보에는 `serious-ae:{case_id}`가 사용된다.

## 하나의 데이터베이스 경계에서 닫는 상태들

중단 이벤트를 기록한 같은 트랜잭션에서 활성 또는 실행 중인 `agent_runs`와 완료·중단되지 않은 `recommendation_runs`를 `STOPPED`로 바꾼다. 해당 계획에 열린 `followups`는 `CLOSED`, `READY`나 `CLAIMED` 상태인 `workflow_jobs`는 `CANCELLED`가 되며 오류에는 `SERIOUS_ADVERSE_EVENT_STOP`이 남는다. 마지막으로 이유 코드와 사례 출처를 연결한 `URGENT` 검토 작업을 생성한다. 어느 SQL 변경이 실패해도 사례만 남고 계획이 살아 있는 부분 완료를 커밋하지 않는다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`는 중단된 후속 업무가 다시 선점되지 않도록 활성 계획 재검사와 관련 업무 취소를 제공한다. `wellnessbox-rnd/apps/inference_api/routes/interim.py`의 이상사례 API는 내부 인증뿐 아니라 이벤트 변경용 토큰을 추가로 요구한다. PRO 후속 API에서 중대 사례가 들어오면 일반 PRO 후속 행보다 `record_adverse_event()`를 먼저 호출한다. 안전 중단이 과거의 같은 `case_id`와 내용 충돌로 실패하면 멈추지 않은 일반 후속 행도 저장하지 않는다.

중단 뒤 새 실행을 막는 검사도 같은 저장소 상태를 읽는다. `BoundedAgent.create_run()`은 즉시 트랜잭션 안에서 해결되지 않은 중대 사례 보류를 확인하고 `serious_adverse_event_recommendation_hold`를 낸다. 에이전트 실행과 일반 추천 경로 모두 이 보류에 걸리므로 이미 열린 업무만 취소하고 새 추천 생성은 허용하는 빈틈을 남기지 않는다.

## diff가 보여 주는 경쟁 조건 수정 순서

커밋 `c35abf`는 PRO·기기 입력 업무와 함께 최초의 중대 이상사례 중단 묶음을 구현했다. 초기 PRO 라우트 diff에서는 일반 후속 설문을 저장한 뒤 중대 사례 중단을 호출하는 순서가 있었다. 같은 사례 ID가 과거 내용과 충돌하면 중단은 실패하지만 보통 후속 행은 남을 수 있는 상태였다. 실행 생성의 안전 보류 확인도 트랜잭션 밖 시점에 의존해, 확인 직후 사례가 들어오는 경쟁 창이 있었다.

커밋 `617d7f`는 두 문제를 공통적으로 저장 순서에서 고쳤다. PRO 라우트는 중대 사례 중단이 성공한 뒤에만 필요한 응답을 만들고, 충돌 시 일반 후속 행을 남기지 않는다. `create_run()`은 보류 확인, 멱등 요청 확인, 실행 삽입을 하나의 즉시 트랜잭션에 넣어 이상사례 기록과 직렬화한다. 두 스레드가 동시에 진행돼도 활성 새 실행과 중단 사례가 함께 커밋되지 않는다.

커밋 `932358`은 대문자가 포함된 사례 ID의 재전송에서 검토 이유 코드 정렬이 달라질 수 있던 경계를 보강했다. 같은 사례를 재요청하면 이미 만든 검토 ID를 유지해야 하며, 표현 대소문자가 재전송 때 새 검토를 만들게 해서는 안 된다. 저장소에는 수정 전 프로덕션 사고나 환자 영향 기록이 없으므로, 이 연대기는 코드 diff와 추가된 회귀 시험이 보여 주는 결함 가능성과 수정 내용만을 말한다.

## 회귀 시험의 사후조건

`wellnessbox-rnd/tests/test_interim_agent.py`의 `test_serious_ae_atomically_stops_plan_and_creates_review`는 사례 상태, 계획 중단 이벤트, 실행·추천 정지, 후속 종료, 업무 취소, 긴급 검토 생성을 한꺼번에 확인한다. `test_serious_event_cannot_race_with_run_creation`은 실행 생성이 보류 검사 직후 대기하도록 만든 뒤 다른 스레드에서 사례를 기록한다. 두 스레드가 끝났을 때 활성 실행이 0건이고 안전 중단만 남아야 한다. `test_serious_event_retry_keeps_review_link_for_uppercase_case_id`는 재전송 후 동일 검토 연결을 단언한다.

`wellnessbox-rnd/tests/test_pro_plan_service.py`의 `test_serious_pro_followup_stops_plan_and_cancels_prior_next_job`은 먼저 PRO·기기 재평가 업무를 만든 뒤 중대한 PRO가 두 업무와 추천을 모두 정지하는지 본다. `test_serious_pro_conflict_does_not_persist_unstopped_followup`은 안전 중단 충돌 응답 이후 중단되지 않은 후속 설문 행 수가 0인지 검사한다. 이는 HTTP 오류만 확인하는 시험이 아니라 부분 저장 부재를 데이터베이스에서 확인한다.

`wellnessbox-rnd/tests/test_interim_api.py`의 `test_serious_ae_flow_creates_review_and_review_decision_is_immutable`은 이상사례 API 호출 뒤 에이전트 추천과 일반 추천 진입이 각각 차단되고, 생성된 검토의 완료 전제에 `serious_hold_active`와 `plan_stop_recorded`가 포함되는지 다룬다. 검토 완료의 의약학적 적절성을 평가하는 시험은 아니며 안전 상태가 실제 저장됐는지를 확인한다.

## 스모크가 연결한 여덟 결과와 버전 제한

`wellnessbox-rnd/scripts/run_followup_input_serious_ae_smoke.py`는 같은 계획에 PRO·기기 재평가 업무 두 건을 준비한 뒤 중대 사례 `ae_op075_op076_serious`를 기록한다. 결과 `wellnessbox-rnd/data/original_plan/evidence/op075_op076_followup_input_serious_ae_smoke_v1.json`에서 업무 둘은 `CANCELLED`, 후속 둘은 `CLOSED`, 진행 중 추천은 `STOPPED`다. 중단 실행 이벤트와 검토가 각각 한 건 추가됐고 이후 새 실행은 `serious_adverse_event_recommendation_hold`로 거부됐다.

증거 파일은 스스로 `op076_proven_stage=IMPLEMENTED`라 적고 `production_serious_ae_stop_proven=false`, `service_integration_proven=false`, `production_deployment_proven=false`로 범위를 제한한다. 생성 당시 `source_commit`은 `24d82df`이고 기록된 묶음 SHA-256 `3e2e9b…`은 현재 대응 파일의 계산값 `6686066e…`와 다르다. 스모크 이후 수정까지 자동으로 실행된 것으로 간주하지 않고, 현재 동작은 현행 테스트의 단언과 소스를 함께 근거로 삼았다.

## 운영 영수증이 비어 있는 핵심 열

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-076.json`을 연결하고 `claimed_stage=OPERATED`로 기록한다. 그러나 해당 로컬 세션의 증가량은 `adverse_events=0`, `review_tasks=0`이며 사례 ID, 중단 이벤트, 취소 업무, 추천 보류 결과가 없다. `executed_paths`에 후속·검토 이름이 있다는 사실만으로 중대한 이상사례 안전 절차가 실행됐다고 볼 수 없다.

따라서 이 보고서가 인정하는 단계는 `IMPLEMENTED`다. 임시 로컬 데이터베이스의 원자적 상태 변경과 경쟁 조건 차단은 재현됐지만 실제 사용자의 사례, 운영 업무 처리 중 취소 반영 시간, 실제 약사의 긴급 대응, 외부 알림 중지는 확인되지 않았다. 운영 단계에는 가명화된 사례 식별자, 계획 중단 이벤트, 정지된 실행·추천, 취소 업무 목록, 검토 식별자, 새 추천 차단 결과를 동일 추적 문맥으로 남긴 자료가 필요하다.
