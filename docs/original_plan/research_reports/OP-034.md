# OP-034 질환별 금기와 검토 필요 규칙을 구분한다.

manifest의 구현 근거 `wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`는 질환 규칙의 효과를 `contraindication`과 `review_required`로 구분한다. 현재 정책은 일반 신장 질환, 중증 신장 질환, 간 질환, 혈색소침착증을 별도 규칙으로 평가한다. 규칙 데이터와 두 안전 경로, 실행용 DB, 단위 테스트, 대표 시나리오 증거를 확인한 결과 OP-034는 `IMPLEMENTED`다.

## 하나로 묶였던 장기 질환 규칙을 나눈 이유

질환 이름이 다르면 제한할 성분과 필요한 대응도 달라진다. 단순히 “신장 또는 간 문제가 있으면 주의”라는 하나의 경고로 합치면 중증 신부전의 전역 차단과 일반 신장 질환의 성분 검토를 구별할 수 없다. 혈색소침착증에서 철과 비타민 C를 피해야 하는 이유도 간 질환과 동일하지 않다.

커밋 `9e1a171` 전의 사전 점검은 kidney, liver, dialysis, cirrhosis 같은 단어를 넓은 한 조건으로 묶었다. 같은 시점의 추천 정책에도 일반 신장 질환 규칙만 있어 중증도와 다른 질환을 충분히 표현하지 못했다. 변경 후 일반 신장 검토, 중증 신장 차단, 간 질환 차단, 혈색소침착증 검토 규칙과 개별 회귀 테스트가 생겼다. 커밋 `c39f0f6`은 대표 시나리오 결과 파일에 각 규칙이 참조하는 외부 자료 또는 내부 범위 정책을 명시했다. 이력은 결손과 수정은 보여 주지만 장애 티켓이나 실패 로그는 제공하지 않는다.

## 규칙 모델과 현재 정책 결과

`wellnessbox-rnd/data/rules/safety_rules.json`의 `SAFETY-RENAL-001`은 `kidney disease`, `chronic kidney disease`를 일반 신장 조건으로 보고 마그네슘 글리시네이트를 제외하며 `needs_review`를 만든다. `SAFETY-RENAL-SEVERE-001`은 `kidney failure`, `dialysis`를 별도로 받아 같은 성분을 제외하되 심각도 `blocker`로 전체 상태를 `blocked`로 만든다. `renal impairment`와 `severe renal impairment`라는 별칭은 현재 조건 목록에 없다.

`SAFETY-HEPATIC-001`은 `liver failure`, `cirrhosis`를 대상으로 한다. 모델의 효과 값은 `review_required`지만 규칙 심각도가 `blocker`이므로 현재 추천 결과는 `blocked`다. 이 규칙은 특정 성분을 열거하지 않는다. 반면 `SAFETY-HEMO-001`은 `hemochromatosis`에서 철과 비타민 C를 제외하고 상태를 `needs_review`로 둔다. `liver disease`, `hepatitis`, `iron overload`라는 별칭은 현재 등록되어 있지 않다. 따라서 효과 분류, 제외 성분, 최종 상태는 같은 필드가 아니며 규칙별로 함께 읽어야 한다.

도메인 검증은 `effect="contraindication"`인 규칙에 제외 성분이 하나도 없으면 객체 생성을 거부한다. `wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py`는 해결되지 않은 현재 질환의 정규화된 이름과 규칙 조건을 정확히 비교해 제외 성분, 경고, 규칙 참조를 만든다. `wellnessbox-rnd/src/wellnessbox_rnd/knowledge/runtime_db.py`는 이 효과와 조건을 런타임 레코드로 옮기며, 생성 결과는 `wellnessbox-rnd/data/knowledge/runtime_knowledge_db_v1.json`에 보존된다.

사전 점검인 `wellnessbox-rnd/src/wellnessbox_rnd/interim/safety.py`도 신장, 간, 혈색소침착증을 서로 다른 재생 규칙으로 평가한다. 하지만 이 경로는 중증 신장과 간 질환에 즉시 `BLOCK`, 일반 신장에는 `WARN`을 반환하는 단순화된 판정기다. 추천 경로와 규칙 ID, 입력 구조, 결과 모델이 같지 않으므로 대표 시나리오 파일은 두 경로의 결과를 나란히 기록한다.

## 자동화 검사가 고정한 경계

`wellnessbox-rnd/tests/test_special_population_condition_safety.py`의 `test_condition_rules_distinguish_contraindication_from_review`는 네 사례를 직접 비교한다. 일반 신장 질환은 `SAFETY-RENAL-001`, `needs_review`, 마그네슘 제외를 요구한다. 신부전은 `SAFETY-RENAL-SEVERE-001`, `blocked`, 마그네슘 제외를 요구하고, 간경변은 `SAFETY-HEPATIC-001`과 `blocked`를 확인한다. 혈색소침착증은 `SAFETY-HEMO-001`, `needs_review`, 철과 비타민 C 제외를 단언한다.

같은 파일의 `test_unmatched_condition_does_not_trigger_expanded_rules`는 계절성 알레르기가 이 질환 규칙을 잘못 활성화하지 않고 `ok`와 빈 규칙 목록을 반환하는지 검사한다. `test_contraindication_rule_requires_at_least_one_excluded_ingredient`는 제외 성분 없는 금기 객체가 Pydantic 검증 오류를 내는지 확인한다. `test_runtime_knowledge_keeps_special_population_and_condition_effects`는 런타임 DB에서 일반 신장은 `review_required`, 중증 신장은 `contraindication`, 간 질환은 `review_required`로 보존되는지 점검한다. `wellnessbox-rnd/tests/test_interim_safety.py`의 `test_condition_replay_separates_renal_hepatic_and_hemochromatosis_rules`는 사전 점검의 분리된 규칙 ID를 고정한다.

`wellnessbox-rnd/scripts/run_special_population_condition_safety_smoke.py`는 질환별 판정 차이를 한 번에 재생하는 스모크 스크립트다. 결과 파일 `wellnessbox-rnd/data/original_plan/evidence/op033_op034_special_population_condition_safety_smoke_v1.json`은 네 질환 사례와 불일치 사례를 포함한다. 결과에는 적용 규칙, 제외 성분, 추천 상태, 사전 점검 결과가 함께 있어 상태 차이를 다시 확인할 수 있다.

## 근거가 허용하는 단계

대표 시나리오 결과의 정책 근거는 일반·중증 신장 규칙에 NIH ODS 마그네슘 자료, 혈색소침착증 규칙에 NIH ODS 철 자료를 연결한다. 재확인한 마그네슘 자료는 신장 기능 저하에서 독성 위험이 커진다는 일반 근거를 제공하지만 마그네슘 글리시네이트만을 자동 제외해야 한다는 구체적 결론까지 직접 제시하지 않는다. 철 자료는 혈색소침착증 치료에서 철과 비타민 C 보충제를 피하라는 근거를 제공한다. 간 질환 규칙은 외부 문헌이 아니라 `wellnessbox-rnd/docs/context/master_context.md`의 초기 고위험 범위 정책을 근거로 표시한다.

구현 경로 여섯 개와 테스트·증거 경로 네 개는 모두 존재하며 등록 목적과 맞는다. 다만 런타임 질환 규칙에는 reference ID나 claim ID가 없고, 운영 환자 결과나 외부 임상 검증도 없다. 따라서 저장소에서 재현되는 `IMPLEMENTED`까지만 인정하며 정책의 의학적 충분성, 시스템 통합, 운영 효과는 확인하지 않은 항목으로 남긴다.
## 안전 판단에서 놓치면 안 되는 경계
안전 그룹의 기준은 추천을 많이 만드는 것이 아니라 위험한 결과를 통과시키지 않는 것이다. 입력 단계와 후보 생성 뒤에 안전 판단을 두고, 중대한 위험이나 불명확한 용량이 나오면 fail-closed로 멈추는 경계를 확인한다.

`OP-034`는 “질환별 금기와 검토 필요 규칙을 확대한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=17`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`, `wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/safety.py`, `wellnessbox-rnd/src/wellnessbox_rnd/knowledge/runtime_db.py` 외 2개
- 테스트·실행: `wellnessbox-rnd/tests/test_special_population_condition_safety.py`, `wellnessbox-rnd/tests/test_interim_safety.py`, `wellnessbox-rnd/scripts/run_special_population_condition_safety_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op033_op034_special_population_condition_safety_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
