# OP-061 효능, 안전, 비용, 복용 수, 제형 선호를 최적화 제약으로 명시한다.

다섯 판단 기준은 하나의 독립 계약과 판정 함수로 구현돼 있다. 기준 정책 원문은 `wellnessbox-rnd/data/contracts/optimization_constraints_v1.json`이고, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/constraints.py`가 후보 사실에서 위반 이유를 계산한다. manifest의 요구 단계와 등록 증거가 모두 `IMPLEMENTED`이므로 그보다 높은 통합 단계를 주장하지 않는다. 특히 판매 상품 서비스는 아직 이 다섯 기준 전체를 한 요청에서 소비하지 않는다.

## 점수만 높은 후보를 고르던 문제를 다섯 축으로 분해했다

효능 예상값이 높아도 금지 성분이 있거나 예산을 넘으면 선택할 수 없다. 제품 수와 하루 복용 단위가 많으면 사용자가 계획을 지키기 어렵고, 원하지 않는 제형도 실제 선택에서 제외 사유가 된다. 커밋 `8ec6896` 이전에는 이 다섯 항목을 같은 후보 자료와 같은 판정 결과로 묶는 계약이 없었다. 이 커밋은 `OptimizationConstraintsV1`, `OptimizationCandidateFactsV1`, `OptimizationConstraintEvaluationV1`을 새로 만들고 정책 파일을 코드 밖에 두었다.

현재 기준 정책은 최소 효과 점수 5.0, 제외 성분 `unsafe_ingredient`, 총비용 50,000원 이하, 제품 두 개 이하, 하루 네 단위 이하, 선호 제형 캡슐·정제다. 이 숫자는 연구용 정책 버전 `2026-07-21.1`의 기본값이다. 모든 사용자에게 임상적으로 적절하다고 확정한 값은 아니다. 정책을 JSON으로 분리한 덕분에 임계값 변경과 판정식 변경을 구분할 수 있고, 시험은 파일 내용이 모델 기본값과 정확히 같은지도 대조한다.

## 함수는 통과 여부보다 위반 이유를 먼저 만든다

`evaluate_optimization_candidate_v1`은 내부 함수 `_derive_violations`로 일곱 가지 위반 코드를 정해진 순서대로 만든다. 효능은 `expected_effect_score`가 최솟값보다 작은지 본다. 안전은 후보 전체의 `safety_status`와 제외 성분 교집합을 따로 살핀다. 비용은 합계, 복용 부담은 제품 수와 하루 단위 수, 제형은 후보 제형 전체가 선호 집합의 부분집합인지로 판정한다. 위반이 하나도 없을 때만 `feasible=True`다.

`OptimizationConstraintEvaluationV1.validate_derived_output`은 후보와 정책에서 위반 목록을 다시 계산한다. 누군가 결과의 `feasible`이나 `violations`만 고쳐도 저장 모델이 이를 거부한다. 숫자에는 NaN과 무한대를 허용하지 않고, `StrictInt`를 사용해 참·거짓이나 소수를 비용·제품 수로 받지 않는다. 성분과 제형 목록의 중복, 선언하지 않은 추가 필드도 실패한다. 잘못된 입력을 임의 기본값으로 바꾸는 대신 계산을 멈추는 방식이다.

## 처음 구현 뒤 변경 가능한 목록 문제가 수정됐다

커밋 `8ec6896`의 첫 모델은 `excluded_ingredient_keys`, `preferred_formulations`, `checked_dimensions`, `violations`를 Python `list`로 두었다. 모델 자체에 `frozen=True`가 있어도 내부 목록은 나중에 `append`나 `clear`로 바꿀 수 있었다. 커밋 `ea3bc72`는 이 컬렉션을 모두 튜플로 바꾸고 `test_validated_contract_and_evaluation_collections_are_immutable`을 추가했다. 같은 커밋은 smoke의 표현도 고쳤다. 서비스의 Prisma 조회 구현이 연결됐다는 표현을 `configured_prisma_query_source_bound=true`, `actual_prisma_query_executed=false`로 나눠 실제 조회를 한 것처럼 읽히지 않게 했다. 이 두 수정은 코드와 증거 단계의 과장을 함께 막는다.

`wellnessbox-rnd/tests/test_optimization_constraints.py`의 `test_feasible_candidate_records_all_five_constraint_dimensions`는 정상 후보가 효능·안전·비용·복용 부담·제형을 모두 기록하고 통과하는지 본다. `test_each_constraint_violation_is_explicit`은 효과 4.99, 안전 차단, 제외 성분, 50,001원, 제품 3개, 하루 5단위, 분말 제형을 각각 넣어 정확한 위반 코드를 요구한다. `test_evaluation_rejects_derived_output_mutation`은 파생 결과 변조를 막고, `test_candidate_rejects_ambiguous_or_non_finite_input`은 중복 성분·NaN·중복 제형을 거부한다. 이번 검토에서 이 파일을 포함한 집중 시험 96개가 모두 통과했다.

## 등록 smoke는 여섯 후보를 비교했다

`wellnessbox-rnd/data/original_plan/evidence/op061_op062_optimization_product_catalog_smoke_v1.json`에는 정상 후보 한 건과 효능·안전·비용·하루 부담·제형 실패 후보 다섯 건이 있다. 정상 후보는 효과 7.5, 42,000원, 제품 2개, 하루 3단위, 캡슐·정제로 통과했다. 효과 4.99는 `minimum_effect_score_not_met`, 50,001원은 `maximum_total_cost_exceeded`, 하루 5단위는 `maximum_daily_unit_count_exceeded`, 분말은 `preferred_formulation_not_met`를 남겼다. 안전 차단 후보도 `safety_status_blocked`로 제외됐다.

현재 시험에는 등록 smoke보다 더 넓은 사례가 있다. 제외 성분 교집합과 최대 제품 수 위반도 각각 확인한다. 반대로 smoke의 여섯 사례에는 `excluded_ingredient_present`와 `maximum_product_count_exceeded`가 직접 들어 있지 않다. 등록 JSON만 보고 일곱 위반 유형 모두를 smoke로 실행했다고 말하면 사실과 다르다.

## 구현 완료와 서비스 통합 사이에는 세 기준이 남아 있다

현재 판매 상품 경로의 `product_optimization_constraints_v1`은 예산, 최대 제품 수, 안전 제외 성분과 안전 규칙 ID를 전달한다. 그러나 최소 효과 점수, 하루 복용 단위, 제형 선호를 `OptimizationConstraintsV1`에서 서비스 상품 조합 필터로 넘기지 않는다. 그러므로 다섯 항목은 독립 계산기로 구현됐지만 실제 상품 추천이 모두 사용한다는 증거는 없다.

등록 JSON의 결합 지문 `a24d386cbf72d82fc94a6db2560afcb240508af474fea586ace3d0ed7e05530b`과 현재 재계산 값 `aa97a0a6d60e37c08e7f1cf198842bc44943e360fcb903d76bd1de0ede959765`도 다르다. 현재 단위 시험은 성공했지만 등록 smoke를 최신 파일로 다시 만들지 않았고, 실제 사용자별 임계값이 어디에서 정해지는지도 확인되지 않았다. 따라서 OP-061의 결론은 다섯 제약을 명시하고 검증하는 계산기가 `IMPLEMENTED`라는 데서 멈춘다.
## 상품 조합을 고를 때 함께 본 조건
상품 조합은 효능 점수 하나로 결정하지 않는다. 안전하게 남은 후보, 성분 중복, 일일 용량, 가격, 재고, 제형과 복용 수를 함께 보고, 선택되지 않은 조합의 이유도 다시 설명할 수 있어야 한다.

`OP-061`는 “효능, 안전, 비용, 복용 수, 제형 선호를 최적화 제약으로 명시한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=20`
- 구현·설계: `wellnessbox-rnd/data/contracts/optimization_constraints_v1.json`, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/constraints.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_optimization_constraints.py`, `wellnessbox-rnd/scripts/run_optimization_constraints_product_catalog_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op061_op062_optimization_product_catalog_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
