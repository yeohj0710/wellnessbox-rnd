# OP-061 효능, 안전, 비용, 복용 수, 제형 선호를 최적화 제약으로 명시한다.

다섯 판단 항목은 `wellnessbox-rnd/data/contracts/optimization_constraints_v1.json`에 수치와 목록으로 고정돼 있고, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/constraints.py`가 후보마다 위반 이유를 계산한다. 등록 smoke인 `wellnessbox-rnd/data/original_plan/evidence/op061_op062_optimization_product_catalog_smoke_v1.json`도 직접 대조했다. 현재 입증 단계는 `IMPLEMENTED`다. 이 제약 계산기가 구현되고 자동 시험을 통과했다는 뜻이며, 서비스의 실제 추천이 다섯 항목을 모두 사용한다는 뜻은 아니다.

## 좋은 점수 하나로 조합을 고를 수 없는 이유

효과 예상값이 높아도 안전 차단 성분이 들어 있거나 예산을 넘으면 선택할 수 없다. 제품 수와 하루 복용 단위가 지나치게 많으면 사용자가 계획을 지키기 어렵다. 선호하지 않는 제형도 같은 문제를 만든다. 그래서 후보 하나를 `expected_effect_score`, 안전 상태, 총비용, 제품 수, 하루 복용 단위, 제형 목록으로 표현하고 한 번에 다섯 범주를 판정한다.

기준 정책은 최소 효과 점수 5.0, 제외 성분 `unsafe_ingredient`, 총비용 50,000원 이하, 제품 두 개 이하, 하루 네 단위 이하, 캡슐 또는 정제 선호다. 이 숫자는 연구용 기본 정책이지 모든 사용자에게 적용할 확정 운영값이 아니다. 정책 파일을 코드 밖에 둔 이유는 임계값 변경을 계산식 변경과 구분하고, 어떤 기준으로 후보를 걸렀는지 기록으로 남기기 위해서다.

## 위반 이유를 숨기지 않는 계산 구조

`evaluate_optimization_candidate_v1`은 효능, 안전, 비용, 복용 부담, 제형을 항상 같은 순서로 살핀다. 결과에는 확인한 다섯 범주, 위반 코드 목록, 선택 가능 여부가 함께 남는다. 안전은 두 갈래다. 후보 전체가 차단 상태인지 보고, 정책의 제외 성분이 후보에 들어왔는지도 따로 판단한다. 복용 부담 역시 제품 수와 하루 복용 단위 두 제한으로 나뉜다.

결과 자료는 원래 후보와 정책에서 다시 계산된다. 누군가 `feasible` 값만 true나 false로 고쳐도 모델 검증을 통과하지 못한다. 성분과 제형의 중복 목록, 숫자가 아닌 값, 무한대와 NaN, 선언하지 않은 추가 필드도 거부한다. 입력 오류를 적당한 기본값으로 바꾸지 않는 이유는 잘못된 제약이 통과 후보를 만드는 것보다 계산을 중단하는 편이 안전하기 때문이다.

## 자동 시험과 기준 증거가 보여 준 범위

`wellnessbox-rnd/tests/test_optimization_constraints.py`는 정상 후보 한 건이 다섯 범주를 모두 기록하고 통과하는지 확인한다. 이어 최소 효과 미달, 안전 차단, 제외 성분 포함, 예산 초과, 제품 수 초과, 하루 단위 초과, 비선호 제형을 각각 넣어 해당 위반 코드가 나오는지 살핀다. 결과값 변조, 중복 목록, 비정상 숫자와 추적되지 않는 필드도 실패해야 한다.

기준 smoke는 정상 후보 한 건과 효능·안전·비용·하루 부담·제형 실패 후보 다섯 건을 실행했다. 정상 후보만 선택 가능했고 나머지는 모두 해당 이유로 제외됐다. 현재 작업에서도 이 시험을 포함한 Python 집중 시험 96개가 통과했다. 구현 전후의 최초 실패 로그는 등록 증거, 계산기, 시험 파일에서 찾지 못했다. 어떤 오류를 먼저 발견해 현재 검증 규칙을 추가했는지는 `확인되지 않음`으로 기록한다.

## 구현 완료 이후에도 남는 간격

OP-061은 요구 단계와 입증 단계가 모두 `IMPLEMENTED`다. 서비스 쪽 상품 조합 경로가 현재 직접 받는 제한은 예산, 최대 제품 수와 안전 제외 목록이다. 최소 효과 점수, 하루 복용 단위, 제형 선호까지 같은 서비스 요청에서 전달되고 실제 상품 조합을 거르는 장면은 이 증거로 확인되지 않는다. 다섯 항목이 하나의 독립 계산 계약에 들어 있다는 사실과, 운영 추천 전체가 그 계약을 쓴다는 주장을 구분해야 한다.

등록 smoke의 소스 결합 지문은 현재 소스 목록의 재계산 값과 같지 않았다. 현재 단위 시험은 통과했지만 기준 smoke를 최신 소스로 다시 생성하지 않았으므로, 정본 JSON의 수치와 최신 파일이 완전히 같은 상태인지는 `확인되지 않음`으로 남는다. 이 제한을 포함해도 저장소에서 정책과 판정기를 재현할 수 있으므로 완료 단계는 `IMPLEMENTED`를 넘지 않는다.
