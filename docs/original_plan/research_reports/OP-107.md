# OP-107 관리자 화면이 데이터, 규칙, 모델, 실행 상태를 실제 API에서 조회한다.

## 결론

OP-107은 `INTEGRATED` 단계까지 확인했다. WellnessBox 관리자 서버 라우트가 별도 프로세스로 실행한 R&D API에서 데이터 적재 상태, KPI 상태, 출처 목록, 규칙 버전, 모델 버전, 실행 상태를 읽는다. 검증 코드는 관리자 인증을 먼저 거치며, 인증이 실패하면 R&D 서버를 호출하지 않는다. 요구 단계는 `OPERATED`이므로 OP-107의 완료 판정은 `PARTIAL`이다. 공개 관리자 화면의 실제 사용, 운영 데이터베이스, 운영 트래픽, 장기 관측은 이번 증거에 포함하지 않았다.

## 요구사항을 어떻게 해석했는가

원문은 관리자 화면이 데이터, 규칙, 모델, 실행 상태를 실제 API에서 조회하도록 요구한다. 단순히 화면용 JSON fixture를 반환하거나 함수의 예상 호출 목록만 확인하면 이 요구를 충족하지 못한다. 따라서 이번 검증은 두 프로세스를 띄웠다. Python 프로세스는 임시 SQLite를 사용하는 실제 FastAPI 애플리케이션을 실행하고, Node 프로세스는 WellnessBox의 `runAdminInterimDashboardRoute`를 실행한다. Node 프로세스는 서비스의 실제 `callWbRndInterim` 클라이언트를 사용해 localhost HTTP 요청을 보낸다.

관리자 상태를 네 부분으로 나눴다. 데이터 상태는 `/v1/interim/status`, KPI는 `/v1/interim/kpis`, 출처는 `/v1/interim/admin/sources`, 규칙·모델·실행 상태는 `/v1/interim/admin/runtime`에서 가져온다. 마지막 API는 이번 루프에서 추가했다. `knowledge_rules`, `safety_rules`, `model_versions`, `executions`, `agent_runs` 테이블을 직접 집계하므로 정적 화면 값이 아니다.

## 구현 내용

R&D 서버의 `/v1/interim/admin/runtime`는 규칙, 모델, 실행을 명시적으로 구분한다. 규칙 응답에는 지식 규칙 수와 상태별 수, 안전 규칙 버전 수와 검토 상태별 수가 들어간다. 모델 응답에는 등록된 모델 버전 수와 상태별 수가 들어간다. 실행 응답에는 실행 수, 실행 상태별 수, 에이전트 실행 수, 에이전트 실행 상태별 수가 들어간다. 빈 테이블도 오류로 취급하지 않고 0과 빈 상태 맵을 반환한다. 관리자는 모델이나 실행이 아직 없다는 사실도 상태로 확인할 수 있다.

서비스 라우트는 상태, KPI, 출처, 런타임 상태를 순서대로 조회한다. 초기 구현에서는 여러 호출을 동시에 실행했지만, 테스트 프로세스의 단일 SQLite 초기화 시점에 `database is locked`가 발생했다. 현재 구현은 단일 컴퓨터와 단일 저장소라는 원래 전제에 맞춰 순차 호출한다. 순차 호출은 응답 시간을 조금 늘리지만, 관리자 조회는 쓰기 중심 사용자 경로가 아니며 초기화 경쟁을 없애는 편이 더 중요하다.

KPI 조회는 별도로 실패 경계를 둔다. 초기 저장소에는 평가 행이 없어 KPI 계산이 실패할 수 있다. 이때 대시보드 전체를 502로 닫으면 데이터·규칙·모델·실행 상태까지 볼 수 없다. 서비스는 KPI만 `{availability: "UNAVAILABLE", error: ...}`로 표시하고 나머지 실제 상태를 계속 반환한다. 알려지지 않은 원인을 성공 값으로 꾸미지 않으며, 관리자가 재시도나 데이터 적재를 결정할 수 있는 명시적 상태를 제공한다.

## 인증과 실패 처리

관리자 라우트는 `requireAdminSession`을 통과한 뒤에만 R&D API를 호출한다. 자동 검증은 인증 실패 응답이 401인지 확인하고, 인증이 실패한 경우 주입한 R&D 호출 함수가 실행되면 즉시 실패하도록 구성했다. 이 검증으로 관리자 권한이 없는 사용자가 내부 상태 API에 도달하지 않는다는 라우트 수준의 불변식을 확인했다.

R&D API 자체도 내부 토큰을 요구한다. 집중 Python 테스트는 토큰이 없는 `/v1/interim/admin/runtime` 요청이 401인지 확인한다. 올바른 내부 토큰으로 호출하면 부트스트랩한 안전 규칙 1개가 `ACTIVE`로 집계되고, 모델과 실행이 없는 임시 저장소는 각각 0으로 보고된다. 서비스 인증과 R&D 내부 인증이 서로 다른 경계에서 적용된다.

## canonical evidence

canonical runner는 버전 관리된 8개 사례 데이터셋을 읽고 임시 SQLite를 생성한다. `bootstrap_operational_evidence`가 출처 어댑터와 안전 규칙을 넣은 뒤 FastAPI를 실제 포트에서 시작한다. 서비스 QA는 실제 HTTP 클라이언트를 사용해 상태, KPI, 출처, 런타임 API를 호출한다. 증거의 `admin_rules_loaded`, `admin_models_state_loaded`, `admin_executions_state_loaded`는 응답에 각 상태가 존재하고 숫자로 직렬화됐는지 확인한다.

증거 파일은 WellnessBox 커밋과 wellnessbox-rnd 커밋을 함께 기록한다. 또한 API 구현, 사례 데이터셋, canonical runner의 Git blob SHA를 기록한다. 따라서 나중에 같은 파일명에 다른 내용이 들어가도 어떤 소스로 증거를 만들었는지 구분할 수 있다. GitHub Actions는 WellnessBox 커밋을 고정해 체크아웃하고, runner를 다시 실행한 결과가 커밋된 증거와 같은지 비교한다.

## 확인 결과와 해석

관리자 인증 거부, 데이터 상태 키, KPI `UNAVAILABLE`, 출처와 어댑터 목록, 안전 규칙 수, 모델 수, 실행 수를 한 번의 서비스 응답에서 확인했다. 이 결과는 관리자 서버 라우트와 R&D API가 실제 HTTP 경계에서 연결됐음을 보인다. 모델 수와 실행 수가 0이라는 값은 기능 부재를 뜻하지 않는다. 임시 저장소에 모델과 실행을 심지 않았다는 현재 데이터 상태이며, API는 그 상태를 숨기지 않는다.

이번 증거가 보여 주지 않는 항목도 분명하다. React 관리자 화면을 브라우저로 렌더링하지 않았다. 공개 주소나 Vercel 배포를 만들지 않았다. 실제 운영 데이터베이스, 운영 관리자 계정, 운영 트래픽을 사용하지 않았다. KPI가 사용 가능한 상태가 되는 실제 평가 데이터 적재도 확인하지 않았다. 따라서 `OPERATED` 또는 그 이상으로 올리지 않는다.

## 재현 방법

R&D 저장소에서 `python scripts/run_admin_product_integration_smoke.py`를 실행하면 된다. runner는 서비스 저장소 위치를 기본값 `C:/dev/wellnessbox`로 사용하며 `WELLNESSBOX_SERVICE_REPO`로 바꿀 수 있다. 집중 API 회귀는 `python -m pytest tests/test_interim_api.py -k admin_runtime -q`로 실행한다. 정적 검사는 `python -m ruff check apps/inference_api/routes/interim.py tests/test_interim_api.py scripts/run_admin_product_integration_smoke.py`로 실행한다.

## 남은 단계

`OPERATED` 판정을 받으려면 승인된 환경에서 관리자 화면을 실제로 열고, 운영과 동등한 데이터베이스에서 규칙·모델·실행 변화가 화면에 반영되는지 관측해야 한다. KPI가 사용 가능한 경우와 사용할 수 없는 경우를 모두 운영 로그와 연결해야 한다. 권한이 다른 계정의 접근 통제, 장애 시 재시도, 장기 지연과 오류율도 기록해야 한다. 이번 루프는 로컬 통합 증거까지만 만들었으며 외부 검증이나 운영 효과를 주장하지 않는다.
## 서비스에 연결할 때 확인한 경계
서비스 통합은 R&D 코드가 존재한다는 사실만으로 끝나지 않는다. 두 저장소의 계약, 인증, 실제 요청·응답, 상품·주문 경계와 상태 환류를 같은 실행에서 확인해야 하며, 승인 전 데이터 변경은 허용하지 않는다.

`OP-107`는 “관리자 화면이 데이터, 규칙, 모델, 실행 상태를 실제 API에서 조회한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox/lib/server/wb-rnd-interim-route.ts`, `wellnessbox/components/tips/InterimRoleConsole.tsx`
- 테스트·실행: `wellnessbox-rnd/tests/test_interim_api.py`, `wellnessbox/scripts/qa/check-rnd-admin-dashboard-roundtrip.cts`, `wellnessbox-rnd/scripts/run_admin_product_integration_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op107_op108_admin_product_integration_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op107_op108_admin_product_integration_smoke_v1.json`, `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-107.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-107.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
