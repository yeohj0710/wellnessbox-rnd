# OP-100 W/C/G 출처별 성공률과 macro 평균을 다시 계산한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/interim/kpi.py`에서 구현과 검증 대상을 확인할 수 있다.

## 결론

기기 연동 성공률을 W, C, G 출처별로 다시 계산하고 세 출처를 같은 비중으로 평균내는 함수를 구현했다. 계산 대상은 호출자가 지정한 하나의 `data_class`로 제한한다. production 지표를 계산할 때 simulation과 proxy 행은 섞이지 않는다. 수신 단계에서 이미 차단한 exact replay는 분모와 분자에 다시 들어가지 않는다.

고정 사례의 고유 production 이벤트는 W 2건 중 2건 성공, C 2건 중 1건 성공, G 1건 중 1건 성공이다. 출처별 성공률은 W 100%, C 50%, G 100%다. macro 평균은 `(100 + 50 + 100) / 3 = 83.33333333333333%`다. 표본 수가 많은 출처가 전체 값을 지배하는 micro 평균을 쓰지 않는다.

OP-100의 기본 요구 단계는 `IMPLEMENTED`다. 계산 함수, 데이터 분류 필터, 중복 제외, 단위 테스트, 실제 API와 SQLite를 사용한 canonical smoke를 갖췄다. 따라서 주장 단계와 요구 단계가 모두 `IMPLEMENTED`이며 완료 판정은 `COMPLETE`다. 다만 계산 완료가 실제 production 성능 달성을 뜻하지는 않는다.

## 전체 성공 건수만 합치면 출처 차이가 사라진다

W/C/G는 서로 다른 입력 경로다. W는 wearable, C는 임상 또는 CGM 계열 입력, G는 유전 정보 계열 입력을 나타낸다. 출처별 요청량이 다르면 전체 성공 건수를 전체 요청 건수로 나눈 값은 표본이 많은 출처의 상태를 주로 반영한다. 예를 들어 W가 1,000건이고 G가 10건이면 G가 모두 실패해도 전체 비율에서는 작게 보일 수 있다.

원계획은 출처별 성공률과 macro 평균을 요구한다. 그래서 먼저 각 출처 안에서 `성공 건수 / 고유 수신 건수 × 100`을 계산한다. 그다음 W, C, G의 세 성공률을 단순 평균한다. 출처별 표본 수는 결과에 함께 남기지만 macro 평균의 가중치로 쓰지 않는다.

## 계산 대상 데이터 분류를 먼저 고른다

`device_linkage_metrics(store, data_class=...)`는 세 데이터 분류만 허용한다.

- `PRODUCTION_DEVICE_SESSION`
- `SIMULATED_DEVICE_SESSION`
- `SIMULATED_INTEGRATION_PROXY`

그 밖의 분류는 `unsupported_device_linkage_data_class`로 거절한다. SQL은 선택한 데이터 분류의 `connector_sessions`만 조회한다. production 계산에 simulation 기록을 섞거나, proxy 평가를 production 수치처럼 표시하는 경로를 막는다.

신규 production·simulation 기기 세션에서는 `deduplicated=0`인 행만 계산한다. 현재 수신 구현은 exact replay를 새 세션 행으로 저장하지 않으므로 이 조건은 방어선이다. 과거 importer가 제공하는 `SIMULATED_INTEGRATION_PROXY`의 `deduplicated` 필드는 실제 API 재수신 표지가 아니라 고정 proxy 자료의 특성값이다. 기존 proxy KPI의 의미를 보존하기 위해 proxy 분류에는 신규 수신 중복 필터를 소급 적용하지 않는다. 처음 구현할 때 이 차이를 무시하자 기존 proxy KPI가 7개 중 6개만 통과했다. 데이터 생성 경로의 의미를 나눈 뒤 신규 운영형 세션에만 중복 제외를 적용해 회귀를 해소했다.

## W, C, G가 모두 있어야 macro를 계산한다

기존 `linkage_macro_rate`는 W/C/G 중 하나라도 없으면 `linkage_requires_w_c_g`로 실패한다. 없는 출처를 0%로 간주하지 않고, 두 출처만의 평균을 세 출처 macro처럼 표시하지도 않는다. 계산에 필요한 세 분모가 모두 관측된 뒤에만 aggregate를 만든다.

각 출처의 성공률은 boolean `success`를 합산해 계산한다. `source_counts`에는 출처별 고유 행 수, `source_rates`에는 백분율, `aggregate`에는 같은 비중의 산술평균을 반환한다. 반환값에는 `aggregation="equal_weight_macro_average"`도 포함돼 후속 보고서가 계산 방식을 추측할 필요가 없다.

## 성공의 뜻은 수신 후조건 전체 통과다

기기 세션의 `success`는 값이 있다는 뜻만이 아니다. 필요한 필드가 모두 있고, 단위가 비어 있거나 `unknown`이 아니며, 시간대가 있고, 출처 레코드 ID가 저장되는 조건을 모두 만족해야 한다. canonical 사례에서 C의 두 번째 이벤트는 단위를 `unknown`으로 보내 실패 표본으로 남겼다. 이벤트 자체는 고유하게 수신됐지만 연동 후조건을 통과하지 못했으므로 C의 분모에는 포함되고 분자에는 포함되지 않는다.

이 구분이 있어야 전송 장애와 데이터 품질 장애를 같은 성공으로 처리하지 않는다. exact replay는 새 관측이 아니므로 분모에서 제외한다. schema 또는 단위 후조건이 실패한 고유 이벤트는 실제 수신 품질을 보여 주므로 분모에 포함한다.

## 고정 사례의 계산을 다시 풀어 보면

W에는 `watch-1`, `watch-2` 두 고유 이벤트가 있고 둘 다 후조건을 통과했다. `watch-1`의 새 세션 재시도는 영수증에서 중복으로 판정돼 새 행을 만들지 않았다. 따라서 W는 2/2, 100%다.

C에는 `clinic-1`, `clinic-2` 두 고유 이벤트가 있다. 첫 이벤트는 성공했고 두 번째 이벤트는 `unit="unknown"`으로 실패했다. 따라서 C는 1/2, 50%다.

G에는 `gene-1` 한 고유 이벤트가 있고 성공했다. 따라서 G는 1/1, 100%다. micro 방식이라면 전체 5건 중 4건 성공이므로 80%다. 하지만 요구된 macro 방식은 출처별 100%, 50%, 100%를 같은 비중으로 평균해 약 83.33%다. canonical evidence는 두 계산 중 macro 값만 요구 결과로 기록한다.

## 검증 결과

단위 테스트는 production 행과 simulation 행을 같은 임시 데이터베이스에 넣고 production 분류만 조회되는지 확인한다. W 2건, C 2건, G 1건의 분모를 확인하고 출처별 비율과 `250/3` macro 평균을 검증한다. 방어적으로 넣은 `deduplicated=1` production 행은 계산에서 제외된다.

canonical smoke는 실제 `/v1/interim/connectors/device` API로 사건을 수신한다. 같은 이벤트의 새 세션 재수신, 충돌 재수신, 세션 재사용을 먼저 검사한 뒤 production W/C/G 행을 조회한다. 관측 결과는 `source_counts={W:2,C:2,G:1}`, `source_rates={W:100,C:50,G:100}`, `macro_rate=83.33333333333333`이다. 저장된 connector 행과 영수증은 각각 다섯 개로 같았다.

## 완료 판정과 해석 제한

OP-100은 계산 구현 요구이므로 `IMPLEMENTED / COMPLETE`다. 이 판정은 production 연동 성공률이 83.33%라고 운영 성과를 선언하는 것이 아니다. 로컬 고정 사례가 production 데이터 분류 경계를 지나 계산됐다는 뜻이다. 실제 운영 지표를 발표하려면 인증된 공급자 트래픽, 관측 기간, 공급자별 표본 수, 재시도 정책, 장애 구간을 함께 제시해야 한다.

운영 대시보드에서는 출처별 분모를 macro 옆에 항상 표시해야 한다. G 표본 한 건의 100%와 W 표본 만 건의 100%는 불확실성이 다르다. 기간 내 한 출처가 0건이면 계산을 실패 상태로 표시하고, 임의로 0%나 직전 값을 채우지 않아야 한다. 이 구현은 그 원칙을 fail-closed 동작으로 남겼다.
## 센서와 유전자 자료를 넣는 기준
센서와 유전자 자료는 많이 넣는 것보다 동의한 자료를 올바른 단위와 시점으로 연결하는 것이 중요하다. 이 그룹은 파일 원본, 출처별 정규화, data_class, 동의, 중복 수신, 실제 점수 반영을 분리해 확인한다.

`OP-100`는 “W/C/G 출처별 성공률과 macro 평균을 다시 계산한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=23`, `docs/context/original_plan.pdf#page=24`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/interim/kpi.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/connectors.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_interim_kpi.py`, `wellnessbox-rnd/scripts/run_device_dedup_linkage_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op099_op100_device_dedup_linkage_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
