# OP-080 연구보고서: 추천 계획의 상태와 실제 주문 상태를 왜 분리했는가

## 같은 “상태 변경”처럼 보여도 서로 다른 일이다

OP-080의 원문은 “상태기계 실행과 실제 주문 상태 변경을 명시적으로 분리한다”이다. 사용자가 추천 계획을 유지하거나 조정하거나 교체한다는 판단과, 쇼핑몰에서 주문을 생성하거나 결제하거나 배송 상태를 바꾸는 일은 화면에서는 이어진 동작처럼 보일 수 있다. 하지만 시스템 책임은 완전히 다르다. 계획 상태는 건강 데이터와 안전 판단, 효과 해석을 바탕으로 다음 행동을 정하는 R&D 결정이다. 주문 상태는 사용자의 명시적인 구매 의사, 재고, 가격, 결제, 약국 처리와 배송을 다루는 상거래 기록이다.

두 상태를 한 함수에서 함께 바꾸면 위험한 일이 생긴다. PRO 점수가 나빠져 계획을 `adjust`로 바꿨다는 이유만으로 결제된 주문을 취소해서는 안 된다. 반대로 주문이 배송 완료됐다고 해서 건강 계획이 자동으로 `maintain`이 되어도 안 된다. 교체 후보를 계산했다는 사실은 새 상품을 주문했다는 뜻이 아니며, 중대한 이상사례로 계획을 멈춘 사실도 이미 발생한 결제 환불이 완료됐다는 뜻이 아니다. OP-080은 이런 의미 혼합을 코드와 증거 양쪽에서 차단하라는 요구사항으로 해석했다.

## 기존 WellnessBox 주문 경로를 먼저 확인한 결과

WellnessBox 서비스 저장소에는 이미 주문 책임을 가진 코드가 있다. `lib/order/orderStatus.ts`는 서비스가 사용하는 주문 상태를 정의하고, `lib/order/mutations.ts`는 `updateOrderStatus` 같은 실제 주문 변경 함수를 제공한다. 장바구니는 별도의 client cart storage 경로를 사용한다. 이 코드는 R&D의 `execution_events`나 plan lifecycle과는 다른 저장소와 비즈니스 규칙을 가진다. 따라서 OP-080을 구현한다는 이유로 R&D 저장소에 주문 테이블을 복제하거나, 기존 서비스 주문 함수를 흉내 내는 adapter를 새로 만드는 것은 요구사항에 반한다.

이번 loop에서는 서비스 기본 worktree에 이미 다른 사용자가 수정 중인 QA 파일이 있었기 때문에 해당 변경을 건드리지 않았다. 서비스 커밋 `4d904f43b028a35524a29206aaf7c6b99f58a97b`의 clean detached worktree를 R&D의 `etc/service-clean-op079` 아래에 만들고, 주문 상태 파일과 `/api/tips` 경로를 읽기 전용 증거로 사용했다. 이렇게 해야 source hash가 사용자 작업 중인 변경에 흔들리지 않고, R&D 구현이 서비스 파일을 수정하지 않았다는 경계도 분명해진다.

## API 계약에서 주문 입력을 받지 않도록 한 방법

`PlanLifecycleTransitionRequestV1`은 허용 필드를 실행 ID, 사용자 ID, 계획 ID, 예상 상태, lifecycle 행동, 이유 코드, idempotency key, 발생 시각과 선택적인 교체 계획 ID로 제한한다. Pydantic 설정은 `extra="forbid"`다. 따라서 `order_id`, `order_status`, `payment_status`, cart나 fulfillment 관련 값은 요청 모델에 들어갈 수 없다. 주문 필드를 받아 놓고 내부에서 무시하는 방식이 아니라, API 경계에서 HTTP 422로 거부한다.

canonical smoke는 모니터링 상태인 계획에 `order_status: "PAID"`를 추가한 요청을 실제 FastAPI 경로로 보냈다. 응답은 HTTP 422였고, 그 요청의 idempotency key를 가진 `execution_events` 행은 0개였다. 이 확인이 중요한 이유는 단순히 응답에 오류가 적혀 있는지만 보는 것보다 강하기 때문이다. 검증 실패가 저장 이후에 일어났다면 잘못된 계획 이벤트가 남을 수 있다. 이번 결과는 주문 필드가 Pydantic 요청 검증에서 먼저 거부되어 계획 장부에도 흔적을 만들지 않았다는 사실을 보여준다.

## 응답이 보장하는 주문 무효과 경계

모든 lifecycle 전이 결과에는 `order_state_effect`가 literal `NONE`으로, `order_state_mutation_allowed`가 literal `False`로 들어간다. 이 값은 호출자가 자유롭게 정하는 문자열이 아니라 `PlanLifecycleTransitionResultV1` 모델이 검증하는 상수다. 유지, 조정, 교체, 중단, 모니터링 다섯 사례가 모두 같은 경계를 반환했다. 교체 전이는 같은 실행에 이미 저장된 추천·최적화 후보의 이벤트 ID와 hash를 확인한 뒤 그 후보만 활성화했지만 주문을 만들지 않았다. 중단 전이는 follow-up과 workflow job을 취소했지만 주문 상태를 바꾸지 않았다.

이 두 필드만으로 주문 분리를 증명했다고 주장하지는 않는다. 문자열은 실제 부작용이 없다는 사실과 함께 확인해야 한다. smoke는 R&D lifecycle 모듈과 API route에서 `updateOrderStatus`, `prisma.order`, `writeClientCartItems`라는 서비스 mutation symbol이 사용되지 않는지 검사한다. 동시에 clean WellnessBox 소스의 `lib/order/mutations.ts`에는 실제 `updateOrderStatus`가 존재하는지 확인한다. 즉 “주문 기능이 어디에도 없다”가 아니라 “주문 변경 기능은 서비스의 기존 책임으로 남아 있고, R&D lifecycle 경로는 그 기능을 호출하지 않는다”는 구조를 증명한다.

## 주문 테이블을 만들지 않은 것이 왜 기능 누락이 아닌가

OP-080을 피상적으로 보면 R&D에도 주문 상태를 저장하고 계획 상태와 비교하는 기능이 필요해 보일 수 있다. 그러나 그 방식은 기존 WellnessBox와 별개인 중복 시스템을 만들지 말라는 전체 목표와 충돌한다. 실제 주문의 진실은 서비스 저장소에 있다. R&D가 필요한 정보가 있다면 향후 인증된 서비스 API로 읽기 전용 snapshot이나 명시적인 사용자 승인 결과를 받아야 한다. R&D가 자체 주문 row를 만들면 결제 취소, 환불, 배송 변경 같은 서비스 규칙을 따라가지 못하고 두 주문 상태가 어긋날 수 있다.

이번 구현은 계획 terminal 전이에서 R&D가 소유한 follow-up과 workflow job만 닫는다. 이 작업은 건강 계획의 후속 실행을 막기 위한 것이며 주문 취소가 아니다. `PLAN_LIFECYCLE_STOPPED`가 job의 `last_error`에 기록되어도 서비스의 주문 status에는 아무 변화가 없다. 교체 행동에서 replacement plan이 `ACTIVE`가 되어도 장바구니 추가나 주문 생성은 일어나지 않는다. 사용자가 실제 상품 변경을 승인하고 주문 절차를 밟는 단계는 별도 서비스 기능으로 남는다.

## source identity와 재현 결과가 말해 주는 것

canonical evidence는 R&D source commit `f0e012d80e48f1fe907162a0fba1dbfae2e1c55d`와 R&D source SHA-256 `d1e3fcab2c81aa6c3489b7d1ab3adce2f1aaf9c6798a99d3f0c0482c5e6bc36c`를 기록한다. 이 source identity에는 lifecycle 서비스뿐 아니라 데이터 정정 방어와 SQLite trigger를 설치하는 저장소 코드도 포함한다. 서비스는 commit `4d904f43b028a35524a29206aaf7c6b99f58a97b`이며, `/api/tips`, 주문 mutation, 주문 상태 파일을 합친 SHA-256은 `eaf5a2a022f010fe807a29c9e3f896a0c9e2fc5eeb9b3107b2d98734539eb7be`다. 두 번의 smoke 결과 파일은 byte-identical했고 SHA-256은 `42984e289301fbe7d5d5740d9b7258554ed7d49ecd3db5e77ace8bb8c3d86bec`로 같았다.

이 source scan은 중요한 정적 증거이지만 실제 서비스 통합 증거는 아니다. 이번 loop에서 WellnessBox `/api/tips`가 새 lifecycle API를 호출하지 않았고, 실제 주문 데이터베이스를 조회하지 않았으며, 주문 mutation도 실행하지 않았다. `actual_order_mutation_executed`와 `production_operation_proven`은 canonical evidence에서 모두 false다. 그 결과는 실패가 아니라 OP-080의 분리 경계를 지킨 결과다. 다만 향후 서비스가 lifecycle API를 호출하게 되면, 새 adapter가 주문 mutation을 몰래 연결하지 않았는지 다시 검증해야 한다.

## 현재 단계와 운영 단계로 가기 위한 조건

현재 증거는 요청 계약, 저장된 lifecycle 이벤트, source boundary, 주문 필드 거부와 부작용 부재를 로컬에서 직접 확인한다. 따라서 OP-080에 대해 주장할 수 있는 단계는 `IMPLEMENTED`다. 그룹 H의 required stage는 `OPERATED`이므로 OP-080은 아직 PARTIAL이다. 서비스 코드 파일을 읽고 hash를 기록한 사실은 `INTEGRATED`나 `OPERATED`가 아니다. 실제 서비스 프로세스와 R&D 프로세스 사이의 인증된 왕복도 없고, 운영 주문에 영향이 없었다는 telemetry도 없다.

운영 증거를 만들려면 먼저 공개 배포와 운영 환경 변경에 대한 사용자 승인이 필요하다. 승인 뒤에는 실제 서비스에서 계획 조정 요청을 보내더라도 주문 row와 결제 row가 바뀌지 않는지 before/after snapshot으로 확인해야 한다. 반대로 사용자가 명시적으로 주문 상태를 변경했을 때 plan lifecycle이 자동으로 바뀌지 않는지도 확인해야 한다. 두 프로세스의 audit log에 서로 다른 actor, endpoint, idempotency key와 저장 대상이 남아야 한다. 그 증거가 생기기 전에는 “주문과 계획이 운영에서도 분리됐다”고 주장하지 않는다.
