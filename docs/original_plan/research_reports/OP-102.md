# OP-102 필수 R&D API군 배포 준비와 로컬 통합 결과

## 결론

health, 추천, 상태기계, 기기, 상담의 다섯 API군이 실제 FastAPI 앱에 모두 mounted됐는지 실행 시점에 검사하는 endpoint inventory를 만들었다. `/health`는 소스 문자열이나 수동 목록이 아니라 `app.routes`에서 method와 path를 읽는다. 하나라도 빠지면 `required_deployment_endpoints_missing`으로 실패한다.

두 개의 독립 localhost 프로세스에서 health, 추천, 기기 API를 실제 HTTP로 호출했다. 상태기계와 상담 API는 내부 토큰을 통과한 뒤 빈 payload에 422를 반환하는지 확인해 라우트와 request validation 경계까지 도달했다. 토큰 없는 interim 요청은 401이었다. 그러나 provider URL에 배포하거나 외부 운영 트래픽을 받지는 않았다. OP-102의 요구 단계는 `OPERATED`, 현재 주장 단계는 `INTEGRATED`, 완료 판정은 `PARTIAL`이다.

## 파일에 endpoint가 있다는 것과 배포된 앱에 있다는 것은 다르다

프로젝트에는 이전부터 각 기능의 route 함수가 있었다. `/health`는 runtime readiness를 반환한다. `/v1/recommend`는 deterministic 추천을 만든다. `/v1/interim/plan-lifecycle/transitions`는 계획 상태를 바꾼다. `/v1/interim/connectors/device`는 W/C/G 기기 이벤트를 수신한다. `/v1/interim/counseling/turns`는 상담 turn을 직렬화하고 검증된 snapshot을 저장한다.

하지만 route 함수가 파일에 존재해도 `FastAPI.include_router`가 빠지거나 prefix가 달라지면 배포 앱에서는 호출할 수 없다. 문서에 적힌 path가 코드 변경 뒤 오래된 값이 될 수도 있다. 그래서 테스트가 파일 텍스트를 찾는 방식만으로는 OP-102의 배포 준비를 증명하기 어렵다.

endpoint inventory는 최종 `app.routes`를 읽는다. router include, `/v1` prefix, HTTP method가 모두 적용된 결과다. 이 목록에서 요구한 method와 path의 쌍을 찾는다. 다섯 쌍이 모두 있을 때만 `COMPLETE`를 반환한다.

## 다섯 API군의 기준 path

health API는 `GET /health`다. 로드밸런서와 운영자가 프로세스 준비 상태를 읽는다. 이번 변경 뒤에는 runtime 파일 준비 상태, 계약 schema와 준비 상태만 담은 공개 요약, 필수 endpoint inventory를 함께 반환한다. DB 경로, 배포 ID, target, 인증 방식, secret-derived 값은 반환하지 않는다.

추천 API는 `POST /v1/recommend`다. 기존 deterministic baseline을 유지했다. canonical smoke는 실제 sample request를 보내 HTTP 200, `status=ok`, `metadata.mode=deterministic_baseline_v1`을 확인한다. 배포 계약을 추가하면서 추천 정책이나 안전 규칙을 바꾸지 않았다.

상태기계 API는 `POST /v1/interim/plan-lifecycle/transitions`다. 내부 토큰이 필요하다. 빈 payload를 올바른 토큰과 함께 보내면 401이 아니라 422가 나온다. 인증 dependency와 route가 모두 실행되고 Pydantic 입력 검증에서 멈췄다는 뜻이다. 이 smoke는 실제 주문 상태를 변경하지 않는다.

기기 API는 `POST /v1/interim/connectors/device`다. 올바른 토큰과 동의 범위, production 데이터 분류를 사용해 이벤트 한 건을 저장했다. 두 번째 프로세스에서 같은 공급자 이벤트를 새 세션 ID로 재전송해 DB 보존과 중복 제거를 함께 확인했다.

상담 API는 `POST /v1/interim/counseling/turns`다. 상태기계 API와 마찬가지로 올바른 토큰과 빈 payload를 보내 422를 확인했다. 상담 생성은 RAG corpus와 추천 실행 identity를 포함하는 별도 복합 기능이므로, 이번 배포 inventory loop에서 가짜 상담 결과를 만들지 않았다. 상담 자체의 canonical 기능 증거는 OP-081~090에 있고, 이번 증거는 최종 앱 mount와 HTTP 도달성에 한정된다.

## inventory는 어떻게 오래된 문서를 막나

각 API군은 method, path, mounted boolean으로 기록된다. canonical JSON으로 정렬한 뒤 SHA-256을 계산한다. 현재 inventory hash는 evidence에 저장된다. path나 method가 바뀌면 hash도 바뀌고 canonical evidence diff가 발생한다.

필수 API가 빠지면 health 응답을 만드는 과정에서 오류가 난다. 단순히 `mounted=false`를 보여 주고 정상 상태를 반환하지 않는다. 로드밸런서가 health 200을 받는데 핵심 API는 없는 상태를 막기 위해서다. 배포 전에 테스트가 같은 함수를 직접 실행하므로 누락 원인을 더 빠르게 찾을 수 있다.

inventory는 인증 토큰이나 DB 내용을 포함하지 않는다. endpoint schema 전체를 공개하지도 않는다. API군의 최소 method와 path, 검증 상태, hash만 반환한다. production에서 OpenAPI 문서가 꺼져 있어도 필수 mount를 확인할 수 있다.

## 실제 HTTP로 확인한 경계

canonical runner는 첫 프로세스가 뜬 뒤 `/health`를 호출한다. 배포 계약 상태는 `READY_FOR_PROVIDER_DEPLOYMENT`, endpoint family 수는 5다. 토큰 없이 interim status를 호출하면 401이다. 올바른 토큰으로 profile과 device endpoint를 호출하면 200이다. 추천 endpoint도 200이며 deterministic mode를 유지한다.

상태기계와 상담 endpoint는 두 번째 프로세스에서 올바른 토큰을 사용한다. 빈 payload이므로 둘 다 422다. 404라면 route가 없고, 401이라면 인증을 넘지 못한 것이며, 422는 해당 route의 입력 모델까지 도달했다는 구분을 smoke가 고정한다.

첫 프로세스가 저장한 connector 행은 두 번째 프로세스의 status API에서 한 건으로 보인다. 재시도 요청은 최초 세션 ID를 반환한다. health와 추천만 떠 있는 무상태 프로세스가 아니라, 인증된 interim API와 영속 저장 경로가 같은 앱에서 연결됐음을 보여 준다.

## 왜 아직 “배포 완료”가 아닌가

localhost subprocess는 integration 증거다. provider가 컨테이너를 실행했다는 증거가 아니다. provider DNS, TLS, private ingress, health check 설정, persistent volume, secret injection, restart policy를 확인하지 않았다. 외부 네트워크에서 다섯 API군을 호출하지도 않았다.

특히 상태기계와 상담은 이번 smoke에서 정상 업무 payload를 실행하지 않았다. 각 기능의 기존 통합 증거를 재사용하고, 이번에는 최종 앱 mount와 인증 후 validation 도달성만 확인했다. provider 배포 뒤에는 승인된 비파괴 staging fixture로 정상 응답까지 확인해야 한다.

`OPERATED`로 올리려면 provider 배포 기록과 일정 기간의 health, 요청 수, 오류율, 인증 실패, DB 쓰기, 프로세스 재시작 결과가 필요하다. 실제 서비스가 R&D URL을 호출하는 OP-103~105 증거도 이어져야 한다. 공개 배포와 환경변수 등록은 승인 없이 수행하지 않는다.

## 회귀 범위

새 코드는 추천 모델, 안전 규칙, 상태 전이, 기기 계산, 상담 답변을 바꾸지 않는다. FastAPI lifespan과 health response에 검증 정보를 더하고 별도 deployment 모듈을 추가했다. 배포 계약 enforcement가 꺼진 기존 local/test 실행은 종전처럼 시작된다. enforcement를 켠 배포만 엄격한 조건을 적용받는다.

집중 테스트는 완전한 계약, 환경·API 활성화·상대 DB·볼륨 선언·짧은 토큰·worker 오류, 실제 mounted route inventory, health 응답을 확인한다. canonical smoke는 두 프로세스와 재시작 DB를 확인한다. frozen 평가와 모델 결과에는 변화가 없어야 한다.

## 현재 판정

필수 다섯 API군의 최종 mount를 기계적으로 검사하고, 독립 프로세스에서 인증·HTTP·재시작 저장을 연결했다. provider 배포와 운영 트래픽은 없으므로 OP-102는 `INTEGRATED / PARTIAL`이다.

Reference basis: tossfeed-easy-finance의 항목별 비교 방식. 다섯 API의 역할과 판정 기준을 먼저 나누고, 200·401·422가 각각 무엇을 뜻하는지 같은 요청 예로 설명하는 전개만 참고했다.
