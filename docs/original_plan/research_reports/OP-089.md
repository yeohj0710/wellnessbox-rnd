# OP-089 연구일지: 공급자 장애가 상담 답변을 중단시키지 않도록 결정론적 복귀 절차를 구현한 과정

## 연구 목적과 요구사항을 해석한 기준

OP-089의 원문은 “provider 장애 시 구조화된 deterministic 답변으로 복귀한다”이다. 여기서 provider는 상담 답변 초안을 만들기 위해 선택적으로 호출하는 외부 언어 모델 공급자를 뜻하고, deterministic 답변은 같은 입력과 같은 근거 자료를 사용하면 매번 같은 내용과 같은 구조가 나오는 답변을 뜻한다. 이 요구사항을 단순히 예외를 잡아 빈 문자열이나 고정 문구를 반환하라는 뜻으로 해석하지 않았다. 건강 상담에서는 외부 공급자가 실패한 순간에도 응급 위험을 먼저 가려내야 하고, 근거가 있는 질문과 근거가 없는 질문을 구분해야 하며, 답변에 사용한 근거와 검증 결과를 기록해야 한다. 따라서 OP-089의 완료 조건은 공급자 호출 실패를 숨기는 것이 아니라, 실패 사실을 구조화해 남기면서도 기존의 근거 검색과 안전 검증을 거친 답변을 안정적으로 반환하는 것이었다.

이 연구에서는 구현, 통합, 운영을 구분했다. 로컬 R&D 응용프로그램에서 공급자 장애를 주입하고 결정론적 답변이 생성되는 것을 확인하면 구현 단계의 근거가 된다. wellnessbox 서비스의 실제 공개 채팅 경로가 운영 환경에서 이 절차를 사용하고 있다는 사실은 별도의 통합 또는 운영 근거가 필요하다. 이번 작업에서는 공개 배포를 실행하지 않았고 운영 자격증명도 사용하지 않았다. 그러므로 OP-089에는 `IMPLEMENTED`만 주장한다. 이 단계 구분은 기능이 존재한다는 사실과 실제 고객 요청이 그 기능을 통과한다는 사실을 혼동하지 않기 위한 것이다.

## 기존 상담 시스템을 조사한 결과

새 상담 엔진이나 별도 이벤트 저장소를 만들지 않았다. 기존 R&D 상담 경로에는 로컬 지식 범위를 읽는 검색기, 질문에서 성분과 약물과 위험 표현을 추출하는 처리기, 근거 문장을 조합해 답변을 만드는 템플릿 생성기, 답변이 허용된 지식 범위와 안전 정책을 지키는지 검사하는 검증기가 이미 있었다. 외부 언어 모델 호출도 이 경로의 선택적 단계로 구현돼 있었다. 상담 API는 기존 `agent_runs`와 `agent_steps`에 한 세션의 답변과 추천 실행을 연결했고, 추천은 기존 `recommendation_runs`를 그대로 사용했다. OP-089에서는 이 경로를 확장해 공급자 실패 정보를 보존하고 재시도 결과를 고정했다. 별도의 fallback 데이터베이스나 두 번째 상담 시스템은 만들지 않았다.

조사 과정에서 답변을 결정하는 입력이 소스 코드 하나가 아니라는 점을 확인했다. `answering.py`는 질문의 범위와 응급 표현을 판정하고 템플릿 답변을 조합한다. `retrieval.py`는 승인된 corpus manifest에서 후보 근거를 검색한다. `verifier.py`는 상담 답변 검증 정책을 적용한다. `runtime_db.py`와 `runtime_knowledge_db_v1.json`은 성분명, 약물명, 위험 표현을 표준화하는 데 관여한다. 상담 지식 범위 registry, 검증 정책, 검색 corpus manifest도 결과를 직접 바꾼다. 따라서 이 파일들을 제외한 소스 해시는 재현 가능한 증거가 될 수 없다. 최종 smoke 증거에는 이 직접 의존 파일을 모두 포함했다.

## 공급자 장애를 표현하는 구조

상담 API 응답에는 `answer_execution` 객체를 추가했다. 이 객체는 어떤 provider가 최종 답변을 만들었는지, 외부 호출을 시도했는지, 왜 fallback으로 전환했는지, 어떤 모델을 요청했는지, 검색된 근거 chunk와 reference가 무엇인지, 외부 호출 실패가 어느 단계에서 발생했는지를 기록한다. 예를 들어 로컬 시험 공급자가 HTTP 503을 반환하면 최종 provider는 `deterministic_template_fallback`, fallback 이유는 `openai_call_failed`, 실패 단계는 `http_request`, 상태 코드는 503으로 남는다. 응급 질문은 외부 공급자보다 안전 절차가 먼저 실행되므로 외부 호출을 시도하지 않으며 fallback 이유는 `urgent_safety_precedence`가 된다.

구조화된 실패 기록은 답변 본문과 분리했다. 사용자가 읽는 상담 문장에 내부 예외나 공급자 응답을 섞으면 불필요한 기술 정보가 노출되고 문장도 불안정해진다. 반대로 실패를 로그에만 남기면 세션 재시도나 증거 감사에서 어떤 경로가 사용됐는지 알기 어렵다. 최종 구조는 답변, 답변 검증 결과, 답변 실행 정보, 추천 실행 정보를 한 binding에 저장한다. 저장된 binding은 `counseling_session_binding_v2`로 버전을 명시했고, canonical JSON 해시를 계산해 이후 응답과 비교할 수 있게 했다.

## 외부 공급자 처리 동의를 추가한 이유

초기 구현은 `WELLNESSBOX_CHAT_ALLOW_LIVE_API=1` 환경변수와 공급자 자격증명이 있으면 외부 호출을 허용했다. 독립 검토에서는 이 조건이 운영자의 기능 설정만 확인하고, 질문 원문을 외부 공급자에 보내는 데 필요한 사용자 동의를 확인하지 않는다는 결함을 발견했다. 건강 질문에는 복용 약물, 질환, 증상과 같은 민감한 내용이 포함될 수 있다. 서비스가 당시 보내던 consent scope는 `simulation:write`뿐이어서 환경변수가 잘못 켜지면 사용자가 외부 처리를 명시적으로 허용하지 않았는데도 질문이 전송될 수 있었다.

수정 후 외부 공급자 호출은 환경 설정과 `counseling:external-provider` 동의가 동시에 있어야 한다. 둘 중 하나라도 없으면 원문 질문을 공급자에 보내지 않고 로컬 결정론적 경로를 사용한다. 회귀 시험에서는 live API 환경변수와 가짜 자격증명을 모두 설정한 뒤 동의 scope를 빼고, 공급자 호출 함수가 실행되면 즉시 시험을 실패시키도록 했다. API는 공급자를 호출하지 않았고 `attempted_live_call=false`, `fallback_reason=live_api_disabled`를 반환했다. 장애 주입 E2E에서는 외부 처리를 시험하려는 목적을 분명히 하기 위해 서비스 시험 클라이언트가 `counseling:external-provider`를 명시적으로 보낸다. 이 scope는 로컬 시험 동의이며 실제 운영 동의가 수집됐다는 근거로 사용하지 않는다.

## 같은 turn 재시도의 멱등성을 보장한 과정

상담 요청은 네트워크 재전송이나 브라우저 재시도로 같은 turn이 여러 번 도착할 수 있다. 첫 구현은 저장된 step을 먼저 조회하고, 같은 요청이 이미 있으면 저장된 답변을 반환했다. 순차 재시도에는 충분했지만 두 요청이 거의 동시에 들어오면 둘 다 저장 전 상태를 보고 외부 공급자를 따로 호출할 수 있었다. 외부 공급자의 출력이 비결정적이면 두 호출자가 서로 다른 답변을 받을 수 있고, 그중 하나만 데이터베이스에 남을 수 있었다. 최종 insert에서 중복을 발견하더라도 늦은 요청이 자신이 새로 만든 미저장 답변을 반환했던 것도 문제였다.

첫 번째 수정에서는 동일한 profile, session, turn 조합을 프로세스 내부 lock으로 직렬화하고, 데이터베이스에서 중복을 발견하면 새 계산 결과가 아니라 이미 저장된 binding을 반환하도록 했다. 이 수정은 하나의 Python 프로세스에서는 공급자 호출을 한 번으로 제한했다. 그러나 R&D 설정은 최대 네 개 worker를 허용하므로 프로세스 메모리의 lock만으로는 충분하지 않았다. 독립 재검토가 이 경계를 다시 지적했고, 두 worker가 같은 turn을 처리하면 공급자를 두 번 호출할 수 있다는 사실을 Important 결함으로 남겼다.

최종 구현은 프로세스 내부 lock과 프로세스 간 파일 lock을 함께 사용한다. 데이터베이스 경로마다 고정된 `.counseling-turns.lock` 파일을 두고, profile, session, turn의 canonical 해시에서 정한 byte 범위를 잠근다. Windows에서는 `msvcrt.locking`을, POSIX 계열 환경에서는 `fcntl.lockf`를 사용한다. 서로 다른 turn은 다른 byte 범위를 사용할 가능성이 높아 병렬 처리할 수 있고, 같은 turn은 worker가 달라도 반드시 같은 범위를 기다린다. 잠금을 얻은 worker만 기존 저장 여부를 다시 확인하고 필요할 때 공급자를 호출한다. 완료 후에는 OS 잠금을 해제하고 파일 handle을 닫는다. 프로세스 내부 lock map은 참조 수를 관리해 대기자와 실행자가 모두 사라지면 key를 제거하므로 처리한 turn 수만큼 메모리가 계속 증가하지 않는다.

프로세스 간 잠금은 실제로 두 개의 별도 Python 프로세스를 시작하는 회귀 시험으로 확인했다. 두 프로세스는 같은 데이터베이스 경로와 같은 상담 turn을 사용하고 동시에 시작한 뒤, 잠금 구간의 진입 시각과 종료 시각을 기록한다. 먼저 진입한 프로세스가 잠금을 해제한 뒤에만 두 번째 프로세스가 진입하는지 비교한다. 같은 프로세스 안의 동시 요청 시험에서는 두 요청을 thread pool로 동시에 보내고 공급자 호출 횟수가 정확히 한 번인지, 두 응답의 답변과 session binding 해시가 같은지, 한 응답만 최초 실행이고 다른 응답은 deduplicated 재사용인지 확인한다.

## 질문 범위 판정에서 발견한 잘못된 근거 연결

frozen QA를 만들면서 “Can this supplement cure cancer?”라는 질문이 로컬 corpus의 수면 관련 chunk를 선택하는 문제가 드러났다. 원인은 supplement처럼 거의 모든 보충제 질문에 등장할 수 있는 일반 단어가 질문과 근거의 관련성을 성립시키는 데 사용됐기 때문이다. 이렇게 선택된 chunk는 질문의 치료 주장을 뒷받침하지 않지만, 단순 키워드 점수만 보면 후보로 남을 수 있었다. 이 문제를 특정 cancer 문자열에 대한 예외 처리로 고치지 않았다.

공통 원인은 일반적인 대명사와 범주어가 실제 건강 주장과 성분을 식별하는 단어처럼 취급된 데 있었다. 관련성 판정에서는 supplement와 this 같은 일반 token만으로 근거 일치를 인정하지 않도록 바꿨다. cure, treat, diagnose처럼 근거가 없으면 위험한 의료 주장을 명시하는 동사는 질문을 건강 상담 범위 안의 미지원 주장으로 분류한다. 따라서 이 질문은 날씨처럼 상담 범위 밖 질문이 아니라, 상담 범위에는 들어오지만 로컬 근거가 없어 사실로 말할 수 없는 `unsupported` 답변을 반환한다. 관측된 오류를 한 문장만 통과시키는 방식이 아니라 동일한 유형의 잘못된 근거 연결을 막는 불변식으로 수정했다.

날씨 질문도 별도로 확인했다. 영어의 be 동사가 남아 건강 문장과 우연히 일치하는 문제를 없애기 위해 의미 없는 일반 동사를 검색 token에서 제외했다. “What will the weather be tomorrow?”는 근거 chunk를 사용하지 않고 `out_of_scope` 답변을 반환한다. 미지원 건강 주장과 범위 밖 질문을 구분함으로써 사용자는 답할 수 없는 이유를 더 정확히 알 수 있고, 검증기는 서로 다른 안전 규칙을 적용할 수 있다.

## 장애 주입과 결정론 증거를 만든 방법

canonical smoke는 인터넷의 실제 공급자 상태에 의존하지 않는다. 로컬 HTTP 서버를 열어 모든 공급자 요청에 의도적으로 503을 반환한다. 별도의 포트에서 실제 FastAPI 응용프로그램을 uvicorn으로 시작하고, wellnessbox 저장소의 실제 TypeScript R&D 클라이언트가 HTTP로 상담 endpoint를 호출한다. 시험용 SQLite 데이터베이스는 매 실행마다 새로 만든다. 여덟 개 frozen 질문을 한 번씩 실행한 뒤 같은 요청을 다시 보내 순차 재시도도 확인한다. 응급 사례를 제외한 일곱 건에서만 공급자 요청이 발생해야 하며, 재시도에서는 추가 공급자 요청이 없어야 한다.

초기 smoke는 사례별 status와 chunk ID 같은 축약 결과만 비교했다. 독립 검토는 이 비교가 답변 문장이 달라져도 `normalized_runs_byte_identical=true`가 될 수 있다고 지적했다. 최종 smoke는 각 사례의 전체 `answer_text`, canonical answer SHA-256, 전체 verifier 결과, answer execution 정보를 비교한다. 추천 실행의 무작위 run ID는 결정론적 답변과 무관하므로 status와 simulation 여부만 정규화한다. 두 개의 새 데이터베이스와 두 개의 새 API 프로세스를 사용해 전체 실행을 반복했고, 정규화한 결과가 byte-identical인지 확인했다. 최종 canonical 증거 자체도 두 번 생성해 파일 SHA-256이 같은지 비교했다.

실행 결과 여덟 사례의 답변과 검증 결과가 모두 일치했다. 일곱 비응급 사례는 한 번째 실행에서만 503 공급자 호출을 시도하고 로컬 템플릿으로 복귀했다. 응급 흉통·호흡곤란 사례는 공급자를 부르지 않고 즉시 응급 안내를 반환했으며 추천 실행도 만들지 않았다. 데이터베이스에는 agent run 여덟 건, 상담 answer step 여덟 건, 비응급 추천 run 일곱 건이 저장됐다. 같은 turn을 다시 보낸 응답은 모두 저장된 binding을 재사용했고 binding 해시가 최초 응답과 같았다.

## 재현 가능한 source identity와 증거의 한계

증거 파일의 source identity는 현재 working tree의 파일을 직접 읽어 해시하지 않는다. 커밋된 Git blob을 읽어 SHA-256을 계산하고, 관련 경로의 마지막 소스 커밋을 기록한다. 이렇게 해야 smoke를 실행한 뒤 문서를 수정하거나 working tree에 다른 변경이 생겨도 어떤 소스가 결과를 만들었는지 분명하다. R&D 쪽에는 API route, 답변 생성기, 외부 공급자 adapter, 검색기, 검증기, runtime knowledge loader, interim store, frozen dataset, corpus manifest, scope registry, verifier policy, runtime knowledge DB가 포함된다. 서비스 쪽에는 실제 TypeScript client와 frozen E2E runner가 포함된다.

이 증거는 로컬에서 주입한 공급자 장애에 대한 구현 근거다. 실제 OpenAI 또는 다른 외부 공급자의 운영 장애를 관측한 자료가 아니고, production 트래픽의 복구 시간이나 성공률을 측정하지 않았다. 외부 공급자 동의가 실제 서비스 화면에서 수집된다는 사실도 증명하지 않는다. 서비스의 `/api/chat` route와 Prisma 데이터베이스를 통과하지 않았으며 공개 배포도 하지 않았다. 따라서 이번 결과를 운영 복원력, 실제 개인정보 처리 동의, 서비스 전체 통합의 증거로 확대하지 않는다.

## 결론과 현재 단계

OP-089에서는 기존 상담·검색·검증·추천 저장 경로를 유지하면서 공급자 실패를 구조화하고, 명시적 외부 처리 동의를 강제하고, 같은 turn의 순차·동시·multi-worker 재시도를 하나의 저장된 답변으로 수렴시켰다. 장애 시 반환되는 답변은 단순 고정 문구가 아니라 승인된 로컬 근거, 응급 우선순위, 미지원 주장 억제, 답변 검증을 모두 거친 결과다. 두 개의 독립 실행에서 전체 답변과 검증 결과가 동일했고 source identity도 직접 의존 파일까지 포함한다.

현재 증거로 주장할 수 있는 단계는 `IMPLEMENTED`다. 이 단계는 OP-089가 요구하는 기본 구현 단계와 일치한다. 다만 운영 공급자의 실제 장애 대응, 공개 서비스 route 통합, 실제 사용자 동의 수집, production 데이터베이스 저장은 확인하지 않았다. 후속 요구사항이나 운영 승인 절차에서 그 증거가 생기기 전에는 `INTEGRATED` 또는 `OPERATED`로 올리지 않는다.
