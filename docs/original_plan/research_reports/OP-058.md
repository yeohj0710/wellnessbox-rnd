# OP-058 추천 성분과 관찰 효과 계보를 같은 계획 ID로 연결한다.

## 추천, 실행, 시작 점수, 추적 효과가 하나의 계획 ID를 공유해야 한다

OP-058은 추천 성분을 만든 기록과 그 뒤 관찰한 PRO 변화를 `plan_id`로 연결하도록 요구한다. 추천 응답, 최적화 이벤트, 실행 계획, 시작 평가, 추적 평가, 수정·재계산 결과가 서로 다른 계획을 가리키면 효과 계보를 만들지 않는다. 이 연결은 “성분이 효과를 일으켰다”는 인과 증명이 아니라, 어떤 추천 계획을 실행한 뒤 어떤 관찰값이 기록됐는지 추적하는 데이터 계보다.

매니페스트가 지정한 연구 구현은 `wellnessbox-rnd/src/wellnessbox_rnd/metrics/pro_correction.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/data_lake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`, `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/recommendation_service.py`다. 제품 통합 경로는 `wellnessbox/lib/server/wb-rnd-interim-route.ts`, plans/effects API route에 있다. 연구 저장소 안에서만 같은 문자열을 쓰는 수준이 아니라 제품의 계획 생성과 추적 요청도 동일한 계획 식별자를 전달해야 한다.

기능 도입 전에는 추천·최적화 이벤트와 PRO 관찰을 계획 ID로 끝까지 묶는 불변조건이 없었다. 추천 성분 목록과 점수 변화가 각각 존재해도 어느 실행 계획의 결과인지 기계적으로 확인할 수 없었다. 초기 구현 뒤에는 암시적으로 계산한 계획 ID가 원래 요청에 없던 필드로 직렬화되어 입력 정체성이 달라지는 문제가 별도로 발견됐다.

## 추천 요청이 계획 ID를 정하고 원장이 응답과 이벤트를 대조한다

`RecommendationRequest.resolve_plan_id`는 호출자가 계획 ID를 주면 그 값을 사용하고, 생략하면 `request_id`의 SHA-256 앞 32자에 `plan_` 접두사를 붙여 결정적 ID를 만든다. 요청 직렬화는 호출자가 `plan_id`를 생략했으면 계산된 값을 다시 요청 필드로 내보내지 않아 원래 입력 형태를 보존한다. `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/recommendation_service.py`는 정상 추천과 차단 응답 모두에 내부에서 해석한 `plan_id`를 넣는다. 같은 `request_id`에서는 같은 계획 ID가 계산되므로 서비스 결과와 이후 실행 계보가 안정적으로 이어진다.

`ExecutionLedger.record_recommendation`은 요청 계획 ID와 추천 응답 계획 ID가 다르면 저장을 거부한다. 일치하면 추천 이벤트와 최적화 이벤트 양쪽에 같은 계획 ID를 기록하고, 최적화 이벤트에는 실제 선택된 성분 키를 보존한다. `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/pro_plan_service.py`의 `enroll_pro_plan_v1`은 이 추천 결과로 실행을 등록하고 같은 계획에 시작 평가를 정확히 하나 연결한다. `record_or_correct_pro_followup_v1`은 이후 추적 생성과 같은 시점 수정에서도 저장된 시작 분포와 계획을 재사용하며, 다른 계획이나 다른 평가 도구의 점수를 섞으면 실패한다.

`PRORecommendationEffectLineageV1`은 실행·계획·추천·최적화 이벤트 식별자, 선택 성분 키, 시작·추적 평가 식별자를 한 구조로 반환한다. `PROCorrectionRecalculationResultV1`은 수정 기록과 새 해석에 이 계보를 붙인다. 모델 검증은 모든 하위 객체의 `plan_id`를 다시 대조하고 인과 해석을 금지한다. 따라서 응답에 계획 ID 문자열만 우연히 같게 넣고 원장 이벤트가 다른 계획을 가리키는 상태는 유효한 계보가 아니다.

## 직렬화와 재시도에서 계획 정체성을 잃던 두 경계가 수정됐다

커밋 `12c984b`은 추천·최적화 이벤트와 PRO 계획을 같은 ID로 묶는 초기 구현을 추가했다. 초기 모델은 호출자가 `plan_id`를 생략해도 검증기가 계산한 값을 요청 직렬화에 새 필드처럼 포함했다. 커밋 `e09831e`은 호출자가 계획 ID를 직접 제공했는지 별도 상태로 기억하고, 암시적으로 계산한 값은 요청 직렬화에서 제외하도록 고쳤다. 서비스 내부와 응답은 계산된 계획 ID를 계속 사용하되, 직렬화된 요청은 원래 호출 입력의 의미를 보존한다.

커밋 `c1bb470`은 등록과 추적 수정의 재시도에서 기존 실행과 시작 평가를 재사용하도록 했다. 커밋 `86823c3`은 같은 재시도 키로 다른 시작 평가 식별자를 제출하는 요청을 기존 계획에 합치지 않고 충돌로 거부했다. OP-057의 커밋 `c8c0767`은 추천·최적화 이벤트가 없을 때 효과 재계산이 실패하면서 수정만 저장되는 문제를 막아, OP-058 계보 검증도 수정 원장보다 먼저 완료되게 했다.

제품 저장소의 커밋 `252041d`는 plans/effects route, 사용자용 연구 client, 화면 흐름을 연결했고, `d4c197e`는 사용자 동작에서 안정적인 요청 식별자를 만들었다. 후속 `f545b83`은 추적 요청에서도 서버가 확정한 연구 프로필 가명을 유지했다. 계획 ID 계보와 프로필 가명은 다른 식별자이지만, 둘 중 하나가 호출 사이에 바뀌어도 같은 사용자 계획의 종단 추적을 신뢰할 수 없으므로 각 경계에서 따로 보존한다.

## 테스트는 계획 불일치, 등록 재시도, 추적 교차 연결을 차단한다

`wellnessbox-rnd/tests/test_data_lake_lineage.py`의 `test_recommendation_and_optimization_events_retain_plan_id`에서는 추천·최적화 이벤트가 같은 계획 ID와 선택 성분 키를 보존해야 한다. `test_record_recommendation_rejects_response_plan_mismatch`는 요청과 응답의 계획이 다를 때 원장 기록을 허용하지 않는다.

`wellnessbox-rnd/tests/test_pro_plan_service.py`의 `test_enrollment_persists_one_bound_baseline_and_core_plan_ids`에서는 등록 시 실행, 추천, 최적화, 시작 평가가 하나의 계획에 묶이고 시작 평가는 한 건이어야 한다. `test_followup_rejects_cross_plan_and_cross_instrument`는 추적 입력이 다른 계획이나 도구의 시작 분포를 사용할 수 없게 한다. `test_enrollment_retry_reuses_execution_and_baseline`은 같은 요청의 재시도가 기존 계보를 재사용하는지 확인하고, `test_enrollment_retry_rejects_changed_baseline_identity`는 시작 평가 정체성이 바뀐 재시도를 거부한다. OP-057의 `test_user_correction_recalculates_effect_and_links_recommendation_plan`은 수정 뒤에도 추천 계획 연결이 유지되는지 보완한다.

현재 점수·추적·집단효과·계획 서비스 핵심 네 파일에서 수집된 79개 테스트는 모두 통과했다. 매니페스트에 연결된 계보·수정 원장 파일까지 포함한 실행에서는 106개 중 104개가 통과하고, 정식 증거가 데이터베이스 스키마 14를 기록한 반면 현재 코드가 15를 요구하는 감사 테스트 2개가 실패했다. 계획 연결 기능의 계산 실패는 아니지만 등록 증거 전부가 현재 스키마와 일치한다는 주장은 할 수 없다.

## 통합 스모크는 한 계획에서 추천 성분과 수정 효과를 왕복했다

`wellnessbox-rnd/data/original_plan/evidence/op057_op058_pro_correction_plan_lineage_smoke_v1.json`은 로컬 연구 API와 제품 TypeScript 서버 helper를 HTTP로 연결해 계획 등록, 추적 생성, 같은 시점 수정을 실행했다. 기록된 계획 ID는 `plan_0974bca3a038aabfccd5f5ccc0ed9b8b`이고 선택 성분은 `magnesium_glycinate`, `l_theanine`이다. 시작 원점수 10, 첫 추적 8, 수정 추적 7이 같은 실행과 계획에 남으며, 추천·최적화 이벤트와 시작·추적 평가 식별자가 `PRORecommendationEffectLineageV1` 결과에 함께 기록됐다.

이 JSON의 생성 시점 단계는 통합이며 인과 해석은 허용하지 않는다. 합산 소스 해시 `04d6548…`는 현재 등록 경로의 재계산 값 `611873ea…`와 다르다. 기록된 연구·제품 커밋은 각각 `a5a6908`, `a24b6c`이고 관련 경로에는 `651984d`, `f545b83`까지 후속 변경이 있다. 따라서 계획 계보를 실제 HTTP로 재현한 시점 증거는 남아 있지만, 저장된 해시를 현재 소스의 다이제스트로 사용할 수 없다. 현재 연구 핵심 테스트와 제품 route/client QA 통과는 후속 코드에 대한 별도 검증이다.

## 직접 확인한 단계는 INTEGRATED이며 운영 영수증은 구체 계보를 담지 않는다

매니페스트는 OP-058의 요구 단계와 주장 단계를 `OPERATED`로 기록한다. `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-058.json`은 `wellnessbox-local-research-pc`의 `ACTUAL` 세션 `local-20260724T010245964049Z`에서 프로필 또는 설문, 추적, 약사 검토 경로가 실행됐고 `followups`가 1 증가했음을 기록한다. 파일의 존재는 매니페스트 스키마의 운영 경로 형식을 충족하지만, 영수증 내용은 OP-058의 계획 계보를 직접 식별하지 않는다.

영수증에는 실제 이벤트의 `plan_id`, 추천 이벤트 ID, 최적화 이벤트 ID, 선택 성분 키, 시작·추적 `assessment_id`가 없다. `recommendation_runs`, `recommendation_items`, `pro_observations` 증가량도 모두 0이다. 따라서 한 운영 세션에서 일반 추적 경로가 실행됐다는 사실은 확인하지만, 추천 성분부터 관찰 효과까지의 구체 계보가 그 세션에서 사용됐다고 볼 수 없다. 구체 연결은 합성 로컬 HTTP 스모크가 `INTEGRATED`까지 증명한다. 스모크 자체도 OP-058의 입증 단계는 `INTEGRATED`, 요구 단계는 `OPERATED`라고 구분한다.

따라서 직접 확인되는 현재 단계는 `INTEGRATED`다. 프로덕션 데이터베이스의 종단 계보, 장기간 재시작과 마이그레이션 뒤 연결 보존, 동시 계획과 동시 수정, 실제 사용자·브라우저 경로, 외부 연구기관 검토, 추천 성분의 임상 인과 효과는 검증되지 않았다. `OPERATED`로 올리려면 가명 계획 ID, 추천·최적화 이벤트 ID, 선택 성분 키, 시작·추적 평가 ID와 저장 시각을 한 실제 세션 영수증에 연결해야 한다.
