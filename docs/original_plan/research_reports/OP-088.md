# OP-088 서비스 채팅이 R&D 상담 API를 호출하는 얇은 어댑터를 사용한다.

## 구현 결과부터 설명하면

WellnessBox의 기존 `/api/chat` 경로가 기능 플래그가 켜진 경우 R&D의 `/v1/interim/counseling/turns`를 호출하도록 연결했다. 서비스는 상담 지식을 다시 검색하거나 답변을 자체 규칙으로 조립하지 않는다. 서비스가 담당하는 일은 사용자와 세션의 소유권을 확인하고, 원래 식별자를 가명화하고, 기존 채팅 입력을 버전이 고정된 R&D 요청으로 바꾸고, R&D 응답 계약을 검사하고, 검증된 답변을 기존 채팅 세션에 저장해 스트리밍하는 것이다. 상담 범위, 검색, 응급 우선순위, 근거 연결, 답변 verifier와 추천 안전 판단은 R&D가 계속 소유한다.

이 경계를 실제 코드와 두 프로세스 호출로 확인했다. canonical smoke가 localhost에서 실제 FastAPI 애플리케이션을 실행하고, WellnessBox 저장소에 있는 실제 TypeScript 어댑터를 Node.js로 호출했다. 그러나 독립 검토 결과 이 smoke는 `/api/chat` route와 Prisma 저장 함수를 실행하지 않고 어댑터 함수를 직접 호출한다. 따라서 두 저장소의 HTTP 계약은 실제로 연결됐지만 “서비스 채팅 전체 경로가 통합됐다”는 required stage까지 증명하지 못한다. OP-088의 현재 주장은 `IMPLEMENTED`이며 required `INTEGRATED`보다 낮으므로 PARTIAL이다.

## 얇은 어댑터가 지켜야 하는 책임 경계

“얇다”는 코드 줄 수가 적다는 뜻이 아니다. 서비스가 R&D의 연구 판단을 복제하지 않고 전달과 검증에 필요한 책임만 가진다는 뜻이다. 서비스가 glucosamine과 warfarin의 위험을 자체 상수로 넣거나, R&D 답변이 실패했을 때 다른 근거 검색기로 비슷한 답변을 만들면 두 시스템의 정책이 갈라진다. 한쪽 정책만 갱신됐을 때 같은 질문이 호출 경로에 따라 다른 답을 낼 수도 있다. 이번 구현에서는 그런 중복 판단을 넣지 않았다.

어댑터는 기존 `lib/server/wb-rnd-interim-client.ts`를 확장했다. 이 파일은 이미 R&D interim base URL, 내부 토큰, timeout, feature flag, 허용 경로와 가명화 salt를 관리하고 있었다. 상담 전용 generic fetch 모듈을 새로 만들지 않았다. `callWbRndCounselingTurn`은 기존 `callWbRndInterim`에 `/v1/interim/counseling/turns`와 POST body를 넘긴다. 따라서 URL protocol 제한, `/v1/interim/` 하위 경로 제한, `..`와 이중 slash 거부, 500~15000ms timeout, `cache: no-store`, 내부 토큰 전달과 비정상 status 처리를 그대로 재사용한다.

R&D 응답을 TypeScript 타입으로 단언하는 것만으로는 런타임 안전이 생기지 않는다. 그래서 `validateCounselingTurn`이 실제 JSON을 검사한다. 스키마 버전이 `counseling_turn_response_v1`인지, answer가 비어 있지 않은 문자열인지, verifier가 실제 boolean true인지, 서비스 세션 ID와 turn ID가 문자열인지, agent run ID와 결합 해시가 있는지 검사한다. 추천 실행이 null이 아니면 run ID, 상태와 simulation 표시의 자료형을 확인한다. 하나라도 맞지 않으면 `WB_RND_COUNSELING_invalid_contract`를 던지고 답변을 사용자에게 정상 상담 결과처럼 내보내지 않는다.

## 기존 채팅 요청을 R&D 계약으로 바꾸는 과정

기존 `runChatPostRoute`는 요청 JSON과 actor를 병렬로 읽는다. actor는 로그인 사용자라면 `appUserId`, 익명 사용자라면 device client ID를 가진다. 기존 검사는 로그인 상태인데 app user ID가 없거나, 익명 상태인데 client ID가 없는 요청을 거부한다. 새 경로도 이 검사를 우회하지 않는다.

`withPatchedChatBody`가 기존 메시지와 질문을 정규화한 다음, `runRndCounseling`이 실제 서비스 세션 ID와 마지막 user 메시지를 읽는다. 세션 ID나 사용자 질문이 없으면 R&D를 부르지 않고 기존 채팅 경로를 유지한다. R&D feature flag가 꺼져 있어도 기존 LangChain 채팅이 그대로 동작한다. 따라서 이번 통합은 별도의 `/chat-rnd` 화면이나 두 번째 채팅 제품을 만들지 않고 현재 사용자가 쓰는 `/api/chat` 안에 들어간다.

profile ID는 app user ID나 device client ID를 그대로 보내지 않는다. 기존 interim pseudonym salt로 HMAC-SHA256을 계산하고 앞의 32자리만 `usr_` 뒤에 붙인다. 이 함수는 로그인 사용자만 받던 기존 `pseudonymizeInterimUserId`를 일반 subject 함수로 확장했고, 기존 함수는 새 함수에 위임한다. 기존 호출자의 결과 형식은 바뀌지 않는다.

건강 목표는 서비스 profile의 `goals`를 우선 사용하고, 없으면 기존 local assessment category를 사용한다. 둘 다 없으면 `general_wellness`를 넣는다. 이 값은 R&D의 interim 추천 입력이며 임상 진단을 새로 추론한 값이 아니다. 서비스가 명시적으로 제공한 ingredients와 safety 객체도 그대로 전달한다. turn ID가 요청에 있으면 유지하고, 없으면 세션 ID와 질문을 SHA-256으로 묶어 32자리 결정적 ID를 만든다. 같은 세션에서 같은 질문을 재시도하면 같은 turn으로 취급된다.

답변 시각은 요청에 `answeredAt`이 있으면 사용하고 없으면 서버의 현재 ISO 시각을 사용한다. R&D는 시간대 없는 값을 거부한다. 답변의 근거 유효성은 이 시각을 기준으로 계산되기 때문에 서비스와 R&D가 서로 다른 암묵적 날짜를 사용하는 문제를 막는다. 후속 구현에서는 서비스가 요청을 처음 받은 시각을 명시적으로 고정해 재시도 간 시각까지 완전히 동일하게 만드는 것이 더 안전하다.

## R&D 호출 뒤 서비스가 하는 일

어댑터 응답이 계약 검사를 통과해도 서비스는 요청한 `sessionId`와 반환된 `service_session_id`, 요청한 turn ID와 반환된 `turn_id`를 다시 비교한다. R&D가 다른 세션의 정상적인 응답을 잘못 반환하는 경우에는 타입 검사가 모두 통과할 수 있기 때문이다. 이 교차 검사에서 다르면 저장과 스트리밍을 중단한다.

일치한 응답은 OP-087에서 설명한 `persistRndCounselingTurn`으로 기존 Prisma 세션에 저장한다. 저장이 끝난 다음 작은 async generator가 R&D의 `answer_text` 하나를 기존 text stream으로 내보낸다. 클라이언트는 기존 응답 형식을 그대로 받기 때문에 별도 상담 UI나 새 transport protocol이 필요하지 않다. 기능 플래그가 꺼져 있거나 세션·질문 조건이 맞지 않으면 기존 `streamChat`의 token stream을 사용한다.

현재 R&D 호출이 실패한 경우 기존 언어 모델로 조용히 우회하지 않는다. catch 경계는 기존 안전 오류 문장을 스트림에 내보낸다. provider 장애 시 검증된 deterministic 답변으로 돌아가는 정확한 정책은 OP-089의 요구사항이다. 이번 loop에서 임의 fallback을 넣으면 OP-089의 실패 종류, 증거 상태와 응급 우선순위를 먼저 결정해 버릴 수 있으므로 범위를 넘지 않았다.

## 계약 시험과 실제 프로세스 검증

서비스의 `check-rnd-counseling-adapter.cts`는 전역 fetch를 통제해 어댑터가 정확히 `http://127.0.0.1:8765/v1/interim/counseling/turns`로 POST하는지, 서비스 세션 ID가 body에 보존되는지 확인한다. 정상 응답에서는 답변과 추천 run ID를 읽을 수 있어야 한다. 가명화 결과는 `usr_`와 32자리 16진수 형식을 만족해야 한다. verifier가 false인 응답은 HTTP 200이어도 invalid contract로 거부하는 negative probe도 포함했다.

실제 통합 smoke는 이 mock을 사용하지 않는다. Python 스크립트가 임시 SQLite 파일을 만들고 Uvicorn으로 `apps.inference_api.main:app`을 실행한다. health endpoint가 준비됐는지 polling한 뒤 WellnessBox 저장소를 작업 디렉터리로 삼아 `node --conditions=react-server --import tsx scripts/qa/run-rnd-counseling-live-smoke.cts`를 실행한다. 이 Node 스크립트는 production 어댑터 함수를 직접 import하고 실제 HTTP 요청을 보낸다. 호출이 끝나면 SQLite의 `agent_runs`, `agent_steps`, `recommendation_runs`를 별도 프로세스로 조회한다.

질문은 “What should counseling say about glucosamine with warfarin?”이었다. R&D는 승인된 interaction reference를 찾아 `supported` 답변을 만들고 verifier의 모든 항목을 통과했다. 추천 쪽에는 임신 안전 입력을 주어 기존 R&D 안전 판단이 모델 호출 전에 차단하도록 했다. 추천 실행은 `rec_` 형식의 실제 run ID를 가졌고 상태는 `BLOCKED`, simulation은 true였다. SQLite에는 agent run, 상담 answer step, recommendation run이 각각 한 건 있었다. 서비스 세션 ID와 turn ID는 요청값과 같았다.

smoke 스크립트는 임시 데이터베이스를 바꿔 두 번 실행하고 UUID처럼 실행마다 달라져야 하는 값은 형식 검사로 정규화했다. 상담 답변 본문 SHA-256, 답변 상태, verifier 결과, 추천 상태, simulation 표시, 세 테이블 수, 세션 및 turn ID를 비교했다. 두 결과는 byte-identical이었다. canonical 증거에는 R&D와 서비스의 실제 source commit과 일곱 개 핵심 파일 SHA-256을 포함했다. cached `origin/main`이나 작업 의도를 source identity로 사용하지 않았다.

서비스 정적 검증도 함께 수행했다. 새 세 파일과 QA 스크립트에 ESLint를 실행했고 오류가 없었다. 전체 TypeScript `npx tsc --noEmit`이 통과했다. `npm run build`도 성공했다. build의 preflight는 encoding audit, route method export audit, Prisma Client 생성과 asset 준비를 수행했고, Next.js는 production compile, lint와 type validation, page data 수집, 98개 정적 페이지 생성을 끝냈다. 이 결과는 기존 채팅 경로에 추가한 import와 Prisma JSON 쓰기가 production compiler와 호환된다는 근거다.

## 실제 통합이라고 주장하는 범위

현재 증거가 직접 증명하는 범위는 서비스 TypeScript 어댑터와 R&D FastAPI 사이의 localhost HTTP 연결이다. R&D 단위 테스트만 통과했거나 서비스가 예상 URL 문자열만 가진 상태보다는 강한 증거다. 실제 서비스 TypeScript 모듈이 실제 R&D FastAPI 프로세스에 요청했고, R&D SQLite 원장에 결과가 남았으며, 응답 계약이 서비스 검사를 통과했다.

canonical evidence는 `local_two_process_integration=true`, `production_operation_observed=false`, `service_database_persistence_observed=false`를 동시에 기록한다. 특히 마지막 값 때문에 `/api/chat`, `runRndCounseling`, `persistRndCounselingTurn`과 실제 서비스 데이터베이스를 한 번에 실행했다는 주장을 할 수 없다. 연결 정보가 들어 있는 `.env`의 Neon 데이터베이스가 안전한 개발 전용인지 확인되지 않았으므로 임의 레코드를 쓰지 않았다. 실제 채팅 route와 격리된 서비스 데이터베이스를 함께 실행하는 증거가 생길 때 OP-088을 `INTEGRATED`로 올려야 한다.

## 발견한 결함과 수정 과정

canonical smoke 스크립트를 처음 Ruff로 검사했을 때 긴 inline SQLite 조회 문자열 세 줄이 100자 제한을 넘었다. 기능 실패나 통합 실패는 아니었지만, 검증 스크립트 자체가 저장소 품질 기준을 통과하지 못하면 canonical 증거 생성기로 사용할 수 없다. 오류가 지목한 줄을 확인했고, 원인이 한 줄에 여러 SQL 조회를 직렬화한 문자열 구성이라는 점을 재현했다. SQL과 결과 구조는 바꾸지 않고 인접 문자열 리터럴을 여러 줄로 나눴다. 수정 뒤 py_compile과 Ruff를 다시 실행해 통과했다.

이 실패도 연구 기록에서 숨기지 않는다. 검증기는 제품 코드뿐 아니라 증거 생성 코드에도 적용돼야 한다. smoke 생성기가 lint를 통과하지 못한 상태에서 결과 JSON만 정상이라는 이유로 완료를 주장하면, 후속 실행자가 같은 생성기를 안전하게 유지할 수 없다.

독립 검토는 서로 다른 세션이 같은 client-supplied turn ID를 쓰면 첫 번째 세션 메시지가 갱신되는 Critical 결함도 찾았다. 서비스 저장 함수는 이제 세션 ID와 turn ID의 길이 접두사 문자열을 함께 SHA-256으로 계산해 전역 메시지 기본키를 만들고, 기존 메시지의 session ID가 다르면 저장을 거부한다. 같은 검토에서 profile 전체 전달과 허위 동의 scope도 지적했다. 서비스는 나이, 허용된 biological sex, 임신·수유 여부와 목표만 전달하고 이메일·전화번호 같은 추가 필드를 제거한다. safety도 정해진 boolean만 허용한다. 확인된 사용자별 동의 원장이 없으므로 production에서는 R&D 상담 분기를 실행하지 않고, 비production proxy simulation만 `simulation:write`로 표시한다.

두 번째 재검토에서는 동일 질문 재시도의 시각 불일치와 비원자적 Prisma 저장을 찾았다. 서비스는 마지막 user message의 기존 ID와 createdAt이 모두 유효할 때만 R&D를 호출하므로 같은 turn 재시도가 같은 입력 해시를 사용한다. 세션 meta와 assistant message는 한 Prisma transaction에서 함께 upsert한다. 기존 meta는 JSON object로 병합해 다른 기능의 metadata를 지우지 않는다. 이 수정은 코드와 mock 계약 검증을 통과했지만 실제 격리된 Postgres 실행 증거는 아니므로 stage를 높이지 않는다.

마지막 재검토에서는 UI의 실제 `UserProfile` 계약과 allowlist 이름이 다른 문제를 찾았다. `sex`를 `biological_sex`로 변환하고 `pregnantOrBreastfeeding`이 true면 임신과 수유를 모두 true로 전달한다. 동의 없이 질환·약물·알레르기 문자열을 전송하지 않지만, 목록이 존재하면 `requires_test=true`를 보내 안전정보가 보류됐음을 추천 경로가 무시하지 않게 했다. 실제 UserProfile 모양을 사용한 QA가 이 변환과 개인정보 제거를 검사한다.

## 최종 판단

서비스 채팅 코드에는 R&D 상담 API 호출이 구현돼 있다. 어댑터는 기존 interim HTTP 보안과 timeout 경계를 재사용하고, 원래 사용자 식별자를 가명화하고, 요청과 응답의 세션 일치를 확인한다. 상담 지식 검색, 답변 조립, verifier, 응급 우선순위와 추천 안전 판단은 R&D에 남아 있다. localhost 두 프로세스 호출, R&D 원장 조회, 결정론 비교와 서비스 production build는 구현과 어댑터 연결을 증명한다. 실제 채팅 route와 격리된 Prisma 데이터베이스를 포함한 실행 증거가 없으므로 OP-088은 `IMPLEMENTED`이며 `PARTIAL`이다.
## 상담 답변을 믿을 수 있게 만드는 조건
상담 답변은 자연스러운 문장보다 근거 범위와 위험 차단이 먼저다. 허용된 지식 범위만 검색하고, 답변에 근거와 유효일·불확실성을 남기며, 응급 신호나 provider 장애에서는 안전 안내와 결정적 fallback을 우선한다.

`OP-088`는 “서비스 채팅이 R&D 상담 API를 호출하는 얇은 어댑터를 사용한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox/app/api/chat/route-service.ts`, `wellnessbox/app/api/chat/save/route-service.ts`, `wellnessbox/lib/server/wb-rnd-interim-client.ts`
- 테스트·실행: `wellnessbox/scripts/qa/check-rnd-counseling-adapter.cts`, `wellnessbox/scripts/qa/run-rnd-counseling-live-smoke.cts`, `wellnessbox-rnd/scripts/run_counseling_session_service_adapter_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op087_op088_counseling_session_service_adapter_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op087_op088_counseling_session_service_adapter_smoke_v1.json`, `wellnessbox-rnd/data/original_plan/evidence/op088_op090_full_service_roundtrip_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
