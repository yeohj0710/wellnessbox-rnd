# OP-063 실제 상품을 성분 조합 후보로 변환한다.

성분별 상품 후보를 나열하는 것과 구매 가능한 조합을 만드는 것은 다른 일이다. manifest의 구현 경로 `wellnessbox/lib/server/wb-rnd-product-candidates.ts`는 추천 성분별 후보를 탐색해 고유 상품 조합으로 만들고, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/product_combinations.py`는 서비스 결과의 파생값을 다시 계산한다. 등록 smoke가 `POST /api/tips` route 함수와 Python 검증 모델을 함께 통과했으므로 단계는 `INTEGRATED`다. 여기서 “실제 상품”은 서비스 상품 계약 형식의 고정 자료이며 운영 DB 조회를 뜻하지 않는다.

## 성분 후보만 이어 붙이면 같은 복합 상품이 여러 번 세어진다

한 복합 상품이 칼슘, 마그네슘, 비타민 D, 아연을 함께 담을 수 있다. 추천 성분마다 상품 행을 하나씩 붙이면 이 상품을 네 번 사고 복용하는 것처럼 계산할 수 있다. 반대로 한 성분에 여러 단일 상품이 있으면 가능한 선택 조합을 만들어야 가격과 제품 수를 비교할 수 있다. 커밋 `23b2533`은 이런 성분별 후보를 상품 조합으로 바꾸는 `buildProductCombinations`와 `materializeCombination`을 추가했다.

탐색은 추천 순서대로 후보를 하나씩 고른다. 완성된 선택에서는 `product_id`가 같은 상품을 한 번만 남기고 ID 순으로 정렬한다. 각 상품은 가격이 가장 낮은 유효 판매 옵션을 이미 앞에 두므로 첫 옵션을 사용한다. 상품 ID와 판매 옵션 ID 목록을 정해진 JSON으로 만든 뒤 SHA-256 앞 16자를 붙여 `combo_` 식별자를 만든다. 같은 추천, 같은 상품, 같은 판매 옵션이면 입력 순서가 달라도 같은 조합 ID가 나온다.

## 첫 조합 생성기는 탐색 상한과 함량 확인을 보강했다

초기 구현은 원시 선택 수가 64개에 닿으면 탐색을 멈춘 뒤 중복 조합을 합쳤다. 같은 복합 상품을 여러 성분이 공유하면 서로 다른 선택 경로가 같은 조합으로 합쳐지므로, 앞부분의 중복 경로가 상한을 소모하고 실제 고유 조합을 놓칠 수 있었다. 커밋 `cee66e7`은 완성 조합의 고유 ID를 먼저 모으고, `index|선택 상품 집합` 상태를 기억해 같은 상태를 다시 탐색하지 않게 바꿨다. 계약에는 탐색 상태 4,096개와 반환 조합 64개의 서로 다른 상한이 생겼다.

같은 수정은 이름 검색의 거짓 일치도 막았다. 상품명이나 분류가 성분 검색어와 맞더라도 목표 성분의 확정 함량이 없으면 후보로 쓰지 않는다. 검색 상태가 4,096개에 닿으면 `search_truncated=true`를 남기며, 현재 순위 로직은 일부 결과를 최선으로 오해하지 않도록 상위 조합을 비운다. 후보가 하나라도 없는 추천이 있으면 존재하지 않는 상품 ID를 만들지 않고 조합 결과를 비운다.

## 서비스 결과를 Python 모델이 독립적으로 다시 읽는다

`ProductCombinationV1.validate_derived_combination`은 서비스가 보고한 `product_count`, `total_cost_krw`, 성분 합계, 중복 성분, 조합 ID를 원상품에서 재계산한다. 선택 상품 ID는 고유하고 정렬돼야 하며, 가격 합계는 각 선택 옵션 가격의 합이어야 한다. `ProductCombinationEvidenceV1`은 조합 ID 목록도 고유·정렬 상태인지 본다. TypeScript 생성기와 Python 모델이 서로 다른 언어로 같은 불변 조건을 계산하므로 서비스 응답의 숫자만 믿는 구조보다 오류를 찾기 쉽다.

`wellnessbox-rnd/tests/test_product_combinations.py`의 `test_combination_validates_duplicate_and_total_dose`는 두 상품 조합의 제품 수, 비용, 중복 아연, 합계를 확인한다. `test_combination_rejects_forged_derived_fields`는 제품 수·비용·중복 목록·조합 ID 변조를 거부하고, `test_combination_rejects_duplicate_product_identity`는 같은 상품 ID가 두 번 들어온 결과를 막는다. 현재 서비스 QA는 같은 고정 상품 목록을 순서를 바꿔도 결과 지문과 순위가 같고, 목표 성분 함량이 없는 이름 일치는 `NO_MATCH`가 되며, 탐색 상한에 닿으면 상위 조합이 비는지까지 확인했다. Python 집중 시험 96개와 서비스 QA가 모두 통과했다.

## 등록 실행은 여덟 성분에서 네 조합을 만들었다

기준 파일 `wellnessbox-rnd/data/original_plan/evidence/op063_op064_product_combination_dose_smoke_v1.json`은 서비스 고정 상품 7개와 추천 성분 8개를 사용했다. 서비스가 만든 조합은 4개였고, smoke는 그중 복합 상품 공유 조합과 중복 아연 조합 2개를 `ProductCombinationEvidenceV1`로 검증했다. 공유 조합은 상품 29가 네 추천 성분을 함께 맡아 여덟 성분을 상품 다섯 개로 충족했고, 같은 상품 ID는 한 번만 남았다. 아연 단일 상품 42를 추가한 경우는 상품 여섯 개와 별도 조합 ID가 됐다.

현재 계약은 L-테아닌과 차전자피를 더해 열 성분을 다루므로 서비스 QA의 공유 조합은 상품 일곱 개다. 등록 증거의 다섯 개와 최신 QA의 일곱 개는 계약 버전이 다른 결과다. 현재 QA에서 조합 수가 여전히 네 개라는 사실은 확인했지만, 등록 JSON의 실행을 최신 계약으로 재현한 것은 아니다.

## 통합 판정에서 제외되는 운영 범위

등록 JSON은 `service_route_function_integration_proven=true`와 `configured_prisma_query_source_bound=true`를 남긴다. 반면 `actual_prisma_query_executed`, 운영 상품 최신성, 주문·결제 생성은 모두 false다. 조합 탐색은 상품 후보를 만들 뿐 장바구니에 쓰지 않는다.

정본의 결합 지문 `ff1cda3ce8b5684628a776ea05741316b27748ab2212c800490d04a81072a412`은 현재 값 `c72cec8feba9a237f0ab968620d74a76adcecc3f777e492e96d1bcbb8446466f`과 다르다. 최신 시험은 통과했지만 현재 운영 DB 상품으로 route를 실행하지 않았고 등록 smoke도 다시 만들지 않았다. 따라서 OP-063은 서비스 함수와 R&D 검증 모델이 연결된 `INTEGRATED`로 판정하되, 실제 재고 상품을 이용한 운영 조합과 구매 가능성은 확인되지 않았다.
## 상품 조합을 고를 때 함께 본 조건
상품 조합은 효능 점수 하나로 결정하지 않는다. 안전하게 남은 후보, 성분 중복, 일일 용량, 가격, 재고, 제형과 복용 수를 함께 보고, 선택되지 않은 조합의 이유도 다시 설명할 수 있어야 한다.

`OP-063`는 “실제 상품을 성분 조합 후보로 변환한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=20`
- 구현·설계: `wellnessbox/lib/server/wb-rnd-product-candidates.ts`, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/product_combinations.py`
- 테스트·실행: `wellnessbox/scripts/qa/check-rnd-product-candidates.cts`, `wellnessbox-rnd/tests/test_product_combinations.py`, `wellnessbox-rnd/scripts/run_product_combination_dose_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op063_op064_product_combination_dose_smoke_v1.json`
- 통합 증거: `wellnessbox/app/api/tips/route.ts`, `wellnessbox/lib/server/wb-rnd-product-candidates.ts`, `wellnessbox-rnd/data/original_plan/evidence/op063_op064_product_combination_dose_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
