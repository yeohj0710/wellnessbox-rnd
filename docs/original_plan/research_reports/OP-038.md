# OP-038 규칙 버전과 적용 시각을 안전 판정 응답에 포함한다.

## 요구사항과 변경 전 상태

이 요구사항은 안전 판정에 사용한 규칙의 버전과 한 번의 판정에 공통으로 적용한 시각을 응답에 남겨, 나중에 같은 규칙과 시점 조건을 식별할 수 있게 하려는 것이다. 변경 전에는 상호작용·금기·용량 상한 규칙을 적용해도 응답의 RuleReference가 규칙 버전을 요구하지 않았고, SafetySummary에도 판정 시각이 없었다. 특히 용량 문자열이 범위이거나 성분을 하나로 결정할 수 없으면 상한 비교를 건너뛰어, “상한을 넘지 않았다”와 “상한을 계산하지 못했다”를 결과만으로 구분하기 어려웠다.

manifest의 기준 파일은 data/original_plan/requirements_manifest_v1.json이다. OP-038은 그룹 D의 기본 요구 단계인 IMPLEMENTED를 따르며 manifest도 IMPLEMENTED를 주장한다. 이번 확인은 manifest의 표기를 그대로 받아들이지 않고, 등록된 구현·테스트·스모크 파일의 현재 내용을 기준으로 단계를 다시 판단했다.

## 응답 계약과 실행 코드가 바뀐 지점

src/wellnessbox_rnd/schemas/recommendation.py의 RuleReference는 rule_version을 1 이상의 정수로 제한한다. SafetySummary.applied_at은 시간대 정보가 있는 값만 받는 AwareDatetime이다. src/wellnessbox_rnd/domain/models.py의 InteractionRuleRecord, ContraindicationRuleRecord, DoseLimitRecord도 rule_version을 1 이상으로 제한하므로, 원천 규칙부터 API 응답까지 버전이 빠질 수 없다.

src/wellnessbox_rnd/knowledge/runtime_db.py의 build_runtime_knowledge_db는 data/rules/safety_rules.json에 적힌 metadata.version을 런타임 지식 DB의 규칙 버전으로 옮긴다. 근거 문서에서 만든 지식 규칙은 식별자 끝의 _vN에서 N을 읽어 버전으로 만든다. src/wellnessbox_rnd/safety/service.py의 assess_safety는 판정 시작 시각을 한 번 정하고, 같은 응답에 들어가는 모든 RuleReference와 SafetySummary.applied_at에 그 값을 사용한다. 재현성 비교에서는 실행할 때마다 달라지는 applied_at을 제외하므로 규칙 결과의 결정성 검사는 유지된다.

src/wellnessbox_rnd/interim/data_lake.py는 안전 결과와 실행 식별 정보를 저장할 때 이 계약을 보존한다. data/knowledge/runtime_knowledge_db_v1.json에는 현재 빌더가 만든 규칙 버전이 저장되어 있고, data/rules/safety_rules.json은 버전의 원천이다. 따라서 응답의 숫자는 임의로 붙인 상수가 아니라 등록 규칙에서 전달된 값이다.

## 용량 증거를 계산하지 못한 경우의 수정

커밋 8b5f6dd 변경 전에는 제목만으로 추정한 성분, 범위형 용량, 변환할 수 없는 단위처럼 합산 근거가 불완전한 경우 상한 규칙을 생략했다. 수정 후에는 해당 성분을 추천 검토 대상에서 제외하고 application_reason=dose_evidence_incomplete인 용량 규칙을 반환한다. 이 경우 전체 안전 상태는 입력의 다른 위험에 따라 ok일 수 있지만 excluded에는 성분이 남으므로, 계산 실패를 안전 통과로 오해하지 않는다.

실제 상한 초과는 별도로 application_reason=upper_limit_exceeded, severity=blocker, status=blocked를 반환한다. 예를 들어 저장된 스모크에서 비타민 C 2개 제품의 1일 용량 합계 2,200 mg은 차단되며, 1,500 mg은 상한 초과 규칙을 만들지 않는다. 범위형 용량과 호환되지 않는 단위는 합계를 만들지 않고 dose_evidence_incomplete로 기록한다. 용량이 아예 없는 단일 비타민 D 제품은 상한을 평가했다고 주장하지 않으면서 성분을 제외한다.

## 등록된 구현 및 검증 근거

manifest가 등록한 구현 파일은 다음 일곱 개이며 모두 존재하고 현재 요구사항과 직접 연결된다. 등록 경로 중 하나를 원문 그대로 쓰면 wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py다.

- src/wellnessbox_rnd/domain/models.py
- src/wellnessbox_rnd/schemas/recommendation.py
- src/wellnessbox_rnd/knowledge/runtime_db.py
- src/wellnessbox_rnd/safety/service.py
- src/wellnessbox_rnd/interim/data_lake.py
- data/rules/safety_rules.json
- data/knowledge/runtime_knowledge_db_v1.json

등록 테스트와 실행 증거도 모두 열어 확인했다. tests/test_medication_supplement_input_contracts.py, tests/test_runtime_knowledge_db.py, tests/test_inference_api.py, tests/test_session_replay.py, tests/test_learned_runtime_boundary_audit.py, scripts/run_dose_limit_fail_closed_rule_metadata_smoke.py, data/original_plan/evidence/op037_op038_dose_limit_rule_metadata_smoke_v1.json이 해당 근거다.

중요한 회귀 테스트는 test_safety_summary_returns_rule_versions_and_one_fixed_application_time, test_complete_mass_doses_are_normalized_before_upper_limit_comparison, test_nonconvertible_dose_evidence_fails_closed, test_runtime_knowledge_db_builds_required_tables, test_assess_safety_fails_closed_for_title_only_magnesium_dose_evidence다. API와 저장 경계는 test_recommend_endpoint_blocks_urgent_risk_flag_before_recommendation, test_replay_snapshot_is_stored_only_with_persistent_storage_consent, test_build_learned_runtime_boundary_audit_proves_no_core_promotion이 보완한다.

## 저장된 스모크가 입증하는 범위

data/original_plan/evidence/op037_op038_dose_limit_rule_metadata_smoke_v1.json은 complete_above_limit, complete_below_limit, partial_dose, ambiguous_range, incompatible_unit, missing_dose의 여섯 사례를 기록한다. 모든 사례의 applied_at은 2026-07-16T00:00:00+00:00으로 같고, 응답에 관측된 최소 규칙 버전은 1이며 런타임 규칙 버전은 13개다. complete_above_limit의 SAFETY-DOSE-VITC-001과 불완전 용량 사례의 규칙 모두 rule_version=1을 보존한다.

scripts/run_dose_limit_fail_closed_rule_metadata_smoke.py는 원천 규칙, 새로 만든 런타임 DB, 저장된 런타임 DB, 안전 응답의 버전을 서로 비교한다. .github/workflows/original-plan-evidence.yml은 이 스크립트를 실행한 뒤 저장 JSON에 차이가 생기면 git diff --exit-code로 실패하도록 구성되어 있다. 이번 검토에서 스모크는 재실행하지 않았고, 저장된 결과와 현재 파일 내용을 대조했다. 등록 pytest 묶음은 실행했으며 OP-038의 규칙 버전·적용 시각·용량 경계 단언은 통과했다. 다만 tests/test_session_replay.py의 별도 정본 증거가 DB 스키마 15 대신 14를 남겨 한 건 실패했다. 이 실패는 OP-038 응답 메타데이터 단언이 아니라 저장 증거 버전 문제다.

## 현재 단계와 남은 한계

현재 근거 단계는 IMPLEMENTED다. 스키마, 런타임 변환, 안전 판정, 저장 경계와 회귀 테스트가 모두 존재하고 저장된 스모크도 요구한 버전·시각 정보를 보여 준다. 그러나 등록 근거에는 배포된 서비스에서 실제 사용자 요청을 처리하며 이 필드를 수집한 운영 기록이나 외부 검증 결과가 없다. 규칙 버전 1이 임상적 최신성이나 규칙 품질을 뜻하지도 않는다. 따라서 OP-038은 구현 완료로만 판단하며 INTEGRATED, OPERATED, EXTERNAL 단계는 확인되지 않았다.
