# OP-109 사용자 승인 후 기존 createOrder만 재고와 주문을 변경한다.

## 결론

OP-109은 `IMPLEMENTED` 단계다. WellnessBox의 기존 `createOrder` Server Action이 결제 제공자를 서버에서 다시 조회한 뒤 한 데이터베이스 트랜잭션 안에서 재고를 조건부 차감하고 주문과 주문 항목을 만든다. R&D 추천 및 계획 컨텍스트 경로에는 주문·주문 항목·재고 변경 코드가 없다. 다만 canonical evidence는 실제 결제 제공자, PostgreSQL, Prisma 트랜잭션을 실행하지 않는다. 요구 단계 `OPERATED`에 못 미치므로 완료 판정은 `PARTIAL`이다.

## 요구사항을 어떻게 판단했는가

이 요구사항의 핵심은 추천 결과가 곧바로 구매나 재고 변경으로 이어지지 않게 하는 것이다. R&D는 상품 후보와 조합을 제안할 수 있지만, 사용자 승인과 결제 검증 이전에는 주문을 만들거나 재고를 줄이면 안 된다. 실제 변경이 필요할 때도 새로운 R&D 전용 주문 함수를 만들지 않고 서비스가 이미 사용하는 `createOrder` 경계를 재사용해야 한다.

이번 루프는 세 경계를 구분했다. 첫째, R&D 추천 라우트는 후보만 반환한다. 둘째, 주문 완료 화면은 결제 결과가 성공으로 해석된 경우에만 주문 생성 함수를 부른다. 셋째, 실제 재고와 주문 변경은 `createOrder`의 데이터베이스 트랜잭션 안에서 함께 일어난다. 이 구분이 깨지면 추천 요청만으로 재고가 줄거나, 주문만 생성되고 재고 차감이 실패하는 불일치가 생길 수 있다.

## 현재 주문 생성 경로

`useOrderCompleteBootstrap`은 결제 ID와 결제 방식을 확인하고 결제 정보 API를 호출한다. `resolvePaymentOutcome`이 유효한 결제 결과를 만들지 못하면 결제 실패로 처리하고 주문 생성 함수를 호출하지 않는다. 유효한 결과가 있을 때만 `createOrderFromPaymentOutcome`을 실행한다. 이 함수는 로컬 저장소의 주문 초안을 읽고 빈 카트와 선택 옵션 누락을 검사한 뒤 기존 `createOrder`를 호출한다.

`createOrder`는 결제 ID, 결제 방식, 제공자 조회 ID를 필수로 받는다. Server Action 내부의 `verifyOrderPayment`가 결제 제공자를 다시 조회하고 결제 완료 상태, merchant ID 일치, 거래 ID, 양의 결제 금액을 확인한다. 클라이언트가 보내던 status, txId, totalPrice는 더 이상 신뢰하지 않는다. 주문 항목을 정규화한 뒤 데이터베이스 상품 가격 합계와 서버가 검증한 결제 금액도 비교한다.

`paymentId`에는 Prisma unique 제약을 추가했다. migration은 기존 non-null paymentId 중복을 먼저 검사하고, 중복이 있으면 조정이 필요하다는 명시적 오류로 중단한다. 조용히 임의 주문을 삭제하지 않는다. 검사를 통과한 뒤에만 unique index를 만든다. `createOrder`는 트랜잭션 안에서 같은 paymentId를 먼저 조회하고, 동시 요청이 조회 경쟁을 통과하더라도 unique insert 경쟁에서 한 요청만 성공한다. 실패한 트랜잭션의 재고 차감은 함께 rollback된다. P2002 unique 충돌이 나면 rollback 뒤 기존 주문을 다시 읽어 멱등 재시도 응답을 반환한다.

신규 주문은 `db.$transaction` 안에서 처리한다. 각 약국 상품은 요청 수량 이상의 재고가 있을 때만 `updateMany`로 차감된다. 하나라도 조건을 충족하지 못하면 오류를 던져 전체 트랜잭션을 되돌린다. 모든 재고 차감이 성공한 뒤 `tx.order.create`가 주문과 주문 항목을 만든다. 주문 생성과 재고 차감이 같은 원자적 경계에 있으므로 중간 상태가 남지 않는다.

## R&D 경계에서 금지한 행동

서비스의 `runUserInterimRecommendationRoute`는 R&D 추천 응답의 안전 권한을 검사하고 상품 후보를 붙인다. 이 라우트에는 Prisma 주문 접근, 주문 항목 생성, 재고 decrement가 없다. 새로 추가한 주문 계획 컨텍스트 라우트도 최신 주문 상태를 읽어 R&D로 전달할 뿐 주문을 쓰지 않는다. R&D의 계획 컨텍스트 API는 수신한 상태를 계산 결과에 넣지만 실행 이벤트를 추가하지 않고 주문 상태 변경 권한을 항상 `false`로 반환한다.

canonical QA는 추천·계획 라우트 소스에 주문 및 재고 변경 기호가 없는지 확인한다. 주문 완료 경로에는 결제 결과 판정 뒤 `createOrderFromPaymentOutcome`과 `createOrder`가 이어지는지 확인한다. 주문 mutation 파일에서는 기존 `createOrder`가 재고 decrement와 `tx.order.create`를 함께 소유하는지 확인한다. 이 검사는 코드 경계가 우회되지 않았는지 알려 준다.

## 인증과 사용자 승인

계획 컨텍스트 API는 사용자 세션을 먼저 요구한다. 인증이 실패하면 주문 조회와 R&D 호출이 모두 실행되지 않는다. canonical QA는 인증 실패 경로에 호출 금지 함수를 주입해 어느 하나라도 실행되면 즉시 실패하게 했다.

이번 증거에서 사용자 승인은 결제 성공 결과를 주문 생성의 선행 조건으로 둔 서비스 흐름을 뜻한다. 추천 후보의 단순 노출이나 계획 상태 조회는 승인이 아니다. UI 검증을 우회해 Server Action을 직접 호출해도 서버가 결제 제공자를 다시 조회한다. 결제 정보가 없거나 merchant ID가 다르거나 결제가 실패하면 주문을 만들지 않는다. 다만 canonical 실행에서는 결제 제공자 응답을 주입했으므로 운영 승인을 관측했다고 주장하지 않는다.

## canonical evidence

주 데이터셋 `data/original_plan/op109_op110_order_plan_context_cases_v1.json`은 OP-109 사례 네 개와 OP-110 사례 네 개를 포함한다. OP-109 사례는 결제 게이트, 기존 mutation 경계, 추천 라우트의 무변경, 실제 Prisma 미실행을 명시한다. runner는 별도 FastAPI 프로세스와 서비스 QA 프로세스를 실행하고 결과를 한 증거 파일로 묶는다.

증거의 `existing_create_order_owns_mutations`는 기존 함수가 재고 차감과 주문 생성을 소유한다는 소스 계약 검사다. `recommendation_route_order_mutation_free`는 R&D 서비스 라우트에 주문 변경 기호가 없다는 뜻이다. `actualPrismaMutationExecuted`는 `false`다. 이 값을 통해 정적·통합 계약 증거를 실제 데이터베이스 mutation 증거로 잘못 해석하지 않게 했다.

증거는 WellnessBox 커밋과 R&D runner의 소스 커밋을 기록한다. 또한 R&D API, 계획 생명주기 모듈, 데이터셋, runner의 Git blob SHA를 기록한다. GitHub Actions는 WellnessBox 커밋을 고정해 서비스 코드가 바뀌어도 같은 경계를 재생한다.

## 실패 조건과 안전성

재고가 부족하면 `createOrder`는 오류를 던지고 트랜잭션이 주문 생성을 취소한다. 같은 결제 ID의 주문이 있으면 기존 주문을 반환하므로 중복 재고 차감이 일어나지 않는다. 주문 항목이 비어 있거나 유효하지 않으면 데이터베이스 변경 전에 실패한다. 추천 라우트의 카탈로그가 잘못되면 후보 단계에서 502로 닫히며 주문 단계로 넘어가지 않는다.

이 경계는 R&D가 주문 상태를 직접 수정하지 못하게 한다. R&D 응답은 `order_state_effect: NONE`, `order_state_mutation_allowed: false`를 반환한다. 주문 취소나 배송 완료 같은 서비스 상태도 계획 컨텍스트로 읽을 뿐, R&D가 서비스 주문을 되돌리거나 다음 상태로 이동시키지 않는다.

## 확인하지 않은 범위

이번 루프는 실제 Prisma 클라이언트나 PostgreSQL을 실행하지 않았다. 실제 재고 행을 만들고 차감 결과를 조회하지 않았다. unique 제약과 트랜잭션 코드는 추가했지만 동시 주문 경쟁을 데이터베이스에서 실행하지 않았다. 결제 제공자 재시도, 트랜잭션 격리 수준, 알림 실패 이후 상태도 관측하지 않았다. 브라우저에서 사용자가 결제를 승인하는 과정과 운영 주문 생성도 실행하지 않았다.

따라서 OP-109을 `INTEGRATED`나 `OPERATED`로 올리지 않는다. 코드가 구현됐고 서비스·R&D 경계가 연결돼도 핵심 변경 대상인 실제 재고와 주문 데이터베이스를 실행하지 않았기 때문이다.

## 재현과 다음 검증

R&D 저장소에서 `python scripts/run_order_plan_context_integration_smoke.py`를 실행하면 canonical evidence를 재생할 수 있다. 서비스 정적·라우트 QA는 `node --conditions=react-server --import tsx scripts/qa/check-rnd-order-plan-context.cts`로 실행한다. 서비스 타입 검사는 `npm run typecheck`, 인코딩 검사는 `npm run audit:encoding`으로 확인한다.

다음 승격 검증은 격리된 PostgreSQL에 약국 상품과 재고를 넣고 실제 `createOrder`를 호출해야 한다. 성공 사례에서 재고가 정확히 줄고 Order와 OrderItem이 생기는지, 재고 부족 사례에서 모든 변경이 rollback되는지, 같은 paymentId 재시도에서 재고가 한 번만 줄어드는지 확인해야 한다. 그 뒤 승인된 브라우저와 결제 sandbox를 관측해야 `OPERATED` 승격을 검토할 수 있다.
