# OP-083 bounded RAG가 허용된 지식 범위만 검색하게 한다.

## 질문에 답하기 전에 먼저 정해야 하는 것

OP-083의 원문은 “bounded RAG가 허용된 지식 범위만 검색하게 한다”이다. 짧은 문장이지만, 실제 구현에서 가장 먼저 답해야 할 질문은 검색 정확도가 아니다. 어떤 문서가 검색 후보가 될 수 있는지, 그 범위를 누가 어떤 값으로 정하는지가 먼저다. 검색 결과가 질문과 비슷해 보여도 허용하지 않은 출처에서 가져왔다면 bounded RAG라고 부를 수 없다. 반대로 허용 목록을 코드 밖의 설명문에만 적어 두고 실행 시점에 검사하지 않아도 같은 문제가 생긴다. 이번 작업은 이 경계를 실행 가능한 계약으로 바꾸는 데 초점을 맞췄다.

기존 R&D 저장소에는 이미 상담용 passage를 만드는 절차가 있었다. `reference_claims_v1.jsonl`의 claim을 읽고, `reference_knowledge_base_v1.json`에 등록된 출처와 연결한 뒤, 원문 파일의 줄 범위가 claim ID와 claim 본문을 실제로 포함하는지 검사한다. OP-081에서 이 경로를 강화했기 때문에 passage마다 출처 제목, 원문 URI, 파싱한 원문 URI, 라이선스 상태, 시행 시각, 폐기 시각, 줄 시작과 끝이 남아 있었다. 이번 구현은 별도의 문서 저장소나 두 번째 검색기를 만들지 않았다. 이미 검증된 `RetrievalCorpusManifest`와 기존 점수 계산기를 그대로 사용하고, 검색 직전에 허용 범위를 적용하는 한 단계만 추가했다.

## 허용 범위를 문자열 하나로 표현하지 않은 이유

“상담 지식만 검색한다”라는 이름만으로는 실행 경계를 증명할 수 없다. 그래서 `BoundedKnowledgeScope`는 세 종류의 허용 목록을 동시에 요구한다. 첫째는 `allowed_source_types`다. 현재 canonical corpus에는 임상 가이드라인, 정부 보건 자료, 상호작용 참고자료, 내부 master context, 동료평가 논문이라는 다섯 출처 유형이 있다. 둘째는 `allowed_claim_types`다. 약물 상호작용, 제한적 근거, 혼합 근거, 신호 임계값, 안전 재검사 정책처럼 현재 상담에서 다룰 수 있는 claim 유형 열여섯 개가 여기에 들어간다. 셋째는 `allowed_reference_ids`다. 현재 corpus에서 검증된 열아홉 출처의 안정적인 ID만 허용한다.

세 목록 가운데 하나만 맞는 passage는 검색 대상이 아니다. 예를 들어 출처 유형이 임상 가이드라인이어도 reference ID가 허용 목록 밖이면 제외한다. 반대로 reference ID가 우연히 허용 목록과 같아도 claim 유형이 범위 밖이면 제외한다. 세 조건을 모두 만족해야 기존 점수 계산기로 넘어간다. 이 방식은 “허용 출처인데 용도가 다른 문장”이나 “허용된 claim 이름을 붙인 미등록 출처”가 검색 결과에 섞이는 일을 막는다.

허용 목록은 비어 있을 수 없고, 중복이 없어야 하며, 정렬된 상태여야 한다. 정렬 규칙은 기능상의 편의가 아니라 재현성을 위한 장치다. 같은 집합을 호출 순서에 따라 다르게 직렬화하면 evidence 파일의 바이트와 해시가 달라질 수 있다. `scope_id`도 답변에 그대로 남긴다. 나중에 답변을 감사할 때 어느 허용 범위를 적용했는지 이름만 추정하지 않고 정확히 확인하기 위해서다. 한 번에 검색할 수 있는 결과 수도 `max_results`로 제한했고, 호출자가 그 수보다 큰 `top_k`를 요청하면 조용히 잘라 내지 않고 오류로 거부한다.

독립 검토에서는 호출자가 같은 scope ID를 유지한 채 미검토 출처와 claim, reference ID를 허용 목록에 추가할 수 있다는 결함을 찾았다. 이름만 같으면 승인된 범위처럼 보이는 문제였다. 이를 고치기 위해 `data/knowledge/counseling_knowledge_scope_registry_v1.json`을 repository-pinned registry로 추가했다. 검색 함수와 verifier는 전달받은 scope 전체가 registry의 같은 ID 항목과 정확히 일치하는지 다시 확인한다. 호출자가 `wellnessbox-counseling-knowledge-v1`이라는 이름을 재사용하더라도 목록 내용이 한 글자라도 다르면 `knowledge_scope_content_not_repository_approved`로 거부한다.

## 날짜가 없는 검색은 bounded 검색으로 인정하지 않았다

OP-081에서 passage의 시행일과 폐기일을 보존했더라도, 검색 함수가 “언제의 지식”을 요청했는지 모르면 날짜 정보는 장식에 그친다. 이번에 추가한 `retrieve_bounded_chunks`는 timezone이 있는 `as_of`를 필수로 받는다. 시행일보다 이른 시각에는 passage를 검색하지 않는다. 폐기일과 같거나 뒤인 시각에도 검색하지 않는다. timezone이 없는 날짜를 받으면 서버가 임의의 지역 시간을 가정하지 않고 `bounded_retrieval_as_of_timezone_required`로 거부한다.

canonical smoke의 답변 시각은 `2026-07-21T13:00:00+00:00`으로 고정했다. smoke는 실제 스물네 passage를 사용한다. 그중 하나를 복사해 `unreviewed_external_blog`라는 허용되지 않은 출처 유형과 새 reference ID를 부여한 뒤 corpus에 끼워 넣었다. 질문 문구를 원래 passage와 똑같이 맞춰 검색 점수가 높아지게 해도, 새 passage는 결과에 들어오지 않았다. 또 다른 passage에는 답변 시각보다 앞선 폐기일을 넣었다. 내용이 정확히 일치해도 검색 결과는 비어 있었다. 이 두 검사는 단순히 “정상 검색이 된다”는 양성 사례보다 중요하다. 허용 경계가 실제로 입력을 배제하는지 보여 주기 때문이다.

## 검색 결과가 없을 때 답을 만들어 내지 않는다

bounded RAG의 범위 제한은 검색 단계에서 끝나지 않는다. 허용 범위를 적용한 뒤 결과가 없으면 답변 생성기가 원래의 전체 manifest를 다시 검색하거나, live provider에 일반 지식을 묻는 우회 경로가 생겨서는 안 된다. `generate_bounded_template_answer`는 `scope`와 `as_of`를 필수로 받고 `retrieve_bounded_chunks`만 호출한다. 허용 결과가 없으면 범위 밖 질문은 `out_of_scope`, 범위 안의 단어를 포함하지만 요구한 관계를 입증하지 못하면 `unsupported`로 돌려준다. 두 경우 모두 citation과 사용한 chunk ID는 비어 있다.

OpenAI adapter도 같은 범위를 사용한다. provider 호출을 허용하더라도 먼저 bounded 검색으로 evidence chunk를 정한다. provider 프롬프트에는 그 chunk만 들어간다. provider가 반환한 chunk ID가 미리 정한 목록에 없으면 citation으로 복구하지 않는다. provider가 근거 없는 supported 답변을 만들면 deterministic fallback으로 돌아간다. 이번 smoke에서는 live API를 사용하지 않았고, `live_llm_inference_used`를 명시적으로 `false`로 기록했다. 따라서 이번 증거는 외부 모델 성능을 입증하지 않는다. 검색 범위와 deterministic 답변 계약을 구현했다는 증거다.

## 실제로 재현한 사례

canonical evidence는 네 답변 사례와 세 음성 probe를 기록한다. 첫 번째 답변은 glucosamine과 warfarin의 상호작용 질문이다. 허용된 interaction passage를 선택하고 stable chunk ID, reference ID, claim ID를 남긴다. 두 번째는 magnesium과 insomnia 근거 질문이다. `mixed_goal_evidence` passage를 선택하고 혼합 근거라는 불확실성을 보존한다. 세 번째는 glucosamine이 diabetes를 치료하는지 묻지만 interaction 답변 형식을 요구하는 사례다. 약물 관계를 입증할 passage가 없으므로 `unsupported`가 된다. 네 번째는 quadratic topology theorem 설명을 요구하는 질문이며 상담 corpus와 겹치는 검색어가 없어 `out_of_scope`가 된다.

초기 smoke에서는 “서울 날씨” 질문을 범위 밖 사례로 사용했다. 그런데 기존 lexical scorer가 여러 passage에 양의 점수를 주어 supported 후보가 생겼다. 이 결과를 예상값에 억지로 맞추지 않았다. 해당 질문은 현재 점수 함수의 일반 단어 겹침을 시험하는 사례가 되어 버렸고, OP-083이 확인하려는 허용 지식 경계와는 다른 문제였다. 그래서 corpus와 의미상 겹치지 않는 topology 질문으로 범위 밖 probe를 좁혔다. 이 기록은 현재 검색기가 의미 검색기가 아니라 결정적 lexical 검색기라는 한계도 드러낸다. 관련성 품질과 허용 경계는 같은 문제가 아니다.

## 검증 결과와 완료 단계

canonical evidence 파일은 `data/original_plan/evidence/op083_op084_bounded_rag_answer_provenance_smoke_v1.json`이다. 현재 파일에는 스물네 passage, 열아홉 출처, 다섯 출처 유형, 열여섯 claim 유형이 기록돼 있다. 허용하지 않은 출처 유형, reference ID, claim 유형을 각각 따로 바꾼 세 사례와 forged registry scope, 폐기 passage, 미래 시행 passage, 답변 유효성 변조, 중복 provenance를 모두 차단했다. 파일 SHA-256은 `cfb10b0bdb9d02fbd1851cddde8b32c914a1ac00929b47f60e514c343fffb04d`다. source commit은 `6528c50d9d453bf397389746b7889ad489cc1b92`이고, source SHA-256은 `03c86d65261517c360e4120a9d2f3039cc30fa8db568c9bebe431e558e026f5f`이다. data SHA-256은 `95cc551d1be3fe9bb9d62fc39e0a1418587d529f6f89f9fc942cbedd39290356`이다.

OP-083의 required stage는 `IMPLEMENTED`다. 현재 코드는 기존 corpus와 검색 경로에 명시적 허용 범위를 적용하고, 날짜가 지난 passage와 범위 밖 passage를 실행 시점에 제외하며, 같은 경계를 deterministic 답변과 provider adapter에 전달한다. 집중 테스트와 canonical smoke가 이 경계를 직접 재현한다. 따라서 OP-083은 `IMPLEMENTED`를 주장할 수 있고 required stage를 충족한다.

다만 이 완료 판단은 서비스 통합이나 운영을 뜻하지 않는다. WellnessBox 서비스 저장소는 이번 loop에서 바꾸지 않았다. 배포된 R&D 상담 프로세스도 없고, production에서 허용 범위 위반이 차단됐다는 telemetry도 없다. 외부 전문가가 범위 목록을 검증한 증거도 없다. OP-083은 코드 구현 단계에서 완료된 것이며, 서비스 호출과 실제 운영은 OP-088 이후의 별도 요구사항으로 남는다.
## 상담 답변을 믿을 수 있게 만드는 조건
상담 답변은 자연스러운 문장보다 근거 범위와 위험 차단이 먼저다. 허용된 지식 범위만 검색하고, 답변에 근거와 유효일·불확실성을 남기며, 응급 신호나 provider 장애에서는 안전 안내와 결정적 fallback을 우선한다.

`OP-083`는 “bounded RAG가 허용된 지식 범위만 검색하게 한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/chat/retrieval.py`, `wellnessbox-rnd/src/wellnessbox_rnd/chat/answering.py`, `wellnessbox-rnd/src/wellnessbox_rnd/chat/openai_adapter.py`, `wellnessbox-rnd/data/knowledge/counseling_knowledge_scope_registry_v1.json`
- 테스트·실행: `wellnessbox-rnd/tests/test_chat_retrieval.py`, `wellnessbox-rnd/tests/test_chat_openai_adapter.py`, `wellnessbox-rnd/scripts/run_bounded_rag_answer_provenance_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op083_op084_bounded_rag_answer_provenance_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
