# OP-096 원본 파일 해시와 정규화 결과 계보를 저장한다.

manifest에 등록된 증거 `wellnessbox-rnd/apps/inference_api/routes/interim.py`에서 구현과 검증 대상을 확인할 수 있다.

## 결론

센서 파일의 정확한 원본 바이트 SHA-256과 정규화 결과 SHA-256을 같은 추가 전용 계보 행에 저장하도록 구현했다. 성공한 파일은 정규화 JSON과 두 해시를 함께 남긴다. 스키마 오류로 실패한 파일도 원본 해시와 오류를 남길 수 있다. 단, 추천 목적 사용 동의가 없으면 본문을 읽거나 해시하지 않으며, 영구 저장 동의가 없으면 데이터베이스 행을 만들지 않는다. 원본 파일 본문은 저장하지 않는다.

OP-096의 요구 증거 단계는 `OPERATED`다. 이번 루프는 인증된 API와 실제 SQLite 저장·재조회까지 구현했지만 배포 환경과 운영 트래픽은 확인하지 않았다. 따라서 주장 단계는 `IMPLEMENTED`, 완료 판정은 `PARTIAL`이다. 로컬 실행 성공을 운영 증거로 부풀리지 않는다.

## 계보가 답해야 하는 질문

정규화된 걸음 수나 혈당 평균만 저장하면 나중에 어떤 파일에서 결과가 나왔는지 확인하기 어렵다. 원본 파일 이름만 저장해도 충분하지 않다. 같은 이름으로 내용이 다른 파일을 올릴 수 있기 때문이다. 반대로 원본 파일 전체를 관계형 데이터베이스에 복사하면 민감정보 보유 범위가 커진다. 이번 설계는 원본 본문을 보관하지 않으면서도 특정 바이트열과 정규화 결과의 연결을 검증할 수 있어야 했다.

원본 SHA-256은 Base64를 해제한 정확한 바이트에서 계산한다. 텍스트를 읽은 뒤 줄바꿈을 바꾸거나 JSON을 다시 직렬화한 값에서 계산하지 않는다. 따라서 Windows와 Linux 줄바꿈이 다른 파일은 서로 다른 원본으로 식별된다. 이것이 원본 무결성 확인에 필요한 성질이다.

정규화 결과 SHA-256은 정렬된 키와 고정 구분자를 사용하는 정규 JSON 바이트에서 계산한다. 같은 의미의 정규화 결과는 입력 JSON의 공백이나 키 순서가 달라도 같은 결과 해시를 만든다. 원본 해시와 결과 해시의 역할을 분리했기 때문에 원본 재전송 여부와 정규화 결과 동일성을 각각 판단할 수 있다.

## 저장 구조

기존 `InterimStore`의 스키마 버전을 11에서 12로 올리고 `sensor_file_ingestions` 테이블을 추가했다. 새 데이터베이스는 버전 12로 생성되며, 버전 11 데이터베이스를 열면 기존 행을 유지한 채 새 테이블과 불변 트리거를 만든다. 별도 데이터베이스나 두 번째 저장 계층은 만들지 않았다.

각 행은 결정적 수집 ID, 프로필 ID, 파일 ID, 출처 종류, 상태, 원본 SHA-256, 정규화 결과 SHA-256, 정규화 JSON, 오류 JSON, 정규화 레코드 수, 생성 시각을 가진다. 원본 바이트나 Base64 본문을 담는 열은 없다. 실패 시 정규화 결과가 없으면 결과 해시와 결과 JSON은 비어 있다. 사용 동의 거부처럼 본문을 읽지 않은 경우 원본 해시도 비어 있다.

행 수정과 삭제는 SQLite 트리거가 거부한다. 계보는 현재 상태를 덮어쓰는 테이블이 아니라 처리 사실을 추가하는 기록이기 때문이다. 잘못된 행을 정정해야 한다면 기존 행을 고치지 않고 새로운 처리 요청을 추가해야 한다. 이 규칙은 애플리케이션 코드의 실수뿐 아니라 직접 SQL 수정도 막는다.

## 재시도와 중복 방지

수집 ID는 프로필 ID, 파일 ID, 원본 해시, 정규화 버전을 사용해 결정적으로 만든다. 같은 요청을 그대로 재생하면 같은 ID가 나온다. 저장소는 기존 행의 모든 예상 값을 비교한다. 값이 같으면 기존 행을 재사용하고 응답에서 중복 제거로 표시한다. 같은 ID인데 값이 다르면 충돌로 실패한다. 단순 `INSERT OR IGNORE`로 불일치를 숨기지 않는다.

이 설계는 네트워크 재시도 때문에 같은 파일 계보가 계속 늘어나는 문제를 막는다. 파일 내용이 바뀌면 원본 해시가 달라져 새 ID로 남고, 정규화 버전이 바뀌어도 새 ID가 된다. 같은 ID에서 출처, 상태, 결과 해시 같은 저장 값이 기존 행과 다르면 `identity_conflict`로 실패해 불일치를 숨기지 않는다.

## 동의 경계

추천 목적 사용 동의와 영구 저장 동의를 분리했다. 추천 목적 사용 동의가 없으면 서비스는 민감 파일을 해시 계산 목적으로도 읽지 않는다. 응답은 동의 거부 오류를 반환하며 원본 해시와 저장 행을 만들지 않는다. 영구 저장 동의만 없으면 메모리에서 파일을 검증하고 정규화할 수 있지만 SQLite에는 아무 행도 쓰지 않는다. 응답에는 저장되지 않았다는 사실이 들어간다.

해시는 가명화된 안전한 원본이 아니다. 같은 파일을 가진 사람은 해시를 비교할 수 있고, 작은 후보 집합에서는 추측 공격도 가능하다. 그래서 원본 본문을 저장하지 않는다는 이유만으로 동의 규칙을 생략하지 않았다. 해시와 정규화 결과도 영구 저장 동의의 적용을 받는다.

## 실패 계보를 남기는 이유

스키마 오류 파일을 완전히 버리면 반복적으로 실패한 공급자 형식이나 사용자 업로드 문제를 추적하기 어렵다. 사용과 저장이 모두 허용된 경우에는 실패 상태, 원본 해시, 구조화된 오류를 남긴다. 원본 본문은 남기지 않는다. 이 기록으로 같은 잘못된 파일이 반복됐는지 확인할 수 있고, 오류 건수도 재현할 수 있다.

실패 계보는 정상 데이터로 취급되지 않는다. 상태가 `FAILED`이고 정규화 결과 해시와 결과 JSON이 비어 있으므로 후속 소비자는 성공 행만 명시적으로 선택해야 한다. 한 요청에서 세 파일 중 두 파일이 성공하고 한 파일이 실패하면 세 행이 저장될 수 있다. 응답의 성공 파일 수 2와 저장 계보 수 3이 다른 이유다.

## 고정 증거

고정 실행기는 일곱 사례를 인증된 FastAPI 경로로 보낸다. 부분 성공 사례는 두 성공 행과 한 실패 행의 원본 해시를 독립적으로 확인한다. 다중 행 CSV 사례는 정규화 레코드 두 개가 하나의 결과 JSON과 결과 해시로 연결되는지 확인한다. 중복 머리글과 중복 JSON 키 사례는 오류가 발생해도 원본 해시와 실패 상태가 저장되는지 확인한다.

사용 동의 거부 사례는 해시와 행이 모두 없음을 확인한다. 저장 동의 거부 사례는 정상 응답 뒤 데이터베이스 행 수가 증가하지 않음을 확인한다. 동일 요청 재생 사례는 세 파일 모두 기존 행으로 중복 제거되고 전체 행 수가 유지되는지 확인한다. 변조 사례는 `UPDATE`와 `DELETE`가 모두 거부되는지 확인한다.

실행기는 임시 SQLite 파일을 API 호출 뒤 다시 열어 여섯 행을 조회했다. 각 성공 행의 정규화 JSON을 다시 해시해 저장된 결과 해시와 비교했다. 원본 본문 열이 스키마에 존재하지 않는 것도 검사했다. 버전 11에서 12로 올리는 마이그레이션 테스트와 새 데이터베이스 생성 테스트도 통과했다.

## 검증 결과와 운영 단계의 공백

새 수집·계보 테스트와 기존 센서 파서, 파일 스키마, 중간 저장소, 중간 API 테스트를 함께 실행해 79개 검사가 통과했다. 실제 API 인증, 실제 SQLite 쓰기와 재조회, 정확 재생 중복 제거, 동의 거부, 변조 거부가 모두 포함됐다. 정적 검사도 통과했다.

그러나 `OPERATED`에는 배포된 서비스, 운영 데이터베이스, 실제 사용자 또는 기기 트래픽, 운영 보존·삭제 정책, 백업 복구, 접근 통제 기록, 장애 대응 관측이 필요하다. 이번 증거는 그 항목을 제공하지 않는다. 따라서 OP-096은 구현됐지만 요구된 운영 단계에는 아직 도달하지 않았다.

## 다음 검증 항목

운영 단계로 올리기 전에는 배포 환경의 영구 저장소를 확정하고, 암호화와 키 관리, 보존 기간, 사용자 삭제 요청 처리, 백업 복구 뒤 불변성, 관리자 접근 감사 로그를 확인해야 한다. 대용량 파일과 동시 재시도에서도 결정적 ID와 행 수가 유지되는지 부하 시험이 필요하다. 실제 공급자 파일을 쓸 경우 개인정보 처리 승인과 형식별 계약도 별도로 확인해야 한다.
## 센서와 유전자 자료를 넣는 기준
센서와 유전자 자료는 많이 넣는 것보다 동의한 자료를 올바른 단위와 시점으로 연결하는 것이 중요하다. 이 그룹은 파일 원본, 출처별 정규화, data_class, 동의, 중복 수신, 실제 점수 반영을 분리해 확인한다.

`OP-096`는 “원본 파일 해시와 정규화 결과 계보를 저장한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

- 구현·설계: `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/sensor_file_ingestion.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/store.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
