# OP-040 프로덕션 추천 경로에서 안전 엔진의 최종 차단 권한을 통합 검증한다.

## 요구사항과 이전 위험

OP-040은 추천 모델이나 서비스 화면이 안전 엔진의 차단 결과를 덮어쓰지 못하게 하고, 최종 사용자 경로에서도 차단 시 추천을 0건으로 만드는 요구사항이다. 초기 경로는 현재 요청의 안전 입력이 저장된 프로필보다 우선하면 기존 임신·질환·약물 위험을 지울 수 있었고, 모델 예측 뒤의 추천 결과를 서비스가 충분히 검증하지 않으면 상위 서비스가 안전 응답의 의미를 바꿀 수 있었다.

manifest의 정확한 경로는 data/original_plan/requirements_manifest_v1.json이다. 이 파일은 OP-040의 required_stage와 claimed_stage를 OPERATED로 둔다. 로컬 연구 PC에서 실제 추천 경로를 실행한 기록은 있지만, 그 세션이 안전 차단을 실행했다는 관측값은 없다. 따라서 manifest의 단계 표시, 최종 차단 권한의 실제 운영, 공개 프로덕션 배포를 서로 나눠서 판단해야 한다.

## R&D 경로의 최종 판정 순서

apps/inference_api/routes/interim.py의 _merge_safety_input은 저장 프로필, 현재 요청, 추천 성분에서 얻은 위험 사실을 안정적으로 합친다. 현재 요청에 필드가 없다는 이유만으로 저장된 고위험 사실을 제거하지 않으며, 서로 다른 입력에 나뉜 동적 규칙 조건도 합쳐 평가한다. _combine_safety_decisions는 여러 판정 중 더 강한 안전 행동을 보존한다.

_recommendation은 등록 모델을 부르기 전에 src/wellnessbox_rnd/interim/safety.py의 evaluate_safety를 실행한다. 사전 판정이 STOP_AND_ESCALATE 또는 BLOCKED이면 모델을 호출하지 않고 추천 0건을 반환한다. 모델이 후보를 만든 경우에는 후보 성분까지 포함해 다시 평가하므로, 사전 입력에는 없던 추천 성분의 위험도 최종 응답 전에 차단할 수 있다.

evaluate_safety는 SafetyRank 순서로 행동을 비교하고 SafetyDecision에 status, action, findings, matched_rule_ids를 남긴다. 응급 신호는 SAFE-EMERGENCY-001과 STOP_AND_ESCALATE로 연결된다. 이 판정은 모델 점수나 상품 선택보다 먼저 적용되며, 차단 결과에서는 추천 배열을 비운다.

## WellnessBox 서비스가 권한을 보존하는 방식

C:/dev/wellnessbox/app/api/tips/route.ts의 POST는 R&D 추천 경로를 사용한다. C:/dev/wellnessbox/lib/server/wb-rnd-interim-route.ts의 runUserInterimRecommendationRoute는 R&D 응답을 받아 서비스 응답으로 넘기기 전에 최종 안전 검사와 성분 식별자 보강을 수행한다. C:/dev/wellnessbox/lib/server/wb-rnd-interim-safety-authority.ts의 validateWbRndInterimRecommendation은 상태, 행동, 발견 규칙, 추천 항목의 구조를 검사한다.

enforceWbRndInterimSafetyAuthority는 R&D 응답이 BLOCKED 또는 STOP_AND_ESCALATE이면 추천 항목을 0건으로 강제하고 authority_mode=rnd_final을 보존한다. 응답 계약이 잘못되었거나 준비된 추천 성분을 서비스 식별자로 안전하게 바꿀 수 없으면 buildWbRndInterimFailClosedResponse를 사용해 service_fail_closed와 HTTP 502를 반환한다. 서비스가 R&D 차단을 “성공한 추천”으로 바꾸는 경로는 등록 구현에서 발견되지 않았다.

## 회귀 테스트와 수정된 실패 사례

tests/test_interim_api.py의 test_interim_api_blocks_emergency_before_registered_model은 응급 입력에서 모델 호출 전 차단과 추천 0건을 확인한다. test_current_safety_input_cannot_remove_stored_high_risk_facts는 새 요청이 저장 위험을 지우지 못하는지 검사한다. test_current_safety_input_cannot_remove_stored_dynamic_rule_predicate와 test_dynamic_rule_predicate_combines_risk_facts_across_sources는 분산된 규칙 조건을 보수적으로 합친다. test_interim_api_requires_token_and_runs_recommendation은 내부 인증 경계도 확인한다.

scripts/run_wellnessbox_final_safety_authority_smoke.py는 실제 localhost HTTP로 R&D POST /v1/interim/recommendations와 WellnessBox POST /api/tips를 연결한다. C:/dev/wellnessbox/scripts/qa/check-rnd-final-safety-authority.cts는 최종 차단, 계약 오류, 식별자 변환을 검사하고, check-rnd-interim-safety-authority.cts는 중간 응답 계약을 점검한다.

초기 통합 커밋 e830c7 계열은 저장·현재 입력을 합치기 전 각각 검사한 뒤 보수적으로 병합하고, 모델 예측 뒤에도 안전 판정을 반복하도록 바꿨다. 서비스 커밋 9609ce 계열은 잘못된 상위 응답을 서비스에서 다시 차단하고 /api/tips에 최종 권한 검사를 연결했다. 이 변경은 보고된 한 사례만 예외 처리한 것이 아니라, 안전 입력과 최종 응답이라는 공통 경계를 수정했다.

## 등록 근거와 저장 결과의 실제 범위

manifest에 등록된 구현 경로는 apps/inference_api/routes/interim.py, src/wellnessbox_rnd/interim/safety.py, C:/dev/wellnessbox/app/api/tips/route.ts, C:/dev/wellnessbox/lib/server/wb-rnd-interim-route.ts, C:/dev/wellnessbox/lib/server/wb-rnd-interim-safety-authority.ts다. 테스트 경로는 tests/test_interim_api.py, scripts/run_wellnessbox_final_safety_authority_smoke.py, C:/dev/wellnessbox/scripts/qa/check-rnd-final-safety-authority.cts, C:/dev/wellnessbox/scripts/qa/check-rnd-interim-safety-authority.cts다. 모든 파일이 존재하며 설명한 역할과 맞는다.

통합 근거는 data/original_plan/evidence/op040_final_safety_authority_integration_smoke_v1.json, .github/workflows/original-plan-evidence.yml, C:/dev/wellnessbox/.github/workflows/encoding-guard.yml, data/original_plan/final_session/operational_evidence/OP-040.json이다. 저장된 통합 스모크는 SAFE-EMERGENCY-001, STOP_AND_ESCALATE, BLOCKED, 추천 0건, 잘못된 계약과 매핑 실패의 HTTP 502를 기록한다. 다만 transport는 localhost_http, claimed_evidence_stage는 INTEGRATED, production_operation_proven은 false다.

같은 스모크의 성분 맵 버전은 2026-07-16.1이지만 현재 두 저장소의 맵은 2026-07-24.1이다. 안전 차단 관측은 유효한 과거 통합 결과지만, 현재 성분 맵을 사용한 새 통합 실행 결과는 아니다. 두 CI 파일은 관련 스크립트와 QA를 실행하도록 구성되어 있으나 이번 문서 검토에서는 CI나 스모크를 재실행하지 않았다.

## 운영 기록과 최종 판단

data/original_plan/final_session/operational_evidence/OP-040.json은 schema_version=local_operational_session_receipt_v1, data_class=ACTUAL, environment_id=wellnessbox-local-research-pc를 기록한다. executed_paths에는 recommendation이 있고 recommendation_runs와 recommendation_items가 각각 1 증가했다. Ed25519 서명과 두 저장소의 소스 커밋도 포함한다. 이 기록은 로컬 연구 운영에서 추천 경로를 실행했다는 근거지만, 안전 차단을 관측한 근거는 아니다. 오히려 recommendation_items가 1 증가했으므로 이 세션은 추천 0건을 만드는 차단 사례와 다르다. operational_action_coverage_v1.json이 recommendation 행동을 OP-040에 연결한 사실만으로 요구사항 특유의 최종 차단 권한까지 운영됐다고 볼 수는 없다.

요구사항 내용에 맞춰 평가한 현재 근거 단계는 INTEGRATED다. localhost HTTP로 R&D와 WellnessBox를 연결한 스모크가 STOP_AND_ESCALATE, BLOCKED, 추천 0건과 서비스 재차단을 입증한다. 반면 등록 운영 기록은 차단 결과를 표시하지 않고 추천 항목 1건을 남겨, 최종 차단 권한을 실제 자료로 운영했다는 OPERATED 근거가 되지 못한다. 즉 manifest의 claimed_stage=OPERATED는 현재 등록 파일 내용보다 한 단계 높다. 공개 배포 URL, 배포 식별자, 프로덕션 로그, 현재 2026-07-24.1 맵으로 재실행한 결과와 EXTERNAL 검증도 없다.
