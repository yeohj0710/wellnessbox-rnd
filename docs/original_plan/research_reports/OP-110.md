# OP-110 소분, 배송, 재주문, 취소 상태를 계획에 읽기 전용으로 환류한다.

## 결론

OP-110은 `IMPLEMENTED` 단계다. WellnessBox 서비스는 사용자의 최신 주문 상태를 읽고 소분, 배송, 재주문, 취소 상태로 정규화해 R&D 계획 컨텍스트 API에 보낸다. 별도 FastAPI 프로세스까지 실제 HTTP 왕복을 확인했다. R&D는 현재 계획 상태와 주문 컨텍스트를 반환하지만 실행 이벤트와 주문 상태를 바꾸지 않는다. 실제 Prisma 주문 조회는 fixture로 대체했으므로 요구 단계 `OPERATED`에 못 미치며 완료 판정은 `PARTIAL`이다.

## 요구사항 해석

주문 상태 환류는 주문 시스템을 R&D가 제어한다는 뜻이 아니다. 주문 서비스가 가진 사실을 계획이 참고할 수 있게 전달하되, R&D는 그 사실을 읽기 전용으로 취급해야 한다. 소분이 완료됐는지, 배송 중인지, 배송이 끝나 재주문을 검토할 수 있는지, 주문이 취소됐는지를 계획 설명과 후속 판단에 사용할 수 있어야 한다.

읽기 전용이라는 조건은 두 가지를 요구한다. 서비스는 조회 전용 Prisma 쿼리만 사용해야 한다. R&D는 주문 컨텍스트를 받았다는 이유로 주문 레코드나 계획 실행 이벤트를 자동 변경하면 안 된다. 이번 구현은 입력과 출력 계약에 `read_only`, `order_state_effect`, `order_state_mutation_allowed`를 고정하고 이벤트 수가 호출 전후 같은지 확인한다.

## 서비스의 상태 조회

`createOrder`는 클라이언트가 보낸 execution ID와 plan ID를 그대로 저장하지 않는다. 인증된 앱 사용자 ID를 가명처리한 profile ID와 execution·plan을 R&D `/plans/bindings/validate` API에 보내 소유권과 계획 존재를 먼저 확인한다. 검증이 실패하면 주문을 만들지 않는다. 검증된 결합만 주문 열에 저장한다.

`getOrderPlanContextByBinding`은 인증된 애플리케이션 사용자 ID, 주문 ID, 검증된 R&D execution ID, plan ID가 모두 일치하는 주문 하나만 조회한다. 따라서 같은 사용자에게 여러 주문과 계획이 있어도 무관한 주문 상태를 다른 계획에 전달하지 않는다. 선택 필드는 주문 ID, 상태, 갱신 시각뿐이다. 주소, 전화번호, 비밀번호, 결제 식별자 같은 주문 개인정보는 R&D에 전달하지 않는다. 바인딩이 없으면 서비스는 404를 반환한다.

서비스 라우트는 사용자 세션을 먼저 확인하고 요청에서 `execution_id`와 `plan_id`를 받는다. 앱 사용자 ID는 기존 HMAC 가명처리 함수를 거쳐 R&D profile ID가 된다. 주문 조회는 원래 앱 사용자 ID로 수행하지만 R&D에는 앱 사용자 ID를 보내지 않는다. 인증이 실패하면 주문 조회와 R&D 요청을 모두 중단한다.

## 주문 상태 정규화

서비스의 `mapOrderToReadOnlyPlanContext`는 알려진 주문 상태만 허용한다. 알 수 없는 상태를 추측하지 않고 `WB_RND_ORDER_CONTEXT_unknown_order_status`로 실패한다. 알려진 여섯 상태는 결제 완료, 상담 완료, 조제 완료, 픽업 완료, 배송 완료, 주문 취소다.

결제 완료와 상담 완료는 `packaging_state=PENDING`, `delivery_state=PENDING`, `reorder_state=NOT_ELIGIBLE`로 해석한다. 조제 완료는 소분·조제가 끝난 것으로 보고 `packaging_state=COMPLETE`를 반환한다. 픽업 완료는 배송 인계가 시작된 상태로 보고 `delivery_state=IN_TRANSIT`를 반환한다. 배송 완료는 `delivery_state=DELIVERED`, `reorder_state=ELIGIBLE`이 된다. 주문 취소는 소분, 배송, 재주문, 취소 상태를 모두 취소 경계로 닫는다.

이 매핑은 주문 상태를 바꾸지 않는다. 재주문 `ELIGIBLE`도 자동 주문을 뜻하지 않는다. 사용자가 다음 주문을 검토할 수 있다는 계획 컨텍스트일 뿐 카트, 재고, 주문, 결제를 만들지 않는다. R&D가 `ELIGIBLE`을 받아도 action space에 구매 실행 권한이 생기지 않는다.

## R&D 읽기 전용 API

`POST /v1/interim/plans/order-context`는 실행 ID, profile ID, plan ID, 주문 ID, 원래 주문 상태, 네 개의 정규화 상태, 관측 시각을 받는다. Pydantic 모델은 추가 필드를 거부하고 상태 값을 제한한다. 관측 시각에는 시간대가 있어야 한다.

API는 실행이 존재하는지, 실행의 profile ID가 요청과 같은지 확인한다. 해당 실행의 이벤트를 읽어 계획 생명주기 상태를 재구성하고 plan ID가 없으면 404로 실패한다. 일치하면 현재 계획 상태와 받은 주문 컨텍스트를 반환한다. 실행 이벤트를 insert하거나 update하지 않는다.

응답은 `read_only=true`, `order_state_effect=NONE`, `order_state_mutation_allowed=false`를 고정한다. `persisted_event_count_before`와 `persisted_event_count_after`도 반환한다. 단위 테스트와 두 프로세스 QA 모두 두 값이 같음을 확인한다. 현재 계획 상태도 여섯 주문 상태 호출 동안 `ACTIVE`로 유지된다.

## 실제 HTTP 왕복 검증

canonical runner는 임시 SQLite를 만들고 사용자, 동의, 실행, 활성 계획 이벤트를 심는다. 별도 포트에서 실제 FastAPI 애플리케이션을 시작한다. Node QA는 WellnessBox의 실제 `runUserInterimOrderPlanContextRoute`와 `callWbRndInterim`을 사용한다. 주문 조회 함수만 여섯 상태 fixture를 반환하도록 주입한다.

각 요청은 서비스의 사용자 인증, profile ID 가명처리, 상태 매핑, 내부 토큰 HTTP 클라이언트, R&D Pydantic 검증, 계획 상태 재구성을 차례로 지난다. 결제 완료부터 주문 취소까지 여섯 상태가 모두 200을 반환하고 계획 상태와 이벤트 수를 보존한다. 이 결과는 서비스와 R&D의 계약 및 HTTP 연결을 증명한다.

하지만 주문 조회는 `getLatestOrderPlanContextByAppUserId`의 실제 Prisma 실행이 아니다. fixture가 주문 ID, 상태, 갱신 시각을 제공한다. 따라서 실제 서비스 데이터베이스와 R&D API가 한 경로에서 연결됐다고 주장하지 않는다. 이 제한 때문에 단계는 `IMPLEMENTED`다.

## 개인정보와 권한 경계

R&D에 전달되는 주문 데이터는 ID, 상태, 갱신 시각에서 파생된 관측 시각뿐이다. 주문 주소, 상세 주소, 전화번호, 공동현관 비밀번호, 결제 ID, 거래 ID, 가격은 전송하지 않는다. profile ID는 서비스 사용자 ID를 HMAC으로 가명처리한 값이다.

사용자 인증 실패 검사는 401 응답을 확인한다. 인증 실패 뒤 주문 조회나 R&D 호출이 발생하면 QA가 즉시 실패한다. R&D는 별도 내부 토큰을 요구한다. 서비스 세션과 내부 API 토큰이 서로 다른 경계를 보호한다.

## canonical evidence와 판정

데이터셋은 8개 사례를 담는다. OP-110 사례는 소분·배송 매핑, 배송 완료 후 재주문 가능 상태, 취소 상태, 호출 전후 무변경을 포함한다. 증거의 `six_order_statuses_mapped`와 `order_context_read_only`가 모두 참이어야 runner가 성공한다.

증거는 서비스 커밋, R&D runner 소스 커밋, R&D API·계획 생명주기·데이터셋·runner blob SHA를 기록한다. `actual_rnd_http_roundtrip_proven`은 참이다. `actual_prisma_order_status_query_proven`과 `production_operation_proven`은 거짓이다. 판정에 필요한 긍정 증거와 미검증 경계를 같은 파일에 남겼다.

## 오류 처리

요청에 execution ID나 plan ID가 없으면 서비스는 400을 반환한다. 인증된 사용자의 주문이 없으면 404다. 알 수 없는 주문 상태는 502 fail-closed 응답으로 바뀐다. R&D 실행 또는 계획이 없으면 404, profile ID가 다르면 403이다. 시간대 없는 관측 시각이나 허용되지 않은 상태 값은 422다.

이 실패들은 주문이나 계획 이벤트를 바꾸지 않는다. 컨텍스트 읽기가 실패해도 기존 계획과 주문은 그대로 남는다. 호출자가 오류를 정상 상태로 추측해 자동 재주문을 실행할 수 없게 했다.

## 재현과 남은 단계

`python scripts/run_order_plan_context_integration_smoke.py`로 두 프로세스 증거를 재생할 수 있다. 계획 생명주기 단위 검사는 `python -m pytest tests/test_plan_lifecycle.py -q`로 실행한다. 서비스 타입과 인코딩은 `npm run typecheck`, `npm run audit:encoding`으로 확인한다.

다음 검증은 격리된 PostgreSQL에서 실제 사용자 주문 여섯 상태를 만들고 `getOrderPlanContextByBinding`을 실행해야 한다. 최소 선택 필드만 반환되는지, 다른 사용자·execution·plan의 주문이 섞이지 않는지 확인해야 한다. 이후 승인된 환경에서 실제 배송 상태 변화가 계획 화면에 반영되되 주문과 이벤트가 변하지 않는지 관측해야 `INTEGRATED`와 `OPERATED` 승격을 검토할 수 있다.
## 서비스에 연결할 때 확인한 경계
서비스 통합은 R&D 코드가 존재한다는 사실만으로 끝나지 않는다. 두 저장소의 계약, 인증, 실제 요청·응답, 상품·주문 경계와 상태 환류를 같은 실행에서 확인해야 하며, 승인 전 데이터 변경은 허용하지 않는다.

`OP-110`는 “소분, 배송, 재주문, 취소 상태를 계획에 읽기 전용으로 환류한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

- 테스트·실행: `wellnessbox-rnd/tests/test_plan_lifecycle.py`, `wellnessbox/scripts/qa/check-rnd-order-plan-context.cts`, `wellnessbox-rnd/scripts/run_order_plan_context_integration_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op109_op110_order_plan_context_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
