# OP-008 증거가 없는 완료 표기를 거부하는 manifest 감사기를 만든다.

## manifest에 경로를 적는 것만으로는 증거가 되지 않는다

`implementation_files`에 그럴듯한 파일명을 넣는 일은 쉽다. 파일이 존재하지 않거나 Git에 추적되지 않아도 문자열 자체는 비어 있지 않다. `../`를 사용해 다른 저장소의 파일을 가리키거나, 서비스 파일을 R&D 소유 증거라고 적을 수도 있다. 원본 PDF가 바뀌었는데 예전 요구사항을 그대로 감사하면 숫자는 정상처럼 보여도 기준 문서가 달라진다. OP-008이 요구하는 실제 결과는 이런 manifest를 PASS로 처리하지 않는 감사기다.

구현 증거는 `wellnessbox-rnd/src/wellnessbox_rnd/governance/original_plan_audit.py`와 public export를 제공하는 `wellnessbox-rnd/src/wellnessbox_rnd/governance/__init__.py`다. 감사기는 Pydantic schema 계약을 먼저 확인한 뒤 원본 PDF, completion program, 각 주장 단계의 evidence 경로를 실제 저장소 root와 Git index에 대조한다. 문제가 하나라도 있으면 status는 `FAIL`이고, issue가 없을 때만 `PASS`다.

## 감사 입력은 manifest와 두 저장소 root다

`audit_original_plan_manifest_v1`은 manifest, repository roots, 선택적인 tracked-file 집합을 받는다. repository root 키는 OP-007이 고정한 `wellnessbox-rnd` 또는 `wellnessbox`다. 일반 실행에서는 각 root에 `git ls-files -z`를 호출해 현재 Git이 추적하는 상대 경로 집합을 만든다. 테스트에서는 고정 tracked-file 집합을 주입해 untracked 경계를 결정적으로 재현할 수 있다.

Git index를 읽지 못하면 빈 집합으로 조용히 계속하지 않는다. `tracked_file_index_unavailable` issue를 남기고 해당 저장소의 tracked set을 빈 값으로 둔다. 감사 결과는 issue가 있으므로 FAIL이다. Git 명령 실패를 “증거 없음”과 구분해 기록하면서도 완료 판정을 허용하지 않는 fail-closed 동작이다.

## 원본 PDF는 경로와 SHA-256을 함께 확인한다

manifest의 `original_plan_path`는 `wellnessbox-rnd/docs/context/original_plan.pdf`를 가리킨다. 감사기는 먼저 저장소 접두사를 해석하고 root 안의 절대 경로로 변환한다. 파일 존재와 Git 추적 여부를 확인한 뒤 실제 bytes의 SHA-256을 계산한다. 현재 manifest의 고정값 `31291e6f93977fa2d5d083d0161743c49debef25caf12dccf6edc7fa1c2197d4`와 다르면 `original_plan_sha256_mismatch`를 기록하고 `source_hash_matches=false`가 된다.

이번 시각 검토에서 25쪽은 일곱 KPI의 목표와 가중치를, 26쪽은 각 수식과 최소 표본을 담고 있음을 다시 확인했다. OP-008은 수식 자체를 재계산하는 요구가 아니다. 감사 대상 manifest가 바로 그 PDF bytes를 기준으로 작성됐는지 확인한다. 원문이 바뀌면 새 요구 분석과 manifest 갱신 없이 기존 PASS를 재사용할 수 없다.

## 저장소 접두사와 소유자가 일치해야 한다

`implementation_files`, `test_files`, `integration_evidence`, `operational_evidence`, `replacement_contracts`에 등록한 모든 파일형 reference는 `wellnessbox-rnd/` 또는 `wellnessbox/`로 시작해야 한다. `_parse_repository_reference`는 이 접두사와 나머지 상대 경로를 분리한다. 접두사가 없거나 빈 상대 경로면 `evidence_reference_invalid`다. 각 reference의 저장소가 요구사항 `owners`에 없으면 `evidence_owner_not_declared`를 낸다. 파일 경로가 아닌 `external_dependencies` 문자열은 이 경로 감사 대상에서 제외된다.

이 규칙은 두 저장소의 책임을 섞지 않게 한다. R&D 알고리즘 구현을 서비스 파일로 대신하거나 서비스 통합을 R&D fixture로 대신할 수 없다. 여러 저장소가 실제로 공동 소유하는 요구라면 owners에 두 값을 명시해야 한다. OP-008 자체는 R&D 감사기만 소유하므로 서비스 저장소를 구현 증거로 사용하지 않는다.

## root 밖으로 빠져나가는 경로는 존재해도 실패한다

감사기는 reference를 `/` 기준 POSIX 상대 경로로 정규화한 뒤 repository root와 결합해 resolve한다. 최종 절대 경로가 root의 하위 경로인지 `is_relative_to`로 확인한다. `wellnessbox-rnd/../wellnessbox/AGENTS.md`처럼 실제 파일이 존재하더라도 R&D root를 벗어나면 `evidence_path_escape`다. 원본과 completion program에도 같은 root 경계 검사를 적용한다.

경로 탈출 방지는 단순 파일 존재 검사보다 먼저 필요한 경계다. 두 저장소가 같은 상위 디렉터리에 있기 때문에 `..`를 허용하면 한 저장소의 추적 파일을 다른 저장소 증거처럼 사용할 수 있다. resolve된 최종 경로를 root와 비교하므로 중간의 `.`이나 `..` 표기 방식에 기대지 않는다.

## 존재하는 파일도 Git에 추적되지 않으면 canonical evidence가 아니다

경로가 root 안에 있어도 `is_file()`이 거짓이면 `evidence_file_missing`이다. 파일이 존재하지만 `git ls-files` 결과에 없으면 `evidence_file_untracked`다. 로컬 `etc/`, 임시 로그, 아직 stage하지 않은 draft, 개인 checkout 결과는 이 조건을 통과하지 못한다. 원본 PDF와 completion program에도 각각 missing·untracked 검사를 적용한다.

이 구분은 현재 작업 방식과 맞닿아 있다. R&D worktree에는 보호된 untracked `etc/`가 있지만 manifest evidence로 등록하지 않는다. 서비스 저장소에는 사용자가 수정한 파일과 untracked QA script가 있지만 이번 loop는 건드리거나 증거로 재사용하지 않는다. canonical evidence는 저장소에 커밋돼 다른 환경에서 같은 path로 checkout할 수 있어야 한다.

## 단계별 최소 증거 계약도 같은 감사에서 다시 실행한다

OP-008은 경로만 확인하지 않는다. 먼저 `validate_original_plan_manifest_v1`을 호출해 그룹 순서, 120개 ID 연속성, 중복, 그룹별 10개 요구, 단계별 필수 evidence 목록을 검사한다. `OP-031:implemented_claim_missing_test_files` 같은 계약 오류에서 OP ID를 추출해 `manifest_contract_violation` issue에 연결한다. 경로가 모두 존재해도 claimed stage에 필요한 목록이 빠지면 FAIL이다.

현재 claimed stage가 있는 119개 요구사항만 evidence file 검사를 받는다. 아직 단계를 주장하지 않은 항목은 존재하지 않는 증거를 억지로 요구하지 않는다. 반면 주장한 항목은 단계에 필요한 모든 등록 경로를 검사한다. 같은 reference가 여러 요구에 쓰이면 checked-file count에서는 집합으로 한 번만 세지만, 소유자나 경로 오류는 해당 requirement ID에 귀속된다.

## 감사 보고서는 재현 가능한 사실과 issue 목록을 함께 남긴다

`OriginalPlanAuditReportV1`은 PASS/FAIL, manifest schema version, canonical manifest SHA-256, requirement count, claimed requirement count, 단계별 주장 수, 검사한 evidence 파일 수, 원본 hash 일치 여부, issue 목록을 가진다. 현재 감사 결과는 요구 120개, 주장 119개, 구현 88·통합 31·운영 0·외부 0, 확인한 evidence 파일 333개, source hash 일치, issue 0이다.

manifest SHA-256은 모델을 JSON으로 직렬화할 때 key를 정렬하고 compact separator를 사용해 계산한다. 같은 manifest는 운영체제의 공백이나 key 입력 순서와 무관하게 같은 hash를 낸다. 감사 보고서가 성공 숫자만 출력하지 않고 어떤 manifest를 검사했는지 식별할 수 있는 이유다.

## 테스트는 누락, 오소유, 경로 탈출, untracked, 원본 변조를 각각 재현한다

테스트 증거 `wellnessbox-rnd/tests/test_original_plan_audit.py`는 현재 manifest와 실제 두 저장소 root를 감사해 PASS, 120개 요구, 119개 주장, 원본 hash 일치, issue 0을 확인한다. 그다음 manifest 복사본을 바꿔 실패 분기를 하나씩 실행한다. 존재하지 않는 구현 파일은 `evidence_file_missing`, 다른 저장소만 owners로 지정하면 `evidence_owner_not_declared`, `../` reference는 `evidence_path_escape`가 된다.

tracked-file 집합을 빈 값으로 주입하면 `evidence_file_untracked`가 생긴다. 원본 SHA-256을 0으로 바꾸면 `source_hash_matches=false`와 `original_plan_sha256_mismatch`를 확인한다. 구현 주장에 테스트 목록을 비우면 OP-031에 귀속된 `manifest_contract_violation`이 나온다. 한 개의 “잘못된 manifest 실패” 테스트로 뭉치지 않고 실패 이유별 계약을 고정했다.

## 오류 입력은 issue로 모으되 PASS로 축소하지 않는다

감사기는 첫 오류에서 예외로 끝내기보다 가능한 issue를 모아 한 보고서로 반환한다. 잘못된 reference, path escape, missing, untracked, owner mismatch가 각각 다른 code를 가진다. 사용자는 어느 OP의 어느 evidence field가 어떤 reference 때문에 실패했는지 확인할 수 있다. 여러 오류를 한 번에 고칠 수 있지만, issue가 하나라도 남으면 status는 FAIL이다.

이 동작은 Pydantic이 manifest JSON 자체를 읽지 못하는 경우까지 복구한다는 뜻은 아니다. schema parsing 단계에서 형식이 완전히 깨지면 load가 실패한다. 정상 schema로 읽히는 manifest 안의 계약·경로 문제를 구조화 issue로 모으는 범위다. Git tracked 여부도 현재 checkout의 index를 기준으로 하므로 원격 branch의 존재나 CI 성공을 대신 확인하지 않는다.

## 감사기가 증거 파일 내용의 진실성까지 판정하지는 않는다

추적된 파일이 존재한다는 사실과 그 파일이 claimed stage를 실제로 증명한다는 사실은 다르다. 예를 들어 integration evidence라는 이름의 Markdown 파일이 있어도 실제 두 프로세스 왕복이 없을 수 있다. OP-008은 일반적인 모든 파일 형식을 이해해 내용의 진위를 판정하지 않는다. 파일의 의미 검증은 해당 OP의 focused test, canonical smoke, completion generator, CI, 독립 검토가 맡는다.

운영과 외부검증도 마찬가지다. `operational_evidence` 경로가 추적됐다는 이유만으로 production traffic을 자동 인정할 수 없다. 외부 receipt의 발급자와 서명은 OP-120 최종 감사가 별도 신뢰 목록과 Ed25519 검증으로 확인한다. OP-008의 역할은 최소한 존재하지 않거나 재현할 수 없는 파일을 완료 증거로 사용하는 첫 관문을 닫는 것이다.

## canonical evidence가 만들어지는 순서

첫째, strict schema로 manifest를 읽는다. 둘째, 원본 PDF와 completion program의 경로·추적·hash를 확인한다. 셋째, claimed requirement마다 단계별 최소 목록과 소유 저장소를 확인한다. 넷째, `external_dependencies`를 제외한 파일형 evidence reference를 root 안의 tracked file과 대조한다. 다섯째, canonical manifest hash와 집계 수치, issue 목록을 보고서로 직렬화한다. `scripts/audit_original_plan_requirements.py`는 이 함수를 CLI에서 실행하고 GitHub workflow도 같은 경로를 사용한다.

감사기 구현은 2026-07-15의 `17da3a15e7bd755a1074682ca40f7b532b1008e3` 커밋에서 도입됐다. 같은 날 `a449b605dceb29471103076d03de4e137ce421a5`가 CLI와 GitHub Actions gate를 연결했다. OP-008 manifest의 implementation evidence는 audit module과 governance export, test evidence는 위 부정 테스트 파일을 가리킨다.

## 현재 완료 단계와 남은 조건

OP-008의 required stage와 claimed stage는 모두 `IMPLEMENTED`다. 원본 hash, root 경계, owner, 파일 존재, Git 추적, 단계별 최소 목록을 검사하는 감사기와 각 실패 분기를 실행하는 테스트가 있으므로 구현 단계는 충족한다. 작성 직전 전체 audit는 PASS였고 canonical 최종 감사 evidence SHA-256은 `6d761eba95504e84b5de02fe1efdca62604cdad2235d4fecfff9db1c7e3e6b71`, 마지막 성공 GitHub Actions는 `29917930551`이다.

서비스 통합, production 운영, 외부검증은 OP-008 자체의 요구 단계가 아니다. 이번 보고서 작성은 서비스 저장소, 원천 데이터, frozen dataset, 학습, 모델, 시뮬레이션을 바꾸지 않는다. 남은 조건은 다른 OP의 증거 내용과 실제 stage 부족을 해결하는 일이다. 현재 43개 PARTIAL과 OP-039 외부 검증 부족은 감사기가 사라지게 만들 수 있는 문제가 아니다. OP-008의 결과는 완료 표시를 늘리는 기능이 아니라, 존재하지 않거나 소유권이 틀리거나 재현할 수 없는 파일로 완료 표시를 만드는 일을 거부하는 기능이다.
## 원문을 요구사항으로 바꾸는 과정
이 그룹은 기능을 먼저 만들기보다, 원문에서 무엇을 읽었고 어느 파일이 그 해석을 지지하는지 고정하는 데서 출발한다. 원본 해시, 페이지, 요구사항 ID, 증거 단계가 따로 남아 있어야 나중에 코드가 바뀌어도 출발점과 해석을 다시 대조할 수 있다.

`OP-008`는 “증거가 없는 완료 표기를 거부하는 manifest 감사기를 만든다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=1-59`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/governance/original_plan_audit.py`, `wellnessbox-rnd/src/wellnessbox_rnd/governance/__init__.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_original_plan_audit.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
