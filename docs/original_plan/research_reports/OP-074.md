# OP-074 CronJob이 만기 계획을 찾아 재평가 작업을 생성한다.

OP-074가 요구하는 결과는 주기 실행 자체가 아니라, 만기된 활성 후속 계획만 찾아 재평가 업무를 정확히 한 건씩 만드는 것이다. manifest의 실행 진입점 `wellnessbox-rnd/scripts/run_due_plan_reevaluation_cron.py`와 큐 구현을 대조하면 예약 검색·중복 방지·계획 재검사는 구현돼 있다. 반면 등록 운영 영수증은 Cron 호출과 `PLAN_REEVALUATION` 업무를 식별하지 못하므로 직접 증거 단계는 `IMPLEMENTED`로 판정한다.

## 만기 검색이 지켜야 하는 선택 조건

저장된 후속 일정이 있어도 주기 작업이 예정일을 업무로 바꾸지 않으면 상태기계는 다음 판단으로 넘어가지 않는다. 너무 일찍 업무를 만들면 아직 수집되지 않은 설문이나 기기 자료로 재평가할 수 있고, 매 실행마다 같은 행을 추가하면 한 계획을 여러 번 판단할 수 있다. 이미 중단된 실행을 단순히 `due_at` 조건만으로 고르는 경우에는 안전 중단 뒤 새 추천이 열리는 더 큰 문제가 생긴다.

`WorkflowJobQueue.enqueue_due_plan_reevaluations()`는 `followups.status`가 `OPEN` 또는 `REEVALUATION_QUEUED`이고 `due_at <= as_of`인 행을 조회한다. 결과는 예정 시각과 후속 식별자 순서로 정렬된다. 각 후보의 `execution_id`, `profile_id`, `plan_id`를 다시 읽어 실행 계획이 활성인지 확인한다. 활성 상태가 아니면 재평가 업무를 만들지 않고 후속 기록을 닫으며 관련 준비·선점 업무를 취소한다.

## 반복 호출을 한 업무로 수렴시키는 방식

만기 후보가 유효하면 `_enqueue_in_transaction()`이 `PLAN_REEVALUATION` 업무를 만들고 후속 상태를 `REEVALUATION_QUEUED`로 바꾼다. 멱등 키는 `plan-reevaluation:{followup_id}`다. 다음 Cron이 같은 후보를 다시 읽더라도 고유 키와 동일 업무 내용이 기존 `job_id`를 반환하며, 결과의 `deduplicated` 수만 증가한다. 업무 내용에는 원래 `due_at`, 정렬된 `requested_data`, 당시 활성 동의의 `consent_snapshot_id`, 실행 이벤트 지문 `execution_evidence_sha256`가 보존된다.

이 자료는 단지 중복 생성을 막는 값이 아니다. Cron 실행 뒤 작업자가 가져가기 전 계획이 중단되거나 동의·근거가 바뀔 수 있으므로 `claim_ready_jobs()`가 활성 계획과 두 안전 기준을 다시 검사한다. 생성 시 유효했다는 사실로 실행 시점의 유효성을 대신하지 않는다. 선점 뒤 변경은 `acknowledge_job()`에서 한 번 더 검사하므로 완료 상태로 잘못 넘어가지 않는다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`가 검색과 생성을 맡고, `wellnessbox-rnd/apps/inference_api/routes/interim.py`의 `/agent/cron/due-plans` 경로와 명령행 스크립트가 이 함수를 공유한다. `wellnessbox-rnd/scripts/run_due_plan_reevaluation_cron.py`는 저장소 경로와 선택적인 `--at` 시각을 받아 큐를 열고 `created`, `deduplicated`, 생성 업무 식별자를 출력한다. 서버 API에서는 임의 `as_of` 입력을 기본적으로 현재 UTC로 덮어쓰며, `WB_RND_ALLOW_CRON_AS_OF_OVERRIDE=1`인 시험 환경에서만 호출자가 기준 시각을 바꿀 수 있다.

## 초기 구현 이후 추가된 안전 장치

커밋 `aeacb64`에서 만기 조회와 `plan-reevaluation:{followup_id}` 중복 제거가 처음 들어왔다. 그 시점의 diff는 후속 기록과 업무 큐 연결을 만들었지만, 실행 계획의 식별자와 작업자 임대 중 상태 변화에 대한 방어가 현행보다 약했다. 커밋 `21dade`는 `execution_id`를 필수 연결로 추가하고 Cron 생성 시 및 업무 선점 시 활성 계획을 확인하도록 바꿨다. 같은 수정에서 API의 과거·미래 기준 시각 덮어쓰기를 환경변수 뒤로 숨겨 운영 호출자가 임의 시점의 업무를 대량 생성할 가능성도 줄였다.

커밋 `948aca`는 Cron이 업무를 만든 직후 계획이 중단되는 순서를 회귀 사례로 고정했다. 현재 `claim_ready_jobs()`는 SQL 조회로 `READY` 행을 찾은 뒤에도 실행 수명주기를 계산하고, 중단된 계획의 업무를 `CANCELLED`로 바꾼다. 과거 스키마에서 실행 연결이 비어 있던 업무도 마이그레이션 때 `LEGACY_UNLINKED_EXECUTION`으로 취소되므로 새 검사에 필요한 식별자가 없는 행을 실행하지 않는다.

수정 전 운영 장애 로그나 실제 중복 재평가 건수는 저장소에 남아 있지 않다. 여기서 설명한 실패 순서는 git diff가 보여 주는 코드 변화와 현행 테스트가 재현하는 조건에 근거하며, 프로덕션 사고가 있었다고 확대 해석하지 않는다.

## 경계 시각과 중단 직후를 검사한 테스트

`wellnessbox-rnd/tests/test_interim_jobs.py`의 `test_cron_creates_one_reevaluation_job_only_when_due`는 만기 전 생성 0건, 만기 시점 생성 1건, 다음 재실행의 신규 0건·중복 1건을 단언한다. `test_cron_orders_multiple_due_followups_and_excludes_closed`는 서로 다른 예정 시각의 결과 순서와 이미 닫힌 후속 기록의 제외를 확인한다. `test_claim_rechecks_plan_after_cron_enqueue`는 업무 생성 후 계획 중단 이벤트를 넣고 선점 결과가 비어 있으며 해당 업무가 취소되는지를 검사한다.

`wellnessbox-rnd/tests/test_interim_api.py`의 `test_due_plan_cron_endpoint_enqueues_shared_reevaluation_job`은 내부 인증을 거쳐 HTTP 경로를 호출한 뒤 동일 공용 큐에 `PLAN_REEVALUATION` 한 건이 생기는지 본다. 서비스 함수만 직접 호출하는 시험으로는 놓칠 수 있는 라우트 연결과 입력 시각 제한을 포함한 확인이다. 외부 스케줄러가 정해진 간격으로 API나 명령을 호출했다는 단언은 이 테스트 묶음에 없다.

## 스모크 결과를 읽을 때의 시간 경계

`wellnessbox-rnd/scripts/run_followup_job_queue_cron_smoke.py`는 임시 SQLite에 두 활성 계획을 심고 네 번의 기준 시각으로 큐 함수를 실행한다. 그 출력인 `wellnessbox-rnd/data/original_plan/evidence/op073_op074_followup_job_queue_cron_smoke_v1.json`에서 2026-07-21 11:59:59 UTC 결과는 생성 0건이다. 12:00에는 첫 업무 1건, 13:00에는 둘째 업무 1건과 기존 업무 중복 1건, 다음 날에는 신규 0건과 중복 2건이 기록돼 있다. 최종 업무 표에는 알림 2건과 재평가 2건만 남는다.

스모크 JSON은 `op074_proven_stage=IMPLEMENTED`와 함께 `deployed_cron_schedule_proven=false`, `production_queue_operation_proven=false`, `service_integration_proven=false`, `production_deployment_proven=false`를 명시한다. 또한 `source_commit=24d82df`의 기록된 묶음 해시 `207848…`은 현재 관련 파일로 계산한 `fa8d34…`와 다르다. 이는 고정 결과의 생성 시점을 알려 주는 제한이다. 이후 커밋의 현행 소스가 같은 바이트였다는 증거로 이 JSON을 사용하지 않는다.

## 장부 표기와 직접 관찰의 차이

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-074.json`을 운영 증거로 등록했다. 파일에는 `data_class=ACTUAL`, 로컬 연구 PC 세션, `followup` 실행 경로, `workflow_jobs +1`이 있다. 그러나 Cron 실행 시각, `followup_id`, `job_type`, `deduplicated`, 선점 또는 완료 결과가 없어서 증가한 행이 알림인지 만기 재평가인지 판단할 수 없다.

따라서 현재 보고서의 결론은 `IMPLEMENTED`다. 함수·명령행·API 연결과 경계 시각 회귀 시험은 요구 동작을 뒷받침하지만, 배포된 CronJob의 예약표, 실제 호출 성공률, 중단 기간 뒤 재기동, 운영 작업자의 처리 완료는 확인되지 않았다. `OPERATED` 주장을 뒷받침하려면 호출 시각과 기준 시각, 만기 후속 식별자, 생성된 `PLAN_REEVALUATION` 업무 식별자, 중복 여부, 최종 상태를 같은 운영 영수증에 남겨야 한다.
## 다음 행동을 결정하는 순서
Closed-loop는 추천 한 번을 자동화하는 기능이 아니라 상태를 다시 읽고 다음 작업을 정하는 흐름이다. 이 그룹은 상태 전이, 예약, 재평가, 이상사례 중단, 약사 검토와 주문 경계를 시간 순서로 확인한다.

`OP-074`는 “CronJob이 만기 계획을 찾아 재평가 작업을 생성한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.
