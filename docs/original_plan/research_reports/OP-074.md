# OP-074 CronJob이 만기 계획을 찾아 재평가 작업을 생성한다.

manifest가 가리키는 실행 진입점은 `wellnessbox-rnd/scripts/run_due_plan_reevaluation_cron.py`이며, 기준 결과는 `wellnessbox-rnd/data/original_plan/evidence/op073_op074_followup_job_queue_cron_smoke_v1.json`에 보존돼 있다.

## 예정일이 지났을 때만 재평가를 열어야 한다

후속 일정이 저장돼 있어도 만기 항목을 찾아 다음 작업으로 바꾸는 절차가 없으면 상태기계는 멈춘다. 반대로 주기 실행 명령이 돌 때마다 같은 재평가를 새로 만들면 한 계획을 여러 번 판단할 수 있다. OP-074의 핵심은 현재 시각 이전에 만기가 된 활성 후속 기록만 고르고, 각 후속 기록에 재평가 작업을 정확히 하나만 연결하는 것이다.

## 시각 검색과 작업 생성을 같은 큐 서비스에 모았다

`WorkflowJobQueue.enqueue_due_plan_reevaluations()`는 상태가 `OPEN` 또는 `REEVALUATION_QUEUED`이고 `due_at <= as_of`인 후속 기록을 예정일과 식별자 순으로 읽는다. 각 행마다 원래 실행과 계획이 여전히 활성인지 다시 계산한다. 계획이 이미 중단됐으면 새 작업을 만들지 않고 후속 기록을 닫으며, 남은 업무도 취소한다. 활성 계획에는 `PLAN_REEVALUATION` 작업을 추가하고 후속 상태를 `REEVALUATION_QUEUED`로 바꾼다.

작업 식별자는 `plan-reevaluation:{followup_id}`로 정했다. 같은 만기 항목을 다음 Cron 실행이 다시 찾아도 새 행을 만들지 않고 기존 행을 반환하기 위해서다. 작업 내용에는 만기 시각, 요청 자료, 당시 동의 기록 식별자, 실행 근거 지문이 들어간다. 명령행 파일과 FastAPI의 `/agent/cron/due-plans` 경로는 별도 계산식을 갖지 않고 이 큐 함수를 호출한다. 시험 목적으로 기준 시각을 바꾸는 API 입력은 `WB_RND_ALLOW_CRON_AS_OF_OVERRIDE=1`일 때만 허용된다.

## 반복 실행과 중단된 계획을 실패 조건으로 고정했다

가장 큰 재현 위험은 스케줄러 재시작 뒤 같은 일을 다시 만드는 것이다. `tests/test_interim_jobs.py`는 만기 전 0건, 만기 시 1건, 다음 날 재실행 시 신규 0건과 중복 1건을 기대한다. 여러 계획이 동시에 만기되면 이른 예정일부터 처리하며, 이미 닫힌 후속 기록은 제외한다. Cron이 작업을 만든 뒤 계획 중단 이벤트가 추가되는 경우도 시험한다. 작업자가 업무를 가져가기 직전에 활성 계획을 다시 확인하므로 그 작업은 실행되지 않고 취소된다.

현재 저장소에서 과거의 첫 실패 실행이나 수정 전 출력은 확인되지 않음이다. 다만 현행 회귀 시험은 “주기 실행을 한 번 통과했으니 계속 안전하다”는 가정을 쓰지 않는다. 생성 시점과 업무 선점 시점에 계획 상태를 각각 확인하며, 동일 만기 항목은 고정 멱등 키로 합친다. 이 두 방어선이 현재 코드에 남아 있는 수정 결과다.

## 고정 시각 네 번으로 경계를 재현했다

등록된 기준 실행은 2026-07-21 11:59:59 UTC에는 재평가를 0건 만들었다. 첫 계획의 만기 시각인 12:00에는 1건, 두 번째 계획까지 만기된 13:00에는 새 작업 1건과 기존 작업 1건을 반환했다. 다음 날 실행에서는 새 작업이 0건이고 기존 두 건이 모두 중복 처리됐다. 최종 SQLite에는 알림 작업 2건과 재평가 작업 2건만 남았다. `tests/test_interim_api.py`도 내부 API를 통해 만기 후 `PLAN_REEVALUATION` 한 건이 생기는지 확인한다.

## 장부의 운영 표기와 직접 증거의 차이

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-074.json`을 붙여 OP-074를 `OPERATED`로 등록했다. 이 영수증은 로컬 실제 세션에서 `followup` 경로가 실행됐고 `workflow_jobs`가 1건 늘었다고 기록한다. 그러나 늘어난 업무의 `job_type`과 Cron 호출 결과는 영수증에 없다. 알림 업무인지 만기 재평가 업무인지 이 파일만으로 구분할 수 없다.

따라서 이 보고서가 직접 주장하는 단계는 `IMPLEMENTED`다. 등록된 로컬 영수증은 후속 업무 큐가 사용됐다는 보조 근거로만 본다. 배포된 CronJob의 일정 실행, 장기 중단 후 재기동, 실제 업무 처리 프로그램이 재평가를 끝낸 기록은 확인되지 않음이다. 운영 단계로 올리려면 Cron 호출 시각, 대상 `followup_id`, 생성된 `PLAN_REEVALUATION`의 `job_id`, 처리 완료 상태를 같은 운영 영수증에 남겨야 한다.
