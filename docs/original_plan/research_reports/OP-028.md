# OP-028 삭제·정정 요청이 계보와 감사 로그를 보존하며 처리되는지 검증한다

## 삭제와 정정은 과거를 몰래 덮어쓰면 안 된다
사용자가 잘못 입력한 사건을 바로잡거나 삭제를 요청하더라도 연구 결과의 출처와 변경 이력을 설명할 수 있어야 한다. 반대로 개인정보 삭제를 명목상 상태값만 바꾸고 원문을 파일에 남겨 두는 것도 허용할 수 없다. OP-028은 이 두 요구를 함께 다룬다. 원본 payload hash를 계보의 시작점으로 보존하고, 정정·삭제 결과 hash와 변경 사이의 연결 hash를 append-only 원장에 남기며, 삭제 때 현재 payload를 tombstone으로 바꾼 뒤 SQLite 파일에서 과거 본문을 제거하도록 구현했다.

이 결과는 원본 plaintext를 영구 감사 로그에 복제한다는 뜻이 아니다. 감사에 필요한 것은 원본과 결과를 식별하는 hash, 변경 종류, 대상, 순서와 시각이다. 삭제된 민감 payload를 감사 metadata에 다시 넣지 않아야 삭제와 설명 가능성을 동시에 지킬 수 있다.

## 기존 이벤트 표 위에 변경 원장을 얹었다
`src/wellnessbox_rnd/interim/data_mutation.py`의 `DataMutationLedger`는 `execution_events`와 `behavior_events`를 공통 대상으로 취급한다. 대상 표에는 최초 `payload_sha256`, 현재 내용을 나타내는 `effective_payload_sha256`, `ACTIVE·CORRECTED·DELETED` 상태가 있다. 변경 요청은 `event_mutations`에 저장되며 원본 이벤트 행의 ID를 유지한다. 추천 실행의 knowledge lineage도 event ID를 계속 가리키므로 정정이나 삭제 때문에 계보 연결 자체가 사라지지 않는다.

별도 데이터 삭제 서비스를 만들지 않고 기존 `InterimStore` transaction과 audit table을 재사용했다. API는 token으로 보호된 `/v1/interim/event-mutations`에서 정정·삭제를 받고 `/v1/interim/event-mutations/{mutation_id}`에서 변경 기록을 조회한다. 이 endpoint는 일반 추천 호출과 달리 내부 mutation token을 요구한다. 권한이 없는 호출자가 데이터 변경을 실행하는 경로를 열지 않은 이유다.

## 요청 계약은 대상과 작업을 명확히 구분한다
입력에는 profile ID, target type, target event ID, operation, idempotency key가 필요하다. target type은 `execution_event` 또는 `behavior_event`, operation은 `correction` 또는 `deletion`만 허용한다. correction에는 replacement payload가 반드시 있어야 하고 deletion에는 replacement payload를 보낼 수 없다. 빈 식별자나 128자를 넘는 key도 거절한다.

대상 event가 해당 profile에 속하는지 join 또는 profile 조건으로 확인한다. 존재하지 않으면 not-found 오류가 발생한다. 이미 `DELETED`인 event에 새 correction을 적용할 수 없고, lifecycle transition처럼 불변이어야 하는 실행 사건과 이미 소비된 replacement candidate도 변경할 수 없다. PRO follow-up 정정은 계약 종류, assessment·plan·timepoint·관측 시각과 점수 계약 identity를 바꾸지 못한다. 이 제한은 정정 API가 결과 해석의 기준을 바꾸는 우회 경로가 되지 않게 한다.

## 변경마다 앞뒤 hash를 연결한다
최초 변경의 `prior_payload_sha256`은 대상 event의 최초 `payload_sha256`과 같아야 한다. 두 번째 이후 변경은 직전 변경의 `result_payload_sha256`이 현재 `effective_payload_sha256`과 같을 때만 진행한다. 각 row에는 `previous_mutation_id`, `previous_mutation_sha256`, 0부터 증가하는 `mutation_index`가 들어간다. 이 값과 요청 identity를 canonical JSON으로 묶어 `mutation_sha256`을 계산한다.

정정은 replacement payload의 hash를 현재 hash로 만들고 상태를 `CORRECTED`로 바꾼다. 삭제는 임의의 빈 문자열로 바꾸지 않고 삭제 사실과 mutation ID만 담은 tombstone을 만들며 상태를 `DELETED`로 바꾼다. `event_mutations`에는 update와 delete를 막는 SQLite trigger가 있어 변경 기록을 사후 수정하거나 지울 수 없다. `verify_chain`은 index 연속성, 이전 mutation 연결, payload hash 연결과 현재 event 상태를 다시 계산한다.

## idempotency와 transaction이 부분 적용을 막는다
mutation의 고유 범위는 `(profile_id, target_type, target_event_id, idempotency_key)`다. 같은 요청을 다시 보내면 기존 mutation을 `deduplicated=true`로 돌려준다. 같은 key로 operation이나 replacement payload를 바꾸면 request hash가 달라지므로 충돌을 반환한다. 정정 row, 대상 payload 갱신과 audit row 기록은 같은 immediate transaction에서 실행된다. 중간 오류가 나면 일부만 확정되지 않는다.

audit event에는 `data_correction` 또는 `data_deletion` 종류, 대상 ID, `INTERIM_RUNTIME_EVENT` data class와 mutation identity hash가 기록된다. 원문 payload는 audit metadata에 복제하지 않는다. 변경 원장 자체와 감사 원장이 같은 수로 생기는지를 smoke와 테스트가 확인한다.

## 삭제는 tombstone 뒤에 안전한 정리를 수행한다
삭제 transaction은 대상 payload를 tombstone으로 교체하고 `event_mutation_cleanup`에 `PENDING` 작업을 남긴다. transaction이 끝난 뒤 store가 WAL checkpoint와 secure compaction을 수행한다. 정리가 성공하면 상태가 `COMPLETE`가 된다. 프로세스가 중단되거나 reader 때문에 checkpoint가 busy이면 `PENDING`을 유지하고 다음 시작 또는 동일 요청 재시도에서 다시 정리한다. 완료되지 않은 정리를 성공으로 표기하지 않는다.

이 구현이 모든 백업과 외부 복제본을 삭제한다는 뜻은 아니다. canonical smoke는 임시 SQLite 본체와 부속 파일에서 고유 marker 조각이 사라졌는지를 확인한다. 운영 backup, 로그 수집기, export, 분석 warehouse와 법적 보존 정책은 별도의 삭제 절차와 receipt가 필요하다. 현재 구현 범위는 R&D interim SQLite 저장소다.

## 테스트는 계보·불변성·복구 실패를 함께 확인한다
`tests/test_event_idempotency_data_mutation.py`는 correction 뒤 deletion을 적용하고 event 상태, effective hash, mutation 수와 audit 수를 검사한다. 같은 correction과 deletion의 재시도는 중복 처리되고, 같은 key로 내용을 바꾸면 충돌하는지 확인한다. 삭제 뒤 correction, 다른 profile의 대상 변경, 불변 lifecycle event 변경도 거절돼야 한다. SQL로 `event_mutations`를 update하거나 delete하면 `event_mutations_append_only` 오류가 발생하는지도 직접 검증한다.

테스트는 chain hash를 변조했을 때 검증이 실패하는 경우와 ingestion fingerprint가 변경되지 않는 경우도 다룬다. secure compaction 실패를 주입해 cleanup이 `PENDING`으로 남는지, store 재시작 뒤 복구되는지, active reader가 사라진 뒤 동일 삭제 요청 재시도로 완료되는지도 확인한다. `tests/test_data_lake_lineage.py`는 mutation 뒤에도 추천 실행과 knowledge lineage 조회가 유지되는 범위를 보완한다.

## canonical evidence는 정정과 삭제를 실제 API로 재현한다
`scripts/run_event_idempotency_data_mutation_smoke.py`는 실제 FastAPI app과 새 SQLite에서 recommendation 및 trace를 만든다. conversation event와 behavior event를 기록한 뒤 correction과 deletion을 route로 수행한다. correction replay와 deletion replay의 중복 처리, 변경 replay 충돌, 삭제 후 correction 거절, tombstone 상태, mutation·audit 개수, hash chain, ingestion fingerprint와 knowledge lineage 보존을 한 결과에 모은다.

결과 파일은 `data/original_plan/evidence/op027_op028_event_idempotency_data_mutation_smoke_v1.json`이다. 현재 case count는 3, event mutation과 mutation audit count는 각각 2, 최종 payload state는 `DELETED`다. database schema version은 14이고 모든 check가 true다. 같은 committed source에서 두 번 생성한 파일은 byte-identical했으며 SHA-256은 `980e5677adcb54db684679a3111b0a6927b4e5fc47d6ddc7c9cc8bf6ab19dfb8`이다.

## IMPLEMENTED 완료와 운영 삭제 증명은 다르다
schema, ledger, 보호 route, append-only trigger, 복구 가능한 cleanup과 실제 route 테스트가 있으므로 OP-028의 required stage `IMPLEMENTED`를 충족한다. manifest의 claimed stage도 `IMPLEMENTED`이고 현재 판정은 `COMPLETE`다. 그러나 production 사용자 요청을 접수하고 신원을 확인하는 절차, SLA 안에 모든 저장 계층에서 삭제하는 작업, backup 만료, 담당자 승인과 실제 운영 receipt는 이번 범위에 없다. 따라서 `INTEGRATED`, `OPERATED` 또는 외부 검증 완료를 주장하지 않는다.

운영 단계로 올리려면 실제 서비스가 mutation endpoint를 어떤 관리자 절차로 호출하는지, 대상 소유권 확인과 이중 승인 여부, primary·replica·backup·export별 삭제 완료 시각을 증명해야 한다. 장기간 chain verification과 cleanup backlog가 0인지도 관측해야 한다. 외부 감사가 필요하다면 hash만으로 개인정보 삭제 의무가 충족되는지와 보존 예외를 독립 검토자가 확인해야 한다.

## 이번 loop의 변경 범위와 남은 조건
핵심 구현은 commit `e2cfc54`에서 시작됐고 후속 commit은 plan lifecycle과 소비된 replacement candidate의 불변성을 강화했다. 이번 loop는 mutation 의미를 바꾸지 않았다. schema version 8에 머문 canonical evidence를 현재 생성기로 재생성하고, evidence의 database schema가 코드의 `SCHEMA_VERSION`과 일치해야 한다는 회귀 테스트를 추가했다.

서비스 저장소, production 데이터, 사용자 원문, 학습 데이터와 모델은 수정하지 않았다. frozen 256건 평가, replay와 weakest slice의 delta는 0이어야 하며 최종 검증에서 다시 확인한다. 이 0 delta는 추천 성능 회귀가 없다는 제한된 근거다. 실제 사용자 삭제 요청이 운영 backup까지 처리됐다는 증거로 해석하면 안 된다. 남은 완료 조건은 120개 연구보고서 전체 감사와 별개이며, OP-028 자체의 상위 stage 승격에는 운영 삭제 receipt와 외부 정책 검토가 필요하다.
