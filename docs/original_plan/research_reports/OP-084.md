# OP-084 답변에 근거 ID, 유효일, 불확실성을 포함한다.

## citation ID만 있으면 충분하다고 보기 어려웠다

OP-084의 원문은 “답변에 근거 ID, 유효일, 불확실성을 포함한다”이다. 기존 상담 답변에도 citation은 있었다. chunk ID, reference ID, claim ID, 출처 제목, 출처 유형, 구간 이름, URI를 반환했다. 이 정보만 보면 어떤 근거를 사용했는지는 찾을 수 있다. 하지만 답변을 만든 시각에 그 근거가 유효했는지, 근거가 제한적이거나 혼합돼 있는지, 답변이 어느 지식 범위에서 만들어졌는지는 알 수 없었다. ID가 존재한다는 사실과 그 ID가 그 시점에 사용 가능하다는 사실은 서로 다르다.

이번 구현은 답변 본문에 날짜 문장을 덧붙이는 방식으로 끝내지 않았다. 사람이 읽는 문장은 바뀌기 쉽고, verifier가 다시 계산하기 어렵다. 대신 `ChatTemplateAnswer`, `AnswerCitation`, `AnswerUncertainty`에 구조화된 필드를 추가했다. 이 필드는 deterministic template 답변과 OpenAI adapter 답변에 똑같이 적용된다. provider가 답변을 썼더라도 근거 날짜와 불확실성을 provider가 자유롭게 정하지 않는다. 저장소가 선택한 passage에서 다시 계산한다.

## 답변이 어느 시점과 범위에서 만들어졌는지 먼저 남겼다

모든 bounded 답변에는 `knowledge_scope_id`와 `answered_at`이 들어간다. `knowledge_scope_id`는 OP-083에서 적용한 허용 범위의 ID다. `answered_at`은 timezone이 있는 답변 시각이다. 답변 시각이 없거나 timezone이 없으면 답변 계약이 성립하지 않는다. 이 두 값이 있어야 verifier가 “이 citation이 그때 활성 상태였는가”를 다시 판단할 수 있다.

각 citation에는 기존 ID와 출처 정보에 더해 `effective_at`, 선택적인 `retired_at`, `active_at_answer_time`이 들어간다. 활성 여부는 단순히 JSON에 적힌 boolean을 믿지 않는다. passage 시행 시각이 답변 시각보다 늦지 않고, 폐기 시각이 없거나 답변 시각보다 뒤인지 다시 계산한다. 답변 시점에 폐기된 passage는 애초에 bounded 검색 결과에 들어오지 않는다. 누군가 citation의 `active_at_answer_time`만 `true` 또는 `false`로 바꿔도 verifier는 원 passage의 날짜와 비교해 불일치를 찾는다.

canonical smoke는 이 경계를 음성 사례로 확인한다. 정상 supported 답변의 citation에서 활성 상태만 `false`로 바꾼 복사본을 만들었다. ID와 본문은 그대로였지만 verification은 실패했고 `answer_evidence_validity_mismatch`를 남겼다. 이 검사는 날짜 필드가 화면 표시용 메타데이터가 아니라 완료 판단에 사용되는 계약임을 보여 준다.

## 불확실성을 숫자 하나로 꾸미지 않았다

근거가 약하다는 사실을 0.63 같은 숫자로 표현하면 정밀해 보이지만, 현재 데이터에는 그 숫자를 보정할 외부 표본이 없다. 이번 구현은 `low`, `moderate`, `high` 세 수준과 하나 이상의 구체적인 이유를 함께 반환한다. 이유 목록은 중복 없이 정렬해야 한다. 같은 답변을 다시 만들었을 때 순서가 달라져 evidence 해시가 바뀌지 않도록 하기 위해서다.

불확실성은 선택한 passage의 `normalized_claim_type`에서 결정적으로 계산한다. `inconclusive_goal_evidence`나 `null_goal_evidence_without_deficiency`가 들어가면 `high`다. 이때 “인용한 claim이 제한된 모집단에서 결론이 불충분하거나 null이다”라는 이유를 남긴다. `limited_goal_evidence`, `mixed_goal_evidence`, candidate policy, safety policy, action-space constraint가 들어가면 `moderate`다. 근거가 제한적이거나 혼합됐거나 정책 범위에 묶여 있다는 이유를 남긴다. 그 밖의 supported claim은 `low`로 표시하지만, “인용 passage에 한정된 답변이며 개인화된 임상 확실성이 아니다”라는 이유는 항상 남는다. `low`가 의학적으로 확실하다는 뜻으로 읽히지 않게 하기 위해서다.

검색 결과가 없는 답변은 더 보수적으로 다룬다. `unsupported`는 허용 corpus가 요청한 주장을 지지하지 않는다는 이유와 함께 `high`다. `out_of_scope`는 허용 범위 안의 근거를 검색하지 못했다는 이유와 함께 `high`다. 두 상태는 citation과 used chunk ID를 가질 수 없다. 근거가 없는데 불확실성만 낮추거나 citation을 붙이는 조합을 verifier가 거부한다.

## magnesium 질문에서 불확실성이 어떻게 달라졌는가

canonical smoke의 두 번째 supported 사례는 “magnesium과 insomnia에 관한 근거가 무엇인가”라는 질문이다. 선택된 claim은 `CLM-NCCIH-MAGNESIUM-SLEEP-001`이고 claim 유형은 `mixed_goal_evidence`다. 원문은 magnesium supplement 연구가 제한적이고 상충하며, magnesium glycinate에 특화된 근거가 아니라고 밝힌다. 답변은 이 passage를 사용하면서 uncertainty를 `moderate`로 기록한다. 이유에는 제한적·혼합·정책 범위라는 설명과 개인화된 임상 확실성이 아니라는 설명이 함께 들어간다.

이 처리는 관측된 claim을 강하거나 약한 효과 숫자로 바꾸지 않는다. magnesium glycinate라는 특정 형태의 효과도 추론하지 않는다. passage가 말하는 범위와 답변이 말하는 범위를 같게 유지한다. OP-082에서 generic magnesium을 magnesium glycinate로 자동 매핑하지 않은 결정과도 맞닿아 있다. 질문에서 특정 성분을 임의로 좁히지 않고, 답변에서도 근거가 다루지 않은 하위 유형을 확실한 것처럼 쓰지 않는다.

첫 번째 supported 사례인 glucosamine과 warfarin 상호작용은 `drug_interaction` claim을 사용한다. 이 claim은 현재 분류 규칙에서 `low` uncertainty를 받지만, 답변이 cited passage에 한정되고 개인화 진료가 아니라는 이유는 유지한다. 여기서 `low`는 상호작용이 없다는 뜻도, 개인에게 안전하다는 뜻도 아니다. 현재 구조화된 claim 유형 안에서 혼합·제한·불충분 표지가 추가로 붙지 않았다는 뜻이다. 실제 응급 위험 우선순위와 금지 표현 검사는 OP-085/086이 소유한다.

## provider 답변도 같은 값을 다시 계산한다

OpenAI adapter가 live provider를 사용할 수 있는 경로에도 동일한 필드를 적용했다. provider에게는 OP-083의 bounded 검색으로 정한 evidence chunk만 전달한다. provider 응답은 status, answer text, used chunk ID만 제안할 수 있다. citation의 reference ID, claim ID, 출처 정보, 시행일, 폐기일, 활성 상태는 허용된 chunk에서 서버가 다시 만든다. uncertainty도 provider 문장에서 추측하지 않고 같은 결정 규칙으로 계산한다.

provider가 존재하지 않는 chunk ID를 반환하면 그 ID는 citation으로 인정하지 않는다. supported 상태인데 유효한 chunk가 하나도 없으면 파싱 실패로 처리하고 deterministic fallback으로 돌아간다. provider가 답변 본문을 만들었다는 사실 때문에 근거 계약이 느슨해지지 않는다. 이번 canonical smoke는 live provider를 호출하지 않았으므로 provider 품질이나 외부 모델 안정성을 증명하지는 않는다. 다만 provider 경로가 사용될 때에도 근거와 불확실성의 작성 권한이 서버에 남아 있다는 코드 경계를 테스트한다.

## verifier가 다시 계산하는 항목

`verify_bounded_template_answer`는 답변 객체만 검사하지 않는다. 원 manifest, 적용한 scope, 답변 시각을 함께 받는다. 먼저 scope 전체가 repository-pinned registry의 같은 ID 항목과 정확히 일치하고, 답변의 scope ID와 시각도 호출자가 지정한 값과 같은지 확인한다. 다음으로 모든 used chunk가 manifest에 존재하고, 출처 유형·claim 유형·reference ID의 세 허용 목록을 모두 통과하는지 확인한다. citation이 used chunk를 정확히 가리키는지, citation의 전체 내용이 원 chunk에서 다시 만든 값과 같은지, 답변 시각에 실제로 활성인지도 확인한다.

독립 검토에서는 같은 used chunk ID를 두 번 넣어도 이전 verifier가 통과하는 결함도 찾았다. 현재 답변 모델은 used chunk ID와 citation chunk ID 각각의 중복을 거부하고, 두 목록이 정확히 일대일로 대응해야 한다. `model_copy`처럼 모델 검증을 우회한 객체가 verifier에 들어오는 경우에도 verifier가 used chunk 중복을 다시 검사한다. canonical smoke는 같은 ID를 두 번 넣은 답변을 만들고 verification이 실패하는지 확인한다.

마지막으로 status와 selected chunk에서 기대 uncertainty를 다시 만든다. 답변의 수준이나 이유가 다르면 `answer_uncertainty_mismatch`가 된다. 테스트에서는 정상 답변의 citation 활성 상태를 바꾸고 uncertainty 수준도 `high`로 바꿨다. verification은 두 변조를 모두 발견했다. 이 검사는 JSON 필드를 채웠다는 사실이 아니라 필드 사이의 관계가 맞는지를 본다.

다만 이 verifier가 OP-085 전체를 완료한 것은 아니다. OP-085는 근거 없는 자유 주장, 위험 누락, 금지 표현을 종합적으로 차단해야 한다. 이번 변경은 OP-084의 날짜·범위·불확실성 필드를 재계산하는 부분까지만 강화했다. 응급 위험 질문에서 추천보다 안전 안내를 우선하는 동작도 OP-086에서 별도로 구현하고 검증해야 한다. 요구사항 소유권을 섞지 않기 위해 OP-085/086은 아직 claim하지 않았다.

## 증거와 단계 판단

canonical evidence는 `data/original_plan/evidence/op083_op084_bounded_rag_answer_provenance_smoke_v1.json`에 있다. 네 답변 사례는 각각 status, scope ID, 답변 시각, 사용한 chunk ID, reference ID, claim ID, citation 시행일, 활성 상태, uncertainty와 verification 결과를 보존한다. 세 allowlist 축, forged registry scope, 폐기·미래 passage, 변조한 활성 상태, 중복 provenance를 차단하는 여덟 probe도 함께 들어 있다. 파일 SHA-256은 `cfb10b0bdb9d02fbd1851cddde8b32c914a1ac00929b47f60e514c343fffb04d`이다. source commit은 `6528c50d9d453bf397389746b7889ad489cc1b92`, source SHA-256은 `03c86d65261517c360e4120a9d2f3039cc30fa8db568c9bebe431e558e026f5f`, data SHA-256은 `95cc551d1be3fe9bb9d62fc39e0a1418587d529f6f89f9fc942cbedd39290356`이다.

OP-084의 required stage는 `IMPLEMENTED`다. 답변과 citation 계약에 필요한 값이 들어갔고, deterministic 경로와 provider adapter가 같은 계산을 사용하며, verifier가 원 passage와 날짜를 사용해 다시 확인한다. 집중 테스트와 canonical smoke가 정상 사례와 변조 사례를 모두 재현하므로 `IMPLEMENTED`를 주장할 수 있다.

이 판단은 상담 API의 production 운영이나 외부 임상 검증을 포함하지 않는다. WellnessBox 서비스 저장소 변경, 공개 배포, 환경 변수 변경, 실제 사용자 세션, 외부 전문가 검토는 이번 loop에 없다. 따라서 이번 보고서는 근거 표시와 불확실성 계약의 코드 구현을 설명한다. 운영 중에 사용자가 이 정보를 이해하는지, 불확실성 수준이 외부 평가에서 적절한지는 후속 요구사항과 외부 검증으로 남아 있다.
## 상담 답변을 믿을 수 있게 만드는 조건
상담 답변은 자연스러운 문장보다 근거 범위와 위험 차단이 먼저다. 허용된 지식 범위만 검색하고, 답변에 근거와 유효일·불확실성을 남기며, 응급 신호나 provider 장애에서는 안전 안내와 결정적 fallback을 우선한다.

`OP-084`는 “답변에 근거 ID, 유효일, 불확실성을 포함한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/chat/answering.py`, `wellnessbox-rnd/src/wellnessbox_rnd/chat/openai_adapter.py`, `wellnessbox-rnd/src/wellnessbox_rnd/chat/retrieval.py`, `wellnessbox-rnd/data/knowledge/counseling_knowledge_scope_registry_v1.json`
- 테스트·실행: `wellnessbox-rnd/tests/test_chat_retrieval.py`, `wellnessbox-rnd/tests/test_chat_openai_adapter.py`, `wellnessbox-rnd/scripts/run_bounded_rag_answer_provenance_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op083_op084_bounded_rag_answer_provenance_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
