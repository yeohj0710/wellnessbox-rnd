# OP-004 16~24쪽의 입력·처리·출력을 master context와 대조했다

## 아홉 쪽을 기능 이름만으로 읽으면 생기는 문제

원본 16~24쪽은 페이지마다 다른 기술을 설명하지만 공통 구조가 있다. 어떤 데이터를 받는지, 데이터를 어떤 규칙이나 모델로 처리하는지, 다음 단계가 사용할 결과를 무엇으로 내보내는지다. 기술 이름만 옮기면 “Two-Tower”, “LangGraph”, “online fine-tuning” 같은 구현 예시가 영구 요구사항으로 굳을 수 있다. 반대로 입력·처리·출력만 지나치게 단순화하면 금기 규칙, 비용 제약, 후속 행동, 센서 지표, 유전자별 조정처럼 원문이 요구한 세부 계약을 잃는다. OP-004는 원본 화면과 `master_context.md`를 대조해 두 오류를 피하는 작업이다.

## 16~17쪽은 정규화된 입력에서 안전 범위를 만든다

16쪽 데이터 레이크의 입력은 성별, 연령, 키, 체중, 병력, 증상, 복용 약물, 생활 습관 같은 사용자 특성이다. 공공 건강정보와 마이데이터, 의약학 문헌, 식약처·약학정보원 자료, 상품·구매·세션·리뷰 같은 행동 데이터, 사용자와 LLM의 대화 로그, 엔진 연산 결과와 외부 호출 기록도 들어온다. 처리는 서로 다른 데이터를 규정된 형식으로 정제하고 단일 지식 허브에서 조회 가능하게 만드는 일이다. 출력은 안전 엔진, 효과 모델, 최적화, 상담 모듈이 함께 읽는 정규화된 사용자 상태·근거·계보 데이터다.

17쪽 안전 검증 엔진은 사용자 특성과 약물, 질환, 알레르기, 생활 습관, 건강 목표를 구조화 JSON으로 받는다. 의약학 데이터베이스와 학술 근거에서 만든 규칙 테이블을 사용자 상태와 순서대로 대조하는 rule-based matching이 핵심 처리다. 출력은 성분별 허용 용량 범위, 복용 규칙 허용 범위, 금기 성분과 금기 규칙이다. `docs/context/master_context.md`의 6.1~6.2는 이 입력·처리·출력을 원문 도식과 같은 순서로 풀어 쓴다.

## 18~20쪽은 후보, 효과 수치, 제약 조합을 구분한다

18쪽 효과 추론의 입력은 개인 특성, 질환, 약물, 생활 습관, 과거 반응, 성분과 용량, 복용 후 변화, PubMed·Micromedex·JAMA·USP 같은 근거다. 원문은 초기 후보 추천에 전문가 라벨, Two-Tower, 유사도, GBDT ranking을 예시로 들고, 개인별 효과에는 ITE를 제안한다. 처리의 본질은 후보를 순위화하는 일과 특정 후보를 복용했을 때의 변화량을 추정하는 일을 분리하는 것이다. 출력은 후보 조합과 개인별 효과 예측 벡터 C 또는 C'다.

19쪽은 효과 수치의 생성 절차를 더 구체화한다. 개인 변수는 표준화하고, PSQI·ISI 같은 임상 타당성이 있는 환자보고결과(PRO) 설문으로 카테고리별 변화를 측정하며, z-score나 변화 점수로 비교 가능한 데이터를 만든다. 처리 결과는 특정 사용자의 예상 변화량과 복용 전후 실제 변화량이다. `master_context.md`는 원문의 특정 딥러닝 구조를 바꿀 수 있다고 명시하면서도 표준화, PRO, 개인별 효과 수치라는 출력 계약은 보존한다.

20쪽 최적화 엔진은 안전 엔진이 만든 safe set, 효과 점수, 제품 또는 제제 후보, 예산, 최대 복용 수, 사용자 선호를 입력으로 받는다. 처리는 효과를 높이고 부작용·비용·복용 부담을 낮추는 다중제약 탐색이다. 원문은 Multiple-choice Knapsack과 MILP를 구현 후보로 든다. 출력은 안전 범위 안에 있는 Top-k 조합과 사용자가 가격·알약 수·선호를 보고 선택할 수 있는 대안이다. 특정 최적화 라이브러리보다 안전 제약을 지키면서 재현 가능한 대안을 내는 계약이 우선한다.

## 21~22쪽은 상태를 보고 다음 행동을 결정한다

21쪽 Closed-loop AI의 입력은 현재 계획 상태, 복용 이력, 검사 결과, 상담 내용, 주문·배송 상태, 예정된 재평가 시각이다. 처리는 상태를 보고 상담, 검사 요청, 엔진 호출, 주문·배송 중계, 알림, 모니터링 중 다음 작업을 선택하는 것이다. 원문은 LangGraph의 Node, Edge, State와 Corrective RAG를 예시로 제시한다. 그러나 `master_context.md`는 특정 프레임워크 사용보다 테스트 가능한 상태 기반 후속 행동 자동화가 본질이라고 해석한다.

22쪽은 출력을 실제 서비스 노드로 구체화한다. 상담 세션 답변, 검사·측정 요청, 안전·추천 엔진 호출, 주문·결제·배송 중계, 복용 알림, 재검사와 재주문 판단이 출력이다. 상담 로그의 핵심 키워드는 Data Lake에 저장되고 CronJob이 주기적 작업을 호출한다. 30일치 소분 주문, 7일 모니터링, 30일 후 재검사와 변경 조합 배송은 반복 주기의 예시다. 이 페이지가 요구하는 것은 LLM이 모든 일을 임의로 수행하는 것이 아니라 상태와 권한에 따라 허용된 다음 행동을 실행하는 경계다.

## 23~24쪽은 측정값과 유전자 결과를 개인화 입력으로 바꾼다

23쪽의 입력은 웨어러블 활동량·심박수·수면 시간과 연속혈당측정기(CGM)의 혈당·TIR(Time in Range)다. 처리는 측정 시각과 단위를 맞추고 복용 전후 변화를 계산해 개인별 피드백 루프에 넣는 것이다. 원문은 심박수 78→72, 수면 6.0→7.2시간, 혈당 148→135, TIR 62→78% 같은 변화 예시를 제시한다. 출력은 객관적 변화량, 후속 판단 입력, 모델 갱신 후보 데이터다. 원문의 online fine-tuning은 구현 예시이며, 검증되지 않은 측정값으로 모델을 자동 재학습하라는 무조건적 운영 명령은 아니다.

24쪽의 입력은 외부 검사기관이 전달한 유전자 결과 파라미터 벡터와 사용자 동의다. 처리는 MTHFR, LCT, CYP1A2, FTO, TCF7L2, LPL 같은 변이를 안전 규칙과 추천 가중치에 연결하는 것이다. 출력은 제외 성분, 대체 제형, 우선순위 조정, 모니터링 확대와 Data Lake에 저장된 유전자 특성이다. 검사 신청과 채취, 외부 기관 분석, 결과 수령이라는 공급 경계를 보존해야 하며, 유전자 정보가 있다는 이유만으로 질병을 확정해서는 안 된다.

## manifest와 master context의 대조 결과

첫 번째 구현 증거인 `wellnessbox-rnd/docs/context/master_context.md`는 원본 16~24쪽을 6.1부터 6.9까지 페이지별로 재구성한다. 각 절에는 원문 입력, 처리 단계, 출력 또는 다음 단계가 읽을 결과가 들어 있다. 두 번째 구현 증거인 `wellnessbox-rnd/data/original_plan/requirements_manifest_v1.json`은 이 계약을 그룹 B~J의 OP 항목으로 나눈다. 사용자 입력과 동의는 B, 데이터 레이크는 C, 안전은 D, 후보와 효과는 E·F, 최적화는 G, Closed-loop는 H·I, 센서·유전자는 J가 소유한다.

테스트 증거인 `wellnessbox-rnd/tests/test_original_plan_manifest.py`는 120개 OP의 연속성, 그룹 재고, 출처와 소유자, 현재 주장 단계를 검사한다. 이 테스트가 16~24쪽의 작은 글자를 OCR로 다시 읽는 것은 아니다. 이번 시각 대조와 master context가 원문 의미를 확인하고, 테스트는 그 의미를 구현 요구사항으로 만든 manifest가 빠지지 않게 지킨다. PDF 전체의 바이트 동일성은 별도의 canonical manifest 감사가 확인한다.

Git 이력에서 `docs/context/master_context.md`와 원본 PDF는 2026-03-08의 `e5ef1ecf8575d1a09cf4fb3a8d0063e9a8b24d4d`에 함께 들어왔다. 2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad`는 OP-004와 A~L manifest, manifest 테스트를 도입했다. 이후 입력 구조화, 안전, 효과, 최적화, Closed-loop, 센서 연동 구현이 각 OP의 구체적 증거를 추가했다. OP-004는 이 후속 구현을 새로 완료하는 항목이 아니라, 구현 항목이 원문의 입력·처리·출력과 연결되는지 확인하는 기준선이다.

## 현재 주장할 수 있는 범위

OP-004의 기본 요구 단계와 현재 주장 단계는 `IMPLEMENTED`다. 16~24쪽의 입력·처리·출력이 master context에 재구성되고 manifest의 독립 요구사항과 대조됐으므로 이 단계는 충족한다. 모든 하위 요구가 production에서 운영됐다는 뜻은 아니다. 외부 유전자 검사 결과, 실제 센서 장치, 운영 약사 검토, production 재조회는 각각 별도 증거가 필요하다. 원문이 예로 든 Two-Tower, LangGraph, MILP, online fine-tuning을 그대로 사용하지 않았다고 OP-004가 실패하는 것도 아니다. 같은 입력과 안전 경계, 검증 가능한 출력을 더 단순한 구현으로 만들 수 있다.

이번 반복은 연구보고서와 감사 집계만 바꾼다. 코드, 데이터 스키마, 학습 데이터, 모델, 안전 규칙, 시뮬레이션에는 손대지 않는다. 따라서 frozen 평가, replay, weakest slice의 결과 변화도 없다. OP-004가 제공하는 결과는 기술 선택을 고정하는 설계가 아니라, 16~24쪽에서 요구한 정보가 어디서 들어와 어떤 판단을 거쳐 무엇으로 나가야 하는지 잃지 않게 하는 대조표다.
