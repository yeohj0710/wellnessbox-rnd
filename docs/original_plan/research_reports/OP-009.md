# OP-009 manifest 감사를 pytest와 CI 명령에 연결한다.

## 구현된 감사 규칙을 매번 실행할 수 있어야 한다

OP-008에서 manifest의 원본 해시, 증거 경로, Git 추적 여부와 소유 저장소를 검사하는 감사기를 만들었더라도 개발자가 그 함수를 직접 호출해야만 결과를 볼 수 있다면 회귀를 지속적으로 막기 어렵다. OP-009가 요구하는 실제 결과는 감사기를 명령줄에서 실행할 수 있게 하고, 같은 명령과 계약 테스트를 GitHub Actions에 연결해 관련 변경이 들어올 때 자동으로 실패시키는 것이다. 이 항목은 새로운 요구사항 저장소나 별도 CI 체계를 만드는 일이 아니다. 기존 canonical manifest, 기존 Python 감사 함수, 기존 R&D 저장소의 `Original plan evidence` workflow를 그대로 사용한다.

원본 PDF 25~26쪽에는 추천 성공률, 실제 효과, 다음 행동, 상담, 안전 레퍼런스, 이상반응, 센서·유전자 연동 KPI와 최소 표본이 제시돼 있다. 이 지표를 구현했다는 주장을 원본과 연결하려면 120개 OP의 증거가 깨지지 않았는지 반복해서 확인해야 한다. OP-009는 KPI 값을 계산하지 않는다. 대신 원본과 구현 사이의 추적 계약을 pull request와 main push에서 다시 실행할 수 있게 한다. 따라서 이 항목의 성과는 감사 실행 관문이며, 모든 KPI 달성이나 모든 OP 완료가 아니다.

## CLI는 기존 감사 함수를 얇게 감싼다

구현 경로 `scripts/audit_original_plan_requirements.py`는 `load_original_plan_manifest_v1`로 manifest를 읽고 `audit_original_plan_manifest_v1`을 호출한다. 기본 manifest는 `data/original_plan/requirements_manifest_v1.json`이며 `--manifest`로 다른 파일을 지정할 수 있다. 상대 경로는 R&D 저장소 root를 기준으로 해석한다. 감사 결과는 Pydantic 모델의 JSON 직렬화 결과로 표준 출력에 쓰며, status가 `PASS`일 때만 종료 코드 0을 반환한다. issue가 하나라도 있으면 종료 코드 1이다.

CLI가 별도 감사 규칙을 복제하지 않는 점이 중요하다. 원본 SHA-256 비교, 요구사항 ID 연속성, 단계별 필수 증거, 저장소 owner, root 탈출, 파일 존재와 Git 추적 여부는 모두 OP-008의 공용 함수가 담당한다. CLI에는 입력 경로 해석과 결과 출력, 종료 코드 변환만 있다. 감사 규칙을 바꿀 때 함수와 CLI의 두 구현을 함께 고칠 필요가 없고, 테스트와 CI가 개발자가 로컬에서 실행하는 것과 같은 코드를 사용한다.

## 두 저장소 root는 명시적인 우선순위로 결정한다

감사 대상은 R&D 저장소뿐 아니라 manifest가 참조하는 서비스 저장소 `wellnessbox`도 포함한다. R&D root는 CLI 파일 위치에서 결정한다. 서비스 root는 `--wellnessbox-root` 인자가 있으면 그 값을 가장 먼저 사용하고, 없으면 `WELLNESSBOX_EVIDENCE_ROOT` 환경변수, 그것도 없으면 R&D 저장소와 같은 부모 아래의 `wellnessbox` 디렉터리를 사용한다. 이 순서는 로컬 sibling checkout과 CI의 격리 checkout을 같은 명령으로 지원한다.

서비스 root를 자동으로 내려받거나 최신 커밋으로 바꾸지는 않는다. 지정된 checkout이 없거나 필요한 파일이 추적되지 않았다면 감사기가 missing 또는 tracked-index 오류를 내고 CLI는 실패한다. 로컬에 사용자 변경이 있는 서비스 checkout을 CI의 canonical 증거라고 주장하지도 않는다. workflow는 별도의 깨끗한 service evidence checkout을 만들고 `WELLNESSBOX_EVIDENCE_ROOT`로 전달한다. 따라서 로컬 편의 기본값과 CI의 재현 가능한 입력이 구분된다.

## GitHub Actions는 기존 original-plan workflow에 감사 관문을 추가한다

`.github/workflows/original-plan-evidence.yml`의 `Original plan evidence` workflow는 관련 pull request와 main push에서 실행된다. 경로 필터에는 manifest와 `data/original_plan/**`, `docs/original_plan/**`, governance 모듈, 감사·보고서 script, 관련 테스트와 여러 evidence 입력이 들어 있다. workflow의 `Audit requirement evidence` 단계는 깨끗하게 준비한 서비스 checkout을 환경변수로 지정한 뒤 `python scripts/audit_original_plan_requirements.py`를 실행한다. 종료 코드가 1이면 job도 실패하므로 다음 단계를 성공으로 오인하지 않는다.

같은 workflow는 `python scripts/build_original_plan_completion_report.py --check`도 실행한다. 이는 OP-010이 생성하는 JSON과 Markdown이 현재 manifest·audit 결과와 byte 단위로 같은지 검사한다. 이어서 `tests/test_original_plan_manifest.py`, `tests/test_original_plan_audit.py`, `tests/test_original_plan_audit_cli.py`, `tests/test_original_plan_completion_report.py`를 포함한 계약 테스트를 pytest로 실행하고 Ruff 검사를 수행한다. OP-009는 workflow 전체의 수많은 제품 evidence 단계를 새로 만든 항목이 아니다. 감사 CLI와 생성 보고서 확인, 관련 계약 테스트가 기존 workflow에서 빠지지 않도록 연결한 범위만 소유한다.

## 경로 필터와 workflow 문자열 테스트의 한계를 숨기지 않는다

경로 필터는 관련 없는 변경마다 긴 evidence job을 실행하지 않기 위한 선택이다. 따라서 필터 밖의 파일만 바뀐 push에서는 이 workflow가 시작되지 않을 수 있다. 반대로 original-plan manifest, 문서, governance, script, 테스트와 등록된 핵심 evidence 입력이 바뀌면 job이 실행되도록 목록을 유지한다. 새 evidence 경로를 추가하면서 필터를 갱신하지 않으면 자동 실행 범위에 공백이 생길 수 있으므로 workflow 자체를 계약 테스트로 검사한다.

`tests/test_original_plan_audit_cli.py`의 workflow 테스트는 YAML을 문자열로 읽어 감사 CLI, completion report `--check`, 네 계약 테스트 경로와 주요 evidence 명령이 포함됐는지 확인한다. 이 테스트는 연결 문구가 우연히 삭제되는 회귀를 빠르게 찾지만 GitHub runner가 실제 checkout, Python 설치, 환경변수와 명령을 성공적으로 실행했다는 사실까지 증명하지 않는다. 그 부분은 실제 GitHub Actions 성공 run이 담당한다. 정적 연결 검사와 원격 실행 증거를 서로 바꾸어 말하지 않는다.

## 실패 입력은 성공 출력으로 보정하지 않는다

CLI의 정상 테스트는 현재 manifest를 실제 두 저장소 root에 대해 감사해 종료 코드 0, status `PASS`, 요구사항 120건, 주장 119건, issue 0을 확인한다. 실패 테스트는 manifest 복사본의 원본 PDF SHA-256을 64개의 0으로 바꾼다. 감사 결과에는 `original_plan_sha256_mismatch`가 생기고 종료 코드는 1이 된다. 프로그램은 잘못된 해시를 현재 파일 값으로 자동 수정하거나 경고만 출력한 뒤 성공하지 않는다.

서비스 저장소 경로가 없거나 Git index를 읽지 못하는 경우도 같은 fail-closed 원칙을 따른다. manifest JSON 자체가 Pydantic schema에 맞지 않으면 load 단계에서 오류가 발생한다. 이는 구조가 깨진 입력으로 가짜 PASS 보고서를 만들지 않는 동작이다. CLI는 사람에게 친절한 자동 복구 도구가 아니라 CI가 신뢰할 수 있는 판정 명령이므로, 불완전한 입력을 추정해 계속하지 않는다.

## canonical evidence는 clean checkout과 동일 명령에서 나온다

canonical 절차는 먼저 GitHub Actions가 R&D main을 checkout하고, manifest가 참조하는 서비스 근거를 지정된 커밋의 깨끗한 checkout으로 준비하는 것이다. 그다음 개발 의존성을 설치하고 `WELLNESSBOX_EVIDENCE_ROOT`를 설정해 감사 CLI를 실행한다. 감사기는 두 Git index와 실제 파일 bytes를 사용해 원본 hash와 evidence reference를 검증한다. 이어서 completion report의 committed 산출물이 최신인지 확인하고 계약 테스트를 실행한다. 어느 단계든 실패하면 workflow는 성공 run을 만들지 않는다.

이 순서는 로컬 `etc/` 로그나 수정된 서비스 worktree를 canonical 증거로 승격하지 않는다. 추적된 repository 파일과 workflow 실행 기록이 재현 단위다. 보고서 작성 직전 기준 manifest 감사 상태는 PASS이며 completion 집계는 `76 COMPLETE / 43 PARTIAL / 0 PENDING / 1 EXTERNAL / 0 CONTRADICTED`다. 이전 bounded loop에서 생성한 OP-120 canonical evidence SHA-256은 `1be4ea55dcca71849aaed7332ee6859fdb419061561177ddf8eb2e7120a4ce01`이고, 당시 마지막 성공 `Original plan evidence` run은 `29919479757`이었다. 이번 보고서가 canonical 입력에 추가되면 OP-120 evidence와 새 CI run은 다시 생성해 새 값으로 인계해야 한다.

## 커밋 이력은 CLI 도입과 후속 확장을 구분한다

감사 CLI와 최초 CI gate는 2026-07-15의 `a449b605dceb29471103076d03de4e137ce421a5` 커밋에서 도입됐다. 이후 같은 workflow에는 서비스 profile, 안전성, replay, PRO, 센서, 주문, 보안, 최종 감사 등 후속 OP의 evidence 단계와 경로가 누적됐다. `git log --follow`에서 최초 책임 커밋과 후속 변경이 모두 보이는 이유다. OP-009의 완료 근거를 현재 workflow 전체와 동일시하지 않고, 최초 연결 계약과 현재도 유지되는 실행 경로를 함께 확인한다.

pytest는 CLI 성공·실패 종료 코드와 workflow wiring을 검증한다. 실제 workflow는 감사 CLI, completion `--check`, 계약 테스트, Ruff를 실행한다. GitHub Actions 성공은 저장소에 적힌 YAML 문자열만 존재한 것이 아니라 clean runner에서 명령이 끝까지 통과했다는 외부 실행 기록이다. 다만 GitHub Actions는 저장소 소유자가 관리하는 CI이지 독립 규제기관이나 외부 전문가 검증은 아니다.

## 서비스 통합, 운영, 외부 검증을 주장하지 않는다

OP-009의 manifest required stage와 claimed stage는 모두 `IMPLEMENTED`다. CLI가 감사 함수를 실행하고 실패를 non-zero exit로 전달하며, workflow와 테스트가 그 연결을 고정하므로 구현 단계는 충족한다. 서비스 저장소는 감사 입력으로 읽힐 뿐 OP-009가 서비스 API나 UI에 연결된 것은 아니다. production request를 처리하지 않고 사용자 데이터를 쓰지 않으며 운영 트래픽도 만들지 않는다. 이번 backfill은 원천 데이터, frozen evaluation 256건, 학습 데이터, 모델과 시뮬레이션을 변경하지 않는다.

따라서 `INTEGRATED`, `OPERATED`, 외부검증은 주장하지 않는다. OP-009가 required stage를 충족한 사실은 43개 PARTIAL을 완료로 만들지 않으며 OP-039의 독립 약사 검증도 대신하지 않는다. 남은 조건은 workflow 경로 필터와 서비스 evidence pin을 후속 변경에 맞게 유지하고, 새 canonical 변경마다 실제 Actions 성공을 확인하는 것이다. OP-009는 잘못된 완료 주장이 main에 들어갈 가능성을 낮추는 자동 관문이지, 누락된 구현·운영·외부 증거를 만들어 주는 기능은 아니다.
