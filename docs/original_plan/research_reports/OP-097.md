# OP-097 기기 수치를 추천 점수와 후속평가에 연결한 결과

## 결론

웨어러블과 연속혈당측정기(CGM) 수치가 추천 점수에 들어간 뒤, 같은 수치가 후속평가에서 얼마나 바뀌었고 후보 점수가 얼마나 달라졌는지 한 계보에서 확인할 수 있게 했다. 기준 평가와 후속평가는 인증된 `POST /v1/interim/device-assessments` API를 사용한다. API는 실제 추천 엔진을 호출하고, 선택된 후보마다 웨어러블 조정점수, CGM 조정점수, 전체 점수를 저장한다. 후속평가에서는 기준 수치와 후속 수치의 차이, 기준 점수와 후속 점수의 차이를 계산해 함께 저장한다.

OP-097의 요구 단계는 `INTEGRATED`다. 새 API는 기존 입력 계약, 동의 계약, 후보 점수 계산기, 추천 엔진, 중간 SQLite 저장소를 실제 호출한다. 고정 사례는 인증 HTTP 요청으로 기준 평가와 후속평가를 차례대로 실행하고 데이터베이스를 다시 조회한다. 따라서 로컬 통합 증거는 요구 단계에 도달했다. 생산 기기 공급자나 배포 서비스가 필요하다는 뜻은 아니다.

## 이전에는 무엇이 끊겨 있었나

추천 엔진은 이미 웨어러블 수면 시간과 CGM time-in-range 같은 값을 후보 점수에 반영했다. 예를 들어 수면 시간이 부족하면 근거가 등록된 일부 수면 지원 후보의 `wearable_adjustment`가 올라간다. 이 계산은 추천 응답의 `score_breakdown`에도 나타났다. 하지만 후속평가는 주로 환자보고결과(PRO) 설문 점수와 복용 이행률을 다뤘다. 기기 수치가 나중에 바뀌었을 때 어떤 후보 점수 항목이 함께 바뀌었는지 보여주는 지속 계보가 없었다.

추천 시점의 단위 테스트만으로는 OP-097 전체를 증명하기 어렵다. 단위 테스트는 수치가 점수 함수에 들어간다는 사실을 보여주지만, 기준 평가와 후속평가가 같은 사용자와 같은 데이터 분류에 묶이는지는 보여주지 않는다. 이번 구현은 점수 계산을 새로 만들지 않고 기존 추천 엔진을 두 시점에서 실행한다. 그 결과를 같은 평가 테이블에 저장해 끊어진 연결을 메웠다.

## API가 처리하는 순서

요청에는 평가 ID, 평가 단계, 데이터 분류, 세션 출처, 추천 요청이 들어간다. 평가 단계는 `BASELINE` 또는 `FOLLOW_UP`이다. 후속평가는 기준 평가 ID를 반드시 가져야 한다. 기준 평가는 다른 기준 평가를 참조할 수 없다. 요청 모델이 이 규칙을 먼저 확인한다.

추천 요청에는 기존과 같은 사용자 특성, 목표, 입력 가용성, 정규화된 기기 스냅샷, 출처별 동의가 들어간다. 웨어러블이나 CGM 값이 하나도 없으면 기기 평가가 아니다. 실제로 포함된 기기 출처는 추천 목적 사용 동의와 영구 저장 동의를 모두 받아야 한다. 동의가 빠진 민감 수치를 점수 계산이나 계보 저장에 사용하지 않는다.

검증을 통과하면 기존 `recommend()`를 호출한다. 새 코드가 후보 점수 공식을 복제하지 않는다. 추천 응답에서 선택 후보별 `wearable_adjustment`, `cgm_adjustment`, `total`을 뽑아 점수 스냅샷을 만든다. 기기 스냅샷은 웨어러블·CGM 가용성 표시와 수치 필드만 남긴다. 유전자 값이나 설문 값은 기기 후속 변화량에 섞지 않는다.

후속평가는 저장된 기준 평가를 읽는다. 프로필 ID, 데이터 분류, 세션 출처가 모두 같아야 한다. 프로필 ID는 실행 원장과 같은 결정 규칙으로 만든다. 같은 요청 주체가 아니거나 시뮬레이션 기준 평가에 생산 후속평가를 붙이면 실패한다. 이 검사를 통과한 뒤 같은 수치 필드의 기준값, 후속값, 차이를 계산한다. 양쪽 추천 결과에 모두 존재하는 후보는 웨어러블 조정, CGM 조정, 전체 점수의 차이를 계산한다.

## 구체적인 고정 사례

고정 사례는 수면 지원 목표와 웨어러블 수면 시간을 사용한다. 기준 수면 시간은 5시간이다. 기존 후보 점수 규칙은 `magnesium_glycinate`에 웨어러블 조정점수 4점을 적용한다. 이 값은 새 코드가 만든 숫자가 아니라 실제 추천 엔진 응답에서 읽은 값이다.

후속 수면 시간은 8시간이다. API가 계산한 수면 변화량은 `8.0 - 5.0 = 3.0`시간이다. 부족 수면 조건이 사라지므로 같은 후보의 웨어러블 조정점수 변화량은 `-4.0`이다. 고정 증거는 기준 점수 4.0, 수면 변화 +3.0, 점수 변화 -4.0을 함께 확인한다. 이 사례로 기기 값이 추천 점수에 들어가고, 후속 값이 같은 점수 항목의 변화로 이어졌다는 사실을 한 번에 재현한다.

점수 변화는 치료 효과를 뜻하지 않는다. 기기 값과 후보 우선순위가 규칙에 따라 달라졌다는 뜻이다. 수면 시간이 늘어난 원인을 추천 제품으로 돌릴 수 없고, 후보 점수가 내려갔다고 건강 상태가 악화됐다는 뜻도 아니다. 그래서 저장 결과는 수치와 점수의 관찰 변화만 제공한다. 인과 효과 문구를 만들지 않는다.

## 저장과 재시도

스키마 버전은 12에서 13으로 올렸다. `device_recommendation_assessments` 테이블에는 평가 ID, 프로필 ID, 단계, 기준 평가 ID, 데이터 분류, 세션 출처, 요청 해시, 기기 스냅샷, 점수 스냅샷, 기기 변화량, 점수 변화량, 생성 시각을 저장한다. 원본 기기 파일은 이 테이블에 넣지 않는다. 원본 파일 해시는 OP-096의 별도 계보가 맡는다.

테이블은 추가 전용이다. `UPDATE`와 `DELETE`는 SQLite 트리거가 거부한다. 같은 평가 ID를 재전송했을 때 모든 저장 값이 같으면 기존 행을 재사용하고 `deduplicated=true`를 반환한다. 같은 ID인데 요청이나 결과가 다르면 `device_assessment_identity_conflict`로 실패한다. 네트워크 재시도를 허용하면서 서로 다른 평가를 같은 ID로 덮어쓰지 않는다.

## 검증 범위

자동 테스트는 수면 값이 실제 추천 점수를 바꾸는지, 후속 수치와 점수 차이가 계산되는지, 정확 재생이 중복 제거되는지, 다른 요청이 같은 ID를 쓸 때 실패하는지 확인한다. 생산/시뮬레이션 오표기와 교차 데이터 분류 후속평가도 거부한다. 저장 행 수정과 삭제를 직접 SQL로 시도해 불변 트리거도 확인한다. 인증 토큰이 없는 API 요청은 401, 올바른 토큰 요청은 200이다.

canonical 실행기는 6개 고정 사례를 실제 FastAPI `TestClient`와 임시 SQLite 파일에서 실행한다. 기준·후속·생산 경계 평가 3개 행을 저장하고 다시 읽는다. 추천 엔진을 흉내 낸 고정 점수 표를 사용하지 않는다. 데이터셋과 실행기, 구현 파일의 Git 내용 해시와 소스 커밋을 증거에 기록한다.

## 남은 한계

현재 후속평가는 동일 후보가 두 추천 결과에 모두 있을 때 점수 차이를 제공한다. 기준 시점에만 있거나 후속 시점에만 있는 후보는 공통 후보 차이 표에 들어가지 않는다. 후보 진입·이탈을 별도 상태로 설명하는 기능은 다음 확장 범위다. 여러 웨어러블 공급자의 원본 세션을 가져오는 연결도 아직 없다.

생산 트래픽, 실제 기기 사용자, 운영 데이터베이스, 장기 수치 품질, 임상 효과는 검증하지 않았다. OP-097의 통합 완료는 저장소 내부의 실제 API·추천·후속평가 연결을 뜻한다. 생산 운영 완료나 의료적 유효성 확인을 뜻하지 않는다.
