# OP-108 실제 상품 후보를 추천 결과와 연결한다.

## 결론

OP-108은 `IMPLEMENTED` 단계다. WellnessBox 서비스에는 R&D 추천의 성분·함량·안전 제약을 판매 상품 후보와 결합하는 코드와 회귀 검사가 있다. 다만 canonical evidence는 상품 카탈로그와 R&D 응답을 dependency injection으로 넣은 fixture를 사용한다. 실제 Prisma 조회, 실제 판매 데이터베이스, 실제 R&D HTTP 추천 응답을 한 경로에서 함께 실행하지 않았다. 요구 단계 `OPERATED`에 못 미치므로 완료 판정은 `PARTIAL`이다.

## 요구사항과 판정 기준

원문은 “실제 상품 후보”를 추천 결과와 연결하라고 요구한다. 구현 코드가 상품 ID 모양의 문자열을 만들어 내는 것만으로는 부족하다. 최소한 서비스의 판매 상품 저장소에서 상품을 읽고, 실제 R&D 추천 응답과 결합하며, 재고와 안전 조건을 지키는 경로를 증명해야 `INTEGRATED`라고 판단할 수 있다. 운영 단계라면 승인된 환경에서 최신 재고, 사용자 승인, 주문 경계까지 관측해야 한다.

현재 QA는 서비스 라우트의 의존성 주입 지점을 사용한다. R&D 응답 fixture와 상품 카탈로그 fixture를 주입해 조합 규칙을 결정적으로 검증한다. 이 방식은 빠르고 실패 원인을 분리하기 좋지만, Prisma 연결이나 R&D 서버 연결을 증명하지 않는다. 이전 증거가 fixture 상품을 `selling_products_loaded`라고 표현하고 `INTEGRATED`를 주장한 것은 증거보다 강한 표현이었다. 이번 수정은 검사를 `selling_product_fixture_loaded`로 바꾸고 단계도 `IMPLEMENTED`로 낮췄다.

## 구현된 상품 후보 계약

서비스의 추천 라우트는 먼저 사용자 인증을 확인하고 사용자 식별자를 가명 처리한다. R&D 추천 응답은 안전 권한 검사를 통과해야 한다. 안전 응답이 유효하지 않거나 R&D가 실패하면 상품 후보를 붙이지 않고 fail-closed 응답을 반환한다. 추천이 비어 있으면 카탈로그를 읽지 않고 원래 응답을 반환한다.

추천 항목이 있으면 `listWbRndProductCatalog`가 판매 가능한 상품 필드를 읽도록 설계돼 있다. `attachWbRndProductCandidates`는 추천 성분, 상품 성분, 함량, 재고, 조합 제약을 비교해 후보를 만든다. 후보 ID를 임의로 합성하지 않으며, 일치하는 상품이 없으면 `NO_MATCH` 상태를 남긴다. 이 계약은 후보가 없는 상황을 성공한 판매 연결처럼 표시하지 않게 한다.

상품 카탈로그가 잘못됐거나 함량이 모호하면 서비스는 502로 닫힌다. 안전 검사가 제외한 성분은 상품 후보 단계에서 다시 들어올 수 없다. 재고가 바뀌면 기존 최적화 규칙으로 안전한 대체 후보를 다시 고른다. 이 규칙은 추천 품질보다 안전 제약을 우선하고, 데이터가 불완전할 때 상품을 추측하지 않는 경계를 만든다.

## 자동 검증 범위

서비스 QA는 고정 카탈로그에서 기대한 상품 ID가 후보에 들어가는지 확인한다. 상품 조합이 결정적으로 생성되는지, 재고 변경이 안전한 대체 상품 선택으로 이어지는지, 안전 제외 성분이 다시 나타나지 않는지 확인한다. 잘못된 카탈로그가 502를 반환하는지도 확인한다. 이러한 검사는 상품 후보 결합 코드의 구현과 회귀 방지에는 충분하다.

그러나 QA의 `listProductCatalogImpl`은 실제 `listWbRndProductCatalog`가 아니다. fixture 배열을 반환하는 함수다. R&D 응답도 실제 HTTP 응답이 아니라 주입한 객체다. canonical runner가 별도의 R&D FastAPI 프로세스를 띄우지만, 상품 QA는 그 프로세스를 호출하지 않는다. 같은 runner 안에서 두 검사를 실행했다는 사실만으로 상품 경로가 R&D 서버와 연결됐다고 볼 수 없다.

## canonical evidence를 정직하게 읽는 법

증거의 `selling_product_fixture_loaded`는 fixture에 상품 ID가 있다는 사실만 나타낸다. `product_candidates_attached`는 서비스 결합 로직이 그 fixture를 후보로 붙였다는 뜻이다. `invalid_catalog_fails_closed`와 `stock_and_safety_preserved`는 오류 처리와 안전 불변식을 나타낸다. `actual_prisma_catalog_or_rnd_product_integration_proven`은 `false`다.

이 구분은 결과를 낮춰 보이게 만들기 위한 것이 아니다. 다음 검증이 무엇을 추가해야 하는지 정확히 드러낸다. 실제 Prisma 카탈로그를 사용한 테스트가 통과하면 상품 출처에 대한 증거가 생긴다. 그 테스트가 실제 R&D HTTP 응답까지 받아 결합하면 로컬 통합 단계로 올릴 근거가 생긴다. 지금은 두 경계가 모두 fixture이므로 `IMPLEMENTED`가 맞다.

## 사용자 행동과 데이터 변경 경계

이번 검증은 카트, 주문, 결제를 만들지 않는다. 추천 결과에 후보 정보를 붙이는 순수한 서버 응답 경로만 확인한다. 사용자 승인 전 상품을 자동으로 카트에 저장하지 않으며, 재고를 차감하지 않는다. Order, OrderItem, Payment 레코드를 만들거나 바꾸지 않는다. 운영 상품 데이터도 쓰지 않는다.

상품 후보가 안전하고 재고가 있다는 판단은 구매 완료를 의미하지 않는다. 실제 주문 시점에는 가격, 재고, 판매 상태를 다시 확인해야 한다. 결제와 법적 고지는 별도 서비스 경계에 남아 있다. OP-108 증거는 이러한 후속 행동을 수행하거나 승인하지 않는다.

## 재현 방법

R&D 저장소에서 `python scripts/run_admin_product_integration_smoke.py`를 실행하면 관리자 검증과 상품 계약 검증을 함께 재생할 수 있다. 상품 계약만 확인하려면 WellnessBox 저장소에서 `node --conditions=react-server --import tsx scripts/qa/check-rnd-product-candidates.cts`를 실행한다. 두 명령 모두 fixture 경계를 유지하므로 실행 결과를 실제 판매 데이터 조회 증거로 해석하면 안 된다.

증거 파일은 사용한 WellnessBox 커밋과 R&D 커밋, runner·데이터셋·API 파일의 Git blob SHA를 기록한다. 워크플로는 WellnessBox 커밋을 고정해 서비스 코드가 바뀌어도 동일한 입력을 재생한다. 이 재현성은 구현 검증을 강화하지만, fixture를 실제 데이터로 바꾸지는 않는다.

## 남은 단계

다음 단계는 격리된 테스트 데이터베이스에 판매 상품을 심고 실제 Prisma 어댑터 `listWbRndProductCatalog`를 호출하는 것이다. 그 다음 실제 localhost R&D 추천 API의 READY 응답을 서비스 추천 라우트가 받아 Prisma 상품과 결합해야 한다. 실제 상품 ID, 함량, 재고, 안전 제외 결과를 canonical evidence에 남겨야 `INTEGRATED` 승격을 검토할 수 있다.

`OPERATED` 판정에는 승인된 환경의 최신 상품 데이터, 관리자 또는 사용자 화면 관측, 재고 변화, 오류율과 지연, 사용자 승인 이후의 안전한 주문 경계가 필요하다. 공개 배포, 운영 데이터 변경, 주문 또는 결제는 이번 루프에서 수행하지 않았다. 외부 전문가 검증과 실제 구매 결과도 주장하지 않는다.
