# OP별 연구보고서 작성 원칙

## 왜 120개의 별도 보고서가 필요한가

`requirements_manifest_v1.json`은 OP-001부터 OP-120까지 빠짐없이 추적하는 기계 판독용 장부다. 이 장부만 보면 어떤 파일과 테스트가 특정 요구사항의 증거로 등록됐는지는 알 수 있다. 하지만 왜 그 구현을 선택했는지, 기존 시스템의 어느 부분을 재사용했는지, 실험 과정에서 무엇이 실패했는지, 로컬 구현과 실제 운영 사이에 어떤 간격이 남았는지는 충분히 이해하기 어렵다. 짧은 smoke JSON이나 테스트 통과 숫자만으로는 연구 과정도 복원할 수 없다.

최종 결과물에는 따라서 OP마다 하나씩, 모두 120개의 독립된 연구보고서가 있어야 한다. 보고서 한 편은 그 OP를 처음 접한 사람이 다른 인계 문서를 읽지 않아도 문제와 결과를 이해할 수 있는 독립 문서여야 한다. 여러 OP를 한 보고서에 묶어 개수를 줄이지 않는다. 서로 같은 bounded loop에서 구현한 두 요구사항이라도 설계 목적과 증거 경계가 다르면 각각 별도 문서로 설명한다.

## 보고서는 무엇을 설명해야 하는가

각 보고서는 먼저 원문 요구사항을 쉬운 말로 풀어 쓴다. 그다음 요구사항이 기존 WellnessBox 서비스와 R&D 시스템에서 어떤 사용자 문제를 해결하는지 설명한다. 구현 전 상태에서는 사용할 수 있었던 코드, 저장소, 데이터 계약, 테스트가 무엇이었는지 밝히고, 빠져 있던 기능과 증거를 구분한다. 새 구현을 추가했다면 새 시스템을 하나 더 만든 것이 아니라 기존 경로를 어떻게 확장했는지 파일과 데이터 이동 순서에 맞춰 서술한다.

실험과 검증 과정은 성공 결과만 나열하지 않는다. 처음 실행한 테스트가 왜 실패했는지, 실패 원인을 어떤 증거로 좁혔는지, 수정 범위를 왜 그 수준으로 제한했는지 적는다. 결정적 smoke, 집중 테스트, GitHub workflow 선택 테스트, 전체 회귀, frozen eval, 독립 검토 결과는 각각 무엇을 증명하고 무엇을 증명하지 못하는지 문장으로 설명한다. 숫자는 문장 속 근거로 사용하되 숫자 목록만으로 본문을 대신하지 않는다.

마지막에는 `IMPLEMENTED`, `INTEGRATED`, `OPERATED`, `EXTERNAL` 중 실제로 증명한 단계를 명시한다. 배포하지 않았다면 운영을 주장하지 않고, 실제 서비스 연결을 확인하지 않았다면 통합을 주장하지 않는다. 외부 라벨이나 실제 사용자 관측이 필요한 요구사항은 로컬 테스트가 아무리 많이 통과해도 그 한계를 그대로 남긴다. 독자가 다음 연구자가 해야 할 일을 구체적으로 알 수 있도록 남은 위험과 다음 검증 방법을 설명한다.

## 문장과 구성 원칙

본문은 축약 메모가 아니라 완전한 문장과 연결된 문단으로 쓴다. 제목 아래에 한두 줄짜리 bullet만 반복하는 방식은 사용하지 않는다. 표는 여러 상태나 수치를 정확히 비교해야 할 때만 보조적으로 사용한다. 파일명, 함수명, 명령, 해시, 커밋, 오류 문자열은 정확한 값을 보존하지만, 그 값이 왜 중요한지도 바로 이어서 설명한다.

분량 자체를 KPI로 삼아 의미 없는 문장을 늘리지는 않는다. 다만 짧게 줄이기 위해 문제, 판단 근거, 실패 과정, 증거 한계 중 하나를 생략해서도 안 된다. 단순한 요구사항도 독립적으로 이해할 수 있을 만큼 설명하고, 복잡한 요구사항은 설계와 검증을 충분히 따라갈 수 있을 때까지 길게 쓴다. 보고서를 읽은 사람이 “무엇을 만들었는가”뿐 아니라 “왜 이 결과를 믿어도 되는가”와 “아직 무엇을 믿으면 안 되는가”까지 이해하는 것이 완료 기준이다.

## 파일과 추적 방식

보고서 파일명은 `OP-001.md`부터 `OP-120.md`까지 고정한다. 보고서는 `docs/original_plan/research_reports/`에 저장하며, 같은 OP의 `v2`, `final`, `latest` 복사본을 만들지 않고 canonical 파일을 갱신한다. 보고서가 존재한다는 사실만으로 완료로 보지 않는다. 해당 OP의 최신 manifest, canonical evidence, 소스 커밋, 테스트, 운영 또는 외부 증거와 내용이 일치하는지 다시 확인한 뒤 보고서 상태를 확정한다.

현재 OP별 장문 보고서는 아직 120개가 아니다. OP-079와 OP-080부터 이 원칙을 적용하고, 이미 구현된 OP-001부터 OP-078도 기존 완료 숫자를 그대로 옮겨 적지 않고 증거를 다시 읽으며 소급 작성한다. 최종 감사에서는 120개 파일의 존재뿐 아니라 각 문서의 요구사항 일치, 근거 정확성, 단계 주장, 남은 한계를 함께 확인한다.
