# OP-012 질환·증상·중증도·응급 위험 신호를 구조화한다

## 같은 “가슴 통증”도 상태와 심각도가 다르면 다르게 처리해야 한다

원본 데이터 레이크 그림은 병력과 증상을 개인 특성 파라미터에 포함하고, 사용자 입력이 엔진·모델과 상호작용 기록으로 이어지게 한다. 문자열 목록만 쓰면 현재 질환과 과거 해결된 질환, 가벼운 증상과 critical 증상, 실제로 존재하는 응급 신호와 부재를 구분하기 어렵다. OP-012의 결과는 질환 상태, 증상 중증도와 기간, 응급 위험 신호의 존재와 출처를 구조화하고, 명시적인 응급 신호가 추천보다 먼저 안전 차단으로 이어지게 하는 것이다.

## 세 입력 모델이 서로 다른 질문에 답한다

`src/wellnessbox_rnd/schemas/recommendation.py`의 `ConditionInput`은 code, status, 선택 display name을 가진다. status는 `active`, `suspected`, `history`, `resolved`다. `SymptomInput`은 code, `unspecified`부터 `critical`까지의 severity, 0~36,500일의 선택 duration을 가진다. `UrgentRiskSignal`은 code, present boolean, `self_report`, `clinician`, `device`, `imported_record`, `legacy` source를 가진다. 세 모델 모두 알 수 없는 필드를 거부하고 code는 공백 제거 후 1~128자로 제한한다.

기존 문자열 입력도 즉시 폐기하지 않았다. `RecommendationRequest`는 각 목록에서 문자열이나 구조 객체를 받는다. `src/wellnessbox_rnd/domain/intake.py`는 둘을 동일한 normalized code 경로로 보낸다. legacy symptom은 severity `unspecified`, legacy condition은 `active`, legacy risk flag는 present true와 source `legacy`가 된다. 새 API를 따로 만들지 않고 기존 요청·intake·안전 서비스·모델 feature 경로를 확장했다.

## 중복 코드에는 가장 보수적인 상태를 남긴다

증상 정규화는 같은 code가 여러 번 들어오면 `unspecified < mild < moderate < severe < critical` 순서에서 가장 높은 severity를 map에 남긴다. 질환은 `resolved < history < suspected < active` 순서로 집계하고 resolved만 있는 code는 현재 `condition_set`에서 제외한다. 위험 신호는 `present=true`인 항목만 활성 set과 source map에 넣는다. present false로 들어온 imported signal은 원본 normalized record에는 남지만 차단 신호로 사용하지 않는다.

이 설계는 중복 입력을 임의의 마지막 값으로 덮지 않는다. 동시에 입력 원문 레코드를 보존해 왜 집계가 그렇게 됐는지 추적할 수 있다. 다만 서로 다른 source가 같은 active risk code를 여러 번 보낼 때 source 우선순위를 임상 신뢰도로 계산하지는 않는다. 마지막 active source가 map에 남는 현재 동작은 임상 출처 합의 시스템이 아니며, 외부 기록의 진위를 검증하지도 않는다.

## 응급 신호는 추천을 비우고 안전 재검사를 요구한다

`src/wellnessbox_rnd/safety/service.py`는 normalized `risk_flag_set`을 data-defined risk rule과 대조한다. 샘플의 `red_flag_chest_pain`은 `SAFETY-URGENT-SYMPTOM-001`을 적용한다. `/v1/recommend` 응답은 status `blocked`, 빈 recommendations, next action `trigger_safety_recheck`를 반환한다. 모델 점수가 높더라도 응급 위험 신호를 지나 추천을 만들지 않는다. 질환 set은 condition-specific exclusion·review 규칙에 재사용된다.

severity가 critical이라는 사실만으로 모든 임상 응급상황을 자동 분류하지는 않는다. 현재 차단은 등록된 urgent risk code와 안전 규칙의 교집합에 근거한다. 자유 텍스트 증상을 진단하거나 누락된 응급 신호를 추론하는 의료 모델이 아니다. 지원하지 않는 code가 들어오면 구조적으로 저장될 수 있으나 해당 안전 rule이 없으면 그 code만으로 차단되지 않는다. 이 한계 때문에 실제 의료상담과 외부 임상 검증을 주장할 수 없다.

## 테스트는 상태 손실과 우회 경계를 실행한다

`tests/test_health_input_contracts.py`는 critical chest pressure, active와 resolved condition, present true·false 위험 신호를 샘플에서 읽는다. 정규화 뒤 symptom severity, duration 0, condition status, display name, risk source가 보존되는지 확인한다. legacy 문자열도 같은 code path를 통과하며 기본 severity·status·source가 명시되는지 검사한다. resolved condition이 deterministic risk와 learned model guard를 활성화하지 않고 active condition은 guard reason을 만드는지도 실행한다.

같은 테스트와 `tests/test_inference_api.py`는 urgent flag를 실제 FastAPI TestClient로 POST한다. HTTP 200 안에서 안전 판정이 blocked이고 추천 배열이 비며 next action과 rule ID, timezone-aware 적용 시각과 양의 rule version이 존재하는지 확인한다. OpenAPI에는 `ConditionInput`, `SymptomInput`, `UrgentRiskSignal`과 구조화 예제가 노출된다. 이 테스트는 schema parsing, intake, 안전 서비스, 응답 계약을 잇지만 production 배포나 실제 응급 대응 시간을 증명하지 않는다.

## 모델 경로는 구조화 code를 안정적으로 재사용한다

효능·정책 feature builder는 active condition과 symptom code를 안정된 key로 만든다. resolved condition은 active count와 guard에서 제외된다. closed-loop와 synthetic generator도 같은 normalized 상태를 사용해 과거 해결 질환을 현재 위험으로 잘못 올리지 않는다. manifest에 여러 모델·simulation 파일이 구현 증거로 등록된 이유는 새로운 병렬 모델을 만들었다는 뜻이 아니라 기존 feature 소비자가 구조화 상태를 이해하도록 함께 수정했기 때문이다.

핵심 도입 커밋은 `d57c8804be59c19932db01262df82ee1ee265bad`다. 기존 응급 안전 입력과 rule 연결은 `1ef1cf3646b5a276c9b299d20c1e25fff44e9c54`에서 먼저 자리 잡았고, 구조화 commit이 상태·severity·source를 추가하면서 같은 안전 경로를 보존했다. canonical manifest 감사와 completion report, GitHub workflow는 이 경로와 테스트가 추적된 상태인지 반복 확인한다.

## 완료 단계와 남은 조건

OP-012의 required stage와 claimed stage는 `IMPLEMENTED`다. 구조화 모델, 단일 normalization 경로, resolved·active 경계, 명시적 urgent 차단, API·model 회귀 테스트가 있으므로 구현 단계는 완료다. 서비스 production traffic, 실제 의료진 대응, 응급 신호의 민감도·특이도, 외부 임상 검증은 증명하지 않았다. `INTEGRATED`, `OPERATED`, 외부검증을 주장하지 않는다.

이번 보고서 backfill은 코드·서비스·데이터·학습·모델·simulation을 변경하지 않는다. frozen 평가와 replay·slice delta는 0이다. 남은 조건은 지원 code와 임상 rule의 근거를 계속 관리하고, 실제 운영이 요구되는 후속 OP에서 승인된 배포·관찰 증거를 확보하며, 독립 전문가가 필요한 안전 평가는 외부 receipt로 검증하는 것이다.
