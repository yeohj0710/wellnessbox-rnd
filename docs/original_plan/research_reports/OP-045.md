# OP-045 안전 차단 전후 후보를 모두 보존한다

## 결론과 요구사항

OP-045의 요구사항은 안전 규칙을 적용하기 전 후보, 제외된 후보와 제외 이유, 안전 규칙을 통과한 후보, 최종 선택 후보를 한 응답에서 서로 대조할 수 있게 보존하는 것이다. 현재 구현은 이 네 집합을 `CandidatePoolTrace`에 담고 각 후보의 식별자와 목표를 유지한다. 따라서 최종 추천만 보고 “원래 후보가 없었는지”, “후보는 있었지만 안전 규칙 때문에 빠졌는지”, “안전 후보였지만 점수나 출력 개수 때문에 선택되지 않았는지”를 구분할 수 있다.

이전 구조의 핵심 결함은 최종 선택 목록만으로 탈락 시점을 재구성하기 어렵다는 점이었다. 특히 전역 차단이 발생하면 결과가 빈 배열이 되므로, 후보 생성 실패와 안전 차단을 같은 상태로 오해할 수 있었다. 이번 변경은 전체 성분 카탈로그를 무조건 노출하는 방식이 아니라 요청 목표와 연결된 후보만 `pre_safety_candidates`에 넣는다. 그 후보 집합을 안전 규칙, 사용자가 피하려는 성분, 현재 복용 성분으로 나눈 뒤 추적한다.

매니페스트에 등록된 핵심 구현 경로는 `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/service.py`이다. 이 경로와 함께 스키마, 단위 테스트, 스모크 스크립트, JSON 증거 파일이 모두 실제 저장소에 존재하며 요구사항과 일치한다.

## 코드에서 후보 집합을 보존하는 방식

`select_recommendations_with_diagnostics`는 `_partition_candidate_pool`을 먼저 호출한다. `_partition_candidate_pool`은 요청 목표에 연결된 후보마다 `CandidatePoolItem`을 만들고, 다음 세 제외 사유를 누적할 수 있다: `SAFETY_RULE_EXCLUDED`, `USER_AVOIDED`, `CURRENT_REGIMEN`. 하나의 후보에 이유가 여러 개면 첫 이유만 남기지 않고 모두 보존한다. 안전 통과 후보에 대해서만 점수와 순위를 계산하며, `build_candidate_pool_trace`가 사전 후보·제외 후보·통과 후보·선택 후보를 하나의 추적으로 묶는다.

`wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`의 `CandidatePoolTrace.validate_candidate_partition`은 추적값을 단순 설명 필드로 취급하지 않는다. 사전 후보가 제외 후보와 통과 후보의 정확한 분할인지, 후보의 성분 키와 목표가 단계 사이에서 바뀌지 않았는지, 선택 후보가 통과 후보의 부분집합인지 검사한다. 각 통과 후보에는 `CandidatePreselectionScore`가 있어야 하고, 순위는 1부터 끊김 없이 이어져야 한다. 점수가 같을 때 성분 키로 순서를 고정하며, 전역 차단이면 선택 후보가 하나도 없어야 한다. `CandidatePreselectionScore.validate_preserved_candidate_score`는 보존된 점수 합계와 이유 분해의 합계, 목표 보너스까지 다시 맞춘다.

오케스트레이션의 `recommend`는 안전 결과가 차단이어도 후보 추적 생성을 생략하지 않는다. 하드 차단에서는 `globally_blocked=true`와 빈 선택 집합을 반환하되 사전 후보와 제외 근거는 남긴다. 이 설계 때문에 빈 추천 결과가 후보 부재인지 전역 차단인지 응답만으로 판별된다.

## 검증한 실패 사례와 결과

`wellnessbox-rnd/tests/test_candidate_pool_structured_reasons.py`의 `test_candidate_pool_preserves_pre_excluded_post_and_selected_sets`는 와파린 입력에서 오메가3가 `SAFETY-ANTICOAG-001`로 제외되고 CoQ10이 통과하는 분할을 확인한다. `test_candidate_pool_keeps_user_avoidance_and_current_regimen_categories`는 사용자 회피와 현재 복용 사유가 별도 범주로 남는지 확인한다. `test_global_block_preserves_pool_but_never_claims_a_selection`은 전역 차단 뒤 후보 흔적은 남지만 선택은 없다는 불변식을 고정한다. `test_candidate_trace_and_reason_contracts_fail_closed_on_mismatch`는 후보 누락, 식별자 변경, 잘못된 선택 부분집합 같은 변조가 검증 오류로 닫히는지 확인한다. `test_api_and_openapi_expose_candidate_pool_and_structured_reasons`는 내부 객체뿐 아니라 API 응답과 OpenAPI 스키마에도 추적 필드가 노출되는지 검사한다.

등록된 `wellnessbox-rnd/scripts/run_candidate_pool_structured_reasons_smoke.py`가 만든 `wellnessbox-rnd/data/original_plan/evidence/op045_op046_candidate_pool_structured_reasons_smoke_v1.json`에는 와파린 사례의 사전 후보 `coq10`, `omega3`, 제외 후보 `omega3`, 통과·선택 후보 `coq10`이 기록되어 있다. 별도 사례에서는 한 후보에 안전 사유와 현재 복용 또는 사용자 회피 사유가 함께 남고, 전역 차단 사례에서는 사전 후보 2개와 선택 0개가 기록된다. 이번 확인에서 OP-045 관련 집중 테스트를 포함한 74개 테스트가 모두 통과했다.

## 증거 단계와 남은 한계

현재 단계는 매니페스트와 증거 파일이 선언한 `IMPLEMENTED`가 맞다. 스키마, 최적화 함수, API 직렬화, 변조 거부 테스트가 같은 후보 집합 규칙을 검증하고, 증거 파일의 연구 코드 커밋 `94b0374a3599973ba5201a3cc751912f07bb146a` 이후 등록된 OP-045 소스에는 차이가 없다. 구현과 재현 가능한 테스트를 넘어 실제 서비스 트래픽에서 이 진단 정보가 저장·조회되었다는 증거는 없다.

증거 파일도 `production_operation_proven=false`라고 명시한다. 그러므로 이 보고서는 실제 사용자 요청에서 후보 추적이 운영 로그나 상담 화면에 사용되었다고 주장하지 않는다. 또한 `pre_safety_candidates`는 전체 카탈로그가 아니라 목표에 맞는 후보 집합이므로, 목표 매핑 이전 단계에서 누락된 성분까지 추적한다는 의미도 아니다. 운영 관측, 장기 보관, 상담자 사용성은 별도 검증 대상이다.
## 추천 후보를 점수로 바꿀 때
추천 후보를 잘 고르는 일과 특정 후보를 복용했을 때의 효과를 추정하는 일은 다르다. 이 그룹은 입력 신호가 어떤 점수로 바뀌는지, 안전 차단 전후의 후보가 어떻게 보존되는지, 불확실성을 어디에 표시하는지를 분리해 설명한다.

`OP-045`는 “안전 차단 전후 후보를 모두 보존한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=18`, `docs/context/original_plan.pdf#page=19`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/optimizer/service.py`, `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/recommendation_service.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_candidate_pool_structured_reasons.py`, `wellnessbox-rnd/scripts/run_candidate_pool_structured_reasons_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op045_op046_candidate_pool_structured_reasons_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
