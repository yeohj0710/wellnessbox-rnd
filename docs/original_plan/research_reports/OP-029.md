# OP-029 세션을 같은 입력과 버전으로 재생하는 replay API를 만든다.

## 다시 실행했다는 말에는 조건이 붙어야 한다
추천 결과가 어제와 오늘 같았다는 사실만으로 재현됐다고 말할 수는 없다. 입력이 달랐을 수도 있고, 모델·데이터셋·설정·코드가 바뀌었을 수도 있다. 반대로 버전이 달라졌는데 추천을 다시 실행한 뒤 결과만 비교하면 무엇 때문에 차이가 났는지 알기 어렵다. OP-029가 요구하는 replay는 저장된 입력과 실행 identity가 모두 같은지 먼저 확인하고, 조건이 맞을 때만 추천을 다시 계산해 canonical 출력 hash를 비교하는 절차다.

원본 계획 16쪽은 개인 특성, 전문 지식, 행동·상호작용 로그와 엔진 결과를 한 저장 체계에서 연결하는 그림을 제시한다. 그 구조에서 replay는 결과 로그를 한 번 더 읽는 기능이 아니다. 어떤 입력과 어떤 모델·코드·데이터가 결과를 만들었는지 묶어 두고 같은 묶음을 다시 실행할 수 있어야 한다. 현재 구현은 이 요구를 R&D interim SQLite와 FastAPI 안에서 재현 가능한 단위로 만들었다.

## 기존 추천 실행 원장에 snapshot을 덧붙였다
`src/wellnessbox_rnd/interim/data_lake.py`는 추천 요청과 응답을 `executions`, profile snapshot, consent snapshot, execution events와 실행 identity에 기록한다. OP-029는 별도 추천 시스템을 만들지 않고 이 저장 transaction에 `execution_replay_snapshots`를 추가했다. snapshot에는 정규화된 요청 JSON, 요청 SHA-256, 비교용 예상 출력 JSON과 출력 SHA-256이 들어간다.

실행 identity는 `src/wellnessbox_rnd/interim/execution_identity.py`가 만든다. model ID, engine version, code commit, dataset artifact의 ID·경로·SHA-256, 설정 JSON과 설정 hash를 고정한다. replay는 이 identity를 다시 계산해 저장 identity와 비교한다. 원 추천과 replay가 같은 코드만 썼다는 좁은 조건이 아니라, 결과에 영향을 줄 수 있는 모델·데이터·설정까지 같은지 보는 구조다.

## 저장 동의가 없으면 입력 snapshot을 만들지 않는다
같은 입력을 재생하려면 원 입력을 저장해야 하지만, 재현성 때문에 동의 경계를 넘을 수는 없다. 추천에 사용된 모든 표현 source가 persistent storage를 허용할 때만 replay snapshot을 저장한다. survey 저장 동의가 꺼져 있거나 NHIS처럼 payload에 나타난 source가 저장을 허용하지 않으면 실행 행은 남더라도 replay snapshot은 만들지 않는다.

따라서 세션 목록의 전체 저장 건수와 replay 가능 건수는 다를 수 있다. `total_saved_sessions`는 execution 수, `replayable_sessions`는 snapshot 수, `unavailable_sessions`는 둘의 차이다. 저장 동의를 받지 못한 민감 입력을 replay 편의를 위해 다른 table에 복제하지 않는다. 테스트는 저장이 금지된 NHIS marker가 profile snapshot과 execution event payload에 남지 않는지도 확인한다.

## replay는 입력·버전·출력을 세 단계로 비교한다
`src/wellnessbox_rnd/interim/session_replay.py`의 `SessionReplayLedger.replay`는 execution ID 형식을 먼저 검사한다. 저장 snapshot과 identity를 읽은 뒤 JSON을 Pydantic request로 다시 검증하고, 저장 request hash·execution request hash·재계산 hash가 모두 같은지 확인한다. 예상 출력 hash도 저장 JSON에서 다시 계산한다. 하나라도 다르면 손상된 snapshot으로 보고 추천을 실행하지 않는다.

그다음 저장 identity와 현재 identity를 비교한다. code commit이 unresolved이거나 model·engine·dataset·config가 다르면 상태는 `VERSION_MISMATCH`다. 이 경우 추천 runner를 호출하지 않고 `actual_output_sha256=null`, `output_match=null`을 남긴다. 조건이 다른 실행을 같은 replay로 포장하지 않는 fail-closed 동작이다.

입력과 버전이 모두 같을 때만 저장 요청으로 추천을 실행한다. 응답에서 execution ID, decision ID, generated time처럼 실행마다 달라지는 필드를 제외한 canonical payload를 만들고 SHA-256을 비교한다. 같으면 `MATCH`, 다르면 `MISMATCH`이며 차이가 난 필드 경로를 최대 20개까지 기록한다. runner 자체가 실패하면 민감한 exception 본문은 저장하지 않고 `recommendation_execution`이라는 제한된 mismatch만 남긴 뒤 원 오류를 다시 발생시킨다.

## API는 원문 대신 제한된 비교 결과만 돌려준다
FastAPI 경로는 `GET /v1/interim/executions?limit=20`과 `POST /v1/interim/executions/{execution_id}/replay`다. 두 endpoint는 내부 token을 요구한다. 목록은 execution ID, 생성 시각, 상태, replay 가능 여부, 마지막 replay 상태와 시각을 반환한다. replay 응답은 입력·버전·출력 일치 여부, 저장·현재 model과 engine, hash와 mismatch field를 제공한다.

요청 원문이나 추천 응답 원문은 API 응답에 넣지 않는다. UI가 replay 상태를 보여주기 위해 개인 건강정보 전체를 다시 받을 필요가 없기 때문이다. 존재하지 않는 execution은 404, 잘못된 ID 형식은 422, 저장 동의 때문에 replay snapshot이 없는 실행은 409로 구분한다. 목록 limit도 1~100으로 제한한다.

## replay 기록은 결과를 덮어쓰지 않는다
실행할 때마다 `execution_replay_runs`에 새 row가 생긴다. replay ID, 상태, 일치 flag, 예상·실제 출력 hash, mismatch fields, 저장 identity hash와 현재 identity hash, 실행 시각을 기록한다. snapshot과 run table에는 update·delete를 막는 append-only trigger가 있다. 이전 결과를 최신 결과로 덮어써서 과거 불일치를 지울 수 없다.

이 원장은 추천 품질 평가 데이터셋을 대신하지 않는다. replay는 동일 조건에서 계산이 결정적인지 확인한다. 추천 자체가 올바른지, 임상적으로 유효한지, 실제 사용자에게 도움이 됐는지는 별도 평가와 운영 결과가 필요하다. 같은 버전에서 같은 오답을 반복해도 replay 상태는 `MATCH`일 수 있다.

## 테스트는 실행을 건너뛰는 경우까지 확인한다
`tests/test_session_replay.py`는 저장 동의 허용·거부, 표현된 source의 동의 거부, 같은 입력·버전 두 번 재생, code commit 변경, unresolved commit, 출력 mismatch, runner exception, token 보호와 잘못된 execution ID를 검사한다. version mismatch 테스트는 가짜 runner가 호출되면 즉시 실패하도록 해 추천 실행을 실제로 건너뛰는지 확인한다. append-only trigger도 SQL update를 직접 시도해 검증한다.

이번 loop에는 canonical evidence의 schema version이 코드의 `SCHEMA_VERSION`과 같아야 한다는 회귀 테스트를 추가했다. 과거 evidence는 schema 9에서 생성된 뒤 migration이 14까지 올라갔는데도 남아 있었다. 생성기는 현재 version을 제대로 읽고 있었으므로 알고리즘 결함이 아니라 증거 현재성 검사 누락이었다.

## canonical smoke는 네 route 사례를 재현한다
`scripts/run_session_replay_service_ui_smoke.py`는 임시 SQLite와 실제 FastAPI app을 사용한다. token 없는 목록 요청, 추천 생성, 인증된 목록, 동일 버전 replay, code commit을 바꾼 replay를 실행한다. route 사례는 4개로 집계되고 execution 1개, replay snapshot 1개, replay run 2개가 남는다.

동일 조건 replay는 `MATCH`이고 expected·actual output hash가 같다. commit 변경 replay는 `VERSION_MISMATCH`, mismatch field `code_commit`, 추천 실행 생략으로 기록된다. 목록과 replay 응답 어디에도 raw health payload key가 노출되지 않는다. 현재 schema version은 14이며 두 번 생성한 evidence는 byte-identical하다. 파일 `data/original_plan/evidence/op029_op030_session_replay_service_ui_smoke_v1.json`의 SHA-256은 `65d55171560922f63fa4b591bf358498f3f4e969771a08edfb7ca3bb2812905f`다.

## 구현 완료와 운영 replay는 다른 단계다
R&D 저장기, identity, replay ledger, 보호 API와 실제 route smoke가 있으므로 claimed stage `IMPLEMENTED`는 직접 증명된다. 하지만 Group C의 required stage는 `OPERATED`다. 배포 환경에서 실제 세션이 쌓이고, 동일 배포 identity로 replay가 주기적으로 실행되며, mismatch가 관측·처리됐다는 운영 receipt는 없다. 따라서 OP-029의 현재 판정은 `IMPLEMENTED / PARTIAL`이다.

상위 단계로 가려면 production 또는 승인된 운영 환경에서 code·dataset identity가 해석 가능한 상태로 기록돼야 한다. 저장 동의를 받은 실제 세션의 replay 성공률, version mismatch 수, output mismatch 수, replay 불가 세션 수와 대응 기록을 일정 기간 남겨야 한다. 이번 loop는 production, 원천·frozen·학습 데이터, 모델과 simulation을 바꾸지 않았다. 핵심 구현 commit은 `8727853`, 이번 증거 현재성 보완은 `452ae1d`다.
## 데이터가 남는 방식
데이터를 저장하는 것만으로는 연구 근거가 남지 않는다. 이 그룹은 원문과 파싱 구간, 입력 버전, 동의, 실행 ID, 규칙과 결과를 이어 붙여서 누가 어떤 자료를 사용했는지 다시 따라갈 수 있게 만든다.

`OP-029`는 “세션을 같은 입력과 버전으로 재생하는 replay API를 만든다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/interim/store.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/data_lake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/execution_identity.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/session_replay.py` 외 1개
- 테스트·실행: `wellnessbox-rnd/tests/test_session_replay.py`, `wellnessbox-rnd/tests/test_interim_store.py`, `wellnessbox-rnd/scripts/run_session_replay_service_ui_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op029_op030_session_replay_service_ui_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-029.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-029.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
