# OP-119 외부 항목별 책임자, 입력, 교체 계약, 차단 사유를 기록한다

## 이 요구사항은 외부 검증을 대신하지 않고 필요한 자료를 숨기지 않게 한다

OP-119의 목적은 외부 기관이 해야 할 검증을 코드로 완료 처리하는 것이 아니다. 외부 단계가 필요한 요구사항마다 내부 책임 역할, 독립 공급자 역할, 받아야 할 파일, 파일을 받아들이는 계약, 기존 신뢰 기준을 교체하는 조건과 현재 차단 사유를 한 원장에 기록해야 한다. 자료가 없는데 `READY`로 바꾸거나 내부 합성 자료를 외부 증거로 쓰는 일을 막는 관리 기능이다.

요구사항 장부가 등록한 구현은 `wellnessbox-rnd/src/wellnessbox_rnd/governance/external_dependency_registry.py`와 `wellnessbox-rnd/data/original_plan/op119_external_dependency_registry_v1.json`이다. 시험 경로는 `wellnessbox-rnd/tests/test_external_dependency_registry.py`, `wellnessbox-rnd/scripts/run_external_dependency_registry_smoke.py`, `wellnessbox-rnd/data/original_plan/op119_external_dependency_registry_cases_v1.json`, `wellnessbox-rnd/data/original_plan/evidence/op119_external_dependency_registry_smoke_v1.json`이다. 여섯 파일은 모두 존재하며 OP-119의 `IMPLEMENTED` 단계에는 내용이 맞는다.

## 현재 원장은 외부 단계 요구사항 OP-039 한 건을 관리한다

`data/original_plan/op119_external_dependency_registry_v1.json`에는 OP-039만 들어 있다. 내부 책임 역할은 `wellnessbox_external_evidence_governance`이며, 독립 임상 안전성 검토 조직과 별도 증명 검증 조직이 외부 공급 역할로 명시돼 있다. 원장이 임의로 다른 항목을 빼거나 추가하지 못하게 감사 함수는 요구사항 장부에서 `required_stage=EXTERNAL`인 집합과 원장 집합이 정확히 같은지 비교한다. 현재 두 집합은 모두 `OP-039` 한 건이다.

필수 입력은 네 종류다. 독립 라벨 고위험 데이터셋, 외부 증명서, 별도 조직의 진위 확인 영수증, 라벨링 전에 고정한 위험군 포함 기준이다. 각 항목에는 공급 역할, 스키마 버전과 수락 계약이 있다. 현재 네 항목 모두 `MISSING`이며 `artifact_path`와 `artifact_sha256`은 비어 있다. 원장은 이 상태를 `BLOCKED`로 기록한다.

교체 계약은 `wellnessbox-rnd/data/original_plan/contracts/op039_external_coverage_trust_roots_v1.json`과 `wellnessbox-rnd/data/original_plan/contracts/op039_external_attestation_trust_roots_v1.json` 두 파일이다. 두 파일은 실제로 존재한다. 첫 파일의 `approved_coverage_protocols`와 `approval_record_references`, 둘째 파일의 `approved_attestations`와 `approval_record_references`가 모두 빈 목록이다. 원장의 차단 사유 네 건은 이 네 목록을 JSON 위치까지 지정해 가리킨다.

## 입력 계약은 원장 문구가 임의로 바뀌는 것을 막는다

원장은 `data/original_plan/contracts/op039_external_input_contract_v1.json`을 입력 계약으로 지정한다. `audit_external_dependency_registry_v1`은 원장의 각 필수 입력에서 상태·파일 경로·해시를 제외한 정의를 꺼내 입력 계약과 순서와 값까지 비교한다. `input_id`, 공급 역할, 스키마 버전 또는 수락 계약이 달라지면 `required inputs do not match input contract`로 실패한다.

네 입력의 수락 계약은 모두 `docs/original_plan/OP039_EXTERNAL_HIGH_RISK_EVAL_CONTRACT.md`다. 이 문서는 내부 고정 평가 세트와 합성 자료를 외부 증거로 쓸 수 없다고 명시한다. 외부 데이터 라벨링 전에 위험군별 최소 사례 수를 고정하고 독립 승인 기록을 남겨야 한다. 데이터셋, 외부 증명서, 진위 영수증과 고정 포함 기준을 별도 파일로 받아야 하며, hard false negative 0뿐 아니라 기대 차단 규칙이 실제 규칙과 맞는지도 요구한다.

## 경로와 제공 파일은 저장소 안에서 내용까지 확인한다

`_resolve_repository_file`은 `wellnessbox-rnd/` 접두사를 제거한 뒤 저장소 루트 안의 절대 위치로 바꾼다. 처음부터 절대 경로인 값과 `..`로 저장소 밖에 나가는 값은 거부한다. 교체 계약, 입력 계약과 수락 계약이 실제 파일인지도 확인한다. 경로 문자열만 있어도 통과하는 구조가 아니다.

`_validate_provisioned_input`은 `MISSING` 항목에 파일 경로나 해시가 붙으면 실패시킨다. `PROVIDED`로 바꾸려면 둘 다 있어야 한다. 실제 파일의 SHA-256이 등록값과 같은지 계산하고, JSON 또는 JSONL의 `schema_version`도 계약과 비교한다. 외부 고위험 사례는 빈 줄을 제외한 모든 JSONL 행이 `external_high_risk_safety_case_v2`인지 확인한다. 해시만 맞고 스키마가 다른 파일도 받아들이지 않는다.

차단 사유는 설명 문장만 저장하지 않는다. `_resolve_json_pointer`가 지정 JSON 위치를 실제로 따라가며 기대값 `EMPTY_LIST`와 같은지 본다. 현재 네 위치가 모두 빈 목록이어서 검증된 관찰 수는 4다. 값이 채워지면 기존 차단 사유는 더 이상 현재 상태와 맞지 않으므로 감사가 실패하고 원장을 갱신해야 한다.

## READY와 BLOCKED 전이는 부분 진행을 허용하되 근거 없는 승격을 막는다

`_validate_readiness`는 누락 입력이나 차단 사유가 하나라도 남은 상태에서 `READY`를 허용하지 않는다. 반대로 입력과 차단 사유가 모두 해소됐는데 계속 `BLOCKED`로 두는 것도 거부한다. 입력 네 건이 먼저 제공됐지만 독립 승인 목록이 아직 비어 있는 중간 상태는 `BLOCKED`로 허용한다. 외부 수집과 승인 절차가 한 번에 끝난다고 가정하지 않은 것이다.

이 규칙은 처음부터 완성된 것은 아니었다. `0d02027`의 첫 구현은 책임자, 네 입력, 두 교체 계약과 네 차단 사유를 만들었지만, 제공 파일의 실제 경로·해시·스키마와 저장소 이탈을 확인하지 않았다. `8f2ddfa`는 입력 계약 비교, 파일 무결성, 스키마 판정과 경로 이탈 차단을 추가했다. 그 수정은 `BLOCKED`가 되려면 누락 입력과 차단 사유가 모두 있어야 한다고 너무 엄격하게 묶었다. 입력만 먼저 도착하는 정상 중간 상태를 허용하지 못했다.

`43f6a06`은 이 오류를 고쳐 누락 입력 또는 차단 사유 중 하나만 남아도 `BLOCKED`를 허용했다. `test_readiness_allows_all_provided_with_approval_blockers`와 `test_readiness_allows_ready_after_all_conditions_resolve`가 각각 중간 상태와 최종 전이를 고정한다. Git 이력은 외부 완료를 느슨하게 만든 것이 아니라, 자료 제공과 독립 승인이 순차로 진행되는 실제 절차를 표현하도록 상태 규칙을 바로잡은 과정이다.

## 집중 시험은 정상 차단과 변조 실패를 각각 이름으로 고정한다

`test_current_external_dependency_registry_is_complete_and_blocked`는 감사 상태가 PASS이고 외부 집합과 원장 집합이 OP-039로 같으며, OP-039가 차단됐는지 확인한다. 필수 입력 4건, 교체 계약 2건과 차단 사유 4건도 정확히 센다. 여기서 PASS는 외부 평가 성공이 아니라 원장이 현재 누락을 정확히 표현한다는 뜻이다.

`test_registry_rejects_missing_external_requirement`는 OP-039를 원장에서 빼면 실패하는지 본다. `test_registry_rejects_empty_accountable_role`은 책임 역할을 빈 값으로 만들 수 없게 한다. `test_registry_rejects_replacement_contract_drift`와 `test_registry_rejects_required_input_contract_drift`는 요구사항 장부와 입력 계약에서 원장이 벗어나는 변경을 막는다.

`test_registry_rejects_ready_when_inputs_and_trust_roots_are_missing`은 현재 자료를 그대로 둔 채 READY만 바꾸는 승격을 거부한다. `test_registry_rejects_unverified_blocker_observation`은 존재하지 않는 JSON 위치를 차단 사유로 꾸밀 수 없게 한다. `test_registry_rejects_provided_input_without_artifact`는 파일 없이 PROVIDED만 쓰는 경우를, `test_registry_rejects_repository_path_traversal`은 저장소 밖 파일을 참조하는 경우를 실패시킨다. 제공 파일의 실제 해시 불일치와 스키마 불일치는 구현 함수에 있지만 전용 시험 이름은 현재 파일에서 찾지 못했다.

## 고정 사례 결과는 관리 기능을 증명하고 외부 완료를 명시적으로 부정한다

고정 사례 8건은 외부 집합, 책임자, 공급자 역할, 필수 입력, 교체 계약, 차단 사유, 준비 상태와 승격 조건을 각각 비교한다. 실행 결과는 원장 1건, 입력 4건 모두 누락, 교체 계약 2건, 차단 사유 4건, 검증된 빈 목록 4곳을 기록한다. `blocked_requirement_ids=["OP-039"]`, `ready_count=0`이다. 사례 파일과 원장 파일의 SHA-256은 현재 실제 파일과 결과 JSON의 기록이 일치한다.

결과의 단계 경계도 정확하다. `registry_contract_implemented=true`인 동시에 `external_inputs_provided=false`, `external_approvals_registered=false`, `op039_external_validation_complete=false`다. 그러므로 이 결과를 OP-039의 외부 검증 완료로 인용하면 내용과 반대가 된다.

다만 결과 파일의 소스 결속은 현재 요구사항 장부보다 오래됐다. 결과에는 manifest Git 개체 ID `3884fc7badcaec4f60f24da87d77be7654fca61d`와 소스 커밋 `ce3afe990ecae41143f17bac9c6f8fa53260021c`이 기록돼 있다. 현재 manifest 개체 ID는 `ea47e7293ed4fe0a1060ec4dde21639238814f54`이고, 등록 소스 중 가장 늦은 변경은 `b014abda7a9fb4478ab4c8dda2c7b1bbd01f22d9`다. 현재 파일을 직접 대조하면 외부 요구사항 집합과 교체 계약은 여전히 같지만, 등록 결과는 현재 manifest로 다시 생성한 정본은 아니다.

## OP-039의 현재 자료는 원장의 차단 판단과 일치한다

현재 신뢰 기준 두 파일의 승인 목록 네 곳은 모두 비어 있다. 필수 외부 입력도 네 건 모두 누락이다. 별도로 존재하는 `data/original_plan/final_session/external_validation/op039_external_validation.json`은 검토자를 `웰니스박스 TIPS 과제 참여연구원`, `project_co_researcher`, `independent_of_implementation_team=false`로 기록한다. 약사 자격 번호는 수집하지 않았고 확인 방법은 프로젝트 소유자 확인이라고 적혀 있다. 이 파일은 계약이 요구하는 독립 외부 조직의 네 입력을 대신할 수 없다.

그런데 현재 요구사항 장부는 OP-039의 `claimed_stage`를 `EXTERNAL`로 표시한다. 같은 항목의 `external_dependencies`에는 독립 검증 영수증과 저장소에 고정된 승인이 없다고 쓰여 있다. OP-119 원장의 `BLOCKED` 및 신뢰 기준의 빈 목록과 단계 표시는 서로 모순된다. 이 보고서는 요구사항 장부를 수정할 권한이 없으므로 모순만 기록한다.

## 현재 단계와 확인하지 못한 외부 자료

OP-119 자체는 요구 단계와 현재 증거가 모두 `IMPLEMENTED`다. 책임 역할, 공급 역할, 네 입력, 두 교체 계약, 네 차단 사유와 승격 조건이 코드와 자료로 고정돼 있다. 경로 이탈, 계약 변경, 파일 없는 PROVIDED, 근거 없는 READY를 거부하는 시험도 있다. 외부 입력을 얻거나 외부 평가를 완료하는 것은 OP-119의 완료 조건이 아니다.

확인되지 않은 것은 독립 조직이 실제 고위험 데이터, 외부 증명서, 진위 확인 영수증과 사전 고정 포함 기준을 제공했는지, 그 파일 해시가 신뢰 기준에 별도 승인 기록과 함께 등록됐는지다. 조사한 원장·입력 계약·신뢰 기준에는 그런 자료가 없다. OP-039의 `EXTERNAL` 주장을 유지하려면 네 입력과 독립 승인 기록을 계약대로 등록하고 현재 manifest를 포함한 소스에서 감사를 다시 실행해야 한다. 그렇지 않다면 최종 감사는 OP-119의 `BLOCKED` 결과를 우선해 OP-039 단계 표시를 재검토해야 한다.
