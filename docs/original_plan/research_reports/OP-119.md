# OP-119 외부 항목별 책임자, 입력, 교체 계약, 차단 사유를 기록한다

구현의 기준 파일은 `wellnessbox-rnd/src/wellnessbox_rnd/governance/external_dependency_registry.py`이고, 실행 결과는 `wellnessbox-rnd/data/original_plan/evidence/op119_external_dependency_registry_smoke_v1.json`에 있다. 원장, 입력 계약, 두 신뢰 기준 파일과 집중 시험까지 직접 대조했다.

## 외부 증거를 코드가 대신 만들지 못하게 한 이유

이 요구사항은 외부 검증을 끝내는 기능이 아니라, 외부에서 받아야 할 자료를 빠짐없이 드러내는 관리 기능이다. 구현팀이 만든 합성 사례나 자기 서명 문서를 외부 검증으로 바꾸면 hard false negative 0이라는 안전 지표의 독립성이 사라진다. 그래서 원장은 누가 책임지는지, 어떤 조직이 무엇을 공급해야 하는지, 기존 파일을 어떤 계약에 따라 교체하는지, 현재 무엇 때문에 멈췄는지를 한 항목에 묶는다.

현재 원장 `data/original_plan/op119_external_dependency_registry_v1.json`에는 외부 단계 요구사항 OP-039 한 건이 있다. 내부 책임 역할은 `wellnessbox_external_evidence_governance`이고, 외부 공급 역할은 구현팀과 독립된 임상 안전성 검토 조직과 별도 증명 검증 조직으로 나뉜다. 필요한 입력은 외부 고위험 사례, 외부 증명서, 진위 확인 영수증, 라벨링 전에 고정한 위험군 포함 기준의 네 종류다. 원장에서는 네 입력이 모두 `MISSING`이고 파일 경로와 SHA-256도 비어 있다.

## 잘못된 승격을 막는 검사 순서

감사 함수는 요구사항 장부에서 `required_stage=EXTERNAL`인 ID 집합과 원장 ID 집합이 정확히 같은지 먼저 비교한다. 그다음 OP-039의 교체 계약 두 경로가 요구사항 장부와 일치하고 실제 저장소 안에 존재하는지 본다. 절대 경로와 `..`를 통한 저장소 이탈은 거부한다. 입력 정의는 `op039_external_input_contract_v1.json`과 필드 단위로 같아야 하며, 각 승인 계약 문서도 실제 파일이어야 한다.

입력이 `MISSING`이면 자료 경로와 해시를 적을 수 없다. `PROVIDED`로 바꾸려면 파일 경로, 64자리 SHA-256과 맞는 스키마를 모두 제공해야 한다. 고위험 사례는 JSONL 각 행의 스키마를 확인하고, 나머지 자료는 JSON의 `schema_version`을 읽는다. 차단 사유는 설명만 저장하지 않는다. 두 신뢰 기준 JSON의 정확한 위치를 가리키고 그 값이 빈 목록인지 실제로 읽는다. 입력 누락이나 차단 사유가 남은 상태에서 `READY`로 바꾸면 함수가 실패한다.

## 부정 시험과 관찰 결과

`tests/test_external_dependency_registry.py`는 정상 원장이 PASS이면서 OP-039를 차단하는지 확인한다. 이어 외부 요구사항 삭제, 빈 책임 역할, 교체 계약 누락, 입력 없이 READY 승격, 존재하지 않는 JSON 위치, 입력 계약 변경, 자료 없이 PROVIDED 표기와 저장소 경로 이탈을 각각 실패시킨다. 모든 자료가 제공됐더라도 승인 차단 사유가 남아 있으면 `BLOCKED`를 허용하고, 입력과 차단 사유가 모두 해소됐을 때만 `READY`를 허용하는 전이도 따로 시험한다.

고정 사례 8건을 실행한 핵심 경로 시험 결과는 원장 항목 1건, 필수 입력 4건, 교체 계약 2건, 차단 사유 4건과 검증된 빈 목록 4곳을 기록한다. `blocked_requirement_ids=["OP-039"]`, `ready_count=0`이며 감사 상태는 PASS다. 여기서 PASS는 외부 검증 성공이 아니라 “현재 부족한 자료를 규칙대로 차단했다”는 뜻이다. 결과 파일도 `external_inputs_provided=false`, `external_approvals_registered=false`, `op039_external_validation_complete=false`를 명시한다.

## 현재 자료 사이의 불일치와 완료 단계

OP-119 원장과 두 신뢰 기준 파일은 여전히 같은 결론을 낸다. `approved_coverage_protocols`, `approved_attestations`와 두 `approval_record_references` 목록은 모두 비어 있고 필수 입력 네 건도 누락 상태다. 따라서 외부 의존성 관리 계약 자체는 요구 단계 `IMPLEMENTED`를 충족하지만, OP-039가 외부 검증을 통과했다는 뜻은 아니다.

현재 manifest는 OP-039의 `claimed_stage`를 `EXTERNAL`로 올려 두었다. 동시에 같은 항목의 `external_dependencies`에는 독립 검증 영수증과 저장소에 고정된 승인이 여전히 없다고 적혀 있다. 실제 최종 세션 검토 파일도 검토자를 과제 공동연구자로 기록하고 `independent_of_implementation_team=false`라고 밝힌다. 이 상태는 OP-119 원장이 표현하는 `BLOCKED`와 manifest 승격이 서로 맞지 않음을 보여준다.

OP-119의 구현 결과는 유지할 가치가 있다. 오히려 이 원장이 현재 모순을 드러냈다. 확인되지 않은 것은 독립 조직이 네 입력을 제공하고 두 신뢰 기준에 별도 승인 기록을 남겼는지 여부이며, 조사한 원장·계약·신뢰 기준에서는 찾지 못했다. OP-039를 외부 완료로 유지하려면 승인된 자료와 해시를 원장에 등록해 다시 검사해야 한다. 그 자료가 없다면 OP-039의 단계와 최종 감사 해석을 원장의 `BLOCKED` 상태에 맞춰 재검토해야 한다.
