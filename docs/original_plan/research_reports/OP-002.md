# OP-002 59쪽 원문에서 연구개발 기능과 사업 설명을 분리했다

## 먼저 답해야 했던 질문

사업계획서의 모든 문장을 제품 요구사항으로 옮기면 시장 규모, 회사 소개, 투자 계획 같은 설명까지 구현 항목으로 잘못 다루게 된다. 반대로 앞부분의 기술 설명만 읽으면 뒤쪽의 안전·보안 준수 조건을 놓칠 수 있다. OP-002는 59쪽 원문을 시각적으로 확인한 뒤 각 문구가 연구개발 기능, 사업 설명, 회사·준비 현황, 안전·보안 준수 조건 중 어디에 속하는지 구분하는 요구사항이다. 이 분류가 있어야 후속 요구사항이 원문의 뜻을 보존하면서도 구현 가능한 단위가 된다.

## 59쪽 문서의 큰 구성을 어떻게 읽었나

`docs/context/master_context.md`는 원문의 큰 구성을 시장과 문제, 해결책과 세부 기술, 사업화, 회사 소개, 연구개발 안전·보안의 다섯 부분으로 정리한다. 일상적인 기술 구현 컨텍스트는 연구개발 설명이 밀집한 1~27쪽을 우선 사용한다. 28쪽 이후의 사업화·회사 소개·운영 설명은 기술 요구사항과 같은 무게로 가져오지 않는다. 다만 28쪽 이후를 전부 버리는 규칙은 아니다. 뒤쪽에 있는 연구개발 안전과 보안 준수 문구는 별도 제약 조건으로 분류해야 한다.

이 원칙은 원문 충실 계층과 재설계 계층도 구분한다. 원문 충실 계층은 문서가 실제로 약속한 기능과 지표를 보존한다. 재설계 계층은 현재 저장소 구조에서 구현하기 좋은 계약과 모듈로 바꾼다. 두 계층을 섞지 않으면 새 설계 아이디어를 원문 요구사항처럼 꾸미거나, 사업 홍보 문구를 이미 구현된 기능처럼 주장하는 오류를 줄일 수 있다.

## 이번 시각 검토에서 59쪽 전체를 어떻게 확인했나

PDF 렌더링 도구로 원본 59쪽을 모두 이미지로 변환하고 1~10쪽, 11~20쪽, 21~30쪽, 31~40쪽, 41~50쪽, 51~59쪽의 여섯 접촉 시트로 나눠 페이지 번호와 화면 구성을 빠짐없이 점검했다. 별도로 1쪽, 15쪽, 28쪽, 59쪽을 큰 이미지로 열어 경계 페이지의 글자와 도표를 확인했다. 1쪽은 TIPS 연구개발계획서 표지와 과제명을 보여 주므로 문서 정체성을 확인하는 페이지다. 15쪽은 `Solution & Technology` 제목 아래 서비스 아키텍처와 연구개발 로드맵을 배치해 기술 기능을 설명한다. 이 페이지의 구성 요소는 후속 시스템 요구사항을 추출할 근거가 된다.

28쪽은 준비 현황과 서비스 프로토타입을 설명한다. 이 내용은 구현 참고 자료가 될 수 있지만 제품 런타임 계약 자체와 같지는 않다. 59쪽은 연구개발 안전과 보안 실행 계획을 다룬다. 따라서 뒤쪽 페이지라는 이유만으로 사업 문구로 제외하면 안 되며, 안전·보안 준수 조건으로 따로 보존해야 한다. 대표 페이지 검토는 앞부분 기술 기능, 중간 준비·사업 설명, 마지막 준수 조건의 경계를 실제 화면에서 확인하기 위해 선택했다.

전체 화면 검토 결과 3~10쪽은 시장 현황과 문제 정의, 11~27쪽은 해결책·기술 구성·개발 목표와 준비 로드맵, 28~36쪽은 프로토타입과 준비 현황, 37~55쪽은 시장 규모·사업화·수익·해외 진출·자금 계획, 56~58쪽은 창업팀 소개, 59쪽은 연구개발 안전·보안 계획으로 이어진다. 각 범위의 제목과 페이지 배열이 목차와 맞고 빈 페이지, 중복 페이지, 순서가 뒤바뀐 페이지는 보이지 않았다. 이 범위별 기록이 59쪽 전체를 기술 기능으로 오해하지 않게 하는 시각 분류 증거다.

## 구현 증거와 테스트 증거

manifest가 지정한 첫 구현 증거는 `wellnessbox-rnd/docs/context/master_context.md`다. 저장소 내부 경로 `docs/context/master_context.md`는 원문 1~27쪽에서 연구개발 관련 내용을 재구성하고, 28쪽 이후의 사업·회사·운영 문구를 일상적인 기술 컨텍스트에서 낮은 우선순위로 분리한다. 두 번째 구현 증거는 `wellnessbox-rnd/docs/plans/2026-07-15-original-plan-completion-program.md`다. 이 문서는 59쪽 시각 확인과 연구개발 기능·사업 문구 구분을 OP-002의 완료 조건으로 기록한다.

테스트 증거는 `wellnessbox-rnd/tests/test_original_plan_manifest.py`다. 저장소 내부의 `tests/test_original_plan_manifest.py`는 원본 SHA-256, 120개 요구사항의 연속성, 각 요구사항의 출처와 소유자, 현재 주장 단계를 검사한다. OP-002가 고정된 원본과 연결되고 `IMPLEMENTED`로만 주장되는지 회귀 검사한다. 시각 판단 자체를 픽셀 단위로 자동 판정하는 테스트는 아니지만, 시각 검토 결과가 연결된 manifest 계약이 사라지거나 다른 원본으로 바뀌는 문제는 탐지한다.

## Git 이력이 보여 주는 근거의 연결

`docs/context/master_context.md`와 `docs/context/original_plan.pdf`는 2026-03-08의 `e5ef1ecf8575d1a09cf4fb3a8d0063e9a8b24d4d` 커밋에서 함께 추적됐다. 2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad` 커밋은 원본 SHA-256, OP-001부터 OP-120까지의 manifest, OP-002 완료 주장과 회귀 테스트를 하나의 거버넌스 계약으로 묶었다. 이후 `17da3a15e7bd755a1074682ca40f7b532b1008e3`의 감사 보강과 후속 자동화가 이 계약을 재사용했다. 이 이력은 페이지 해석 문서와 요구사항 목록이 서로 독립적인 임시 메모가 아니라 같은 원본을 기준으로 발전했음을 보여 준다.

## 분류 규칙이 막는 오류와 남은 한계

시장 기회나 사업화 계획은 연구 방향을 설명할 수 있지만 곧바로 API, 데이터 모델, 추천 정책의 완료 증거가 되지 않는다. 프로토타입 화면도 실제 서비스 통합이나 운영 실적을 자동으로 증명하지 않는다. 반면 안전·보안 실행 계획은 화면 기능이 아니더라도 연구개발이 지켜야 할 제약 조건이다. 문구의 위치가 아니라 문구가 요구하는 행동과 검증 대상을 보고 분류해야 한다.

이번 검토는 59쪽 전체를 접촉 시트로 확인하고 경계 페이지를 큰 이미지로 재검토했으며, 기존 `master_context.md`가 문서의 장별 역할을 구분한 결과와 대조했다. 렌더링 파일은 저장소의 보호된 `etc/` 아래 검토용 중간 산출물로 두었고 canonical 구현 증거로 주장하지 않는다. 모든 페이지의 모든 작은 글자를 전사하거나 두 명의 독립 검토자가 페이지별 라벨을 합의한 작업은 아니다. 따라서 보고서가 주장하는 것은 59쪽의 시각적 완전성과 문서 구조, 요구사항 추출 경계를 확인했다는 사실이며, 외부 검증이나 운영 단계의 완전한 문서 감사를 주장하지 않는다.

## 완료 단계와 결론

OP-002의 기본 요구 단계와 현재 주장 단계는 `IMPLEMENTED`다. 59쪽 원문을 기준으로 연구개발 기능과 사업 설명을 분리하는 규칙이 컨텍스트 문서, 완료 프로그램, manifest 테스트에 남아 있으므로 구현 단계는 충족한다. 이번 보고서 작업은 코드, 서비스 데이터, 모델 훈련, 시뮬레이션을 변경하지 않았다. 서비스 통합이나 실제 운영 관측도 새로 주장하지 않는다.

결론적으로 1~27쪽은 일상적인 연구개발 기능 추출의 주된 출처로 사용하고, 28쪽 이후의 사업화·회사·준비 현황은 제품 요구사항과 분리한다. 다만 59쪽처럼 안전·보안 실행을 요구하는 내용은 준수 조건으로 보존한다. 이 경계는 원문을 과장하지 않으면서 후속 구현 항목을 빠뜨리지 않게 만드는 OP-002의 핵심 결과다.
