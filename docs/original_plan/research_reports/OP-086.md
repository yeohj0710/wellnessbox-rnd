# OP-086 응급 위험 질문은 추천보다 안전 안내를 우선한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/chat/retrieval.py`에서 구현과 검증 대상을 확인할 수 있다.

## 가장 먼저 지켜야 할 순서

사용자가 “가슴이 아프다”, “숨을 쉴 수 없다”, “목이 붓는다”, “출혈이 멈추지 않는다”고 말하면서 어떤 보충제를 먹을지 묻는다면, 시스템이 먼저 할 일은 제품이나 원료를 찾는 것이 아니다. 즉시 응급 도움을 받으라는 안내를 먼저 보여주고, 보충제 복용을 멈추게 하며, 채팅 답변이나 추천을 기다리지 말라고 말해야 한다. OP-086은 바로 이 실행 순서를 코드와 증거로 고정하라는 요구사항이다.

이번 구현은 응급 질문을 일반 상담의 한 템플릿으로 처리하지 않았다. 질문 분석에서 명시적인 응급 위험이 확인되면 bounded Retrieval-Augmented Generation, 즉 허용된 근거만 검색해 답변하는 절차에 들어가기 전에 종료한다. 외부 언어 모델 설정도 읽지 않고, 검색 결과도 만들지 않으며, 추천 문장도 생성하지 않는다. 저장소가 승인한 세 문장을 정해진 순서로 반환한다. 검증기는 원 질문을 다시 분석해 이 우선순위가 실제로 지켜졌는지 확인한다.

OP-086의 required stage는 `IMPLEMENTED`다. 로컬 코드와 결정론 테스트로 이 단계를 증명했다. 실제 WellnessBox 채팅 화면에 배포된 기능, 실제 응급 상황에서의 사용자 행동, 의료기관 연결 성공률, 외부 의료진의 검토 결과는 이번 loop에 없다. 그런 운영 및 외부 검증을 구현 완료와 섞어 말하지 않는다.

## 기존 질문 분석을 그대로 사용한 이유

응급 신호를 찾기 위해 새 키워드 분류기를 만들지 않았다. OP-082에서 이미 질문 속 건강 목표, 원료, 의약품과 위험 신호를 실제 문자열 위치로 추적하는 `extract_question_entities`가 구현되어 있었다. 이 함수에는 출혈, 가슴 통증, 호흡 곤란, 아나필락시스에 해당하는 표현과 별칭이 들어 있다. 각 일치 결과에는 원문에서 시작한 위치와 끝난 위치, 실제 일치 문자열, 표준 위험 키, 부정 여부가 기록된다.

이 기존 경로를 재사용해야 같은 질문을 두 분석기가 다르게 판단하는 문제를 피할 수 있다. 일반 상담 검색은 위험이 없다고 보는데 응급 분기만 위험이 있다고 보거나, 그 반대가 되면 최종 동작을 설명하기 어렵다. 이번 구현에서는 답변 생성기와 검증기가 모두 같은 entity extraction을 호출한다. 생성기가 응급으로 판단한 결과를 검증기가 그대로 믿는 것도 아니다. 검증기는 원 질문과 runtime knowledge database를 사용해 위험 키와 부정 여부를 다시 계산한다.

응급 정책에는 현재 extractor가 만드는 네 가지 표준 키가 명시되어 있다. `active_bleeding`은 진행 중인 출혈, `anaphylaxis`는 아나필락시스 또는 목이 붓는 증상, `chest_pain`은 가슴 통증이나 압박감, `difficulty_breathing`은 호흡 곤란을 뜻한다. 정책 목록은 정렬되고 중복이 없어야 하며, 호출자가 임의로 바꾼 정책은 저장소 원본과 같지 않으면 거부된다.

## 단어가 보인다고 무조건 응급으로 처리하지 않는다

위험 단어만 찾는 방식은 “가슴 통증은 없습니다” 같은 질문도 응급으로 올릴 수 있다. 기존 entity extraction은 위험 표현 앞뒤의 명시적인 부정을 함께 본다. 영어의 `no`, `without`, `deny`와 저장소에 등록된 한국어 부정 표현이 가까운 범위에 있으면 해당 match에 `negated=true`를 기록한다. 응급 여부는 위험 키가 있다는 사실만으로 정하지 않고, 부정되지 않은 응급 match가 하나라도 있는지로 계산한다.

부정 표현이 뒤 문장까지 잘못 퍼지지 않게 하는 것도 중요하다. “출혈은 없지만 가슴 통증이 있다”는 문장에서 출혈만 부정되고 가슴 통증은 살아 있어야 한다. “출혈은 없고 가슴 통증은 있다”처럼 접속된 두 명제도 같은 원칙을 적용한다. 기존 OP-082 테스트가 이 절 경계를 검증했고, 이번 smoke는 contrast-clause 사례를 다시 통과시킨다. 반대로 “가슴 통증은 없다”는 질문은 응급 분기로 보내지 않는다.

이 규칙이 모든 자연어 부정을 완벽하게 이해한다고 주장하지 않는다. 복잡한 시제, 인용문, 가족의 증상을 대신 묻는 문장, 오타, 새로운 은어는 추가 자료가 필요하다. 현재 증거는 등록된 표현과 명시적인 부정·대조 사례에 대한 것이다. 응급 탐지 범위를 넓힐 때는 단어 수만 늘리는 것이 아니라 오탐과 미탐 사례를 함께 추가해야 한다.

## 응급 안내가 검색보다 먼저 실행되는 과정

일반 답변 생성 함수는 원래 허용 지식 범위로 passage를 검색한 뒤, 지원되는 근거를 선택하고 템플릿을 렌더링했다. 이번에는 함수 시작 부분에서 runtime knowledge database와 repository-approved verifier policy를 불러오고 질문 entity를 먼저 추출한다. 부정되지 않은 응급 키가 있으면 검색 함수를 호출하기 전에 `ChatTemplateAnswer`를 즉시 반환한다.

응급 답변의 상태는 일반 지원 답변과 구분되는 `safety_escalation`이다. `answer_template_key`는 `urgent_safety_guidance`이며, `rationale`에는 응급 위험이 검색과 추천보다 앞선다는 사실을 기록한다. `detected_urgent_risk_keys`에는 실제로 확인한 표준 키를 정렬된 고유 목록으로 보존한다. `safety_policy_id`에는 사용한 정책 버전을 넣는다. 근거 passage를 검색하지 않았으므로 citation과 used chunk 목록은 비어 있어야 한다. 이 구조를 어기면 답변 모델 자체가 유효하지 않다.

사용자가 읽는 문장은 세 단계로 고정했다. 첫 문장은 현지 응급 서비스에 즉시 전화하거나 가장 가까운 응급실로 가라고 말한다. 두 번째 문장은 응급 의료진이 평가할 때까지 보충제 복용을 중단하라고 말한다. 세 번째 문장은 채팅 답변이나 보충제 추천을 기다리지 말라고 말한다. 세 문장의 순서를 정책 데이터에 보존하고, 최종 문자열은 이 순서대로 합친 결과와 정확히 같아야 한다.

첫 문장을 즉시 행동 안내로 둔 이유는 설명이나 면책 문구가 긴급 행동을 밀어내지 않게 하기 위해서다. “저는 의료인이 아닙니다” 같은 소개를 먼저 하면 사용자가 가장 필요한 행동을 늦게 읽는다. 보충제 추천을 하지 않는 것만으로도 충분하지 않다. 사용자가 무엇을 해야 하는지, 무엇을 멈춰야 하는지, 무엇을 기다리면 안 되는지를 앞에서 분명히 말해야 한다.

## 외부 언어 모델 호출도 먼저 막았다

답변 생성 함수에서 응급 분기를 넣었더라도 adapter가 그 전에 검색이나 공급자 호출을 실행하면 OP-086을 완전히 지키지 못한다. 그래서 `generate_chat_answer_with_openai_fallback`은 먼저 deterministic fallback을 만든다. 그 답변이 `safety_escalation`이면 즉시 반환한다. 반환 객체에는 `urgent_safety_precedence`를 fallback reason으로 기록하고, `attempted_live_call=false`, `model=null`, evidence chunk 목록과 reference 목록은 빈 배열로 둔다.

집중 테스트에서는 가짜 API 키를 설정하고 공급자 호출 함수를 호출되는 즉시 실패하도록 바꾼다. 가슴 통증 질문을 전달한 뒤에도 그 함수가 한 번도 실행되지 않았는지 확인한다. canonical smoke에서도 `allow_live_api=true`로 adapter를 실행하고 실제 응답의 provider-call 시도 값과 retrieval evidence 수가 각각 거짓과 0인지 확인한다. API 키가 없어서 우연히 호출하지 않은 상황과 응급 우선순위 때문에 의도적으로 호출하지 않은 상황을 구분한 것이다.

## 검증기는 응급 답변에서 무엇을 다시 확인하는가

응급 답변을 만들었다는 메타데이터만 믿지 않는다. 검증기는 원 질문을 다시 분석해 부정되지 않은 응급 키를 구한다. 응급 키가 있으면 답변 상태가 반드시 `safety_escalation`이어야 한다. 답변 문장은 저장소 정책의 세 문장과 정확히 같아야 하고, detected key와 policy ID도 재계산 결과와 같아야 한다. citation과 used chunk는 없어야 한다. “제가 추천합니다”, “이 보충제를 드세요”, “이 보충제를 시도하세요” 같은 추천 표현도 없어야 한다.

반대 방향도 검사한다. 원 질문에 부정되지 않은 응급 키가 없는데 답변 상태만 `safety_escalation`으로 위조하면 `emergency_safety_precedence_failed`가 발생한다. 이는 모든 불명확한 질문을 응급으로 보내는 방식으로 통과율을 높이는 것을 막는다. 응급 질문에는 반드시 응급 답변을, 비응급 질문에는 기존 bounded 경로를 적용한다.

응급 문장 뒤에 “마그네슘을 추천합니다”를 덧붙인 변조는 두 이유로 실패한다. 승인된 응급 안내와 정확히 같지 않고, 응급 답변 금지 추천 표현도 포함하기 때문이다. “응급 진료를 받기 전에 기다려 보라”는 변조는 승인 문장 불일치와 금지 표현으로 실패한다. 정책 ID만 다른 객체를 넘기는 변조도 repository policy identity 검사에서 실패한다.

## canonical smoke가 증명하는 사례

결정론 smoke는 기존 reference claims에서 24개 passage를 다시 만들고 OP-083의 승인 scope를 그대로 불러온다. 정상 약물 상호작용 답변이 모든 verifier 항목을 통과하는지 먼저 본다. 이어 가슴 통증 질문이 응급 상태로 바뀌고, 정확한 첫 문장과 세 문장을 반환하며, citation을 만들지 않는지 확인한다. adapter에 live 호출을 허용한 상태에서도 provider call과 retrieval evidence가 생기지 않아야 한다.

경계 사례로는 명시적으로 가슴 통증이 없다는 질문과, 출혈은 없지만 가슴 통증은 있다는 질문을 사용한다. 첫 사례는 응급 분기로 가지 않아야 하고, 두 번째는 대조 접속사 뒤의 가슴 통증 때문에 응급 분기로 가야 한다. 이 둘을 함께 두면 위험 단어가 보일 때마다 무조건 escalation하는 구현과, 앞의 부정 표현을 문장 전체에 잘못 적용하는 구현을 모두 구분할 수 있다.

negative probes에는 응급 진료 지연 문장, 올바른 안내 뒤의 추천 문장, 정책 위조가 포함된다. OP-085와 공유하는 근거 없는 주장, 위험 누락, 진단·보장 표현 변조도 같은 smoke에서 실행한다. 응급 우선순위는 답변 검증과 별개의 섬이 아니라 같은 최종 출력 경계에 있어야 하기 때문이다.

smoke는 고정된 `as_of` 시각을 사용하고 JSON 키와 목록 순서를 결정적으로 만든다. 두 번 실행한 결과가 byte-identical인지 비교한다. canonical 파일에는 source commit과 코드·데이터 SHA-256이 들어간다. 배포, 운영, 외부 검증, live language-model inference, 학습, frozen dataset 변경이 없었다는 경계도 함께 기록한다.

## 안전하게 남겨 둔 한계

이번 구현은 응급 의료 판단기가 아니다. 네 가지 등록 신호를 찾고 명시적인 부정을 처리하는 보수적인 텍스트 경계다. 증상의 강도, 지속 시간, 발생 원인, 사용자의 위치, 현지 응급 전화번호, 보호자 연락 가능 여부를 평가하지 않는다. 실제 응급 대응 서비스처럼 위치 기반 번호를 제공하거나 전화를 연결하지도 않는다.

또한 한국어 별칭 데이터 일부는 기존 저장소 인코딩 이력의 영향을 받는다. 현재 테스트에 등록된 한국어와 영어 표현은 검증하지만, 실제 사용자 문장의 모든 표기 변형을 포괄한다는 증거는 없다. 다국어 frozen 질문 세트와 외부 의료 검토가 후속으로 필요하다. 운영 환경에서는 응급 분기 횟수, 사용자 이탈, 이후 행동을 개인정보 보호 원칙에 맞게 관측해야 하지만, 그런 telemetry도 아직 없다.

이 한계 때문에 `IMPLEMENTED`를 넘는 주장을 하지 않는다. WellnessBox 서비스와의 실제 채팅 연결은 OP-088에서 별도 증명해야 하고, 질문 유형별 frozen Quality Assurance와 실제 Application Programming Interface end-to-end는 OP-090의 과제다. 배포와 운영은 OP-101 이후 단계의 증거가 필요하다.

## 최종 판단

최초 독립 검토에서는 흔한 영어 표현이 빠진 결함도 발견됐다. “My chest hurts”, “pressure in my chest”, “chest discomfort”, “trouble breathing”, “hard to breathe”는 사람이 읽으면 응급 위험을 뜻하지만 초기 별칭 목록에는 없었다. 일부 질문은 일반 근거 답변으로 내려가고 일부는 단순 unsupported가 됐다. 또한 정책 파일 경로가 실행 중인 작업 디렉터리를 기준으로 해, R&D 루트가 아닌 WellnessBox 서비스 디렉터리에서 패키지를 호출하면 응급 판단 전에 `FileNotFoundError`가 발생했다.

수정에서는 가슴 통증·압박·불편감과 호흡 곤란의 흔한 표현을 기존 entity extraction 별칭에 추가하고 각 표현을 독립 회귀 사례로 만들었다. 정책 경로는 `verifier.py` 파일 위치에서 R&D 저장소 루트를 계산한 절대 경로로 바꿨다. canonical smoke는 WellnessBox 서비스 디렉터리로 작업 디렉터리를 바꾼 상태에서도 같은 정책을 읽는지 확인하고, 다섯 가지 흔한 표현이 모두 `safety_escalation`이 되는지 기록한다. 이 결함과 수정 과정은 응급 탐지가 완전하다는 주장이 아니라, 독립 검토가 찾아낸 구체적인 미탐과 실행 위치 의존성을 제거했다는 증거다.

OP-086은 “응급이라는 라벨을 붙였다”가 아니라, 실행 순서에서 검색과 추천과 외부 모델 호출을 실제로 앞질렀을 때 충족된다. 현재 구현은 같은 질문 entity trace를 생성과 검증에서 재사용하고, 부정되지 않은 응급 신호가 있으면 고정된 안전 안내를 첫 문장부터 반환한다. citation, 검색 근거, 추천, provider 호출은 만들지 않는다. 부정 문장과 대조 문장, 변조된 응급 안내를 독립적으로 검사했다. 이 코드와 결정론 증거를 기준으로 OP-086은 required stage `IMPLEMENTED`를 충족한다. 실제 서비스 통합, 운영 효과, 외부 의료 검증은 아직 증명되지 않았다.
