# OP-006 각 요구사항의 소유 저장소와 구현·테스트·운영 증거를 지정한 manifest를 만든다.

## 체크 표시만으로는 완료를 감사할 수 없다

120개 요구사항을 문서의 체크박스로만 관리하면 누가 구현하는지, 어느 저장소의 어떤 파일이 근거인지, 테스트가 실제 분기를 실행하는지 알기 어렵다. 구현 파일이 있어도 두 저장소가 실제로 왕복하지 않을 수 있고, 통합 테스트가 있어도 production에서 결과를 다시 조회한 증거는 없을 수 있다. OP-006은 각 요구사항을 기계가 읽을 수 있는 manifest에 넣고 소유 저장소, 원문 출처, 요구 단계, 현재 주장 단계, 구현·테스트·통합·운영·외부 증거를 분리하는 요구사항이다.

## manifest의 최상위 계약

첫 번째 구현 증거인 `wellnessbox-rnd/data/original_plan/requirements_manifest_v1.json`은 schema version, 원본 PDF 경로와 SHA-256, 완료 프로그램 경로, A~L 그룹을 가진다. 원본 SHA-256은 `31291e6f93977fa2d5d083d0161743c49debef25caf12dccf6edc7fa1c2197d4`다. 그룹은 제목, 원문 페이지 출처, 기본 소유 저장소, 기본 요구 단계와 정확히 10개의 OP 항목을 제공한다. 그룹 기본값 덕분에 같은 기술 영역의 공통 출처와 소유자를 반복하지 않으면서 개별 요구사항이 필요할 때 값을 덮어쓸 수 있다.

각 요구사항에는 `OP-NNN` ID, 제목, 선택적 개별 출처·소유자·요구 단계, 현재 주장 단계와 증거 묶음이 들어간다. materialize 과정은 개별 값이 없으면 그룹 기본값을 복사해 완전한 요구사항 레코드를 만든다. 그 결과 감사기는 OP-001부터 OP-120까지 모든 항목에서 group ID, source refs, owners, required stage, claimed stage와 evidence를 같은 형식으로 읽는다.

## 소유 저장소는 두 값만 허용한다

두 번째 구현 증거 `wellnessbox-rnd/src/wellnessbox_rnd/schemas/original_plan_manifest.py`의 `RepositoryName`은 `wellnessbox-rnd`와 `wellnessbox`만 허용한다. 연구 엔진, 지식, 평가, 안전, 최적화 같은 자산은 주로 R&D 저장소가 소유한다. 인증, 사용자 화면, 상품, 주문, 결제, 약국과 배송 경계는 서비스 저장소가 소유하거나 두 저장소가 함께 소유한다. 임의 문자열을 넣지 못하므로 감사기가 경로 앞의 저장소 이름을 실제 root와 연결할 수 있다.

소유자는 단순 담당자 표시가 아니다. `wellnessbox-rnd/...` 증거를 R&D root에서, `wellnessbox/...` 증거를 서비스 root에서 찾아야 한다는 검증 경계다. 다른 저장소가 소유한 파일을 자기 증거처럼 등록하거나 `..` 경로로 root 밖을 참조하면 canonical 감사가 거부한다. 두 저장소의 사용자 변경은 이 manifest 작업과 무관하므로 이번 반복에서 건드리지 않는다.

## 증거 유형은 완료 단계에 따라 늘어난다

`RequirementEvidenceV1`은 `implementation_files`, `test_files`, `integration_evidence`, `operational_evidence`, `external_dependencies`, `replacement_contracts`를 서로 다른 목록으로 둔다. `IMPLEMENTED`를 주장하려면 구현 파일과 테스트 파일이 모두 필요하다. `INTEGRATED`는 두 목록에 더해 integration evidence가 필요하다. `OPERATED`는 operational evidence까지 있어야 한다. `EXTERNAL`은 내부 단계 서열에 억지로 넣지 않고 외부 의존성과 교체 계약을 모두 요구한다.

이 구분은 파일 개수로 단계를 올리는 일을 막는다. 구현 파일 열 개가 있어도 실제 두 프로세스 왕복이 없으면 `INTEGRATED`가 아니다. 로컬 E2E가 있어도 production 저장 결과와 사후조건을 다시 조회하지 못하면 `OPERATED`가 아니다. 외부 약사 라벨이 필요한 항목은 내부 합성 라벨을 많이 만들더라도 `EXTERNAL`이 아니다. 교체 계약은 외부 입력이 도착했을 때 저장소의 임시 증거를 어떤 동일 형식의 실제 증거로 바꿀지 정의한다.

## strict schema가 조용한 오타를 막는다

manifest의 모든 Pydantic 모델은 `extra="forbid"`를 사용한다. `unsupported_completion_flag`처럼 스키마에 없는 필드는 검증 오류가 된다. 단계 값은 `IMPLEMENTED`, `INTEGRATED`, `OPERATED`, `EXTERNAL` 네 개만 허용하므로 `DONE`, `COMPLETE`, `VERIFIED` 같은 모호한 단어를 넣을 수 없다. 요구사항 ID는 `OP-`와 세 자리 숫자, 그룹 ID는 A~L, 원본 해시는 소문자 64자리 16진수 형식을 요구한다.

`validate_original_plan_manifest_v1`은 그룹 순서가 A~L인지, 요구사항이 OP-001~OP-120 순서인지, 중복 ID가 없는지, 그룹마다 10개 요구사항이 있는지 검사한다. 각 요구사항은 주장 단계에 필요한 증거 목록도 검사받는다. 따라서 새 항목을 중간에 빠뜨리거나 번호를 중복하고도 전체 120개라고 주장하기 어렵다.

## 테스트가 실제로 거부하는 잘못된 manifest

manifest 증거인 `wellnessbox-rnd/tests/test_original_plan_manifest.py`는 현재 파일을 읽어 schema version, 원본 SHA-256, 120개 연속 ID, A~L 그룹, 출처와 소유자, 전체 검증 issue 0을 확인한다. 현재 주장 단계의 전체 사전도 고정해 한 항목이 검토 없이 승격되는 변경을 드러낸다. OP-006 자체는 `IMPLEMENTED`로 등록돼 있다.

부정 테스트는 `IMPLEMENTED` 주장에 구현 또는 테스트 파일이 없을 때 두 오류를 반환하는지 확인한다. `OPERATED` 주장에 integration 또는 operational evidence가 없으면 각각 오류가 난다. `EXTERNAL` 주장에 external dependency와 replacement contract가 없으면 두 누락을 지적한다. 인식하지 못하는 단계 단어와 지원하지 않는 필드도 Pydantic validation error로 거부한다. 이 테스트는 성공 사례만 세는 것이 아니라 허위 완료가 실패하는 경계를 실행한다.

## manifest만으로는 증거 파일의 내용까지 증명되지 않는다

OP-006의 schema 검사는 필요한 경로 목록이 비어 있지 않은지 확인하지만, 문자열이 가리키는 파일이 Git에 추적되는지, root 안에 있는지, 증거 단계와 실제 내용이 맞는지까지 혼자 판단하지 않는다. 그 검사는 `src/wellnessbox_rnd/governance/original_plan_audit.py`와 후속 OP-008 감사가 담당한다. OP-120은 연구보고서, 요구 단계 부족, 외부 검증, 최종 영수증까지 더해 전체 완료를 판정한다.

이 책임 분리는 중요하다. OP-006은 공통 데이터 구조와 최소 증거 계약을 만든다. OP-008은 등록된 경로와 Git 추적 상태를 감사하고, OP-009는 pytest와 CI에 연결하며, OP-010은 manifest에서 완료 보고서를 만든다. 한 validator가 모든 정책을 암묵적으로 처리하지 않으므로 어느 단계에서 문제가 생겼는지 구분할 수 있다.

## Git 이력과 현재 단계

manifest schema, 120개 JSON 재고, OP-006 등록과 기본 테스트는 2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad` 커밋에서 함께 도입됐다. 같은 날 `17da3a15e7bd755a1074682ca40f7b532b1008e3`가 증거 경로 감사를 추가했고, `a449b605dceb29471103076d03de4e137ce421a5`가 CI gate를 연결했다. 이후 각 OP 구현이 추가될 때 manifest의 claimed stage와 evidence 경로도 함께 갱신됐다.

OP-006의 기본 요구 단계와 현재 주장 단계는 `IMPLEMENTED`다. 기계 판독형 manifest와 strict Pydantic schema, 긍정·부정 회귀 테스트가 있으므로 구현 단계는 충족한다. 그러나 manifest에 `OPERATED` 문자열을 적는 것만으로 실제 운영이 생기지는 않는다. 현재 OP-120 감사에는 비외부 단계 미달과 외부 검증 부족이 남아 있으므로 전체 완료를 주장하지 않는다.

이번 반복은 OP-006의 기존 계약을 설명하는 연구보고서와 감사 집계만 보강한다. schema, manifest 재고, 서비스 코드, 데이터, 학습, 모델, 시뮬레이션을 바꾸지 않는다. OP-006이 만든 핵심 결과는 한 문장짜리 완료 표시가 아니다. 누가 어떤 원문 요구를 어느 단계까지 구현했고, 그 주장을 어떤 저장소 파일과 테스트로 반박 가능하게 검증할지를 한 레코드에 묶은 감사 계약이다.
## 원문을 요구사항으로 바꾸는 과정
이 그룹은 기능을 먼저 만들기보다, 원문에서 무엇을 읽었고 어느 파일이 그 해석을 지지하는지 고정하는 데서 출발한다. 원본 해시, 페이지, 요구사항 ID, 증거 단계가 따로 남아 있어야 나중에 코드가 바뀌어도 출발점과 해석을 다시 대조할 수 있다.

`OP-006`는 “각 요구사항의 소유 저장소와 구현·테스트·운영 증거를 지정한 manifest를 만든다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=1-59`
- 구현·설계: `wellnessbox-rnd/data/original_plan/requirements_manifest_v1.json`, `wellnessbox-rnd/src/wellnessbox_rnd/schemas/original_plan_manifest.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_original_plan_manifest.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
