# OP-087 상담 답변과 추천 실행을 같은 세션에 저장한다.

manifest에 등록된 증거 `wellnessbox-rnd/apps/inference_api/routes/interim.py`에서 구현과 검증 대상을 확인할 수 있다.

## 이 요구사항이 필요한 이유

OP-087의 원문은 “상담 답변과 추천 실행을 같은 세션에 저장한다”이다. 이 문장은 단순히 두 객체에 같은 문자열을 붙이라는 뜻이 아니다. 사용자가 채팅에서 받은 설명이 어떤 추천 실행과 연결됐는지 나중에 재현할 수 있어야 하고, 반대로 추천 실행을 조사할 때 사용자가 그 실행 직전에 어떤 질문을 했고 어떤 답변을 받았는지 찾을 수 있어야 한다. 답변과 추천이 서로 다른 저장소에서 아무 관계 없이 남으면 안전사고나 잘못된 추천을 조사할 때 당시 판단 과정을 복원할 수 없다. 같은 사용자가 같은 날 여러 질문을 했거나 추천을 여러 번 실행한 경우에는 사용자 식별자와 날짜만으로 정확한 쌍을 찾을 수도 없다.

이번 구현에서는 세션을 “사용자가 보고 있는 채팅 묶음”과 “R&D가 그 채팅을 처리한 실행 묶음”의 결합으로 정의했다. WellnessBox 서비스가 이미 사용하는 `ChatSession.id`를 외부 세션 식별자로 유지하고, R&D는 이 값을 받아 기존 `agent_runs`의 멱등 키에 포함한다. 한 상담 요청 안에서는 `turn_id`가 질문과 답변 한 쌍을 식별한다. R&D가 만든 답변 해시, 기존 추천 실행의 `run_id`, R&D 에이전트 실행의 `run_id`를 하나의 결합 자료로 만든 뒤 SHA-256으로 고정한다. 서비스는 이 결합 자료를 새 테이블에 복제하지 않고 기존 `ChatSession.meta`와 기존 assistant `ChatMessage.meta`에 저장한다.

이 구현의 현재 주장 단계는 `IMPLEMENTED`이다. OP-087이 요구하는 단계는 `OPERATED`, 즉 실제 운영 환경에서 이 저장이 일어나고 운영 기록으로 확인되는 단계다. 이번 검증은 localhost의 실제 R&D 프로세스와 실제 서비스 TypeScript 어댑터를 연결했지만, 운영 서비스 데이터베이스에 시험 레코드를 쓰지 않았다. 운영 데이터베이스가 개발용인지 production용인지 확인되지 않은 상태에서 임의 세션을 쓰는 것은 안전한 검증이 아니다. 따라서 코드와 로컬 통합이 정상이라는 사실은 증명했지만, production 운영까지 증명했다고 말하지 않는다.

## 기존 시스템을 조사한 결과

WellnessBox 서비스에는 이미 채팅 영속화 경로가 있었다. Prisma의 `ChatSession`은 세션 식별자, 익명 기기 식별자, 로그인 사용자 식별자, 제목, 상태, 메타데이터를 보관한다. `ChatMessage`는 각 메시지의 역할과 본문, 생성 시각, 메타데이터를 세션에 연결한다. `/api/chat/save`의 `persistChatSession`은 세션 소유권을 먼저 확인하고, 기존 세션을 갱신하거나 새 세션을 만든 뒤 메시지를 멱등 upsert한다. 이 구조가 있는데 상담 전용 세션 테이블을 새로 만들면 사용자 소유권 검사, 익명 사용자 승격, 세션 삭제, 채팅 화면 로딩 기능을 모두 다시 구현해야 한다. 그래서 서비스 쪽에는 새 저장소를 만들지 않았다.

R&D에도 추천 실행 원장이 이미 있었다. `recommendation_runs`는 추천 실행의 상태, 요청 해시, 응답 JSON, 모델 식별자와 시각을 보관한다. `agent_runs`와 `agent_steps`는 한 에이전트 실행에서 어떤 단계가 어떤 입력과 결과 해시를 만들었는지 기록한다. 이번 구현은 상담 답변을 보존하려고 별도의 추천 테이블을 만들지 않았다. 기존 추천 함수가 안전성 검사를 거쳐 `recommendation_runs`와 `recommendation_items`를 기록하도록 그대로 호출했다. 상담 세션에는 추천 결과 전체를 복사하지 않고 기존 추천 실행을 가리키는 `run_id`만 연결했다.

OP-083부터 OP-086까지 구현한 상담 경로도 그대로 재사용했다. 저장 전에 답변을 새로 조립하는 간이 로직을 만들지 않았다. 저장 대상 답변은 승인된 상담 지식 범위, 기준 시각, 검색 근거, 불확실성, 응급 우선순위와 verifier 결과를 포함하는 기존 `generate_chat_answer_with_openai_fallback`의 반환값이다. verifier가 통과하지 못한 답변은 세션 결합 단계로 넘어가지 않고 HTTP 422로 끝난다. 응급 질문이면 추천 실행을 만들지 않고 `RECOMMENDATION_SUPPRESSED_FOR_URGENT_SAFETY`라는 이유를 기록한다. 이 예외는 “항상 추천 실행 ID가 있어야 한다”는 형식 요건보다 응급 안전 우선순위가 높다는 OP-086의 결정을 보존한다.

## 세션 결합 계약

R&D의 새 경로는 `/v1/interim/counseling/turns`이다. 요청은 `counseling_turn_request_v1`으로 고정했다. 서비스 세션 ID, turn ID, 가명화된 profile ID, 질문, 답변 기준 시각, 프로필, 동의 범위, 목표, 성분과 안전성 입력을 받는다. 예상하지 않은 필드는 Pydantic의 `extra="forbid"`로 거부한다. 답변 기준 시각에는 시간대가 반드시 있어야 한다. profile ID는 기존 interim 규칙과 같은 `usr_` 접두사와 16~64자의 16진수 형식을 사용한다.

서비스는 로그인 사용자의 원래 ID나 익명 기기 ID를 R&D에 그대로 보내지 않는다. 기존 interim 환경의 HMAC salt를 사용해 32자리 가명 식별자를 만든다. 같은 서비스 사용자와 같은 salt는 같은 R&D profile ID가 되므로 세션을 이어 갈 수 있지만, R&D 데이터만 보고 원래 서비스 식별자를 복원할 수는 없다. salt가 없으면 호출을 허용하지 않는다. 내부 호출 토큰도 기존 `x-wb-rnd-token` 계약을 그대로 사용하며, 설정된 토큰과 일치하지 않으면 401을 반환한다.

R&D는 기존 agent run을 먼저 조회해 같은 세션과 turn의 과거 입력을 검사한 뒤 profile을 `user_profiles`에 upsert하고 `BoundedAgent.create_run`을 호출한다. 멱등 키는 `counseling-session:{service_session_id}`이고, 기존 함수가 profile ID를 앞에 붙인다. turn의 입력 해시는 세션과 질문만이 아니라 profile, goals, ingredients, safety, product constraints, consent scopes와 answered time을 포함한 요청 전체를 canonical JSON으로 직렬화해 계산한다. 같은 turn ID에 다른 안전 정보나 프로필을 넣으면 profile을 바꾸기 전에 HTTP 409를 반환한다. 완전히 같은 요청만 기존 `counseling_answer` 단계를 재사용한다.

추천 실행도 중복 생성하지 않는다. 기존 추천 요청 객체의 Pydantic JSON을 SHA-256으로 계산한 뒤 같은 profile과 요청 해시를 가진 `recommendation_runs`가 있는지 확인한다. 이미 있으면 저장된 `response_json`에서 기존 run ID와 상태를 읽는다. 없을 때만 기존 `recommendation` 함수를 호출한다. 이 때문에 네트워크 재시도나 서비스 스트림 재연결이 같은 추천을 두 번 실행하지 않는다. 집중 테스트는 동일 요청을 두 번 보낸 뒤 `agent_runs`, `agent_steps`, `recommendation_runs`의 행 수가 모두 1인지 직접 조회했다.

반환 계약은 `counseling_turn_response_v1`이다. 검증된 답변 전체와 verifier 결과, agent run ID, 추천 실행의 run ID·상태·simulation 표시, 세션 결합 해시를 포함한다. 서비스 어댑터는 단지 HTTP 200인지 확인하고 값을 믿지 않는다. 스키마 버전, 답변 본문, verifier의 `passed=true`, 세션 및 turn 식별자, agent run ID, 결합 해시, 추천 실행 필드의 자료형을 다시 검사한다. R&D가 요청과 다른 세션 ID나 turn ID를 돌려주면 서비스 채팅 경로가 `WB_RND_COUNSELING_session_binding_mismatch`로 중단한다.

## 기존 채팅 저장 경로에 넣은 방식

서비스의 `persistRndCounselingTurn`은 기존 `ensureClient`로 기기 주체를 먼저 보장하고, 기존 세션이 있으면 `canWriteChatSession`으로 소유권을 검사한다. 로그인 사용자 세션은 같은 `appUserId`만 쓸 수 있고, 익명 세션은 같은 `clientId`만 쓸 수 있다. 이 검사를 통과한 뒤 기존 `ChatSession`을 upsert한다. 메타데이터의 `rndCounseling`에는 agent run ID, recommendation run ID, 추천 상태, simulation 표시와 결합 해시를 넣는다.

답변 본문은 기존 `ChatMessage`에 assistant 역할로 저장한다. 독립 검토 전 구현은 `turn_id`만 전역 메시지 기본키에 사용했다. 서로 다른 사용자가 같은 turn ID를 보내면 다른 세션의 메시지를 갱신할 수 있는 Critical 결함이었다. 수정 후 메시지 ID는 길이 접두사를 붙인 서비스 세션 ID와 turn ID를 함께 SHA-256으로 계산한다. 저장 전에 같은 해시의 기존 메시지가 다른 세션에 속하는지도 검사한다. 같은 세션의 같은 turn은 같은 메시지를 재사용하지만 다른 세션은 같은 turn 문자열을 써도 다른 기본키를 가진다. 메시지 메타데이터에는 같은 R&D 결합 정보를 기록한다.

서비스가 기존 채팅 저장 API와 별도로 이 함수를 호출하는 이유는 스트리밍 답변이 끝난 뒤 클라이언트가 저장을 요청하기만 기다리면 추천 실행과 답변 저장 사이에 공백이 생기기 때문이다. 브라우저가 응답을 받은 직후 닫히거나 네트워크가 끊기면 추천은 R&D에 남지만 서비스 답변은 저장되지 않을 수 있다. R&D 상담 응답을 받은 서버가 assistant 메시지와 실행 연결을 먼저 upsert하고, 기존 클라이언트 저장은 같은 메시지 ID를 다시 upsert하도록 만들었다.

## 재현 검증 결과

R&D 집중 테스트는 실제 FastAPI `TestClient`를 통해 새 경로를 두 번 호출했다. 첫 호출과 두 번째 호출은 같은 agent run ID와 같은 추천 실행 객체를 반환했다. verifier는 통과했고 서비스 세션 ID도 요청과 일치했다. SQLite를 직접 조회했을 때 `agent_runs=1`, `agent_steps=1`, `recommendation_runs=1`이었다. 내부 토큰 없이 같은 요청을 보내면 401이 반환됐다. 이 검사는 인증이 경로 선언에만 붙어 있고 실제로는 우회되는 문제를 막는다.

canonical smoke는 별도 Python 프로세스에서 실제 Uvicorn 서버를 시작하고, WellnessBox 저장소의 실제 Node.js/TypeScript 어댑터를 실행했다. 질문은 glucosamine과 warfarin 상호작용이었고 verifier를 통과한 `supported` 답변이 나왔다. 안전 입력에는 임신 상태를 넣어 추천 모델 실행 전에 기존 안전 규칙이 추천을 차단하도록 했다. 그 결과 추천 실행은 생겼지만 상태는 `BLOCKED`였고 simulation 표시는 true였다. 이 선택은 실제 등록 모델이나 운영 데이터를 요구하지 않으면서도 “답변과 추천 실행을 같은 세션에 결합한다”는 경계를 검증한다. 안전 차단을 우회하거나 추천 성공처럼 꾸미지 않았다.

smoke는 서로 다른 임시 SQLite 파일에서 두 번 실행했다. UUID 자체는 매번 달라질 수 있으므로 특정 UUID를 기대값으로 고정하지 않았다. 대신 agent run ID와 recommendation run ID가 각각 정해진 형식을 만족하는지, 답변 본문 SHA-256이 같은지, 세션과 turn ID가 같은지, verifier 통과와 추천 상태가 같은지, 결합 해시가 64자리인지, 세 테이블 행 수가 모두 1인지 비교했다. 정규화한 두 결과는 byte-identical이었다. canonical 파일의 SHA-256은 생성 후 별도로 계산하며 manifest 증거에 연결한다.

서비스에서는 새 어댑터 계약 시험, ESLint, TypeScript `--noEmit`, production `next build`를 통과했다. production build는 Prisma Client 생성, encoding audit, route export audit, 타입 검사와 98개 정적 페이지 생성을 포함했다. 이 검증은 새 import가 server-only 경계를 깨뜨리거나 App Router 빌드를 망가뜨리지 않았다는 근거다. 다만 build 통과는 실제 서비스 데이터베이스에 레코드가 저장됐다는 증거가 아니다.

## 아직 운영 완료라고 말할 수 없는 이유

이번 smoke의 서비스 데이터베이스 저장은 의도적으로 실행하지 않았다. WellnessBox `.env`에 데이터베이스 연결 정보가 있지만 그 연결이 개발 전용인지 production인지 확인하지 않은 상태에서 임의 상담 세션을 쓰면 운영 데이터에 불필요한 레코드를 남길 수 있다. production 배포와 운영 환경 변경은 사용자 사전 승인이 필요한 범위이기도 하다. 따라서 canonical 증거에는 `service_database_persistence_observed=false`와 `production_operation_observed=false`를 명시했다.

초기 OP-087 구현의 `agent_steps`에는 답변 해시와 최소 결합 정보만 저장했고 답변 원문은 서비스 `ChatMessage`가 보관했다. 후속 OP-089 작업은 장애 fallback과 재시도의 반환값을 정확히 고정하기 위해 binding을 `counseling_session_binding_v2`로 올렸다. 현재 binding JSON에는 서비스 세션 ID, turn ID, profile ID, agent run ID, answer hash뿐 아니라 답변 전체, verifier 결과, 답변 실행 정보와 추천 실행 정보가 함께 저장된다. SQLite 행만 읽어도 저장된 답변을 그대로 반환하고 결합 해시를 대조할 수 있다. 서비스 메시지와 R&D snapshot이 함께 남으므로 조사 가능성은 높아졌지만 두 저장소의 보존 기간과 삭제 정책을 함께 운영해야 한다는 조건은 남는다. 어느 한쪽의 기록이 삭제되면 두 시스템에 실제로 같은 상담이 기록됐는지를 대조할 수 있는 범위가 줄어든다.

## 독립 검토가 바꾼 구현

독립 검토는 앞의 메시지 기본키 문제 외에도 같은 turn의 의미 입력 변경, 동시 추천 중복, 과도한 profile 전달과 R&D 결합 자료 미보존을 Important로 분류했다. 전체 요청 해시와 409 충돌 검사를 추가했고, `recommendation_runs(profile_id, request_sha256)`에 unique index를 추가했다. 두 요청이 동시에 기존 행을 찾지 못해도 한 insert만 성공하며 다른 요청은 unique conflict 뒤 저장된 응답을 읽는다. 병렬 회귀 테스트는 같은 요청 두 개가 모두 200을 받고 추천 run은 한 건만 남는지 확인한다.

서비스는 더 이상 `body.profile` 전체를 R&D로 펼쳐 보내지 않는다. 나이, 허용된 biological sex, 임신·수유 boolean과 목표만 새 객체로 구성한다. safety도 임신·수유와 정해진 안전 boolean만 허용한다. 이메일, 전화번호와 자유 서술 medication note를 넣은 회귀 입력은 R&D 요청에서 제거된다. 사용자별 동의 원장이 서비스 채팅에 아직 없으므로 production에서는 R&D 상담 분기를 실행하지 않는다. 비production proxy simulation에서만 `simulation:write` 범위를 보내며, 실제 사용자 동의가 확인됐다는 뜻으로 쓰지 않는다.

마지막 재검토에서는 실제 UI profile이 `sex`와 `pregnantOrBreastfeeding`을 쓰는데 초기 allowlist가 다른 필드명을 읽는 문제를 찾았다. 서비스는 이제 `sex`를 `biological_sex`로 명시적으로 바꾸고, 임신 또는 수유의 결합 boolean이 true면 두 위험 상태를 모두 true로 보수적으로 전달한다. 질환·약물·알레르기 원문은 확인된 동의 없이 보내지 않는다. 다만 세 목록 중 하나라도 비어 있지 않으면 `requires_test=true`를 보내 추천이 완전한 안전정보를 가진 것처럼 처리되지 않게 한다.

재검토는 세션과 질문으로 만든 turn ID는 같지만 답변 시각을 매번 현재 시각으로 만들면 재시도가 409가 된다는 문제도 찾았다. 서비스는 이제 마지막 user message의 기존 ID를 turn ID로 사용하고 그 메시지의 기존 createdAt을 answered time으로 사용한다. 두 값이 없거나 잘못됐으면 R&D를 호출하지 않는다. 세션 metadata와 assistant message 저장은 하나의 Prisma transaction 안에서 처리하고, 기존 JSON metadata의 다른 기능 필드를 보존한 채 `rndCounseling`만 병합한다.

과거 추천 중복 행 때문에 migration이 시작 자체를 중단하는 문제도 수정했다. 기존 recommendation run은 삭제하거나 request hash를 바꾸지 않는다. nullable `idempotency_identity` 열을 추가하고 새 상담 추천에만 profile과 request hash의 결정적 식별자를 기록한다. unique index는 null이 아닌 새 식별자에만 적용되므로 과거 데이터를 보존하면서 새 동시 중복을 막는다.

또한 이번 상담 추천은 `PROXY_GOLD_SIMULATION`이다. 추천 실행이 `BLOCKED`였다는 사실은 안전 경로가 동작했다는 뜻이지, 실제 사용자에게 적절한 상품이나 복용 계획을 제공했다는 뜻이 아니다. 실제 제품 매핑, 약사 검토, 운영 동의, production 데이터 보존과 삭제, 장애 복구를 확인하지 않았다. 그래서 OP-087은 구현이 존재하고 로컬 통합으로 일부 동작을 관측했지만 required stage `OPERATED`보다 낮은 `IMPLEMENTED`로 남긴다.

## 최종 판단

상담 답변과 추천 실행은 더 이상 서로 관계없는 출력이 아니다. 서비스의 기존 채팅 세션 ID가 R&D agent run의 멱등 키가 되고, 검증된 답변의 해시와 기존 추천 run ID가 하나의 결합 해시로 묶인다. 서비스는 같은 연결 정보를 기존 `ChatSession`과 assistant `ChatMessage`에 저장하며, 재요청은 같은 turn 메시지와 같은 R&D 실행을 재사용한다. 실제 두 프로세스 호출과 R&D 원장 조회는 이 결합이 재현 가능하다는 것을 증명했다. 다만 운영 서비스 데이터베이스와 production 배포에서 저장을 관측하지 않았으므로 OP-087은 `IMPLEMENTED`이며 `PARTIAL`이다.
## 상담 답변을 믿을 수 있게 만드는 조건
상담 답변은 자연스러운 문장보다 근거 범위와 위험 차단이 먼저다. 허용된 지식 범위만 검색하고, 답변에 근거와 유효일·불확실성을 남기며, 응급 신호나 provider 장애에서는 안전 안내와 결정적 fallback을 우선한다.

`OP-087`는 “상담 답변과 추천 실행을 같은 세션에 저장한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox-rnd/src/wellnessbox_rnd/interim/store.py`, `wellnessbox-rnd/data/knowledge/counseling_retrieval_corpus_manifest_v1.json`, `wellnessbox/app/api/chat/save/route-service.ts`
- 테스트·실행: `wellnessbox-rnd/tests/test_interim_api.py`, `wellnessbox-rnd/scripts/run_counseling_session_service_adapter_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op087_op088_counseling_session_service_adapter_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op087_op088_counseling_session_service_adapter_smoke_v1.json`, `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-087.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-087.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
