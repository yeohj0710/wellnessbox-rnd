# OP-003 한 장의 아키텍처를 여섯 개의 독립 요구사항 묶음으로 풀었다

## 페이지 15를 한 기능으로 등록하면 무엇이 빠질까

원본 15쪽은 서비스 아키텍처와 연구개발 로드맵을 한 화면에 담는다. 화면 중앙에는 자가적응형 AI가 있고, 주변에 Data Lake, 안전 검증 엔진, 다목적 최적화 엔진, 개인화 효과 추론 모델, 약국과 웰니스박스, 바이오센서·유전자 데이터가 연결된다. 이 그림을 “AI 기반 맞춤 추천 시스템”이라는 한 문장으로만 등록하면 어느 구성요소가 구현됐고 무엇이 빠졌는지 판단할 수 없다. OP-003은 그림 왼쪽 표에 번호 [1]부터 [6]까지 적힌 기술 블록을 각각 추적 가능한 요구사항 묶음으로 바꾸는 작업이다.

## 원문이 직접 구분한 여섯 기술 블록

첫 번째 블록은 데이터 레이크 구축이다. AI 에이전트가 정확히 작동할 수 있도록 데이터 형식을 규정하고 단일 저장소를 만드는 일, 사용자 특성과 유저 행동, 의약학 전문 문헌, 로그 데이터를 정제하는 일이 포함된다. 두 번째는 개인화 안전 검증 엔진이다. 개인 특성에서 위험 사항을 찾고, 금기·상호작용·과용량을 사전에 필터링하며, 레퍼런스 제시와 탐색 범위 설정을 맡는다.

세 번째는 개인화 효과 추론 모델(ITE)이다. 사용자별 파라미터로 복용 효과를 추론하고 수치화해 건강기능식품별 개선 효과를 비교하게 한다. 네 번째는 다중제약 복용 조합 최적화 엔진이다. 효과, 부작용, 가격, 복용 편의를 함께 고려해 사용자에게 적합한 조합을 찾는다. 다섯 번째는 자가적응형 Closed-loop AI다. 사용자의 상태를 주기적으로 확인하고 복용 유지·조정·중단을 판단하며, 다음 행동을 호출하고 결과를 보완한다. 여섯 번째는 바이오센서·유전자 데이터 연동이다. 설문 중심 진단의 한계를 줄이고 웨어러블, 연속혈당측정기, 유전자 검사 결과를 개인화 판단에 더한다.

## manifest에서는 여섯 블록을 어떻게 독립 추적하나

구현 기준 문서인 `wellnessbox-rnd/data/original_plan/requirements_manifest_v1.json`은 여섯 블록을 하나의 완료 표기로 합치지 않는다. 데이터 레이크는 그룹 C의 OP-021~030, 안전 검증은 그룹 D의 OP-031~040으로 분리한다. 효과 추론은 추천 후보와 효과 점수를 다루는 그룹 E의 OP-041~050, 복용 전후 수치화와 환자보고결과(PRO)를 다루는 그룹 F의 OP-051~060으로 더 세분화한다. 이 분리는 후보를 고르는 일과 실제 변화량을 측정하는 일이 서로 다른 검증을 요구하기 때문이다.

다중제약 최적화는 그룹 G의 OP-061~070, Closed-loop 실행은 그룹 H의 OP-071~080에 등록한다. 페이지 15의 중앙 AI가 수행할 상담과 근거 검색은 그룹 I의 OP-081~090으로 별도 추적한다. 센서와 유전 데이터는 그룹 J의 OP-091~100에 등록한다. 서비스와 약국을 잇는 선은 그룹 K의 OP-101~110, 배포·보안·최종 감사는 그룹 L의 OP-111~120에서 검증한다. 따라서 여섯 블록은 독립성을 유지하면서도 실제 서비스 연결과 검증 단계까지 이어진다.

이 대응은 완전한 일대일 표가 아니다. 효과 추론은 E와 F로 나뉘고, Closed-loop는 H와 I에 걸치며, 모든 블록의 프로덕션 연결은 K와 L이 공통으로 다룬다. 중요한 점은 블록별 실패를 숨기는 상위 완료 표시가 없다는 것이다. 예를 들어 안전 엔진이 구현돼도 데이터 계보와 운영 증거가 없으면 데이터 레이크까지 완료된 것으로 보지 않는다.

## 구현·테스트·Git 증거는 무엇을 보장하나

두 번째 구현 증거인 `wellnessbox-rnd/docs/plans/2026-07-15-original-plan-completion-program.md`는 120개 실행 항목을 A~L로 나누고 OP-003에 “원본 p.15의 여섯 기술 블록을 독립 요구사항으로 등록한다”는 완료 조건을 둔다. 저장소 내부 경로는 `docs/plans/2026-07-15-original-plan-completion-program.md`다. 이 계획과 manifest는 같은 여섯 블록을 구현, 통합, 운영, 외부 검증 단계로 추적하는 기준을 제공한다.

테스트 증거는 `wellnessbox-rnd/tests/test_original_plan_manifest.py`다. 이 테스트는 OP-001부터 OP-120까지 번호가 빠짐없이 이어지는지, A~L 그룹이 모두 존재하는지, 각 요구사항에 출처와 소유자가 있는지, 현재 주장 단계가 고정 기대값과 같은지 검사한다. 테스트가 페이지 15의 도형을 자동 인식하는 것은 아니다. 페이지 15의 시각 확인과 `docs/context/master_context.md`의 재구성이 원문 해석을 담당하고, manifest 테스트는 그 결과로 만든 요구사항 재고가 사라지거나 번호가 깨지는 일을 막는다.

Git 이력에서는 2026-03-08의 `e5ef1ecf8575d1a09cf4fb3a8d0063e9a8b24d4d`가 원본 PDF와 master context를 함께 도입했다. 2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad`는 120개 manifest, OP-003 완료 항목, manifest 테스트를 같은 변경 계열에 등록했다. 이후 감사와 CI는 이 재고를 재사용했다. 이 연결은 여섯 블록이 보고서 문장에만 남은 분류가 아니라 기계 판독 가능한 요구사항 체계의 출발점임을 보여 준다.

## 독립 등록과 실제 구현 완료는 같은 말이 아니다

OP-003의 기본 요구 단계와 주장 단계는 `IMPLEMENTED`다. 여기서 구현됐다는 뜻은 여섯 기술 블록이 누락 없이 독립 요구사항으로 등록되고 테스트 가능한 재고가 됐다는 뜻이다. 각 블록의 모든 하위 요구사항이 운영 단계까지 완료됐다는 뜻은 아니다. 현재 OP-120 감사에는 비외부 단계 미달 항목이 남아 있고, OP-039의 외부 검증도 없다. 페이지 15의 연결선을 실제 production traffic 증거로 해석해서도 안 된다.

이번 반복은 요구사항 등록 근거를 설명하는 연구보고서만 보강한다. 서비스 코드, 사용자 데이터, 학습 데이터, 모델, 안전 규칙, 시뮬레이션은 변경하지 않는다. 따라서 여섯 블록의 제품 동작이나 성능 지표가 새로 개선됐다고 주장하지 않는다. 독립 등록은 후속 구현을 빠짐없이 감사하기 위한 전제 조건이다.

## 여섯 블록을 따로 보는 이유

데이터가 있어도 안전 규칙이 없으면 위험한 추천이 나온다. 안전한 후보가 있어도 효과를 비교하지 못하면 최적 선택을 만들 수 없다. 최적 조합을 한 번 계산해도 후속 상태를 다시 보지 않으면 Closed-loop가 아니다. 센서와 유전자 데이터가 연결돼도 동의, 정규화, 계보가 없으면 신뢰할 수 있는 입력이 아니다. 여섯 블록을 독립 등록하면 이런 실패를 “전체 시스템 구현”이라는 말로 덮지 못한다.

OP-003의 결과는 명확하다. 원본 15쪽의 [1] 데이터 레이크, [2] 안전 검증, [3] 효과 추론, [4] 다중제약 최적화, [5] Closed-loop AI, [6] 바이오센서·유전자 연동을 manifest의 독립 요구사항 묶음으로 추적한다. 각 묶음은 자신의 구현 파일과 테스트, 단계 증거가 있어야만 완료된다. 이 재고 계약이 있으므로 후속 감사는 여섯 블록 중 빠진 부분을 구체적인 OP 번호로 지목할 수 있다.
