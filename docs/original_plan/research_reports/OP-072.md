# OP-072 안전검사, 후보 생성, 근거 조회, 최적화, 계획 시작 순서를 강제한다.

## 요구된 다섯 단계의 선후 관계

안전검사→후보 생성→근거 조회→최적화→계획 시작 순서를 건너뛸 수 없어야 한다. 안전검사보다 후보나 최적화를 먼저 실행하면 위험 성분이 계획에 들어갈 수 있다. 근거가 없는 후보를 최적화에 넘기거나, 계획 시작을 단순 상태 변경으로 처리해도 같은 문제가 생긴다. OP-072는 기능 다섯 개의 존재가 아니라 성공 조건과 중단 조건을 포함한 실행 순서를 요구한다.

초기 에이전트의 상태표는 `PROFILE_READY`에서 `EVIDENCE_RETRIEVAL`로 이동한 뒤 `SAFETY_CHECK`로 가는 순서를 허용했다. 커밋 `ecb3540`은 단일 계약을 만들면서 안전검사를 후보 생성보다 앞에 고정했다. 커밋 `403afec`은 이 계약을 실제로 실행하는 `execute_recommendation_workflow()`와 FastAPI의 `/v1/interim/agent/workflow`를 추가했다. 하지만 첫 실행기는 안전검사에 넣은 성분과 후보 생성 성분이 달라도 막지 않았고, 공개 상태 이동, 재시도 입력 변경, 추적 누락의 우회가 남아 있었다.

커밋 `48b314c`는 직접 상태 이동을 금지하고 안전검사 성분과 후보 성분을 같게 묶었다. 요청 내용 전체를 지문에 넣어 같은 멱등 키의 재시도를 저장 추적에 연결했으며, 실행 추적을 검증 자료형으로 바꿨다. 커밋 `3a4e452`는 다른 프로세스가 같은 실행의 다음 단계를 동시에 점유하지 못하게 했고, `26941e9`는 실패한 도구가 `EXECUTING` 상태에 갇히지 않도록 점유 해제 순서를 고쳤다.

## 실행기가 각 단계에서 확인하는 조건

`wellnessbox-rnd/src/wellnessbox_rnd/interim/agent.py`의 `_execute_recommendation_workflow_serialized()`는 먼저 안전 인자에 별도 `ingredients`가 있으면 후보 성분 배열과 정확히 같은지 비교한다. 다르면 `safety_candidate_ingredients_mismatch`를 내고 실행을 만들지 않는다. 안전 인자, 성분, 근거 질의, 최대 상품 수를 묶은 SHA-256 지문은 멱등 요청의 신원이 된다. 같은 기본 키와 같은 지문은 저장된 실행을 재사용하고, 같은 키에 다른 지문은 `workflow_idempotency_payload_conflict`로 중단한다.

새 실행은 `load_profile`로 `INTAKE`에서 `CONSENT_CHECK`로 간다. `verify_consent`가 `PROFILE_READY`에 도착한 뒤에야 `check_safety`를 호출할 수 있다. 안전 결과가 `BLOCK` 또는 `STOP_AND_ESCALATE`이면 `stop`을 기록하고 `STOPPED`에서 끝난다. 후보 생성 도구는 이 경우 호출되지 않는다.

안전을 통과하면 `rank_ingredients`가 후보를 만든다. 후보가 비면 중단한다. 후보가 있으면 `retrieve_evidence`가 은퇴하지 않았고 격리되지 않았으며 `approved_for_safety=1`인 근거 문단을 최대 10건 읽는다. 근거 식별자가 없으면 최적화 전에 멈춘다. 근거가 있어도 후보 성분 이름이 문단에 나타난 후보만 `supported_ranked`에 남는다. 뒷받침된 후보가 하나도 없을 때도 계획은 시작되지 않는다.

`optimize_regimen`은 근거가 남은 후보 중 `max_items`만큼을 선택한다. 마지막 `start_plan`은 조합과 근거 식별자 배열이 모두 비어 있지 않을 때만 `postcondition_success=true`를 반환한다. 각 도구 결과가 성공한 뒤에만 `agent_steps`에 입력·결과 지문이 저장되고 계약 상태가 다음 단계로 이동한다. 실패한 호출은 단계와 상태를 앞당기지 않는다.

API 연결은 `wellnessbox-rnd/apps/inference_api/routes/interim.py`의 `OrderedWorkflowRequest`와 `execute_ordered_workflow()`에 있다. 요청 자료형은 프로필 식별자, 128자 이하 멱등 키, 1~20개 성분, 200자 이하 근거 질의, 1~20의 최대 항목 수를 제한한다. 에이전트의 `PermissionError`는 HTTP 403, 값·후조건 오류는 HTTP 422로 바뀐다.

## 정상 경로와 실패 경로를 나눈 시험

`wellnessbox-rnd/tests/test_interim_workflow_contract.py`의 `test_ordered_workflow_runs_safety_candidate_evidence_optimization_then_plan`은 마그네슘 근거를 등록한 임시 데이터베이스를 사용한다. 저장 원장에는 `load_profile`, `verify_consent`, `check_safety`, `generate_candidates`, `lookup_evidence`, `optimize`, `start_plan`의 7단계가 남아야 한다. 최종 상태는 `PLAN_READY`, `plan_start_recorded=true`, `agent_steps`는 7건이다.

`test_ordered_workflow_stops_after_hard_safety_result`는 임신 상태를 넣어 `check_safety` 다음 `stop`으로 끝나는지 본다. `test_ordered_workflow_stops_before_optimization_when_evidence_is_missing`은 검색 결과가 없으면 `lookup_evidence` 뒤에 멈추고 추적에 `optimize`가 없는지 확인한다. `test_direct_optimization_before_evidence_is_rejected`는 초기 실행에서 최적화 도구를 직접 불러 `workflow_operation_not_allowed`가 나고 `agent_steps`가 0건인지 확인한다.

우회 회귀도 순서 보장의 일부다. `test_ordered_workflow_rejects_different_safety_candidates`는 안전검사에는 비타민D, 후보에는 마그네슘을 넣은 요청을 거부한다. `test_ordered_workflow_retry_returns_same_durable_trace`는 같은 실행을 다시 요청해 단계가 중복되지 않는지 본다. `test_same_idempotency_key_rejects_changed_payload`은 같은 키로 `max_items`만 바꾸는 재시도를 차단한다. `test_failed_tool_postcondition_releases_execution_claim`은 빈 후보로 실패한 실행이 다시 시도할 수 있는 상태로 돌아오는지 다룬다.

API 시험 `wellnessbox-rnd/tests/test_interim_api.py`의 `test_ordered_agent_workflow_endpoint_enforces_safety_to_plan_sequence`는 FastAPI `TestClient`로 `/v1/interim/agent/workflow`를 호출한다. 응답의 마지막 다섯 작업이 요구된 순서와 같고 최종 상태가 `PLAN_READY`인지 확인한다. 생성기 `wellnessbox-rnd/scripts/run_closed_loop_state_order_smoke.py`는 정상, 안전 차단, 근거 없음, 직접 이동 우회를 서로 다른 임시 데이터베이스에서 실행한다.

`wellnessbox-rnd/data/original_plan/evidence/op071_op072_closed_loop_state_order_smoke_v1.json`의 정상 추적은 요구된 5단계를 포함한 7단계로 `PLAN_READY`에 도착한다. 임신 사례는 안전검사 뒤 `STOPPED`, 근거 없음 사례는 근거 조회 뒤 `STOPPED`이며 둘 다 `plan_start_recorded=false`다. 직접 이동 오류는 `direct_agent_move_forbidden`이다. 이 JSON의 계약 목록은 후속 상태 확장 전 11개 상태·11개 작업이라 현재 전체 계약의 최신 목록으로 쓰지 않았지만, OP-072의 초기 다섯 단계와 세 중단 경로는 현재 코드와 일치한다.

## 운영 표기와 실제 입증 단계

매니페스트는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-072.json`을 연결해 `OPERATED`를 주장한다. 파일은 서명된 `ACTUAL` 로컬 세션 영수증이고 `covered_requirement_ids`에 OP-072를 포함한다. 그러나 실행 경로는 일반 `recommendation`이며 데이터베이스 변화량은 `recommendation_runs=1`, `recommendation_items=1`, `agent_runs=0`, `agent_steps=0`이다. 다섯 단계가 실제 세션에서 실행됐다는 원장이 없다.

등록 연기 시험은 `op072_proven_stage=IMPLEMENTED`, `service_integration_proven=false`, `production_operation_proven=false`라고 명시한다. 따라서 현재 단계는 `IMPLEMENTED`다. 로컬 코드, 단위 시험, FastAPI 내부 시험에서 순서와 중단 조건은 확인했다. 반면 실제 서비스가 `/agent/workflow`를 호출했는지, 운영 장애 뒤 재시도가 같은 7단계를 보존했는지, 공개 배포에서 단계별 `agent_steps`가 남았는지는 확인되지 않았다. `OPERATED`로 올리려면 `agent_runs`와 `agent_steps`가 증가하고 다섯 단계가 순서대로 기록된 실제 세션 영수증이 필요하다.
## 다음 행동을 결정하는 순서
Closed-loop는 추천 한 번을 자동화하는 기능이 아니라 상태를 다시 읽고 다음 작업을 정하는 흐름이다. 이 그룹은 상태 전이, 예약, 재평가, 이상사례 중단, 약사 검토와 주문 경계를 시간 순서로 확인한다.

`OP-072`는 “안전검사, 후보 생성, 근거 조회, 최적화, 계획 시작 순서를 강제한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=21`, `docs/context/original_plan.pdf#page=22`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/interim/agent.py`, `wellnessbox-rnd/apps/inference_api/routes/interim.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_interim_workflow_contract.py`, `wellnessbox-rnd/tests/test_interim_api.py`, `wellnessbox-rnd/scripts/run_closed_loop_state_order_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op071_op072_closed_loop_state_order_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-072.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-072.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
