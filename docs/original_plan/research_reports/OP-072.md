# OP-072 안전검사, 후보 생성, 근거 조회, 최적화, 계획 시작 순서를 강제한다.

순서 검증의 기준 파일은 `wellnessbox-rnd/data/original_plan/evidence/op071_op072_closed_loop_state_order_smoke_v1.json`이다. 이 증거에는 정상 완료뿐 아니라 안전 차단, 근거 없음, 순서 우회 실패가 각각 별도 실행 추적으로 남아 있다.

## 순서가 바뀌면 무엇이 위험한가

최적화를 먼저 실행하고 나중에 안전 검사를 붙이면 위험한 성분이 이미 후보나 계획에 들어갈 수 있다. 근거 조회 전에 조합을 확정하면 점수는 높지만 뒷받침할 자료가 없는 성분이 선택될 수 있다. 계획 시작을 단순 상태 변경으로 허용하면 앞 단계가 실패했는데도 복용 계획이 준비된 것처럼 기록될 수 있다. OP-072는 다섯 기능이 존재하는지만 묻지 않고, 반드시 안전검사→후보 생성→근거 조회→최적화→계획 시작 순서로 실행되도록 요구한다.

`src/wellnessbox_rnd/interim/agent.py`의 `execute_recommendation_workflow()`는 입력 내용에서 지문을 만든 뒤 같은 요청의 기존 실행이 있는지 먼저 찾는다. 새 실행이면 프로필 로드와 동의 확인을 마친 다음 안전 검사를 부른다. 안전 결과가 `BLOCK` 또는 `STOP_AND_ESCALATE`면 곧바로 `STOPPED`로 끝나며 후보 생성은 실행하지 않는다.

안전을 통과한 경우에만 후보를 만든다. 후보가 비면 중단하고, 후보가 있으면 승인된 근거 자료를 조회한다. 근거 식별자가 하나도 없거나 근거 본문에서 후보 성분을 뒷받침하지 못하면 최적화 전에 멈춘다. 뒷받침된 후보만 `optimize_regimen`에 전달하고, 최적화 결과와 근거 식별자를 함께 `start_plan`에 넘긴 뒤에야 `PLAN_READY`가 된다.

## 같은 후보와 근거를 유지하는 보호 장치

안전 검사에 넣은 성분 목록과 후보 생성에 넣은 성분 목록이 다르면 `safety_candidate_ingredients_mismatch`가 발생한다. 안전 검사는 마그네슘만 봤는데 후보 단계에서 비타민D를 끼워 넣는 식의 입력 변경을 막는 장치다. 직접 `optimize_regimen`을 부르면 현재 상태에서 허용되지 않은 작업이므로 `workflow_operation_not_allowed`로 끝난다.

각 도구는 결과의 `postcondition_success`가 false가 아닌지 본 뒤에만 다음 상태로 이동한다. 실행 중 오류가 나면 원장의 상태를 다시 `ACTIVE`로 돌리고 실패한 단계의 전이는 기록하지 않는다. 동일한 멱등 키에 같은 내용을 보내면 저장된 추적을 돌려주지만, 같은 키에 다른 최대 상품 수나 다른 안전 입력을 보내면 `workflow_idempotency_payload_conflict`로 거부한다. 재시도가 이전 실행의 의미를 바꾸지 못하게 한 것이다.

## 정상·차단·근거 없음 경로의 결과

등록 기준 실행의 정상 경로는 `load_profile`, `verify_consent` 뒤에 요구된 다섯 작업을 정확한 순서로 실행해 `PLAN_READY`에 도착했다. `plan_start_recorded`는 true였다. 같은 요청을 다시 보낸 결과는 실행 식별자만 제외하면 같았고, 저장된 추적을 재사용했다.

임신 상태를 넣은 안전 차단 사례는 `check_safety` 다음에 `stop`으로 끝났다. 후보 생성, 근거 조회, 최적화, 계획 시작은 실행되지 않았다. 승인된 근거 자료를 넣지 않은 사례는 후보 생성과 근거 조회까지 수행한 뒤 멈췄고 `plan_start_recorded=false`였다. 공개 상태 이동으로 바로 계획 준비 상태에 가려는 시도는 `direct_agent_move_forbidden`을 반환했다.

`wellnessbox-rnd/tests/test_interim_workflow_contract.py`는 이 세 경로와 순서 위반, 재시도, 입력 충돌을 다룬다. `wellnessbox-rnd/tests/test_interim_api.py`는 실제 FastAPI `TestClient`로 `/v1/interim/agent/workflow`를 호출해 마지막 다섯 단계가 요구 순서인지 확인한다. 등록 자료에서는 구현 중 어떤 실패가 먼저 발견됐고 어떤 수정이 뒤따랐는지 확인되지 않았다. 보고서에는 현재 시험에서 재현한 실패와 차단 결과만 적었다.

## 현재 단계와 실제 운영의 공백

로컬 구현과 API 시험은 순서 강제와 단계별 중단을 직접 보여 준다. 그러나 기준 증거는 `op072_proven_stage=IMPLEMENTED`, `service_integration_proven=false`, `production_operation_proven=false`라고 명시한다. 따라서 코드와 로컬 시험만 놓고 본 현재 단계는 `IMPLEMENTED`다.

manifest의 운영 경로 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-072.json`은 `data_class=ACTUAL`이고 서명 값이 포함된 로컬 추천 실행 영수증이다. 다만 그 세션은 `agent_runs=0`, `agent_steps=0`으로 기록돼 다섯 단계의 운영 실행 순서를 보여 주지 못한다. 실제 서비스 요청이 `/agent/workflow`를 통과하고 단계별 원장이 남는지, 운영 장애 뒤 재시도가 같은 순서를 보존하는지는 확인되지 않았다. 이 항목을 `OPERATED`로 올리려면 다섯 단계가 기록된 실제 세션 영수증과 서비스 호출 근거가 필요하다.
