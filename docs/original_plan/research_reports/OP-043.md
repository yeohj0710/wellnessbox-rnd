# OP-043 증상, 검사, 생활 습관, 식이 패턴이 후보 점수에 영향을 주게 한다.

## 요구사항과 변경 전 점수 구조

OP-043은 사용자가 입력한 증상, 검사값, 생활 습관, 식이 패턴을 실제 후보 정렬 점수에 반영하고, 어떤 입력이 몇 점을 더했는지 응답에서 확인할 수 있게 하는 요구사항이다. 각 점수는 적용 규칙, 버전, 출처, 주장, 제한 문구를 함께 가져야 하며 진단이나 효능 확률로 해석하면 안 된다.

변경 전 score_candidate는 카탈로그의 supported_symptoms와 preferred_signals가 입력과 맞는 수에 각각 8점과 6점을 곱했다. 검사값과 식이 패턴은 별도 점수 항목이 없었고, 증상·생활 습관 점수도 어떤 코드가 적용됐는지 응답에 남지 않았다. 총점은 계산됐지만 개별 입력에서 총점까지의 계산을 완전히 다시 맞추기 어려웠다.

manifest 경로는 data/original_plan/requirements_manifest_v1.json이다. OP-043의 claimed_stage는 IMPLEMENTED다. 구현과 테스트 파일, 저장 스모크의 소스 지문을 다시 대조한 결과 이 단계는 현재 파일 내용과 맞는다.

## 점수 규칙 자료와 검증기

data/rules/candidate_signal_scoring_rules_v1.json은 scoring_version=2026-07-16.1인 규칙 자료다. 증상 일치당 8점, 생활 신호 일치당 6점을 정의하고, 검사 3개와 식이 1개를 포함해 전체 10개의 구조화 규칙을 등록한다. 검사 규칙은 고혈당 범위의 soluble_fiber 4점, berberine 2점과 고중성지방 범위의 omega3 4점이다. vegan 등 채식 패턴은 energy_support 또는 general_wellness 목표의 vitamin_b_complex에 3점을 준다.

src/wellnessbox_rnd/knowledge/candidate_signals.py의 CandidateSignalScoringRegistry는 규칙 종류와 숫자 범위를 제한한다. validate_candidate_signal_registry는 스키마 버전, 적용 시각, 점수 의미, 정책 출처와 주장, 정확한 규칙 집합을 고정한다. 각 규칙의 성분이 카탈로그에 있고 목표가 그 성분 범위에 속하는지, 선언한 claim_id가 reference_id를 실제로 소유하는지, 주장의 domain_keys가 목표를 포함하는지 검사한다.

검증기는 제한 문구도 규칙별 고정 문자열과 비교한다. 따라서 검사 기준범위를 “진단”으로 바꾸거나, 약한 근거를 확정적 효능으로 고치는 변경은 자료 검증에서 실패한다. 내부 점수 정책 주장과 외부 임상·영양 주장을 함께 등록하되, 내부 정책을 임상 주장으로 위조하지 못하게 분리한다.

## 입력 정규화와 점수 계산 변경

src/wellnessbox_rnd/domain/intake.py는 증상 코드와 중증도, 생활 습관에서 파생한 신호, 식이 패턴, 최신 검사 관측값과 검사기관 기준범위에 따른 low·within·high 상태를 NormalizedIntake에 보존한다. 같은 검사 코드와 시각에 값이 충돌하면 거부하며, 검사 시각은 시간대가 있어야 한다. 숫자에는 불리언, NaN, 무한대를 허용하지 않고 μ·µ 표기를 포함한 단위를 정규화한다.

src/wellnessbox_rnd/efficacy/service.py의 score_candidate는 _symptom_signals, _lifestyle_signals, _laboratory_signals, _dietary_signals를 따로 만든다. 검사 규칙은 사용자가 제출한 reference_range를 기준으로 계산된 상태가 규칙과 맞을 때만 적용한다. 식이 규칙은 정규화된 패턴과 목표·성분 범위가 모두 맞아야 한다.

각 적용 결과는 src/wellnessbox_rnd/schemas/recommendation.py의 CandidateScoreSignal로 반환된다. source, code, observed_value, unit, points, rule_id, scoring_version, reference_ids, claim_ids, limitation이 들어간다. CandidateScoreBreakdown은 symptom_alignment, lifestyle_alignment, laboratory_alignment, dietary_alignment를 분리하고 applied_signals를 정렬해 보존한다. total에는 네 항목과 목표 prior, 근거 준비도, 예산·안전·보수 조정 등을 모두 한 번씩 더한다.

data/knowledge/runtime_knowledge_db_v1.json은 후보 신호 규칙 자료를 실행용 DB에 저장한다. src/wellnessbox_rnd/knowledge/runtime_db.py의 새 빌드 결과와 저장본이 다르면 검증이 실패하므로 규칙 JSON만 바꾸고 실행 자료를 갱신하지 않는 상태를 잡는다.

## 실패 사례와 정확한 회귀 검사

tests/test_candidate_signal_scoring.py의 test_candidate_signal_registry_is_evidence_linked_and_runtime_persisted는 10개 규칙, 근거 연결, 런타임 저장을 확인한다. test_candidate_signal_registry_rejects_forged_claim_and_unowned_reference와 test_candidate_signal_registry_rejects_unpinned_thresholds_and_genetic_tags는 다른 출처를 빌려 붙이거나 고정하지 않은 임계값·태그를 넣는 변경을 거부한다.

test_symptom_lifestyle_lab_and_dietary_terms_are_separate_and_auditable에서는 soluble_fiber 사례의 증상 8점, 생활 6점, 검사 4점이 서로 다른 적용 신호로 나뉘고 vegan 입력의 vitamin_b_complex는 3점이어야 한다. test_candidate_score_total_reconciles_every_visible_term은 응답에 보이는 모든 점수 항목의 합과 total이 같아야 한다고 정한다.

tests/test_diet_lifestyle_lab_input_contracts.py의 test_openapi_and_api_expose_structured_diet_lifestyle_lab_contract는 OpenAPI와 실제 API에서 구조화 입력을 노출한다. tests/test_recommendation_contracts.py의 test_recommendation_set_contract_rejects_component_signal_sum_mismatch는 구성 점수와 적용 신호 합계가 다른 추천 계약을 거부한다. 이 검사는 표시된 숫자와 내부 총점이 갈라지는 회귀를 막는다.

## manifest 등록 근거와 저장 스모크

구현 근거는 data/rules/candidate_signal_scoring_rules_v1.json, src/wellnessbox_rnd/knowledge/candidate_signals.py, src/wellnessbox_rnd/efficacy/service.py, src/wellnessbox_rnd/domain/intake.py, src/wellnessbox_rnd/schemas/recommendation.py, data/knowledge/runtime_knowledge_db_v1.json이다. 테스트 근거는 tests/test_candidate_signal_scoring.py, tests/test_diet_lifestyle_lab_input_contracts.py, tests/test_recommendation_contracts.py, scripts/run_candidate_signal_scoring_smoke.py, data/original_plan/evidence/op043_op044_candidate_signal_scoring_smoke_v1.json이다. manifest에 적힌 원문 경로의 하나는 wellnessbox-rnd/data/rules/candidate_signal_scoring_rules_v1.json이다. 모든 경로가 존재하고 등록 목적에 맞는 내용을 가진다.

저장 스모크는 증상 8점, 생활 6점, 검사 4점, 식이 3점을 기록하며 rule_count=10, scoring_version=2026-07-16.1, production_operation_proven=false다. 스크립트는 규칙 검증, 새 런타임 DB의 결정성, 저장본 일치, 점수 사례, 동의 거부 입력 제외를 확인하도록 작성되어 있다.

저장 결과의 source_identity.commit은 94b0374a3599973ba5201a3cc751912f07bb146a이고 source_sha256은 ab17bdd5807bd26121ea2e733861214e2cb5577405efa4b723e68ba932cce5e4다. 스모크 스크립트가 정한 SOURCE_PATHS로 다시 계산한 현재 지문도 ab17bdd5807bd26121ea2e733861214e2cb5577405efa4b723e68ba932cce5e4로 같다. commit 필드는 저장소 HEAD가 아니라 git log -1 -- SOURCE_PATHS의 결과를 저장하므로, 현재 HEAD 3814984dfccbd188282e5b3e1b02576a2fdc958a와 다른 것은 stale 판단 근거가 아니다. 저장 JSON은 현재 등록 소스 내용과 일치하며 production_operation_proven=false라는 한계도 그대로 남긴다.

## 현재 단계와 확인되지 않은 범위

현재 근거 단계는 IMPLEMENTED다. 네 입력 종류가 실제 score_candidate에 들어가고, 규칙·출처·제한·총점 계약 및 회귀 테스트가 존재한다. 저장 스모크의 관측값과 소스 지문도 현재 등록 코드와 맞는다. 다만 스모크는 구현 계산을 재현한 자료이지, 서비스 운영이나 외부 평가 근거가 아니다.

INTEGRATED 이상을 주장하려면 현재 소스에서 스모크를 다시 만들어 해시와 커밋을 갱신하고, 서비스 경로의 실제 응답에서도 applied_signals와 total을 확인해야 한다. 실제 사용자 운영 자료나 독립 평가 자료는 등록되어 있지 않다. 점수 8·6·4·3은 버전이 있는 후보 정렬 정책일 뿐 진단, 용량 권고, 치료 목표 또는 효능 확률을 입증하지 않는다.
