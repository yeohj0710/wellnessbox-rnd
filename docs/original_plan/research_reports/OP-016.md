# OP-016 검사값의 코드, 값, 단위, 기준범위, 측정시각을 구조화한다.

## 숫자 하나만으로는 검사 결과가 되지 않는다

원본 계획 16쪽은 건강검진과 마이데이터에서 들어오는 사용자 특성을 개인 특성 파라미터로 모으는 데이터 레이크를 제시한다. 검사값 `102`만 저장하면 혈당인지 다른 검사인지, mg/dL인지 mmol/L인지, 정상 범위가 무엇인지, 언제 측정했는지 알 수 없다. OP-016의 결과는 검사 code, 값, 단위, 기준범위, timezone이 있는 측정시각을 하나의 관측값으로 묶는 것이다. 최신 관측과 정상·낮음·높음 상태를 결정할 때도 이 다섯 요소를 함께 사용한다.

검사 결과는 의료기관과 시점에 따라 기준범위가 달라질 수 있다. 그래서 구현은 code별 전역 정상 범위를 새로 만들지 않고 각 관측에 reference range를 붙인다. 이 방식은 원본 값을 보존하면서 추천에 필요한 상태를 계산할 수 있다. 단위를 모르는 값을 임의 변환하거나 timezone이 없는 시각을 로컬 시각으로 추정하지 않는다. 애매한 입력은 요청 경계에서 거부한다.

## schema가 관측값의 최소 의미를 강제한다

`src/wellnessbox_rnd/schemas/recommendation.py`의 `LaboratoryObservationInput`은 code, 유한한 숫자 value, 정규화 가능한 unit, `LaboratoryReferenceRange`, timezone이 있는 `measured_at`을 요구한다. 기준범위는 low나 high 중 하나 이상이 있어야 하고, 둘 다 있으면 low가 high보다 클 수 없다. 값과 경계에는 `NaN`, 무한대, boolean을 허용하지 않는다. 측정시각은 timezone 정보가 없으면 실패한다.

단위는 공백과 표기를 canonical 형태로 정리한다. 예를 들어 `mg / dL`은 `mg/dL`이 된다. `mcg/L`, 그리스 문자 μ를 쓴 `μg/L`, 마이크로 기호를 쓴 `µg/L`은 모두 ASCII `ug/L`로 모인다. mol 단위도 같은 원칙을 적용한다. 구현이 지원하지 않는 단위는 조용히 통과시키지 않는다. 이 제한은 모든 임상 단위를 이미 지원한다는 뜻이 아니라, 현재 계산 경로가 이해하는 단위만 명확하게 받는다는 뜻이다.

같은 code와 같은 측정시각에 내용이 다른 관측 두 개가 들어오면 `RecommendationRequest`의 충돌 검사가 거부한다. 같은 순간의 HbA1c가 6.1과 5.2라고 동시에 기록된 입력에서 하나를 순서대로 덮어쓰지 않는다. 완전히 같은 관측은 중복으로 해석할 수 있지만 값, 단위 또는 기준범위가 다르면 오류다. 이 fail-closed 계약이 요청 순서에 따른 비결정성을 막는다.

## intake는 UTC 시각과 최신 관측을 만든다

`src/wellnessbox_rnd/domain/intake.py`의 `_normalize_laboratory_observations`는 code를 canonical text로 바꾸고 측정시각을 UTC로 정규화한다. 관측 목록은 안정된 순서로 유지되며, code별 최신 시각을 비교해 `latest_laboratory_observation_by_code`를 만든다. 값이 low보다 작으면 LOW, high보다 크면 HIGH, 범위 안이면 WITHIN_RANGE로 분류해 `laboratory_range_status_by_code`에 넣는다. 기준 한쪽만 있는 검사도 주어진 경계만 사용한다.

예시 fixture `data/samples/api_recommend_diet_lifestyle_lab_request_v1.json`에는 HbA1c 6.1%, 공복혈당 102mg/dL, 각각의 기준범위와 `2026-07-14T09:30:00+09:00` 시각이 들어 있다. intake에서는 시각이 `2026-07-14T00:30:00Z`로 보존되고 두 관측은 HIGH로 분류된다. 더 오래된 HbA1c가 함께 오면 최신 관측 6.1을 선택한다. 날짜나 목록 순서가 최신값 선택을 대신하지 않는다.

정규화된 검사 정보는 별도 병렬 모델이 아니라 기존 feature 경로로 전달된다. `src/wellnessbox_rnd/models/efficacy_model_v0.py`와 `src/wellnessbox_rnd/models/policy_model_v0.py`는 `laboratory::hba1c`, `laboratory_unit::fasting glucose::mg/dL`, `laboratory_status::hba1c::high` 같은 공통 feature를 읽는다. 혈당 목표가 있는데 관련 검사 관측이 없으면 intake가 `missing_glucose_context`를 남기고, fixture처럼 관련 관측이 있으면 그 결측 사유를 제거한다.

## API와 테스트가 경계 오류를 재현한다

`apps/inference_api/routes/recommend.py`는 구조화 검사 관측을 OpenAPI 요청 예제로 제공한다. 실제 `/v1/recommend` 요청도 같은 schema를 통과해야 한다. `tests/test_diet_lifestyle_lab_input_contracts.py`는 code, 값, 단위, low·high, UTC 시각, 최신 관측 선택, range status를 필드별로 비교한다. 잘못된 범위, 빈 범위, timezone 없는 시각, `NaN`, boolean 값을 각각 거부하는지도 검사한다.

같은 테스트는 동일 시각 충돌을 Pydantic 모델과 FastAPI 422 응답 양쪽에서 확인한다. 세 가지 micro 단위 표기가 하나의 ASCII 단위로 모이는지, 검사 feature가 efficacy와 policy 양쪽에 도달하는지, 관련 검사가 혈당 결측을 해소하는지, OpenAPI가 세 검사 schema를 노출하는지도 확인한다. `tests/test_unsupported_input_contracts.py`는 지원하지 않는 검사 단위가 모델과 API에서 함께 거부되는 경계를 보완한다.

## 구현 완료와 운영 완료를 구분한다

OP-016의 핵심 구현은 `93714c62` 커밋에서 OP-015와 같은 요청·intake 경로를 확장했다. 뒤이은 회귀 수정은 boolean 숫자와 단위 표기, 동일 시각 충돌처럼 공용 health input 경계를 더 엄격하게 만들었다. manifest는 schema, intake, 두 모델 feature builder, API route, fixture와 계약 테스트를 구현 증거로 등록한다. canonical manifest 감사는 파일 소유자, 경로 탈출, 존재, Git 추적 여부를 검사한다. completion generator는 required `IMPLEMENTED`와 claimed `IMPLEMENTED`가 일치하고 감사 issue가 없어 OP-016을 COMPLETE로 판정한다.

이 단계는 검사기관 연동이나 production 운영을 뜻하지 않는다. 검사 code가 국제 표준 코드 체계와 외부에서 매핑됐다는 증거도 아니고, 모든 임상 단위를 지원한다는 주장도 아니다. 실제 서비스 통합에는 동의가 확인된 source payload, 운영 중 단위·code 매핑, 호출 결과 receipt가 더 필요하다. 이번 보고서 backfill은 서비스 코드, production 환경, 데이터셋 내용, 학습, 모델 artifact, simulation을 바꾸지 않았다. 공식 frozen evaluation 256건의 일곱 지표와 replay·slice delta도 0이다.
## 입력값을 먼저 고정한 이유
이 그룹에서 입력을 세분화한 이유는 값 하나를 편의상 문자열로 받으면 안전 판단과 효과 해석이 서로 다른 의미를 사용할 수 있기 때문이다. 단위, 누락, 지원하지 않는 입력, 동의 범위를 먼저 고정해야 뒤의 계산과 차단 결과를 설명할 수 있다.

`OP-016`는 “검사값의 코드, 값, 단위, 기준범위, 측정시각을 구조화한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=13`, `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/models/efficacy_model_v0.py`, `wellnessbox-rnd/src/wellnessbox_rnd/models/policy_model_v0.py` 외 2개
- 테스트·실행: `wellnessbox-rnd/tests/test_diet_lifestyle_lab_input_contracts.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
