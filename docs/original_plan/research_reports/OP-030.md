# OP-030 wellnessbox 화면에서 세션 저장 건수와 replay 결과를 조회한다.

## replay 기능은 화면에서 상태를 읽을 수 있어야 쓸 수 있다
API가 있어도 운영자가 저장 세션 수와 최근 replay 결과를 보지 못하면 재현성 문제를 발견하기 어렵다. OP-030은 R&D 데이터베이스를 브라우저에 직접 연결하라는 요구가 아니다. WellnessBox 서버가 내부 인증으로 R&D API를 호출하고, 화면에는 제한된 집계와 일치 상태만 전달하는 구조가 필요하다.

원본 계획 16쪽은 사용자 인터페이스, 도메인 데이터 레이크와 엔진 결과가 연결되는 모습을 그린다. 현재 구현은 이 연결을 `/tips`의 interim console 안에 넣었다. 다만 화면 코드가 존재한다는 사실과 실제 운영 환경에서 R&D 서버가 연결돼 사용됐다는 사실은 구분한다. 이 보고서는 전자를 증명하고 후자는 남은 조건으로 둔다.

## 서비스 서버가 R&D API의 경계를 맡는다
`lib/server/wb-rnd-interim-client.ts`는 고정된 허용 operation만 R&D 서버로 보낸다. base URL, enabled flag, 내부 token과 timeout을 환경 변수에서 읽고 `cache: no-store`로 호출한다. browser component는 token이나 R&D 주소를 알지 못한다. GET 요청은 503과 timeout 같은 재시도 가능 실패에 한해 최대 두 번만 시도하며, POST replay는 중복 실행을 피하려고 한 번만 보낸다.

`lib/server/tips-lab/rnd-session-replay.ts`는 R&D snake_case 응답을 화면용 camelCase contract로 바꾼다. 단순 type assertion으로 믿지 않고 total, replayable, unavailable count가 서로 맞는지, item 수가 20 이하인지, execution ID 형식과 replay status가 허용값인지 검사한다. `MATCH`, `MISMATCH`, `VERSION_MISMATCH`와 input·version·output flag의 조합도 일관돼야 한다.

응답이 깨졌거나 HTTP 오류·timeout이 발생하면 원 payload를 화면까지 전달하지 않는다. 목록은 `UNAVAILABLE`, 기능이 꺼졌으면 `DISABLED`를 반환한다. replay도 연결 여부와 availability를 제한된 구조로 돌려준다. 이 fail-closed adapter 덕분에 UI는 잘못된 응답을 성공 결과로 표시하지 않는다.

## runtime action이 목록과 replay를 한 경로로 묶는다
`lib/server/tips-lab/runtime.ts`는 `list_rnd_sessions`와 `replay_rnd_session` action을 등록한다. 목록 action은 현재 UI state와 `rndSessions`를 함께 반환한다. replay action은 선택된 execution ID로 replay를 호출한 뒤 목록을 다시 읽어 마지막 상태와 replay run count를 갱신한다. 화면별 임시 fetch를 추가하지 않고 기존 TIPS lab action 경로를 재사용한 선택이다.

execution ID는 adapter와 runtime 양쪽 계약에서 제한된다. 빈 값이나 `exec_` 뒤 32자리 hex 형식이 아닌 값은 R&D 서버로 보내기 전에 거절한다. 서비스가 disabled 상태면 네트워크 요청 자체를 하지 않는다. 연결 오류를 무시하고 빈 성공 목록으로 바꾸지 않고 `DISABLED`와 `UNAVAILABLE`을 구분해 운영자가 설정 누락과 장애를 다르게 볼 수 있게 한다.

## 화면은 건수와 세 가지 일치 상태를 보여준다
`components/tips/InterimUserConsole.tsx`의 저장 세션 영역은 전체 저장 세션, replay 가능, replay 불가, 누적 replay 실행 수를 표시한다. 최근 세션 selector에는 생성 시각과 마지막 상태를 보여주며 replay 가능한 항목만 선택 대상으로 쓴다. 사용자는 `저장 세션 다시 조회`와 `선택 세션 재생` 버튼으로 action을 실행한다.

최근 결과 영역은 입력 일치, 실행 버전 일치, 추천 결과 일치를 따로 보여준다. version mismatch로 추천을 실행하지 않았으면 출력 상태를 `실행 안 함`으로 표시한다. 이를 단순 실패나 결과 불일치와 섞지 않는다. 연결이 꺼졌을 때는 R&D 서버 주소와 내부 인증 설정이 필요하다고 안내하고, 응답 장애일 때는 잠시 뒤 다시 조회하라는 복구 행동을 제공한다.

화면에는 health payload, 저장 request JSON, 추천 원문, 내부 token과 mismatch hash 전체를 노출하지 않는다. 세션 ID, 시각, 가용 여부와 일치 flag만 필요 범위로 보여준다. 운영자가 더 깊은 원인을 조사하려면 보호된 R&D endpoint와 audit evidence를 사용해야 한다.

## 서비스 QA는 정상·오류 계약을 실제 HTTP로 확인한다
`scripts/qa/check-tips-rnd-session-replay.cts`는 localhost HTTP server를 만들고 실제 service adapter가 GET 목록과 POST replay를 호출하게 한다. token 전달, 정상 count와 `MATCH` 변환, 잘못된 execution ID의 사전 거절, malformed 목록, 일관되지 않은 replay 응답, invalid JSON, 503, timeout과 disabled 상태를 검사한다.

이번 loop에서 이 QA가 실제 전체 요청 9건을 만들면서 과거 기대값 7건과 충돌했다. 원인은 shared client에 추가된 bounded GET retry를 QA가 반영하지 않은 것이다. 테스트를 전체 9건으로 고치고 그중 GET이 7건인지도 명시했다. 정상·malformed·invalid JSON은 각 1건, 503과 timeout은 각 2건이고 POST replay는 정상·불일치 각 1건이다. 서비스 구현은 바꾸지 않았으며 회귀 검증만 현재 계약에 맞췄다.

`scripts/qa/check-tips-interim-modules.cts`는 feature flag, 고정 server proxy, HMAC 가명화, 역할 인증, timeout 시 no-store, 안전 판단 fail-closed, simulation 고지와 replay module 연결을 정적 검사한다. 두 OP-030 관련 QA는 최종 실행에서 통과했다. 범용 `qa:tips:web-lab`은 PRO 화면의 다른 문구 기대값 때문에 실패했으며 session replay 경로의 실패가 아니다. 이번 좁은 loop에서는 사용자 소유 작업과 충돌할 수 있는 unrelated 문구를 고치지 않았다.

## R&D smoke는 서비스 화면 전체를 실행한 증거가 아니다
canonical 파일 `data/original_plan/evidence/op029_op030_session_replay_service_ui_smoke_v1.json`은 R&D FastAPI route 네 건과 화면에 필요한 contract를 검증한다. 저장 세션 1개, replay 가능 1개, visible item 1개와 replay run 2개를 기록하고 raw health payload가 반환되지 않았음을 확인한다. schema 14 evidence SHA-256은 `65d55171560922f63fa4b591bf358498f3f4e969771a08edfb7ca3bb2812905f`다.

하지만 이 smoke는 Next.js 앱을 띄워 실제 브라우저에서 버튼을 누른 end-to-end 증거가 아니다. 서비스 adapter와 UI module은 별도 QA로 확인한다. 더구나 현재 로컬 WellnessBox에는 사용자가 진행 중인 주소·QA 안전성 변경이 있어 이를 보존했다. OP-030 관련 clean 파일 하나만 고쳐 commit `a94d51a`로 push했다.

## 저장 건수는 운영 KPI가 아니라 관측값이다
화면의 total·replayable·unavailable 수는 현재 R&D database의 row count다. 특정 기간의 성공률, 사용자 수 또는 production 전체 세션 수를 의미하지 않는다. 최근 목록은 최대 20건이고 server summary limit 기본값도 20이다. pagination이나 기간 filter, 운영 alert는 아직 없다.

replay `MATCH`도 추천 품질 합격을 뜻하지 않는다. 같은 입력·버전에서 canonical 결과가 같았다는 뜻이다. `VERSION_MISMATCH`는 현재 조건이 달라 추천 실행을 생략했다는 뜻이고, `MISMATCH`는 같은 version 조건에서 출력 필드가 달랐다는 뜻이다. 화면은 이 세 상태를 보여주지만 원인 분석과 조치 workflow를 자동화하지 않는다.

## 현재 단계는 IMPLEMENTED이며 OPERATED는 아니다
서비스 adapter, runtime action, UI 표시, localhost QA와 R&D canonical smoke가 있으므로 manifest의 claimed stage `IMPLEMENTED`는 증명된다. 그러나 Group C의 required stage는 `OPERATED`다. production `/tips`에서 실제 R&D 설정이 활성화되고 승인된 사용자가 저장 건수와 replay 결과를 조회했다는 배포·접근·관측 receipt가 없다. 따라서 OP-030의 현재 판정은 `IMPLEMENTED / PARTIAL`이다.

운영 단계로 올리려면 승인된 배포에서 내부 URL·token이 안전하게 주입되고 브라우저 역할 인증을 거쳐 목록과 replay가 동작해야 한다. 실제 화면 capture만으로는 부족하며 R&D run ID, 서비스 deployment, 조회 시각, count, replay status와 오류 대응을 연결한 receipt가 필요하다. 공개 배포나 인증정보 변경은 승인이 필요하므로 이번 loop에서는 수행하지 않았다.

## 이번 변경과 다음 완료 조건
핵심 화면 연결은 service commit `6adf202`, R&D replay는 `8727853`에서 도입됐다. 이번 loop는 R&D evidence 현재성 테스트와 schema 14 재생성, 서비스 QA의 GET retry 기대값만 보완했다. 원천·frozen·학습 데이터, 모델, 추천·simulation 로직은 변경하지 않았다.

공식 frozen evaluation 256건과 일곱 지표의 입력이 그대로이므로 metric delta는 0이다. replay와 weakest-slice 평가 입력도 바뀌지 않아 의미 delta는 0이다. OP-030을 완료하려면 실제 운영 환경의 장기 관측과 receipt가 필요하고, 전체 goal에는 별도로 남은 연구보고서와 stage gap, OP-039 외부 검증, 최종 validation·independent-review receipt가 남는다.
## 데이터가 남는 방식
데이터를 저장하는 것만으로는 연구 근거가 남지 않는다. 이 그룹은 원문과 파싱 구간, 입력 버전, 동의, 실행 ID, 규칙과 결과를 이어 붙여서 누가 어떤 자료를 사용했는지 다시 따라갈 수 있게 만든다.

`OP-030`는 “wellnessbox 화면에서 세션 저장 건수와 replay 결과를 조회한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=16`
- 구현·설계: `wellnessbox-rnd/apps/inference_api/routes/interim.py`, `wellnessbox/lib/server/wb-rnd-interim-client.ts`, `wellnessbox/lib/server/tips-lab/rnd-session-replay.ts`, `wellnessbox/lib/server/tips-lab/runtime.ts` 외 2개
- 테스트·실행: `wellnessbox-rnd/tests/test_session_replay.py`, `wellnessbox-rnd/data/original_plan/evidence/op029_op030_session_replay_service_ui_smoke_v1.json`, `wellnessbox/scripts/qa/check-tips-rnd-session-replay.cts`, `wellnessbox/scripts/qa/check-tips-interim-modules.cts` 외 1개
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-030.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-030.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
