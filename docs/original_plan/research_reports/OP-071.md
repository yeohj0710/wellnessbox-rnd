# OP-071 상태, 허용 작업, 금지 전이를 단일 R&D 계약으로 통합한다.

manifest에 등록된 구현 증거 `wellnessbox-rnd/src/wellnessbox_rnd/interim/workflow_contract.py`는 상태와 작업의 관계를 `_ORDERED_TRANSITIONS` 한 곳에 선언한다. 등록 시험 증거 `wellnessbox-rnd/data/original_plan/evidence/op071_op072_closed_loop_state_order_smoke_v1.json`은 이 계약으로 초기 추천 절차를 재생한 기록이다.

## 여러 상태표를 하나로 모아야 한 이유

상태 목록, 화면의 허용 버튼, 실제 함수의 이동 규칙이 따로 관리되면 같은 상태에서 서로 다른 행동이 가능해질 수 있다. 예를 들어 화면은 계획 시작을 막지만 내부 함수는 바로 `PLAN_READY`로 이동하거나, 안전 검사를 마치지 않았는데 최적화가 실행될 수 있다. OP-071은 상태 이름만 한 파일에 모으는 요구가 아니다. 현재 상태에서 어떤 작업을 할 수 있고 그 작업 뒤 어느 상태로 가는지를 한 계약에서 계산하게 한다.

현재 계약은 초기 입력부터 완료까지의 상태와 복용 뒤 재평가 상태를 함께 다룬다. 초기 절차에는 `INTAKE`, `CONSENT_CHECK`, `PROFILE_READY`, `SAFETY_CHECK`, `RANKING`, `EVIDENCE_RETRIEVAL`, `REGIMEN_OPTIMIZATION`, `PLAN_READY`가 있다. 후속 처리에는 `FOLLOWUP_ACTIVE`, 검토 보류, 유지, 재최적화, 감량, 교체, 에스컬레이션 상태가 있으며 마지막은 `STOPPED` 또는 `COMPLETED`다. 각 작업은 `ClosedLoopOperation`에 고정돼 자유 문자열을 실행하지 않는다.

`CLOSED_LOOP_ALLOWED_OPERATIONS_V1`과 `CLOSED_LOOP_TRANSITIONS_V1`은 별도 표를 손으로 복사한 값이 아니다. 둘 다 `_ORDERED_TRANSITIONS`에서 만들어진다. 상태가 추가되거나 전이가 바뀌면 허용 작업 목록과 목표 상태 목록이 함께 달라진다. 이 방식은 같은 규칙을 세 군데 수정하다 한 곳을 빠뜨리는 위험을 줄인다.

## 에이전트가 계약을 우회하지 못하게 한 방식

`src/wellnessbox_rnd/interim/agent.py`는 도구 이름을 계약 작업에 연결한다. 도구를 실행하기 전에 현재 상태의 허용 작업인지 먼저 보고, 허용되지 않으면 `workflow_operation_not_allowed`로 중단한다. 작업 결과가 성공 조건을 충족한 뒤에만 `agent_steps`에 지문과 사유를 기록하고 다음 상태로 옮긴다. 실패한 도구는 실행 중 표시를 풀어 다시 시도할 수 있게 하지만 상태를 앞당기지 않는다.

공개 `move()` 함수는 항상 `direct_agent_move_forbidden`을 낸다. 내부 이동도 작업과 목표 상태를 함께 `apply_closed_loop_transition_v1()`에 넘겨야 한다. 예상 목표와 다르면 `forbidden_closed_loop_transition`이 발생한다. 이 제한 때문에 호출자가 상태 이름만 지정해 안전 검사나 근거 조회를 건너뛸 수 없다.

종료 상태에는 허용 작업이 없다. 실행 추적 자료도 첫 단계가 `INTAKE`에서 시작하는지, 앞 단계의 도착 상태와 다음 단계의 출발 상태가 이어지는지, 마지막 상태가 전체 상태와 같은지 다시 본다. `start_plan` 작업이 실제 단계에 있을 때만 `plan_start_recorded=true`가 허용된다.

## 시험과 등록 증거가 보여 주는 것

`wellnessbox-rnd/tests/test_interim_workflow_contract.py`는 모든 상태가 허용 작업표와 전이표에 들어 있는지 확인한다. `PROFILE_READY`에서 계획 시작을 시도하는 금지 전이, 끊어진 실행 추적, 거짓 계획 시작 표시, 종료 뒤 추가 작업, 직접 상태 이동도 각각 거부한다. 같은 요청을 다시 실행하면 새 원장을 만들지 않고 저장된 7단계 추적을 반환한다.

등록 기준 실행은 당시 계약의 11개 상태와 11개 작업을 저장했고, 성공·안전 차단·근거 없음·직접 이동 우회 네 경로를 실행했다. 이후 현재 소스에는 후속 의사결정 상태와 작업이 추가됐으므로 등록 증거의 계약 목록은 최신 소스 전체를 열거하지 않는다. 현재 회귀 시험은 확장된 열거형에서 표가 빠지지 않는지 직접 계산한다. 과거 구현 오류와 수정 순서는 등록 파일에서 확인되지 않았고, 현재 금지 전이 시험으로 우회 실패를 확인했다.

## 운영 영수증과 보수적 단계 판단

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-071.json`을 운영 증거로 등록했다. 이 파일은 `data_class=ACTUAL`이고 서명 값이 포함된 로컬 세션 영수증이며, `recommendation` 실행 경로의 요구사항 목록에 OP-071을 포함한다. 그러나 같은 영수증의 변화량은 `recommendation_runs=1`, `recommendation_items=1`인 반면 `agent_runs=0`, `agent_steps=0`이다. 따라서 이 영수증만으로 상태·작업 계약을 실제 세션에서 통과했다고 독립적으로 재구성할 수 없다.

등록 기준 실행도 `op071_proven_stage=IMPLEMENTED`, `production_operation_proven=false`, `service_integration_proven=false`라고 경계를 적었다. 이에 따라 이 보고서의 보수적 판단은 `IMPLEMENTED`다. 로컬 코드와 시험에서 단일 계약 및 우회 차단은 확인했다. 실제 운영 세션의 `agent_runs`와 `agent_steps`에 상태 전이가 남는지, 공개 서비스가 같은 계약을 사용하는지는 확인되지 않았다. manifest의 `OPERATED` 표기는 운영 행위와 요구사항을 연결한 범용 매핑에 의존하므로, 상태 전이 원장이 있는 운영 영수증으로 보강해야 한다.
