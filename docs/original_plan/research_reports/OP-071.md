# OP-071 상태, 허용 작업, 금지 전이를 단일 R&D 계약으로 통합한다.

## 하나의 계약이 필요한 이유

상태 목록, 작업별 허용 조건, 실제 상태 이동 규칙을 한 곳에서 계산해야 한다. 세 표를 따로 유지하면 화면이나 에이전트가 허용한 작업과 저장 원장이 기록한 전이가 달라질 수 있다. OP-071은 상태 이름을 열거하는 데 그치지 않고, `(현재 상태, 작업) → 다음 상태`를 단일 기준으로 삼아 허용 작업표와 허용 전이표를 파생하도록 요구한다.

통합 전 `src/wellnessbox_rnd/interim/agent.py`에는 `AgentState`와 `TRANSITIONS`가 직접 선언돼 있었다. 당시 표는 `PROFILE_READY`에서 근거 조회로 먼저 이동하고 그 뒤 안전검사를 허용했다. 작업 이름과 전이의 관계도 별도 자료가 아니어서 목표 상태만 지정하는 `move()`가 전이의 의미를 대신했다. 커밋 `ecb3540`은 이 상태 열거형과 이동 규칙을 새 `workflow_contract.py`로 옮기고, 안전검사 뒤 후보 생성과 근거 조회로 이어지는 순서를 하나의 `_ORDERED_TRANSITIONS`에 선언했다.

## 계약에서 파생되는 상태와 작업

`wellnessbox-rnd/src/wellnessbox_rnd/interim/workflow_contract.py`에는 현재 17개 `ClosedLoopState`와 17개 `ClosedLoopOperation`이 있다. 초기 추천 절차는 `INTAKE`, `CONSENT_CHECK`, `PROFILE_READY`, `SAFETY_CHECK`, `RANKING`, `EVIDENCE_RETRIEVAL`, `REGIMEN_OPTIMIZATION`, `PLAN_READY` 순으로 이동한다. 후속 절차에는 `FOLLOWUP_ACTIVE`, `FOLLOWUP_REVIEW`, 계획 유지·재최적화·감량·교체, `ESCALATED` 상태가 추가됐고 최종 상태는 `STOPPED` 또는 `COMPLETED`다.

모든 정상 이동은 `_ORDERED_TRANSITIONS`의 `(ClosedLoopState, ClosedLoopOperation)` 키 한 곳에 적혀 있다. `CLOSED_LOOP_ALLOWED_OPERATIONS_V1`은 같은 사전에서 현재 상태별 작업을 모으고, `CLOSED_LOOP_TRANSITIONS_V1`은 목표 상태를 모은다. 별도의 복사본을 손으로 갱신하지 않는다. 커밋 `3e6b7db`가 후속 의사결정 상태 여섯 개와 작업 여섯 개를 추가했을 때도 이 사전만 확장됐고 두 파생 표는 자동으로 새 항목을 포함했다.

`apply_closed_loop_transition_v1()`은 현재 상태와 작업으로 기대되는 목표를 찾고, 호출자가 제시한 목표가 다르면 `forbidden_closed_loop_transition:<state>:<operation>:<target>`을 낸다. 종료 상태는 `_ORDERED_TRANSITIONS`의 출발점으로 등록되지 않으므로 허용 작업과 목표 상태가 모두 빈 집합이다. `closed_loop_contract_snapshot_v1()`은 상태·작업·두 파생 표·종료 상태를 정렬된 JSON 자료로 내보낸다.

## 에이전트 우회 가능성을 고친 과정

커밋 `403afec`은 도구를 계약 작업에 연결하고 순서가 정해진 추천 실행기를 추가했다. 그러나 그 시점의 공개 `move()`는 작업을 받더라도 `_move_with_operation()`을 그대로 호출했다. 도구의 성공 조건을 통과하지 않고도 올바른 작업 이름과 목표 상태만 알면 상태를 바꿀 수 있었다. 실행 추적도 일반 사전이어서 끊어진 상태 연결이나 거짓 `plan_start_recorded` 값을 구조적으로 거부하지 못했다.

커밋 `48b314c`는 공개 `move()`가 항상 `direct_agent_move_forbidden`을 내도록 바꿨다. 내부 이동만 `apply_closed_loop_transition_v1()`을 통과할 수 있다. 같은 수정에서 `ClosedLoopExecutionStepV1`과 `ClosedLoopExecutionTraceV1`이 추가됐다. 각 단계는 계약에 있는 전이인지 확인하고, 전체 추적은 첫 상태가 `INTAKE`인지, 앞 단계의 도착과 다음 단계의 출발이 이어지는지, 마지막 상태가 실행 상태와 같은지, 실제 `start_plan` 단계와 `plan_start_recorded`가 일치하는지 검사한다.

동시 실행에서도 계약을 건너뛰지 않도록 후속 수정이 이어졌다. 커밋 `3a4e452`는 `agent_runs.status`를 `ACTIVE`에서 `EXECUTING`으로 조건부 변경해 한 실행을 한 작업자만 점유하게 했다. 커밋 `26941e9`는 도구 결과의 `postcondition_success`가 false이거나 예외가 나면 점유 상태를 `ACTIVE`로 되돌리도록 고쳤다. 성공한 작업만 `agent_steps`에 입력·결과 지문과 사유를 남기고 상태를 이동한다.

`wellnessbox-rnd/src/wellnessbox_rnd/interim/agent.py`의 `_TOOL_OPERATIONS`는 공개 도구 이름을 계약 작업으로 바꾼다. `_execute_tool_serialized()`는 현재 상태의 `CLOSED_LOOP_ALLOWED_OPERATIONS_V1`에 작업이 없으면 `workflow_operation_not_allowed`로 중단한다. 동의 확인과 중단처럼 도구 호출이 아닌 내부 작업도 `_record_internal_operation()`이 `agent_steps`에 기록한다. 같은 요청의 재시도는 저장된 작업 목록에서 계약 전이를 다시 구성해 동일한 실행 추적을 반환한다.

## 회귀 시험과 기준 파일의 시점 차이

`wellnessbox-rnd/tests/test_interim_workflow_contract.py`의 `test_closed_loop_contract_has_one_complete_state_and_operation_registry`는 모든 현재 상태가 허용 작업표와 전이표에 들어 있고 `manual_review`, `human_handoff` 작업이 없음을 확인한다. `test_closed_loop_contract_rejects_forbidden_transition`은 `PROFILE_READY`에서 `START_PLAN`으로 가는 이동을 거부한다. `test_execution_trace_rejects_discontinuous_or_false_plan_start`는 끊어진 두 단계와 거짓 계획 시작 표시를 각각 실패시킨다. `test_closed_loop_terminal_states_allow_no_operations`는 두 종료 상태에서 추가 작업이 불가능한지 본다.

우회와 내구성 시험도 따로 있다. `test_public_move_cannot_bypass_tool_execution`은 공개 이동에서 `direct_agent_move_forbidden`을 기대한다. `test_ordered_workflow_retry_returns_same_durable_trace`는 같은 요청을 두 번 실행해 `agent_runs` 1건과 `agent_steps` 7건만 남고 두 추적이 같은지 확인한다. `test_same_idempotency_key_rejects_changed_payload`은 같은 키로 최대 상품 수를 바꾸면 `workflow_idempotency_payload_conflict`가 나는지 본다. `test_failed_tool_postcondition_releases_execution_claim`은 후보가 비어 실패한 뒤 실행 상태가 `ACTIVE`로 복구되는지 확인한다.

등록 기준 `wellnessbox-rnd/data/original_plan/evidence/op071_op072_closed_loop_state_order_smoke_v1.json`은 성공, 안전 차단, 근거 없음, 직접 이동 우회 네 사례를 저장했다. 다만 이 파일은 후속 상태 확장 전의 11개 상태와 11개 작업을 담는다. 현재 소스의 17개 상태·17개 작업 전체를 열거하는 최신 기록이 아니다. 보고서가 이 JSON을 현재 계약 목록의 완전한 증거로 사용하면 내용 불일치가 된다. 현재 전체 등록 여부는 위 회귀 시험과 소스에서 확인했고, JSON은 초기 추천 절차와 우회 차단을 재현한 역사적 기준으로만 사용했다.

## 매니페스트 주장보다 낮게 판단한 단계

`data/original_plan/requirements_manifest_v1.json`은 OP-071을 `OPERATED`로 적고 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-071.json`을 운영 근거로 연결한다. 운영 영수증은 `data_class=ACTUAL`, 로컬 연구 PC의 세션 시간, 두 저장소 커밋, 서명 값을 갖고 있다. 그러나 실행 경로는 `recommendation` 하나이고 변화량은 `recommendation_runs=1`, `recommendation_items=1`인 반면 `agent_runs=0`, `agent_steps=0`이다.

이 영수증의 `covered_requirement_ids`에 OP-071이 들어간 이유는 `operational_action_coverage_v1.json`이 일반 추천 행위를 OP-071과 연결하기 때문이다. 상태·작업 계약을 실제로 거쳤다는 단계별 원장은 없다. 등록 연기 시험도 `op071_proven_stage=IMPLEMENTED`, `service_integration_proven=false`, `production_operation_proven=false`라고 경계를 명시한다. 따라서 현재 증거 단계는 보수적으로 `IMPLEMENTED`다. 코드와 로컬 회귀 시험에서 단일 계약과 우회 차단은 확인했지만, 실제 세션의 `agent_runs`·`agent_steps`와 공개 서비스가 같은 계약을 사용했다는 사실은 확인되지 않았다.
