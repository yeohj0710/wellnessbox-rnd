# OP-010 원본 요구사항 100% 감사 보고서를 manifest에서 자동 생성한다.

## 100%는 요구사항 포함률이지 완료율이 아니다

OP-010이 요구하는 실제 결과는 원본 계획의 OP-001부터 OP-120까지 단 하나도 빠뜨리지 않고, 각 항목의 required stage와 claimed stage, 증거와 판정을 같은 규칙으로 보여 주는 보고서다. 여기서 “100% 감사”는 120개 요구사항을 120개 모두 inventory에 포함한다는 뜻이다. 현재 120개가 모두 required stage를 충족한다는 뜻이 아니다. 보고서가 `원계획 요구사항 포함: 120/120건`과 함께 COMPLETE, PARTIAL, PENDING, EXTERNAL, CONTRADICTED 수를 따로 표시하는 이유다.

원본 PDF에는 기능 목록뿐 아니라 KPI 수식, 최소 표본, 서비스·상담·안전·센서 연동 조건이 섞여 있다. manifest에 120개 ID를 만들었어도 사람이 수동으로 상태 문서를 고치면 누락, 숫자 불일치, 근거 없는 승격이 생길 수 있다. OP-010은 OP-007의 단계 어휘와 OP-008·009의 감사 결과를 입력으로 받아 같은 manifest에서 JSON과 한국어 Markdown을 결정적으로 생성한다. 별도 완료 데이터베이스나 두 번째 상태 원장을 만들지 않는다.

## 생성기는 감사가 통과한 manifest만 받는다

핵심 구현은 `src/wellnessbox_rnd/governance/original_plan_report.py`다. `build_original_plan_completion_report_v1`은 materialize된 manifest와 `OriginalPlanAuditReportV1`을 입력으로 받는다. 먼저 audit schema version, requirement count, canonical manifest SHA-256이 현재 manifest와 일치하는지 확인한다. 감사 이후 manifest가 바뀌었거나 다른 manifest의 audit를 섞으면 `audit_manifest_sha256_mismatch` 같은 오류로 중단한다. 오래된 PASS 결과를 새 요구사항에 재사용할 수 없다.

보고서 모델은 strict Pydantic 계약을 사용한다. 최상위에는 schema version, 생성 시각, 원본 path와 SHA-256, manifest hash, audit status, 120개 요구 수, disposition 집계, 그룹 집계, 전 요구사항 레코드와 global issue가 들어간다. 각 레코드는 OP ID, 제목, 그룹, source refs, owners, required stage, claimed stage, disposition, reasons와 등록된 evidence를 보존한다. 보고서가 상태 숫자만 남기지 않고 각 판단을 원본 요구와 파일 근거로 되짚을 수 있게 한다.

## 다섯 판정은 단계 차이와 감사 실패를 분리한다

판정값은 `COMPLETE`, `PARTIAL`, `PENDING`, `EXTERNAL`, `CONTRADICTED` 다섯 가지다. `IMPLEMENTED`, `INTEGRATED`, `OPERATED`에는 명시적인 rank 1, 2, 3을 사용한다. claimed rank가 required rank 이상이고 관련 감사 issue가 없으면 COMPLETE다. 유효한 claimed stage는 있지만 required stage보다 낮으면 PARTIAL이다. claimed stage 자체가 없으면 PENDING이다.

`EXTERNAL`은 rank 4처럼 비교하지 않는다. required stage나 claimed stage가 외부 검증을 요구하면 별도 EXTERNAL 판정으로 남긴다. 내부 코드와 운영 증거가 독립 기관의 receipt를 자동 대체할 수 없기 때문이다. 현재 OP-039가 이 범주다. EXTERNAL이라는 판정은 외부 검증 완료가 아니라 외부 의존성이 남았음을 표시한다.

감사기가 특정 요구사항의 missing, untracked, owner mismatch 또는 계약 오류를 발견하면 그 항목은 CONTRADICTED다. 반면 원본 PDF hash 불일치처럼 전체 audit의 신뢰 기반이 깨지는 global issue가 있으면 claimed stage가 있는 모든 119건을 CONTRADICTED로 판정한다. 원본이 달라진 상태에서 개별 파일이 존재한다는 이유로 완료 숫자를 유지하지 않는 fail-closed 규칙이다.

## 국소 오류와 전역 오류를 서로 다른 테스트로 고정했다

`tests/test_original_plan_completion_report.py`는 현재 manifest와 실제 repository roots로 보고서를 만들고 120건 전부 포함되는지 확인한다. 현재 기대 집계는 `76 COMPLETE / 43 PARTIAL / 0 PENDING / 1 EXTERNAL / 0 CONTRADICTED`다. OP-010 자체는 COMPLETE이며, higher-stage 증거가 부족한 여러 항목은 PARTIAL로 남고 OP-039는 EXTERNAL로 남는다. 테스트가 대표 OP의 판정을 구체적으로 고정하므로 집계 숫자만 우연히 같은 잘못된 분류도 찾을 수 있다.

한 요구사항의 구현 경로를 존재하지 않는 파일로 바꾸는 테스트에서는 해당 항목만 CONTRADICTED가 된다. 테스트 목록을 비운 계약 위반도 영향을 받은 OP만 모순으로 처리하고 이웃 OP는 COMPLETE를 유지한다. 반대로 원본 SHA-256을 바꾼 전역 실패에서는 COMPLETE가 0이 되고 기존 claimed requirement 119건이 모두 CONTRADICTED가 된다. 국소 증거 결함과 전체 기준 문서 훼손의 영향 범위를 의도적으로 다르게 처리한다.

감사가 끝난 뒤 manifest 제목 하나를 바꾸는 테스트는 보고서 생성이 `audit_manifest_sha256_mismatch`로 거부되는지 확인한다. 이 테스트는 audit 객체의 status가 PASS라는 사실만 신뢰하지 않고 audit가 어떤 manifest bytes를 판정했는지 결합한다. 오류를 경고 문구로만 남긴 채 정상 보고서를 출력하지 않는다.

## CLI는 생성 모드와 검사 모드를 분리한다

`scripts/build_original_plan_completion_report.py`는 감사 CLI와 같은 방식으로 manifest와 두 저장소 root를 해석한 뒤 audit를 실행하고 completion report를 만든다. 기본 산출물은 `docs/original_plan/completion_status_v1.json`과 `docs/original_plan/COMPLETION_STATUS.md`다. 일반 모드는 두 파일을 UTF-8과 LF 개행으로 쓴다. JSON은 구조화된 후속 검사 입력이고 Markdown은 사람이 읽는 현재 상태 문서다.

`--check` 모드는 파일을 다시 쓰지 않는다. 현재 입력으로 만든 예상 bytes와 Git에 커밋된 두 산출물을 비교하고 다르면 `stale_outputs`에 경로를 넣어 종료 코드 1을 반환한다. 테스트는 임시 디렉터리에서 먼저 생성하고, 같은 입력의 check가 0인지 확인한 뒤 Markdown을 `stale` 문자열로 바꿔 check가 1인지 검증한다. 사람이 집계 숫자 하나를 고치거나 manifest를 바꾼 뒤 생성 파일 갱신을 잊으면 CI가 실패한다.

생성 시각도 재현성을 해치지 않도록 명시적인 규칙 안에서 계산된다. 같은 tracked 입력과 같은 감사 결과로 만든 canonical JSON과 Markdown은 byte 비교가 가능하다. normal mode는 산출물 갱신 작업에 쓰고 CI는 `--check`만 사용하므로 runner가 repository 내용을 조용히 고쳐 성공하지 않는다.

## 한국어 Markdown은 판정과 근거를 함께 보여 준다

`render_original_plan_completion_report_markdown_v1`은 문서가 자동 생성됐으며 수동 편집하지 말라는 안내를 먼저 적는다. 이어서 원본 path와 hash, manifest hash, 감사 status, `120/120건` 포함률과 disposition 집계를 보여 준다. 그룹별 표와 120개 요구사항 표에는 required stage, claimed stage, 판정, 근거가 포함된다. disposition별 목록도 제공해 PARTIAL과 EXTERNAL 항목을 따로 추적할 수 있다.

테스트는 Markdown에 `원계획 요구사항 포함: **120/120건**`, 완료 76, 부분 완료 43, 대기 0이 있는지 확인한다. 동시에 `전체 완료: **100%**`라는 문구가 없어야 한다고 명시한다. 생성기가 100% inventory coverage를 100% completion으로 과장하지 않는 핵심 copy 계약이다. 현재 보고서를 읽는 사람은 누락 없는 감사와 미완료 44건을 동시에 볼 수 있다.

## canonical evidence 생성 절차는 수동 집계를 배제한다

첫째, canonical manifest를 strict schema로 읽고 OP-001~120을 materialize한다. 둘째, R&D와 clean service checkout의 Git index, 원본 PDF bytes, evidence reference를 OP-008 감사기로 확인한다. 셋째, audit의 manifest hash와 현재 manifest hash를 대조한다. 넷째, 각 요구사항의 required stage, claimed stage, issue 범위에 따라 다섯 disposition 중 하나를 계산한다. 다섯째, 같은 모델에서 canonical JSON과 한국어 Markdown을 생성한다. 마지막으로 `--check`와 pytest, Ruff를 GitHub Actions에서 실행한다.

이 절차는 completion status를 사람이 따로 입력하지 않는다. manifest가 유일한 요구·주장 원장이고 audit가 경로 사실을 제공하며 report generator가 판정을 계산한다. OP-120 최종 감사는 여기에 120개 연구보고서의 존재·본문 품질, frozen 평가 불변성, replay와 slice, CI·review·외부 receipt 같은 더 넓은 완료 조건을 추가한다. 따라서 OP-010 보고서가 PASS여도 연구보고서 90건이 누락된 현재 전체 goal은 완료가 아니다.

## 구현 이력과 재현 근거가 담당하는 범위

보고서 모델과 생성 CLI의 최초 도입 커밋은 2026-07-15의 `af70e950357d8b0b268391634685a37bf29238d8`이다. 같은 날 `a449b605dceb29471103076d03de4e137ce421a5`가 generated report `--check`와 관련 pytest를 `Original plan evidence` workflow에 연결했다. 이후 manifest stage와 evidence가 추가될 때마다 같은 generator가 현재 JSON과 Markdown을 갱신해 왔다. 별도 수동 완료 문서를 병렬로 유지하지 않는다.

보고서 작성 직전의 canonical completion 집계는 76/43/0/1/0이며, 이전 OP-120 final audit evidence SHA-256은 `1be4ea55dcca71849aaed7332ee6859fdb419061561177ddf8eb2e7120a4ce01`이다. 당시 마지막 성공 GitHub Actions run `29919479757`은 audit CLI와 generated report `--check`, 계약 테스트가 clean runner에서 통과했음을 보여 준다. 이번 OP-009·010 연구보고서 추가는 completion disposition을 바꾸지 않지만 OP-120의 report inventory를 바꾸므로 final audit evidence와 CI run을 다시 생성해야 한다.

pytest 결과는 분류 규칙, global·local failure scope, stale output, 한국어 copy 계약을 증명한다. GitHub Actions 성공은 committed generated files가 현재 manifest에서 다시 계산한 결과와 같았음을 증명한다. 이 근거들은 실제 사용자에게 추천이 전달됐거나 production에서 KPI가 달성됐다는 사실을 증명하지 않는다. 보고서가 등록한 integration·operation evidence와 각 OP의 focused smoke가 별도로 그 범위를 담당한다.

## 서비스 통합과 실제 운영은 이 생성기의 완료 조건이 아니다

OP-010의 required stage와 claimed stage는 모두 `IMPLEMENTED`다. 감사에 결합된 결정적 판정 함수, JSON·Markdown renderer, 생성·검사 CLI와 실패 테스트가 있으므로 구현 단계는 충족한다. generator가 service repository의 evidence path를 감사 입력으로 읽을 수는 있지만 서비스 API, 데이터베이스, UI에 연결된 기능은 아니다. production에서 실행됐다고 주장하지 않으며 외부 기관이 결과를 승인했다고도 주장하지 않는다.

이번 backfill은 서비스 코드, API, 저장 구조, 원천 데이터, frozen dataset, 학습, 모델과 시뮬레이션을 바꾸지 않는다. 변경되는 것은 OP-010의 기존 구현을 설명하는 연구보고서와, 이를 inventory에 반영하는 OP-120 감사 근거뿐이다. 따라서 frozen eval 256건의 일곱 지표, replay와 weakest slice는 같은 값을 유지해야 하며 실제 재실행으로 확인한다.

## 현재 완료 단계와 남은 조건

OP-010은 120개 요구를 누락 없이 판정하고, 잘못된 감사·stale 산출물·과장된 100% 표현을 거부하므로 `IMPLEMENTED` 완료다. 그러나 자동 보고서는 등록된 증거의 의미를 모두 이해하지 않으며 실제 운영이나 외부검증을 만들어 내지 않는다. 특히 추적된 Markdown이 진짜 integration evidence인지, external receipt가 신뢰 가능한 발급자의 서명을 가졌는지, 120개 연구보고서가 충분한지는 OP-120과 독립 검토가 추가로 확인한다.

현재 전체 계획에는 required stage보다 낮은 PARTIAL 43건과 외부 의존 OP-039 한 건이 남아 있다. 이 숫자를 숨기지 않고 그대로 보여 주는 것이 OP-010의 성공이다. 남은 작업은 누락 연구보고서를 계속 역작성하고, 각 PARTIAL의 실제 서비스 통합·운영 조건을 충족하며, 외부 receipt가 필요한 항목은 승인된 증거를 확보하는 것이다. generator를 다시 실행해 COMPLETE 숫자만 높이는 방식으로는 어떤 단계도 승격되지 않는다.
## 원문을 요구사항으로 바꾸는 과정
이 그룹은 기능을 먼저 만들기보다, 원문에서 무엇을 읽었고 어느 파일이 그 해석을 지지하는지 고정하는 데서 출발한다. 원본 해시, 페이지, 요구사항 ID, 증거 단계가 따로 남아 있어야 나중에 코드가 바뀌어도 출발점과 해석을 다시 대조할 수 있다.

`OP-010`는 “원본 요구사항 100% 감사 보고서를 manifest에서 자동 생성한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=1-59`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/governance/original_plan_report.py`, `wellnessbox-rnd/scripts/build_original_plan_completion_report.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_original_plan_completion_report.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
