# OP-022 대화, 추천, 안전, 최적화, 후속평가 이벤트를 공통 실행 ID로 연결한다

## 요구사항은 한 번의 판단을 여러 로그에서 다시 조립할 수 있게 하는 것이다

원본 계획 16쪽은 사용자 대화, 개인 특성, 의약학 전문 문헌, 엔진·모델 연산 결과와 사용자 상호작용 로그를 하나의 데이터 레이크에 모으는 구상을 보여 준다. 각 구성요소가 자체 run ID만 쓰면 추천 결과와 안전 차단, 최적화 결과, 이후 평가가 같은 판단에서 나왔는지 확인하기 어렵다. OP-022는 한 추천 실행에서 파생된 다섯 event type을 공통 `execution_id`로 연결한다.

다섯 type은 `recommendation`, `safety`, `optimization`, `conversation`, `followup_evaluation`이다. 앞의 세 이벤트는 추천 완료 transaction에서 생성한다. 대화와 후속평가는 나중에 도착할 수 있으므로 같은 실행에 append한다. 공통 식별자는 단순 응답 필드가 아니라 `executions` 기본키, `execution_events` 외래키, API trace 조회와 응답의 동일한 값이어야 한다.

## schema가 실행과 이벤트의 일대다 관계를 강제한다

`src/wellnessbox_rnd/interim/store.py`의 `executions`는 `execution_id`를 기본키로 사용한다. `execution_events`는 각 행이 그 실행을 외래키로 참조하고, `event_index`, `event_type`, source, idempotency key, payload hash와 생성 시각을 저장한다. `UNIQUE(execution_id, event_index)`는 실행 안의 순서를, `UNIQUE(execution_id, event_type, idempotency_key)`는 같은 의미의 지연 이벤트 중복 방지를 강제한다.

event type은 schema의 CHECK 제약으로 다섯 값만 허용한다. 추천·안전·최적화는 system source이고 대화·후속평가는 허용된 사용자 데이터 출처다. 각 이벤트에는 당시 적용된 `consent_snapshot_id`도 남는다. 공통 실행 ID만 연결하고 개인정보 저장 근거를 잃는 구조가 아니다. `idx_execution_events_execution_index`는 실행 trace를 순서대로 읽는 조회를 지원한다.

## 추천 응답에서 생성한 식별자를 ledger가 그대로 사용한다

`src/wellnessbox_rnd/schemas/recommendation.py`는 `RecommendationResponse.execution_id` 계약을 정의한다. `src/wellnessbox_rnd/orchestration/recommendation_service.py`는 추천을 계산하면서 실행 ID를 만들고 응답에 포함한다. `apps/inference_api/routes/recommend.py`는 같은 응답을 반환한 뒤 `ExecutionLedger.record_recommendation`으로 기록한다. ledger가 별도의 ID를 다시 만들지 않기 때문에 client가 받은 값과 저장된 trace가 갈라지지 않는다.

`src/wellnessbox_rnd/interim/data_lake.py`의 `record_recommendation`은 응답의 plan ID가 요청과 같은지 먼저 검사한다. 실행, 실행 identity, 선택적 replay snapshot을 저장한 뒤 `_core_event_payloads`가 만든 추천·안전·최적화 payload를 event index 0부터 순서대로 삽입한다. 세 이벤트는 같은 transaction과 같은 `execution_id`, 같은 consent snapshot을 사용한다.

## 핵심 이벤트는 결과의 서로 다른 책임을 분리한다

추천 이벤트는 plan과 후보·선택 결과를 추적하는 기준이다. 안전 이벤트는 차단·제외·rule reference와 안전 상태를 담는다. 최적화 이벤트는 개인화 후보 조합과 목적함수 결과를 설명한다. 세 payload를 한 덩어리 로그로 저장하지 않아 안전 판단과 최적화 판단을 각각 감사할 수 있지만, 실행 ID가 같아 최종 추천과의 관계를 잃지 않는다.

저장 동의가 충분하지 않으면 derived output payload는 redaction된 형태로 기록된다. 모든 사용 출처가 영속 저장을 허용할 때만 상세 지식 lineage를 연결한다. 따라서 공통 실행 ID는 동의 거부를 우회하는 join key가 아니다. 식별자가 같다는 사실과 상세 payload를 저장할 권한은 별도로 판단한다.

## 지연 대화와 후속평가는 현재 활성 동의를 다시 확인한다

`ExecutionLedger.append_event`는 delayed event를 `conversation`과 `followup_evaluation`으로 제한한다. 존재하지 않는 실행 ID, system source, 빈 idempotency key와 지원하지 않는 event type은 거부한다. 대화 source는 survey로 제한하며, versioned PRO 후속평가도 survey source와 plan ID, 평가 순서 규칙을 확인한다.

이 함수는 실행에 저장된 과거 동의만 보지 않는다. 해당 profile의 `active_profile_consents`를 조회하고 지연 이벤트 출처의 현재 `allow_persistent_storage`가 true인지 확인한다. 동의가 철회됐으면 이벤트를 추가하지 않는다. 같은 idempotency key와 같은 payload는 기존 event ID를 돌려주고, source나 payload가 달라지면 conflict로 fail closed한다.

## API가 append와 trace 조회를 노출한다

`apps/inference_api/routes/interim.py`는 `/v1/interim/executions/{execution_id}/events`에서 대화·후속평가를 추가하고 `/v1/interim/executions/{execution_id}`에서 전체 trace를 조회한다. mutation token 보호와 request validation을 통과해야 저장 mutation이 일어난다. trace 응답은 실행 ID, profile·consent version, ordered events를 한 구조로 반환한다.

API 소비자는 추천 응답의 `execution_id`를 보관했다가 대화나 후속평가를 같은 경로에 붙일 수 있다. 별도의 conversation session ID나 recommendation run ID를 실행 ID처럼 혼용하지 않는다. 각 하위 시스템이 내부 식별자를 유지할 수는 있지만, OP-022가 요구하는 교차 단계 결합 키는 `execution_id` 하나다.

## 테스트는 다섯 이벤트의 순서와 동일성을 직접 검사한다

`tests/test_data_lake_lineage.py`는 core event 세 개를 기록하고 conversation과 follow-up evaluation을 append한다. 최종 event type 순서가 recommendation, safety, optimization, conversation, followup evaluation인지, 모든 event의 execution ID 집합이 최초 trace ID 하나뿐인지 검사한다. 저장 동의 거부, 최신 동의 철회, source relabel 우회, 중복 replay와 payload conflict도 별도 사례로 검증한다.

`tests/test_inference_api.py`는 `/v1/recommend`가 `exec_[a-f0-9]{32}` 형식의 ID를 반환하고 ledger trace가 같은 ID와 세 core event를 가지는지 확인한다. `tests/test_interim_api.py`는 event append와 follow-up lifecycle을 실제 FastAPI 경계에서 검사한다. 존재하지 않는 실행이나 plan mismatch가 조용히 새 trace를 만들지 않는다.

## canonical evidence는 공통 ID 연결을 재현한다

`scripts/run_data_lake_lineage_smoke.py`는 임시 SQLite와 실제 route를 사용해 추천을 실행한 뒤 응답의 ID로 conversation과 follow-up evaluation을 추가한다. 마지막 trace의 event type을 읽고 각 event의 execution ID 집합을 계산한다. `data/original_plan/evidence/op021_op022_data_lake_lineage_smoke_v1.json`에는 다섯 type, `all_event_execution_ids_match: true`, `all_five_event_types_connected: true`, `response_execution_id_matches_trace: true`가 기록돼 있다.

이 smoke의 case count는 프로필 v1, v2, 저장 거부 실행을 포함한 3이다. 실행 수는 3이지만 다섯 이벤트 연결 검사는 첫 허용 실행 하나의 trace에 대해 수행한다. 따라서 서로 다른 사용자의 이벤트를 우연히 한 집합으로 모은 결과가 아니다. 원본 값 비저장과 동의 snapshot 검사도 함께 수행해 lineage와 개인정보 경계를 동시에 확인한다.

## IMPLEMENTED 완료는 운영 관측을 뜻하지 않는다

manifest의 required·claimed stage는 `IMPLEMENTED`이며 schema, orchestration, FastAPI 경로, 회귀 테스트와 canonical smoke가 모두 존재한다. 따라서 OP-022는 `COMPLETE`다. 이 판정은 로컬 실행에서 다섯 이벤트가 공통 ID를 공유한다는 구현 완료다. production message bus, 분산 trace collector, 실제 장기 사용자 follow-up, 장애 시 재처리율과 보존 기간을 입증한 `OPERATED` 증거는 아니다.

이번 보고서 backfill은 코드, 데이터 schema, service, production, 원천·frozen·학습 데이터, 모델과 simulation을 변경하지 않았다. 공식 frozen 256건의 일곱 지표, replay와 weakest slice delta는 모두 0이다. 운영 승격에는 배포된 서비스에서 추천 응답 ID로 지연 이벤트를 연결한 receipt, 동의 철회 후 저장 거부 관측, 중복 전달과 장애 복구를 포함한 장기 trace 완전성 지표가 필요하다.
