# OP-031 알레르기 규칙을 데이터로 관리하고 추천 전에 적용한다.

요구사항 manifest가 구현 근거로 등록한 `wellnessbox-rnd/data/rules/safety_rules.json`에는 생선 알레르기 규칙 `SAFETY-ALLERGY-FISH-001`이 있다. 사용자가 `fish` 또는 `fish allergy`를 입력하면 이 규칙은 `omega3`를 제외하고 경고를 남긴다. 입력 계약, 정규화, 규칙 평가, 후보 제외, API 회귀 테스트를 함께 확인한 결과 현재 단계는 `IMPLEMENTED`다.

## 요구사항과 구현 전 상태

OP-031은 알레르기 정보를 추천 설명에 덧붙이는 수준이 아니라, 개인화 점수를 계산해 후보를 고르기 전에 위험 성분을 후보 집합에서 제거하라고 요구한다. 원문 요구 위치는 manifest에 `docs/context/original_plan.pdf#page=17`로 등록되어 있다. 이 순서가 필요한 이유는 알레르기 성분이 높은 효용 점수를 받아도 최종 추천으로 복구되면 안 되기 때문이다.

커밋 `1ef1cf3`의 변경 전후를 비교하면 기존 `RecommendationRequest`와 정규화된 섭취 모델에는 알레르기 필드가 없었고, 안전 서비스에도 알레르기 규칙을 적용하는 반복문이 없었다. 같은 커밋이 요청 스키마, 정규화된 `allergy_set`, 도메인 규칙 모델, JSON 규칙, API 회귀 테스트를 한 묶음으로 추가했다. 이 diff는 누락된 기능과 수정 범위를 보여 주지만, 당시 실패한 테스트의 원문 로그까지 보존하지는 않는다.

## 입력부터 후보 제외까지 이어지는 구현

`wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`의 `RecommendationRequest.allergies`는 문자열 목록을 받는다. `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`의 `normalize_request`는 각 값을 소문자로 바꾸고 연속 공백을 정리한 뒤 집합으로 만든다. 따라서 입력 순서나 중복 때문에 같은 알레르기 규칙이 여러 번 적용되지 않는다. 다만 이 정규화는 동의어 추론이 아니라 철자와 공백을 정돈하는 처리다.

`wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`는 알레르기 조건과 제외 성분을 별도 필드로 가진 규칙 모델을 정의한다. 실제 정책 데이터는 `wellnessbox-rnd/data/rules/safety_rules.json`에 있다. 현재 등록된 규칙은 `fish`와 `fish allergy`를 정확한 조건값으로 사용하고 `omega3`를 제외하며 심각도는 `warning`이다. 규칙 ID와 버전, 경고 문구도 JSON에 함께 있으므로 파이썬 조건문을 바꾸지 않고 정책 데이터를 검토할 수 있다.

`wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py`의 `assess_safety`는 정규화된 알레르기 집합과 규칙 조건이 겹치는지 확인한다. 조건이 맞으면 규칙의 `excluded_ingredients`를 안전 요약에 합치고 적용 규칙과 경고를 기록한다. 그 뒤 `wellnessbox-rnd/src/wellnessbox_rnd/orchestration/recommendation_service.py`가 안전 요약을 후보 선택에 전달한다. 후보 선택기는 제외된 오메가3에 `safety_summary_excluded` 사유를 붙인다. 알레르기 규칙의 심각도가 경고이므로 요청 전체를 차단하지는 않지만, 오메가3 후보는 점수와 무관하게 최종 추천에서 빠진다.

## 회귀 테스트가 확인하는 결과

`wellnessbox-rnd/tests/test_inference_api.py`의 `test_recommend_endpoint_excludes_omega3_for_fish_allergy`는 `/v1/recommend`의 전체 요청 경로를 실행한다. 테스트는 `allergies=["fish"]`를 포함한 요청이 HTTP 200을 반환하는지, 응답의 제외 성분에 `omega3`가 있는지, 적용 규칙에 `SAFETY-ALLERGY-FISH-001`이 있는지 확인한다. 마지막으로 반환된 추천 항목 중 오메가3가 하나도 없다고 단언한다. 이 검사는 JSON 규칙을 읽는 것에서 끝나지 않고 알레르기 입력이 실제 API 출력의 후보 제거로 이어지는지 검증한다.

현재 저장소에서 관련 테스트 묶음을 다시 실행해 통과 여부를 확인할 수 있지만, 보고서 근거의 핵심은 등록된 구현 파일과 해당 API 테스트의 구체적인 단언이다. manifest에는 구현 경로 다섯 개와 `wellnessbox-rnd/tests/test_inference_api.py`가 등록되어 있으며 모두 현재 저장소에 존재하고 위 동작과 일치한다.

## 판정 범위와 남은 한계

OP-031은 저장소 코드와 자동화 테스트에서 요구된 동작이 재현되므로 `IMPLEMENTED`로 판정한다. 외부 시스템 배포, 실제 사용자 입력, 운영 차단 로그는 확인하지 않았으므로 `INTEGRATED`, `OPERATED`, `EXTERNAL`로 올리지 않는다.

현재 정책이 인식하는 조건은 `fish`와 `fish allergy` 두 값뿐이다. 다른 언어, 철자 오류, 어종 이름, 해산물 전체를 자동으로 생선 알레르기로 확장한다는 근거는 없다. 또한 이 규칙에는 외부 임상 문헌의 reference ID나 claim ID가 연결되어 있지 않다. 따라서 이번 확인은 등록된 정책을 정확히 적용하는 소프트웨어 동작을 입증하며, 정책의 의학적 완전성이나 실제 진료 적합성까지 입증하지 않는다.
## 안전 판단에서 놓치면 안 되는 경계
안전 그룹의 기준은 추천을 많이 만드는 것이 아니라 위험한 결과를 통과시키지 않는 것이다. 입력 단계와 후보 생성 뒤에 안전 판단을 두고, 중대한 위험이나 불명확한 용량이 나오면 fail-closed로 멈추는 경계를 확인한다.

`OP-031`는 “알레르기 규칙을 구조화 데이터로 추가하고 추천 전에 적용한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=17`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/recommendation.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/intake.py`, `wellnessbox-rnd/src/wellnessbox_rnd/domain/models.py`, `wellnessbox-rnd/src/wellnessbox_rnd/safety/service.py` 외 1개
- 테스트·실행: `wellnessbox-rnd/tests/test_inference_api.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
