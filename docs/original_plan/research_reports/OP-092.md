# OP-092 CGM의 혈당, 식후 상승, time-in-range를 정규화한다.

manifest에 등록된 증거 `wellnessbox-rnd/src/wellnessbox_rnd/domain/sensor_parser.py`에서 구현과 검증 대상을 확인할 수 있다.

## 요구사항의 핵심과 단계 구분

OP-092는 연속혈당측정기, 즉 Continuous Glucose Monitor(CGM)의 혈당, 식후 상승, time-in-range를 정규화하라고 요구한다. time-in-range는 혈당이 정해진 목표 범위 안에 있었던 시간 비율이다. 같은 숫자 78이라도 목표 범위가 70–180 mg/dL인지 80–140 mg/dL인지에 따라 의미가 다르므로 percentage만 저장하면 재현 가능한 지표가 아니다. 식후 상승도 boolean 하나만 저장하면 최고 혈당이 얼마였는지, 식전 기준보다 얼마나 올랐는지 구분할 수 없다.

이번 연구에서는 CGM provider API나 실제 환자의 sensor stream을 연결하지 않았다. raw 5분 간격 glucose series에서 meal window를 추론하지도 않았다. versioned daily-summary CSV가 제공하는 평균 혈당, 식후 최고치 또는 상승량, 70–180 mg/dL time-in-range를 내부 일별 계약으로 변환했다. 따라서 현재 증거는 parser 구현 단계이며 production CGM integration이나 임상 해석을 증명하지 않는다. OP-092의 required stage는 `IMPLEMENTED`이고 그보다 높은 단계는 주장하지 않는다.

## 기존 CGM 처리 경로와 부족했던 정보

기존 `sensor_parser.py`는 dictionary payload에서 `mean_glucose_mg_dl`, `avg_glucose_mg_dl`, mmol/L alias와 `timeInRangePct`를 읽었다. mmol/L 값은 18을 곱해 mg/dL로 바꿨고 conversion note를 남겼다. 표준 alias `time_in_range_70_180_pct`를 사용하면 low 70, high 180 경계를 snapshot에 기록했다. 같은 payload에서 일반 TIR alias와 표준 alias가 서로 다른 값을 주면 conflict로 거부했고, 표준 alias와 80–140 같은 다른 경계를 함께 주면 fail-closed했다.

그러나 식후 정보는 `post_meal_spike_concern` boolean뿐이었다. 평균 혈당과 TIR도 여러 날짜를 가진 CSV에서 일별 record로 변환하는 함수가 없었다. `validate_cgm_summary_csv_schema`는 sample 한 행의 header와 숫자를 확인했지만 downstream에서 사용할 typed daily model을 만들지 않았다. OP-092에서는 이 기존 parser와 snapshot을 확장했고 별도 CGM 저장소나 별도 추천 경로는 만들지 않았다.

## 일별 CGM 계약

새 `NormalizedCgmDailySummary`는 date, mean glucose mg/dL, postprandial peak mg/dL, postprandial rise mg/dL, time-in-range percentage, low/high range bounds, source row count와 normalization note를 가진다. 평균 혈당은 20–600 mg/dL, 식후 최고치는 20–600 mg/dL, 식후 상승량은 0–580 mg/dL, TIR은 0–100% 범위다. Pydantic이 NaN과 infinity를 허용하지 않으므로 숫자처럼 보이는 비정상 floating value도 계약을 통과할 수 없다.

날짜는 `date`, `day`, `recorded_date` alias를 ISO date로 읽는다. 같은 날짜가 여러 행이면 parser가 임의로 평균하지 않고 `duplicate_cgm_daily_summary_date`로 거부한다. daily-summary producer가 여러 sensor segment를 합칠 책임과 R&D parser가 한 일별 summary를 읽는 책임을 분리한 것이다. raw series aggregation이 필요하면 별도의 versioned raw-CGM 계약을 만들어야 한다.

## mg/dL와 mmol/L 단위 변환

평균 혈당은 `mean_glucose_mg_dl`, `avg_glucose_mg_dl`, `avg_glucose`를 읽는다. glucose unit은 `glucose_unit` 또는 `avg_glucose_unit`에서 가져온다. 명시된 단위가 `mmol/L`이면 18을 곱하고 소수점 첫째 자리로 반올림한다. `6.8 mmol/L`는 `122.4 mg/dL`가 된다. `mg/dL`은 숫자를 그대로 사용한다. 지원하지 않는 단위는 `unsupported_glucose_unit`으로 거부한다.

필드명 자체가 `_mg_dl`로 끝나는 식후 최고치와 상승량은 global glucose unit이 mmol/L이더라도 이미 mg/dL로 해석한다. 반대로 `post_meal_peak`, `post_meal_rise`처럼 단위가 없는 alias는 row의 glucose unit을 따른다. frozen mmol/L 사례에서 peak 8.9는 160.2 mg/dL, rise 2.1은 37.8 mg/dL가 된다. 이 구분은 header가 이미 선언한 단위와 row-level unit을 이중 변환하는 오류를 막는다.

독립 검토에서 `_mg_dl` 명시 필드까지 global mmol/L 단위로 다시 변환되는 결함을 찾았다. 수정한 parser는 `_mg_dl` 필드를 항상 mg/dL로 해석한다. 명시적 mg/dL 평균과 일반 `avg_glucose`가 함께 있으면 일반 값만 row 단위에 따라 환산한 뒤 두 값이 같은지 비교한다. 값이 다르면 `conflicting_cgm_mean_glucose_aliases`로 거부한다. 후속 독립 검토에서는 같은 의미 그룹 안의 snake/camel 동의어 충돌도 첫 값만 선택한다는 결함을 찾았다. 최종 parser는 평균 혈당, 표준·일반 TIR, 식후 최고치와 상승량의 모든 non-empty 동의어 값을 비교하고 불일치하면 의미별 conflict 오류로 거부한다. 회귀 시험은 명시적 평균, 두 TIR 그룹, peak, rise 충돌을 각각 재현한다.

## 식후 최고치와 상승량을 분리한 이유

식후 최고치와 상승량은 같은 정보가 아니다. 최고치는 식후 window 안에서 관측된 가장 높은 절대 혈당이고, 상승량은 식전 또는 meal baseline에서 최고치까지의 차이다. 평균 혈당에서 peak를 빼거나 peak와 rise로 식전 값을 역산하면 원본 producer가 사용한 meal window와 baseline 정의를 알 수 없어 잘못된 해석이 된다. parser는 입력에 있는 수치만 보존하고 임의 계산하지 않는다.

daily summary는 peak 또는 rise 중 적어도 하나를 요구한다. 둘 다 없으면 `cgm_postprandial_metric_required`로 실패한다. 둘 다 있으면 각각 보존한다. 이 요구는 OP-092의 “식후 상승을 정규화한다”는 내용을 boolean `postMealSpike=true` 하나로 대체하지 않기 위한 것이다. 기존 snapshot의 boolean은 하위 호환을 위해 유지하지만, 새 numeric fields인 `postprandial_peak_mg_dl`과 `postprandial_rise_mg_dl`을 recommendation schema, intake canonical payload와 Data Lake execution payload에 추가했다.

숫자를 보존하는 것은 보충제 효과의 인과관계를 주장하는 것과 다르다. 식후 혈당 변화는 식사 구성, 활동, 수면, 약물, sensor 오차와 여러 요인의 영향을 받는다. parser는 관측값을 정규화할 뿐 특정 영양제가 상승량을 낮췄다고 해석하지 않는다. downstream 모델도 별도 consent, context와 검증 없이 이 값을 치료 효과로 말해서는 안 된다.

## 70–180 mg/dL time-in-range 경계를 고정한 방식

표준 daily CSV는 `time_in_range_70_180_pct` 또는 camelCase 동등 alias를 지원한다. 필드명 자체가 표준 범위를 선언하므로 low/high를 생략할 수 있다. 일반 `time_in_range_pct`는 계산 범위를 알 수 없으므로 `time_in_range_low_mg_dl=70`과 `time_in_range_high_mg_dl=180`을 함께 제공해야 한다. 경계가 빠지면 `generic_cgm_time_in_range_bounds_required`, 다른 범위면 `standardized_cgm_time_in_range_bounds_mismatch`로 거부한다. 표준 alias와 일반 alias가 동시에 있고 값이 다르면 `conflicting_cgm_time_in_range_aliases`로 거부한다.

이 결정은 70–180 범위가 모든 사용자와 모든 임상 상황에 항상 적합하다는 선언이 아니다. original plan과 현재 repository의 standardized CGM 계약이 이 범위를 사용하기 때문에 schema에 경계를 함께 보존한 것이다. 임신, 특정 치료 목표나 다른 분석 목적에서 다른 range를 지원하려면 range-qualified schema를 새 version으로 추가해야 한다. 기존 `time_in_range_70_180_pct` 이름에 다른 bounds를 붙여 통과시키지 않는다.

TIR 값은 0에서 100 사이여야 한다. 문자열 숫자는 float로 변환하지만 `?`, 빈 값, NaN처럼 유효하지 않은 입력은 거부된다. dictionary snapshot 경로에서는 과거 malformed value를 note와 함께 무시하는 하위 호환 동작이 남아 있다. 새 daily-summary CSV는 canonical evidence용 엄격한 계약이므로 필수 값이 잘못되면 record 전체를 실패시킨다. 두 경로의 strictness 차이는 입력 목적 차이이며 장기적으로는 versioned API에서 어떤 경로를 사용할지 명시해야 한다.

## 기존 snapshot, intake와 Data Lake 연결

`NormalizedSensorGeneticSnapshot`에 `postprandial_peak_mg_dl`과 `postprandial_rise_mg_dl`을 추가했다. cgm_available이 false인데 이 값이 있으면 기존 source-availability validator가 실패하도록 조건을 확장했다. recommendation request의 canonical intake payload에도 두 필드를 넣었다. 요청 hash는 canonical payload에 기반하므로 같은 평균과 TIR이라도 식후 수치가 달라지면 다른 입력 identity가 된다.

Data Lake가 recommendation request snapshot을 execution event payload로 저장할 때도 두 numeric fields를 포함한다. 이 변경은 새 CGM 테이블을 만들지 않고 기존 execution lineage를 확장한다. 기존 mean glucose, TIR, bounds와 boolean concern도 그대로 보존된다. 실제 daily record를 어느 사용자와 consent snapshot에 연결해 저장하는 production ingestion API는 이번 loop에서 실행하지 않았다.

## frozen 사례와 실패 계약

mg/dL 정상 사례는 평균 122.4, 식후 peak 160.2, rise 37.8, TIR 78을 입력하고 같은 수치와 70/180 bounds가 나오는지 확인한다. mmol/L 사례는 평균 6.8, peak 8.9, rise 2.1을 입력해 각각 122.4, 160.2, 37.8 mg/dL로 변환되는지 확인한다. 두 사례는 동일한 normalized clinical numbers를 만들므로 단위 변환이 일관적인지 비교할 수 있다.

오류 사례는 80–140 bounds를 `time_in_range_70_180_pct`와 함께 제공해 mismatch를 확인한다. 또 평균과 TIR만 있고 식후 metric이 없는 파일이 `cgm_postprandial_metric_required`로 실패하는지 확인한다. wearable 오류 사례까지 포함한 전체 frozen dataset은 여덟 건이며 exact error string을 고정한다. 예상 결과를 generator 코드에 숫자로 숨기지 않고 versioned JSON에 둬 변경 review가 가능하다.

## 결정론과 source identity

smoke generator는 각 정상 record의 전체 model dump를 evidence에 기록한다. 실패 record는 case ID와 exact error를 기록한다. dataset case count가 실제 사례 수와 다르면 실행을 실패시킨다. Apple Health, generic wearable, mg/dL와 mmol/L, postprandial peak/rise, standardized TIR 관측 여부를 별도 boolean으로 표시한다. production provider API와 production operation은 false로 명시한다.

source identity에는 generator, dataset, 두 sample CSV, sensor parser, recommendation schema, intake와 Data Lake를 포함한다. 모두 Git HEAD blob에서 SHA-256을 계산하므로 uncommitted 파일이 evidence identity에 섞이지 않는다. 두 번 생성한 canonical file은 byte-identical했다. 소스나 dataset을 수정하면 source-first commit 후 canonical evidence를 다시 생성해야 한다.

## 검증 범위와 남은 위험

집중 검증은 sensor parser와 file schema뿐 아니라 CGM event bridge, Data Lake lineage, health input contracts, consent/input hash, recommendation contracts, candidate signal scoring, inference API를 포함했다. 새 필드가 기존 strict schema와 canonical hashing을 깨지 않는지 확인했다. 기존 70–180 TIR conflict 시험과 malformed dictionary fallback도 통과했다.

현재 parser는 raw CGM 시계열에서 mean, TIR, meal peak를 계산하지 않는다. meal timestamp나 식전 baseline definition도 받지 않는다. provider별 CSV header 전체, sensor gap, timezone alignment, calibration status, duplicate sensor reading, daylight-saving transition은 별도 raw ingestion 계약이 필요하다. 실제 CGM provider 연결률이나 KPI 90%도 이 작은 frozen dataset으로 주장하지 않는다.

## 현재 단계

OP-092는 평균 혈당, 식후 최고치와 상승량, 70–180 mg/dL TIR percentage와 bounds를 하나의 typed daily summary로 정규화한다. mg/dL와 mmol/L을 구분하고, 식후 수치 누락과 range mismatch를 fail-closed한다. 두 식후 numeric fields는 기존 snapshot, canonical intake와 Data Lake payload로 연결됐다.

현재 주장 단계는 `IMPLEMENTED`다. required stage도 `IMPLEMENTED`이므로 최종 독립 검토와 감사가 통과하면 COMPLETE 후보다. production CGM API, 실제 사용자 ingestion, raw-series 계산, 임상 외부 검증과 운영 성능은 증명하지 않았으며 높은 단계로 확대하지 않는다.
## 센서와 유전자 자료를 넣는 기준
센서와 유전자 자료는 많이 넣는 것보다 동의한 자료를 올바른 단위와 시점으로 연결하는 것이 중요하다. 이 그룹은 파일 원본, 출처별 정규화, data_class, 동의, 중복 수신, 실제 점수 반영을 분리해 확인한다.

`OP-092`는 “CGM의 혈당, 식후 상승, time-in-range를 정규화한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.
