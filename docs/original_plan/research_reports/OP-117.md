# OP-117 브라우저에서 사용자, 약사, 관리자 핵심 경로를 재현한다

## 요구사항은 세 역할의 핵심 업무가 실제 화면에서 이어지는지 확인하라는 것이다

OP-117은 사용자·약사·관리자 화면 파일이 저장소에 있는지만 세는 요구사항이 아니다. 실제 브라우저가 서버에 접속해 각 역할의 인증 경계를 통과하고, 역할별 핵심 업무를 끝까지 수행할 수 있는지 재현해야 한다. 사용자라면 설문 또는 프로필을 제출하고 추천 결과를 받아야 한다. 약사라면 로그인 뒤 대기 초안을 읽고 결정을 저장해야 한다. 관리자는 인증 뒤 R&D 데이터·규칙·모델·실행 상태를 실제 API에서 읽어야 한다.

요구사항 장부에 등록된 구현 파일은 `wellnessbox/scripts/qa/check-rnd-role-browser-paths.cjs`다. 실행기는 `wellnessbox-rnd/scripts/run_browser_operational_evidence_smoke.py`, 고정 사례는 `wellnessbox-rnd/data/original_plan/op117_op118_browser_operational_evidence_cases_v1.json`, 결과는 `wellnessbox-rnd/data/original_plan/evidence/op117_op118_browser_operational_evidence_smoke_v1.json`이다. 운영 근거로는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-117.json`이 연결돼 있다. 이 파일들은 모두 존재하지만, 실제 브라우저 사례는 역할별 업무 전체가 아니라 화면 도달과 일부 인증만 확인한다.

## 실행기는 로컬 Next.js와 실제 Chromium을 사용했다

`run_browser_operational_evidence_smoke.py`는 비어 있는 포트를 고르고 WellnessBox의 `npm run dev`를 별도 프로세스로 시작한다. 환경에는 관리자 비밀번호, JWT 비밀값과 쿠키 비밀값을 시험용 문자열로 넣으며 결과 JSON에는 그 값을 쓰지 않는다. `/survey`가 응답할 때까지 기다린 다음 Node.js 브라우저 스크립트를 실행한다. 브라우저는 Playwright의 실제 Chromium을 headless 방식으로 띄운다.

실행 환경은 `PATH`, `SystemRoot`, 임시 폴더와 사용자 자료 폴더 등 필요한 항목만 넘긴다. 첫 구현은 현재 프로세스의 환경 전체를 복사했고 Windows 전용 `taskkill /F`로 종료했다. 커밋 `84aed96`은 비밀값이 섞일 여지를 줄이도록 전달 환경을 제한하고, 정상 종료를 먼저 시도한 뒤 시간 초과 때만 강제 종료하도록 바꿨다. 같은 수정에서 단순 본문 표시 대신 HTTP 상태와 실제 제어 요소 수를 확인하게 했다.

## 사용자 사례는 설문 화면 도달까지만 증명한다

`user_survey` 사례는 `/survey`로 이동해 HTTP 200, 최종 경로 `/survey`, 입력칸과 버튼 합계가 1개 이상인지 본다. 등록 결과에는 제어 요소 3개가 기록돼 있다. 빈 문서나 404 화면을 성공으로 세는 초기 검사의 약점은 제거됐다.

그러나 이 사례는 필드에 값을 넣거나 제출 버튼을 누르지 않는다. 서비스가 R&D 프로필 API를 호출했는지, 추천 실행 ID가 생겼는지, 사용자가 추천 결과를 화면에서 보았는지는 관찰하지 않는다. 따라서 “사용자 핵심 경로” 중 첫 화면 렌더링만 재현됐다. OP-105의 별도 로컬 HTTP 시험이 프로필·추천 연결을 다루지만, 그 시험은 브라우저를 사용하지 않으므로 OP-117의 누락을 대신하지 못한다.

## 약사 사례는 비인증 차단만 확인한다

`pharmacist_auth_boundary`는 로그인하지 않은 새 페이지에서 `/pharm`을 연다. 최종 주소가 `/pharm-login`이고 입력칸이 정확히 2개이며 비밀번호 입력칸이 보이는지 확인한다. 이는 비인증 방문자가 약사 화면으로 바로 들어가지 못하는 경계에는 적합한 검사다.

약사 로그인을 성공시키는 입력, 대기 초안 목록, 승인·수정 승인·반려 버튼은 이 브라우저 사례에 없다. 결과 파일도 `pharmacist_authenticated_session_proven=false`라고 명시한다. 따라서 현재 증거는 약사 핵심 경로를 재현했다고 쓰기보다 약사 인증 전 차단 화면을 재현했다고 써야 한다. 특히 OP-106에서 확인한 AI 초안 화면의 `draft_id`와 결정 행은 이 브라우저 결과에 포함되지 않는다.

## 관리자 사례는 인증과 화면 진입을 확인하지만 상태값을 읽지 않는다

`admin_authenticated`는 브라우저 문맥의 요청 기능으로 `/api/verify-password`에 관리자 비밀번호를 보낸다. 로그인 응답이 200인지 확인한 뒤 같은 문맥에서 `/admin`을 연다. 관리자 화면의 HTTP 상태와 최종 경로가 정상이고 `/admin/`으로 시작하는 링크가 하나 이상 있어야 한다. 등록 결과에는 링크 4개가 남아 있다.

이 검사는 관리자 쿠키가 브라우저 문맥에 적용되고 화면에 들어갈 수 있음을 보여준다. 하지만 링크를 누르지 않고 `/api/admin/tips` 응답도 읽지 않는다. 데이터, 규칙, 모델, 실행 상태의 실제 값이 표시되는지는 OP-107의 별도 통합 시험 범위이며, 이번 브라우저 증거에서는 확인되지 않았다. 인증된 관리자 화면 진입과 관리자 핵심 업무 완료를 같은 뜻으로 볼 수 없다.

## 고정 사례와 Git 이력은 검사의 약점과 수정 범위를 드러낸다

고정 자료 8건 중 OP-117은 `user_survey`, `pharmacist_auth_boundary`, `admin_authenticated` 세 건이다. 각 기대값은 사용자 200·제어 요소, 약사 로그인 이동·입력 두 개, 관리자 로그인 200·화면 200·관리자 링크로 한정된다. 실행기는 브라우저 사례가 정확히 3건이고 전체 고정 사례가 8건인지도 확인한다. 데이터 SHA-256과 결과 JSON의 값은 실제 파일과 일치한다.

서비스 커밋 `0984f98`의 첫 검사는 사용자와 관리자에서 본문이 보이기만 하면 성공했다. 잘못된 오류 화면도 본문은 있을 수 있다는 문제가 있었다. `8b9e2df`는 사용자·관리자 HTTP 상태, 사용자 제어 요소 수, 약사 입력 수, 관리자 링크 수를 추가했다. R&D 커밋 `a102bc3`은 로컬 브라우저를 썼다는 이유만으로 OP-117을 `INTEGRATED`로 적었던 생성기의 자체 주장을 `IMPLEMENTED`로 낮췄다. 이 수정은 약사 인증 세션과 역할별 업무 완료가 빠졌다는 실제 증거 경계를 반영한다.

## 등록 결과는 과거 소스에는 결속됐지만 현재 장부로 재실행되지 않는다

결과 파일은 브라우저 스크립트 SHA-256 `d6c65676b21d78812ec9ee0242d225d5b650fd36ff5d69180754f242b0c2fb38`과 WellnessBox 커밋 `8b9e2df62c998147ef045390909f7244501ef6e8`을 기록한다. 현재 브라우저 스크립트의 SHA-256도 같아서 브라우저 검사 코드 자체는 변하지 않았다. 세 역할의 관찰값과 `local_real_browser_proven=true`도 파일 내용과 맞는다.

반면 같은 생성기는 OP-118 집계를 함께 수행하며 `operated_requirement_count`가 0이어야 한다고 고정했다. 현재 요구사항 장부에는 `OPERATED`가 41건이라 브라우저 성공 뒤 이 단정문에서 실패한다. 등록 결과를 덮어쓰지 않는 조건 때문에 이번 검토에서 생성기를 실행하지 않았다. 결과 파일은 당시의 브라우저 관찰을 보존하지만, 현재 요구사항 장부와 전체 생성 절차가 다시 통과한다는 증거는 아니다.

## 운영 영수증은 브라우저 역할 경로와 내용이 다르다

`OP-117.json`은 로컬 연구 PC에서 `recommendation_runs`와 `recommendation_items`가 각각 1건 늘어난 세션을 기록한다. 실행 경로는 `recommendation` 하나다. 브라우저 주소, 사용자 설문, 약사 로그인 또는 관리자 인증 기록은 없다. OP-117은 일반 매핑표에서 추천 행동에 연결돼 `covered_requirement_ids`에 포함됐다.

추천 실행 한 건은 실제 연구 활동이 있었다는 근거지만 세 역할의 브라우저 경로를 재현한 관찰은 아니다. 영수증에 내용 지문과 서명 문자열이 있어도 요구 행동이 기록되지 않았다면 단계 근거가 되지 않는다. 이번 검토에서는 그 서명 자체의 진위도 별도 공개키로 다시 확인하지 않았다.

## 현재 단계와 아직 필요한 브라우저 관찰

직접 입증된 최상위 단계는 결과 파일이 스스로 기록한 `IMPLEMENTED`다. 실제 로컬 브라우저에서 사용자 설문 화면, 약사 로그인 차단, 관리자 인증과 화면 진입이 재현됐다. 세 역할 모두 화면 파일 존재보다 강한 증거는 얻었지만, 역할별 핵심 업무를 끝까지 수행하지 않았으므로 요구사항 장부의 `OPERATED`는 확인되지 않았다.

운영 승격에는 하나의 통제된 세션에서 사용자 설문 제출과 추천 결과 표시, 약사 로그인과 특정 `draft_id` 결정, 관리자 R&D 상태값 조회를 각각 수행해야 한다. 각 화면의 최종 주소·응답 상태·보이는 핵심 값과 대응 데이터베이스 변화를 같은 결과에 묶어야 한다. 공개 배포, 실제 사용자 트래픽과 운영 브라우저 세션은 현재 자료에서 확인되지 않았다.
## 운영 증거와 종료 판단을 나눈 이유
운영 증거는 구현 파일을 나열하는 데서 끝나지 않는다. 보안, 장애 복구, 계약 일치, 배포 health, 브라우저 경로, 운영 증거, 외부 의존성과 최종 감사가 각각 어떤 주장을 지지하는지 단계별로 나눈다.

`OP-117`는 “브라우저에서 사용자, 약사, 관리자 핵심 경로를 재현한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15-26`
- 구현·설계: `wellnessbox/scripts/qa/check-rnd-role-browser-paths.cjs`
- 테스트·실행: `wellnessbox-rnd/scripts/run_browser_operational_evidence_smoke.py`, `wellnessbox-rnd/data/original_plan/op117_op118_browser_operational_evidence_cases_v1.json`, `wellnessbox-rnd/data/original_plan/evidence/op117_op118_browser_operational_evidence_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-117.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-117.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
