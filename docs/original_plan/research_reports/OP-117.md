# OP-117 브라우저에서 사용자, 약사, 관리자 핵심 경로를 재현한다

브라우저 검증의 등록 증거는 `wellnessbox-rnd/data/original_plan/evidence/op117_op118_browser_operational_evidence_smoke_v1.json`이다. 생성기와 고정 사례, WellnessBox의 브라우저 자동화 스크립트, 이후 운영 영수증을 각각 열어 역할별로 실제 관찰한 범위를 확인했다.

## 파일 존재 확인 대신 브라우저를 사용한 이유

화면 소스가 있어도 서버가 시작되지 않거나 인증 이동이 잘못되면 사용자는 기능에 도달할 수 없다. OP-117은 사용자·약사·관리자라는 세 역할의 핵심 경로를 브라우저에서 재현하라고 요구한다. 그래서 `scripts/run_browser_operational_evidence_smoke.py`는 빈 포트를 골라 로컬 Next.js 개발 서버를 시작하고, 브라우저 자동화 도구 Playwright로 실제 Chromium 화면을 연다. 이 방식은 컴포넌트 파일 개수나 라우트 이름만 세는 검사보다 화면 접근과 인증 경계를 더 직접적으로 보여준다.

시험용 관리자 비밀번호와 쿠키 비밀값은 실행 환경에만 넣고 결과 JSON에는 저장하지 않는다. 사용자 경로는 `/survey`, 약사 경로는 `/pharm`, 관리자 경로는 `/admin`으로 고정했다. 브라우저가 받은 최종 주소, HTTP 상태와 화면 제어 요소 수를 남겨 빈 HTML이나 잘못된 이동을 성공으로 세지 않게 했다.

## 세 역할에서 실제로 본 결과

사용자 사례는 `/survey`에서 HTTP 200을 받았고 최종 주소도 `/survey`였다. 입력과 버튼은 3개로 집계됐다. 이 결과는 설문 화면 본문이 실제 서버에서 렌더링됐음을 뜻한다. 다만 프로필을 끝까지 제출하거나 R&D 추천 응답을 화면에서 보지는 않았다.

약사 사례는 로그인하지 않은 상태로 `/pharm`을 열었다. 브라우저는 `/pharm-login`으로 이동했고 입력칸 2개와 보이는 비밀번호 입력칸을 찾았다. 이것은 비인증 사용자를 막는 경계를 증명하지만, 약사 로그인이 성공하거나 검토 목록을 열고 결정을 저장한 사실은 증명하지 않는다. 등록 evidence도 `pharmacist_authenticated_session_proven=false`로 같은 한계를 적었다.

관리자 사례는 브라우저 문맥의 요청 기능으로 `/api/verify-password`에 비밀번호를 보낸 뒤 `/admin`을 열었다. 로그인 응답과 관리자 화면 모두 200이었으며 `/admin/` 아래 링크 4개가 보였다. 관리자 인증과 화면 진입은 관찰했지만, 링크를 눌러 데이터·규칙·모델·실행 값을 읽는 세부 업무는 이 사례에 포함되지 않았다.

## 고정 사례와 생성 과정에서 남은 실패

고정 파일 `data/original_plan/op117_op118_browser_operational_evidence_cases_v1.json`에는 8건이 있다. OP-117의 브라우저 사례는 앞의 3건이고, 나머지 5건은 OP-118 장부 집계다. 생성기는 브라우저 사례 수가 3이고 전체 사례 수가 8인지 먼저 확인한다. 그 뒤 사용자 200, 약사 로그인 이동, 관리자 로그인과 본문 접근 조건 중 하나라도 다르면 결과를 만들지 않는다.

현재 생성기는 작성 당시 요구사항 장부 상태를 상수처럼 가정한다. `evidence_linked_count=119`와 함께 `operated_requirement_count=0`을 요구한다. 지금 요구사항 장부를 직접 세면 비외부 요구사항 119건 중 41건이 `OPERATED`이므로 같은 코드를 다시 실행하면 브라우저 성공 뒤 집계 단정문에서 실패한다. 이 샤드는 등록 증거를 덮어쓰지 않기 위해 생성기를 실행하지 않았다. 과거 결과의 브라우저 관찰은 유효하지만, 생성기가 현재 장부 상태를 재현한다는 뜻으로 읽으면 안 된다.

## 운영 단계 판단과 필요한 다음 관찰

요구사항 장부에는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-117.json`이 등록돼 있다. 이 서명 영수증은 로컬 연구 PC에서 추천 실행과 추천 항목이 각 1건 늘어난 세션을 기록하고, 범용 매핑표에 따라 OP-117을 포함한다. 그러나 파일 안에는 방문한 브라우저 주소, 사용자·약사·관리자 역할, 로그인 결과나 화면 표시값이 없다. 추천 테이블 증가만으로 세 역할의 핵심 경로 재현을 직접 입증할 수는 없다.

따라서 현재 강한 결론은 실제 로컬 브라우저에서 사용자 설문, 약사 로그인 차단, 관리자 인증 화면을 재현했다는 `IMPLEMENTED`다. 약사 로그인 이후 경로가 빠졌고 세 역할 모두 핵심 업무를 끝까지 수행하지 않았으므로 `OPERATED`는 확인되지 않았다. 운영 승격에는 동일한 실제 세션에서 사용자의 프로필·추천, 약사의 대기 초안 조회·결정, 관리자의 실제 R&D 상태 조회를 차례로 수행하고, 각 화면의 최종 주소와 대응 데이터베이스 변화를 같은 영수증에 남겨야 한다.
