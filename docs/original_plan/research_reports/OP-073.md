# OP-073 후속 일정과 알림 예약을 실제 업무 큐에 저장한다.

manifest에 등록된 구현 경로는 `wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`이고, 실제 로컬 세션의 확인 기록은 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-073.json`이다.

## 후속 일정을 메모리가 아니라 저장소에 남겨야 하는 이유

복용 계획을 시작했다는 기록만으로는 다음 확인이 이루어지지 않는다. 프로그램이 꺼지거나 다시 시작돼도 “언제, 어떤 자료를 다시 받아야 하는가”와 “그 전에 언제 알릴 것인가”가 남아 있어야 한다. OP-073은 후속 일정과 알림을 실행 중인 프로그램의 임시 예약으로 두지 않고, 다른 작업자도 이어서 읽을 수 있는 업무 큐에 저장하라는 요구다. 계획·사용자·실행 기록이 서로 맞지 않는 예약을 만들면 엉뚱한 사람의 계획을 확인할 수 있으므로 저장 전 연결 관계도 함께 점검해야 한다.

## 한 번의 저장으로 후속 기록과 알림 작업을 묶었다

`WorkflowJobQueue.schedule_followup_with_reminder()`는 SQLite의 한 `immediate` 트랜잭션 안에서 `followups` 행과 `workflow_jobs` 행을 만든다. 먼저 `execution_id`, `profile_id`, `plan_id`가 같은 활성 계획을 가리키는지 확인한다. 이어서 동의 기록 식별자와 실행 근거의 지문 값(SHA-256)을 알림 작업 내용에 넣는다. 알림 시각이 후속 예정일보다 늦으면 `followup_reminder_after_due`로 거부하고, 시간대가 없는 시각도 받지 않는다.

별도 알림 저장소를 만들지 않고 공용 `workflow_jobs`를 택한 이유는 재시도·작업 선점·만료 처리 규칙을 한곳에서 사용하기 위해서다. 알림 작업의 종류는 `FOLLOWUP_REMINDER`, 상태는 처음에 `READY`다. `requested_data`는 중복을 없애고 정렬해 저장하므로 입력 순서만 바뀌어도 다른 예약으로 오인하지 않는다. `store.py`의 외래키는 업무가 기존 후속 기록과 실행 기록을 가리키도록 제한한다.

## 재요청과 충돌을 같은 성공으로 숨기지 않는다

같은 `followup_id`로 완전히 같은 요청이 다시 오면 `followup-reminder:{followup_id}`를 멱등 키로 사용해 기존 `job_id`를 돌려준다. 반면 계획, 예정일, 알림일, 요청 자료, 실행 ID 중 하나가 바뀌면 `followup_idempotency_payload_conflict`로 멈춘다. 네트워크 재시도는 한 건으로 합치되, 뜻이 달라진 요청을 기존 예약에 덮어쓰지 않는 구분이다.

현재 자료에는 이 기능을 개발하면서 처음 마주친 실패 명령이나 오류 로그가 남아 있지 않다. 대신 `tests/test_interim_jobs.py`가 충돌 조건을 실패 사례로 고정했다. 같은 예약을 두 번 보내면 업무가 한 건으로 유지되고, 계획이나 알림 시각을 바꾼 재요청은 예외가 나며, 알 수 없는 실행은 후속 기록을 남기지 않는다. 조사 범위는 manifest의 구현 파일, 위 테스트 파일, 생성 스크립트와 두 증거 JSON까지다.

## 저장 결과와 실제 세션 기록을 따로 확인했다

기준 실행 결과인 `wellnessbox-rnd/data/original_plan/evidence/op073_op074_followup_job_queue_cron_smoke_v1.json`에는 두 계획의 후속 기록과 알림 작업이 각각 두 건 저장돼 있다. 각 알림에는 계획 ID, 실행 ID, 후속 ID, 알림 시각, 요청 자료, 동의 기록 식별자, 실행 근거 지문이 들어 있다. 같은 큐를 다시 읽을 수 있다는 점과 후속 기록·알림 기록이 함께 생성됐다는 점을 이 파일에서 직접 확인했다.

로컬 운영 세션 `local-20260724T010245964049Z`는 `data_class`를 `ACTUAL`로 기록하고 `executed_paths`에 `followup`을 포함한다. 그 세션에서 `followups`와 `workflow_jobs`가 각각 1건 증가했다. 따라서 OP-073은 로컬 연구 PC에서 실제 큐 저장까지 관측한 `OPERATED` 단계로 판단한다. 이는 단순한 함수 시험보다 높은 근거지만 공개 서비스 운영을 뜻하지는 않는다.

## 확인된 범위와 남은 한계

현재 근거는 예약이 영속 저장되고 재시작 가능한 큐에 남는 지점까지 뒷받침한다. 알림 작업을 실제 문자·앱 푸시·카카오톡으로 전달한 결과, 장기간 실행한 작업자의 처리율, 운영 장애 뒤 복구 시간은 확인되지 않음이다. 운영 영수증도 업무 종류별 상세 행을 공개하지 않아 저장된 1건이 어떤 채널로 발송됐는지는 알 수 없다. 그러므로 OP-073의 `OPERATED` 주장은 로컬 업무 큐 저장에 한정하며, 사용자에게 알림이 도착했다는 외부 효과까지 확장하지 않는다.
