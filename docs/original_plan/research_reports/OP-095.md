# OP-095 파일별 오류와 부분 성공 응답 구현 보고서

## 결론

센서 파일 묶음 가운데 정상 파일은 처리하고 잘못된 파일은 파일별 오류로 돌려주는 수집 API를 구현했다. 응답에는 전체 파일 수, 성공 파일 수, 실패 파일 수, 정규화 레코드 수, 저장된 계보 수가 함께 들어간다. 일부 파일만 성공하면 상태는 `PARTIAL_SUCCESS`가 된다. 모든 파일이 성공하면 `SUCCESS`, 모든 파일이 실패하면 `FAILED`가 된다. 따라서 호출자는 HTTP 요청 하나가 성공했다는 사실만 보고 전체 파일이 수집됐다고 잘못 판단하지 않는다.

OP-095의 요구 증거 단계는 `IMPLEMENTED`다. 인증된 FastAPI 경로, 파일 형식 검증, 정규화, SQLite 저장, 자동 테스트와 고정 사례 실행 결과를 갖췄으므로 요구 단계를 충족했다. 다만 운영 배포나 실제 사용자의 파일 전송은 이번 증거에 포함하지 않는다.

## 문제와 판단 기준

기기 자료는 한 번에 여러 파일이 들어올 수 있다. 예를 들어 사용자가 웨어러블 CSV, 연속혈당측정기(CGM) CSV, 유전자 JSON을 함께 보낼 수 있다. 이때 유전자 JSON 하나의 문법이 잘못됐다는 이유로 정상 웨어러블 자료까지 버리면 재전송 비용이 커진다. 반대로 요청 자체를 성공으로만 표시하면 실패한 파일이 숨어 버린다. 구현 기준은 정상 파일을 보존하면서 실패한 파일을 명시하는 것이었다.

부분 성공은 데이터 품질 규칙을 느슨하게 적용한다는 뜻이 아니다. 각 파일은 기존 스키마 검증기와 정규화기를 독립적으로 통과해야 한다. 중복 CSV 열 이름, 중복 JSON 키, UTF-8이 아닌 본문, 크기 제한 초과, 필수 필드 누락은 해당 파일의 실패다. 다른 파일의 성공 여부는 이 실패로 바뀌지 않는다. 다만 출처 종류처럼 요청 모델 자체가 허용하지 않는 값은 파일 처리 전 Pydantic 검증에서 요청 전체를 HTTP 422로 거절한다. 부분 성공 계약은 허용된 출처 종류의 파일 내용 검증에 적용된다.

## 구현 범위

`POST /v1/interim/sensor-files/ingest` 경로를 기존 내부 토큰 인증에 연결했다. 새 경로만 별도 인증 규칙을 만들지 않았다. 요청 모델은 프로필 ID, 동의 값, 파일 배열을 받는다. 각 파일은 파일 ID, 출처 종류, Base64 본문을 가진다. Base64를 사용하는 이유는 HTTP JSON 전송 과정에서 원본 바이트를 임의로 다시 인코딩하지 않고 해시 계산에 쓸 정확한 바이트를 복원하기 위해서다.

서비스는 파일마다 다음 순서로 처리한다. 먼저 추천 목적 사용 동의를 확인한다. 동의가 없으면 본문을 디코딩하거나 해시하지 않는다. 동의가 있으면 Base64와 크기, UTF-8을 검증한다. 그다음 출처별 파서가 CSV 또는 JSON 스키마를 검사하고 정규화한다. 정규화가 끝나면 결과 건수와 계보 값을 만든다. 영구 저장 동의가 있으면 기존 `InterimStore`에 결과를 추가한다. 영구 저장 동의가 없으면 응답은 만들되 SQLite 행은 남기지 않는다.

응답의 파일별 결과에는 `file_id`, 출처, 처리 상태, 오류 목록, 정규화 레코드 수, 저장 여부가 들어간다. 원본 해시와 정규화 결과 해시도 함께 제공하지만, OP-095의 핵심은 호출자가 실패 범위와 성공 건수를 기계적으로 판정할 수 있다는 점이다. 오류는 파일별 `failure_types` 문자열 목록으로 반환한다. 호출자는 안정된 오류 문자열을 기준으로 재업로드 안내나 파일 수정 안내를 선택할 수 있다.

## 공유 결함을 고친 이유

기존 파일 스키마 검증기는 CSV가 정확히 한 행일 때만 정상으로 보았다. 반면 기존 웨어러블·CGM 정규화기는 여러 행을 순회하도록 이미 작성돼 있었다. 두 규칙은 서로 모순됐다. 이번 사례만 통과시키는 예외를 수집 API에 넣으면 다른 호출자는 계속 한 행 제한을 받는다. 따라서 가장 이른 공통 원인인 파일 스키마 검증기에서 한 행 제한을 제거했다. 열과 값 검증은 그대로 유지했고, 다중 행 정상 처리 회귀 테스트를 추가했다.

## 고정 사례와 결과

고정 데이터셋 `op095_op096_sensor_file_ingestion_cases_v1.json`에는 일곱 사례가 있다. 첫 사례는 세 파일 가운데 두 파일이 성공하고 한 파일이 실패한다. API 응답은 전체 3, 성공 2, 실패 1, 정규화 레코드 2, 저장 계보 3을 반환한다. 실패 파일도 시도 계보를 남기므로 저장 건수가 성공 건수보다 클 수 있다. 이 차이를 응답 필드 이름으로 분명히 구분했다.

두 번째 사례는 한 웨어러블 CSV에 두 행을 넣는다. 파일 성공 건수는 1이고 정규화 레코드 수는 2다. 파일 수와 레코드 수를 혼동하지 않는지 확인한다. 세 번째 사례는 중복 CSV 머리글과 중복 JSON 키를 각각 넣는다. 두 파일 모두 실패하며, 각 오류가 다른 파일 ID에 연결된다. 요청 전체의 상태는 `FAILED`다.

네 번째 사례는 추천 목적 사용 동의를 거부한다. 서비스는 본문을 디코딩하거나 해시하지 않고 저장도 하지 않는다. 다섯 번째 사례는 추천 목적 사용은 허용하지만 영구 저장을 거부한다. 정상 정규화 결과는 응답하되 데이터베이스에는 쓰지 않는다. 여섯 번째 사례는 같은 요청을 다시 보낸다. 첫 요청의 결과를 재사용하고 행을 중복 추가하지 않는다. 일곱 번째 사례는 저장된 행을 수정하거나 삭제하려고 시도하고 SQLite 트리거가 두 작업을 모두 거부하는지 확인한다.

정식 스모크 실행기는 테스트용 함수를 직접 호출하지 않는다. 실제 FastAPI `TestClient`로 인증 헤더를 보내고 실제 임시 SQLite 파일을 연다. API 응답 뒤 데이터베이스를 다시 조회해 응답 집계와 저장 행 수를 비교한다. 모든 사례가 통과했고 최종 계보 행은 6개였다. 저장 테이블에 원본 본문 열이 없다는 점도 검사했다.

## 검증과 실패 경계

집중 테스트는 새 수집 테스트와 기존 센서 파서, 파일 스키마, 중간 저장소, 중간 API 테스트를 함께 실행했다. 79개 검사가 통과했다. Ruff 검사도 통과했다. 이 조합은 새 기능 자체뿐 아니라 공유 검증기 변경이 기존 웨어러블·CGM·유전자 입력을 깨지 않았는지 확인한다.

이번 구현은 파일을 진단하거나 의료적으로 해석하지 않는다. 유전자 자료는 이미 허용된 제한된 구조만 정규화한다. 파일 크기는 2MiB로 제한한다. 원본 본문은 저장하지 않는다. 알 수 없는 문자 인코딩을 추측하지 않고 UTF-8이 아니면 실패한다. 이 제한은 오류를 숨기는 자동 보정보다 재현 가능한 실패를 우선한다.

## 남은 한계

운영 트래픽, 대용량 객체 저장소, 악성 파일 검사 서비스, 압축 파일, 공급자별 원본 포맷 전체는 검증하지 않았다. 현재 API는 내부 인증 토큰을 사용하고 로컬 또는 테스트 환경의 SQLite에 쓴다. 배포 환경의 요청 제한, 데이터 보존 정책, 운영 관측 지표는 별도 운영 단계에서 확인해야 한다. 이러한 한계는 OP-095의 `IMPLEMENTED` 판정을 바꾸지 않지만, 생산 준비 완료를 뜻하지는 않는다.
