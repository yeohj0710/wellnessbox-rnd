# OP-106 — 약사 검토 화면과 R&D 검토 큐 연결

## 결론

WellnessBox 약사 경로가 R&D 검토 큐를 조회하고 결정을 제출하는 왕복을 실제 FastAPI 프로세스로 검증했다. canonical runner는 약국 미배정 상태의 검토 항목을 임시 SQLite에 만든다. 서비스 QA는 약국 ID 105로 목록을 조회하고, 해당 항목에 `APPROVE` 결정을 제출한다. R&D는 상태를 `COMPLETED`로 바꾸고 불변 완료 증거를 반환한다. 같은 검토 항목에 두 번째 결정을 보내면 409가 발생한다.

요구 단계 `OPERATED`에 비해 현재 주장은 `INTEGRATED`다. 서비스 클라이언트, 인증 라우트, 약사 화면 경로, R&D 큐와 결정 API가 코드와 로컬 두 프로세스에서 연결됐다. 실제 약사 계정의 운영 사용과 공개 배포는 증명하지 않았다.

## 목록이 보이는 조건

R&D 큐 조회는 약국 ID가 같은 항목과 아직 어느 약국에도 배정되지 않은 항목만 반환한다. WellnessBox 라우트는 브라우저가 보낸 약국 ID를 신뢰하지 않고 약사 세션의 `pharmacyId`로 쿼리를 만든다. 약사 세션이 없으면 R&D 호출 전에 중단한다. 결정 요청에도 세션의 약국 ID를 덮어쓴다. 검토 ID는 `review_`와 소문자 16진수 형식만 통과한다.

약사 화면은 `/api/pharm/tips/reviews`를 호출한다. 화면은 `PROXY_GOLD_SIMULATION` 배지를 유지해 실제 조제·복약지도 기록으로 오인하지 않게 한다. 이번 QA는 서비스의 실제 내부 클라이언트로 목록과 결정을 호출하며, canonical evidence는 라우트의 사용자·약사 인증 경계와 화면의 서비스 API 경로가 커밋된 상태인지 함께 확인한다.

## 결정은 한 번만 기록된다

첫 결정은 상태, 약국 ID, 결정 기록 여부, 완료 시각을 postcondition으로 묶고 SHA-256을 저장한다. 같은 검토에 다른 결정을 덮어쓸 수 없다. QA는 첫 요청의 `COMPLETED`, `immutable: true`, 약국 ID 105를 확인하고 두 번째 요청이 `WB_RND_INTERIM_upstream_409`로 거부되는지 확인한다.

운영 완료를 주장하려면 실제 배포 주소, 지속 DB, 실제 약사 로그인, 브라우저 화면, 권한 분리, 운영 로그까지 검증해야 한다. 이번 루프는 공개 환경을 바꾸지 않고 그 직전의 통합 경계를 닫았다.
