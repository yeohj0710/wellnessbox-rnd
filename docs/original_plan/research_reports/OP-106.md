# OP-106 약사 검토 화면을 R&D 검토 큐와 연결한다

요구사항 장부(manifest)의 등록 경로 `wellnessbox/components/tips/InterimRoleConsole.tsx`와 통합 결과 `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`을 직접 열어 화면, 서비스 라우트, R&D 큐가 어디까지 이어지는지 분리해 확인했다.

## 화면 연결에서 풀어야 했던 문제

약사 화면은 목록을 보여주는 데서 끝나면 안 된다. 로그인한 약국의 대기 항목만 받아야 하고, 승인·수정 승인·반려 중 하나를 보낸 뒤 그 결정이 R&D 원장에 한 번만 기록돼야 한다. 브라우저가 다른 약국 번호나 검토자 ID를 넣어도 서버 세션의 값이 우선해야 한다. 아직 승인되지 않은 자동 생성 초안이 학습·평가·추천·지식 자료로 흘러가지 않도록 막는 조건도 같은 연결의 일부다.

현재 서비스에는 성격이 다른 검토 큐가 두 개 있다. `review_tasks`는 안전사고나 작업 실패에서 생긴 검토 작업이며 R&D의 `/v1/interim/admin/reviews`를 쓴다. `ai_drafts`는 자동 생성 초안을 약사가 승인하는 원장이고 `/v1/interim/admin/ai-drafts`를 쓴다. 실제 `InterimRoleConsole.tsx`의 약사 화면은 두 번째 큐를 호출한다. 화면은 첫 대기 초안의 내용과 판단 근거를 보여주고, 승인·수정 승인·반려 입력을 `/api/pharm/tips/ai-drafts/{draft_id}`로 보낸다.

## 약사 신원과 결정 자료를 보존하는 방법

`wellnessbox/lib/server/wb-rnd-interim-route.ts`는 약사 세션이 없으면 R&D에 요청하지 않는다. 일반 약국 계정의 검토자 ID는 브라우저 값이 아니라 `pharmacy:{pharmacyId}`로 만든다. 연구용 약사 경로에서는 이름을 받되 프로젝트 소유자 이름을 약사 검토자로 등록하지 못하게 막는다. 초안 ID는 `draft_`와 소문자 16진수 형식만 허용한다.

R&D의 `AiDraftService`는 초안의 자료 유형, 모델 식별자, 지시문 버전과 멱등 키로 결정적인 ID를 만든다. 같은 ID에 내용이 달라지면 `ai_draft_idempotency_conflict`로 거부한다. 결정할 때는 현재 상태가 `pending`인지 먼저 보고, 수정 승인은 전후 내용을 `edit_diff`에 남기며 반려는 이유를 요구한다. 승인이나 수정 승인이 끝난 자료만 하류 소비 함수가 반환한다. 대기 또는 반려 자료를 요청하면 `unapproved_ai_draft_blocked`로 중단한다. `tests/test_interim_api.py`의 집중 시험은 승인 전 소비가 409인지, 승인 후 소비가 성공하는지, 결정 응답이 다음 초안을 함께 주는지 확인한다.

## 등록 핵심 경로 시험이 확인한 별도 검토 작업

등록 핵심 경로 시험(smoke)은 약사 화면의 AI 초안 경로가 아니라 `review_tasks` 경로를 실제 두 프로세스로 왕복시켰다. 생성기는 `PharmacistReviewService.create_in_transaction`으로 약국 미지정 대기 작업을 만든다. 서비스 QA는 약국 105 세션으로 목록을 읽고, 브라우저가 보낸 `pharmacy_id=999`를 무시한 채 105로 결정을 저장한다. 같은 작업에 두 번째 결정을 보내면 409가 반환된다. 결과의 `review_queue_roundtrip_completed`, `review_decision_completed`, `review_replay_rejected`, `pharmacist_route_auth_denial_executed`, `service_pharmacy_id_override_executed`는 모두 참이다.

여기서 드러난 문제는 `pharmacist_screen_uses_service_api` 검사의 범위다. 생성기는 서비스 파일 네 개를 한 문자열로 합친 뒤 `"/api/pharm/tips/reviews"`가 있는지만 찾는다. 그 네 파일에는 실제 화면뿐 아니라 이 주소를 스스로 사용하는 QA 스크립트도 포함된다. 따라서 이 참값만으로 React 화면이 `review_tasks` 큐를 사용한다고 결론 내릴 수 없다. 실제 화면을 열어 확인하면 화면은 `ai_drafts` 큐를 사용한다. 두 큐 모두 구현돼 있지만 등록 smoke의 화면 검사와 실제 화면 대상이 서로 다르다.

## 운영 기록에서 확인되는 것과 남는 공백

운영 등록 파일 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-106.json`은 2026-07-24 로컬 연구 세션을 담는다. 이 세션에서 `ai_drafts`가 1건 생겼고 `ai_drafts_reviewed`도 1건 늘었다. 반면 `review_tasks`와 `review_tasks_completed` 증가는 0이다. 즉 실제 운영 영수증은 화면이 쓰는 AI 초안 원장의 결정 한 건을 뒷받침하지만, smoke가 재현한 안전 검토 작업 큐와는 다른 자료다.

코드와 각 큐의 로컬 API 연결, 인증 경계, 한 번만 결정되는 규칙은 `INTEGRATED` 수준으로 확인됐다. manifest는 운영 영수증을 근거로 `OPERATED`를 주장하지만, 영수증에는 브라우저 주소·클릭·응답 상태가 없고 검토자 신원도 이 파일만으로 확인할 수 없다. 따라서 화면에서 실제 약사가 어떤 큐를 열어 결정했는지까지는 확인되지 않았다. 다음 검증에서는 AI 초안 화면의 로그인부터 승인까지 브라우저로 재현하고, 해당 `draft_id`, 서버 응답과 같은 세션의 `ai_drafts_reviewed` 증가를 한 증거에 묶어야 한다. `review_tasks` 화면이 별도로 필요하다면 현재 UI와 다른 요구로 명시해야 두 큐를 혼동하지 않는다.
