# OP-106 약사 검토 화면을 R&D 검토 큐와 연결한다

## 요구사항은 화면, 서버 권한, 검토 원장을 한 경로로 묶으라는 뜻이다

OP-106은 약사 화면에 대기 건수가 보인다는 사실만 요구하지 않는다. 인증된 약사가 R&D가 만든 대기 초안을 보고 승인·수정 승인·반려 중 하나를 제출한 뒤, 같은 초안의 상태와 검토자, 수정 전후 또는 반려 이유가 R&D 저장소에 한 번만 기록돼야 한다. 승인되지 않은 초안은 학습·평가·추천·지식 자료로 넘어가면 안 된다.

요구사항 장부가 지정한 구현 경로는 `wellnessbox/lib/server/wb-rnd-interim-route.ts`, `wellnessbox/components/tips/InterimRoleConsole.tsx`, `wellnessbox/scripts/qa/check-rnd-profile-review-roundtrip.cts`다. 시험과 결과는 `wellnessbox-rnd/scripts/run_profile_review_roundtrip_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op105_op106_profile_review_roundtrip_smoke_v1.json`, `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-106.json`에 등록돼 있다. 모든 파일은 존재하지만, 핵심 경로 시험이 재현한 큐와 현재 화면이 사용하는 큐가 다르다.

## 기존 시스템에는 목적이 다른 두 검토 큐가 있다

`review_tasks`는 안전사고나 실행 실패 뒤 사람이 확인해야 하는 작업이다. `PharmacistReviewService.create_in_transaction`은 사용자 ID, 사유 목록과 원본 작업 ID로 `review_id`를 결정하고 중복 생성을 막는다. `complete_review`는 상태가 `OPEN`인지, 지정 약국과 결정 약국이 같은지, 원본 작업이 취소됐는지 또는 중대한 이상반응 차단 상태가 남았는지를 확인한 뒤 `COMPLETED`로 바꾼다. 같은 검토에 다시 결정을 내리면 `review_already_completed`가 발생한다.

`ai_drafts`는 자동 생성 초안을 약사가 판단하는 별도 원장이다. `AiDraftService.create`는 자료 유형, 모델 식별자, 지시문 버전과 멱등 키로 `draft_id`를 만들고 내용과 판단 근거까지 포함한 지문을 비교한다. 같은 ID에 다른 내용이 오면 `ai_draft_idempotency_conflict`로 거부한다. `decide`는 `pending`인 행에만 승인, 수정 승인 또는 반려를 기록한다. 수정 승인에는 `edit_diff`가 남고 반려에는 이유가 필수다.

`consume_approved`는 목적이 training, evaluation, recommendation, knowledge 중 무엇이든 승인 또는 수정 승인 상태만 반환한다. 대기나 반려 상태는 `unapproved_ai_draft_blocked`로 중단한다. 즉 약사 화면 연결은 단순 업무 편의가 아니라 자동 생성 자료가 하류 기능에 들어가기 전의 필수 차단 경계다.

## 현재 React 화면은 AI 초안 큐를 사용한다

`InterimRoleConsole`은 약사 역할일 때 `/api/pharm/tips/ai-drafts`를 읽는다. 첫 대기 초안의 `content`와 `rationale`을 보여주고, `decide`가 `/api/pharm/tips/ai-drafts/{draft_id}`로 판단을 보낸다. 승인 버튼은 별도 내용을 요구하지 않는다. 수정 승인은 JSON을 받아야 하고, 반려는 이유가 있어야 활성화된다. 응답이 성공하면 방금 처리한 초안을 화면 목록에서 제거한다.

서비스 함수 `runPharmAiDraftsRoute`는 `requirePharmSession`이 실패하면 R&D를 호출하지 않는다. 결정 함수는 `draft_` 뒤에 소문자 16진수만 있는 ID를 허용한다. 일반 약국 계정은 검토자 ID를 `pharmacy:{pharmacyId}`로 강제하므로 브라우저가 다른 ID를 넣을 수 없다. 연구용 약사 세션인 `pharmacyId=0`은 이름 입력을 요구하고 프로젝트 소유자 이름 `여형준`을 거부한다.

화면에는 검토자 이름 `권혁찬`이 초기값으로 들어 있다. 사용자가 실제로 이름을 입력하지 않아도 승인 버튼을 누를 수 있다는 뜻이다. 서버가 프로젝트 소유자를 차단하는 것과 별개로, 이 초기값은 실제 검토자가 누구였는지를 화면 행동만으로 보장하지 않는다. 현재 코드에는 일반 약국 계정의 세션 신원과 연구용 이름 입력 경로가 함께 있으므로, 운영 증거에서는 어느 경로를 썼는지 반드시 남겨야 한다.

## 등록 핵심 경로 시험은 다른 큐인 review_tasks를 재현했다

`check-rnd-profile-review-roundtrip.cts`는 `runPharmInterimReviewsRoute`와 `runPharmInterimDecisionRoute`를 호출한다. 두 함수의 주소는 `/v1/interim/admin/reviews`와 `/v1/interim/admin/reviews/{review_id}/decision`이다. 생성기는 임시 데이터베이스에 `PharmacistReviewService.create_in_transaction`으로 대기 작업을 먼저 넣고, 약국 105 세션이 그 작업을 읽고 결정하게 한다. 브라우저 본문의 `pharmacy_id=999`는 무시되고 세션의 105가 저장되며, 두 번째 결정은 409로 끝난다.

결과 파일의 `review_queue_roundtrip_completed`, `review_decision_completed`, `review_replay_rejected`, `pharmacist_route_auth_denial_executed`, `service_pharmacy_id_override_executed`는 모두 참이다. 이 결과는 `review_tasks` API와 인증·불변성에는 맞는 근거다. 그러나 `InterimRoleConsole`이 현재 호출하는 `ai_drafts` 주소는 이 시험에서 요청되지 않는다.

`pharmacist_screen_uses_service_api` 검사도 화면 연결을 직접 증명하지 않는다. 생성기는 QA 스크립트, 클라이언트, 라우트, 화면 파일 네 개를 한 문자열로 합친 뒤 `"/api/pharm/tips/reviews"`가 있는지만 찾는다. 그 문자열은 QA 스크립트 자체에 있으므로, React 화면이 다른 주소를 쓰더라도 참이 된다. 실제 파일을 열어 보니 화면은 `/api/pharm/tips/ai-drafts`를 사용한다. 이 불일치는 보고서 주장을 AI 초안 화면과 review_tasks 시험으로 분리해야 하는 이유다.

## AI 초안 원장의 집중 시험은 화면 아래 저장 규칙을 확인한다

`test_ai_draft_review_api_returns_next_item_and_blocks_pending`는 두 초안을 만든 뒤 첫 초안을 승인 전 소비하려 할 때 HTTP 409가 나는지 확인한다. 승인 요청이 성공하면 응답의 `next_draft`가 두 번째 초안을 가리키고, 승인 뒤 소비는 성공해야 한다. 이 시험은 실제 React 클릭은 거치지 않지만 화면이 호출하는 R&D API의 상태 전이를 직접 다룬다.

`test_draft_persists_complete_provenance_and_idempotency`는 같은 입력을 다시 만들 때 같은 ID가 반환되고 중복 표시가 참인지 본다. `test_unapproved_draft_is_blocked_from_every_downstream`은 대기·반려 초안이 네 하류 목적 모두에서 막히는지 조합별로 검사한다. `test_approved_and_edited_drafts_are_consumable`은 승인과 수정 승인의 내용·수정 차이가 보존되는지, `test_decision_is_single_use_and_reviewed_row_is_immutable`은 두 번째 결정과 SQL 직접 변경까지 거부되는지 확인한다.

Git 이력도 두 큐가 갈라진 과정을 보여준다. 서비스의 `c1a8458` 첫 화면은 `review_tasks` 목록을 표시했다. R&D `3f67d0b`와 서비스 `29f1050`에서 AI 초안 원장, 승인 전 차단, 승인·수정 승인·반려 화면이 추가되며 실제 화면 주소가 `ai-drafts`로 바뀌었다. `2be0753`은 연구용 검토자 이름을 받되 프로젝트 소유자는 차단하도록 보완했다. 반면 OP-105/106 핵심 경로 시험은 이전 `review_tasks` 경로를 그대로 유지했다. 변경 뒤 화면과 시험을 다시 맞추는 후속 수정은 등록 이력에서 찾지 못했다.

## 운영 영수증은 AI 초안 결정 한 건을 보여주지만 화면 행동은 담지 않는다

`OP-106.json`의 세션에서는 `ai_drafts`가 1건, `ai_drafts_reviewed`가 1건 늘었다. `review_tasks`와 `review_tasks_completed`의 증가는 0이다. 따라서 운영 영수증은 현재 화면이 쓰는 AI 초안 원장 쪽에서 생성과 결정이 발생했다는 사실에는 맞는다. 과거 핵심 경로 시험의 review_tasks 완료를 운영에서 반복한 것은 아니다.

영수증에는 `draft_id`, `reviewer_id`, 판단 상태, 서버 응답, 방문 주소가 없다. 브라우저에서 약사가 초안을 읽고 버튼을 눌렀는지, 연구용 이름 입력을 썼는지, API를 직접 호출했는지도 구분할 수 없다. 파일에는 내용 지문과 서명 문자열이 있으나, 이번 검토는 서명 진위를 외부 키로 확인하지 않았다. `pharmacist_review` 행동 하나를 OP-087, OP-103~106에 함께 연결하는 일반 매핑이 요구사항별 직접 관찰을 대신하고 있다.

## 현재 단계와 남은 검증

두 큐의 API와 저장 규칙은 구현돼 있고, `review_tasks`는 로컬 두 프로세스 왕복, `ai_drafts`는 API 집중 시험과 운영 테이블 증가로 확인됐다. 그러나 한 시험이 현재 화면에서 로그인, 목록 조회, 결정 제출, 같은 초안 행의 변경까지 연속해서 증명하지 않는다. 그러므로 직접 확인된 최상위 단계는 `INTEGRATED`이며, 요구사항 장부의 `OPERATED`는 아직 충분한 근거가 없다.

다음 증거는 AI 초안 경로 하나로 범위를 고정해야 한다. 인증된 약사 세션이 `/pharm`에서 대기 `draft_id`를 보고 승인·수정 승인·반려 중 하나를 제출한 뒤, 같은 ID의 `review_status`, `reviewer_id`, `reviewed_at`, 수정 차이 또는 반려 이유가 바뀌었음을 한 기록에 묶어야 한다. 검토자 이름 초기값을 사용했는지와 세션 신원이 누구였는지도 남아야 실제 사람 판단을 코드 실행과 구분할 수 있다.
