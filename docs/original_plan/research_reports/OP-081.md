# OP-081 근거 문서를 passage 단위로 수집하고 출처와 시행일을 보존한다.

## 요구사항을 실제 시스템 문제로 해석한 결과

OP-081의 원문은 “근거 문서를 passage 단위로 수집하고 출처와 시행일을 보존한다”이다. 이 요구사항은 문서 파일을 폴더에 넣어 두라는 뜻이 아니다. 상담 시스템이 질문에 답할 때 어떤 문서의 어느 부분을 사용했는지, 그 문서가 언제부터 유효했는지, 현재 시점에도 사용할 수 있는지를 다시 확인할 수 있어야 한다는 뜻이다. 문서 제목이나 URL만 저장하면 같은 문서 안의 서로 다른 주장들을 구분하지 못한다. 반대로 문장만 잘라 저장하고 출처를 잃으면 답변이 그럴듯해도 누가 언제 발표한 근거인지 설명할 수 없다. 따라서 passage 본문과 안정적인 식별자, 원문 출처, 문서 유형, 절이나 표 위치, 줄 범위, 라이선스 상태, 시행일과 폐기일이 하나의 검증 가능한 기록으로 묶여야 한다.

이 문제는 건강 상담에서 특히 중요하다. 같은 성분이라도 일반적인 기능 설명과 약물 상호작용 경고는 근거의 성격이 다르다. 과거 지침이 새 지침으로 대체된 경우에는 검색어가 잘 맞는다는 이유만으로 폐기된 passage를 현재 답변에 사용해서도 안 된다. 안전과 효과를 다루는 문장은 출처와 유효 시점을 잃는 순간 검증 가능한 근거가 아니라 이름 없는 텍스트 조각이 된다. OP-081은 이후 OP-083의 제한 검색과 OP-084의 답변 citation이 의존할 토대를 만드는 요구사항으로 해석했다.

## 이미 존재하던 지식 경로와 부족했던 부분

R&D 저장소에는 새 지식 저장소를 만들 필요가 없을 만큼 많은 기반이 이미 있었다. `data/parsed_references/reference_claims_v1.jsonl`에는 claim ID, reference ID, 주장 본문, citation excerpt, 원문 줄 시작과 끝, 성분·약물·도메인 키가 저장되어 있었다. `data/knowledge/reference_knowledge_base_v1.json`에는 reference ID별 출처 제목, 출처 유형, 원문 URI, 파싱된 로컬 원문, 라이선스 상태, 시행일과 폐기일이 있었다. `data/knowledge/runtime_knowledge_db_v1.json`과 `runtime_db.py`는 이 자료를 추천과 안전 규칙이 사용할 수 있는 구조화 지식으로 변환했다. SQLite interim 저장소에도 `source_registry`와 `evidence_passages`가 이미 있으므로 별도의 상담 전용 데이터베이스를 만드는 것은 기존 시스템을 중복하는 잘못된 선택이었다.

기존 `chat/retrieval.py`와 `build_chat_retrieval_assets.py`도 claim을 `RetrievalChunk`로 바꾸는 경로를 제공했다. chunk에는 claim ID, reference ID, 출처 제목, 출처 유형, 절 위치, URI, 주장과 excerpt가 들어 있었다. 그러나 라이선스 상태, 시행일, 폐기일, 실제 줄 범위가 chunk 계약에 없었다. 빌더는 parsed claim 한 줄만 읽었기 때문에 reference registry에 같은 출처가 실제로 등록됐는지, claim에 적힌 제목과 URI가 registry와 일치하는지도 확인하지 않았다. 검색 결과에서 claim과 reference를 찾을 수는 있었지만, 특정 시점에 사용할 수 있는 passage인지 판단할 정보가 부족했다.

## 선택한 설계와 기존 시스템 재사용 방식

이번 구현은 `RetrievalChunk`를 없애거나 새로운 인덱스 형식을 만들지 않고 기존 계약을 확장했다. 각 chunk는 기존 식별자를 그대로 유지하면서 `license_status`, timezone이 포함된 `effective_at`, 선택적인 `retired_at`, `line_start`, `line_end`를 필수 lineage로 갖는다. `chunk::<claim_id>`라는 기존 식별 방식도 유지했다. 다음 bounded RAG 단계가 현재 corpus와 테스트를 그대로 사용하면서 허용 범위만 추가할 수 있게 하기 위해서다.

Pydantic 계약은 추가 필드를 임의로 허용하지 않고 frozen 상태를 사용한다. 시행일에 timezone이 없으면 거부하고, 폐기일이 시행일보다 빠르거나 같으면 거부한다. 끝 줄이 시작 줄보다 앞서도 거부한다. `RetrievalCorpusManifest`는 선언한 chunk 수와 실제 배열 길이가 다르거나 chunk ID가 중복되면 생성되지 않는다. 파일에 숫자만 적어 놓고 실제 passage 개수와 다른 상태를 통과시키지 않기 위한 방어다.

빌더는 이제 claim 파일과 reference registry를 함께 읽는다. reference ID가 registry에 없으면 `claim_reference_not_registered`로 중단한다. 동일 reference ID가 두 번 나타나도 중단한다. claim의 출처 제목, 유형, 절 위치, URI가 registry 값과 하나라도 다르면 `claim_reference_identity_mismatch`로 중단한다. 검증을 통과한 뒤에만 registry의 라이선스와 시행일·폐기일, claim의 citation 줄 범위를 한 chunk로 결합한다. 따라서 출처 정보를 claim 쪽에서 임의로 복제해 신뢰하는 대신 이미 운영 중인 reference artifact를 권위 있는 원천으로 재사용한다.

독립 검토는 첫 구현이 `line_start`와 `line_end` 숫자를 복사하기만 하고 실제 파싱 원문과 대조하지 않는다는 결함을 찾았다. 숫자가 파일 길이 안에 있는지조차 확인하지 않으면 겉으로는 줄 범위가 있어도 다른 주장이나 존재하지 않는 줄을 가리킬 수 있다. 수정된 빌더는 `parsed_source_uri`도 chunk에 보존하고, 경로를 저장소 루트에 대해 해석한 뒤 루트 밖으로 벗어나는 경로를 거부한다. 실제 UTF-8 원문을 읽어 시작 줄과 끝 줄이 파일 범위 안에 있는지 확인하고, 선택된 줄 안에 정확한 `claim_id`와 `claim_text`가 함께 존재해야만 passage를 만든다. 회귀 테스트는 정상 claim의 줄 범위를 1~2줄로 바꿔 두 identity가 없는 범위를 가리키게 한 뒤 `claim_source_span_identity_mismatch`가 발생하는지 확인한다. 이 검증 덕분에 canonical evidence의 줄 범위 완전성은 숫자 형식만 맞춘 결과가 아니라 실제 committed source와 연결된 결과다.

검색 함수에는 선택적인 `as_of` 시점을 추가했다. `as_of`가 시행일보다 이르면 passage를 반환하지 않고, 폐기일에 도달했거나 지난 passage도 반환하지 않는다. `as_of` 자체가 timezone 없는 시각이면 거부한다. 이 기능은 현재 모든 자료가 현행이라는 가정에 기대지 않고, 앞으로 지침이나 내부 정책이 폐기될 때 같은 corpus 재생에서 올바른 passage만 선택할 수 있게 한다.

## 구현 과정에서 확인한 실패와 수정

계약과 빌더를 확장한 뒤 기존 retrieval 테스트의 chunk fixture가 새 필수 필드를 갖지 않아 처음에는 모델 검증을 통과하지 못했다. 이 문제를 기본값으로 감추지 않았다. 모든 fixture에 라이선스, timezone이 있는 시행일, 실제 줄 범위를 명시하여 테스트도 production 계약과 같은 입력을 사용하도록 고쳤다. 이어서 시행일 timezone 누락, 역전된 줄 범위, manifest count 불일치, 폐기 시점 전후 검색을 각각 회귀 테스트로 고정했다.

전체 retrieval asset을 임시 경로에 다시 만들었을 때 24개 passage와 24개 QA 사례가 생성됐다. 기존 단순 token scoring의 top-1 hit rate는 20.83%, top-3 hit rate는 25.0%였다. 이 낮은 검색 수치를 passage lineage 구현의 성공 숫자로 포장하지 않았다. OP-081은 자료를 정확히 분할하고 출처와 시행일을 보존하는 요구사항이고, 검색을 허용된 범위에 제한하고 랭킹을 개선하는 일은 OP-083의 책임이다. 현재 결과는 lineage가 완전해졌다는 사실과 다음 검색 단계에 실제 품질 공백이 남았다는 사실을 동시에 보여준다.

## canonical smoke가 재현한 내용

`run_counseling_passage_entity_smoke.py`는 committed claim 파일과 reference registry를 직접 읽어 전체 corpus를 다시 만든다. canonical 결과에는 24개 passage와 19개 고유 출처가 기록됐다. 모든 passage에 출처 제목, 공개 URI, 파싱 원문 URI, 라이선스 상태, timezone이 있는 시행일, 실제 원문의 claim identity와 연결된 줄 범위가 존재한다. 현재 artifact에는 폐기된 passage가 없으므로 retired passage count는 0이다. smoke는 2026년 7월 21일 UTC 시점을 고정하고 warfarin·glucosamine 관련 검색이 시행일 조건을 통과한 실제 chunk ID를 반환하는지도 확인한다.

같은 smoke를 서로 다른 임시 파일에 두 번 실행한 결과는 byte-identical이었다. 두 파일의 SHA-256은 모두 `03c0efdc6110208f4e2e185c17524099d5b8fcdc5f27366cf6bd47c5ecb332f4`이다. evidence는 source code 묶음과 세 입력 데이터 파일의 SHA-256을 따로 기록한다. 데이터가 바뀌지 않았는데 코드만 달라진 경우와, 코드가 같지만 reference나 claim이 바뀐 경우를 구분하기 위한 구조다.

## 증명한 단계와 아직 증명하지 못한 범위

OP-081의 required stage는 `IMPLEMENTED`다. 이번 loop는 기존 retrieval 경로에서 passage lineage 계약, 권위 있는 reference registry 결합, 날짜 기반 filtering, 전체 committed artifact 재생, 결정론적 canonical evidence를 직접 검증했다. 따라서 OP-081은 `IMPLEMENTED` 단계에서 COMPLETE로 기록할 수 있다.

그러나 이 결과는 서비스 통합이나 운영을 증명하지 않는다. WellnessBox 채팅이 이 corpus를 호출하지 않았고, 배포된 R&D 프로세스가 passage를 검색하지 않았으며, 운영 중 갱신된 문서를 수집하거나 폐기 처리한 기록도 없다. 외부 기관이 passage 정확성을 검토한 증거도 없다. canonical evidence의 `wellnessbox_service_integration_proven`, `production_operation_proven`, `external_validation_proven`은 모두 false다. 이후 OP-083은 허용 범위와 검색 정확도를, OP-084는 답변이 evidence ID와 유효일을 실제로 반환하는지를 별도로 증명해야 한다.
