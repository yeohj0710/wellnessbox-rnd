# OP-077 중복 작업, 오래된 근거, timeout, 동의 누락을 fail-closed로 처리한다.

OP-077은 처리 조건을 확신할 수 없는 업무를 자동으로 계속하지 않는 요구다. 여기서 fail-closed는 중복, 오래된 실행 근거, 동의 상실, 제한 시간 초과(timeout)를 발견하면 업무와 후속 기록을 닫고 사람이 확인할 검토를 만드는 방식이다. manifest가 등록한 `wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`와 관련 시험은 네 경계를 모두 구현하지만, 운영 영수증에는 어느 실패도 발생하지 않아 증거 단계는 `IMPLEMENTED`다.

## 네 상황은 원인이 달라도 같은 안전 결론을 낸다

중복 요청은 같은 일을 두 번 수행할 위험이 있다. 업무 생성 뒤 실행 원장의 근거가 바뀌면 과거 판단 조건으로 만든 입력 내용(payload)을 더는 신뢰할 수 없다. 사용자의 활성 동의가 사라진 뒤 자료를 처리해서도 안 된다. 작업자가 임대 시간 안에 완료하지 못한 경우에는 외부 동작을 일부 수행했는지 알 수 없어 무조건 재실행하기 어렵다. 이 네 조건은 진단 코드는 다르지만 “자동 업무를 완료 상태로 진행하지 않는다”는 불변식을 공유한다.

업무를 중단할 때 대상 한 행만 바꾸면 같은 후속 기록의 다른 준비 업무가 남을 수 있다. `_fail_closed_job_in_transaction()`은 원인 업무를 `CANCELLED`, 원래 후속 기록을 `CLOSED`로 만들고 같은 후속의 `READY`·`CLAIMED` 업무도 취소한다. 이어서 `wellnessbox-rnd/src/wellnessbox_rnd/interim/reviews.py`의 `PharmacistReviewService.create_in_transaction()`으로 원본 업무와 이유 코드를 연결한 `HIGH` 검토를 만든다. 이 변경은 하나의 즉시 트랜잭션 안에서 커밋된다.

## 중복과 내용 충돌을 나누는 저장 규칙

`wellnessbox-rnd/src/wellnessbox_rnd/interim/store.py`의 `workflow_jobs.idempotency_key`는 고유하다. `_enqueue_in_transaction()`이 같은 키와 같은 의미의 payload를 만나면 기존 `job_id`와 `deduplicated=true`를 반환한다. 키가 같은데 계획, 시각, 입력 지문 같은 업무 의미가 달라지면 `workflow_job_idempotency_payload_conflict`로 거부한다. 중복 제거가 새 요청을 이전 내용으로 덮어 가리는 수단이 되지 않는다.

선점 단계에서도 한 업무는 한 작업자에게만 간다. `claim_ready_jobs()`는 `READY` 행을 골라 임의 claim token, `CLAIMED` 상태, `lease_until`, 증가한 `attempt_count`를 같은 트랜잭션에서 기록한다. 두 번째 작업자는 이미 선점된 행을 받지 못한다. `acknowledge_job()`은 같은 token과 유효 임대를 요구하므로 다른 작업자가 완료를 대신 기록할 수 없다.

정상 처리 실패 뒤 다시 시도해야 할 때는 `retry_job()`이 원래 작업자의 token과 명시된 다음 시각을 요구한다. 자동 임대 만료와 의도적인 재시도는 같은 상태 전이가 아니다. 전자는 안전 폐쇄, 후자는 오류를 인지한 작업자가 새 실행 시점을 고른 명시적 조치다.

## 동의와 실행 근거를 두 번 대조한다

업무 생성 시 저장한 `consent_snapshot_id`는 선점 시점의 활성 동의와 비교한다. 동의가 없거나 식별자가 달라지면 `CONSENT_NOT_ACTIVE`로 닫는다. `execution_evidence_sha256`은 해당 실행의 활성 이벤트들을 `event_id`와 `effective_payload_sha256` 순서로 묶어 계산한 지문이다. 새 계획 조정이나 중단으로 그 값이 달라지면 `STALE_EXECUTION_EVIDENCE`를 남긴다.

검사는 `claim_ready_jobs()`에만 있지 않다. 작업자가 선점한 직후 동의나 근거가 바뀌는 시간차를 잡기 위해 `acknowledge_job()`이 완료 커밋 전에 두 값을 다시 읽는다. 두 번째 검사에서 불일치하면 함수는 오류를 반환하면서도 취소·후속 종료·검토 생성은 커밋한다. 실패 예외 때문에 안전 상태 변경까지 되돌아가지 않도록 트랜잭션 반환 경계를 분리한 구현이다.

정확한 예약 재전송도 오래된 기준을 새 값으로 씻어 내지 못한다. 비교 단계에서는 안전 지문 필드를 제외해 본래 요청이 같음을 확인하되, 기존 업무 행의 원래 지문은 보존한다. 그래서 재전송 뒤에도 선점 시 현재 근거와 비교되어 오래된 업무가 취소된다.

## 자동 재실행에서 안전 폐쇄로 바뀐 이력

커밋 `21dade`가 claim token과 임대 시간을 도입했을 때, 만료된 `CLAIMED` 행은 `LEASE_EXPIRED` 이유로 다시 `READY`가 되어 자동 선점될 수 있었다. 작업자가 외부 효과를 낸 뒤 완료 확인만 하지 못한 상황에서는 같은 일을 반복할 수 있는 정책이었다. 커밋 `bd2429`는 만료 행을 `WORKFLOW_JOB_TIMEOUT`으로 취소하고 후속 종료와 검토 생성을 한 트랜잭션에 묶었다. 같은 커밋에서 동의와 근거 지문을 생성·선점·완료에 연결했다.

커밋 `932358`은 정확한 예약 재시도가 당시 최신 안전 지문으로 기존 업무를 사실상 갱신할 수 있던 경계를 수정했다. 현행 비교는 요청의 업무 의미와 안전 기준을 분리하며, 원래 guard를 보존한다. 이 변화는 “재시도 요청이 같음”과 “처리 근거가 아직 유효함”을 별개 질문으로 취급한다.

저장소에서 실제 운영 작업이 이중 실행된 사고 기록은 찾지 못했다. 따라서 이전 자동 재등록이 실제 피해를 냈다고 주장하지 않고, diff에서 확인되는 전 정책과 현재 실패 회귀가 막는 위험을 구분한다.

## 단위 시험이 확인하는 선점·취소·검토

`wellnessbox-rnd/tests/test_interim_jobs.py`의 `test_claim_ack_and_explicit_retry`는 첫 작업자만 업무를 받고 잘못된 token의 완료가 거부되며, 명시적 재시도 뒤 다시 선점·완료할 수 있는지를 검사한다. `test_expired_claim_fails_closed_and_creates_one_review`는 60초 임대를 61초 넘긴 행이 재선점되지 않고 `CANCELLED`, 후속은 `CLOSED`, 검토는 정확히 한 건인지 단언한다.

`test_stale_evidence_and_consent_loss_fail_closed`는 근거 변경과 동의 제거를 별도 업무에서 재현하고 각각의 오류 코드와 검토 생성을 본다. `test_exact_schedule_retry_keeps_original_guard_for_fail_closed_claim`은 같은 예약을 다시 보낸 후 기존 업무의 원래 지문이 유지되고 선점 단계에서 안전 폐쇄되는지를 확인한다. `test_acknowledgement_rechecks_evidence_and_commits_cancellation`은 선점 후 근거를 바꾼 뒤 완료 호출이 실패하며 데이터베이스 취소 상태가 실제로 남는지를 검증한다.

`wellnessbox-rnd/tests/test_interim_reviews.py`는 여기서 생성된 검토가 결정적으로 같은 ID를 사용하고, 원본 추적 정보(provenance)를 저장하며, 완료 전 원본 업무가 `CANCELLED`인지 확인하는 후속 불변식을 다룬다. OP-077의 핵심은 검토 판단 자체보다 자동 처리를 멈추고 사람이 확인할 원인 기록을 원자적으로 여는 데 있다.

## 고정 스모크의 다섯 시나리오

`wellnessbox-rnd/scripts/run_fail_closed_job_pharmacist_review_smoke.py`의 출력 `wellnessbox-rnd/data/original_plan/evidence/op077_op078_fail_closed_job_review_smoke_v1.json`은 중복 예약을 두 번 넣어도 저장 업무 1건, 첫 선점 1건, 둘째 선점 0건임을 기록한다. 오래된 근거 사례는 업무 `CANCELLED`, 후속 `CLOSED`, 검토 1건이다. 동의 제거 사례도 `CONSENT_NOT_ACTIVE`로 취소되고, 임대 만료 사례는 `WORKFLOW_JOB_TIMEOUT`으로 닫힌다. 정확한 재요청이 기존 업무를 반환했다는 결과도 따로 있다.

이 JSON은 `op077_proven_stage=IMPLEMENTED`이며 배포 작업자, 프로덕션 안전 폐쇄, 서비스 연동과 배포를 증명하지 않았다고 쓴다. `source_commit=24d82df`에서 계산한 묶음 해시 `3038be…`은 현행 관련 파일의 `781e88…`과 다르다. 결과의 시점과 현재 파일 버전을 섞지 않고, 현행 보강은 위 테스트와 코드에서 확인했다.

## 현재 판정과 아직 없는 장애 증거

운영 경로 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-077.json`에는 로컬 `ACTUAL` 세션과 업무 1건 증가가 있으나 중복 수, `STALE_EXECUTION_EVIDENCE`, `CONSENT_NOT_ACTIVE`, `WORKFLOW_JOB_TIMEOUT` 어느 것도 없다. `review_tasks` 증가도 0이어서 안전 폐쇄가 운영 중 발생했다고 연결할 수 없다. manifest의 `claimed_stage=OPERATED`보다 직접 내용이 낮은 이유다.

현재 단계는 `IMPLEMENTED`다. 확인되지 않은 항목은 여러 운영 작업자의 시계 차이, 프로세스 강제 종료 전후 외부 효과, 외부 동의 시스템의 지연 반영, 실제 검토 대기 시간, 장애 뒤 수동 재시도 승인 절차다. `OPERATED`로 승격하려면 각 실패 업무의 식별자, 생성 당시 안전 기준(guard), 실패 시 현재 값, 취소 시각, 닫힌 후속 기록, 검토 식별자를 같은 운영 사건으로 보존해야 한다.
