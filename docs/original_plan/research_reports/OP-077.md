# OP-077 중복 작업, 오래된 근거, timeout, 동의 누락을 fail-closed로 처리한다.

manifest가 지정한 회귀 증거는 `wellnessbox-rnd/data/original_plan/evidence/op077_op078_fail_closed_job_review_smoke_v1.json`이며, 네 가지 중단 규칙은 `wellnessbox-rnd/src/wellnessbox_rnd/interim/jobs.py`에서 확인했다.

## 불확실한 업무는 다시 실행하지 않고 닫아야 한다

후속 업무가 중복됐거나, 업무 생성 뒤 근거·동의가 바뀌었거나, 작업자가 제한 시간 안에 끝내지 못했다면 원래 판단 조건을 신뢰할 수 없다. 이런 업무를 자동 재시도하면 취소된 동의를 사용하거나 오래된 계획으로 새 추천을 만들 수 있다. OP-077은 네 상황을 구분해 기록하되, 안전 결론은 모두 “자동 실행을 계속하지 않는다”로 통일한다. 이것이 문제가 있으면 멈추는 방식(fail-closed)이다.

## 중복은 합치고 의미가 다른 재요청은 거부한다

업무 큐는 `idempotency_key`에 고유 제약을 둔다. 요청 내용까지 같으면 기존 작업을 반환하고 `deduplicated=true`로 표시한다. 첫 작업자가 선점한 행은 `CLAIMED`가 되므로 두 번째 작업자는 같은 행을 가져가지 못한다. 반면 멱등 키는 같지만 계획·입력·시각이 달라지면 `workflow_job_idempotency_payload_conflict` 또는 더 구체적인 충돌 오류가 난다. 중복 제거가 값 변경을 숨기는 덮어쓰기로 변하지 않게 한 것이다.

동의와 근거는 업무를 만들 때 지문으로 고정한다. 동의 기록 식별자는 현재 활성 동의와 비교하고, 실행 원장의 활성 이벤트 목록은 지문 값(SHA-256)으로 다시 계산한다. 둘 중 하나가 바뀌면 각각 `CONSENT_NOT_ACTIVE`, `STALE_EXECUTION_EVIDENCE`로 취소한다. 이 검사는 작업 선점 때 한 번, 완료 확인 때 다시 한 번 수행한다. 선점 직후 근거가 바뀌는 시간차 문제도 완료 처리 전에 잡는다.

## 제한 시간을 넘긴 업무를 무한 재시도하지 않는다

`claim_ready_jobs()`는 `lease_until`이 지난 `CLAIMED` 업무를 발견하면 `WORKFLOW_JOB_TIMEOUT`으로 취소한다. `retry_job()`은 작업자가 오류를 알고 새 시각을 명시한 경우에만 다시 `READY`로 돌린다. 만료된 선점을 자동 재등록하지 않는 이유는 처리 도중 일부 외부 동작이 끝났는지 알 수 없기 때문이다. 자동 재실행 대신 원래 후속 기록을 닫고 같은 후속 묶음의 나머지 준비·선점 업무도 취소한다.

모든 안전 중단은 `PharmacistReviewService.create_in_transaction()`을 호출해 이유 코드를 가진 검토 작업을 만든다. 작업 취소, 후속 종료, 관련 업무 취소, 검토 생성은 한 트랜잭션 안에 있다. 현재 자료에는 이 방식을 채택하기 전 timeout 작업이 실제로 이중 실행된 기록은 확인되지 않음이다. 조사 결과는 현행 소스, 실패 사례를 고정한 테스트, 기준 실행 출력에 한정한다.

## 다섯 사례가 서로 다른 실패 경계를 보여 준다

등록된 기준 실행의 `duplicate_execution`은 같은 예약을 두 번 넣어도 저장 업무가 1건이고 첫 작업자만 1건을 선점하며 두 번째 작업자는 0건을 받았다고 기록한다. `stale_execution_evidence`는 근거 지문을 바꾼 뒤 업무와 후속 기록이 각각 `CANCELLED`와 `CLOSED`가 되고 검토가 1건 생긴 결과다. 활성 동의를 지운 사례도 `CONSENT_NOT_ACTIVE`로 실행 전에 취소된다. 60초 임대가 지난 사례는 61초 시점에 다시 가져오지 않고 `WORKFLOW_JOB_TIMEOUT`으로 닫힌다.

`tests/test_interim_jobs.py`는 선점 뒤 근거가 바뀐 경우 완료 확인이 `stale_execution_evidence`를 내고 취소 상태를 실제로 저장하는지도 다룬다. 이미 중단된 계획의 업무는 Cron 생성 시점과 작업 선점 시점 모두에서 제외한다. 따라서 기준 실행의 성공 숫자만이 아니라 중간 시점에 상태가 바뀌는 조건도 회귀 시험에 포함돼 있다.

## 로컬 안전 규칙은 구현됐지만 운영 장애 이력은 없다

manifest는 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-077.json`을 운영 근거로 연결했다. 해당 로컬 세션은 `followup` 경로와 업무 1건 증가를 보여 주지만, 중복 건수·동의 상실·근거 변경·시간 초과 중 어느 조건도 기록하지 않는다. `review_tasks`와 완료 검토 증가량도 0이다. 이 영수증만으로 운영 중 안전 중단을 관측했다고 볼 수 없다.

따라서 직접 입증 단계는 `IMPLEMENTED`다. 여러 업무 처리 프로그램이 장기간 돌아가는 환경의 시계 차이, 프로세스 강제 종료 뒤 임대 회수, 외부 동의 시스템 지연, 운영 검토자의 처리 결과는 확인되지 않음이다. `OPERATED` 근거에는 실패 이유별 업무 ID, 취소 시각, 후속 종료, 연결된 검토 ID가 함께 남아야 한다.
