# OP-112 개인정보 최소수집·가명처리·로그 마스킹 검증 연구보고서

## 결론

OP-112는 요구 단계 `INTEGRATED`에 도달했다. WellnessBox가 R&D 요청을 만들 때 직접 식별자인 이름과 추천 계산에 사용하지 않는 카페인 민감도 원본을 `source_profile`에서 제거한다. 사용자 식별자는 서버 소유 AppUser ID를 그대로 보내지 않고 환경별 salt를 사용하는 HMAC-SHA256 가명 식별자로 바꾼다. 로그용 값은 자격증명·쿠키·이메일·이름·전화번호·비밀·토큰 키를 재귀적으로 마스킹하고, 문자열 안의 Bearer 토큰·이메일·전화번호도 가린다. 예상하지 못한 오류 문자열은 외부 응답에 그대로 내보내지 않는다.

이번 결과는 로컬 통합 검증이다. 운영 로그 수집기, APM, CDN 로그, 데이터 웨어하우스, 고객지원 도구를 조사하지 않았다. 따라서 운영 로그 전체에서 개인정보가 없다고 주장하지 않는다. 실제 서비스 어댑터와 오류 응답 경계, 실제 R&D HTTP 요청에 적용되는 최소수집·가명처리 정책을 검증했다.

## 최소수집 원칙을 코드 조건으로 바꾼 방법

최소수집은 “필드를 적게 보낸다”는 추상적 선언이 아니다. R&D 추천 계약이 소비하는 필드와 소비하지 않는 필드를 구분해야 한다. 연령, 생물학적 성별, 임신·수유 여부, 키, 체중, 목표, 질환, 약물, 알레르기, 식이 제한은 추천 요청의 명시적 입력으로 매핑된다. 이름은 추천 계산이나 동의 판정에 사용되지 않는 직접 식별자다. 카페인 민감도는 현재 R&D 계약의 어떤 계산 필드로도 매핑되지 않는다. 두 필드는 서비스 입력 검증에는 존재할 수 있지만 R&D `source_profile.profile`에는 넣지 않는다.

서비스는 원본 프로필을 수정하지 않는다. 구조 분해로 `name`과 `caffeineSensitivity`를 분리하고 남은 허용 필드만 새 객체로 복제한다. 기존 어댑터 계약 fixture는 원본 입력에 두 필드를 계속 포함한다. 따라서 테스트는 입력이 허용되는 사실과 출력에서 제거되는 사실을 동시에 검증한다. 알 수 없는 필드는 strict schema가 거부하므로 새 개인정보 필드가 자동으로 R&D에 흘러가지 않는다.

동의도 최소수집 경계에 포함된다. 설문 추천 사용 동의가 없으면 요청 생성 자체를 거부한다. 저장 동의는 추천 사용 동의와 별도로 `allow_persistent_storage`에 기록한다. NHIS, wearable, CGM, genetic 입력은 이 어댑터에서 사용하지 않으므로 추천 사용과 영구 저장을 모두 false로 보낸다.

## 가명처리 설계

가명 식별자는 `usr_` 접두사와 HMAC-SHA256 결과 앞 32자리로 구성한다. 키는 `WB_RND_INTERIM_PSEUDONYM_SALT`에서 읽는다. salt가 없으면 요청을 진행하지 않는다. 단순 SHA-256이 아니라 키 기반 HMAC을 사용하므로 서비스 내부 ID를 아는 사람이 저장된 가명값을 사전 계산하기 어렵다. 같은 환경과 같은 사용자에서는 결과가 안정적이어서 실행·계획·검토 계보를 연결할 수 있다.

가명처리는 익명화와 다르다. 서비스가 salt와 원래 AppUser ID를 관리하므로 동일 사용자를 다시 연결할 수 있다. 보고서와 evidence는 이를 익명 데이터라고 부르지 않는다. 목적은 R&D 저장소가 서비스의 직접 사용자 ID, 카카오 ID, 전화번호를 받지 않도록 경계를 줄이는 것이다.

브라우저가 `profile_id`를 직접 보내도 서비스는 그 값을 무시한다. 세션에서 얻은 AppUser ID를 서버에서 가명처리한다. canonical smoke는 공격자 값 `usr_attacker`가 실제 R&D 본문에 남지 않는지 확인한다. 인증 결과에 전화번호가 포함돼 있어도 R&D 요청 본문에는 전화번호를 추가하지 않는지 함께 확인한다.

## 로그 마스킹과 오류 제한

`lib/server/wb-rnd-security.ts`는 구조화 로그에 사용할 재귀 마스킹 함수를 제공한다. 키 이름에 authorization, cookie, email, name, phone, secret, token이 포함되면 값 전체를 `[REDACTED]`로 바꾼다. 배열과 중첩 객체를 재귀 처리한다. 일반 문자열 안에서도 Bearer 자격증명, 이메일 주소, 한국 휴대전화 형식을 찾아 가린다. 실제 프록시 오류와 관리자 KPI fallback은 이 함수가 적용된 운영 오류 기록 함수를 호출한다.

마스킹 함수만 추가하고 호출 경계가 없다면 통합 증거가 약하다. 이번 작업은 같은 보안 모듈의 `publicWbRndErrorCode`를 실제 R&D 프록시 오류 처리에 연결했다. timeout, 제한된 어댑터 오류 코드, 상류 HTTP 상태 코드만 외부 응답으로 허용한다. 환자 이름이나 이메일이 섞인 임의 예외 메시지는 `R&D request failed`로 바뀐다. 추천 fail-closed 응답도 같은 제한 함수를 사용한다.

canonical 사례는 authorization, email, 중첩 phone, 문자열 안 이메일을 동시에 넣고 모두 마스킹되는지 확인한다. 또 `patient person@example.com`이라는 예외 메시지가 공개 응답 코드로 선택되지 않는지 검사한다. 이 검사는 문자열 검색이 아니라 실제 함수를 실행한다.

## 데이터셋과 증거

데이터셋은 `data/original_plan/op111_op112_security_boundary_cases_v1.json` 8건이다. OP-112에 직접 대응하는 사례는 가명처리, 최소수집, 로그 마스킹, 제한된 오류다. 사용자 역할 사례도 서버 소유 가명 ID와 전화번호 비전달을 검증하므로 OP-112 증거에 포함된다.

canonical evidence는 `data/original_plan/evidence/op111_op112_security_boundary_smoke_v1.json`이다. `direct_identifier_removed`, `unused_field_removed`, `deterministic_pseudonym_used`, `logs_masked`, `public_errors_bounded`가 모두 true여야 한다. 증거는 데이터셋 SHA-256, 서비스 커밋, 보안 관련 서비스 파일별 Git blob, R&D 내부 인증 라우트의 소스 커밋을 기록한다.

서비스 소스 커밋은 `1912f127a02d158a159ed7edd135f389308a1e6e`다. 이 커밋은 profile adapter 출력뿐 아니라 실제 `/profiles` 저장 프록시에 strict schema를 적용한다. 중첩 profile의 이름·이메일·전화번호와 알 수 없는 필드는 R&D 호출 전에 거부된다. 원본 adapter 입력 fixture에는 이름과 카페인 민감도가 남아 있고 expected R&D request에서는 제거된다.

## 회귀 위험과 방어

첫 번째 위험은 새로운 프로필 필드가 자동으로 `structuredClone(profile)`을 통해 R&D에 전달되는 것이다. 이번 구현은 이름과 현재 미사용 필드를 명시적으로 제외했지만, 장기적으로는 허용 필드를 명시적으로 구성하는 방식이 더 강하다. source schema가 strict이므로 알 수 없는 필드는 현재 fail-closed되며, 계약 fixture가 출력 전체를 exact match한다.

두 번째 위험은 가명 salt 누락 또는 환경 간 공유다. 클라이언트는 salt가 없으면 실패한다. 그러나 salt 길이, 회전 정책, 환경별 분리는 현재 배포 계약과 운영 비밀 관리에 의존한다. 이번 smoke는 canonical salt로 결정성을 검증할 뿐 운영 salt 품질을 증명하지 않는다.

세 번째 위험은 다른 로그 경로다. 이번 마스킹은 R&D 프록시 보안 모듈과 오류 응답 경계에 적용된다. Prisma query log, Next.js 플랫폼 log, reverse proxy, 브라우저 console, 외부 APM은 별도 조사 대상이다. 운영 로그 전체 검증은 OP-112의 향후 운영 증거로 남는다.

네 번째 위험은 마스킹 과잉이다. `name`을 포함한 키는 사용자 이름뿐 아니라 일반 이름 필드도 가릴 수 있다. 보안 로그에서는 보수적으로 가리는 선택이지만, 운영 진단에 필요한 비식별 이름까지 사라질 수 있다. 필요한 경우 허용된 진단 필드를 별도 구조로 정의해야 하며 민감 키 예외를 임의로 늘리면 안 된다.

## 재현성과 CI

서비스에서 profile adapter QA를 실행하면 원본 입력의 불변성, strict schema, 동의, 목표 매핑, exact request forwarding과 최소화된 expected request를 확인한다. typecheck와 인코딩 감사는 새 TypeScript와 한국어 fixture가 정상인지 확인한다. R&D runner는 실제 FastAPI 프로세스를 시작하고 서비스 Node QA를 실행한다.

GitHub Actions는 서비스 커밋 `1912f127a02d158a159ed7edd135f389308a1e6e`를 `_evidence/wellnessbox-op112`에 checkout한다. 의존성을 설치하고 동일 runner를 실행하며 canonical evidence diff를 검사한다. requirement audit와 completion report check도 이 최신 checkout을 사용한다. 이전 OP-103~110 smoke는 각자의 고정 서비스 checkout을 계속 사용하므로 과거 증거를 최신 코드로 잘못 재해석하지 않는다.

## 단계 경계

실제 서비스 경로의 인증 허용·거부 분기와 실제 R&D HTTP 토큰 왕복이 로컬에서 실행됐다. 역할 guard 구현은 소스 계약으로 회귀 검증했다. `production_identity_provider_operation_proven=false`는 운영 계정 인증을 실행하지 않았다는 뜻이다. `production_log_sink_inspection_proven=false`는 운영 로그 저장소를 검사하지 않았다는 뜻이다.

개인정보 최소수집과 가명처리의 서비스 경계는 통합됐지만, 데이터 보존기간, 삭제 요청, 키 회전, 접근 감사, 운영 백업, 외부 처리자 계약은 이번 요구의 canonical smoke에서 검증하지 않았다. 이 보고서는 그 항목을 완료로 주장하지 않는다.

## 최종 판정

OP-112는 실제 서비스 프로필 어댑터, 가명 식별자, 보안 마스킹 함수, 실제 프록시 오류 경계를 실행하고 별도 R&D HTTP 프로세스와 함께 재현했으므로 `INTEGRATED`다. 요구 단계와 같아 COMPLETE다. 운영 로그 전체 조사와 운영 비밀·신원 제공자 검증이 없으므로 `OPERATED`로 높이지 않는다.
