# OP-007 IMPLEMENTED, INTEGRATED, OPERATED, EXTERNAL 증거 단계를 Pydantic 스키마로 고정한다.

## 구현됐다는 말과 운영됐다는 말은 서로 다른 사실이다

코드가 저장소에 들어간 상태와 실제 서비스에서 사용된 상태는 같지 않다. 로컬 테스트가 통과해도 두 저장소가 실제 요청을 주고받지 않았을 수 있다. 통합 테스트가 있어도 production에서 입력을 받고 결과를 다시 조회한 기록은 없을 수 있다. 외부 약사나 시험기관이 확인해야 하는 결과를 내부 합성 데이터로 대신할 수도 없다. OP-007이 요구하는 실제 결과는 이런 차이를 문장 표현에 맡기지 않고 `IMPLEMENTED`, `INTEGRATED`, `OPERATED`, `EXTERNAL` 네 값으로 고정하는 것이다.

이 요구는 `original_plan.pdf`에 적힌 한 문장을 그대로 구현한 항목이 아니다. 원본 25~26쪽은 추천, 실제 효과, 다음 행동, 상담, 안전 레퍼런스, 이상반응, 센서·유전자 연동이라는 일곱 KPI를 수식과 최소 표본으로 정의한다. 원본 전체를 구현했다고 주장하려면 KPI 계산 코드뿐 아니라 통합, 운영, 외부 평가 여부도 구분해야 한다. 그래서 manifest의 A그룹은 원본 전체 1~59쪽을 출처로 삼되, OP-007을 완료 증거를 관리하기 위한 저장소 거버넌스 요구로 분해했다.

## 단계 계약은 strict Pydantic 모델 안에 있다

구현 증거 `wellnessbox-rnd/src/wellnessbox_rnd/schemas/original_plan_manifest.py`의 `EvidenceStage`는 네 값만 허용하는 `StrEnum`이다. `DONE`, `COMPLETE`, `VERIFIED`처럼 사람마다 다르게 해석할 수 있는 단어는 모델 검증을 통과하지 못한다. `OriginalPlanRequirementDraftV1`과 materialize된 `OriginalPlanRequirementV1`의 `required_stage`와 `claimed_stage`도 같은 enum을 사용한다. 요구 단계와 현재 주장 단계를 서로 다른 필드에 두므로 “현재 구현됐다”는 사실을 “요구된 운영 단계까지 끝났다”는 뜻으로 읽지 않는다.

모든 manifest 모델은 `extra="forbid"`를 사용하는 `_StrictManifestModel`을 상속한다. 따라서 `is_done=true`나 `manual_verified=yes` 같은 우회 필드를 몰래 추가할 수 없다. 요구사항 ID는 `OP-` 뒤 세 자리 숫자, 그룹 ID는 A~L, 원본 hash는 소문자 64자리 16진수로 제한된다. 단계 어휘만 고정한 것이 아니라 단계 판단에 쓰이는 레코드 모양도 함께 고정했다.

## IMPLEMENTED는 구현 파일과 테스트 파일을 함께 요구한다

`RequirementEvidenceV1`은 구현 파일, 테스트 파일, 통합 증거, 운영 증거, 외부 의존성, 교체 계약을 별도 목록으로 저장한다. `validate_requirement_evidence_v1`은 `IMPLEMENTED`, `INTEGRATED`, `OPERATED` 주장에 구현 파일과 테스트 파일이 모두 있는지 확인한다. 둘 중 하나라도 비면 `implemented_claim_missing_implementation_files` 또는 `implemented_claim_missing_test_files`를 낸다. 코드만 있거나 테스트만 있는 항목은 구현 완료로 등록할 수 없다.

OP-007 자체의 manifest 레코드는 required stage와 claimed stage가 모두 `IMPLEMENTED`다. 구현 경로는 위 Pydantic schema이고 테스트 경로는 `wellnessbox-rnd/tests/test_original_plan_manifest.py`다. 이 두 경로는 현재 Git에 추적돼 있다. 따라서 OP-007은 자신이 정의한 최소 구현 계약도 같은 방식으로 통과한다.

## INTEGRATED와 OPERATED는 증거 목록이 누적된다

`INTEGRATED`를 주장하려면 구현·테스트에 더해 `integration_evidence`가 필요하다. 이 목록은 두 저장소 또는 두 실제 프로세스가 연결된 결과처럼 구현 파일만으로 증명할 수 없는 왕복을 담는다. `OPERATED`는 같은 조건에 `operational_evidence`까지 요구한다. production traffic, 실제 저장 결과, 운영 환경의 사후조건처럼 로컬 E2E가 대신할 수 없는 사실을 별도 경로로 남기기 위한 칸이다.

단계 비교는 문자열 정렬로 처리하지 않는다. validator가 각 단계에 필요한 목록을 명시적으로 검사한다. 이 방식은 enum 순서가 바뀌거나 `EXTERNAL`을 일반적인 상위 단계로 오해하는 문제를 피한다. `INTEGRATED`가 `IMPLEMENTED` 증거를 포함하고, `OPERATED`가 두 단계의 증거를 모두 포함한다는 규칙이 코드의 집합 조건으로 드러난다.

## EXTERNAL은 운영 다음의 자동 승급 단계가 아니다

내부 enum 이름 `EXTERNAL`은 목표에서 말하는 외부검증 증거를 표시한다. 이 단계는 `OPERATED` 다음에 자동으로 올라가는 서열값이 아니다. 외부 기관이나 전문가가 제공해야 하는 입력을 내부 구현이 만들어낼 수 없기 때문이다. `EXTERNAL`을 주장하려면 `external_dependencies`와 `replacement_contracts`가 모두 있어야 한다. 외부 의존성은 누가 어떤 검증 결과를 제공해야 하는지 기록하고, 교체 계약은 임시 내부 증거를 실제 외부 증거로 바꿀 형식을 지정한다.

대표적인 경계는 OP-039다. 고위험 안전 frozen eval에는 독립 약사 라벨이 필요하다. 내부 합성 라벨과 프록시 점수가 아무리 많아도 외부 라벨이 생기지 않는다. OP-007의 단계 계약은 이 부족을 숨기지 않고 `EXTERNAL` 의존성으로 남길 수 있게 한다. 반대로 `EXTERNAL` 레코드가 존재한다는 사실만으로 외부 검증이 성공했다는 뜻도 아니다. 후속 감사가 등록된 계약과 실제 receipt를 함께 확인해야 한다.

## 그룹 기본값과 개별 덮어쓰기가 120개 요구에 같은 규칙을 적용한다

manifest는 A~L 그룹마다 기본 원문 출처, 소유 저장소, required stage를 둔다. `materialize_original_plan_requirements_v1`은 개별 요구사항에 값이 없으면 그룹 기본값을 복사한다. 특정 OP가 두 저장소를 함께 사용하거나 더 높은 운영 단계를 요구하면 개별 값으로 덮어쓴다. 이 과정이 끝나면 OP-001부터 OP-120까지 모든 레코드가 source refs, owners, required stage를 가진다.

그룹 기본값은 편의를 위한 생략 규칙이지 단계 완화 장치가 아니다. A그룹의 기본 required stage는 `IMPLEMENTED`지만, 다른 그룹은 통합·운영·외부 증거가 필요한 항목을 개별적으로 지정한다. 현재 completion report가 `76 COMPLETE / 43 PARTIAL / 0 PENDING / 1 EXTERNAL / 0 CONTRADICTED`를 보이는 이유도 claimed stage와 required stage를 별도로 비교하기 때문이다. 119개 항목이 어떤 단계를 주장해도 required stage 미달 43개는 완료로 바뀌지 않는다.

## 부정 테스트가 모호한 완료 표현을 실제로 거부한다

테스트 증거 `wellnessbox-rnd/tests/test_original_plan_manifest.py`는 `EvidenceStage`에 `DONE`을 넣었을 때 Pydantic `ValidationError`가 발생하는지 확인한다. 지원하지 않는 `unsupported_completion_flag` 필드도 같은 방식으로 거부한다. 구현 주장에 구현·테스트 목록이 없으면 두 누락 오류가 나오고, 운영 주장에 통합·운영 증거가 없으면 각 오류가 나오는지 검사한다. 외부 주장에 외부 의존성과 교체 계약이 없을 때도 두 오류를 고정한다.

같은 테스트 파일은 현재 manifest가 OP-001~OP-120을 순서대로 포함하고 A~L 그룹을 모두 가지며, 모든 항목에 출처와 소유자가 있는지 확인한다. 현재 claimed-stage 전체 사전을 테스트에 명시해 한 항목이 검토 없이 승격되면 diff와 테스트에서 드러나게 한다. 성공 사례만 확인하는 테스트가 아니라 잘못된 단계 단어와 부족한 증거가 실패하는 경계를 실행한다.

## 입력 오류와 경계값은 조용히 보정하지 않는다

알 수 없는 단계, 알 수 없는 저장소, 형식이 틀린 ID, 빈 그룹 출처, 빈 그룹 소유자, 스키마에 없는 필드는 validation error다. 그룹 순서가 A~L과 다르거나 OP 번호가 001~120 연속열과 다르면 manifest issue가 생긴다. 그룹별 요구사항 수가 10개가 아니어도 실패한다. validator는 잘못된 값을 익숙한 값으로 추정하거나 대소문자를 고쳐주지 않는다.

다만 evidence 목록에 문자열 하나가 있다는 것만으로 그 파일이 실제로 존재하는지는 schema가 확인하지 않는다. 경로가 저장소 밖으로 빠져나가는지, 다른 저장소 파일을 잘못 소유했다고 적었는지도 OP-007의 책임 범위 밖이다. 이 검사는 OP-008 감사기가 맡는다. 단계 어휘와 최소 목록 계약을 정하는 일, 실제 Git 파일을 확인하는 일을 분리했기 때문에 실패 원인을 좁혀 볼 수 있다.

## canonical evidence는 manifest와 원본 hash에서 시작한다

manifest 최상위에는 schema version, 원본 PDF 경로, 원본 SHA-256, completion program 경로가 있다. 현재 원본 hash는 `31291e6f93977fa2d5d083d0161743c49debef25caf12dccf6edc7fa1c2197d4`다. 단계 레코드는 이 고정 원본과 같은 manifest 안에 저장되고 canonical JSON 직렬화로 manifest SHA-256을 계산할 수 있다. key 정렬과 공백 없는 구분자를 사용하므로 같은 manifest는 같은 hash를 낸다.

2026-07-15의 `b96a92d6ff275ed6858ef7737d63a054678bbbad` 커밋은 단계 enum, strict schema, 120개 manifest와 테스트를 함께 도입했다. 현재 원본-plan 감사는 120개 요구, 119개 주장, 333개 evidence 파일을 검사하고 source hash 일치를 확인한다. OP-007의 구현 증거는 별도 임시 파일이 아니라 이 반복 가능한 전체 감사 입력에 포함된다.

## 서비스 통합과 운영 여부는 단계 계약과 별도로 판단한다

OP-007 구현은 R&D 저장소 안의 schema와 테스트만 사용한다. 서비스 저장소 코드를 호출하지 않고 production 환경에도 배포되지 않는다. 이번 보고서 backfill도 서비스의 기존 사용자 변경, 원천 데이터, frozen evaluation, 학습 데이터, 모델, 시뮬레이션을 바꾸지 않는다. 따라서 OP-007의 `IMPLEMENTED` 완료는 증거 단계 계약이 코드로 존재하고 실패 경계가 테스트됐다는 뜻이다.

OP-007 자체에 `INTEGRATED`, `OPERATED`, 외부검증을 주장할 필요는 없다. required stage가 `IMPLEMENTED`이기 때문이다. 그렇다고 전체 original plan이 완료되는 것은 아니다. 이 schema로 다른 OP의 부족한 단계를 정확히 표시하는 일이 남아 있다. 실제 운영 증거와 외부 receipt가 없는 항목은 계속 PARTIAL 또는 EXTERNAL로 남는다.

## 현재 완료 단계와 남은 한계

OP-007은 required stage `IMPLEMENTED`와 claimed stage `IMPLEMENTED`가 일치한다. strict Pydantic 모델이 네 증거 단계와 최소 evidence 목록을 고정하고, 긍정·부정 테스트가 모호한 완료 표현을 거부하므로 구현 단계는 충족한다. 관련 도입 커밋은 `b96a92d6ff275ed6858ef7737d63a054678bbbad`다. 작성 직전 기준 canonical 최종 감사 evidence SHA-256은 `6d761eba95504e84b5de02fe1efdca62604cdad2235d4fecfff9db1c7e3e6b71`, 마지막 성공 GitHub Actions는 `29917930551`이다.

남은 한계도 분명하다. 단계 enum은 증거를 분류하지만 증거 내용이 사실인지 스스로 판단하지 않는다. `EXTERNAL`이라는 값은 외부 기관의 서명된 결과를 만들어내지 않는다. 운영 단계 문자열도 production traffic을 만들지 않는다. OP-008의 Git 경로 감사, OP-010의 completion 판정, OP-119의 외부 의존성 registry, OP-120의 receipt 검증이 이 계약 위에서 추가로 작동해야 한다. OP-007의 성과는 모든 일을 끝냈다는 표시가 아니라, 서로 다른 완료 주장을 같은 단어와 같은 최소 규칙으로 비교할 수 있게 만든 것이다.
## 원문을 요구사항으로 바꾸는 과정
이 그룹은 기능을 먼저 만들기보다, 원문에서 무엇을 읽었고 어느 파일이 그 해석을 지지하는지 고정하는 데서 출발한다. 원본 해시, 페이지, 요구사항 ID, 증거 단계가 따로 남아 있어야 나중에 코드가 바뀌어도 출발점과 해석을 다시 대조할 수 있다.

`OP-007`는 “IMPLEMENTED, INTEGRATED, OPERATED, EXTERNAL 증거 단계를 Pydantic 스키마로 고정한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=1-59`
- 구현·설계: `wellnessbox-rnd/src/wellnessbox_rnd/schemas/original_plan_manifest.py`
- 테스트·실행: `wellnessbox-rnd/tests/test_original_plan_manifest.py`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `IMPLEMENTED`, 현재 주장 단계를 `IMPLEMENTED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
