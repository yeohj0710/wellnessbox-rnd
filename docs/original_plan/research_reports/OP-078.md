# OP-078 약사 검토 작업 생성과 완료 사후조건을 저장한다.

manifest에 등록된 구현 파일 `wellnessbox-rnd/src/wellnessbox_rnd/interim/reviews.py`와 검증 파일 `wellnessbox-rnd/data/original_plan/evidence/op077_op078_fail_closed_job_review_smoke_v1.json`을 기준으로 검토 작업의 저장 범위를 판단했다.

## 검토 요청과 검토 완료는 서로 다른 증거다

안전 업무가 멈췄다는 이유만 남기면 누가 어떤 전제를 확인하고 결정을 끝냈는지 알 수 없다. 반대로 결정 문자열만 저장하면 원래 실패 업무가 실제로 취소됐는지, 중대한 이상사례 보류가 유지됐는지 설명할 수 없다. OP-078은 검토 작업을 만들 때 원인과 대상 실행을 연결하고, 완료할 때 필요한 사후조건을 다시 확인해 그 결과를 변경 불가능한 기록으로 남기도록 요구한다.

## 원인·대상·긴급도를 가진 검토 작업을 한 건만 만든다

`PharmacistReviewService.create_in_transaction()`은 사용자 ID, 정렬된 이유 코드, 원본 업무 ID를 묶어 검토 ID를 계산한다. 같은 실패를 다시 처리하면 기존 검토 ID를 반환하고 새 행을 만들지 않는다. 저장 항목에는 에이전트 실행 ID, 자료 구분, 시험 표시, 긴급도, 이유 코드, 원본 업무 ID와 생성 시각이 포함된다. `review_tasks`가 원본 `workflow_jobs`를 외래키로 가리키므로 어느 업무에서 검토가 생겼는지 데이터베이스 안에서 추적할 수 있다.

일반 업무 실패는 `HIGH`, 중대한 이상사례는 `URGENT`로 생성된다. 둘을 같은 완료 규칙으로 섞지 않는다. 업무 실패 검토는 원본 업무가 `CANCELLED`인지 확인한다. 중대한 이상사례 검토는 해결되지 않은 사례 보류가 남아 있고, 실행 원장에 `serious-ae:{case_id}` 중단 이벤트가 존재하는지 점검한다. 전제가 사라졌으면 약사 ID와 결정이 들어와도 완료하지 않는다.

## 완료 기록은 약사 ID와 사후조건을 함께 고정한다

완료 요청은 1 이상의 `pharmacy_id`, 빈 문자열이 아닌 결정, 선택 메모를 받는다. 이미 다른 약사에게 배정된 검토는 `review_pharmacy_mismatch`로 거부한다. 완료 시각이 생성 시각보다 앞서도 저장하지 않는다. 검사가 끝나면 결정 내용, 약사 ID, 완료 시각과 사후조건을 기록하고, 사후조건 전체의 SHA-256을 계산한다. 이 지문은 완료 상태와 원본 업무 상태가 나중에 바뀌지 않았는지 대조하는 값이다.

SQLite에는 완료된 `review_tasks`의 수정과 삭제를 막는 두 트리거가 있다. 서비스 수준에서도 두 번째 결정은 `review_already_completed`로 끝난다. `tests/test_interim_reviews.py`는 완료 뒤 SQL `UPDATE`와 `DELETE`를 직접 시도해 모두 `completed_review_immutable` 오류가 나는지 확인한다. 원본 업무가 취소 상태가 아니거나 완료 시각이 생성 시각보다 이른 경우도 별도 실패 시험으로 남겼다.

## 시험은 결정 내용보다 저장 불변식을 평가했다

등록된 기준 실행은 timeout으로 취소된 업무에 검토 작업을 만들고 `pharmacy_id=7`, 결정 `acknowledged`를 저장했다. 완료 사후조건에는 원본 업무 상태 `CANCELLED`와 `decision_recorded=true`가 들어갔다. 시험은 저장된 JSON을 같은 순서로 정리해 지문을 다시 계산했고 일치함을 확인했다. 두 번째 결정을 보내자 `review_already_completed`가 반환됐다. 별도 API 시험에서는 중대한 이상사례 검토를 완료할 때 보류와 계획 중단 기록이 모두 true인지 확인한다.

이 시험은 약사의 판단이 의약학적으로 옳았는지 평가하지 않는다. `pharmacy_id=7`과 결정 문구는 저장 계약을 확인하기 위한 시험 입력이다. 실제 약사가 검토했다는 뜻으로 쓰면 안 된다. 개발 과정에서 수정 전 검토 행이 덮어써진 실제 사고나 최초 오류 로그도 등록 근거에서는 확인되지 않음이다. 확인 가능한 실패·수정 범위는 현행 불변 트리거와 회귀 시험이 재현하는 조건까지다.

## 운영 영수증은 실제 검토 완료를 보여 주지 않는다

manifest가 연결한 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-078.json`은 `pharmacist_review` 경로가 실행됐다고 적지만, 증가량은 `review_tasks_completed=0`이고 `review_tasks=0`이다. 대신 `ai_drafts_reviewed=1`이 기록돼 있다. AI 초안 검토와 이 요구사항의 `review_tasks` 완료는 서로 다른 저장소이므로 그 숫자를 약사 검토 완료 증거로 바꾸어 해석할 수 없다.

현재 직접 입증 단계는 `IMPLEMENTED`다. 검토 생성, 중복 방지, 완료 전제, 완료 기록의 불변성은 로컬 데이터베이스에서 확인됐다. 실제 약사가 지정된 검토 큐를 열고 판단을 남긴 건수, 검토 범위와 처리 시간, 운영 중 재배정 절차는 확인되지 않음이다. 운영 단계에는 가명화된 검토 ID, 실제 약사 식별·권한 증거, 원본 업무 상태, 완료 사후조건 지문을 연결한 별도 기록이 필요하다.
