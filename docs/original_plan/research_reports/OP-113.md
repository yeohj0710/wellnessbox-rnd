# OP-113 timeout, 재시도, circuit breaker, fallback을 장애 주입으로 검증한다.

## 결론

OP-113은 요구 단계 `INTEGRATED`에 도달했다. WellnessBox의 실제 R&D HTTP 클라이언트에 timeout, 제한된 재시도, circuit breaker를 연결했고, 실제 관리자 통합 라우트의 fallback까지 같은 장애 주입 실행에서 확인했다. 읽기 전용 GET은 일시 장애에 한 번만 재시도하지만 POST는 중복 저장이나 중복 결정을 만들 수 있으므로 자동 재시도하지 않는다. 세 번의 논리적 호출이 최종 실패하면 circuit이 30초 동안 열리고, 열린 동안 네트워크 호출을 생략한다. 냉각 시간이 끝난 첫 호출이 성공하면 circuit은 정상 상태로 복구된다.

이번 검증은 로컬 프로세스의 결정적 장애 주입이다. production 네트워크 장애, 실제 R&D 인스턴스 중단, 다중 WellnessBox 인스턴스 사이의 circuit 상태 공유, 사용자 트래픽의 복구 시간은 측정하지 않았다. 따라서 운영 단계 `OPERATED`를 주장하지 않는다.

## 재시도 정책과 부작용 경계

재시도는 모든 실패를 같은 방식으로 반복하는 기능이 아니다. 현재 정책은 HTTP 429, 502, 503, 504와 네트워크 오류, timeout을 일시 장애 후보로 분류한다. GET 요청은 최초 호출과 한 번의 재시도까지 최대 두 번 실행한다. 첫 재시도 전 대기 시간은 50ms로 고정해 테스트와 운영 동작이 예측 가능하도록 했다. 현재 최대 시도 횟수가 둘이므로 지수 증가를 가장한 불필요한 복잡성을 추가하지 않았다.

POST 요청은 자동 재시도하지 않는다. 프로필 저장, 추천 실행, 약사 결정, 계획 상태 변경은 서버가 요청을 처리한 뒤 응답만 유실될 수 있다. 클라이언트가 같은 POST를 자동 반복하면 idempotency 계약이 없는 경로에서 중복 상태 변경이 생길 수 있다. 이번 구현은 안전한 읽기 복구와 쓰기 부작용 방지를 분리한다. POST 재시도는 각 API가 idempotency key와 동일 요청 재생 계약을 제공할 때만 별도 요구사항으로 추가해야 한다.

## timeout과 오류 공개 경계

각 시도는 기존 `AbortController`와 환경별 timeout 상한을 그대로 사용한다. timeout 값은 500ms보다 작거나 15초보다 크게 설정할 수 없고, 유효한 설정이 없으면 7.5초를 사용한다. 장애 주입 QA는 `AbortError`를 발생시켜 GET 재시도 경로와 최종 오류 경계를 실행한다. 외부 응답에는 내부 예외 메시지 대신 `R&D timeout`만 노출된다. 자격증명, URL, 요청 본문, 내부 stack은 공개 오류에 포함되지 않는다.

timeout timer는 매 시도의 `finally`에서 제거한다. 성공, HTTP 실패, JSON 처리 실패, timeout 중 어떤 경로로 끝나더라도 남은 timer가 다음 요청을 잘못 중단하지 않는다. 재시도가 발생하면 새 `AbortController`와 새 timer를 사용하므로 첫 시도의 abort signal이 두 번째 시도에 전달되지 않는다.

## circuit breaker 상태 전이

circuit 상태는 R&D origin별로 보관한다. 서로 다른 origin의 장애가 같은 circuit을 열지 않는다. 한 논리적 호출은 내부 재시도를 모두 소진한 뒤 한 번의 실패로 집계된다. 따라서 GET 세 호출이 각각 두 번 실패하면 네트워크 시도는 여섯 번이고 circuit 실패 수는 세 번이다. 이 구분이 없으면 한 번의 사용자 요청이 두 번의 실패로 계산돼 circuit이 지나치게 빨리 열릴 수 있다.

세 번째 논리적 실패가 끝나면 `openedAt`을 기록한다. 그 뒤 30초 이내 호출은 fetch를 실행하지 않고 `WB_RND_INTERIM_circuit_open`을 반환한다. 냉각 시간이 지나면 단 하나의 half-open probe만 허용한다. probe가 진행 중인 동안 들어온 동시 요청은 네트워크로 보내지 않는다. probe가 성공하면 정상 상태로 돌아가고, retryable 장애면 즉시 다시 열린다. 4xx와 JSON 계약 오류는 R&D origin의 가용성 장애가 아니므로 circuit 실패 수에 넣지 않는다. 현재 상태는 한 Node 프로세스 안에만 존재한다. 분산 circuit breaker나 외부 상태 저장소를 도입하지 않은 이유는 서비스 인스턴스 전체의 장애율과 복구 정책을 운영 자료 없이 임의로 결합하지 않기 위해서다.

## fallback 검증

단순히 circuit 오류가 발생하는지만 확인하면 사용자 경로가 안전하게 계속되는지 알 수 없다. QA는 실제 `runAdminInterimDashboardRoute`를 실행한다. status, sources, runtime 응답은 성공시키고 KPI 호출에 circuit-open 오류를 주입한다. 관리자 응답은 HTTP 200을 유지하면서 KPI만 `UNAVAILABLE`로 표시하고 공개 오류를 `R&D request failed`로 제한한다. 이 동작은 부분 장애가 전체 관리자 화면을 실패시키지 않으면서도 빈 KPI를 실제 값처럼 가장하지 않는 기존 경계를 보존한다.

전체 status 호출 자체가 실패할 때는 502 fail-closed가 유지된다. 이번 fallback은 모든 장애를 성공으로 바꾸는 기능이 아니다. 부분적으로 대체 가능한 KPI에만 명시적 unavailable 상태를 제공하고, 핵심 상태를 확인할 수 없는 요청은 실패로 남긴다.

## 재현 가능한 증거

데이터셋 `data/original_plan/op113_op114_resilience_contract_cases_v1.json`은 OP-113의 여섯 사례를 정의한다. canonical evidence `data/original_plan/evidence/op113_op114_resilience_contract_smoke_v1.json`은 GET 시도 수 2, 대기 `[50]`, POST 시도 수 1, circuit 전 네트워크 시도 수 6, timeout 제한, open 상태의 네트워크 생략, 30초 뒤 복구, 실제 관리자 fallback 결과를 기록한다.

runner는 서비스 커밋 `d07123903072f5eac7ef7f5021cf8278ca02c9c9`과 관련 파일별 Git blob을 기록한다. 데이터셋은 작업 폴더의 미커밋 내용이 아니라 R&D HEAD의 Git blob으로 읽는다. 같은 커밋에서 runner를 다시 실행하면 canonical evidence가 바뀌지 않아야 한다.

## 단계 경계와 다음 검증

현재 증거는 실제 TypeScript 클라이언트 정책과 실제 관리자 라우트 fallback을 실행하므로 `INTEGRATED` 요구를 충족한다. 다만 production outage, 다중 인스턴스, 실제 네트워크 지연 분포, 운영 경보, 사용자 관찰 복구 시간은 증명하지 않는다. `OPERATED` 승격에는 승인된 장애 훈련, 배포 버전 식별, 관찰 기간, 요청 성공률과 지연, circuit open 횟수, fallback 비율, 복구 후 정상화 자료가 필요하다.
## 운영 증거와 종료 판단을 나눈 이유
운영 증거는 구현 파일을 나열하는 데서 끝나지 않는다. 보안, 장애 복구, 계약 일치, 배포 health, 브라우저 경로, 운영 증거, 외부 의존성과 최종 감사가 각각 어떤 주장을 지지하는지 단계별로 나눈다.

`OP-113`는 “timeout, 재시도, circuit breaker, fallback을 장애 주입으로 검증한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15-26`
- 구현·설계: `wellnessbox/lib/server/wb-rnd-interim-client.ts`, `wellnessbox/lib/server/wb-rnd-interim-route.ts`
- 테스트·실행: `wellnessbox/scripts/qa/check-rnd-resilience-contract.cts`, `wellnessbox-rnd/scripts/run_resilience_openapi_contract_smoke.py`, `wellnessbox-rnd/data/original_plan/evidence/op113_op114_resilience_contract_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/evidence/op113_op114_resilience_contract_smoke_v1.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `INTEGRATED`, 현재 주장 단계를 `INTEGRATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
