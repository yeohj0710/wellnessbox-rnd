# OP-118 모든 비외부 요구사항에 운영 증거를 연결한다

## 요구사항의 대상은 파일 링크가 아니라 단계에 맞는 요구사항별 증거다

OP-118은 외부 기관의 자료가 필요한 항목을 제외하고, 저장소가 완료라고 표시한 모든 요구사항에서 그 완료 단계를 직접 뒷받침하는 증거를 찾을 수 있게 하라는 요구다. 구현 파일이 하나 있다는 이유로 운영 완료라고 표시하면 안 된다. `IMPLEMENTED`에는 코드와 집중 시험, `INTEGRATED`에는 실제 구성요소 사이 왕복, `OPERATED`에는 실제 세션에서 해당 행동을 수행한 관찰 기록이 필요하다.

요구사항 장부의 등록 구현은 `wellnessbox-rnd/scripts/run_browser_operational_evidence_smoke.py`다. 고정 사례 `wellnessbox-rnd/data/original_plan/op117_op118_browser_operational_evidence_cases_v1.json`과 결과 `wellnessbox-rnd/data/original_plan/evidence/op117_op118_browser_operational_evidence_smoke_v1.json`이 시험 근거로 연결돼 있다. 운영 파일은 `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-118.json`이다. 모든 경로는 존재하지만 세 자료가 서로 다른 시점과 의미를 담으므로, 한 묶음으로 합쳐 `OPERATED`를 주장할 수 없다.

## 현재 요구사항 장부의 숫자는 54·24·41이다

현재 `data/original_plan/requirements_manifest_v1.json`을 그룹 기본 단계까지 펼쳐 다시 계산했다. 전체 120건 중 외부 단계는 OP-039 한 건이고 비외부 요구사항은 119건이다. 비외부 119건에는 모두 하나 이상의 `evidence` 항목이 있다. 주장 단계는 `IMPLEMENTED` 54건, `INTEGRATED` 24건, `OPERATED` 41건이며, 요구 단계와 주장 단계 표시는 모든 항목에서 서로 같다.

이 집계는 “119건 모두에 어떤 경로 문자열이 등록됐다”는 추적성만 보여준다. 등록 파일이 존재하는지, 그 내용이 요구사항을 실제로 뒷받침하는지, `OPERATED` 41건의 영수증이 해당 행동을 직접 기록했는지는 별도 검사다. OP-105~117에서 확인한 것처럼 넓은 행동 매핑 하나가 서로 다른 요구사항 여러 건에 같은 영수증을 복사할 수 있으므로 링크 수와 근거 충족 수는 같지 않다.

## 첫 집계는 운영 증거가 전혀 없던 시점을 올바르게 기록했다

고정 사례의 OP-118 항목은 `non_external_coverage`, `evidence_link_coverage`, `external_exclusion`, `operated_gap_ledger`, `no_production_inflation` 다섯 건이다. 등록 결과는 비외부 119건과 외부 1건, 증거 링크 119건을 기록했다. 당시 `operated_requirement_count=0`, `operated_gap_count=119`였고 모든 비외부 ID가 공백 목록에 들어 있다. `all_non_external_operated_proven=false`와 `production_deployment_proven=false`도 명시돼 있다.

이 결과는 완료 전 상태를 부풀리지 않았다는 점에서 내용이 맞다. 모든 파일에 경로가 생겼지만 운영 증거는 0건이라는 차이를 보존했다. 결과 파일의 고정 사례 SHA-256은 현재 사례 파일과 일치하고, OP-120 추가 뒤 증거 링크 기대값이 119로 갱신된 이력도 확인했다.

## 생성기는 장부 변화에 대응하지 못하고 과거 숫자를 정답으로 고정했다

`run_browser_operational_evidence_smoke.py`는 현재 장부를 읽어 비외부, 외부, 링크, 운영 주장 수를 계산한다. 문제는 계산 뒤 `evidence_linked_count == 119`뿐 아니라 `operated_requirement_count == 0`을 단정한다는 점이다. 현재 값은 41이므로 같은 코드를 실행하면 OP-117 브라우저 사례가 성공해도 OP-118 집계에서 멈춘다.

Git 이력은 숫자가 117에서 118, 119로 늘 때마다 상수를 손으로 바꾼 과정을 보여준다. `6c40ffd`의 첫 생성기는 증거 링크 117건을 기대했다. OP-119가 추가된 뒤 `b789ed2`가 118로 바꿨고, OP-120까지 연결된 뒤 `278bcef`가 119로 다시 바꿨다. 요구사항 수 변화를 읽어 판단한 것이 아니라 당시 숫자를 코드에 넣은 방식이다. 이후 운영 세션으로 `OPERATED` 41건이 생겼지만 0건 단정은 갱신되지 않았다.

이 실패는 단순한 최신화 누락 이상의 의미가 있다. OP-118은 증거의 현재 상태를 검사해야 하는데, 등록 구현은 과거 완료 전 상태를 재현하도록 작성됐다. 현재 장부를 입력으로 한 최신 증거 점검기가 아니므로 manifest의 `OPERATED` 주장을 지지할 수 없다.

## 운영 영수증 연결은 행동 신호 하나를 여러 요구사항에 넓게 배분한다

`data/original_plan/operational_action_coverage_v1.json`은 `recommendation` 행동의 신호를 `recommendation_runs`, `recommendation_items`, `agent_runs`, `agent_steps`로 정한다. 이 중 하나가 늘면 OP-040, OP-071, OP-072, OP-079, OP-080, OP-096, OP-098, OP-099, OP-101, OP-102, OP-107~110, OP-117, OP-118 등 16건을 한꺼번에 포함한다. 세션 완료는 OP-116과 OP-120에 별도로 붙는다.

`OP-118.json`의 실제 변화는 `recommendation_runs=1`, `recommendation_items=1`이고 나머지 표는 0이다. 이 한 세션이 브라우저 세 역할, 관리자 상태 조회, 주문 결속, 추천 안전 경계와 OP-118 자체의 전체 증거 감사를 각각 수행했다는 세부 기록은 없다. 영수증의 `covered_requirement_ids`는 행동 매핑 결과이지, 요구사항별 실행 로그가 아니다.

파일에는 ACTUAL 자료 등급, 환경 ID, 시작·종료 시각, 두 저장소 커밋, 내용 지문과 서명 문자열이 있다. 이는 세션 기록의 형태를 갖췄다는 뜻이다. 그러나 이번 독립 대조에서는 공개키로 서명을 검산하지 않았고, 무엇보다 OP-118이 요구하는 119건 전체 점검 결과가 들어 있지 않다.

## 등록 결과와 현재 운영 파일은 서로 이어지는 갱신 계보가 아니다

과거 결과 JSON은 `OPERATED` 0건과 공백 119건을 기록한다. 현재 장부는 `OPERATED` 41건을 표시한다. 이후 운영 파일은 추천 행 1건과 넓은 포함 목록만 담는다. 어느 파일도 현재 54·24·41건을 대상으로 등록 경로를 열어 존재, 내용 일치, 단계 적합성을 다시 판정하지 않는다.

따라서 “비외부 119건 모두에 경로가 등록됐다”는 문장은 확인됐다. “모든 비외부 요구사항에 단계에 맞는 운영 증거가 연결됐다”는 OP-118 본문은 확인되지 않았다. 특히 `IMPLEMENTED`나 `INTEGRATED`가 요구 단계인 78건까지 모두 운영 파일을 요구할 것인지, 아니면 각 요구 단계에 맞는 증거로 충분한지 정책 문구도 분명히 해야 한다. 현재 제목은 모든 비외부 항목에 운영 증거를 요구하지만 첫 생성기는 링크와 운영 공백을 따로 센다.

## 실패와 수정 이력에서 배운 검증 기준

초기 브라우저 결과는 화면 본문 표시만 보고 성공했지만 `84aed96`에서 HTTP 상태와 제어 요소 수로 강화됐다. OP-118 집계는 OP-119와 OP-120 추가 때 링크 수를 각각 고쳐 형식적 총수는 맞췄다. 그러나 `operated_requirement_count=0` 고정값과 요구 행동 대 영수증 신호의 의미 대응은 수정되지 않았다. 숫자 통과를 위한 보정은 있었지만 요구사항별 단계 적합성을 판정하는 검사로 확장되지는 않았다.

최신 점검기는 각 요구사항에 대해 필요한 단계, 등록 경로, 파일 존재, 파일 안의 요구사항 ID, 소스 시점, 관찰한 행동을 표로 만들어야 한다. 운영 41건은 `covered_requirement_ids`에 포함됐는지만 볼 것이 아니라 요구 문장의 동사와 `database_count_delta` 또는 화면·API 관찰이 직접 대응하는지 판정해야 한다. 같은 영수증을 여러 요구사항에 쓰더라도 각 요구 행동을 실제로 포함할 때만 허용해야 한다.

## 현재 단계와 확인하지 못한 범위

현재 증거가 지지하는 범위는 장부 수준의 `IMPLEMENTED`다. 비외부 요구사항 119건에 증거 항목이 있고, 외부 OP-039가 분리됐으며, 완료 전 운영 공백도 과거 결과에 보존됐다. 요구사항 장부가 표시한 `OPERATED`는 등록 구현과 영수증 내용으로는 입증되지 않는다.

확인되지 않은 것은 현재 파일 기준의 119건 전수 내용 감사, 운영 41건의 요구 행동별 직접성, 영수증 서명 진위, 공개 배포와 실제 트래픽이다. OP-118을 완료하려면 현재 장부를 입력으로 재실행 가능한 집계기를 만들고, 형식 링크 수와 단계 적합 증거 수를 분리해 보고해야 한다. 모든 요구사항의 판정이 끝난 뒤에만 현재 `OPERATED` 표시를 유지할 수 있다.
## 운영 증거와 종료 판단을 나눈 이유
운영 증거는 구현 파일을 나열하는 데서 끝나지 않는다. 보안, 장애 복구, 계약 일치, 배포 health, 브라우저 경로, 운영 증거, 외부 의존성과 최종 감사가 각각 어떤 주장을 지지하는지 단계별로 나눈다.

`OP-118`는 “모든 비외부 요구사항에 운영 증거를 연결한다.”를 다루는 항목이다. 이 항목을 읽을 때는 파일이 존재한다는 사실과 요구된 동작이 증명됐다는 사실을 구분한다. 아래 근거는 이 보고서의 기존 설명을 다시 확인할 때 먼저 열어야 할 자료다.

### 근거를 읽는 순서
- 원문 출처: `docs/context/original_plan.pdf#page=15-26`
- 구현·설계: `wellnessbox-rnd/scripts/run_browser_operational_evidence_smoke.py`
- 테스트·실행: `wellnessbox-rnd/data/original_plan/op117_op118_browser_operational_evidence_cases_v1.json`, `wellnessbox-rnd/data/original_plan/evidence/op117_op118_browser_operational_evidence_smoke_v1.json`
- 통합 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-118.json`
- 운영 증거: `wellnessbox-rnd/data/original_plan/final_session/operational_evidence/OP-118.json`

구현 파일은 설계와 코드의 위치를 알려 주고, 테스트 파일은 어떤 분기를 실행했는지 알려 준다. 통합·운영·외부 증거가 따로 적혀 있지 않다면 구현 파일만으로 그 단계를 주장하지 않는다. 이 구분이 있어야 연구보고서가 “코드가 있다”와 “실제 연구개발 과정에서 검증됐다”를 섞지 않는다.

### 현재 단계와 해석의 경계
manifest는 요구 단계를 `OPERATED`, 현재 주장 단계를 `OPERATED`로 기록한다.
두 단계 표기는 일치하지만, 이 값이 다른 OP의 운영·외부 검증까지 자동으로 승격시키지는 않는다. 이 보고서는 연결된 증거가 직접 말하는 범위까지만 결론을 쓴다.

이번 보강은 새로운 실험 결과, 사람의 판정·승인·서명, 운영 트래픽을 추가하지 않는다. 기존 연구보고서의 사실과 증거를 더 쉽게 읽도록 연구 질문, 확인 순서, 단계 경계를 풀어 쓴다.
