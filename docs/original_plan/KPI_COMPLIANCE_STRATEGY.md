# KPI 달성 전략과 내부 인력 수행 범위

> 이 문서는 "어떻게 하면 계획서를 어기지 않으면서 내부 인력으로 최대한 진행할 수 있는가"에 답한다.
> 근거는 `docs/context/original_plan.pdf` p.25~26이다. 기계가 읽을 계약은
> `data/original_plan/contracts/kpi_measurement_contract_v1.json`에 있다.

## KOLAS 시험은 연구 과정의 게이트가 아니다

계획서 p.26의 `평가 환경` 칸(TTA, 와이즈스톤 등 KOLAS 인정 시험기관)은 **연구를 마친 뒤 결과물을 가져가 최종 성능을 검증받는 단계**다. 연구 과정에서 통과해야 하는 선행 조건이 아니다.

따라서 연구 기간에는 **내부 측정으로 진행하고 그 값을 연구 결과로 쓴다.** 저장소의 측정 산출물은 `measurement_environment: research_phase_internal_measurement`로 표시한다. 시험 의뢰는 연구 완료 후 별도 단계이며, 이걸 이유로 연구 진행을 막지 않는다.

## 세 가지 대안 판정

### 대안 1 — 2차년도 예비 약사 수행, 3차년도 면허 취득 후 완료

**가능하다. 문제 없다.**

계획서에 검토자의 면허 취득 시점을 규정한 조항이 없다. 개발 로드맵(p.27)상 TIPS 개발 범위는 2026~2027이고, 최종 마감이 2027-10이므로 2027-01 면허 취득 후 재검토할 시간이 있다.

다만 한 군데만 지킨다. **KPI-1의 `약사 그룹`은 최종 측정 시점에 실제 약사여야 한다.** 지표 정의가 "약사 그룹이 도출한 성분 집합 R_i"이기 때문이다. 2차년도 예비 약사 산출물을 "약사 그룹"으로 표기해 KOLAS 시험에 제출하면 안 된다.

- 2차년도: 예비 약사 사전 검토 → `pharmacist_candidate_preliminary_safety_review`
- 3차년도: 면허 취득 후 같은 사례 재검토 → `licensed_pharmacist_expert_safety_review`

전환 방법은 `REVIEWER_QUALIFICATION_POLICY.md`에 있다. 레지스트리의 `qualification_stage` 한 곳만 바꾸면 된다.

### 대안 2 — 생성 데이터 15만건을 약사가 검수·승인해 학습, 생성 사실과 유사도 명시

**학습 입력으로는 가능하다. KPI-2 측정 대상으로는 불가능하다.** 둘을 반드시 분리한다.

**가능한 부분:**
- 계획서는 학습 데이터의 출처를 제약하지 않는다. 합성 자료로 모델을 학습하는 것은 문제없다.
- 생성 사실과 생성 방법을 명시하는 것은 오히려 필요한 처리다.
- 문헌 기반으로 생성한 자료가 실제 분포와 통계적으로 유사함을 보이는 것도 정당한 연구 활동이고 논문화도 된다.

**불가능한 부분:**
- KPI-2는 "**개인 i의 복용 전·후 수치화된 효과 측정치**"를 요구하고 "복용 전·후 PRO 지표 **최소 100명 이상** 확보"를 통과 조건으로 못박았다. 지표 이름 자체가 "**실제** 효과 측정치의 개선도"다.
- 합성 자료로 이 자리를 채우면 지표 정의를 충족하지 못한다. 최종 검증에서 표본 출처를 확인하므로 실무적으로도 통과하지 못한다.
- "99% 유사성"은 **분포 유사성**이다. 분포가 비슷하다는 사실이 "이 조합을 복용해서 실제로 좋아졌다"를 대신하지 못한다. 유사도를 근거로 실제 효과 개선을 주장하면 그건 사실과 다른 진술이 된다.

**현실적 경로:** 계획서 p.31에 이미 답이 있다. `건강기능식품 소분 판매 및 배송 서비스 실 운영 중`, `베타테스트 기간 월 반복 매출 523만 원`, `고객 피드백(유선, 서면) 바탕 서비스 개선`. **실사용자가 이미 있다.** KPI-2의 100명은 새로 모집할 대상이 아니라 기존 서비스 사용자에서 복용 전·후 PRO를 받는 문제다. 이건 내부에서 설계·집행할 수 있다.

정리하면 이렇게 나눈다.

| 용도 | 합성 15만건 | 실사용자 PRO |
|---|---|---|
| 모델 학습 | 주력으로 사용 | 선택 |
| KPI-1·3·4·5 정답 집합 | 불가 | 해당 없음 |
| KPI-2 개선도 측정 | 불가 | **필수, 100명 이상** |
| KPI-6 이상반응 집계 | 불가 | 필수, 12개월 |
| KPI-7 연동율 | 가능(명시 조건) | 선택 |

### 대안 3 — 독립 AI가 준비하고 사람이 최종 결정

운영 워크플로와 KPI 정답 집합에 모두 사용할 수 있다. 다만 측정 대상 엔진이 초안이나 2차 의견을 만들면 안 되고, 사람의 최종 결정 전에 엔진 출력을 보면 안 된다.

**가능한 부분:**
- H-003의 AI 초안 생성 → 예비 약사 사전 검토의 승인·수정 승인·반려 흐름은 정상이다. 3차년도 면허 취득 뒤 같은 자료를 다시 확인한다.
- 이 절의 사람 최종 결정은 오프라인 KPI 정답지에만 적용한다. 운영 추천 절차에는 사람 인계 단계를 새로 넣지 않는다.

**불가능한 부분:**
- KPI-1의 점수는 `s_i = 100 × |R_i ∩ T_i| / |R_i|`다. `R_i`(약사 도출)를 `T_i`(엔진 출력)에서 만들면 교집합이 `R_i` 전체가 되어 **점수가 구조적으로 100%에 수렴한다.** 측정이 아니라 동어반복이 된다.
- KPI-3·4·5도 같은 구조다. 정답 작업, 정답 문항, 참조 규칙을 시스템 출력에서 파생하면 자기 참조가 된다.
- "마지막에 손댄 사람이 약사이므로 약사가 만든 것"이라는 논리는 운영 책임 소재로는 성립하지만, **측정 독립성으로는 성립하지 않는다.** 심사에서 가장 먼저 지적받을 지점이다.

**무결성 게이트는 선택 기능이 아니라 필수 보완이다.** 기존 KPI-1·5 봉인은 100건을 약 3.7초에 자동 수락한 기록이라 사람 검토의 증거가 되지 않았다. 종전 KPI-3·4 정답 경로는 엔진 입력을 읽어 자기 참조 위험이 있었다. 이 두 문제를 막지 않으면 높은 KPI 점수가 나와도 연구 성과를 설명할 수 없다.

반면 교차 AI의 5→20→전수 확대 절차는 사람 시간을 줄이기 위한 운영 최적화다. 독립 출처, 엔진 입력·출력 차단, 사람 최종 결정, 선봉인은 반드시 지켜야 한다. 사람이 100건을 전수 상세 검토한다면 교차 AI 일괄 승인 경로를 쓰지 않아도 된다. 다만 KPI-4의 1차 답은 현재 계약대로 상담 모델과 다른 제공자 계열이어야 한다.

**앞서 이 문서는 "AI가 정답을 만들면 안 된다"고 적었다. 그 표현은 부정확했다.**

문제는 *AI가 만들었다는 것*이 아니라 *측정 대상인 엔진이 자기 정답을 만들었다는 것*이다. 초안을 만드는 역할과 확정하는 역할을 나누면 내부 인력만으로 유효하다.

| 역할 | 누가 | 조건 |
|---|---|---|
| 초안 작성 | AI를 포함해 무엇이든 | 측정 대상 엔진이 아닐 것, 그 사례의 엔진 출력을 보지 않았을 것 |
| 선택적 2차 의견 | 1차와 다른 제공자 계열 AI | 1차 답·근거와 엔진 입력·출력을 보지 않을 것 |
| 상세 검토 | 지명된 사람 | 모든 AI 불일치·위험 플래그·결정적 합의 표본을 수락·수정·반려 |
| 합의안 일괄 승인 | 같은 지명된 사람 | 상세 검토가 끝난 뒤 정확한 확인 문구를 직접 입력 |

이건 표준적인 assisted annotation이다. 초안 출처가 엔진과 다른 파생 경로이고, 엔진 출력을 보기 전에 사람이 확정해 봉인하므로 측정이 자기 참조가 되지 않는다.

**100건을 맨손으로 쓰지 않는다.** 기본 경로에서는 AI 초안을 보며 100건을 사람이 확정한다. 선택 경로에서는 두 AI가 독립적으로 답하고, 사람은 불일치·위험 사례와 결정적 표본을 상세 검토한 뒤 나머지 합의안을 한 번 더 판단해 일괄 승인한다.

```bash
python scripts/run_answer_key_workbench.py export-ai-review --indicator KPI-1 --output <블라인드_패킷.json>
# 다른 제공자 계열 AI가 패킷만 읽고 응답 JSON을 작성한다.
python scripts/run_answer_key_workbench.py import-ai-review --indicator KPI-1 --response <2차_AI_응답.json>
python scripts/run_answer_key_workbench.py review-minimal --indicator KPI-1 --by <검토자>
python scripts/run_answer_key_workbench.py approve-consensus --indicator KPI-1 --by <검토자>
python scripts/run_answer_key_workbench.py seal --indicator KPI-1 --system-under-test-id <엔진_ID>
```

KPI-3은 `import-ai-review` 전에 첫 블라인드 응답을 가져온다. KPI-4도 OpenAI 상담 모델을 측정한다면 비-OpenAI 1차 응답으로 현재 답을 교체한다.

```bash
python scripts/run_answer_key_workbench.py import-primary-ai-draft --indicator KPI-3 --response <1차_AI_응답.json>
python scripts/run_answer_key_workbench.py import-ai-review --indicator KPI-3 --response <다른_제공자_2차_AI_응답.json>
```

`review-minimal` 화면에서 사람은 네 가지 판단만 한다.

| 키 | 뜻 |
|---|---|
| Enter | 1차 AI 초안 수락 |
| p | 2차 AI 의견 수락 |
| e | 수정. 성분을 쉼표로 구분해 다시 입력 |
| r | 반려. 사유를 남기고 정답에서 제외 |
| q | 저장하고 종료. 다시 실행하면 이어서 |

한 건마다 즉시 저장되므로 중간에 끊어도 잃지 않는다. 다만 1초보다 빠른 입력은 저장하지 않고 같은 사례를 다시 판단하게 한다. 봉인 감사도 기록된 상세 판단 시간을 다시 검사한다. 1초는 충분한 임상 검토 시간을 입증하는 기준이 아니라 자동 입력을 찾기 위한 임의의 하한이다.

두 AI가 합의했다고 정답이 자동 확정되지는 않는다. 합의 사례 중 SHA-256으로 고른 5건을 사람이 먼저 상세 검토한다. 표본에서 1건을 고치면 20건으로 늘리고, 2건을 고치면 모든 합의 사례를 상세 검토한다. 이 5건은 통계적·임상적 타당성을 증명하는 표본 수가 아니다. 오류를 일찍 발견하기 위한 운영 하한이다. 합의율·승인율·반려율은 봉인 통과 조건으로 쓰지 않는다.

네 지표에서 두 AI가 모두 합의하고 위험 플래그가 없을 때 사람의 상세 검토 하한은 400건에서 20건으로 줄어든다. 사람은 지표별 5건을 상세 판단하고 지표별 일괄 승인 문구를 한 번씩 직접 입력한다. 불일치·위험 플래그·표본 수정이 늘면 사람 검토량도 늘며, 최악의 경우 400건 전수 검토로 돌아간다.

**KPI-1 초안은 이미 100건 만들어져 있다.** 출처는 프로젝트 오너가 엔진보다 먼저 출판한 `건강상담 Checker`의 독립 참조 추출본이다. 엔진 지식베이스나 안전 규칙에서 답을 가져오지 않는다. 원문 성분 234종 중 엔진 카탈로그와 대조 가능한 범위만 채점한다는 한계는 별도로 공개한다.

### 전부 수락하면 그게 기록에 남는다

`edit_rate_pct`를 함께 기록한다. 100건을 전부 그대로 수락하면 수정률 0%가 되고 `edit_rate_zero_every_draft_was_accepted_unchanged` 경고가 붙는다. 숨기지 않는다.

수정률은 검토 결과를 숨기지 않기 위한 맥락 정보다. 수정률·승인율·반려율 자체는 사람이 제대로 읽었다는 증거나 봉인 통과 기준이 아니다. 감사기는 상세 검토 시간과 결정 경로를 따로 확인한다.

봉인에는 `provenance`가 붙어 두 AI의 주체·제공자 계열·패킷 지문, 엔진 출력 미참조 여부, 상세 검토 건수, 일괄 승인 건수, 수정률, 최종 결정자가 함께 남는다.

### 봉인 이후는 이전과 같다

정답이 봉인되면 그 뒤에 엔진을 돌리고 대조한다. 봉인 후 정답을 고치면 지문이 달라져 `compare`가 `reference_standard_seal_broken`으로 거부한다.

```bash
python scripts/seal_reference_standard.py compare --indicator KPI-1 --engine-output <엔진출력.json>
```

| KPI-1 추천 정확도 80% | 100 case | 가능 | **초안 100건 완료** — 2차 AI 응답과 사람 최종 결정이 남음 |
| KPI-2 효과 개선도 >0pp | **100명** | 불가 | **경로 확정(A), 수집 미착수** — 측정은 3차년도 |

| KPI-5 레퍼런스 정확도 95% | 100 규칙 | 가능 | **초안 100건 완료** — 2차 AI 응답과 사람 최종 결정이 남음 |
| KPI-6 이상반응 ≤5건/year | 12개월 운영 | 가능 | **해결** — 12개월 창 0건, 노출 5세션 |
| KPI-7 연동율 90% | 100 데이터집합 | 가능 | **해결** — 합성 100세트, 연동율 100% |

### KPI-6 해결 방법

`scripts/build_adverse_event_report.py` 가 12개월 창의 이상반응을 집계한다. 운영 원장의 `adverse_events` 테이블에서 `related_to_recommendation = 1` 인 보고만 센다. 지표 정의가 "엔진 추천 건강기능식품 복용으로 인한" 이상반응이기 때문이다.

**노출이 0이면 0건을 통과로 처리하지 않는다.** `INSUFFICIENT_EXPOSURE`로 표시한다. 사용자가 없는데 0건인 것은 측정이 아니기 때문이다. 현재 실행 결과는 세션 5건에 이상반응 0건이라 `READY`다.

별도로 운영해 온 사이트의 보고를 넣으려면 `--external-reports` 로 JSON을 준다. 각 보고에 `engine_recommended: true` 가 있어야 집계에 포함되고, 없는 보고는 `unattributed`로 따로 센다. 그 사이트의 복용이 이 엔진의 추천에서 나온 것이 아니면 KPI-6 정의에 맞지 않기 때문이다.

### KPI-7 해결 방법

`scripts/build_sensor_genetic_datasets.py` 가 시중 기기 스키마를 참고해 100 데이터집합을 만든다. 웨어러블 34, 연속혈당 33, 유전자 33으로 각 10세트 이상 요건을 넘는다.

필드 모양은 Apple HealthKit(`HKQuantityTypeIdentifierStepCount`, `RestingHeartRate`, `SleepAnalysis`), Samsung Health(`com.samsung.shealth.*`), Dexcom v3 EGV(mg/dL, trend, trendRate), SNP 패널(rsid·genotype·phenotype)을 따랐다. 연속혈당은 mg/dL와 mmol/L를 번갈아 넣어 단위 변환 경로도 태운다.

생성 후 **실제 저장소 파서를 통과시켜** 연동율을 계산한다. 파서가 항상 스냅샷을 돌려주므로 호출 성공이 아니라 `wearable_available` / `cgm_available` / `genetic_available` 플래그로 판정한다. 현재 결과는 세 계열 모두 100%, 종합 100%로 목표 90%를 넘는다.

모든 레코드에 `data_class: SYNTHETIC` 이 붙고, 컬렉션에 "실제 사용자 측정값으로 보고하면 안 된다"는 고지가 들어간다. 앞선 연구의 합성 자료 처리와 같은 방식이다.

### KPI-2가 남은 이유

100명은 계획서 p.26의 통과 조건이다. **저장소 파일을 고쳐도 협약상 요건은 바뀌지 않는다.** 지표나 목표치를 조정하려면 전문기관 협약 변경 승인이 필요하다. 그래서 이 항목만 `decision_required` 로 남겨 두고 세 가지 선택지를 계약 파일에 적었다.

| 선택지 | 내용 | 비고 |
|---|---|---|
| A | 운영 중인 서비스 사용자에게서 확보 | 계획서 p.31에 실 운영·고객 피드백 수집이 이미 기재돼 있다. 새 모집이 아니라 기존 사용자 전·후 설문 |
| B | 협약 변경 신청 | 전문기관 승인 사안. 승인 전까지 기존 조건 유효 |
| C | 3차년도로 이월 | 수집에 시간이 걸리므로 지금부터 쌓아야 함 |

선택하면 계약 파일의 `KPI-2.open_decision.chosen` 에 기록한다.

**2026-07-31 결정: A(운영 사용자 확보) + 측정 시점 3차년도.** 오너가 판단을 세션에 위임해 기록했다. 계약 파일 `KPI-2.open_decision.chosen_detail` 에 근거와 함께 남아 있고, 이의가 있으면 그 필드만 바꾸면 된다.

B를 고르지 않은 이유는 협약 변경이 전문기관 승인에 달려 있어 연구팀이 통제할 수 없고, 승인 전까지 100명 조건이 그대로 유효하기 때문이다. C만 고르지 않은 이유는 수집을 착수하지 않은 채 이월하면 3차년도에도 표본이 없기 때문이다. 그래서 **경로는 A로 지금 집행하고, 판정 시점만 3차년도로 둔다.**

이 결정은 100명 요건을 바꾸지 않는다. **아직 수집은 착수되지 않았다.** 다음 행동은 운영 서비스에 복용 전 PRO와 2주 후 후속 PRO 흐름을 붙이는 것이고, 담당은 여형준이다.

## 독립 참조 코퍼스 — KPI-1·5 정답 초안의 출처를 엔진 밖으로 옮겼다

정답을 엔진이 읽는 파일에서 뽑으면 대조가 성립하지 않는다. 2026-07-31 감사에서 KPI-1과 KPI-5 초안이 이 조건을 만족하지 못하는 것을 확인했다.

**KPI-1 — 맥락이 정답을 바꾸지 않았다.** `goal_ingredient_priors_v1` 기반 초안 100건의 서로 다른 정답 조합은 7개뿐이었고 사용된 성분은 11종이었다. 정답이 목표 하나만의 함수라서 `복용약 warfarin`, `임신 중`, `중증 신장질환`을 적어도 정답이 바뀌지 않았다. warfarin 사례 10건 중 1건은 정답에 omega3가 남아 있는데, 엔진의 `SAFETY-ANTICOAG-001` 은 그 조합을 배제한다. 즉 **엔진이 안전하게 행동할수록 점수가 깎이는** 정답지였다. 유효 표본도 100이 아니라 7이다.

**KPI-5 — 엔진 자신의 규칙 파일이 정답이었다.** 초안이 `data/rules/safety_rules.json` 의 등록값을 그대로 물어보는 형태였다(`SAFETY-ANTICOAG-001 의 severity 참조값은?`). 엔진은 정의상 100%를 맞힌다. `assert_source_is_independent` 는 출처 문자열만 보므로 이 경우를 잡지 못한다.

**대체 출처.** `건강상담 Checker` 는 프로젝트 오너가 저술해 이 엔진보다 먼저 출판한 약사 상담 저작물이다. 근거층이 엔진과 겹치지 않는다 — 엔진 지식베이스 19건은 NIH ODS·NCCIH·CDC·ADA·PubMed·master_context뿐이고 저장소 전체에서 이 저작물 인용은 0건이다. 저작권자가 오너와 동일해 연구 내부 이용에 제약이 없다.

| 항목 | 값 |
|---|---|
| 추출기 | `scripts/build_health_checker_reference_extract.py` |
| 추출물 | `data/knowledge/external/health_checker_reference_extract_v1.json` (원본 SHA-256 기록) |
| 초안 생성기 | `src/wellnessbox_rnd/evals/reference_corpus_drafters.py` |
| 초안 파일 | `data/original_plan/kpi/drafts/kpi{1,5}_reference_corpus_cases_v1.json` |
| 매핑된 성분 | 25종 → 카탈로그 12키 전부 커버 |
| 판정 사례 | 138건 (영역·판정 상태별 권장 성분, 쪽수 인용) |
| 약물 맥락 | 7종 (원문 약물표의 고갈·흡수간섭 근거) |

**정답이 맥락을 따라 움직인다.** 판정 상태의 권장 성분에 그 사례가 명시한 약물의 고갈 성분을 더한다. Furosemide 사례는 원문 권장 `probiotics, zinc` 에 루프이뇨제가 고갈시키는 `calcium_citrate, magnesium_glycinate, vitamin_b_complex` 가 붙는다(p236). Levothyroxine은 흡수 간섭형이라 배제하지 않고 원문 상담 문구인 4시간 간격 안내를 근거에 남긴다(p239). 그 결과 100건의 서로 다른 정답 조합이 7개에서 **67개**로 늘었다.

**남는 한계.** 원문 성분 234종 중 카탈로그에 없는 209종은 채점에서 빠지고 `out_of_catalog_nutrients` 로만 기록된다. 이 목록이 카탈로그 확장 우선순위다. 소아·임신 영역과 성인 약물이 기계적으로 교차된 사례는 `검토자 확인 필요` 로 표시하며, 임상적 타당성 판단은 검토자 몫으로 남긴다.

## KPI-3·4 초안도 같은 감사에서 탈락했다 (2026-07-31)

`NEXT_STEPS.md`가 남긴 3번 항목, "KPI-3·4 초안도 같은 기준으로 출처 독립성을 감사한다"를 수행한 결과다. **두 지표 모두 사람이 확정하기 전에 초안을 교체해야 한다.** 지금 상태로 400건을 확정하면 KPI-3·4에 들인 200건의 사람 시간이 봉인 단계에서 버려진다.

### KPI-3 — 엔진 자신의 정책 파일이 정답이다

KPI-5가 탈락한 것과 같은 구조다.

| 확인 항목 | 값 |
|---|---|
| 정책 파일 | `data/original_plan/closed_loop_next_action_policy_v1.json` (규칙 9개) |
| 엔진이 읽는 곳 | `src/wellnessbox_rnd/interim/next_action.py:79` — **같은 파일** |
| 초안 정답 | 각 규칙의 `action` 값 |
| 고유 정답 | **9개** (규칙 수와 정확히 같음, 정책 action 집합의 부분집합) |
| 문항 생성 방식 | `_describe_condition(rule["when"])` — **그 규칙 자신의 발동 조건**을 관찰 신호로 서술 |

각 사례는 특정 규칙이 발동하도록 그 규칙의 `when` 절로 만들어졌고, 정답은 그 규칙의 `action`이다. 엔진은 같은 파일을 위에서부터 읽어 처음 일치한 규칙을 적용한다. **정확도가 구조적으로 100%에 수렴한다.** 실제로 기존 평가 근거 `op071_op080_closed_loop_next_action_policy_v1.json`이 130/130, 100%를 기록하고 있는데, 이 100%는 성능이 아니라 자기 참조의 지문으로 읽어야 한다.

유효 표본도 100이 아니라 **9**다. 프로필 문구(`40대 수면 목표` 등 12종)는 정답에 영향을 주지 않아 표본을 늘리지 못한다. KPI-1 초안이 "맥락이 정답을 바꾸지 않았다"로 탈락한 것과 같은 결함이다.

### KPI-4 — 최소 표본을 문항 수에서 이미 못 채운다

| 확인 항목 | 값 |
|---|---|
| 계약 요건 | 문항 100개 (`minimum_sample.unit = question`) |
| 실제 고유 문항 | **57개** — 템플릿 5종 × 성분 순환에서 충돌 |
| 고유 정답 | **5개** — 템플릿에 하드코딩된 판정 기준이 20건씩 반복 |

계약은 "사전에 라벨링한 정답과 적절성 판정 함수"를 요구하는데, 지금 `draft_answer`는 문항별 정답이 아니라 5종짜리 일반 채점 기준 문구다. 문항 100개 요건도 57개로 미달이라 봉인해도 `meets_minimum_sample`을 만족하지 못한다.

### 부수 확인 — `draft_source` 라벨이 실제 출처와 다르다

KPI-3·4 워크벤치의 `draft_source`는 둘 다 `goal_ingredient_priors_v1+ingredient_catalog`로 기록돼 있으나, 실제 출처는 KPI-3이 `closed_loop_next_action_policy_v1.json`, KPI-4가 드래프터에 하드코딩된 템플릿이다. `assert_source_is_independent`는 출처 **문자열만** 보므로 이 라벨 오류가 있으면 독립성 검사가 실제 출처를 보지 못한다. KPI-5 때 확인된 한계와 같은 지점이며, 교체 시 라벨도 실제 출처로 맞춘다.

### 교체 결과 — 두 지표를 다르게 처리했다

같은 감사에서 탈락했지만 탈락 사유가 달라서 처방도 다르다. 생성기는 `src/wellnessbox_rnd/evals/blinded_drafters.py`, 실행기는 `scripts/build_blinded_answer_key_drafts.py` 다.

**KPI-4 — 참조 코퍼스로 교체했다.** KPI-1·5와 같은 방식이다. 문항과 정답을 모두 `health_checker_reference_extract_v1` 에서 뽑고 쪽수를 함께 남긴다. 정답은 그 목표의 권장 성분에 사례가 요구하는 상담 의무(`separate_dosing`, `supplement_depleted_nutrient`, `advise_professional_consult`)를 더한 집합이다.

| 항목 | 종전 | 교체 후 |
|---|---|---|
| 고유 문항 | 57 (100 미달) | **100** |
| 고유 정답 | 5 | **75** |
| 근거 | 하드코딩 템플릿 | 원문 쪽수 인용 |

약물 맥락이 붙은 사례는 정답이 실제로 달라진다. Levothyroxine 사례에는 `separate_dosing` 이, 고갈형 약물 사례에는 그 고갈 성분이 붙는다. 정답이 맥락을 따라 움직이므로 대조가 의미를 가진다.

다만 측정 대상 상담 모듈은 OpenAI 계열이고 현재 답 초안 작성 표시는 Codex다. 같은 계열 자기채점 방지 조건 때문에 현재 Codex 답을 그대로 봉인하지 않는다. Claude 같은 비-OpenAI 계열 AI의 블라인드 응답을 `import-primary-ai-draft`로 1차 초안에 넣고, 새 블라인드 Codex 작업이 2차 의견을 낸다.

**KPI-3 — 저장소 생성기는 정답을 만들지 않았다.** "다음 수행 작업"은 이 시스템이 정의한 운영 행동 공간이고, 이를 다루는 엔진 밖 저작물이 없다. 그래서 저장소 생성기는 **상황 100건과 미정 표시만 만들었다.**

- 상황은 참조 코퍼스의 목표·복용 성분·약물 맥락에 임상 현장의 관찰 신호 12종을 교차해 만든다. 정책 파일의 `when` 절 문법을 쓰지 않는다.
- 초기 `draft_answer`는 `미정_검토자가_판단` 하나뿐이며 실제 정답으로 세지 않는다.
- 최소 검토 경로에서는 첫 번째 AI가 블라인드 패킷만 보고 9개 행동 중 하나를 제안한다. `import-primary-ai-draft`가 완전성·패킷 SHA-256·엔진 미참조·블라인딩 경로를 검사해 1차 초안으로 가져온다.
- 다른 제공자 계열 AI가 같은 블라인드 패킷을 다시 판단한다. 사람은 두 AI의 불일치·위험 플래그·합의 표본을 상세 검토하고, 남은 합의안을 명시적으로 일괄 승인한다.
- 실제 AI 답안과 사람 결정은 아직 만들지 않았다. 현재 세션은 엔진 정책을 이미 보았으므로 블라인드 AI 역할을 대신하지 않는다.

행동 어휘 9종은 검토자에게 알려 준다. 어휘를 아는 것과 어느 상황에 어느 행동이 맞는지를 아는 것은 다르며, 측정 대상은 후자다.

**블라인딩은 검사 가능한 조건으로 남겼다.** `BLINDED_FROM` 에 이 초안이 읽지 않아야 할 엔진 파일 3종을 적고, `tests/test_blinded_drafters.py` 가 생성기 본문에 그 경로가 등장하지 않는지, KPI-3 문항에 행동 이름이나 정책 트리거 키가 새지 않는지 검사한다. 문서상 주장이 아니라 테스트다.

### KPI-4는 상담 모델과 초안 AI의 제공자 계열도 분리한다

"연구를 돌린 AI와 정답을 만든 AI를 분리하면 자기채점이 사라진다"는 설계는 옳지만, 여기서는 지표마다 효력이 다르다.

- **모든 KPI**에서 먼저 보는 것은 데이터 경로다. 초안 생성 모듈이 engine_logic 9개를 실제로 읽지 않았는지 AST로 검사하고, 모든 사례의 `blinded_from`에 9개가 빠짐없이 기록됐는지 다시 검사한다.
- **봉인할 때** 초안 작성 주체와 측정 대상의 고유 ID가 같으면 거부한다.
- **KPI-4 봉인**은 상담 모델 제공자 계열을 별도로 요구한다. 초안 작성 AI와 상담 모델이 같은 제공자 계열이면 자기채점 위험이 남으므로 봉인을 거부한다.
- **AI 합의로 상세 사람 검토를 줄일 때**는 1차와 2차 AI가 다른 제공자 계열이어야 한다. 같은 계열의 상관 오류를 합의로 잘못 세는 위험을 줄이기 위한 조건이다. 그래도 독립성을 최종 증명하는 것은 블라인드 패킷 SHA-256, 엔진 입력·출력 차단, 사람 승인, 선봉인 순서다.

### 남는 한계

KPI-3 상황을 만든 세션은 감사 과정에서 정책 파일을 이미 읽었다. 그래서 이 모듈의 블라인딩은 "정답을 그 파일에서 뽑지 않았다"까지는 테스트로 보장하지만, 상황 선택이 엔진에 유리하게 치우치지 않았다는 것까지는 보장하지 못한다. 상황 선택의 편향은 검토자가 반려로 걸러야 하며, 반려율도 기록에 남는다.

무결성 감사에도 한계가 있다.

- 감사기는 초안 생성 모듈에서 실제 파일 읽기 호출로 이어지는 경로를 AST로 찾는다. 하지만 같은 모듈이 엔진 파일을 읽었다면 그 파일을 상황 열거에만 썼는지, 정답을 만드는 데 썼는지까지는 구분하지 못한다. 그래서 KPI-3 정답 경로는 정책 파일을 읽지 않도록 분리했고 조용한 예외를 두지 않았다.
- 외부 AI가 실제로 패킷만 보았는지는 저장소에서 직접 관찰할 수 없다. 가져오기 도구는 응답의 `engine_output_consulted: false`, 전체 `blinded_from`, 패킷 SHA-256을 검사하지만 외부 실행자의 진술에 의존한다. `adaptive_answer_key_review.py`의 AST 통과는 가져오기 코드의 독립성만 뜻한다. 외부 AI 실행 화면이나 작업 영수증은 별도 운영 증빙으로 보존해야 한다.
- 제공자 계열은 실행 주체 문자열에서 추정한다. 알 수 없는 문자열은 독립 제공자로 인정하지 않고 차단하지만, 이 휴리스틱은 제공자 독립성을 암호학적으로 증명하지 않는다.
- `MIN_SECONDS_PER_DECISION = 1.0`초는 사람이 사례를 충분히 검토했다는 과학적 기준이 아니다. 100건을 3.7초에 자동수락한 기록을 걸러내기 위한 임의의 보수적 하한이다.
- 원문 성분 234종 중 209종은 엔진 성분 카탈로그 12종에 없다. 이 209종은 `out_of_catalog_nutrients`에 남지만 KPI 채점 대상에서는 빠진다.

같은 참조 코퍼스를 쓰더라도 지표별 실제 생성 모듈을 찾을 수 있어야 한다. 현재 질문·초안 생성 경로는 KPI-1·5가 `health_checker_reference_extract_v1@reference_corpus_drafters`, KPI-4가 `health_checker_reference_extract_v1@blinded_drafters`다. KPI-3·4에서 외부 1차 AI 응답을 가져오면 답의 경로는 `blind_primary_ai_response_v1@adaptive_answer_key_review`로 바뀐다. 감사기는 `(indicator_id, draft_source)`를 사용해 기록된 답 경로를 검사한다.

## 추가 개선안

**1. KPI-2 표본을 지금부터 쌓는다.** 100명은 하루에 모이지 않는다. 서비스 사용자에게 복용 전 PRO를 받고 2주 후 후속 PRO를 받는 흐름을 지금 서비스에 붙여 두면, 3차년도 측정 시점에 표본이 이미 있다. 이게 이번 연구에서 일정상 가장 앞당겨야 할 항목이다.

**2. 블라인드 AI 응답과 사람 최종 결정을 먼저 끝낸다.** KPI-1·3·4·5는 각각 100개가 필요하다. 두 AI의 독립 답을 먼저 준비하면 사람은 최소 20건의 상세 판단과 지표별 일괄 승인부터 시작할 수 있다. 표본 오류가 나오면 20건 또는 전수 검토로 확대한다. 3차년도 면허 취득 후에는 자격 정책에 맞춰 재확인·재봉인한다.

**3. 합성 데이터 검증을 논문 수준으로 남긴다.** 대안 2의 "99% 유사성"을 주장하려면 근거가 필요하다. 문헌에서 가져온 분포와 생성 자료의 분포를 통계적으로 비교한 보고서를 남기면, 학습 데이터의 타당성 근거가 되고 별도 성과로도 쓸 수 있다. 이미 `synthetic_validity_audit.py`가 있으므로 확장하면 된다. 단, 이 보고서로 KPI-2를 대신하지는 않는다.

**4. KOLAS 시험은 연구 완료 뒤에 잡는다.** 연구 진행을 이것 때문에 미루지 않는다. 내부 측정으로 연구를 끝내고, 결과가 목표치를 넘긴 것을 확인한 뒤 시험을 의뢰한다. 접수·수행에 시간이 걸리므로 완료 시점에서 역산해 예산과 일정만 미리 잡아 두면 된다.

**5. KPI-6은 집계 체계부터 만든다.** "최근 12개월 누적"이므로 측정 시점에 12개월치가 있어야 한다. 이상반응 보고 경로와 집계 스크립트를 지금 붙여 두면 3차년도에 자동으로 채워진다.

## 이후 세션의 AI가 지켜야 할 것

이 저장소에서 작업하는 AI 세션은 아래를 전제로 판단한다.

1. **내부 측정은 연구 기간의 정식 측정이다.** 산출물에 `measurement_environment: research_phase_internal_measurement`를 남긴다. 연구 완료 후 공인시험기관 검증은 별도 단계이며, 그 전에 연구를 멈추지 않는다.
2. **정답은 독립 AI 2개 → 사람의 최소 상세 검토와 최종 승인 → 봉인 → 엔진 순서.** 사람이 원하면 100건 전수 상세 검토로 돌아갈 수 있다. `scripts/run_answer_key_workbench.py`를 쓰고 상세 검토와 일괄 승인을 섞어 기록하지 않는다.
3. **합성 자료로 사람 결정을 건너뛰지 않는다.** 사람은 모든 불일치·위험·합의 표본을 상세 판단하고 나머지 합의안을 직접 일괄 승인하거나 거부한다. KPI-2·6의 실측은 합성으로 채우지 않는다.
4. **분포 유사도로 실제 효과를 주장하지 않는다.** 두 진술은 다른 것이다.
5. **2차년도 산출물을 "약사"로 표기하지 않는다.** 예비 약사다. `REVIEWER_QUALIFICATION_POLICY.md`를 따른다.
6. **연구 기간 측정은 내부 측정으로 진행한다.** KOLAS 시험은 연구를 마친 뒤 받는 최종 검증이며, 연구 단계의 차단 조건이 아니다. 다만 내부 측정값을 공인 시험 결과로 표기하지는 않는다.

기계가 읽을 형태는 `data/original_plan/contracts/kpi_measurement_contract_v1.json`에 있다. 지표별 `synthetic_allowed`, `must_precede_engine_output`, `internal_only_possible`, `minimum_sample`을 그 파일에서 확인한다.

## 최종 영수증이 옆 저장소 커밋에 묶여 있다

2026-07-31 확인 사항이다. `final_validation_receipt_v1.json` 과 `independent_final_review_receipt_v1.json` 은 `source_commit` 을 두 저장소의 현재 HEAD 집합과 대조한다. 영수증은 `f545b83`(wellnessbox, 2026-07-24)에 서명돼 있는데 그 저장소가 `b32116e`(2026-07-31)로 3커밋 진행하면서 검증이 깨졌다.

그 결과 최종 감사가 `validation_receipt_missing_or_invalid` 와 `independent_review_receipt_missing_or_invalid` 두 항목으로 `BLOCKED` 다.

**이건 R&D 저장소의 문제가 아니다.** 프로덕션 저장소를 건드리면 영수증이 자동으로 무효가 되는 구조다. 두 가지를 정해야 한다.

1. 영수증은 H-006에서 오너가 서명해 발급하는 것이므로 자동 재발급하지 않는다. 사람 세션에서 다시 발급한다.
2. 프로덕션 저장소가 계속 움직이는 동안에는 발급해도 곧 무효가 된다. 그래서 **H-006은 프로덕션 저장소 작업이 멈춘 뒤에 수행하거나**, 영수증이 프로덕션 커밋에 묶이지 않도록 고정 방식을 바꿔야 한다.

후자를 고른다면 `_validation_receipt_valid` 의 `source_commit` 대조 범위를 R&D 저장소로 좁히는 변경이 필요하다. 이건 감사 계약을 바꾸는 일이므로 사람이 결정한다.
